Why this matters

ShopSphere's Product table in its primary database is optimized for exactly one access pattern well: fetch a product (or a small set of products) by a known key — productId, or sellerId for a seller's own catalog. It is fundamentally the wrong tool for "find every product whose name, description, or category loosely matches wireless bluetooth headphones, ranked by relevance, filterable by price range and brand, in under 100ms, across 20 million products." Building that on the primary database with LIKE '%...%' queries doesn't just perform badly — it's solving a different problem than the database engine was designed to solve, using an index structure (a B-tree, ordered for range/equality lookups on a column) that has no way to represent "this word appears somewhere in this text." A dedicated search index inverts the entire problem — from "for this row, what words does it contain" to "for this word, which rows contain it" — which is precisely what makes free-text and faceted search fast at scale. Understanding why that inversion works, how to keep it in sync with a source-of-truth database without coupling every write path to search infrastructure, and the basic mechanics of relevance ranking and recommendations, is what separates "I called Elasticsearch" from actually knowing what problem it solves and where its consistency model can bite you.

1. Why SQL LIKE Doesn't Scale for Product Search

ShopSphere's Product table looks roughly like Product(id, sellerId, name, description, category, price, stockQuantity). A relational database's standard indexes — B-tree indexes on columns like id, sellerId, or price — support fast equality and range lookups (WHERE sellerId = ?, WHERE price BETWEEN ? AND ?) because a B-tree stores keys in sorted order, so the engine can binary-search down to the right leaf page in O(log n) disk/page accesses. That structure has nothing useful to offer a query like WHERE name LIKE '%wireless%', because the substring you're searching for can start anywhere inside the text — there is no sorted position for "contains this substring somewhere in the middle" the way there is for "equals this value" or "falls in this range."

Concretely, LIKE '%wireless%' (a leading-wildcard pattern) cannot use a B-tree index at all — the database has no choice but to fall back to a full table scan, reading every row and running a string-search check against each one's name/description. This is O(n) in the number of rows, per query, with a non-trivial per-row string-matching cost on top. It gets worse the moment real search requirements show up:

  • Multi-word, ranked queries. A customer searching "wireless bluetooth headphones" doesn't want an exact-substring match — they want products that mention any subset of those words, ranked by how well they match, with a product mentioning all three terms prominently in its title ranked above one that mentions "wireless" once in a buried description field. SQL has no native notion of "relevance rank" between a query and a text column; you'd be building tokenization, scoring, and ranking logic yourself, on top of a full scan, on every request.
  • Typo tolerance and stemming. "Headphone" should match "headphones"; "blutooth" (a typo) should still surface bluetooth products. SQL string matching is exact-substring by construction — there is no built-in notion of edit distance, word stems, or synonyms.
  • Faceted filtering combined with free text. "Wireless headphones, under $50, brand X, in stock, 4+ stars" needs the free-text relevance match and several structured filters evaluated together, then aggregated into facet counts ("Brand: Sony (142), Bose (88)...") for the UI — a fundamentally different query shape than anything a B-tree-backed row store is built to aggregate quickly across millions of rows on every request.
This isn't "SQL is slow" — it's the wrong index structure for the problem

A relational database is not inherently bad at search — it's that LIKE '%term%' asks it to solve a text-retrieval problem using an index designed for sorted-key lookups, which forces a full scan every time. Postgres's own full-text search extension (tsvector/GIN index) is actually a small-scale inverted index bolted onto a relational engine, which tells you something: even the answer within SQL-land is to build the same structure a dedicated search engine builds natively, just with less scale, less relevance tuning, and less operational tooling around it than a system purpose-built for exactly this.

2. The Inverted Index: Why Search Engines Are Fast

An inverted index flips the natural "document → words" relationship into "word → documents." Instead of storing, per product, a blob of text you'd have to scan, the index stores, per distinct term, the sorted list of product IDs (a postings list) whose text contains that term. Looking up "which products contain the word wireless" becomes a direct key lookup into a hash table or sorted structure keyed by the term "wireless" — no scan of product rows required at all.

2.1 Building the index: tokenization and analysis

Before anything is indexed, raw text goes through an analyzer pipeline that turns "Wireless Bluetooth Over-Ear Headphones — Noise Cancelling" into a normalized token stream: lowercase everything, split on whitespace/punctuation (tokenization), strip common low-information words like "the"/"and" (stop-word removal), and reduce words to a root form (stemming, e.g. "cancelling" → "cancel", "headphones" → "headphon") so that a query for "cancel noise" still matches a document that only contains "cancelling." The same analyzer runs over both indexed documents and incoming queries, which is exactly what makes "headphone" (singular, in a query) match "headphones" (plural, in a product title) — they stem to the same token.

// ShopSphere product, before analysis
Product(id="prod-8841", name="Wireless Bluetooth Over-Ear Headphones",
        description="Noise cancelling, 30-hour battery")

// after tokenize -> lowercase -> stop-word removal -> stemming
tokens = ["wireless", "bluetooth", "over", "ear", "headphon",
          "noise", "cancel", "30", "hour", "batteri"]

// inverted index entries this document contributes to (postings list per term)
"wireless"  -> [prod-8841, prod-1092, prod-7723, ...]
"bluetooth" -> [prod-8841, prod-2201, ...]
"headphon"  -> [prod-8841, prod-1092, prod-9042, ...]
"cancel"    -> [prod-8841, prod-3390, ...]

2.2 Answering a query against the index

A search for "wireless headphones" is analyzed the same way into ["wireless", "headphon"], and the engine looks up the postings lists for each term and combines them — an intersection for "must contain all these terms," a union with per-term scoring for "should contain, rank higher if more terms match." Because each postings list is already the exact set of matching document IDs (no scan needed to discover them), the cost of the lookup is roughly proportional to the size of the postings lists involved, not the total number of products in the catalog — the difference between "scan 20 million rows" and "read two short lists and intersect them" is the entire reason this is fast.

Query: "wireless headphones"
  -> analyzed tokens: ["wireless", "headphon"]
  -> postings["wireless"]  = {8841, 1092, 7723, ...}
  -> postings["headphon"]  = {8841, 1092, 9042, ...}
  -> candidates (union, scored by how many/how well terms match) = {8841, 1092, 7723, 9042, ...}
  -> rank candidates by relevance score (section 4) -> return top N

2.3 Faceted search as aggregation over the same index

Facets ("Brand: Sony (142), Bose (88)", "Price: $0-25 (310), $25-50 (204)") are computed by running an aggregation over the same candidate set the query already matched — grouping by a structured field (brand, a price bucket) and counting, the same conceptual operation as a SQL GROUP BY COUNT(*), except it's computed over the inverted-index-derived candidate set in memory rather than re-scanning a row store, and it's computed on every request against a live, filtered result set rather than a precomputed report.

3. Keeping the Search Index in Sync With the Product Database

The inverted index lives in a completely separate system — Elasticsearch or OpenSearch, not the relational database that owns Product as source of truth. That split is deliberate (a relational engine and a search engine are optimized for genuinely different access patterns), but it creates a real problem: every Product insert, price change, or stock update in catalog-service's database now needs to eventually show up in the search index too, or search results go stale — a delisted product still appears in results, or a price drop doesn't show up in a "under $50" facet filter for a while.

3.1 Dual-write: simple, and broken under failure

The naive approach is a dual write: catalog-service's update handler writes to the Product table, then immediately calls Elasticsearch's index API to write the same change there, in the same request:

// naive dual-write - looks fine, is NOT safe against partial failure
@Transactional
public void updateProduct(Product product) {
    productRepository.save(product);              // write 1: relational DB
    searchIndexClient.index("products", product);  // write 2: Elasticsearch
    // if the process crashes, or the network call to ES times out,
    // between these two lines -> DB and search index have now diverged,
    // silently, with no record that a divergence happened
}

This fails because the two writes are against two entirely separate systems with no shared transaction — there is no way to atomically commit "update the row" and "update the index" together. If the service crashes after the DB commit but before the ES call succeeds (or the ES call throws, times out, or the service is killed mid-request), the database has the new price but the search index still has the old one, permanently, with nothing anywhere recording that this product needs to be re-synced. Under any real production failure rate (network blips, ES cluster hiccups, deploys restarting pods mid-request), this drift accumulates continuously and silently.

3.2 Outbox pattern: making the sync durable

The fix that keeps the durability guarantee is the same transactional outbox pattern used for reliably publishing domain events (see the flash-sale checkout flow for the same pattern applied to OrderPlaced): instead of calling the search index directly inside the request, catalog-service writes an outbox row (ProductChanged, with the product id and change type) into its own database, in the exact same local transaction as the Product update itself. Because both writes are against the same database, they commit atomically — either both happen, or neither does, with no window where one succeeds and the other silently doesn't.

@Transactional
public void updateProduct(Product product) {
    productRepository.save(product);
    outboxRepository.save(new OutboxEvent(
        "ProductChanged", product.getId(), toJson(product)));
    // both inserts are in ONE local DB transaction - atomic, all-or-nothing
}

A separate poller or CDC process (section 3.3) reads unpublished outbox rows and pushes them into the search index asynchronously, retrying on failure until it succeeds, then marks the row processed. If the search-index write fails, the outbox row simply stays unprocessed and gets retried — nothing is lost, because the durable record of "this product changed and needs re-indexing" survived in the same transaction as the change itself, independent of whether Elasticsearch was reachable at that exact moment.

3.3 Change Data Capture (CDC): syncing without touching application code at all

CDC takes this a step further by not requiring catalog-service to write an outbox row explicitly at all. A CDC tool (Debezium is the standard choice) tails the database's own replication log — the same write-ahead log (WAL in Postgres, binlog in MySQL) the database already uses for crash recovery and replica sync — and streams every row-level insert/update/delete as an event, without the application ever having to know CDC exists. This has a strong advantage over an application-level outbox: it's impossible for a code path to "forget" to write the outbox row (a bug, a new endpoint someone added without wiring in the sync logic), because CDC reads what actually changed in storage, not what the application remembered to announce.

3.4 The consistency trade-off: eventual, not immediate

Both the outbox and CDC approaches share the same fundamental property: the search index converges to match the database eventually, not instantly, and not within any transaction that also touches the database. There is an unavoidable propagation delay — typically milliseconds to low seconds in a healthy system, but unbounded under a backlog (a Kafka consumer lag spike, an Elasticsearch cluster under load rejecting writes) — during which a query against search can return a result that no longer matches the current database state.

Why "eventual" is an acceptable trade-off here specifically

This asymmetry is exactly why search is a good fit for eventual consistency in a way that, say, decrementing Inventory.availableQty during checkout is not: a stale search result showing a product's old price for a few hundred milliseconds is a minor UX inconsistency the checkout flow itself will correct (the actual charge always reads current price from the source-of-truth Product/Inventory tables, never from the search index), whereas a stale inventory count during a flash sale can directly cause overselling — real money and real fulfillment failures. Search indexes are a read-optimized, secondary, derived view; nothing should ever treat them as the authoritative source for a price, a stock count, or anything a financial transaction depends on.

4. Relevance Ranking: TF-IDF and BM25

Once a query matches a candidate set of products (section 2.2), they still need to be ranked — "wireless bluetooth headphones" should surface a product titled exactly that above one that merely mentions "wireless" once in a warranty disclaimer. This is a fundamentally different problem from a SQL filter, which only ever answers true/false per row with no notion of "how well" a row matches.

4.1 TF-IDF: term frequency, inverse document frequency

TF-IDF scores a term's importance to a specific document by combining two counteracting signals:

  • Term Frequency (TF) — how many times the term appears in this document, normalized by document length. A product description that says "wireless" three times is, all else equal, more about wireless-ness than one that says it once.
  • Inverse Document Frequency (IDF) — a weight that penalizes terms that appear in almost every document in the catalog, and rewards terms that are rare/distinctive. In a headphones catalog, "headphones" itself might appear in nearly every listing (low IDF — not very discriminating between products), while "noise-cancelling" appears in only a subset (higher IDF — a match on it is more informative about relevance).

The product of the two, summed across all query terms, is the TF-IDF score: a document scores highly when it repeats the query's rarer, more distinctive terms often — exactly the intuition "this document is unusually, specifically about what you searched for," rather than just "this document contains common words that happen to be in your query too."

4.2 BM25: the practical improvement over raw TF-IDF that Elasticsearch actually uses

BM25 (the default scoring algorithm in both Elasticsearch and OpenSearch) refines TF-IDF with two corrections that make it behave better in practice:

  • Term frequency saturation. Raw TF-IDF lets term frequency contribute linearly and unboundedly — a description that repeats "wireless" fifty times (whether legitimately or via keyword-stuffing) would score proportionally higher than one that says it three times, which isn't actually more relevant past a point. BM25 applies a saturating function so that additional repetitions matter less and less, capping the benefit of just repeating a word many times.
  • Document length normalization. A longer product description naturally contains more words and thus more chances to match query terms by sheer volume, independent of actual relevance. BM25 explicitly normalizes against the average document length in the catalog, so a short, precise title match isn't unfairly outranked by a long description that happens to mention the term once amid a lot of unrelated text.

In practice a real ShopSphere search request combines both in one query: BM25 scores the free-text relevance of "wireless bluetooth headphones" against product titles/descriptions, while structured filters (category, price range, in-stock) are applied as hard boolean constraints that don't affect the relevance score at all — a product either passes the filter or is excluded outright, but among the ones that pass, BM25 decides the order.

5. Recommendation Systems: The Basics

Search answers "find me things matching this explicit query." Recommendations answer a different question: "given what I know about this customer (or this product), what else should they see, without them typing anything?" — the "customers who bought this also bought" module on a ShopSphere product page, or a personalized homepage feed. The two dominant approaches differ in what signal they mine.

5.1 Collaborative filtering: mining behavior, not content

Collaborative filtering recommends based purely on patterns in behavior across many customers — it never looks at what a product actually is, only at who bought/viewed/rated what. The core idea behind "customers who bought this also bought": build a co-occurrence signal from ShopSphere's own Order/OrderItem history — for every pair of products that show up together in the same customer's order history with unusual frequency (more often than chance would predict), record that as an association.

-- Simplified co-occurrence mining from ShopSphere's own order history
SELECT oi1.productId AS product_a, oi2.productId AS product_b, COUNT(*) AS co_purchase_count
FROM order_item oi1
JOIN order_item oi2 ON oi1.orderId = oi2.orderId AND oi1.productId <> oi2.productId
GROUP BY oi1.productId, oi2.productId
ORDER BY co_purchase_count DESC;
-- e.g. (prod-8841 wireless headphones, prod-9042 charging case) co-purchased 3,400 times
--       -> "customers who bought this also bought" surfaces prod-9042 on prod-8841's page

Two flavors exist, both built on the same underlying idea of a customer × product interaction matrix (rows = customers, columns = products, cells = purchased/rated/viewed):

  • Item-based ("customers who bought this also bought X") — find products that co-occur frequently with the product currently being viewed, across all customers' histories. This is what powers a product-detail-page recommendation module, and it's what the query above builds.
  • User-based ("customers similar to you bought X") — find other customers whose purchase history overlaps heavily with this customer's, then recommend what those similar customers bought that this customer hasn't. This powers a personalized homepage feed rather than a single product page.

The defining property of collaborative filtering is that it needs zero knowledge of product content — it works purely off co-occurrence patterns in behavioral data, which means it can surface genuinely surprising, non-obvious associations (a phone case and a specific brand of screen protector, discovered purely because many customers happen to buy both) that no content-based rule would ever have predicted.

5.2 Content-based filtering: mining product attributes

Content-based filtering instead recommends based on attributes of the products themselves — category, brand, price range, description text, tags — matched against a profile of what a specific customer has shown interest in. If a customer has browsed and purchased several items in ShopSphere's "wireless audio" category from budget-friendly brands, a content-based recommender surfaces other wireless-audio products in a similar price band, purely by comparing product attributes/description similarity (often using the same text-vectorization ideas as TF-IDF from section 4, treating each product's description as a vector and recommending nearby vectors) — with no need for any other customer's purchase history at all.

Most real systems, including large e-commerce platforms, blend both (a hybrid approach) precisely because their weaknesses are complementary — collaborative filtering supplies the strong behavioral signal once enough data exists, content-based filtering fills the gap for anything too new to have that signal yet.

5.3 The cold-start problem

Both approaches share a structural weakness rooted in exactly what data they depend on: they need a history that, for something genuinely new, doesn't exist yet.

  • New product cold start. A seller just listed a brand-new product on ShopSphere. Collaborative filtering has zero co-purchase data for it — it has never appeared in any order, so it cannot be recommended via "bought together" logic no matter how well it would actually sell, and it can't yet be a target of any "customers who bought this also bought" pairing either. The practical mitigation is to lean on content-based signals (category, description similarity to existing well-performing products) until enough purchase/view data accumulates, plus deliberately boosting new listings' visibility in generic browse/search placements (independent of personalization) so they get enough initial exposure to start generating the interaction data collaborative filtering needs.
  • New customer cold start. A customer who just created a ShopSphere account has no purchase history, no ratings, nothing for either a collaborative or a personalized content-based model to work from. The standard mitigations are non-personalized fallbacks — trending/best-selling products, category-level popularity — combined with any explicit signal you can get cheaply (an onboarding "what are you shopping for?" prompt) and a rapid shift to personalization as soon as even a small amount of behavior (a few page views, a first purchase) becomes available.
Cold start isn't a bug to eliminate — it's a permanent edge you design fallbacks for

Every catalog with churn has a constant trickle of new products and new customers, so cold start isn't a one-time bootstrapping problem you solve once and move past — it's a permanent segment of traffic that a production recommendation system must always have a defined, reasonable fallback for. The practical pattern is a tiered fallback: use collaborative filtering when there's enough interaction data, fall back to content-based similarity when there isn't, and fall back further to non-personalized popularity ranking when there's no signal at all — never simply show nothing or an empty recommendation module for a segment of traffic that lacks history.

Two design choices in this diagram are worth calling out explicitly. First, catalog-service never talks to Elasticsearch directly on the write path — it only ever writes to its own relational database, and has no idea CDC or a search index exist at all, which is exactly what keeps a search-infrastructure outage from ever being able to block a seller from updating their product's price or stock (section 3.4's consistency trade-off in architectural form: the write path stays fast and decoupled precisely because it doesn't wait on the read-optimized copy). Second, the recommendation co-occurrence table is precomputed, not calculated live on each product-page request — mining co-purchase patterns across the full order history is a batch aggregation, run periodically (hourly/daily) as a background job, with the product page simply doing a fast key lookup (productId → precomputed list of related productIds) at request time.

Concepts Worth Being Able to Explain From First Principles

Why can't a B-tree index make SQL LIKE '%wireless%' fast, and what structural property of an inverted index fixes that?
A B-tree index stores keys in sorted order so the engine can binary-search down to a value or a range in roughly log(n) steps — but that only works when you're looking for something anchored at a known position in the sort order, like an exact value or "greater than X." A leading-wildcard substring search has no such anchor: the substring can start anywhere inside the text, so there's no sorted position to binary-search toward, forcing a full scan and a per-row string check. An inverted index sidesteps this entirely by flipping the relationship being indexed: instead of indexing "for this document, what text does it contain" (which is what a B-tree on a text column would give you), it indexes "for this specific term, which document IDs contain it," stored as a direct-lookup postings list keyed by term. Looking up a word becomes an O(1)-ish key lookup into that structure rather than a scan over every document's text, because the index was built specifically around the query shape "find documents containing term X," not "sort documents by column value."
Walk through what happens end-to-end when a seller updates a product's price, using CDC, until it's reflected in search results.
Catalog-service runs a normal transactional UPDATE against the Product row in its own relational database — it does not call Elasticsearch, does not know CDC exists, and the request returns as soon as that single-database transaction commits. Separately, Debezium is tailing the database's write-ahead log (the same log the database already writes for crash recovery and replication), and it observes the committed row-level UPDATE as a change event, which it publishes onto a Kafka topic (product-changes) carrying the new row state. A dedicated search-index-sync consumer reads that Kafka event and issues an upsert against the corresponding document in Elasticsearch/OpenSearch, updating the indexed price field. From the moment the seller's update commits to the moment a customer's search reflects the new price, there's a real but typically small propagation delay — driven by WAL-tailing lag, Kafka throughput, and consumer processing time — during which a customer could still see the old price in search results even though the database itself already has the new one.
Why is dual-writing to the database and the search index in the same request unsafe, and how does the outbox pattern fix it without adding a distributed transaction?
A dual write is two independent writes against two different systems with no shared transaction coordinating them — the database commit and the Elasticsearch write can each succeed or fail independently, and any failure (a crash, a timeout, a network blip) landing between the two leaves them permanently diverged with no record anywhere that a divergence happened. The outbox pattern fixes this without needing a two-phase-commit-style distributed transaction across the database and Elasticsearch (which would be slow and operationally fragile, and which Elasticsearch doesn't even support as a transactional participant) by only ever writing to systems that share a single local transaction: the Product update and an outbox row describing that change go into the same relational database, in the same transaction, so they're atomic with each other by construction. The actual push to Elasticsearch happens afterward, asynchronously, off that outbox row — and if it fails, the outbox row simply remains unprocessed and gets retried, so nothing is silently lost; the durability guarantee comes from the outbox row surviving in the same transaction as the change, not from the downstream push succeeding on the first try.
What specifically does BM25 improve over raw TF-IDF, and why do those improvements matter for ranking real product listings?
Raw TF-IDF lets a document's term-frequency contribution grow linearly and without bound, so a description that repeats a keyword many times scores proportionally higher purely from repetition, independent of whether that repetition reflects genuine relevance — this is exploitable by keyword-stuffed listings and generally overweights raw repetition. BM25 applies a saturating function to term frequency so that each additional repetition contributes less and less to the score, capping the benefit of merely repeating a word many times. Separately, raw TF-IDF doesn't account for document length: a longer product description has more words and thus more opportunities to incidentally match query terms, which can make it outrank a short, precise title match purely due to length rather than actual relevance. BM25 explicitly normalizes term frequency against the corpus's average document length, correcting for that length bias. Both corrections matter directly for product search because real catalogs have wildly inconsistent description lengths and real sellers have real incentive to keyword-stuff, and BM25's corrections make the ranking robust to both.
Why can't collaborative filtering recommend a product that was listed five minutes ago, no matter how good a fit it might be for a given customer?
Collaborative filtering's entire signal is behavioral co-occurrence mined from actual customer interaction history — who bought, viewed, or rated what, alongside what else. A product with zero purchase or view history has no co-occurrence data with anything, by definition, because the signal the algorithm depends on is generated purely by accumulated customer behavior after listing, and a five-minute-old product hasn't had time to accumulate any. This isn't a tunable parameter or a bug that better data engineering fixes — it's a structural property of what the algorithm is: it can only ever surface patterns that already exist in historical interaction data, so anything without that history is invisible to it regardless of how well-matched it might actually be to a given customer. The practical fix is to lean on a fundamentally different signal (content-based similarity, using the product's own attributes rather than any behavioral history) until enough interaction data accumulates for collaborative filtering to have something to work with.
Why is it architecturally important that catalog-service's write path never talks to Elasticsearch directly, even though the search index does eventually need every product change?
If catalog-service called Elasticsearch synchronously as part of handling a seller's product update, the availability and latency of the transactional write path would become coupled to the availability and latency of a completely separate system with different scaling characteristics, different failure modes, and a different operational team's on-call rotation — an Elasticsearch cluster having a bad day (overloaded, mid-reindex, network-partitioned) would now be able to block sellers from updating their own prices and stock, which is a core write path with no legitimate reason to depend on a read-optimized secondary system succeeding. Routing the sync through CDC or an outbox instead means catalog-service's write path only ever depends on its own database committing, full stop — the search index update becomes a downstream, asynchronous, retryable concern with its own failure isolation, so a search-infrastructure outage degrades search relevance/freshness but never blocks the actual business-critical write.
Why does ShopSphere precompute the "customers who bought this also bought" table in a batch job rather than computing it live on every product-page load?
Computing genuine co-occurrence statistics requires scanning across a large fraction of the order history — joining OrderItem rows against each other to find which product pairs appear together unusually often — which is an aggregation over potentially the entire historical order dataset, not something that can be computed cheaply per individual page view without imposing a heavy, repeated cost on every single product-page load. Precomputing it periodically (hourly or daily, as a batch or streaming aggregation job) means that expensive aggregation work happens once per cycle regardless of how many customers view the resulting recommendations, and the product page itself only ever does a cheap, fast key lookup (productId to a short precomputed list of related productIds) at request time. The trade-off is explicit: the recommendation reflects order history as of the last batch run, not the literal current instant, which is an acceptable staleness window for a discovery feature in exactly the way section 3.4 argues eventual consistency is acceptable for search — nothing about a "customers who bought this also bought" suggestion needs to be transactionally fresh to the millisecond.
