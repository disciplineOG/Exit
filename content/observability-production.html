Observability & Production Readiness

Metrics Logs Traces Micrometer / Prometheus Spring Boot Actuator ELK Stack OpenTelemetry SLO / Error Budgets
Why this matters

A system with no observability doesn't fail less often — it just fails in the dark. Averages hide the exact latency spikes that make a checkout flow feel broken for 1% of users; a health check that only pings SELECT 1 against a database that's actually saturated with slow queries will happily keep routing traffic to a dying instance; and without a correlation ID threading through every log line, "why did this one request fail" turns into grepping five services' logs by timestamp and hoping the clocks agree. Understanding what each pillar of observability actually measures, and what it structurally cannot tell you, is what lets you build a system where a production incident is a ten-minute diagnosis instead of a two-hour guessing game.

1. The Three Pillars, and Why One Alone Is Never Enough

Observability is usually described as resting on three pillars — metrics, logs, and traces — and the reason it takes three, rather than one very good one, is that each pillar is a different projection of the same underlying reality (requests flowing through a system over time), and each projection deliberately throws away information the others keep, in exchange for being cheap and fast at what it does keep.

Metrics

A metric is a number that changes over time, aggregated across many events, sampled or recorded at regular intervals — "requests per second," "p99 latency over the last minute," "JVM heap used." Metrics answer "how is the system behaving in aggregate, and is it trending toward a problem?" They are extremely cheap to store (a time series is just a sequence of timestamp-value pairs, often compressed) and extremely cheap to query even over long time ranges, which is exactly what makes them suitable for dashboards and alerting rules that need to evaluate constantly. The cost is that aggregation is lossy by construction: once 10,000 individual request latencies have been folded into "p99 = 420ms," you cannot recover which specific request was slow, what its user ID was, or what request body it carried. A metric can tell you that something is wrong and roughly how much, but never which specific instance of the problem to go look at.

Logs

A log is a detailed, per-event record — a line (or structured record) emitted at a specific point in a specific request's execution, carrying whatever context the code chose to include: a stack trace, a user ID, a SQL query, an error message. Logs answer "what exactly happened during this one event?" They preserve the full detail metrics discard, at the cost of volume: a service handling a thousand requests a second, each logging a handful of lines, produces gigabytes of log data per hour, and both storing and searching that volume at scale (full-text search over billions of lines) is a real infrastructure cost, not a rounding error. Logs are also comparatively slow to query for aggregate questions — "what's my error rate over the last hour" is answerable from logs in principle, but it means scanning and counting across a huge volume of records, which is precisely the kind of question a metric already answers for a fraction of the cost.

Traces

A trace is the causal chain of work performed by one specific request as it moves across services — the mechanic covered in depth in microservice-patterns, where a trace ID and a tree of parent-child spans reconstruct which service called which, in what order, and how long each hop took. Traces answer "where, in the causal chain of this one request across N services, did the time go, or did the failure occur?" A trace waterfall is the one artifact that can show you that a checkout request's 800ms was actually 600ms of one downstream currency-conversion call, something no single service's own logs or metrics could show in isolation, because no single service has visibility into the other four services the request also touched.

The three pillars are not redundant, they're sequential in a typical investigation

A realistic production incident usually walks through all three in order: a metric-driven alert fires because p99 latency crossed a threshold (metrics tell you something is wrong and roughly when it started); you pull up a trace for a slow request from around that time to see which service in the chain accounted for most of the latency (traces tell you where); you then pivot to that specific service's logs, filtered by the trace ID from the slow trace, to see the actual exception, query, or condition that caused the slowness (logs tell you why). Each pillar narrows the search space for the next one. Trying to diagnose an incident from only one pillar means either drowning in undifferentiated log volume with no idea where to start looking, or having a metric that confirms something's wrong with no way to find a concrete example of it.

2. Metrics in Depth: Micrometer, Prometheus, and the Four Metric Types

Spring Boot applications instrument metrics through Micrometer, which acts as a facade in front of whichever metrics backend you actually use — Prometheus, Datadog, New Relic, CloudWatch — the same way SLF4J is a facade in front of a concrete logging implementation. This matters for the same reason any facade matters: your application code records "increment this counter" or "record this timing" against Micrometer's API, and swapping the backend is a dependency and configuration change, not a rewrite of instrumentation scattered across the codebase.

Micrometer exposes four fundamental metric types, and picking the right one for a given measurement is not a stylistic choice — each one is backed by different storage and supports different queries.

Counter

A monotonically increasing value — it only ever goes up (or resets to zero on restart), never down. Used for counting occurrences: total requests handled, total orders placed, total exceptions thrown. You never decrement a counter; if you need something that can go down, that's a Gauge. The reason counters are modeled as strictly increasing rather than "current count of X" is that increasing counters compose cleanly across a rate calculation — Prometheus's rate() function divides the increase in a counter over a time window by the window length to get "events per second," and that math only works cleanly if the underlying value never resets except on process restart (which Prometheus detects and handles as a special case).

Gauge

A value that can go up or down, representing a current state: active database connections in a pool, current queue depth, JVM heap used right now, number of in-flight requests. Unlike a counter, a gauge has no notion of a "rate" — you read its current value directly. Gauges are typically sampled by reference (Micrometer holds a reference to the current value and reads it at scrape time), not by push, which avoids the correctness problem of the value changing between when your code updates it and when it's reported.

Histogram

A histogram tracks the distribution of a set of observed values (most commonly latencies or sizes) by counting how many observations fell into each of a set of predefined buckets — for example, buckets at 10ms, 50ms, 100ms, 250ms, 500ms, 1s, and "everything above." Each bucket is actually a cumulative counter of "how many requests took less than or equal to this bucket's boundary" (this is the Prometheus convention, called a cumulative histogram, exposed as separate time series like http_request_duration_seconds_bucket{le="0.1"}, {le="0.5"}, and so on, plus a _sum and a _count).

Summary / Timer

A Summary computes quantiles (percentiles) directly on the client side at recording time and exposes those precomputed quantiles. Micrometer's Timer is the type you actually reach for in Spring Boot code to measure durations, and depending on configuration it can publish either histogram buckets, client-side percentiles, or both. The distinction that matters operationally is where the percentile math happens: a client-side Summary computes an accurate percentile for that one instance, but you structurally cannot average or combine percentiles computed on different instances into a correct fleet-wide percentile (averaging two p99s is not the fleet's p99). A histogram, by contrast, publishes raw bucket counts, and Prometheus can sum those bucket counts across every instance in the fleet before computing the percentile, giving you a mathematically valid fleet-wide p99. This is exactly why Prometheus-oriented setups favor histograms over client-computed summaries for anything you intend to aggregate across instances.

From buckets to percentiles, and why the average is lying to you

An average latency of 120ms sounds fine. But an average is exactly the statistic that hides a tail problem: if 990 requests out of 1000 take 50ms and 10 take 7 seconds, the average is still only around 120ms, yet 1% of your users are having a genuinely broken experience. Percentiles fix this by answering a different, more honest question: "what latency does the slowest N% of requests experience?" p50 (the median) tells you the typical case; p95 tells you what the slowest-1-in-20 requests experience; p99 tells you what the slowest 1-in-100 experience. Because a single slow dependency, a single garbage collection pause, or a single lock contention event tends to affect a small fraction of requests severely rather than all requests slightly, the tail percentiles are usually where real user-facing pain lives, and averages are close to blind to them.

Histogram buckets are what make computing an arbitrary percentile after the fact possible without having stored every individual latency value (which would be enormously expensive at scale). Given cumulative bucket counts — say 900 requests at or under 100ms, 990 at or under 500ms, and 1000 total — Prometheus's histogram_quantile() function finds which bucket boundary a given percentile falls between and linearly interpolates within that bucket to estimate the value. The precision of that estimate is bounded by how fine your bucket boundaries are near the values you actually care about — if your buckets jump from 100ms straight to 1s, a computed p95 that happens to fall in that range is only accurate to within that wide gap, which is why choosing bucket boundaries that cluster around your actual SLO thresholds (if your target is "p95 under 300ms," you want buckets at 100ms, 200ms, 300ms, 400ms, not just round powers of ten) matters in practice.

You cannot retroactively compute a percentile you didn't bucket for

If your histogram's buckets are 50ms, 200ms, 1000ms and nothing finer, you can get a reasonable estimate of p50 or p99 but a fairly poor estimate of p90 if the real p90 sits somewhere in that wide 200ms-to-1000ms gap — the interpolation has almost no data points to interpolate between. Because bucket boundaries have to be chosen ahead of time, at instrumentation time, changing your mind about what precision you need at the tail later means redeploying with new buckets and only getting accurate data going forward — you cannot recompute better precision from already-recorded, coarser buckets. This is the practical reason to default to somewhat generous bucket coverage around your expected latency range up front, rather than trimming buckets down to "just what today's dashboard needs."

3. Pull-Based Scraping vs Push-Based Metrics

Prometheus, the dominant open-source metrics backend paired with Micrometer, uses a pull model: each application exposes its current metric values on an HTTP endpoint (Spring Boot Actuator exposes this at /actuator/prometheus), and the Prometheus server itself is responsible for periodically sending an HTTP GET to that endpoint on every monitored instance — typically every 15 seconds — and recording whatever values it reads (called a "scrape"). This is the inverse of a push model (used by systems like StatsD or Graphite in their classic form), where each application actively sends its metrics out to a central collector on its own schedule.

The pull model has a specific, deliberate advantage in a dynamic, service-discovery-driven environment: Prometheus itself owns the list of "which targets should I be scraping," and that target list can be populated dynamically from the same service registry or orchestrator that already tracks live instances — Kubernetes service discovery, Consul, or a static file that's kept in sync with an autoscaling group. When a new instance comes up, Prometheus's service-discovery integration notices it and starts scraping it automatically; when an instance is torn down, Prometheus simply stops getting a successful response from that target and marks it down, without that instance needing to have known in advance where to push its data. This inverts naturally with how microservice-patterns already handles instance churn — the same registry information that tells a load balancer which instances are live is exactly the information a pull-based monitoring system needs to know which instances to scrape.

A push model, by contrast, requires every application instance to know the address of the central collector and to actively manage sending data to it, which means an application experiencing enough trouble that it can't even complete its own push (heavy GC pause, thread pool exhaustion) may fail to report the very metrics that would explain what's wrong, right when you need them most. A pull-based scrape failing (a scrape that times out or gets no response) is itself a meaningful, automatically captured signal — "this target is now unscrapable" — that a pure push model doesn't get for free.

Pull doesn't fit everything

The pull model assumes the monitoring system can always reach the target over the network and that the target's lifetime is long enough to be scraped on a normal interval. It breaks down for short-lived batch jobs that might finish and terminate in under 15 seconds — there may be no scrape window that catches them at all. Prometheus's answer for that case is the Pushgateway, an intermediary that short-lived jobs push their final metric values to, which Prometheus then scrapes as if it were the job itself — a deliberate, narrow exception to the pull model rather than a wholesale switch to push.

4. Spring Boot Actuator: Health, Metrics, and Why Load Balancers Care

Actuator is Spring Boot's built-in module for exposing operational information about a running application over HTTP, without you having to hand-build any of it. Two endpoints matter most for production operation.

/actuator/health

This endpoint answers one question — "is this instance able to serve traffic right now" — by aggregating the results of every registered HealthIndicator into one overall status. Spring Boot auto-configures indicators for whatever it detects on the classpath: a DataSourceHealthIndicator that runs a lightweight validation query against your database connection pool, a RedisHealthIndicator that pings your Redis connection, a DiskSpaceHealthIndicator that checks free disk space against a configured threshold, and so on. You can add your own by implementing HealthIndicator to check anything specific to your service — a downstream API's reachability, a critical cache's population state.

The aggregation rule is conservative by default: the overall status is DOWN if any individual indicator reports DOWN, regardless of how many others report UP. This matters because health here isn't measuring "is the JVM process alive" (a process can be alive and completely unable to do useful work if its database connection pool is exhausted) — it's measuring "can this instance actually complete the work it exists to do," which by definition depends on its critical dependencies being reachable, not just on itself being up.

This is also why health checks are operationally load-bearing rather than merely informational: a Kubernetes readiness probe, or a load balancer's health-check configuration, calls this endpoint on a schedule and stops routing new traffic to any instance that reports unhealthy. This is the mechanism that turns "the database connection pool on instance 3 is exhausted" from a slow trickle of failed requests being sent to a doomed instance into that instance being automatically pulled out of rotation within one health-check interval, while the other healthy instances keep serving. Kubernetes actually distinguishes two related but different questions here: a liveness probe asks "should this container be restarted because it's in an unrecoverable state" (often not wired to the same deep dependency checks, because you don't want a transient database blip to trigger container restarts), while a readiness probe asks "should traffic be routed to this instance right now," which is exactly what the aggregated Actuator health check with downstream dependency indicators is built to answer.

A shallow health check lies about the thing that actually matters

A health check that only confirms the JVM process is up and responding to HTTP will report healthy even while the instance's database connection pool is fully exhausted and every real request is failing or hanging — because the process itself is fine, only its ability to do useful work is not. This is why the default Spring Boot health aggregation deliberately wires in dependency checks (database, cache, message broker) rather than stopping at "the web server thread accepted this connection." The trade-off runs the other way too: if every downstream dependency check is wired into readiness with no nuance, a brief, recoverable blip in one non-critical dependency can pull every instance in the fleet out of rotation simultaneously, turning a minor hiccup into a total outage. Deciding which indicators should actually gate readiness — versus being reported for visibility only — is a real design decision, not a default you should leave unexamined.

/actuator/metrics and /actuator/prometheus

The /actuator/metrics endpoint exposes the raw Micrometer registry data in a browsable JSON form (useful for ad hoc inspection of a single instance), while /actuator/prometheus exposes the same underlying data in the Prometheus text exposition format — the specific format the pull-based scraping model described above expects to fetch. Enabling this is usually just adding the micrometer-registry-prometheus dependency and exposing the endpoint via management.endpoints.web.exposure.include=health,metrics,prometheus (Actuator endpoints beyond health are not exposed over HTTP by default, deliberately, since some of them can leak operational detail that shouldn't be public).

5. Centralized Logging: The ELK Stack and Structured Logs

Why per-instance log files stop working

A single service running as one process on one box makes "check the logs" mean SSH into that box and tail -f a file. That breaks down almost immediately in a real deployment: a service behind autoscaling might have anywhere from three to thirty instances at any moment, each writing its own local log file, and a container orchestrator routinely destroys and replaces containers, taking their local filesystem — and any logs sitting only on it — with them. Investigating one issue now means knowing which of N instances handled the relevant request, SSHing into each candidate, and grepping files that may not even exist anymore because the container that wrote them was already recycled. This doesn't scale past a handful of instances, and it's actively hostile to investigating anything that spans multiple services.

The ELK stack

The ELK stack — Elasticsearch, Logstash, Kibana — is the classic open-source answer: every service instance ships its log output off-box to a central pipeline instead of relying on local files as the source of truth. Logstash (or a lighter-weight shipper like Filebeat, commonly used in front of it) collects log lines from every instance, parses and enriches them, and forwards them into Elasticsearch, which indexes them for fast full-text and structured search at volume — this is the same inverted-index search technology used for general document search, applied to log lines instead of documents. Kibana sits on top as the query and visualization layer, letting you search across every instance's logs in one place, filter by fields, and build dashboards from log-derived data.

The value of centralization isn't just convenience — it's that it turns "logs" from a per-instance artifact into a queryable dataset spanning the entire fleet and, if trace IDs are included, the entire causal chain of a request across services. "Show me every ERROR-level log line across all sixteen instances of the order service in the last ten minutes" is a normal Kibana query and an essentially unanswerable question if each instance's logs are still sitting in isolated files.

Structured logging: what makes centralized logs actually usable

Centralizing plain, human-formatted text log lines ("2026-08-24 10:14:02 ERROR Failed to process order 4471 for user 88213: timeout") into Elasticsearch technically works, but it only lets you full-text search, not reliably filter or aggregate — extracting "user ID" or "order ID" from free text requires fragile regex parsing that breaks the moment a log message's wording changes. Structured logging means emitting each log entry as a well-defined record (in practice, almost always JSON) with consistent, named fields — timestamp, level, service, traceId, userId, message — rather than a free-text sentence. Spring Boot supports this via Logback's JSON encoders (logstash-logback-encoder is the common choice) configured in logback-spring.xml, producing output like:

{
  "timestamp": "2026-08-24T10:14:02.331Z",
  "level": "ERROR",
  "service": "order-service",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",

Once every log line carries a consistent traceId field, Elasticsearch can filter on it as an exact-match field rather than a text search, which is exactly the join key that lets you pivot directly from a slow or failing span in a distributed trace to every log line, across every service that request touched, that shares that same trace ID — turning "which service actually threw the exception" from a multi-service grep exercise into a single filtered query. This is the concrete mechanism that ties the traces pillar and the logs pillar together into one investigation rather than two disconnected tools; populating the traceId field consistently is typically handled automatically once tracing instrumentation (Micrometer Tracing, formerly Spring Cloud Sleuth) puts the current trace and span IDs into the logging MDC (Mapped Diagnostic Context), so any log statement issued during that request picks them up without the application code needing to pass them around explicitly.

Structured fields are also what makes logs partially do a metric's job — carefully

Because Elasticsearch can aggregate over structured fields, you can compute things like "count of ERROR-level events per service per minute" directly from logs, which starts to look like a metric. This is useful for exploratory analysis but is a poor substitute for a real Counter metric as the basis for alerting: log-based aggregation is slower (scanning indexed documents, even with a fast search engine, costs more than reading a pre-aggregated time series point) and log ingestion pipelines can themselves lag or drop under load exactly when you most need a reliable signal, whereas a Micrometer counter increments in-process and is scraped independently of the logging pipeline's health. The practical rule: log what you need to investigate a specific case, but expose a metric for anything you intend to alert on continuously.

6. OpenTelemetry: One Instrumentation Standard, Many Backends

Historically, instrumenting metrics, logs, and traces meant adopting whatever library and API a specific vendor or tool provided — Spring Cloud Sleuth's API for tracing, a vendor-specific SDK for APM, a separate Micrometer binding for metrics — and switching backends later meant re-instrumenting application code against a different API. OpenTelemetry (often shortened to OTel) is a vendor-neutral, CNCF-governed specification and set of SDKs that standardizes how metrics, logs, and traces are generated and exported, so instrumentation code is written once against the OpenTelemetry API and can be pointed at Jaeger, Zipkin, Prometheus, Datadog, honeycomb.io, or any other OTel-compatible backend by changing configuration (an exporter), not application code.

The practical shape of this in a Spring Boot service is the OpenTelemetry Java agent (attached at JVM startup with no code changes needed for common frameworks) or the OpenTelemetry SDK integrated via Micrometer Tracing's OTel bridge, both of which emit spans, metrics, and log correlation data through the OpenTelemetry Protocol (OTLP) to an OpenTelemetry Collector — a separate process that receives OTLP data and fans it out to whichever concrete backends you've configured (this Elasticsearch instance for logs, this Prometheus for metrics, this Jaeger for traces). The Collector is the seam that isolates "how my application emits telemetry" from "where that telemetry ultimately lives," which is exactly the vendor lock-in problem OpenTelemetry exists to solve — migrating from one tracing backend to another becomes a Collector configuration change rather than a re-instrumentation project across every service.

OpenTelemetry unifies instrumentation, not the pillars themselves

It's worth being precise about what OpenTelemetry actually standardizes: it's a common way to generate and transport telemetry data (the trace context propagation headers, the span data model, the metric data model), not a claim that metrics, logs, and traces stop being distinct concepts with distinct trade-offs. A histogram is still a histogram, a trace is still a per-request causal chain, and the reasons you need all three (section 1) don't change — OpenTelemetry just means you don't have to re-learn and re-integrate a different proprietary SDK for each pillar and each backend vendor.

7. Alerting Philosophy: Symptoms, SLIs, SLOs, and Error Budgets

Alert on symptoms, not causes

A tempting first instinct is to build alerts for every possible root cause you can think of: alert if CPU exceeds 80%, alert if a specific downstream service's latency exceeds some threshold, alert if a particular queue's depth grows past some number. The problem is that the space of possible causes is effectively unbounded, and most individual cause-level thresholds don't actually correlate with user-visible harm — CPU at 85% might be completely fine if latency and error rate are unaffected, and a brief queue depth spike that drains on its own within seconds never needed a human paged for it.

The more robust approach is to alert on symptoms: the user-facing signals that directly indicate something is actually wrong, regardless of which of the many possible internal causes produced it — elevated error rate (the fraction of requests returning 5xx or failing) and elevated latency (p95/p99 crossing a threshold that reflects real user pain) are the two symptoms that matter for almost any request-driven service. A symptom-based alert fires exactly when users are actually being affected, and the investigation that follows (using traces and logs, per section 1) is what identifies the specific cause — which might be CPU, might be a downstream timeout, might be a bad deploy, might be something no one thought to write a cause-specific alert for in advance. Cause-based alerts are still useful as internal, low-urgency signals for capacity planning and trend-watching, but they should rarely be the thing that pages someone at 3 a.m., because they fire on conditions that often don't actually correlate with a real incident.

SLIs, SLOs, and error budgets

This philosophy is formalized through three related concepts, most associated with Google's Site Reliability Engineering practice:

  • SLI (Service Level Indicator) — a specific, measured metric that quantifies some aspect of the service's behavior from a user's perspective: "the proportion of requests served in under 300ms," "the proportion of requests that return a successful response." An SLI is a number you actually compute from real telemetry (a Micrometer histogram is a typical source), not an aspiration.
  • SLO (Service Level Objective) — a target value for an SLI over a defined window: "99.9% of requests succeed, measured over a rolling 30-day window," or "p95 latency stays under 300ms over a rolling 7-day window." The SLO is the line that separates "operating normally" from "burning through reliability budget faster than acceptable."
  • Error budget — the inverse of the SLO, made concrete: if your SLO is 99.9% success over 30 days, your error budget is the remaining 0.1% — the amount of failure you're explicitly allowed to have without violating the objective. A 99.9% target over 30 days allows roughly 43 minutes of full downtime (or an equivalent amount of partial failure spread across the window) before the SLO is breached.

The error budget reframes the alerting question from "did something technically go wrong" (which is always true somewhere, in any sufficiently large system, at almost any moment) to "are we consuming reliability budget at a rate that will breach our objective." A burn-rate alert — a common pattern built on top of this — pages someone specifically when the error budget is being consumed fast enough that, if the current rate continued, the SLO would be breached before the window resets; a brief, small blip that barely dents the budget doesn't need to wake anyone up, while a sustained elevated error rate that would exhaust a 30-day budget within a few hours absolutely does. This is what turns alerting from a reactive pile of disconnected, symptom-shaped thresholds into something that's explicitly calibrated against what was actually promised (implicitly or explicitly) to the service's users, and it directly determines how aggressively a team should be willing to trade reliability work against shipping new features in a given period — a service that's comfortably within its error budget can afford to take on more risk; one that's close to exhausting it should not.

Error budgets make "how careful do we need to be right now" a computable answer instead of a judgment call

Without an error budget, the question of whether it's safe to ship a risky change, or whether an elevated-but-not-yet-critical error rate deserves an urgent fix, tends to be answered by gut feeling or organizational politics. With an explicit SLO and a computed remaining budget, that question has an actual number behind it: if 90% of the 30-day error budget is already consumed twelve days into the window, that's an objective signal to slow down on risky changes and prioritize reliability work, independent of anyone's individual read on how urgent things feel. It also gives a principled reason to not chase every nine of reliability indiscriminately — going from 99.9% to 99.99% costs disproportionately more engineering effort for the last increment than the users on the other end of it may actually need or notice, and the error budget framing makes that trade-off explicit rather than assumed.

Concepts Worth Being Able to Explain From First Principles

Why can't you just pick one of metrics, logs, or traces and standardize on it if it's the most detailed one?
Detail and cost trade off directly against each other, and the pillar with the most detail (logs) is the worst suited to the job the other two do cheaply. Logs preserve full per-event context but are expensive to store and slow to aggregate at scale, which makes them a poor foundation for continuous alerting — you'd be running expensive full-text scans constantly just to answer "is the error rate elevated," a question a Counter metric answers almost for free. Metrics are cheap and fast precisely because they discard per-event identity through aggregation, which means they can tell you something is wrong but never which specific request, user, or instance to go examine. Traces sit in between: they preserve the causal shape of one request across services, which neither logs (scoped to one service) nor metrics (aggregated across all requests) can show, but a trace's spans typically carry only coarse metadata, not the full detail of what happened inside any one span. Each pillar is optimized for a different point on the cost-versus-detail curve, and a real investigation moves through all three because no single point on that curve answers every question you need answered.
Why does Prometheus prefer histogram buckets over client-side percentiles for anything you plan to aggregate across many instances?
A percentile is fundamentally a property of a set of raw observations, not something you can correctly derive by combining other percentiles. If instance A's p99 latency is 200ms and instance B's p99 is 800ms, there is no valid way to combine those two numbers into the correct fleet-wide p99 — averaging them, or taking the max, both produce numbers that don't correspond to any real, principled statistic over the combined set of requests both instances served. A histogram avoids this because what it actually exposes is raw counts per bucket, which are just numbers that add normally: the count of requests under 100ms across the whole fleet is simply the sum of each instance's count of requests under 100ms. Once Prometheus has summed the bucket counts across every instance, it can then compute one valid, fleet-wide percentile from that combined distribution. A client-side Summary skips straight to computing the percentile locally, which is fine for looking at one instance in isolation but has no mathematically sound way to be combined with another instance's percentile.
Concretely, why does an average latency number fail to reveal a real production problem that a p99 would catch immediately?
An average blends every observation into a single number where a small number of very bad outcomes get diluted by a large number of good ones. If 990 out of 1000 requests take 50ms and 10 take 7 seconds (because they happen to hit a lock, a slow downstream call, or a garbage collection pause), the average across all 1000 is roughly 120ms — a number that looks completely healthy and gives no hint that a meaningful number of users are experiencing multi-second waits. The p99, by construction, is defined by exactly the slowest 1% of requests, so those same 10 requests aren't diluted away — they directly determine the reported value, which in this case would be close to 7 seconds and immediately visible as a problem. Because real production slowness is very often caused by something that affects a small subset of requests severely (contention, a slow dependency for a subset of traffic, GC pauses) rather than something that slows every request slightly and uniformly, the tail percentiles are usually where the actual user-facing damage lives, and averages are structurally the wrong statistic to reveal it.
Why does a load balancer or orchestrator care about an aggregated health check rather than just checking whether the process is running?
Whether a process is running answers a much narrower question than whether that process can actually do useful work. A JVM can be fully alive, accepting TCP connections, and responding to a bare liveness ping, while its database connection pool is completely exhausted and every real request it receives times out or fails — from the outside, "process is up" gives no signal that this is happening. An aggregated health check that includes a HealthIndicator for the database connection pool, the cache, and any other hard dependency turns "can this instance do its job" into something that can actually be checked and answered before traffic is routed there. This is precisely why Kubernetes readiness probes and load balancer health checks are typically wired to a deeper endpoint like Spring Boot's aggregated /actuator/health rather than a trivial liveness ping — the entire point of the check is to catch the case where the process is technically alive but functionally broken, and stop sending it traffic before users hit the failure themselves.
Why is a trace ID embedded in every log line the specific mechanism that makes centralized, structured logging useful, rather than just having logs in one place?
Simply centralizing raw text log lines into one searchable store (Elasticsearch) already helps compared to per-instance files, but it only gets you full-text search — finding logs related to one specific failing request still means guessing at keywords or timestamps and hoping they're unique enough, across every service the request might have touched. A shared trace ID, propagated across every service boundary the request crosses and included as a structured field on every log line each service emits during that request's handling, gives you an exact join key. Once you have that, the path from "a trace waterfall shows the pricing service's span failed" to "here is the exact exception the pricing service logged for that failure" is a single filtered query on traceId, rather than a manual, time-window-based search across five separate services' logs and hoping none of the relevant lines got lost in the noise of everything else those services were doing at the same moment.
What does OpenTelemetry actually standardize, and what does it deliberately leave alone?
OpenTelemetry standardizes the generation, data model, and transport of telemetry — a common API your application code instruments against, a common wire format (OTLP) for sending spans, metrics, and logs, and a common propagation format for trace context across service boundaries. What it does not do is collapse metrics, logs, and traces into one undifferentiated thing, or dictate which backend you must store any of it in. A histogram emitted through OpenTelemetry is still fundamentally a histogram with the same aggregation trade-offs described earlier; a span is still a per-request causal record. What changes is that the instrumentation code producing all of this is no longer tied to a specific vendor's proprietary SDK, so pointing that same instrumented data at a different backend (swapping Jaeger for a different tracing store, for instance) is a configuration change to an OpenTelemetry Collector's exporters, not a re-instrumentation effort across every service in the system.
Why is "alert whenever the error budget's burn rate would exhaust it before the window resets" a better rule than "alert whenever any error occurs"?
Alerting on any error at all guarantees a constant stream of pages in any sufficiently large system, because at any given moment something, somewhere, is failing in some small way that's well within normal, expected variance — this trains whoever's on call to start ignoring alerts, which defeats the entire purpose of alerting. A burn-rate alert instead asks a more specific, more meaningful question: given the current rate of failures, will this consume the entire allotted error budget before the measurement window (say, 30 days) resets? A brief spike that resolves quickly barely touches the budget and correctly doesn't page anyone. A sustained, ongoing elevated error rate that would burn through a 30-day budget in a matter of hours is exactly the situation that needs a human's attention immediately, and the burn-rate calculation makes that distinction automatically and quantitatively, rather than relying on a fixed threshold that's either too sensitive (pages on noise) or too insensitive (misses a real, sustained degradation that hasn't yet crossed some arbitrary absolute error count).
