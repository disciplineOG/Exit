Observability & Production Readiness

Why this matters

A system with no observability doesn't fail less often — it just fails in the dark. Averages hide the exact latency spikes that make ShopSphere's checkout flow feel broken for 1% of customers; a health check that only pings SELECT 1 against a database that's actually saturated with slow queries will happily keep routing checkout traffic to a dying order-service instance; and without a correlation ID threading through every log line, "why did this one customer's order get stuck between payment and shipping" turns into grepping five services' logs — order-service, payment-service, inventory-service, notification-service — by timestamp and hoping the clocks agree. Understanding what each pillar of observability actually measures, and what it structurally cannot tell you, is what lets you build a system where a production incident (a flash sale spiking checkout latency, a payment provider timing out) is a ten-minute diagnosis instead of a two-hour guessing game.

1. The Three Pillars, and Why One Alone Is Never Enough

Observability is usually described as resting on three pillars — metrics, logs, and traces — and the reason it takes three, rather than one very good one, is that each pillar is a different projection of the same underlying reality (requests flowing through a system over time), and each projection deliberately throws away information the others keep, in exchange for being cheap and fast at what it does keep. The running example for the rest of this page is a single ShopSphere order placed during a flash sale, moving through cart → order-service (checkout) → payment-service → inventory-service → notification-service — the exact shape of request that each pillar sees from a different angle:

Metrics

A metric is a number that changes over time, aggregated across many events, sampled or recorded at regular intervals — "orders placed per second across all of ShopSphere," "p99 checkout latency over the last minute," "JVM heap used on a payment-service pod." Metrics answer "how is the system behaving in aggregate, and is it trending toward a problem?" They are extremely cheap to store (a time series is just a sequence of timestamp-value pairs, often compressed) and extremely cheap to query even over long time ranges, which is exactly what makes them suitable for dashboards and alerting rules that need to evaluate constantly. The cost is that aggregation is lossy by construction: once 10,000 individual checkout latencies have been folded into "p99 = 420ms," you cannot recover which specific order was slow, which customer placed it, or what payment provider that particular request happened to hit. A metric can tell you that something is wrong and roughly how much — say, that payment-service's p99 spiked during the flash sale — but never which specific order to go look at.

Logs

A log is a detailed, per-event record — a line (or structured record) emitted at a specific point in a specific request's execution, carrying whatever context the code chose to include: a stack trace, an orderId, a customerId, a SQL query, an error message. Logs answer "what exactly happened during this one event?" — for example, the single line payment-service emits recording that order 4471's capture call to its payment provider took 620ms. They preserve the full detail metrics discard, at the cost of volume: a service handling a thousand checkout requests a second during a flash sale, each logging a handful of lines, produces gigabytes of log data per hour, and both storing and searching that volume at scale (full-text search over billions of lines) is a real infrastructure cost, not a rounding error. Logs are also comparatively slow to query for aggregate questions — "what's my checkout error rate over the last hour" is answerable from logs in principle, but it means scanning and counting across a huge volume of records, which is precisely the kind of question a metric already answers for a fraction of the cost.

Traces

A trace is the causal chain of work performed by one specific request as it moves across services — the mechanic covered in depth in microservice-patterns, where a trace ID and a tree of parent-child spans reconstruct which service called which, in what order, and how long each hop took. Traces answer "where, in the causal chain of this one request across N services, did the time go, or did the failure occur?" A trace waterfall for order 4471 above is the one artifact that can show you that the checkout request's ~750ms total was actually 620ms of one downstream call from payment-service to its external payment provider, and only ~125ms combined across order-service, inventory-service, and notification-service — something no single service's own logs or metrics could show in isolation, because order-service has no visibility into how long payment-service's own downstream call took, only that payment-service as a whole took a while to respond.

The three pillars are not redundant, they're sequential in a typical investigation

A realistic production incident usually walks through all three in order: a metric-driven alert fires because ShopSphere checkout's p99 latency crossed a threshold during a flash sale (metrics tell you something is wrong and roughly when it started); you pull up a trace for one slow checkout request from around that time and see the waterfall above, where payment-service's span accounts for almost all of the latency (traces tell you where); you then pivot to payment-service's logs, filtered by that trace's traceId, and see the actual log line recording a 620ms call to the payment provider along with a warning that the provider's connection pool was exhausted (logs tell you why). Each pillar narrows the search space for the next one. Trying to diagnose this incident from only one pillar means either drowning in undifferentiated log volume across five services with no idea where to start looking, or having a metric that confirms payment-service is slow with no way to find a concrete example request to investigate.

2. Metrics in Depth: Micrometer, Prometheus, and the Four Metric Types

Spring Boot applications instrument metrics through Micrometer, which acts as a facade in front of whichever metrics backend you actually use — Prometheus, Datadog, New Relic, CloudWatch — the same way SLF4J is a facade in front of a concrete logging implementation. This matters for the same reason any facade matters: your application code records "increment this counter" or "record this timing" against Micrometer's API, and swapping the backend is a dependency and configuration change, not a rewrite of instrumentation scattered across the codebase.

Micrometer exposes four fundamental metric types, and picking the right one for a given measurement is not a stylistic choice — each one is backed by different storage and supports different queries.

Counter

A monotonically increasing value — it only ever goes up (or resets to zero on restart), never down. Used for counting occurrences: total checkout requests handled by order-service, total OrderPlaced events published, total payment capture failures thrown by payment-service. You never decrement a counter; if you need something that can go down, that's a Gauge. The reason counters are modeled as strictly increasing rather than "current count of X" is that increasing counters compose cleanly across a rate calculation — Prometheus's rate() function divides the increase in a counter over a time window by the window length to get "orders per second," and that math only works cleanly if the underlying value never resets except on process restart (which Prometheus detects and handles as a special case).

Gauge

A value that can go up or down, representing a current state: active database connections in inventory-service's connection pool, current depth of the queue between order-service and payment-service, JVM heap used right now on a payment-service pod, number of in-flight checkout requests during a flash sale. Unlike a counter, a gauge has no notion of a "rate" — you read its current value directly. Gauges are typically sampled by reference (Micrometer holds a reference to the current value and reads it at scrape time), not by push, which avoids the correctness problem of the value changing between when your code updates it and when it's reported.

Histogram

A histogram tracks the distribution of a set of observed values (most commonly latencies or sizes) by counting how many observations fell into each of a set of predefined buckets — for example, buckets at 10ms, 50ms, 100ms, 250ms, 500ms, 1s, and "everything above" for payment-service's capture-call latency. Each bucket is actually a cumulative counter of "how many requests took less than or equal to this bucket's boundary" (this is the Prometheus convention, called a cumulative histogram, exposed as separate time series like payment_capture_duration_seconds_bucket{le="0.5"}, {le="1.0"}, and so on, plus a _sum and a _count).

Summary / Timer

A Summary computes quantiles (percentiles) directly on the client side at recording time and exposes those precomputed quantiles. Micrometer's Timer is the type you actually reach for in Spring Boot code to measure durations — wrapping the checkout call from order-service to payment-service, for instance — and depending on configuration it can publish either histogram buckets, client-side percentiles, or both. The distinction that matters operationally is where the percentile math happens: a client-side Summary computes an accurate percentile for that one instance, but you structurally cannot average or combine percentiles computed on different instances into a correct fleet-wide percentile (averaging two p99s is not the fleet's p99). A histogram, by contrast, publishes raw bucket counts, and Prometheus can sum those bucket counts across every payment-service instance in the fleet before computing the percentile, giving you a mathematically valid fleet-wide p99. This is exactly why Prometheus-oriented setups favor histograms over client-computed summaries for anything you intend to aggregate across instances.

Instrumenting ShopSphere's checkout path with Micrometer

This is what the four types look like as actual code inside order-service's checkout handler — MeterRegistry is the Micrometer object you inject to create and record against any of these metric types, and it's what ultimately gets wired to whichever backend (Prometheus, here) is configured:

@Service
public class CheckoutService {

    private final MeterRegistry registry;
    private final Counter ordersPlacedCounter;
    private final AtomicInteger inFlightCheckouts = new AtomicInteger(0);

    public CheckoutService(MeterRegistry registry, PaymentClient paymentClient) {
        this.registry = registry;
        // Counter: total orders placed, ever - only ever goes up
        this.ordersPlacedCounter = Counter.builder("shopsphere.orders.placed")
            .description("Total orders successfully placed")
            .register(registry);
        // Gauge: current in-flight checkouts - reads inFlightCheckouts.get() at scrape time
        Gauge.builder("shopsphere.checkout.inflight", inFlightCheckouts, AtomicInteger::get)
            .register(registry);
    }

    public Order checkout(Cart cart) {
        inFlightCheckouts.incrementAndGet();
        try {
            // Timer: records this call's duration into histogram buckets, tagged by outcome
            return Timer.builder("shopsphere.payment.capture.duration")
                .tag("provider", "stripe")
                .publishPercentileHistogram() // export bucket counts, not just a client-side percentile
                .register(registry)
                .record(() -> {
                    Payment payment = paymentClient.capture(cart);   // the 620ms hop in the trace above
                    ordersPlacedCounter.increment();                 // Counter: one more order placed
                    return orderRepository.save(Order.from(cart, payment));
                });
        } finally {
            inFlightCheckouts.decrementAndGet();
        }
    }
}

publishPercentileHistogram() is the specific call that makes this Timer export Prometheus-style bucket counts (rather than, or in addition to, client-side percentiles) — this is the mechanism, not just the concept, behind the histogram-vs-summary distinction discussed above; without it, Micrometer's default Timer only tracks count/sum/max, with no bucket data for Prometheus's histogram_quantile() to work with at all.

From buckets to percentiles, and why the average is lying to you

An average latency of 120ms sounds fine. But an average is exactly the statistic that hides a tail problem: if 990 requests out of 1000 take 50ms and 10 take 7 seconds, the average is still only around 120ms, yet 1% of your users are having a genuinely broken experience. Percentiles fix this by answering a different, more honest question: "what latency does the slowest N% of requests experience?" p50 (the median) tells you the typical case; p95 tells you what the slowest-1-in-20 requests experience; p99 tells you what the slowest 1-in-100 experience. Because a single slow dependency, a single garbage collection pause, or a single lock contention event tends to affect a small fraction of requests severely rather than all requests slightly, the tail percentiles are usually where real user-facing pain lives, and averages are close to blind to them.

Histogram buckets are what make computing an arbitrary percentile after the fact possible without having stored every individual latency value (which would be enormously expensive at scale). Given cumulative bucket counts — say 900 requests at or under 100ms, 990 at or under 500ms, and 1000 total — Prometheus's histogram_quantile() function finds which bucket boundary a given percentile falls between and linearly interpolates within that bucket to estimate the value. The precision of that estimate is bounded by how fine your bucket boundaries are near the values you actually care about — if your buckets jump from 100ms straight to 1s, a computed p95 that happens to fall in that range is only accurate to within that wide gap, which is why choosing bucket boundaries that cluster around your actual SLO thresholds (if your target is "p95 under 300ms," you want buckets at 100ms, 200ms, 300ms, 400ms, not just round powers of ten) matters in practice.

You cannot retroactively compute a percentile you didn't bucket for

If your histogram's buckets are 50ms, 200ms, 1000ms and nothing finer, you can get a reasonable estimate of p50 or p99 but a fairly poor estimate of p90 if the real p90 sits somewhere in that wide 200ms-to-1000ms gap — the interpolation has almost no data points to interpolate between. Because bucket boundaries have to be chosen ahead of time, at instrumentation time, changing your mind about what precision you need at the tail later means redeploying with new buckets and only getting accurate data going forward — you cannot recompute better precision from already-recorded, coarser buckets. This is the practical reason to default to somewhat generous bucket coverage around your expected latency range up front, rather than trimming buckets down to "just what today's dashboard needs."

3. Pull-Based Scraping vs Push-Based Metrics

Prometheus, the dominant open-source metrics backend paired with Micrometer, uses a pull model: each application exposes its current metric values on an HTTP endpoint (Spring Boot Actuator exposes this at /actuator/prometheus), and the Prometheus server itself is responsible for periodically sending an HTTP GET to that endpoint on every monitored instance — say, every one of inventory-service's twelve running pods during a flash sale — typically every 15 seconds, and recording whatever values it reads (called a "scrape"). This is the inverse of a push model (used by systems like StatsD or Graphite in their classic form), where each application actively sends its metrics out to a central collector on its own schedule.

The pull model has a specific, deliberate advantage in a dynamic, service-discovery-driven environment: Prometheus itself owns the list of "which targets should I be scraping," and that target list can be populated dynamically from the same service registry or orchestrator that already tracks live instances — Kubernetes service discovery, Consul, or a static file that's kept in sync with an autoscaling group. When Kubernetes scales inventory-service from 4 pods to 12 in response to a flash-sale traffic spike, Prometheus's service-discovery integration notices the new pods and starts scraping them automatically; when the flash sale ends and those pods scale back down, Prometheus simply stops getting a successful response from those targets and marks them down, without any pod needing to have known in advance where to push its data. This inverts naturally with how microservice-patterns already handles instance churn — the same registry information that tells a load balancer which inventory-service pods are live is exactly the information a pull-based monitoring system needs to know which pods to scrape.

A push model, by contrast, requires every application instance to know the address of the central collector and to actively manage sending data to it, which means a payment-service instance experiencing enough trouble that it can't even complete its own push (heavy GC pause, thread pool exhaustion) may fail to report the very metrics that would explain what's wrong, right when you need them most. A pull-based scrape failing (a scrape that times out or gets no response) is itself a meaningful, automatically captured signal — "this target is now unscrapable" — that a pure push model doesn't get for free.

Pull doesn't fit everything

The pull model assumes the monitoring system can always reach the target over the network and that the target's lifetime is long enough to be scraped on a normal interval. It breaks down for short-lived batch jobs that might finish and terminate in under 15 seconds — a nightly job that reconciles ShopSphere's Inventory counts against warehouse system-of-record data, for instance, might run for only a few seconds and be gone before any scrape window catches it. Prometheus's answer for that case is the Pushgateway, an intermediary that short-lived jobs push their final metric values to, which Prometheus then scrapes as if it were the job itself — a deliberate, narrow exception to the pull model rather than a wholesale switch to push. See batch-processing-scheduled-jobs for how these jobs are scheduled and monitored more broadly.

4. Spring Boot Actuator: Health, Metrics, and Why Load Balancers Care

Actuator is Spring Boot's built-in module for exposing operational information about a running application over HTTP, without you having to hand-build any of it. Two endpoints matter most for production operation.

/actuator/health

This endpoint answers one question — "is this instance able to serve traffic right now" — by aggregating the results of every registered HealthIndicator into one overall status. Spring Boot auto-configures indicators for whatever it detects on the classpath: a DataSourceHealthIndicator that runs a lightweight validation query against payment-service's database connection pool, a RedisHealthIndicator that pings the Redis instance backing ShopSphere's cart cache, a DiskSpaceHealthIndicator that checks free disk space against a configured threshold, and so on. You can add your own by implementing HealthIndicator to check anything specific to your service — inventory-service checking that its warehouse-system API is reachable, notification-service checking that its Kafka consumer group is actually connected.

The aggregation rule is conservative by default: the overall status is DOWN if any individual indicator reports DOWN, regardless of how many others report UP. This matters because health here isn't measuring "is the JVM process alive" (a payment-service instance can be alive and completely unable to do useful work if its database connection pool is exhausted) — it's measuring "can this instance actually complete the work it exists to do," which by definition depends on its critical dependencies being reachable, not just on itself being up.

This is also why health checks are operationally load-bearing rather than merely informational: a Kubernetes readiness probe, or a load balancer's health-check configuration, calls this endpoint on a schedule and stops routing new checkout traffic to any order-service instance that reports unhealthy. This is the mechanism that turns "the database connection pool on payment-service pod 3 is exhausted" from a slow trickle of failed checkout requests being sent to a doomed instance into that instance being automatically pulled out of rotation within one health-check interval, while the other healthy instances keep processing orders. Kubernetes actually distinguishes two related but different questions here: a liveness probe asks "should this container be restarted because it's in an unrecoverable state" (often not wired to the same deep dependency checks, because you don't want a transient database blip to trigger a container restart mid-flash-sale), while a readiness probe asks "should traffic be routed to this instance right now," which is exactly what the aggregated Actuator health check with downstream dependency indicators is built to answer.

A shallow health check lies about the thing that actually matters

A health check that only confirms the JVM process is up and responding to HTTP will report payment-service healthy even while its database connection pool is fully exhausted and every real capture request is failing or hanging — because the process itself is fine, only its ability to do useful work is not. This is why the default Spring Boot health aggregation deliberately wires in dependency checks (database, cache, message broker) rather than stopping at "the web server thread accepted this connection." The trade-off runs the other way too: if every downstream dependency check is wired into readiness with no nuance, a brief, recoverable blip in one non-critical dependency (say, notification-service's Kafka connection flickering for two seconds) can pull every payment-service instance in the fleet out of rotation simultaneously, turning a minor hiccup into checkout being unavailable fleet-wide. Deciding which indicators should actually gate readiness — versus being reported for visibility only — is a real design decision, not a default you should leave unexamined.

/actuator/metrics and /actuator/prometheus

The /actuator/metrics endpoint exposes the raw Micrometer registry data in a browsable JSON form (useful for ad hoc inspection of a single instance — checking one payment-service pod's current shopsphere.checkout.inflight gauge value directly), while /actuator/prometheus exposes the same underlying data in the Prometheus text exposition format — the specific format the pull-based scraping model described above expects to fetch. Enabling this is usually just adding the micrometer-registry-prometheus dependency and exposing the endpoint via management.endpoints.web.exposure.include=health,metrics,prometheus (Actuator endpoints beyond health are not exposed over HTTP by default, deliberately, since some of them can leak operational detail that shouldn't be public).

5. Centralized Logging: The ELK Stack and Structured Logs

Why per-instance log files stop working

A single service running as one process on one box makes "check the logs" mean SSH into that box and tail -f a file. That breaks down almost immediately in a real deployment: order-service behind autoscaling might have anywhere from three to thirty instances at any moment during a flash sale, each writing its own local log file, and a container orchestrator routinely destroys and replaces containers, taking their local filesystem — and any logs sitting only on it — with them. Investigating why customer 8841's order 4471 got stuck now means knowing which of N order-service instances handled that specific checkout request, SSHing into each candidate, and grepping files that may not even exist anymore because the container that wrote them was already recycled. This doesn't scale past a handful of instances, and it's actively hostile to investigating anything that spans multiple services — and order 4471's journey spans four (order-service, payment-service, inventory-service, notification-service).

The ELK stack

The ELK stack — Elasticsearch, Logstash, Kibana — is the classic open-source answer: every service instance ships its log output off-box to a central pipeline instead of relying on local files as the source of truth. Logstash (or a lighter-weight shipper like Filebeat, commonly used in front of it) collects log lines from every instance, parses and enriches them, and forwards them into Elasticsearch, which indexes them for fast full-text and structured search at volume — this is the same inverted-index search technology used for general document search, applied to log lines instead of documents. Kibana sits on top as the query and visualization layer, letting you search across every instance's logs in one place, filter by fields, and build dashboards from log-derived data.

The value of centralization isn't just convenience — it's that it turns "logs" from a per-instance artifact into a queryable dataset spanning the entire fleet and, if trace IDs are included, the entire causal chain of a request across services. "Show me every ERROR-level log line across all sixteen instances of payment-service in the last ten minutes" is a normal Kibana query and an essentially unanswerable question if each instance's logs are still sitting in isolated files.

Structured logging: what makes centralized logs actually usable

Centralizing plain, human-formatted text log lines ("2026-08-24 10:14:02 ERROR Failed to process order 4471 for customer 8841: timeout") into Elasticsearch technically works, but it only lets you full-text search, not reliably filter or aggregate — extracting "customer ID" or "order ID" from free text requires fragile regex parsing that breaks the moment a log message's wording changes. Structured logging means emitting each log entry as a well-defined record (in practice, almost always JSON) with consistent, named fields — timestamp, level, service, traceId, customerId, message — rather than a free-text sentence. Spring Boot supports this via Logback's JSON encoders (logstash-logback-encoder is the common choice) configured in logback-spring.xml, producing output like this line from payment-service, one of the four hops in the checkout trace from section 1:

{
  "timestamp": "2026-08-24T10:14:02.331Z",
  "level": "ERROR",
  "service": "payment-service",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "spanId": "00f067aa0ba902b7",
  "customerId": "8841",
  "orderId": "4471",
  "message": "Payment capture timed out calling provider=stripe after 620ms",
  "exception": "java.util.concurrent.TimeoutException"
}

Once every log line carries a consistent traceId field, Elasticsearch can filter on it as an exact-match field rather than a text search, which is exactly the join key that lets you pivot directly from a slow or failing span in a distributed trace to every log line, across every service that request touched, that shares that same trace ID — turning "which service actually threw the exception for order 4471" from a four-service grep exercise (order-service, payment-service, inventory-service, notification-service, each with its own log volume) into a single filtered Kibana query on traceId: 4bf92f3577b34da6a3ce929d0e0e4736. This is the concrete mechanism that ties the traces pillar and the logs pillar together into one investigation rather than two disconnected tools; populating the traceId field consistently is typically handled automatically once tracing instrumentation (Micrometer Tracing, formerly Spring Cloud Sleuth) puts the current trace and span IDs into the logging MDC (Mapped Diagnostic Context — a per-thread key/value map Logback and Log4j2 read from when formatting each log line), so any log statement issued during that request picks them up without the application code needing to pass them around explicitly.

Structured fields are also what makes logs partially do a metric's job — carefully

Because Elasticsearch can aggregate over structured fields, you can compute things like "count of ERROR-level events per service per minute" directly from logs, which starts to look like a metric. This is useful for exploratory analysis but is a poor substitute for a real Counter metric as the basis for alerting: log-based aggregation is slower (scanning indexed documents, even with a fast search engine, costs more than reading a pre-aggregated time series point) and log ingestion pipelines can themselves lag or drop under load exactly when you most need a reliable signal — precisely during the flash sale that's generating both the highest log volume and the highest risk of an incident — whereas a Micrometer counter increments in-process and is scraped independently of the logging pipeline's health. The practical rule: log what you need to investigate a specific case, but expose a metric for anything you intend to alert on continuously.

6. OpenTelemetry: One Instrumentation Standard, Many Backends

Historically, instrumenting metrics, logs, and traces meant adopting whatever library and API a specific vendor or tool provided — Spring Cloud Sleuth's API for tracing, a vendor-specific SDK for APM, a separate Micrometer binding for metrics — and switching backends later meant re-instrumenting application code against a different API. OpenTelemetry (often shortened to OTel) is a vendor-neutral, CNCF-governed specification and set of SDKs that standardizes how metrics, logs, and traces are generated and exported, so instrumentation code is written once against the OpenTelemetry API and can be pointed at Jaeger, Zipkin, Prometheus, Datadog, honeycomb.io, or any other OTel-compatible backend by changing configuration (an exporter), not application code.

The practical shape of this in a Spring Boot service is the OpenTelemetry Java agent (attached at JVM startup with no code changes needed for common frameworks) or the OpenTelemetry SDK integrated via Micrometer Tracing's OTel bridge, both of which emit spans, metrics, and log correlation data through the OpenTelemetry Protocol (OTLP) to an OpenTelemetry Collector — a separate process that receives OTLP data and fans it out to whichever concrete backends you've configured (this Elasticsearch instance for logs, this Prometheus for metrics, this Jaeger for traces). The Collector is the seam that isolates "how my application emits telemetry" from "where that telemetry ultimately lives," which is exactly the vendor lock-in problem OpenTelemetry exists to solve — migrating from one tracing backend to another becomes a Collector configuration change rather than a re-instrumentation project across every service.

How order 4471's trace actually propagates across four ShopSphere services

A trace ID isn't magically shared — it has to be generated once, then explicitly carried along every hop the request makes, whether that hop is a synchronous HTTP call or an asynchronous message. For a checkout request, that looks like:

1. Customer's browser calls POST /checkout on order-service.
   -> order-service has no incoming traceparent header, so it MINTS a new trace:
      traceId=4bf92f3577b34da6a3ce929d0e0e4736, spanId=00f067aa0ba902b7 (root span)

2. order-service calls payment-service synchronously over HTTP to capture payment.
   -> The OpenTelemetry instrumentation (auto-added by the Java agent, or Micrometer
      Tracing's RestTemplate/WebClient interceptor) attaches a W3C Trace Context header:
      traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                    ^version  ^traceId (same as above)      ^parent spanId  ^flags
   -> payment-service's own instrumentation reads this header, creates a CHILD span
      (new spanId, same traceId, parent = 00f067aa0ba902b7), and does the same thing
      on its own outbound call to the payment provider.

3. order-service, after payment succeeds, publishes an OrderPlaced event to Kafka for
   inventory-service and notification-service to consume asynchronously.
   -> There's no HTTP header here - the traceId/spanId are instead written into the
      Kafka record's HEADERS (a small key/value map every Kafka message carries
      alongside its payload), because trace context has to travel wherever the
      request's causal chain travels, HTTP or not.
   -> inventory-service and notification-service each read those headers when they
      consume the record, and start their own child spans under the same traceId -
      this is why the trace waterfall in section 1 shows all four services under
      ONE traceId despite two of the hops being async, not request/response.

This is exactly what makes the earlier claim in section 1 concrete rather than hand-wavy: "all four services share traceId=4bf92f3577b34da6a3ce929d0e0e4736" isn't a coincidence of naming — it's the direct result of that ID being propagated, mechanically, through an HTTP header on the synchronous hop and through Kafka record headers on the asynchronous ones. If any one of these services failed to read or forward that header/header-equivalent, the trace would silently fracture into two or more disconnected traces at that point, and the tracing backend (Jaeger, Zipkin) would have no way to reassemble them into one waterfall — this is the single most common reason a "distributed trace" mysteriously stops at one service in practice: a manually-created Thread, a fire-and-forget async call, or a message producer that wasn't instrumented, breaking the propagation chain.

OpenTelemetry unifies instrumentation, not the pillars themselves

It's worth being precise about what OpenTelemetry actually standardizes: it's a common way to generate and transport telemetry data (the trace context propagation headers, the span data model, the metric data model), not a claim that metrics, logs, and traces stop being distinct concepts with distinct trade-offs. A histogram is still a histogram, a trace is still a per-request causal chain, and the reasons you need all three (section 1) don't change — OpenTelemetry just means you don't have to re-learn and re-integrate a different proprietary SDK for each pillar and each backend vendor.

7. Alerting Philosophy: Symptoms, SLIs, SLOs, and Error Budgets

Alert on symptoms, not causes

A tempting first instinct is to build alerts for every possible root cause you can think of: alert if a payment-service pod's CPU exceeds 80%, alert if inventory-service's downstream warehouse-API latency exceeds some threshold, alert if the Kafka queue feeding notification-service grows past some depth. The problem is that the space of possible causes is effectively unbounded, and most individual cause-level thresholds don't actually correlate with user-visible harm — CPU at 85% on a payment-service pod might be completely fine if checkout latency and error rate are unaffected, and a brief notification-service queue depth spike that drains on its own within seconds never needed a human paged for it (a delayed order-confirmation email is a very different severity than a failed checkout).

The more robust approach is to alert on symptoms: the user-facing signals that directly indicate something is actually wrong, regardless of which of the many possible internal causes produced it — elevated error rate (the fraction of checkout requests returning 5xx or failing to complete) and elevated latency (checkout p95/p99 crossing a threshold that reflects real customer-facing pain) are the two symptoms that matter most for ShopSphere's checkout path. A symptom-based alert fires exactly when customers are actually being affected — checkout requests failing or hanging during a flash sale — and the investigation that follows (using traces and logs, per section 1) is what identifies the specific cause — which might be payment-service's connection pool exhausted, might be inventory-service timing out reserving stock for a hot productId, might be a bad deploy, might be something no one thought to write a cause-specific alert for in advance. Cause-based alerts are still useful as internal, low-urgency signals for capacity planning and trend-watching, but they should rarely be the thing that pages someone at 3 a.m., because they fire on conditions that often don't actually correlate with a real incident.

SLIs, SLOs, and error budgets

This philosophy is formalized through three related concepts, most associated with Google's Site Reliability Engineering practice — applied here to ShopSphere's checkout path specifically:

  • SLI (Service Level Indicator) — a specific, measured metric that quantifies some aspect of the service's behavior from a user's perspective: "the proportion of checkout requests served in under 300ms," "the proportion of checkout requests that complete successfully (order reaches PAID status) without a 5xx." An SLI is a number you actually compute from real telemetry (a Micrometer histogram on order-service's checkout endpoint is a typical source), not an aspiration.
  • SLO (Service Level Objective) — a target value for an SLI over a defined window: "99.9% of checkout requests succeed, measured over a rolling 30-day window," or "p95 checkout latency stays under 300ms over a rolling 7-day window." The SLO is the line that separates "operating normally" from "burning through reliability budget faster than acceptable."
  • Error budget — the inverse of the SLO, made concrete: if checkout's SLO is 99.9% success over 30 days, the error budget is the remaining 0.1% — the amount of checkout failure ShopSphere is explicitly allowed to have without violating the objective. A 99.9% target over 30 days allows roughly 43 minutes of full checkout downtime (or an equivalent amount of partial failure spread across the window, e.g. a flash sale where 2% of checkouts fail for an hour) before the SLO is breached.

The error budget reframes the alerting question from "did something technically go wrong" (which is always true somewhere, in any sufficiently large system, at almost any moment — some tiny fraction of checkouts fail even on a perfectly healthy day, because customers submit expired cards or malformed input) to "are we consuming reliability budget at a rate that will breach our objective." A burn-rate alert — a common pattern built on top of this — pages someone specifically when the error budget is being consumed fast enough that, if the current rate continued, the SLO would be breached before the window resets; a brief, small blip in checkout failures that barely dents the budget doesn't need to wake anyone up, while a sustained elevated checkout error rate during a flash sale that would exhaust a 30-day budget within a few hours absolutely does. This is what turns alerting from a reactive pile of disconnected, symptom-shaped thresholds into something that's explicitly calibrated against what was actually promised (implicitly or explicitly) to ShopSphere's customers, and it directly determines how aggressively the team should be willing to trade reliability work against shipping new features in a given period — a checkout path that's comfortably within its error budget can afford to take on more risk (ship a new payment provider integration); one that's close to exhausting it should not.

Error budgets make "how careful do we need to be right now" a computable answer instead of a judgment call

Without an error budget, the question of whether it's safe to ship a risky change to checkout, or whether an elevated-but-not-yet-critical payment failure rate deserves an urgent fix, tends to be answered by gut feeling or organizational politics. With an explicit SLO and a computed remaining budget, that question has an actual number behind it: if 90% of checkout's 30-day error budget is already consumed twelve days into the window, that's an objective signal to slow down on risky checkout changes and prioritize reliability work, independent of anyone's individual read on how urgent things feel. It also gives a principled reason to not chase every nine of reliability indiscriminately — going from 99.9% to 99.99% checkout success costs disproportionately more engineering effort for the last increment than customers on the other end of it may actually need or notice, and the error budget framing makes that trade-off explicit rather than assumed.

Concepts Worth Being Able to Explain From First Principles

Why can't you just pick one of metrics, logs, or traces and standardize on it if it's the most detailed one?
Detail and cost trade off directly against each other, and the pillar with the most detail (logs) is the worst suited to the job the other two do cheaply. Logs preserve full per-event context but are expensive to store and slow to aggregate at scale, which makes them a poor foundation for continuous alerting — you'd be running expensive full-text scans constantly just to answer "is the error rate elevated," a question a Counter metric answers almost for free. Metrics are cheap and fast precisely because they discard per-event identity through aggregation, which means they can tell you something is wrong but never which specific request, user, or instance to go examine. Traces sit in between: they preserve the causal shape of one request across services, which neither logs (scoped to one service) nor metrics (aggregated across all requests) can show, but a trace's spans typically carry only coarse metadata, not the full detail of what happened inside any one span. Each pillar is optimized for a different point on the cost-versus-detail curve, and a real investigation moves through all three because no single point on that curve answers every question you need answered.
Why does Prometheus prefer histogram buckets over client-side percentiles for anything you plan to aggregate across many instances?
A percentile is fundamentally a property of a set of raw observations, not something you can correctly derive by combining other percentiles. If instance A's p99 latency is 200ms and instance B's p99 is 800ms, there is no valid way to combine those two numbers into the correct fleet-wide p99 — averaging them, or taking the max, both produce numbers that don't correspond to any real, principled statistic over the combined set of requests both instances served. A histogram avoids this because what it actually exposes is raw counts per bucket, which are just numbers that add normally: the count of requests under 100ms across the whole fleet is simply the sum of each instance's count of requests under 100ms. Once Prometheus has summed the bucket counts across every instance, it can then compute one valid, fleet-wide percentile from that combined distribution. A client-side Summary skips straight to computing the percentile locally, which is fine for looking at one instance in isolation but has no mathematically sound way to be combined with another instance's percentile.
Concretely, why does an average latency number fail to reveal a real production problem that a p99 would catch immediately?
An average blends every observation into a single number where a small number of very bad outcomes get diluted by a large number of good ones. If 990 out of 1000 requests take 50ms and 10 take 7 seconds (because they happen to hit a lock, a slow downstream call, or a garbage collection pause), the average across all 1000 is roughly 120ms — a number that looks completely healthy and gives no hint that a meaningful number of users are experiencing multi-second waits. The p99, by construction, is defined by exactly the slowest 1% of requests, so those same 10 requests aren't diluted away — they directly determine the reported value, which in this case would be close to 7 seconds and immediately visible as a problem. Because real production slowness is very often caused by something that affects a small subset of requests severely (contention, a slow dependency for a subset of traffic, GC pauses) rather than something that slows every request slightly and uniformly, the tail percentiles are usually where the actual user-facing damage lives, and averages are structurally the wrong statistic to reveal it.
Why does a load balancer or orchestrator care about an aggregated health check rather than just checking whether the process is running?
Whether a process is running answers a much narrower question than whether that process can actually do useful work. A JVM can be fully alive, accepting TCP connections, and responding to a bare liveness ping, while its database connection pool is completely exhausted and every real request it receives times out or fails — from the outside, "process is up" gives no signal that this is happening. An aggregated health check that includes a HealthIndicator for the database connection pool, the cache, and any other hard dependency turns "can this instance do its job" into something that can actually be checked and answered before traffic is routed there. This is precisely why Kubernetes readiness probes and load balancer health checks are typically wired to a deeper endpoint like Spring Boot's aggregated /actuator/health rather than a trivial liveness ping — the entire point of the check is to catch the case where the process is technically alive but functionally broken, and stop sending it traffic before users hit the failure themselves.
Why is a trace ID embedded in every log line the specific mechanism that makes centralized, structured logging useful, rather than just having logs in one place?
Simply centralizing raw text log lines into one searchable store (Elasticsearch) already helps compared to per-instance files, but it only gets you full-text search — finding logs related to one specific failing checkout request still means guessing at keywords or timestamps and hoping they're unique enough, across every service the request might have touched. A shared trace ID, propagated across every service boundary the request crosses (an HTTP header on synchronous calls, a Kafka record header on asynchronous ones) and included as a structured field on every log line each service emits during that request's handling, gives you an exact join key. Once you have that, the path from "a trace waterfall shows payment-service's span failed" to "here is the exact exception payment-service logged for that failure" is a single filtered query on traceId, rather than a manual, time-window-based search across order-service, payment-service, inventory-service, and notification-service's logs and hoping none of the relevant lines got lost in the noise of everything else those services were doing at the same moment.
What does OpenTelemetry actually standardize, and what does it deliberately leave alone?
OpenTelemetry standardizes the generation, data model, and transport of telemetry — a common API your application code instruments against, a common wire format (OTLP) for sending spans, metrics, and logs, and a common propagation format for trace context across service boundaries. What it does not do is collapse metrics, logs, and traces into one undifferentiated thing, or dictate which backend you must store any of it in. A histogram emitted through OpenTelemetry is still fundamentally a histogram with the same aggregation trade-offs described earlier; a span is still a per-request causal record. What changes is that the instrumentation code producing all of this is no longer tied to a specific vendor's proprietary SDK, so pointing that same instrumented data at a different backend (swapping Jaeger for a different tracing store, for instance) is a configuration change to an OpenTelemetry Collector's exporters, not a re-instrumentation effort across every service in the system.
Why is "alert whenever the error budget's burn rate would exhaust it before the window resets" a better rule than "alert whenever any error occurs"?
Alerting on any error at all guarantees a constant stream of pages in any sufficiently large system, because at any given moment something, somewhere, is failing in some small way that's well within normal, expected variance — this trains whoever's on call to start ignoring alerts, which defeats the entire purpose of alerting. A burn-rate alert instead asks a more specific, more meaningful question: given the current rate of failures, will this consume the entire allotted error budget before the measurement window (say, 30 days) resets? A brief spike that resolves quickly barely touches the budget and correctly doesn't page anyone. A sustained, ongoing elevated error rate that would burn through a 30-day budget in a matter of hours is exactly the situation that needs a human's attention immediately, and the burn-rate calculation makes that distinction automatically and quantitatively, rather than relying on a fixed threshold that's either too sensitive (pages on noise) or too insensitive (misses a real, sustained degradation that hasn't yet crossed some arbitrary absolute error count).
