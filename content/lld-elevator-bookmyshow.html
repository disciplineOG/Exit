LLD #3: Elevator System / BookMyShow

State Pattern Strategy Pattern SCAN/LOOK Scheduling Concurrency Seat Holds / TTL Distributed Locking Resource Allocation
Why this matters

Both of these systems fail in the same way if you model them carelessly: someone writes if (state == IDLE) { ... } else if (state == MOVING) { ... } scattered across a dozen methods, and eventually a transition gets missed — a door opens while the elevator is moving, or two payment attempts both succeed against the same seat. Modeling state as an explicit, closed set of objects (rather than a mutable field checked ad hoc) turns "illegal transition" from a runtime bug into a compile-time impossibility. And the booking system's seat-hold mechanic is the same TTL-expiry idea from caching and rate limiting applied to a business-critical resource — understanding it here is what lets you reason correctly about why a "confirm seat" button that works fine in testing can silently double-book seats in production under real concurrent traffic.

1. The Elevator System — Entities and Requests

An elevator system is fundamentally a scheduling problem wearing physical clothing. Before touching algorithms, get the entity model right, because a sloppy entity model is what forces people into if/else soup later.

  • Elevator — has an id, a currentFloor, a Direction (UP, DOWN, IDLE), an internal ElevatorState (see Section 4), and a sorted collection of pending stops, typically split into two sets: stops above the current floor and stops below it.
  • ElevatorController (or ElevatorManager) — owns the fleet (a List<Elevator>), receives all incoming requests, decides which elevator services which request, and dispatches commands to elevators.
  • Request — split into two distinct types because they carry different information and originate from different places:
    • HallCall (external request) — pressed on a floor, outside any elevator. Carries originFloor and a desired Direction (UP or DOWN) — the person hasn't chosen an elevator yet, only a direction. This is what the controller uses to decide which elevator to send.
    • CabinRequest (internal request) — pressed inside a specific elevator's panel. Carries only a destinationFloor; direction is implied by comparing it to the elevator's current floor. There is no assignment decision here — the request belongs to the elevator whose button was pressed.
Why two request types, not one

Conflating them is a common modeling shortcut that breaks the scheduling algorithm. A hall call is a request for capacity — the system must choose which of several elevators responds, and that choice is what the assignment strategy in Section 3 is for. A cabin request has no such choice to make; it's simply added to the stop list of the elevator that received it. If you model both as "a floor number," you lose the direction intent of hall calls (a person on floor 5 wanting to go down should not be picked up by an elevator passing floor 5 going up, even though it stops there) and you lose the distinction between "which elevator should I dispatch" and "where does this specific elevator go next."

2. Scheduling Within One Elevator: SCAN / LOOK

Given a single elevator with a set of pending stops above and below it, in what order should it serve them? The naive approach — serve requests in the order they arrived (FIFO) — produces pathological behavior: an elevator on floor 1 asked to go to floor 10, then interrupted by a request for floor 2, would go 1 → 10 → 2, wasting enormous travel distance. The fix is to sort by geography, not by arrival time, and this is exactly the disk-scheduling SCAN/LOOK algorithm applied to a vertical shaft instead of a disk arm.

The general algorithm

  1. Maintain two ordered stop sets relative to the elevator's current position: upStops (a min-heap or sorted set of floors above current, so the nearest is served first) and downStops (a max-heap or sorted set of floors below current, nearest served first).
  2. While moving UP: serve every floor in upStops in ascending order — pick up hall calls requesting UP along the way, drop off cabin requests — until upStops is empty or a stop is reached that is the topmost requested floor.
  3. When upStops is exhausted, check downStops. If non-empty, reverse direction and repeat the process descending. If both are empty, transition to IDLE and await the next request.
  4. A new hall call is inserted into upStops or downStops based on where it lies relative to current floor and current direction — a call from a floor below the elevator, while the elevator is heading up, only gets added to the "serve on the way up" set if the call's direction is also UP and its floor is still ahead; otherwise it waits for the return sweep.

This is called LOOK (as opposed to pure SCAN) because the elevator only travels as far as the furthest requested floor in a direction before reversing — it doesn't senselessly travel to the physical end of the shaft (the top or bottom floor) if nobody requested it. Pure SCAN always sweeps to the boundary; LOOK "looks ahead" at the pending queue and reverses early. Every production elevator scheduling system uses some variant of LOOK, not naive SCAN, for exactly this reason.

Why this minimizes wait/travel time

The key insight is that reversing direction is the expensive operation — not distance traveled per se, but the number of direction changes, because each reversal means every request "behind" the elevator has to wait for a full round trip. SCAN/LOOK guarantees monotonic progress in one direction, so a request that lies "in front of" the elevator's current sweep gets served with zero extra travel — it's free, since the elevator was going that way anyway. The only requests that pay a wait penalty are ones behind the current direction of travel, and even those wait at most one full sweep, bounded by the shaft height, rather than an unbounded amount under FIFO ordering.

class Elevator {
    int currentFloor;
    Direction direction; // UP, DOWN, IDLE
    ElevatorState state; // Idle, Moving, DoorOpen (Section 4)
    TreeSet<Integer> upStops = new TreeSet<>();
    TreeSet<Integer> downStops = new TreeSet<>(Comparator.reverseOrder());

    void step() {
        if (direction == Direction.UP) {
            if (!upStops.isEmpty()) {
                currentFloor = upStops.pollFirst();
                openDoorAndServe();
            } else if (!downStops.isEmpty()) {
                direction = Direction.DOWN; // reverse only when the sweep is exhausted
            } else {
                direction = Direction.IDLE;
            }
        } else if (direction == Direction.DOWN) {
            // symmetric
        }
    }
}

3. Fleet Dispatch: Which Elevator Answers the Hall Call?

SCAN/LOOK solves ordering within one elevator. In a multi-elevator bank, there's a prior question: when a hall call arrives, which elevator gets it? This is a completely separate decision and should live in its own component so it can be swapped without touching per-elevator scheduling logic — a textbook application of the Strategy pattern.

interface ElevatorSelectionStrategy {
    Optional<Elevator> selectElevator(List<Elevator> fleet, HallCall call);
}

class NearestElevatorInDirectionStrategy implements ElevatorSelectionStrategy {
    public Optional<Elevator> selectElevator(List<Elevator> fleet, HallCall call) {
        return fleet.stream()
            .filter(e -> isUsable(e, call))
            .min(Comparator.comparingInt(e -> distanceCost(e, call)));
    }
}

class ElevatorController {
    private ElevatorSelectionStrategy strategy; // injected, swappable at runtime
    void onHallCall(HallCall call) {
        strategy.selectElevator(elevators, call)
                 .ifPresentOrElse(e -> e.addStop(call), () -> queueUnassigned(call));
    }
}

The "nearest elevator in the right direction" heuristic ranks candidate elevators by a cost function, typically preferring, in order:

  1. An elevator already moving toward the call's floor in the same direction the caller wants to go (it can pick them up for free, mid-sweep, with zero detour).
  2. An IDLE elevator, ranked by raw floor distance.
  3. An elevator moving away from the call (it will have to finish its sweep, reverse, and come back) — ranked last, and only chosen if no better option is free.
  4. An elevator already moving toward the floor but in the opposite direction of what the caller wants is usually excluded entirely from immediate assignment — it will pass the floor without being able to serve the request, since its cabin is committed to its current directional sweep.
Why Strategy, not a hardcoded method

Real dispatch systems tune this constantly: weight by current cabin load to avoid overloading one car, reserve one elevator for a fire-service or VIP mode, or switch to a zoned strategy during peak hours (each elevator owns a fixed floor range). None of that should require touching Elevator or the SCAN logic — it's purely a different implementation of selectElevator. This mirrors why you'd inject a rate-limiting algorithm rather than hardcode it, as covered in rate limiter design — the selection policy and the mechanism it acts on are different axes of change and should vary independently.

4. The State Pattern: Elevator Lifecycle

An elevator's behavior depends entirely on its current phase, and several transitions must be structurally forbidden: you cannot move while the door is open, you cannot accept new floor stops while doors are opening for safety-interlock reasons in some designs, and a door cannot "close" from Idle because it was never open. Representing state as an enum field checked with conditionals means every one of these invariants has to be manually re-verified at every call site that touches the field — miss one, and you get a door-open-while-moving bug that's a safety issue, not just a UI glitch.

The State pattern fixes this by making each state its own class implementing a common interface, where each state only exposes the transitions that are legal from it:

interface ElevatorState {
    ElevatorState requestMove(Elevator ctx);
    ElevatorState arriveAtFloor(Elevator ctx);
    ElevatorState openDoor(Elevator ctx);
    ElevatorState closeDoor(Elevator ctx);
}

class IdleState implements ElevatorState {
    public ElevatorState requestMove(Elevator ctx) { return new MovingState(); }
    public ElevatorState openDoor(Elevator ctx) { return new DoorOpenState(); }
    public ElevatorState arriveAtFloor(Elevator ctx) { return this; } // no-op, already idle
    public ElevatorState closeDoor(Elevator ctx) {
        throw new IllegalStateException("Door is not open");
    }
}

class MovingState implements ElevatorState {
    public ElevatorState requestMove(Elevator ctx) { return this; } // already moving
    public ElevatorState openDoor(Elevator ctx) {
        throw new IllegalStateException("Cannot open door while moving");
    }
    public ElevatorState arriveAtFloor(Elevator ctx) {
        return ctx.hasPendingStops() ? this : new IdleState();
    }
    public ElevatorState closeDoor(Elevator ctx) { return this; }
}

class DoorOpenState implements ElevatorState {
    public ElevatorState closeDoor(Elevator ctx) { return new MovingState(); }
    public ElevatorState requestMove(Elevator ctx) {
        throw new IllegalStateException("Cannot move with door open");
    }
    public ElevatorState arriveAtFloor(Elevator ctx) { return this; }
    public ElevatorState openDoor(Elevator ctx) { return this; }
}

The controller never checks "what state am I in" — it just calls elevator.getState().requestMove(elevator) and reassigns the returned state. Every illegal transition either doesn't compile as a reachable path or throws immediately at the point of misuse, instead of silently corrupting the elevator's physical behavior three method calls later.

5. The Booking System — Entities

Switch domains but keep the same discipline. A ticket-booking system's core entities:

  • Movie — static metadata (title, duration, language, certification).
  • Theater — a physical venue with one or more Screens, each with a fixed seating layout.
  • Show — the actual bookable unit: a Movie + Screen + start time slot. This is the entity that owns seat inventory for that specific showing — the same physical seat A12 is a completely independent bookable resource per Show, not per Theater.
  • Seat — belongs to a Show (or references a Screen seat template plus per-show status), with a SeatStatus: AVAILABLE, HELD, or BOOKED.
  • Booking — a confirmed transaction: user, show, list of seats, payment reference, timestamp.

The entity that deserves the most design attention isn't any of these nouns — it's the seat's status field, because that's where concurrent users collide.

6. The Core Concurrency Problem: Double-Booking

Picture the obvious, wrong implementation: a user selects seat A12, the backend checks if (seat.status == AVAILABLE), and if true, proceeds to build a booking and eventually sets seat.status = BOOKED once payment succeeds. This is a classic check-then-act race condition.

How the race actually plays out

Two users, A and B, both request seat A12 for the same show within milliseconds of each other, hitting two different application server instances (or even the same instance on two threads). Both read status == AVAILABLE before either has written anything back — the check and the eventual write are separated by an entire payment flow that can take 30+ seconds. Both proceed to payment. Both payments succeed independently, because nothing has told either payment gateway that the seat is contested. Both bookings get written as CONFIRMED. The theater now has two people holding tickets for one physical seat. The bug isn't in the payment integration or the UI — it's that "check availability" and "commit the booking" are not atomic, and the gap between them is wide enough (an entire external payment round trip) that collisions aren't rare edge cases, they're routine under any real load.

Note that this is structurally identical to the lost-update problem discussed with optimistic/pessimistic locking in concurrency and multithreading — the difference here is that the "critical section" spans an external, slow, unreliable step (payment), so you cannot simply wrap it in a database transaction or a synchronized block and hold a lock for 30 seconds without destroying throughput for every other seat on that show.

The fix: a short-lived seat hold with a TTL

The standard resolution is to introduce a third state between AVAILABLE and BOOKED: HELD. The moment a user clicks "proceed to checkout" — before payment even starts — the system atomically transitions the seat from AVAILABLE to HELD and stamps an expiry (typically 5–10 minutes out). This has two effects: no other user can select that seat while it's held, and if the user abandons checkout or payment fails, the hold expires on its own and the seat reverts to AVAILABLE without anyone having to remember to clean it up.

This is the same TTL-expiry mechanic used in cache eviction (see TTL caches and rate limiters), applied to a business resource instead of a cache entry. Two implementation strategies are common:

ApproachMechanismTrade-offs
Status + expiry column UPDATE seats SET status='HELD', held_by=?, expires_at=? WHERE seat_id=? AND status='AVAILABLE' — the WHERE status='AVAILABLE' clause makes the transition atomic and conditional at the database level; if zero rows are affected, someone else won the race. A background sweeper job (or a check on every read) treats any HELD seat whose expires_at has passed as effectively AVAILABLE again. No extra infrastructure — reuses the relational store. Requires either a periodic sweep job or defensive "is this hold actually expired" checks on every read path, since the row doesn't disappear automatically the instant the TTL elapses.
Distributed lock (e.g. Redis key with SET seat:{id} {userId} NX PX 600000) The lock's existence is the hold; Redis expires the key automatically at the TTL, no sweeper needed. NX (set-if-not-exists) gives the same atomic conditional-write guarantee as the SQL WHERE clause. True automatic expiry with no polling. Introduces a second system that must stay consistent with the database's notion of seat status — on payment success you must both confirm the booking in the database and release/convert the Redis lock, and that pair of writes is itself not atomic unless handled carefully (e.g. confirm-then-delete-lock, tolerating a brief window where both exist).
Why the conditional write matters more than the lock itself

The actual concurrency safety doesn't come from "using Redis" or "using a status column" as such — it comes from making the AVAILABLE→HELD transition a single atomic conditional operation (NX, or a WHERE status = 'AVAILABLE' guard) so that when two requests race, exactly one of them observes success and the other observes failure at the same instant it attempts the write, rather than both observing success at read-time and only discovering the conflict much later. This is the general fix for check-then-act races anywhere in a system: collapse the check and the act into one atomic operation instead of performing them as two separate steps with a gap in between.

Sequence with holds

User A: SELECT seat A12 -> attempt HOLD (atomic) -> SUCCESS -> pay -> CONFIRM -> status=BOOKED
User B: SELECT seat A12 -> attempt HOLD (atomic) -> FAILS (already HELD) -> shown "seat taken"

// If User A abandons checkout:
[TTL expires] -> status reverts HELD -> AVAILABLE (via sweep or key expiry)

7. The State Pattern Applied to Seats

Just as with the elevator, the seat's lifecycle is a small closed set of states with strict legal transitions, and modeling it explicitly prevents an entire category of bug where a seat gets booked twice or a hold gets confirmed after it already expired.

interface SeatState {
    SeatState hold(SeatContext ctx, String userId);
    SeatState confirmBooking(SeatContext ctx, String userId);
    SeatState release(SeatContext ctx);
}

class AvailableState implements SeatState {
    public SeatState hold(SeatContext ctx, String userId) {
        ctx.setHeldBy(userId);
        ctx.setExpiresAt(now().plusMinutes(10));
        return new HeldState();
    }
    public SeatState confirmBooking(SeatContext ctx, String userId) {
        throw new IllegalStateException("Cannot book a seat with no active hold");
    }
    public SeatState release(SeatContext ctx) { return this; }
}

class HeldState implements SeatState {
    public SeatState hold(SeatContext ctx, String userId) {
        throw new IllegalStateException("Seat already held");
    }
    public SeatState confirmBooking(SeatContext ctx, String userId) {
        if (ctx.isExpired()) {
            return new AvailableState().hold(ctx, userId); // hold lapsed; caller must retry
        }
        if (!ctx.getHeldBy().equals(userId)) {
            throw new IllegalStateException("Held by a different user");
        }
        return new BookedState();
    }
    public SeatState release(SeatContext ctx) { return new AvailableState(); }
}

class BookedState implements SeatState {
    public SeatState hold(SeatContext ctx, String userId) {
        throw new IllegalStateException("Seat already booked");
    }
    public SeatState confirmBooking(SeatContext ctx, String userId) { return this; }
    public SeatState release(SeatContext ctx) {
        throw new IllegalStateException("Cannot release a confirmed booking directly");
    }
}

Notice that confirmBooking re-checks expiry and ownership inside the state transition itself, rather than trusting that the caller already validated those things — because the caller's validation and this call are separated by the payment gateway round trip, during which the hold could have expired. The state object is the last line of defense, and it's exactly one atomic check away from the underlying storage-level conditional write described in Section 6 — the in-memory state machine and the database-level atomic transition are two layers enforcing the same invariant, which is the correct amount of redundancy for a bug class this costly (a double-booked seat usually means a refund, an angry customer, and a support escalation, not just a retried request).

Both systems illustrate the same broader lesson applicable to almost any resource-allocation system (parking spot assignment has the identical "many seekers, one exclusive resource, need atomic acquisition" shape): identify the finite state machine of the contended resource first, make transitions explicit objects rather than flags, and only then layer scheduling or assignment policy on top as a separate, swappable concern.

Concepts Worth Being Able to Explain From First Principles

Why does LOOK reverse direction only when the pending-stop set in the current direction is empty, rather than reversing whenever a closer request appears behind the elevator?
Because reversing mid-sweep to chase a "closer" request behind the elevator would reintroduce the exact pathology SCAN/LOOK exists to avoid: unbounded direction changes driven by arrival order rather than geography. If the elevator reverses every time a nearer-but-behind request shows up, a steady trickle of such requests could keep it oscillating near one region of the shaft indefinitely, starving requests further along its original sweep. Committing to finish the current directional sweep before reversing guarantees every request gets served within one full up-down cycle, which is the actual fairness and worst-case-wait guarantee the algorithm provides. The trade-off is that a request appearing just behind the elevator has to wait for the return trip — but that wait is bounded, whereas the alternative's worst case is not.
In the elevator selection strategy, why exclude an elevator moving toward the requested floor but in the opposite direction of what the caller wants?
Because that elevator's cabin is already committed to a directional sweep and won't stop to reverse just for one hall call — physically, and by the LOOK algorithm's own rules, it will pass that floor without opening its doors for a call going the other way (someone on floor 5 wanting to go up won't be picked up by a car passing floor 5 while descending). Assigning the call to that elevator anyway would mean the call sits unserved until the elevator finishes its current sweep, reverses, and comes back — which is often worse than assigning it to a genuinely idle elevator or one already heading the correct direction, even if that one is technically farther away in raw floor distance. This is exactly why the cost function in a dispatch strategy needs to reason about direction and commitment, not just Euclidean floor distance.
Why is "check if seat is available, then book it" unsafe even inside a single database transaction with default isolation?
Because the dangerous gap in a booking flow isn't a few milliseconds of database processing — it's the entire external payment round trip, which can take tens of seconds and cannot be held open inside a single database transaction without holding locks that long and destroying concurrency for every other request touching that show's seats. Even under a strict isolation level, a transaction that reads "available," returns control to the application, waits on a payment gateway, and only then writes "booked" leaves the read and the write as two separate transactions from the database's point of view (or one absurdly long-lived one), during which another transaction can freely read the same "available" state and proceed identically. Correctness requires making the state transition itself — not the surrounding business logic — atomic and conditional, exactly as the AVAILABLE-to-HELD hold does at the moment checkout begins, well before payment is even attempted.
What actually goes wrong if a seat hold expires while payment is mid-flight, and how does the design handle it without corrupting data?
If the TTL fires while the user is still in the payment gateway, the seat reverts to AVAILABLE and another user can legitimately acquire a fresh hold on it — the system deliberately favors availability of inventory over indefinitely trusting a possibly-abandoned session. The subtlety is in what happens when the first user's payment then succeeds a moment later: the confirmation step must re-check, atomically, whether the hold is still valid and still owned by that user before marking the seat BOOKED. If it isn't (because it expired and was reassigned), the confirmation must fail gracefully — refund or void the charge — rather than blindly setting status to BOOKED and silently overwriting whatever the second user is now doing with that seat. This is why the state object's confirmBooking method re-validates expiry and ownership internally rather than trusting a stale check performed before payment started.
Why model HallCall and CabinRequest as distinct types instead of one generic Request with an optional direction field?
Because they participate in different decisions and merging them either loses information or forces awkward null-checking. A hall call needs a direction because the controller must decide which elevator to dispatch, and direction is the caller's stated intent before any elevator is involved. A cabin request has no such ambiguity — it was pressed inside a specific car, so there's no assignment decision to make, only an insertion into that car's stop list, and its "direction" is entirely derived from comparing the destination to the car's current floor. Treating them as one type with a nullable direction field means every piece of code that consumes a Request has to first figure out which kind it's looking at before it can act correctly, which is exactly the kind of implicit, easy-to-forget branching that a clean type split avoids.
Why put the seat's status transition logic inside State pattern objects instead of just adding an expiry check to a single method that also updates the database?
A single procedural method can enforce one invariant correctly today but tends to accumulate special cases as new transitions are added — cancellations, admin overrides, partial refunds — each requiring another nested conditional that checks the current status before proceeding. Splitting the states into their own classes means each transition method only needs to reason about the rules for leaving one specific state, which is a much smaller and more reviewable unit, and adding a new global rule (like re-validating expiry) is done once per relevant state rather than threaded through one large method's branching logic. It also means the compiler and the type system, not a comment or a code review, are what prevent a call site from invoking a transition that state doesn't support.
Does using a distributed lock like Redis for seat holds eliminate the need for a status column in the database, or do you need both?
In practice you need both, because they answer different questions with different reliability guarantees. The Redis key with a TTL is the fast, self-expiring mechanism that adjudicates concurrent hold attempts and automatically reclaims abandoned holds without a background job. But the database row is the durable source of truth for what actually got booked — Redis is not typically the system of record for financial/booking data, and if the cache is flushed, evicted under memory pressure, or the process restarts before persistence, you don't want the authoritative record of a paid booking to have vanished with it. The pattern is: use the lock to serialize the hold attempt, and once payment succeeds, write the confirmed booking to durable storage as the definitive record, treating the lock's job as done at that point.
