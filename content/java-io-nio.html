Java I/O & NIO: Files, Channels, Buffers & Non-Blocking I/O

java.io NIO.2 Channels & Buffers Selectors Memory-Mapped Files Non-Blocking I/O
Why this matters

Every ShopSphere service reads and writes bytes constantly — order-service persists audit logs, catalog-service exports a nightly product CSV to sellers, notification-service holds open thousands of long-lived connections to push order-status updates to customer devices — and the I/O model each of these chooses has direct, measurable consequences for memory and throughput under load. A naive Files.readAllBytes on a multi-gigabyte export file will OOM a container that runs fine in every test environment with a small fixture file. A thread-per-connection notification service that works with 500 concurrent devices can fall over at 50,000 not because the code is wrong, but because the underlying I/O model doesn't scale that way. Understanding streams versus buffers, blocking versus non-blocking I/O, and what a Selector actually does is what lets you predict these failures before they happen in production, and it's also the exact mechanism underneath why Spring WebFlux and Netty behave so differently from a traditional servlet container under heavy concurrent load.

1. Classic java.io: Streams, Readers/Writers, and Buffering

The original java.io package, present since Java 1.0, models I/O as a stream — a one-directional, sequential flow of data that you read from or write to, one chunk at a time, with no ability to go backward or jump around. InputStream and OutputStream are the byte-oriented base classes: every concrete implementation (FileInputStream, FileOutputStream, ByteArrayInputStream, the stream side of a Socket) ultimately reduces to reading or writing raw bytes, one at a time or into a byte array via read(byte[] buf)/write(byte[] buf). Reader and Writer are the parallel character-oriented hierarchy, introduced specifically to handle text correctly: a Reader decodes bytes into chars using a specified character encoding (UTF-8, ISO-8859-1, and so on), which matters enormously once you have product descriptions or seller names in ShopSphere's catalog that contain non-ASCII characters — reading those bytes through a raw InputStream and manually slicing them would corrupt multi-byte UTF-8 sequences at chunk boundaries, while a properly configured InputStreamReader handles the decoding correctly regardless of where a chunk boundary happens to fall.

A critical, easy-to-miss detail is that an unbuffered stream is often catastrophically slow, because each call to read() or write() can trigger a system call — a transition into the operating system kernel to actually touch the file descriptor or socket. A loop that calls fileInputStream.read() one byte at a time to parse a product-export CSV in catalog-service would issue one system call per byte, which is orders of magnitude slower than issuing one system call per, say, 8 kilobytes. BufferedInputStream and BufferedOutputStream (and their character equivalents BufferedReader/BufferedWriter) wrap an underlying stream and interpose an in-memory byte array: reads pull a full buffer's worth of data from the underlying stream in one system call and then serve subsequent small reads out of that in-memory array until it's exhausted, and writes accumulate into the buffer and flush to the underlying stream only when the buffer fills or flush()/close() is called. This is why almost every idiomatic use of java.io wraps the raw stream immediately:

try (BufferedReader reader = new BufferedReader(
        new InputStreamReader(new FileInputStream("products-export.csv"), StandardCharsets.UTF_8))) {
    String line;
    while ((line = reader.readLine()) != null) {
        processProductRow(line);
    }
} catch (IOException e) {
    log.error("Failed to read product export", e);
}

try-with-resources and why closing actually matters

Every stream, reader, writer, and socket ultimately holds a scarce operating-system resource — a file descriptor, or a socket handle — and the operating system imposes a hard limit on how many a single process can have open at once (commonly a few thousand by default on Linux, tunable via ulimit). If code opens a FileInputStream to read a seller's uploaded product image and an exception is thrown partway through processing, and the stream was never closed in a finally block, that file descriptor leaks — it stays allocated to the process until the JVM's finalizer eventually runs (which is not guaranteed to happen promptly, and finalizers are deprecated for removal) or the process exits. A service under load that leaks one file descriptor per failed request will, given enough failures, exhaust its descriptor limit entirely, at which point every subsequent attempt to open a file or accept a socket connection fails with "too many open files" — a fully self-inflicted outage that has nothing to do with disk space or memory.

The try-with-resources statement, introduced in Java 7, exists specifically to make this leak structurally impossible to write by accident. Any class implementing AutoCloseable (which includes essentially every I/O type, plus JDBC's Connection/Statement/ResultSet) can be declared in the parentheses of a try, and the compiler guarantees close() is called when the block exits — whether it exits normally, via a checked exception, an unchecked exception, or a return statement buried three levels deep in a conditional. Multiple resources can be declared together, separated by semicolons, and they are closed in reverse declaration order, which matters when one resource wraps another (closing the outer BufferedReader should happen before the underlying FileInputStream, and try-with-resources gets this ordering right automatically).

A finally block without try-with-resources is easy to get subtly wrong

Manually written cleanup code like InputStream in = null; try { in = new FileInputStream(f); ... } finally { in.close(); } throws a NullPointerException in the finally block if the constructor itself failed and in is still null, and if close() itself throws, that exception silently replaces (masks) whatever original exception was being propagated from the try block — losing the real root cause. try-with-resources handles both cases correctly out of the box: it never calls close() on a resource whose initializer failed, and if both the body and close() throw, the body's exception is the one propagated, with the close exception attached as a "suppressed" exception (visible via Throwable.getSuppressed()) rather than silently discarded.

2. NIO.2: The Files/Path API as the Modern Replacement for java.io.File

Java 7's NIO.2 (java.nio.file) was introduced because java.io.File has real, long-standing problems: most of its methods (like delete() or mkdir()) return a bare boolean on failure instead of throwing an exception that explains why it failed, it has no direct support for symbolic links, and several of its operations are not atomic, which matters a great deal for correctness under concurrent access. Path replaces File as the representation of a filesystem location, and the Files utility class provides the actual operations as static methods, most of which throw a specific, informative IOException subtype on failure rather than returning an ambiguous false.

For reading whole files into memory when the file is known to be small — a configuration file, a small lookup table — Files.readAllLines(Path) and Files.readString(Path) are direct, low-ceremony replacements for the old pattern of manually wrapping a BufferedReader and looping. But the far more important addition for a backend engineer is Files.lines(Path), which returns a lazily-evaluated Stream<String> that reads the file incrementally as the stream is consumed, and Files.walk(Path), which lazily traverses a directory tree and returns a Stream<Path> without ever materializing the full tree in memory — invaluable when scanning, for example, a directory of nightly catalog-export archives that may span years.

// Lazily stream a large export file instead of loading it into a List<String>
try (Stream<String> lines = Files.lines(exportPath, StandardCharsets.UTF_8)) {
    long errorCount = lines
        .skip(1) // header row
        .filter(line -> !isValidProductRow(line))
        .count();
}

// Lazily walk a directory tree of nightly export archives
try (Stream<Path> paths = Files.walk(archiveRoot)) {
    paths.filter(p -> p.toString().endsWith(".csv.gz"))
         .forEach(this::registerArchiveForRetentionCheck);
}

Both Files.lines and Files.walk return streams backed by an open file handle or directory handle, so they must be used inside try-with-resources exactly like a raw InputStream — forgetting this is a common source of the same file-descriptor leak described in section 1, just dressed up in Stream API syntax.

Atomic file operations

NIO.2 exposes atomic move and rename semantics that java.io.File.renameTo() never reliably guaranteed across platforms. Files.move(source, target, StandardCopyOption.ATOMIC_MOVE) asks the filesystem to perform the rename as a single, indivisible operation — no other process or thread can ever observe a partially-written or half-renamed file at the target path. This is exactly the pattern catalog-service should use when generating a product-export CSV: write the full file to a temporary path (products-export.csv.tmp), and only once writing is fully complete and flushed, atomically move it to the path that downstream consumers (a scheduled job, or a seller-facing download endpoint) actually read from. Without the atomic move, a consumer that happens to open the file while it's still being written would read a truncated, invalid CSV — a bug that only reproduces under a specific timing window and is miserable to track down after the fact.

Path tmp = exportDir.resolve("products-export.csv.tmp");
Path target = exportDir.resolve("products-export.csv");
try (BufferedWriter writer = Files.newBufferedWriter(tmp, StandardCharsets.UTF_8)) {
    writeAllProductRows(writer);
}
Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE, StandardCopyOption.REPLACE_EXISTING);

WatchService: reacting to filesystem changes

The WatchService API lets an application register interest in a directory and be notified when entries are created, modified, or deleted, without polling the directory on a timer. A WatchKey is registered against a Path for specific event kinds (ENTRY_CREATE, ENTRY_MODIFY, ENTRY_DELETE), and a thread calls watchService.take() (a blocking call) to wait for the next batch of events. A realistic ShopSphere use is a local drop-folder integration where a legacy seller-onboarding tool writes bulk product-upload files to a shared directory that an import job needs to pick up as soon as they land, rather than on a fixed polling interval that either wastes CPU checking too often or adds unnecessary latency checking too rarely.

WatchService watcher = FileSystems.getDefault().newWatchService();
dropFolder.register(watcher, StandardWatchEventKinds.ENTRY_CREATE);

while (true) {
    WatchKey key = watcher.take(); // blocks until an event is available
    for (WatchEvent<?> event : key.pollEvents()) {
        Path newFile = dropFolder.resolve((Path) event.context());
        importJob.submit(newFile);
    }
    key.reset(); // required to receive further events on this key
}

3. The Core NIO Model: Buffer, Channel, and Selector

Beyond the file-path convenience of NIO.2, the original NIO (New I/O, Java 1.4) introduced a fundamentally different model for the data-movement primitives themselves, built around three abstractions: Buffer, Channel, and Selector. This model is not just a different API for the same operations — it changes what's actually possible, and it's the foundation Tomcat's NIO connector, Netty, and ultimately Spring WebFlux are built on.

Buffer: a fixed-size, randomly-accessible container, not a flow

A classic InputStream is a pure sequential flow — you can only ever read the next byte, never look backward or seek to an arbitrary offset. A Buffer (ByteBuffer being the most common) is fundamentally different: it's a fixed-capacity, in-memory array with three cursors that track how it's being used — position (the index of the next element to read or write), limit (the index of the first element that should not be read or written), and capacity (the buffer's fixed total size, set at creation and never changed). Because it's backed by an addressable array, code can call buffer.get(index) to read an arbitrary offset directly, or use mark()/reset() to remember and rewind to a position — none of which a stream supports.

The trap every NIO beginner falls into is the read/write mode switch. A freshly created or just-written-to buffer is in "write mode" — position marks how much has been written, and limit equals capacity. To then read back what was written, the buffer must be flipped: buffer.flip() sets limit to the current position (so reading can't run past what was actually written) and resets position to zero (so reading starts from the beginning). Forgetting to call flip() before reading is the single most common NIO bug, and it silently produces either an empty read or a read of stale/garbage data past the real content, because without it, position is still sitting at the end of the just-written data and limit is still capacity.

ByteBuffer buffer = ByteBuffer.allocate(1024);
int bytesRead = channel.read(buffer);   // fills buffer, position advances, limit == capacity
buffer.flip();                          // now: limit = position (end of real data), position = 0
while (buffer.hasRemaining()) {
    byte b = buffer.get();              // reads real data only, up to limit
}
buffer.clear();                         // reset position = 0, limit = capacity, ready to write again
clear() versus compact()

clear() resets a buffer to empty for writing but does not erase the old bytes — it just resets the cursors, so any unread data still sitting between the old position and limit is silently discarded from the buffer's perspective. compact() is the safer choice when a buffer might still contain unread bytes (common in non-blocking network code, where a partial message can be read in one pass and the rest arrives later): it shifts any unread remaining bytes to the start of the buffer and repositions the cursors so writing resumes right after them, preserving that unread data instead of losing it.

Channel: a bidirectional, block-oriented conduit

A Channel (FileChannel, SocketChannel, ServerSocketChannel) represents an open connection to an entity capable of I/O — a file, a socket, a pipe. The key structural difference from a stream is that a single Channel can typically be used for both reading and writing (a SocketChannel reads incoming bytes and writes outgoing bytes over the same underlying connection), whereas java.io forces a strict split into separate InputStream and OutputStream objects even when they represent the two directions of the exact same socket. Channels always transfer data into or out of Buffers — there's no channel method that reads "the next byte"; every read or write operation moves a block of bytes between the channel and a buffer in one call, which is inherently more efficient for bulk transfer and is also what makes non-blocking mode possible (section 5), since a non-blocking channel read returns immediately with however many bytes were currently available rather than blocking until a full buffer's worth arrives.

Selector: one thread, many channels, readiness-driven dispatch

A Selector is the piece that makes NIO fundamentally different in scale from classic blocking I/O. A channel can be registered with a Selector along with an interest set — which readiness events it cares about (OP_ACCEPT for a server socket ready to accept a new connection, OP_READ for a socket with incoming bytes ready to be read, OP_WRITE for a socket ready to accept more outgoing bytes without blocking). A single thread then calls selector.select(), which blocks (efficiently, via an OS-level mechanism like epoll on Linux or kqueue on macOS/BSD) until at least one registered channel becomes ready for one of its interested operations, and returns the set of ready channels. That one thread then iterates only the channels that are actually ready, does a small, non-blocking amount of work on each, and calls select() again.

This is precisely the mechanism underneath a Tomcat NIO connector and underneath Netty's EventLoop: instead of dedicating one OS thread per open connection (most of which, at any given instant, have nothing to do — a customer's device connected to notification-service that's just sitting idle waiting for the next order update), a small, fixed number of threads (often one per CPU core) take turns servicing whichever connections currently have actual work ready, and the OS itself does the work of tracking readiness across potentially tens of thousands of file descriptors far more efficiently than a naive per-connection polling loop ever could.

Selector selector = Selector.open();
serverChannel.configureBlocking(false);
serverChannel.register(selector, SelectionKey.OP_ACCEPT);

while (running) {
    selector.select(); // blocks until >=1 channel is ready
    Iterator<SelectionKey> keys = selector.selectedKeys().iterator();
    while (keys.hasNext()) {
        SelectionKey key = keys.next();
        keys.remove();
        if (key.isAcceptable()) { acceptNewDeviceConnection(key); }
        else if (key.isReadable()) { readAvailableBytes(key); }
    }
}

4. Memory-Mapped Files: Letting the OS Page Cache Do the Work

FileChannel.map() returns a MappedByteBuffer, which represents a region of a file mapped directly into the JVM process's virtual address space. Reading or writing bytes through this buffer is not a normal read()/write() system call at all — it's a direct memory access, and the operating system's virtual memory subsystem transparently handles bringing the relevant pages of the file into physical memory (the page cache) on first access (a page fault) and writing modified pages back to disk lazily, on its own schedule, or when explicitly forced via force().

The practical benefit is significant for large, randomly-accessed, or repeatedly-accessed files: normal I/O requires copying data from the kernel's page cache into a user-space buffer on every read (and the reverse on every write), whereas a memory-mapped file lets application code read and write the page-cache-backed memory directly, skipping that copy entirely. It also means the operating system's existing, highly-tuned page cache and readahead logic does the actual disk-scheduling work, and multiple processes mapping the same file share the same underlying physical pages, which is useful for large shared read-only datasets. A large ShopSphere product-image cache file or a large local search index built by catalog-service are realistic candidates: instead of a service manually managing its own in-memory cache of file contents, mapping the file lets the OS manage which pages are actually resident in physical memory based on real access patterns, and eviction under memory pressure is handled by the same mechanism that manages every other process's memory on the machine.

try (FileChannel channel = FileChannel.open(indexPath, StandardOpenOption.READ)) {
    MappedByteBuffer buffer = channel.map(FileChannel.MapMode.READ_ONLY, 0, channel.size());
    int magic = buffer.getInt(0);          // direct memory read, no explicit read() syscall
    long offset = buffer.getLong(4096);    // random access anywhere in the mapped region
}
Memory-mapped files are not a silver bullet

A MappedByteBuffer consumes address space and, once pages are touched, physical memory (page cache) proportional to how much of the file is actually accessed — mapping a 50 GB file doesn't allocate 50 GB up front, but heavy random access across a file much larger than available RAM will thrash the page cache no differently than any other memory-pressure scenario. There is also no reliable, portable way to explicitly unmap a MappedByteBuffer before Java 21's more disciplined memory-segment APIs — the underlying mapping is historically released only when the buffer becomes unreachable and is garbage collected, which has caused real production issues on Windows specifically, where a mapped file cannot be deleted or truncated while any mapping onto it is still active.

5. Blocking vs. Non-Blocking I/O: The Thread-per-Connection Trade-off

Classic blocking I/O follows the thread-per-connection model: when a request arrives, a thread is dedicated to it, and any I/O call that thread makes — reading from a socket, waiting on a database query, calling a slow downstream service — blocks that thread, meaning the OS scheduler simply parks it and gives the CPU to something else until the data is ready. This model is simple to write and reason about — code reads top to bottom in the natural order of "read request, do work, write response" — but its scalability is bounded directly by how many threads the process can afford to keep, because each thread carries real, fixed overhead: typically around 1 MB of stack space by default (configurable, but rarely worth shrinking far), plus the cost of context-switching between threads as the OS scheduler rotates the CPU across all of them. A traditional blocking servlet container handling 10,000 concurrent slow clients (imagine 10,000 customer devices each holding open a long-lived connection to notification-service waiting for the next order-status push) would need on the order of 10,000 live threads, most of which are simply blocked waiting for the next event — that's roughly 10 GB of stack memory reserved for threads doing nothing at any given instant, and a scheduler paying real context-switch overhead cycling through all of them.

Non-blocking I/O, built on the Channel/Selector model from section 3, inverts this: a small, fixed pool of threads (an event loop, often sized to the number of CPU cores) never blocks on I/O at all. Instead, each thread asks the Selector "which of these thousands of registered channels currently has actual work ready?", processes only those, and immediately loops back to ask again — the thread is never sitting idle holding a stack reserved for a connection that has nothing to do. The concrete throughput and memory trade-off is exactly the one implied above: a handful of event-loop threads (say, 8, one per core) can service tens of thousands of mostly-idle connections with a small, roughly constant memory footprint, because memory usage scales with actual in-flight work rather than with the number of open connections. This is precisely why Netty (and Spring WebFlux, which runs on Netty by default) scales differently from a traditional blocking servlet container under many concurrent slow clients: WebFlux's reactive pipeline is written so that no thread ever blocks waiting on I/O, so the same small thread pool that handles 100 connections can, memory permitting, handle 100,000 without needing 100,000 threads.

Non-blocking I/O is not automatically "faster" — it's a different scaling curve

For a small number of connections doing CPU-heavy work per request, thread-per-connection can be just as fast or faster, since each request genuinely gets a dedicated thread with no event-loop scheduling overhead or callback indirection. The advantage of the non-blocking/event-loop model shows up specifically at high connection counts with a high proportion of idle-waiting time per connection — long-lived, low-traffic connections being the textbook case. Choosing WebFlux for a CPU-bound, low-concurrency internal batch job would add real complexity (reactive chains, backpressure, harder debugging) for no throughput benefit; choosing a blocking servlet stack for notification-service's tens of thousands of idle device connections would require a thread-pool size that simply doesn't fit in reasonable memory. The choice should follow the actual connection-count and idle-time shape of the workload, not a blanket "non-blocking is more modern" assumption.

6. ShopSphere in Practice: Streaming Exports and Long-Lived Connections

catalog-service: streaming a product export instead of loading it into memory

Suppose catalog-service needs to generate a nightly CSV export of every product in the catalog for sellers to download — potentially millions of rows once ShopSphere has been running for a few years. The naive implementation queries all products into a List<Product>, builds the entire CSV as a String or StringBuilder, and writes it out in one shot; this works fine against a small test dataset and then fails in production with an OutOfMemoryError the first time the catalog grows large enough that the full in-memory representation (query results plus the string being built) no longer fits in the heap. The fix is to never materialize the whole thing at once: stream rows from the database using a cursor-based or paginated query, and write each row directly to a BufferedWriter wrapping the output file as soon as it's fetched, so at any instant memory holds only the current page of rows plus the buffer's fixed-size internal array, regardless of whether the catalog has one thousand or ten million products.

try (BufferedWriter writer = Files.newBufferedWriter(tmpExportPath, StandardCharsets.UTF_8)) {
    writer.write("productId,name,price,sellerId\n");
    int page = 0;
    Page<Product> batch;
    do {
        batch = productRepository.findAll(PageRequest.of(page++, 1000));
        for (Product p : batch) {
            writer.write(p.getId() + "," + escapeCsv(p.getName()) + "," + p.getPrice() + "," + p.getSellerId());
            writer.newLine();
        }
    } while (batch.hasNext());
}
Files.move(tmpExportPath, finalExportPath, StandardCopyOption.ATOMIC_MOVE);

Note the two techniques from earlier sections working together here: bounded, paginated reads keep memory flat regardless of catalog size, and the atomic move at the end ensures a seller or scheduled downstream job never sees a partially-written export file.

notification-service: a Netty-based non-blocking connector for long-lived device connections

notification-service maintains a long-lived connection per active customer device so it can push order-status events (OrderPlaced, OrderShipped, PaymentFailed) the moment they arrive off Kafka, rather than making devices poll on an interval. If this were built on a traditional blocking servlet stack, each open device connection would tie up a dedicated thread for as long as that device stays connected — potentially hours — the vast majority of that time spent doing nothing but waiting for the next event, which is exactly the thread-per-connection memory problem from section 5 at its worst: a customer base of a few hundred thousand simultaneously-online devices would require a similarly enormous thread pool. Built on Netty instead, a small, fixed set of event-loop threads (backed directly by the Channel/Selector model from section 3) holds all of those connections open simultaneously; each device's SocketChannel sits registered with a Selector with no thread dedicated to it, and when a Kafka consumer inside notification-service receives an OrderShipped event and needs to push it to the relevant device, that write is handed to the event loop, which performs it as a normal non-blocking channel write without needing to "wake up" or allocate a thread specifically for that device. The number of concurrently connected devices notification-service can hold open is then bounded mainly by available memory for per-connection state and OS file-descriptor limits, not by how many OS threads the process can afford to keep alive.

Concepts Worth Being Able to Explain From First Principles

Why does forgetting to close a FileInputStream eventually break unrelated requests in the same service, not just the request that leaked it?
An open stream or socket holds a file descriptor, and the operating system enforces a hard per-process limit on how many can be open simultaneously. A single leaked descriptor from one failed request doesn't hurt anything by itself, but if the leak happens on every failure of some code path — say, an exception thrown before a manually-managed stream's close() call runs — then under sustained load the count of leaked descriptors climbs steadily and never comes back down, because nothing is releasing them. Once the process hits its descriptor limit, every subsequent attempt to open a file or accept a new socket connection fails immediately with an operating-system-level "too many open files" error, regardless of whether that specific request's code has anything to do with the original leaky code path. This is why the failure looks like a mysterious, seemingly unrelated outage that appears only after sustained uptime under load — it's actually a slow-building resource exhaustion whose root cause (the leak) and symptom (unrelated requests failing) are far apart in time and in the code.
What does calling flip() on a ByteBuffer actually change, and why does forgetting it produce an empty or garbage read instead of an exception?
A ByteBuffer tracks three cursors — position (where the next operation happens), limit (the boundary past which no operation should go), and capacity (the fixed total size). After a channel.read(buffer) call fills the buffer, position sits at the end of the freshly written data and limit still equals capacity, because the buffer is still configured for writing. flip() sets limit to the current position, capturing exactly how much real data was just written, and resets position to zero so a subsequent read starts from the beginning. If code skips flip() and tries to read immediately, position is still at the end of the written data and limit is still capacity, so buffer.hasRemaining() (which checks position against limit) either returns false immediately, producing an empty read, or in the case of a partially-filled large buffer, allows reading forward into the unused, uninitialized tail region past the real data — which returns zero-bytes or previously-mapped garbage rather than throwing, because from the buffer's own bookkeeping perspective this all still looks like a legal read within its limit.
Why can a single SocketChannel be used for both reading and writing, when java.io forces separate InputStream and OutputStream objects for the same socket?
java.io's Socket.getInputStream() and getOutputStream() exist as separate objects mainly because the java.io.Stream abstraction itself is inherently unidirectional — an InputStream models "the next bytes coming in" and an OutputStream models "the next bytes going out," and there's no single stream type that models both directions at once, even though the underlying TCP connection is genuinely full-duplex (both directions active simultaneously over the same connection). NIO's Channel abstraction was designed from the start around block-oriented transfer into and out of Buffers rather than a directional flow model, so a single SocketChannel object simply exposes both a read(ByteBuffer) and a write(ByteBuffer) method against the same underlying connection, matching the actual full-duplex nature of the TCP socket underneath rather than artificially splitting it into two objects. This isn't just a convenience — it's also what makes registering a single channel with a Selector for both OP_READ and OP_WRITE interest natural, since it's genuinely one object representing one connection's readiness in both directions.
Concretely, what does a Selector let one thread do that it couldn't do by calling read() on many blocking sockets in a loop?
A blocking socket's read() call does not return until at least some data is available (or the connection closes/errors), so a single thread looping over many blocking sockets calling read() on each in turn would get stuck on the first socket that has no data yet, unable to even check whether a later socket in the list already has data waiting — there is no way to "peek" and move on without either blocking or busy-polling every socket constantly, which wastes CPU. A Selector solves this by delegating readiness-tracking to the operating system: registering channels with interest sets (OP_READ, OP_WRITE, OP_ACCEPT) and calling select() blocks the calling thread efficiently (via epoll/kqueue under the hood) until the OS itself signals that at least one of the registered channels has become ready for one of its registered interests, and returns exactly the set of channels that are ready right now. The thread then does non-blocking work only on those specific channels and immediately calls select() again. This is what allows one thread to correctly and efficiently multiplex readiness across thousands of channels: it's never stuck waiting on any single one, and it never wastes CPU polling ones that have nothing to do.
Why does mapping a memory-mapped file skip a data copy that normal file I/O can't avoid?
A normal blocking read (InputStream.read() or FileChannel.read(buffer)) is a system call: the kernel reads the requested bytes from disk into its own page cache (if not already resident there from a previous access), and then copies those bytes a second time from kernel space into the user-space byte array or buffer the application provided — two distinct memory regions, one copy operation between them, on every single read. A memory-mapped file instead maps the file's pages directly into the process's own virtual address space, so the "buffer" the application reads from via MappedByteBuffer.get() is, at the hardware level, the same physical memory as the OS page cache itself — there is no separate user-space copy to populate, because the application is reading the page cache's memory directly through its own address space mapping. The trade-off is that this only helps for repeated or random access to file content that benefits from staying resident in the page cache; a single sequential pass over a huge file gains comparatively little, since the underlying page-fault-driven population of memory still has to read each page from disk at least once regardless of which API triggers it.
Why does a thread-per-connection blocking model run out of capacity at high connection counts even if the CPU itself is barely busy?
In the blocking model, each open connection is tied to a dedicated OS thread for its entire lifetime, and that thread exists (consuming its stack memory, roughly a megabyte by default, and being a schedulable entity the OS has to account for) regardless of whether the connection is actively doing anything at that instant. A connection that's 99% idle — like a notification-service device connection sitting open for hours waiting for the next order event — still permanently reserves a full thread's worth of memory and scheduling overhead the entire time it's idle, because the blocking model has no way to let that thread do other useful work while nothing is happening on that specific connection; the thread is parked, not destroyed. As connection count grows into the tens of thousands, the bottleneck that appears first is essentially never CPU (idle connections use approximately zero CPU) — it's memory consumed by thread stacks and, in the worst cases, the OS scheduler's own overhead managing an unreasonably large number of mostly-dormant threads. This is the exact gap the event-loop/non-blocking model closes: memory usage there scales with actual in-flight work, not with the raw count of open, mostly-idle connections.
Why does an atomic Files.move avoid the "reader sees a half-written file" bug that a plain write-then-rename in java.io could still have on some platforms?
The underlying risk is that generating a large export file takes real, non-zero time, and if a consumer (a scheduled job, or a seller's download request) opens the destination path while the writer is still partway through producing it, the consumer reads a truncated or structurally invalid file — a bug that only reproduces under a specific timing window, making it especially hard to diagnose from a bug report. Writing to a temporary path first and renaming it into place at the end mitigates most of this, but a plain rename operation's atomicity guarantee is filesystem- and platform-dependent, and java.io.File.renameTo() explicitly does not guarantee atomicity across all platforms, silently falling back to non-atomic behavior in some cases with no signal to the caller that it did so. Files.move(source, target, StandardCopyOption.ATOMIC_MOVE) instead makes an explicit, checked request for atomic semantics — if the underlying filesystem cannot honor it, the call throws AtomicMoveNotSupportedException rather than silently degrading, so the calling code either gets the guarantee it asked for or finds out immediately that it can't be provided, rather than discovering the gap only when a customer reports a corrupted download weeks later.
