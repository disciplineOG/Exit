Testing Strategy: JUnit5, Mockito, TestContainers, Contract Tests

Why this matters

A test suite that is green on every commit but still ships a broken database query is worse than no test suite at all — it manufactures false confidence. Understanding why that happens (usually: mocking a repository interface so thoroughly that the test never touches real SQL, or an inverted pyramid where slow end-to-end tests are the only thing catching real bugs) is what lets you design a suite that actually fails when the system is actually broken, and stays fast enough that people keep running it.

1. The Testing Pyramid: Why Shape Is a Design Decision

The testing pyramid is not a rule about proportions for their own sake — it's a statement about a trade-off between three properties that are in tension: speed, isolation, and confidence. Every test you write buys some confidence that the system works, but the cost of that confidence (in execution time, in flakiness, in coupling to infrastructure) rises sharply as the test exercises more of the real system. The examples throughout this page anchor each layer in ShopSphere, a multi-vendor marketplace with order-service, payment-service, inventory-service, and notification-service talking to each other over REST and Kafka:

                    /\
                   /  \        End-to-end (fewest, slowest, highest confidence per test)
                  /    \       e.g. browse -> add to cart -> checkout -> pay -> ship,
                 /------\      driven through ShopSphere's real deployed API/UI
                /        \
               /          \    Integration (fewer than unit, real I/O)
              /            \   e.g. OrdersRepository against real Postgres (Testcontainers),
             /              \  a Kafka consumer against a real broker
            /----------------\
           /                  \  Contract tests (sit beside/above integration -
          /                    \  verify a boundary, not a whole deployed system)
         /                      \ e.g. order-service's expectations of payment-service's API
        /------------------------\
       /                          \  Unit (base, most numerous, milliseconds each)
      /                            \ e.g. OrderService.placeOrder() with a mocked PaymentGateway
     /------------------------------\

  speed:      fast  ---------------------------------------->  slow
  isolation:  high  ---------------------------------------->  low
  confidence per test:  low  ------------------------------->  high
  number of tests:    many   ------------------------------->  few
  • Unit tests (base, most numerous): test a single class or function in isolation, with all collaborators replaced by test doubles. They run in milliseconds because there is no I/O — no network call, no disk write, no JVM class-loading beyond your own code and its immediate dependencies. Because they're isolated, a failure points at almost exactly one place: the unit under test or its direct contract with a collaborator. A ShopSphere example: testing OrderService.placeOrder() with a mocked PaymentGateway and a mocked InventoryClient — section 3 walks through this in full.
  • Integration tests (middle, fewer): verify that two or more real components actually cooperate correctly — your repository code against a real database, your Kafka consumer against a real broker, your HTTP client against a real (or realistically faked) downstream service. These are slower because they involve real I/O and process startup, but they catch a whole category of bug that unit tests are structurally blind to: wrong SQL dialect, wrong Kafka serializer configuration, wrong JSON field name on the wire. A ShopSphere example: an OrdersRepository integration test against a real Postgres instance started by TestContainers (section 5).
  • Contract tests sit conceptually beside/above the integration layer — they verify one service boundary in isolation, without either side being deployed. A ShopSphere example: order-service asserting its expectations of payment-service's POST /payments endpoint (section 6).
  • End-to-end tests (top, fewest): exercise the deployed system as a whole, often through its public API or UI, across every service boundary. They give the highest confidence that a user-facing flow actually works, but they are slow (seconds to minutes each), brittle (any one of a dozen services being flaky fails the test for reasons unrelated to the thing you're testing), and expensive to debug (a failure could be anywhere in the call graph). A ShopSphere example: a test that drives the real checkout flow — add to cart, checkout, reserve inventory, charge payment, confirm order — against a fully deployed staging environment.

The pyramid shape — many unit tests, a moderate number of integration tests, a small number of end-to-end tests — exists because it maximizes total confidence per unit of feedback latency. If unit tests are cheap and catch most logic bugs, you want as much of your correctness argument carried by them as possible, and you want integration and end-to-end tests to cover only the things unit tests structurally cannot: real protocol behavior, real component wiring, and real cross-service contracts.

The inverted pyramid (ice cream cone anti-pattern)

A common and expensive failure mode is a suite shaped like an inverted pyramid or an "ice cream cone": a handful of unit tests, a thin middle layer, and a huge number of slow end-to-end tests that are treated as the primary safety net. Symptoms: a CI pipeline that takes 45 minutes, a flaky end-to-end suite that people start ignoring ("just rerun it"), and bugs that could have been caught in a 2-millisecond unit test instead surfacing an hour later in a UI test that fails for an unrelated reason (a stale test fixture, a slow container, a timing race). The fix is not to delete the end-to-end tests — it's to push the coverage they're providing down into unit and integration tests wherever the underlying logic doesn't actually require the full system to be running.

2. JUnit 5 Architecture: Jupiter, Lifecycle, and the Extension Model

JUnit 5 is not a monolithic library the way JUnit 4 was — it's split into three components: JUnit Platform (the engine that discovers and runs tests, and that build tools like Maven Surefire and Gradle talk to), JUnit Jupiter (the new programming model and annotations you actually write tests against, such as @Test, @BeforeEach, @ParameterizedTest), and JUnit Vintage (a compatibility engine that lets old JUnit 3/4 tests keep running on the Platform during migration). This separation is what lets a single Gradle or Maven run execute a mix of legacy JUnit 4 tests and modern Jupiter tests side by side.

Lifecycle annotations and why @BeforeAll defaults to static

By default, JUnit creates a new instance of the test class for every test method (TestInstance.Lifecycle.PER_METHOD). This is deliberate: it prevents state leaking between test methods through instance fields, which is exactly the kind of hidden coupling that makes a test suite's outcome depend on execution order — a serious defect in a supposedly deterministic suite.

Because a fresh instance is created per test method, there is no single object instance around before the first test method runs to call a @BeforeAll method on. JUnit needs something it can invoke without any instance existing yet, so @BeforeAll (and @AfterAll) methods must be static under the default lifecycle — they run once against the class, not the instance. The same reasoning applies to @AfterAll.

You can flip this with @TestInstance(TestInstance.Lifecycle.PER_CLASS), which tells JUnit to create exactly one instance of the test class and reuse it for every test method. Under this mode, @BeforeAll/@AfterAll no longer need to be static, because there is now a persistent instance they can run against. The trade-off is that instance fields now persist across test methods within the class, so you must be deliberate about resetting mutable state in @BeforeEach if you rely on it — otherwise one test's leftover state silently changes the outcome of the next.

Parameterized tests

@ParameterizedTest replaces the JUnit 4 pattern of writing a separate test method per input, or using a Parameterized runner that applied to the whole class. A single method runs once per supplied argument set, keeping the assertion logic in one place while the data varies:

@ParameterizedTest
@CsvSource({
    "100.00, 10, 90.00",   // 10% off coupon
    "100.00, 0,  100.00",  // no discount
    "50.00,  100, 0.00"    // 100% off coupon (edge case: fully comped order)
})
void appliesCouponDiscountToOrderTotal(BigDecimal subtotal, int percentOff, BigDecimal expected) {
    assertEquals(expected, CouponCalculator.applyDiscount(subtotal, percentOff));
}

Argument sources include @ValueSource (a single primitive/String array), @CsvSource (inline rows), @MethodSource (a static method supplying a Stream of arguments, for cases too complex for a literal), and @EnumSource. The point of all of them is the same: separate the invariant (what the assertion checks) from the variable (which inputs exercise it), so adding an edge case is a one-line addition, not a new method.

The extension model

JUnit 4 used Runners (@RunWith(SpringJUnit4ClassRunner.class)) and Rules to hook into test execution, but a test class could only have one runner, which made composing behaviors from multiple libraries awkward. JUnit 5 replaces both with a single unified Extension model (@ExtendWith), where extensions implement narrow interfaces like BeforeEachCallback, ParameterResolver, or AfterAllCallback, and any number of extensions can be stacked on one test class. This is the mechanism behind @ExtendWith(MockitoExtension.class) (injects @Mock fields and validates stubs) and @ExtendWith(SpringExtension.class) (wires a Spring ApplicationContext into the test) coexisting on the same class — something that was not cleanly possible with the single-runner model in JUnit 4.

3. Mockito: Mocks, Spies, and What They Actually Replace

The running example for this section is OrderService.placeOrder(Cart cart) — the method that turns a customer's cart into an Order, and needs to charge a PaymentGateway and publish an OrderEvent without either of those being real in a unit test:

class OrderService {
    private final PaymentGateway paymentGateway;   // our own interface (see "mocking your own boundary" below)
    private final OrderRepository orderRepository;
    private final EventPublisher eventPublisher;

    Order placeOrder(Cart cart) {
        BigDecimal total = cart.getItems().stream()
                .map(item -> item.getUnitPrice().multiply(BigDecimal.valueOf(item.getQuantity())))
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        PaymentResult result = paymentGateway.charge(cart.getCustomerId(), total);
        if (result.status() != PaymentStatus.CAPTURED) {
            throw new PaymentFailedException(cart.getCustomerId(), result.status());
        }

        Order order = orderRepository.save(new Order(cart.getCustomerId(), cart.getItems(), total, OrderStatus.CREATED));
        eventPublisher.publish(new OrderEvent(order.getId(), order.getStatus(), order.getTotalAmount()));
        return order;
    }
}

Mock vs. spy

A mock, created with Mockito.mock(SomeType.class) or the @Mock annotation, is a dynamically generated object with no real implementation underneath at all. Every method returns a default value (null, 0, empty collection, or empty Optional) unless you explicitly stub it with when(...).thenReturn(...). A mock is appropriate when you want to fully control a collaborator's behavior and assert how your code under test interacts with it, without any risk of real logic running. Testing placeOrder above needs exactly this: a mocked PaymentGateway that returns a controlled PaymentResult without ever calling a real payment processor, and a mocked OrderRepository/EventPublisher so the test never touches a real database or message broker.

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock PaymentGateway paymentGateway;
    @Mock OrderRepository orderRepository;
    @Mock EventPublisher eventPublisher;
    @InjectMocks OrderService orderService; // Mockito constructs OrderService, wiring the three @Mocks in

    @Test
    void placesOrderWhenPaymentIsCaptured() {
        Cart cart = sampleCartTotaling("59.97");
        when(paymentGateway.charge(cart.getCustomerId(), new BigDecimal("59.97")))
                .thenReturn(new PaymentResult(PaymentStatus.CAPTURED, "pay_123"));
        when(orderRepository.save(any(Order.class)))
                .thenAnswer(invocation -> invocation.getArgument(0)); // echo back the saved Order

        Order order = orderService.placeOrder(cart);

        assertEquals(OrderStatus.CREATED, order.getStatus());
        assertEquals(new BigDecimal("59.97"), order.getTotalAmount());
    }

    @Test
    void throwsAndNeverSavesOrderWhenPaymentFails() {
        Cart cart = sampleCartTotaling("59.97");
        when(paymentGateway.charge(any(), any()))
                .thenReturn(new PaymentResult(PaymentStatus.FAILED, null));

        assertThrows(PaymentFailedException.class, () -> orderService.placeOrder(cart));

        verify(orderRepository, never()).save(any());     // the point of this test: no order persisted on a failed charge
        verify(eventPublisher, never()).publish(any());
    }
}

@InjectMocks (paired with @ExtendWith(MockitoExtension.class), the extension mentioned above and detailed further down) tells Mockito to instantiate OrderService itself and inject the @Mock-annotated fields into its constructor, so the test never has to wire the constructor call by hand. any(Order.class)/any() are Mockito argument matchers — they tell the stub "match a call with any argument of this type" rather than one specific value, which is necessary here because the actual Order instance passed to save() is constructed inside placeOrder and isn't available to the test to reference directly. thenAnswer lets a stub compute its return value from the actual invocation (here, just echoing the argument back) rather than returning one fixed canned value via thenReturn.

A spy, created with Mockito.spy(realInstance) or @Spy, wraps an actual, real object. Any method you have not explicitly stubbed executes the real implementation. This matters because it changes the default: with a mock, "unstubbed" means "returns null/0/empty"; with a spy, "unstubbed" means "runs the real code, with real side effects." A spy is useful when you want most of an object's real behavior but need to override one specific method — for example, spying on a real PricingService that computes ShopSphere's flash-sale prices from several real, cheap, purely computational rules, but stubbing just the one method that calls out to a slow external currency-conversion API.

Spy pitfalls: stubbing after construction, and real side effects

Because a spy runs real code by default, calling a real method during stubbing setup (when(spy.someMethod()) instead of the safer doReturn(...).when(spy).someMethod() pattern) can actually execute the real method as a side effect of setting up the stub — surprising when that method talks to a database or throws under certain preconditions. This is why Mockito's own documentation recommends doReturn/doThrow/doAnswer style stubbing for spies. It's also easy to forget that a spy's non-stubbed methods have real side effects at all — if you spy on NotificationService and forget to stub the one method that sends an order-confirmation email, your test will genuinely try to send an email.

verify() vs. assert: behavior verification vs. state verification

assertEquals/assertThat check state — did the method under test return the right value, or leave an object in the right shape? Mockito.verify(mock).someMethod(args) checks behavior — was a particular method called on a collaborator, with particular arguments, a particular number of times? Both are legitimate, but they answer different questions, and over-reaching for verify() when a state assertion would do is a common source of brittle tests. In placesOrderWhenPaymentIsCaptured above, asserting on the returned Order's status and totalAmount is a state assertion — it doesn't care how placeOrder arrived at that order, only that the result is correct.

The problem with excessive behavior verification is that it couples the test to how the code achieves its result, not what result it achieves. If you verify that OrderService calls orderRepository.findById() exactly once and then refactor the implementation to use a batch findAllById() call instead — a change that preserves the exact same externally observable behavior — the test breaks even though nothing is actually wrong. Reserve verify() for interactions that are the actual point of the test: side effects with no return value to assert on, like "did we publish an OrderEvent," "did we call paymentGateway.charge() exactly once" (charging a customer's card twice for one order is a real bug you want caught), or — as in throwsAndNeverSavesOrderWhenPaymentFails above — "did we never call orderRepository.save() on a failed-payment code path."

Argument captors

An ArgumentCaptor lets you inspect the actual value passed to a mocked method, rather than just matching that some call happened. This matters when the interaction you care about isn't just "was it called" but "was it called with the right, possibly derived, argument" — e.g., the constructed OrderEvent domain object, not a raw parameter, is what actually needs checking after placeOrder runs:

@Test
void publishesOrderCreatedEventWithCorrectTotal() {
    Cart cart = sampleCartTotaling("59.97");
    when(paymentGateway.charge(any(), any())).thenReturn(new PaymentResult(PaymentStatus.CAPTURED, "pay_123"));
    when(orderRepository.save(any(Order.class))).thenAnswer(invocation -> invocation.getArgument(0));

    orderService.placeOrder(cart);

    ArgumentCaptor<OrderEvent> captor = ArgumentCaptor.forClass(OrderEvent.class);
    verify(eventPublisher).publish(captor.capture());

    assertEquals(new BigDecimal("59.97"), captor.getValue().total());
    assertEquals(OrderStatus.CREATED, captor.getValue().status());
}

Mocking a type you don't own vs. mocking your own boundary

A subtle but important discipline: avoid mocking types you don't own — a JDBC Connection, a third-party HTTP client, a payment vendor's raw SDK client (say, Stripe's or Adyen's Java SDK). These types have rich, undocumented-in-the-interface contract behavior (exception timing, resource lifecycle, retry semantics) that a hand-written mock can never faithfully reproduce, and doing so means your test is asserting against your own guess of how the library behaves, not how it actually behaves. When that guess is wrong — and it usually eventually is, after a library upgrade changes some edge-case behavior — the mock keeps passing while production breaks.

This is exactly why OrderServiceTest above mocks ShopSphere's own PaymentGateway interface rather than a third-party payment SDK class directly: PaymentGateway is a narrow abstraction ShopSphere itself designed, exposing only charge(customerId, amount) — exactly what OrderService needs, nothing more. The real implementation, something like StripePaymentGatewayAdapter, is a thin class that translates charge() into the actual vendor SDK calls, and that adapter — not OrderService — is the thing tested with an integration test against something real or realistically sandboxed (a payment provider's official test/sandbox mode, or a recorded-interaction contract as in section 6). You mock the boundary you designed and control (PaymentGateway); you do not mock the vendor's API surface.

4. The Over-Mocking Trap and Why It Motivates TestContainers

The failure mode that all of the above guidance is trying to prevent is this: an OrdersRepository class is unit-tested with a mocked EntityManager or a mocked Spring Data JPA repository interface, every method is stubbed to return exactly what the test expects, and the test passes. But the real, unmocked SQL that Hibernate generates from a query method like findByCustomerIdAndStatusIn(customerId, List.of(PAID, SHIPPED)) never runs anywhere in the suite. If the query has a wrong join column between orders and order_items, a wrong @Column mapping on totalAmount, or relies on Postgres-specific syntax that doesn't behave the way you assumed, none of that surfaces — every layer above the mock is only checking that your code calls the mock correctly, not that the real underlying technology behaves the way your code assumes.

This is precisely the gap integration tests exist to close, and it's why an in-memory substitute (H2 standing in for Postgres, a hand-rolled fake message broker standing in for Kafka) is a fragile solution: H2's SQL dialect, type coercion rules, and constraint-enforcement behavior diverge from Postgres's in enough small ways that a query can pass against H2 and fail against real Postgres in production — wrong case-sensitivity handling, different date/time semantics, different handling of NULL in unique constraints (a real, easy-to-hit example: a unique constraint on (order_id, idempotency_key) for Payment rows behaves subtly differently across engines when either column is NULL). An in-memory fake is a model of the real system, built by the same people who might be wrong about the real system's behavior in the first place, so it tends to reproduce the developer's misconceptions rather than catch them.

5. TestContainers: Integration Testing Against the Real Thing

TestContainers is a Java library that programmatically starts and stops real Docker containers from within a test's lifecycle, giving each test run (or test class) an ephemeral, disposable instance of the actual technology being integrated with — a real PostgreSQL server, a real Kafka broker, a real Redis instance, a real LocalStack standing in for AWS services. The container is created fresh, used for the test run, and destroyed afterward, so there's no shared mutable test database drifting into an inconsistent state across CI runs. Below, OrdersRepository — the Spring Data JPA repository backing ShopSphere's order-service — is tested against a real, disposable Postgres instance rather than any in-memory substitute:

@Testcontainers
@SpringBootTest
class OrdersRepositoryIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16")
            .withDatabaseName("shopsphere_orders_test");

    @DynamicPropertySource
    static void configureDataSource(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    OrdersRepository ordersRepository;

    @Test
    void persistsAndReloadsOrderWithLineItems() {
        Order saved = ordersRepository.save(sampleOrderWithTwoItems("cust-8841"));

        Order reloaded = ordersRepository.findById(saved.getId()).orElseThrow();

        assertEquals(2, reloaded.getItems().size());
        assertEquals(new BigDecimal("59.97"), reloaded.getTotalAmount());
    }

    @Test
    void findsOnlyOrdersInPaidOrShippedStatusForACustomer() {
        ordersRepository.save(sampleOrder("cust-8841", OrderStatus.CREATED));
        ordersRepository.save(sampleOrder("cust-8841", OrderStatus.PAID));
        ordersRepository.save(sampleOrder("cust-8841", OrderStatus.CANCELLED));

        // exercises the real generated SQL - a wrong join or status enum mapping would fail here,
        // not in a mocked-repository unit test, which is exactly the gap section 4 describes
        List<Order> active = ordersRepository.findByCustomerIdAndStatusIn(
                "cust-8841", List.of(OrderStatus.PAID, OrderStatus.SHIPPED));

        assertEquals(1, active.size());
        assertEquals(OrderStatus.PAID, active.get(0).getStatus());
    }
}

The @Container field being static here matters for the same lifecycle reason discussed in the JUnit 5 section: a static container is started once (via @BeforeAll-equivalent extension callbacks) and shared across all test methods in the class rather than restarted per test, which is what makes a Postgres-container-per-test-class approach fast enough to be practical — restarting a full database container for every single test method would be prohibitively slow. @DynamicPropertySource exists because the container's mapped port is only known at runtime after Docker assigns it, so the JDBC URL can't be a static property in application.yml; it has to be injected into Spring's environment after the container starts but before the context builds the datasource bean.

6. Contract Testing: Verifying Service Boundaries Without a Full Environment

In a microservices architecture, a classic integration problem is that no single team can run a true end-to-end test cheaply — verifying that order-service's expectations of payment-service's POST /payments API are actually met would otherwise require spinning up both services (and their transitive dependencies, like payment-service's own connection to a real card-network sandbox) together, which is slow, requires coordinated versioning, and doesn't scale as the number of services grows past a handful. Contract testing solves a narrower version of that problem: verifying that a consumer's expectations of a provider match the provider's actual behavior, without either side needing the other running.

The consumer-driven contract flow

  1. The consumer — here, order-service, which calls payment-service to charge a customer at checkout — writes a test against a mock of the provider, expressing exactly the requests it will make and the responses it expects — field names, types, status codes. Running this test produces a contract (a serialized specification, e.g. a Pact file) capturing those expectations.
  2. The contract is published to a shared broker (such as a Pact Broker) that both the order-service and payment-service teams can access.
  3. The provider — payment-service — in its own build pipeline, pulls down every contract published against it (including order-service's) and replays each interaction against its real implementation, asserting that the actual response matches what each consumer expects.
  4. If payment-service's pipeline fails this verification, that is the signal — before any deployment — that a proposed change to payment-service's API would break order-service, without either service ever needing to be deployed alongside the other in a shared environment.

The example below uses Pact, the most common consumer-driven contract testing tool. @Pact/PactDslWithProvider is a fluent builder describing one interaction — .given(...) names a provider state (a precondition payment-service's test data must be seeded into, so the interaction is reproducible), .uponReceiving(...) names the interaction for readability, and the request/response bodies are built with a schema-shape DSL (stringType, decimalType) rather than literal values, because the contract is checking field names and types match, not that payment-service happens to return the exact string "pay_123" every time. Running this test both exercises order-service's own HttpPaymentGateway adapter against a Pact-provided mock server and writes out a Pact file capturing the interaction. On the provider side, @Provider/@PactBroker tell the Pact JUnit5 extension which service this is and where to fetch published contracts from; @State matches a .given(...) string from the consumer side and lets payment-service seed exactly the precondition (a Customer with a payment method on file) that interaction assumes before replaying it.

// --- order-service side: consumer contract test, written against a Pact mock of payment-service ---
@ExtendWith(PactConsumerTestExt.class)
class PaymentServiceContractTest {

    @Pact(consumer = "order-service", provider = "payment-service")
    RequestResponsePact chargeSucceeds(PactDslWithProvider builder) {
        return builder
            .given("customer cust-8841 has a valid payment method on file")
            .uponReceiving("a charge request for a captured order total")
                .path("/payments")
                .method("POST")
                .body(new PactDslJsonBody()
                    .stringType("orderId", "ord-5591")
                    .decimalType("amount", 59.97)
                    .stringType("idempotencyKey", "ord-5591-attempt-1"))  // dedupe key so a retried request can't double-charge
            .willRespondWith()
                .status(201)
                .body(new PactDslJsonBody()
                    .stringType("status", "CAPTURED")
                    .stringType("paymentId", "pay_123"))
            .toPact();
    }

    @Test
    @PactTestFor(pactMethod = "chargeSucceeds")
    void orderServiceParsesACapturedPaymentResponseCorrectly(MockServer mockServer) {
        PaymentGateway gateway = new HttpPaymentGateway(mockServer.getUrl());
        PaymentResult result = gateway.charge("ord-5591", new BigDecimal("59.97"), "ord-5591-attempt-1");
        assertEquals(PaymentStatus.CAPTURED, result.status());
    }
}

// --- payment-service side: provider verification test, run in payment-service's own CI pipeline ---
@Provider("payment-service")
@PactBroker(url = "https://pact-broker.shopsphere.internal")
class OrderServiceContractVerificationTest {

    @State("customer cust-8841 has a valid payment method on file")
    void setUpCustomerWithPaymentMethod() {
        // seed payment-service's test database with the fixture this contract state requires
    }

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)
    void verifyEachPublishedInteraction(PactVerificationContext context) {
        context.verifyInteraction(); // replays order-service's recorded request against real payment-service code
    }
}

The word "consumer-driven" is precise: the contract originates from what the consumer actually needs, not from the provider's own documentation of what it offers. This avoids a subtle failure mode of schema-only approaches (like just sharing an OpenAPI spec): payment-service could be fully compliant with its own documented schema while still breaking order-service if, say, a refactor renamed the response field paymentId to id — a change the OpenAPI spec's authors might not think of as breaking if they weren't tracking every field a specific consumer actually reads. The contract only encodes interactions that are actually exercised, which keeps it a precise, living, executable specification of what would actually break someone, not a hypothetical full behavior. This composes directly with a deployment pipeline: contract verification is typically a gate a provider's build must pass before it's allowed to deploy, exactly the kind of check a pipeline is built to enforce automatically — payment-service should not be able to deploy a breaking change to /payments until its pipeline confirms order-service's contract still passes.

Contract tests are not a replacement for integration tests

Contract testing verifies the shape and semantics of a boundary agreement between two services; it does not verify that either service's internal logic or its interaction with its own database or broker works correctly — that's still the job of that service's own integration tests. The two techniques answer different questions: "does order-service's OrdersRepository code work against the real Postgres behind it" (TestContainers, section 5) versus "does order-service's understanding of payment-service's API match what payment-service actually built and will keep building" (contract tests, this section).

The trade-off is honest, not hidden

TestContainers tests are slower than pure unit tests — container startup is commonly hundreds of milliseconds to a few seconds depending on the image, plus JVM class-loading and Spring context startup if you're bringing up a full ApplicationContext. This is the correct place on the pyramid for that cost: you're not trying to make every test this slow, you're concentrating this cost into a smaller number of integration tests that verify exactly the things unit tests structurally can't — real dialect behavior, real serialization, real constraint enforcement — while the bulk of your logic remains covered by millisecond-fast unit tests with mocked collaborators. The same discipline applies to contract tests: they're deliberately narrow (one boundary's interactions, not a whole service's behavior) precisely so they stay fast and don't need either service actually running.

7. Test Doubles, Precisely

"Mock" is often used loosely to mean "any fake object in a test," but the test-doubles taxonomy (originating with Gerard Meszaros, popularized by Martin Fowler) distinguishes five distinct roles, and Mockito's API blurs some of these together in ways worth untangling deliberately.

The distinction between stub and mock is really about what the test checks, not how the object is constructed: if you configure an object's canned return values and then only assert on the state that results from using them, you're using it as a stub. If you additionally assert that specific methods were called on it, you're using it as a mock in Meszaros's strict sense — and Mockito's single mock() factory method can produce an object used in either role depending on whether your test ever calls verify() on it. A fake is a step up in fidelity from a stub: rather than returning fixed canned data, a fake is a genuinely working alternative implementation — an in-memory repository that actually stores and retrieves objects, enforcing constraints in a real (if simplified) way — which is why a fake occupies a middle ground between a hand-rolled stub and the fully real TestContainers-backed dependency: more realistic than canned answers, cheaper than a real database.

Choosing a double is a fidelity/cost decision, not a style preference

Dummies and stubs are the cheapest, appropriate when the collaborator's behavior is irrelevant to what you're testing. Mocks are appropriate when the interaction itself — not the return value — is the thing under test. Fakes are worth the extra investment when a dependency is used pervasively across many tests and its real behavior (ordering, constraints, state transitions) actually matters, but standing up the real thing in every test would be too slow. Real dependencies via TestContainers are the highest-fidelity, highest-cost option, reserved for the boundary-behavior questions that nothing else can answer honestly.

Concepts Worth Being Able to Explain From First Principles

Why does an inverted testing pyramid make a system harder to change safely over time, not just slower to test?
When most of your confidence comes from slow, brittle end-to-end tests, the feedback loop for a code change lengthens from seconds to potentially tens of minutes, and failures are ambiguous — a failing end-to-end test could indicate a real regression or an unrelated flaky dependency, so people learn to distrust and rerun rather than investigate. That erosion of trust means genuine regressions increasingly slip through because failures are assumed to be noise. Over time, teams become reluctant to refactor or change code at all, because the cost of finding out whether a change broke something is high and the signal is unreliable — the opposite of what a test suite is supposed to enable.
Why must @BeforeAll methods be static under JUnit 5's default lifecycle, and what changes if you use PER_CLASS?
Under the default PER_METHOD lifecycle, JUnit constructs a brand-new instance of the test class for every test method to prevent state from leaking between tests through instance fields. That means there is no instance in existence yet at the point @BeforeAll needs to run — it executes before the first per-method instance is even created — so it must be a static method invoked against the class itself. Switching to @TestInstance(Lifecycle.PER_CLASS) makes JUnit create a single shared instance for the whole class, so @BeforeAll can now run as an instance method against that one instance; the cost is that instance fields persist across test methods, so you take on responsibility for resetting any mutable state in @BeforeEach to keep tests independent.
What is the practical difference between a mock and a spy in Mockito, and when would using a spy actually be the wrong choice?
A mock has zero real implementation underneath — every method returns a default (null/0/empty) unless explicitly stubbed, so you have complete, explicit control over its behavior. A spy wraps a real object, so any method you haven't stubbed executes the real implementation with real side effects. A spy is the wrong choice when the real object's unstubbed methods have expensive or irreversible side effects (network calls, writes, sending notifications) that you didn't intend to trigger just by using the object in a test — spying on ShopSphere's real NotificationService and forgetting to stub the one method that sends an order-confirmation email means the test genuinely sends an email. In that case a mock, or a fake, is safer because nothing runs unless you explicitly said it should.
Why does over-using verify() make tests brittle, and how do you decide when behavior verification is actually warranted?
verify() asserts on how the code under test achieved its result — which methods it called on which collaborators — rather than on the result itself. Since there are usually many valid implementations that produce the same correct externally observable outcome, a test that verifies implementation details breaks the moment you refactor internals, even when behavior hasn't changed for any caller. Behavior verification is warranted specifically when the interaction itself has no observable return value to assert on and is the actual point of correctness — for example, confirming OrderService published an OrderEvent exactly once, or that orderRepository.save() was never called on a code path where payment failed — cases where the side effect, not a return value, is the thing that must be right.
Why is mocking a database driver or third-party SDK directly considered a risky practice, and what should you mock instead?
A type you don't own — a JDBC Connection, a Kafka Producer, a payment vendor's raw SDK client — has rich behavioral contracts (timing of exceptions, resource lifecycle, retry and idempotency semantics) that are not fully captured by its Java interface, so a hand-written mock encodes your own guess about how the library behaves. When that guess diverges from reality — often after a library upgrade — the mock keeps passing while production breaks, because the test was never checking against real behavior, just against your assumption of it. The safer approach is to define your own narrow interface expressing exactly what your domain needs — ShopSphere's OrderService depends on its own PaymentGateway interface, not a vendor SDK class — mock that interface in unit tests, and verify the thin adapter that actually calls the third-party SDK with an integration test against something real (or a realistic sandbox/container), so the risky assumption-laden boundary is tested with real behavior instead of a hand-rolled substitute.
Why does TestContainers exist when an in-memory database like H2 is faster and easier to set up?
An in-memory substitute is a simplified model of the real technology, built with the same assumptions a developer might already be wrong about — H2's SQL dialect, type coercion, and constraint enforcement diverge from Postgres's in specific ways (case sensitivity, date/time handling, NULL semantics in unique constraints), so a query can pass against H2 and still fail against production Postgres. TestContainers runs the actual database or broker in a real, ephemeral Docker container, so the integration test exercises the real engine's real quirks. The cost is slower test startup, which is exactly why these tests sit in the smaller integration layer of the pyramid rather than replacing fast unit tests entirely.
In consumer-driven contract testing, why does the contract originate from the consumer rather than from the provider's published API schema?
A provider's own schema documentation describes everything it theoretically offers, but a given consumer typically only relies on a subset of fields and behaviors in specific ways. If contracts were derived purely from the provider's schema, a fully schema-compliant change could still break a consumer that depended on some incidental behavior not captured by the schema, or the schema could go stale relative to what's actually being tested. By having each consumer publish a contract capturing exactly the interactions it actually performs and depends on — order-service only ever needs a subset of payment-service's response fields, and its contract only encodes exactly that subset — the provider verifies against real, current usage rather than a hypothetical full surface area, catching precisely the changes that would break someone, without needing every consumer and provider deployed together to find out.
In the OrderService unit test, why does mocking PaymentGateway and OrderRepository actually make the test more trustworthy, not less — and what would testing prove if you didn't mock them?
The point of OrderServiceTest is to verify OrderService's own logic — that it computes the correct order total, only persists an order when payment is captured, and publishes exactly one event with the right data. None of that logic lives inside PaymentGateway or OrderRepository, so a test that used the real payment adapter or a real database would be exercising code far beyond what it's meant to check, and would be slow, flaky (dependent on network calls or a live database), and would fail for reasons that have nothing to do with OrderService's own correctness — a payment sandbox being briefly down would fail every OrderService test even if OrderService's logic were perfect. By mocking both collaborators and controlling exactly what they return (PaymentResult.CAPTURED, an echoed-back Order), the test isolates OrderService's own branching logic — the if/throw on a failed payment, the total calculation, the event construction — and nothing else, so a failure in this test can only mean OrderService's own code is wrong. The real behavior of PaymentGateway's adapter and OrderRepository's queries is exactly what section 5 and 6's integration and contract tests exist to verify instead.
