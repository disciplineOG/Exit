Caching Strategies & Redis Architecture

Why this matters

A cache is not "a fast database" — it is a bet that most reads can be answered from a smaller, stale-tolerant copy of the truth, and every caching bug traces back to that bet being violated somewhere. Take ShopSphere's product catalog: on a normal day, catalog-service caches product detail pages (name, description, images, price) because the same few thousand top-selling products account for most of the traffic, while millions of long-tail products get almost none. If you don't understand the read/write race in cache-aside, you will ship a service that — the moment a seller updates a product's price — silently serves a permanently stale price to every customer after a single unlucky interleaving of that write and a concurrent cache miss, and no amount of retrying will fix it, because the stale value is now the one sitting in the cache. And when that product goes into a flash sale and its cache entry expires under a burst of 50,000 concurrent checkout requests, understanding eviction, invalidation, and Redis's single-threaded execution model is what lets you predict, rather than debug after the fact, why checkout latency suddenly collapsed at exactly the moment the sale went live.

1. Why Caching Exists

Every layer of a computer's storage hierarchy trades capacity for speed. A CPU register access takes roughly 1 cycle (~0.3 ns on a 3 GHz core). An L1 cache reference is about 1 ns. Main memory (DRAM) is about 100 ns — already two orders of magnitude slower. A round trip to an SSD is on the order of 100 microseconds, and a round trip across a network to another service or a disk-backed database, including serialization and TCP handling, is typically 1–10 milliseconds even in the same data center. That is roughly 10,000x to 100,000x slower than a memory access. Caching exists because this gap is structural, not incidental — it comes from physics (signal propagation, seek times, network hops) and cannot be engineered away, only worked around.

The reason caching works at all — rather than just being a gamble — is the principle of locality of reference: real workloads are not uniformly random. A small "working set" of data (a product catalog's top-selling items, a user's own profile, the last hour of a feed) accounts for a disproportionate share of requests at any given moment. If you keep that working set in memory, you convert a large fraction of your traffic from millisecond-scale disk/network operations into sub-millisecond memory operations, without needing to make the underlying database itself faster. This is why cache hit ratio, not raw cache size, is the metric that matters — a cache that captures 95% of traffic in a working set that's 1% of total data is far more valuable than one twice its size with a worse hit ratio.

Caching also exists for a second, less discussed reason: cost and blast-radius isolation. A relational database performing a join under load degrades non-linearly — connection pools exhaust, lock contention rises, query planning slows. Absorbing 95% of read traffic in an in-memory tier means the database only ever sees the harder, less frequent 5%, which keeps it in a regime where it behaves predictably. This is directly related to the read/write scaling arguments in hld-basics-scaling.

2. Cache-Aside (Lazy Loading)

Cache-aside — also called "lazy loading" — is the pattern used by the overwhelming majority of application-level caches (Redis or Memcached sitting next to a service, with the application code explicitly managing both). The defining trait is that the cache is dumb and passive: it never talks to the database itself. The application is the only thing that knows both systems exist, and it is responsible for keeping them roughly consistent. Concretely, ShopSphere's catalog-service caches under a key like product:{productId} holding the serialized product (name, price, category, stock summary) that the product detail page and search results both read from.

The read path

  1. A customer's browser requests product productId = 8841's detail page; catalog-service needs the product for key product:8841.
  2. It queries Redis for product:8841.
  3. Cache hit: return the cached product directly. The Postgres products table is never touched.
  4. Cache miss: query the database for the product row, get the value, write it into the cache (usually with a TTL), then return it to the caller.

The write path

  1. A seller updates the price on their product; the write goes directly to the products table in the database.
  2. catalog-service then invalidates (deletes) the corresponding cache key product:8841 — it does not update the cache with the new price.
Why delete instead of update on write?

It is tempting to write the new value into the cache right after writing the database, to "keep it warm." This is a trap for two reasons. First, if two writers update the same key concurrently, the last cache write to land might not correspond to the last database write to land — you can end up with a cache value that is older than the database value, with no mechanism to ever correct it until the TTL expires. Deleting is idempotent and order-independent: no matter which delete "wins," the next reader simply repopulates from the database. Second, if the value is expensive to compute (a joined, aggregated, or serialized representation) and is rarely read after being written, populating it eagerly wastes work. Deletion defers that cost to the next actual reader, or avoids it entirely if no one reads it before the next write.

The classic race condition

Cache-aside has a well-known interleaving hazard between a concurrent read (on miss) and a write. Picture a flash sale: a seller marks a product's price down from $50 to $30 at the exact moment a customer's request happens to miss the cache for that same product:

Thread A (customer read, cache miss)   Thread B (seller price update)
-------------------------------------  --------------------------------
1. GET product:8841 -> miss
                                          2. UPDATE products SET price=30 WHERE id=8841
                                          3. DEL product:8841   (no-op, already absent)
4. SELECT price FROM products WHERE id=8841
   -> 50 (STALE, read before step 2 committed...
   or reads 30 depending on isolation, see below)
5. SET product:8841 = (price read in step 4)

The dangerous case is when step 4 reads the old price 50 (because it was in flight before the transaction in step 2 committed, or because of read-replica lag) but lands in the cache after step 3's delete. The cache now holds 50 forever — or until the TTL expires — even though the database correctly holds 30. Every customer who hits the cache from that point on sees the old price, silently, with no error. No subsequent read will fix this because every subsequent read is a cache hit against the wrong value. This is not a rare, exotic race: under real load with a fast writer and a slow reader (e.g., a reader that queries a replica with replication lag), it happens routinely — and a flash sale, by design, is exactly the moment ShopSphere has the most concurrent readers racing a single price write.

Mitigations, in increasing order of complexity
  • Short TTLs — bound the damage; the stale entry self-heals within the TTL window. Cheap, but doesn't eliminate the problem, only limits blast radius.
  • Delete-after-write with a delay ("double delete") — invalidate immediately after the write, then invalidate again after a short delay (e.g., 500ms) to catch any read that raced in and repopulated a stale value in between.
  • Write-through-style versioning — store a version number or updated-at timestamp alongside the cached value, and have the writer compare-and-swap so an older read never overwrites a newer cache entry.
  • Route reads-after-write to the primary, avoiding replica lag entirely for the window right after a write (read-your-writes consistency), covered further in distributed-systems-core.

3. Read-Through, Write-Through, and Write-Behind

These three patterns differ from cache-aside in one structural way: the cache itself (or a library/sidecar sitting in front of it) owns the responsibility of talking to the database, not the application. The application only ever talks to the cache.

Read-through

On a miss, the cache — not the application — is configured with a loader function that fetches from the database, populates itself, and returns the value. Functionally this produces the same outcome as cache-aside's read path, but the population logic lives in one place (the cache layer) instead of being duplicated across every call site in application code. Libraries like Guava's LoadingCache or Caffeine's CacheLoader implement this locally — e.g., catalog-service could configure a Caffeine LoadingCache<Long, Product> whose loader function is "query the products table by id," so every call site just does cache.get(productId) without ever writing its own miss-handling logic. At the distributed level it requires a caching layer with plugin support (rare for raw Redis, common in ORMs or dedicated caching proxies).

Write-through

Every write goes to the cache first, and the cache synchronously writes it to the database before acknowledging the write to the application. This guarantees the cache and database are never inconsistent (barring the write itself failing), at the cost of every write now paying the full database write latency plus the cache write latency. It solves the cache-aside race condition by construction — there is no window where a stale read can repopulate the cache, because the cache is always updated in the same synchronous path as the database write. A seller's inventory update (decrementing availableQty after a sale) is a reasonable write-through candidate: correctness matters enough that paying extra write latency to guarantee the cache and database agree is worth it.

Write-behind (write-back)

Writes go to the cache and are acknowledged to the application immediately; the cache asynchronously flushes the write to the database later, often batched. This gives the lowest possible write latency (client never waits on the database) and can dramatically reduce database write load by coalescing many rapid updates to the same key into one flush. The trade-off is durability: if the cache node crashes before the buffered write is flushed, that write is lost permanently, even though the client already received a success response. This pattern is used where losing a small, bounded window of recent writes is an acceptable trade against write throughput — view counters, telemetry, or rate-limit counters, or a product's "viewed 4,213 times today" counter on ShopSphere — and essentially never used for anything requiring strict durability (financial ledgers, orders, payment records — see payment-systems-idempotency for why payment state specifically cannot tolerate this kind of silent loss).

4. Eviction Policies

A cache has finite memory. When it's full and a new key needs to be inserted, something has to be evicted. The eviction policy is a bet about which entries are least likely to be needed again soon. On ShopSphere, that bet plays out concretely: the catalog cache can hold, say, 200,000 product entries in memory, but the full catalog across all sellers is tens of millions of products — the eviction policy decides which 200,000 stay warm.

Eviction Policies
├── Recency-based
│   ├── LRU   (Least Recently Used)      — evict the oldest-untouched entry
│   └── FIFO  (First In, First Out)      — evict the oldest-inserted entry, ignoring access
├── Frequency-based
│   └── LFU   (Least Frequently Used)    — evict the lowest access-count entry (needs aging)
├── Hybrid / admission-aware
│   ├── Segmented LRU (SLRU)             — probationary + protected LRU segments
│   └── Window TinyLFU (W-TinyLFU)       — small LRU admission window + frequency sketch
│                                            (used by Caffeine, the JVM cache library)
└── Time-based (orthogonal, not a "which victim" policy)
    └── TTL   (Time To Live)             — entry expires by clock, independent of memory pressure

LRU (Least Recently Used)

Evict the entry that hasn't been accessed for the longest time, on the assumption that recent access predicts near-future access (temporal locality). The efficient implementation is a combination of a hash map (key → node pointer, for O(1) lookup) and a doubly linked list ordered by recency (most-recently-used at the head, least-recently-used at the tail):

  • On get(key): look up the node via the hash map in O(1), then unlink it from its current position and re-insert it at the head — O(1) because it's a doubly linked list (you have direct pointers to the node's neighbors, no traversal needed).
  • On put(key, value) when full: evict the node at the tail (O(1), you hold a tail pointer), remove its entry from the hash map, then insert the new node at the head.

This is exactly the internal structure of Java's LinkedHashMap in access-order mode (new LinkedHashMap<>(cap, 0.75f, true)), which is why overriding removeEldestEntry on it is the textbook way to build a bounded LRU cache in five lines — see collections-internals for how that hash map is actually built underneath. A plain LRU catalog cache works reasonably for ShopSphere on an ordinary day: recently-viewed products predict near-future views. It falls down during a flash sale, though — a one-off marketing push that floods the cache with a burst of curiosity views for products nobody will look at again pushes out genuinely hot, steadily-popular items purely because they weren't touched in the last few seconds.

LFU (Least Frequently Used)

Evict the entry with the lowest access count, on the assumption that historically popular items stay popular. The naive implementation (a counter per key) has a serious flaw: an item that was extremely popular yesterday but hasn't been touched today keeps a high count forever and can never be evicted, starving out genuinely new hot items — this is the "cache pollution from old popularity" problem. Concretely: a product that trended for a week last month keeps a sky-high lifetime counter and permanently occupies cache space, while this week's actual best-seller can never accumulate enough hits to displace it. Real LFU implementations solve this with aging: counts decay over time (halved periodically, or decremented on a schedule), so popularity has to be sustained, not just historical, to survive.

FIFO and TTL

FIFO evicts in strict insertion order regardless of access pattern — simple, cheap, but ignores locality entirely, so it's rarely used for general-purpose caches (it's more common in bounded queues). TTL-based expiry isn't really an eviction policy in the "which victim do I pick under memory pressure" sense — it's a correctness mechanism: every entry carries an expiration timestamp and is treated as absent once that time passes, independent of memory pressure. TTL and a capacity-driven eviction policy (LRU/LFU) are typically used together: TTL bounds staleness (a cached product price is never wrong for longer than the TTL, even if nobody ever writes to invalidate it explicitly), eviction bounds memory.

Window TinyLFU: the practical hybrid

Plain LRU is vulnerable to one-off bursts; plain LFU is vulnerable to stale historical popularity. Window TinyLFU (the algorithm behind Caffeine, the JVM in-process cache library that has largely replaced Guava's cache) combines both ideas cheaply. New entries first land in a small admission window managed by plain LRU — this absorbs the ShopSphere flash-sale scenario, giving a newly-viewed product a chance to prove itself recently-popular without immediately displacing established entries. To graduate out of the window into the "main" cache space, a candidate is compared against the entry it would evict using a compact, probabilistic frequency sketch (a small array of counters, similar in spirit to a Bloom filter, that estimates how often each key has been seen recently without storing an exact per-key counter) — whichever of the two has the higher estimated frequency wins, and the loser is evicted. This gives near-optimal hit rates across both recency-skewed and frequency-skewed access patterns simultaneously, at a small, fixed memory overhead per entry, which is why it has become the default choice for high-performance local caches rather than either pure LRU or pure LFU.

How Redis actually approximates LRU

Exact LRU requires maintaining a globally ordered structure (like the linked list above) that every single access has to touch and reorder. For Redis, which is single-threaded and processes hundreds of thousands of operations per second, adding an O(1)-but-still-real bookkeeping step and extra pointer memory to every single command is real overhead at that scale. Instead, Redis stores an approximate "last accessed" timestamp (a compact clock value) on each key object, and when it needs to evict, it takes a random sample of N keys (maxmemory-samples, default 5) and evicts the one with the oldest access time among just that sample — not a global scan. Increasing the sample size gets closer to true LRU at the cost of more CPU per eviction; the default of 5 is deliberately a "good enough" approximation, and Redis's own documentation is explicit that this is not exact LRU. Redis 4.0+ also offers LFU (maxmemory-policy allkeys-lfu), implemented with an 8-bit logarithmic counter per key that increments probabilistically (so it doesn't need 64 bits per key) and decays over time — the aging solution described above, made memory-cheap.

Where each policy actually fits for ShopSphere

A realistic ShopSphere caching stack layers these rather than picking one globally. Redis (the shared, distributed tier in front of the database, holding product data read by many service instances) runs allkeys-lru or allkeys-lfu as a blunt, cluster-wide memory-pressure valve. Inside each catalog-service instance, a local, in-process Caffeine cache (Window TinyLFU) sits in front of Redis itself, absorbing the very hottest handful of products with sub-microsecond, no-network-hop latency, and falling back to Redis on a local miss before ever reaching the database. This two-tier shape — a small, fast, smart local cache in front of a larger, dumber, shared distributed cache — is common precisely because the two layers are solving different problems: the local tier optimizes latency and offloads Redis traffic, the shared tier ensures every instance sees a consistent, cross-instance view.

5. Cache Invalidation

Phil Karlton's line — "there are only two hard problems in computer science: cache invalidation and naming things" — is not a joke about difficulty for its own sake; it points at something real. Invalidation is hard because it requires the cache to know, at the exact right moment, that a piece of truth it's holding a copy of has changed somewhere else, in a system where "somewhere else" may be a different process, a different node, or a different service entirely, with no shared clock and no atomic way to make "update the source of truth" and "invalidate the copy" happen as one operation.

StrategyMechanismTrade-off
TTL-basedEvery entry expires automatically after N secondsSimple, self-healing, but guarantees staleness up to the full TTL window on every entry, always
Explicit invalidation on writeWriter deletes/updates the specific cache key it just modifiedPrecise and immediate, but requires every write path to know about and correctly touch every cache key derived from that data — easy to miss one
Event-driven invalidationA change-data-capture stream or message bus (e.g., a Debezium feed off the database's write-ahead log, or an application-published event) triggers invalidation in any service holding a cache of that dataDecouples writers from having to know about every downstream cache, and works across service boundaries, but adds a message bus as a dependency and introduces its own propagation delay

Explicit invalidation is what most cache-aside systems use directly (the delete call in the write path from Section 2). Event-driven invalidation matters once the same underlying data is cached in multiple independent services — on ShopSphere, a product's price is cached by catalog-service, but also independently cached by search-service (for search result snippets) and by the recommendation engine (for "similar products" cards). When a seller changes a price, catalog-service's own write path knows to delete its own cache key, but it has no direct way to know search-service and recommendation-service are also holding a stale copy — that's exactly the case where an event like ProductPriceChanged published to Kafka, consumed by every service that caches product data, does what explicit per-writer invalidation structurally cannot.

6. Thundering Herd / Cache Stampede

A stampede happens when a single hot key expires (or is evicted, or the cache node restarts) and a large burst of concurrent requests for that exact key all miss at once. Every one of those requests independently falls through to the database to recompute the same value, and if that computation is expensive (a heavy aggregation query, a slow downstream call), the database or downstream service receives a sudden multiplied spike of identical, redundant load — sometimes enough to fall over, at exactly the moment it's least equipped to handle a spike, because it's already under the same load that made the cache valuable in the first place. The canonical ShopSphere instance: a single flash-sale product's cache entry expires while 50,000 customers are hammering checkout for it at once — without protection, all 50,000 requests miss simultaneously and all 50,000 hit the database with the identical product lookup, at precisely the worst possible moment.

  • Locking / single-flight: the first request to miss acquires a short-lived lock (e.g., SET lock:product:8841 NX PX 5000 in Redis — NX means "only set if the key doesn't already exist," PX 5000 gives it a 5-second auto-expiring TTL so a crashed lock-holder can't strand the lock forever) and is the only one allowed to query the database and repopulate the cache; every other concurrent request either waits briefly and retries the cache, or is served the last known (possibly slightly stale) value.
  • Request coalescing: at the application layer, concurrent in-flight requests for the same key are collapsed into a single outstanding database call, and all callers subscribe to its result rather than each issuing their own — this is single-flight implemented in-process instead of via a distributed lock.
  • Jittered TTLs: instead of setting every related key to expire at exactly the same TTL (which synchronizes their expiry and guarantees a herd later), add randomized jitter — e.g., TTL = base ± random(0, base * 0.1) — so expirations spread out over time instead of clustering. This matters specifically because a flash sale typically caches many products at once (the entire sale catalog, warmed together when the sale page loads) — without jitter, they'd all expire together too.
  • Probabilistic early expiration (early recomputation): instead of waiting for a hard expiry, each read has a small, increasing probability of proactively recomputing the value before it actually expires, with the probability rising as the entry approaches its TTL. This means recomputation gets spread across many individual requests ahead of the deadline rather than concentrated into one burst exactly at expiry — the well-known formulation of this is the XFetch / "beta stampede prevention" algorithm.

7. Redis Architecture Internals

Single-threaded event loop

Redis executes all commands on a single thread, which sounds like it should be a bottleneck but is in fact central to why it's fast and predictable. The reasoning: Redis's operations are almost entirely in-memory and CPU-bound at the microsecond scale, not I/O-bound — so the traditional argument for multithreading (overlap CPU work with I/O wait) doesn't apply the way it does for a disk-bound database. A single thread means every command executes atomically with respect to every other command — there is no possibility of two clients' INCR calls interleaving at the instruction level, no lock contention, and no context-switching overhead. Concurrency across many client connections is handled by an event loop (built on epoll/kqueue) that multiplexes thousands of socket file descriptors on that one thread, dispatching whichever socket has data ready without blocking on any single slow client. The actual bottleneck this creates is that any single slow command blocks everything else — an unbounded KEYS * scan or a SORT over a huge set stalls every other client for its duration, which is why Redis provides SCAN (cursor-based, non-blocking iteration) instead of KEYS for production use, and why Redis 6+ offloads I/O threading (reading/writing socket buffers, not command execution) to background threads purely to reduce network-layer overhead, without changing the single-threaded execution guarantee for the commands themselves.

Why a skip list for sorted sets, not a balanced tree

A skip list gives the same O(log N) expected search/insert/delete as a balanced binary tree (like a red-black tree), but with a much simpler implementation — no rotations, no rebalancing logic — built from ordinary linked-list nodes with randomized "express lane" pointers at multiple levels. It also makes range queries (fetch all elements with a score between X and Y) and ordered iteration naturally cheap, because at the base level it is just a sorted linked list. Redis documents this choice as pragmatic: a skip list gives comparable performance to a balanced tree with substantially less code complexity and easier debugging.

Persistence: RDB vs AOF

Redis is an in-memory store, but "in-memory" and "durable" aren't mutually exclusive if you're willing to trade some performance or some recovery precision.

  • RDB (snapshotting): periodically forks the process and writes the entire dataset to a compact binary file on disk (the fork's copy-on-write pages mean the parent process keeps serving traffic uninterrupted while the child writes). Fast to restart from (just load one file), compact, but any writes since the last snapshot are lost on a crash — the exposure window is however often you snapshot (e.g., every 60 seconds via save 60 10000, meaning "snapshot if at least 10000 keys changed in 60 seconds").
  • AOF (Append-Only File): logs every write command to a file as it happens. With appendfsync everysec (the common default trade-off), at most one second of writes can be lost on crash; with appendfsync always, effectively zero loss but every write now pays a disk fsync — a massive latency cost for an otherwise in-memory store. AOF files are larger and slower to replay on restart than an RDB snapshot, which is why Redis periodically rewrites/compacts the AOF file in the background (folding a long command history down to the minimal set of commands that reproduce the current state).
  • Redis commonly runs both: RDB for fast full backups and fast restarts, AOF for a tighter durability bound, with AOF used for the actual crash-recovery replay and RDB used for portable backups/replication bootstrapping.

Replication: primary-replica

A Redis primary asynchronously streams its write stream (effectively AOF-like propagation) to one or more replicas, which apply those writes and can serve read traffic. Because replication is asynchronous, there is a real consistency gap: an acknowledged write on the primary is not guaranteed to have reached a replica yet, so a client reading from a replica immediately after writing to the primary can observe stale data (or a replica can lag arbitrarily far behind under network pressure or heavy write load). This is the direct Redis instance of the general async-replication trade-off discussed in database-architecture: you get read scalability and failover targets, but only eventual, not immediate, consistency on replica reads.

Redis Cluster: sharding via hash slots

Redis Cluster partitions the entire keyspace into 16384 fixed hash slots. Every key is assigned to a slot via CRC16(key) mod 16384, and each slot is owned by exactly one primary node (with its own replicas for failover) at any given time. A client can compute which node owns a key's slot itself (using cluster topology metadata it caches), or ask any node and get redirected (MOVED/ASK responses) to the correct one. Resharding — moving slot ownership from one node to another, e.g., when adding a new node to spread load — is done slot-by-slot: the cluster migrates the keys within a slot to the new owner, and during that migration window a client might get an ASK redirect telling it to retry a specific key against the new node even though the slot hasn't fully migrated yet. Multi-key operations (like a transaction touching two keys) are only supported if both keys hash to the same slot, which is why Redis Cluster supports "hash tags" — {user:1000}.profile and {user:1000}.settings both hash only on the user:1000 portion inside the braces, forcing them onto the same slot deliberately so they can be operated on together.

Redis Sentinel

Sentinel is a separate, lighter-weight high-availability mechanism (distinct from Cluster) for a single primary-replica set without sharding. A quorum of Sentinel processes monitors the primary; if a majority agree it's unreachable, they elect a new primary from among the replicas and reconfigure the remaining replicas to follow it, then inform clients (via pub/sub notifications and by acting as a discovery service) of the new primary's address. This gives automatic failover without manual intervention, at the cost of a brief unavailability window during the failure-detection-and-election process, and it inherits the same async-replication consistency gap — a failover can lose any writes that hadn't yet reached the promoted replica.

8. CDN Caching (Edge Caching)

The same core idea — keep a copy near where it's consumed — applies at the network edge, not just in application memory. A CDN (Content Delivery Network) caches responses at points of presence geographically close to end users, so a request for a static asset (or even a cacheable API response) never has to traverse the full network path back to the origin server. ShopSphere's product images, and even the JSON response of a rarely-changing "list categories" endpoint, are natural CDN candidates — a customer in Tokyo browsing the catalog shouldn't have every product thumbnail round-trip to an origin server in a US data center. What's cacheable and for how long is controlled by HTTP Cache-Control headers: max-age=3600 tells any cache the response is fresh for an hour, no-store forbids caching entirely (appropriate for a personalized cart or order response — nothing that varies per customer should ever be cached at a shared edge), private restricts caching to the end client (not shared caches like a CDN), and s-maxage sets a separate TTL specifically for shared caches, overriding max-age for them. CDN invalidation ("purging") faces the same fundamental problem as Section 5's cache invalidation, just at a different layer and often with higher propagation latency, since a purge has to reach every edge node globally — a seller uploading a corrected product photo doesn't see it update everywhere instantly, precisely because of this propagation delay.

Concepts Worth Being Able to Explain From First Principles

Why does deleting a cache key on write, rather than updating it, reduce (but not eliminate) the risk of serving stale data forever?
Deleting is order-independent: no matter which of several concurrent writers' deletes executes last, the outcome is the same — an empty cache slot that the next reader will repopulate from the database. Updating is order-dependent: if writer A's database write and cache update happen, then writer B's database write and cache update happen, the cache correctly ends with B's value. But if the operations interleave differently — A writes DB, B writes DB, then A's delayed cache update finally lands after B's — the cache ends up holding A's stale value with no future write scheduled to fix it, because from the system's perspective the "last write" (B's) has already happened and won't recur. Deletion doesn't fully eliminate the race (a read that started before the write and lands after the delete can still restock the stale value), but it removes the specific failure mode where update-ordering directly determines correctness.
Why is Redis's LRU only approximate, and what would it cost to make it exact?
Exact LRU requires a globally consistent recency ordering that every single read touches and re-threads — in practice a doubly linked list where each access unlinks and re-inserts a node at the head. Maintaining that on every single command, at the hundreds-of-thousands-of-ops-per-second scale Redis targets on a single thread, adds real per-command overhead and extra memory (two pointers per key) purely for bookkeeping that most workloads don't need to be perfectly precise. Instead, Redis stores a compact last-access timestamp on each key and, on eviction, samples a small random subset (maxmemory-samples, default 5) and evicts the oldest among just that sample. This trades exactness for near-zero per-access overhead; increasing the sample size buys closer-to-true LRU behavior at the cost of more CPU work per eviction.
What actually causes a cache stampede, and why doesn't a longer TTL fix it?
A stampede happens when many concurrent requests for the same key all discover a miss at effectively the same instant — because the key expired, was evicted, or the cache restarted — and each of them independently goes to the database to recompute the same value, multiplying load on the database exactly at the moment the key's popularity (which is why it's cached at all) is highest. A longer TTL doesn't fix this: it only postpones the moment of collective expiry, and if many related keys share the same TTL, it also makes the eventual synchronized expiry burst larger and more concentrated, not smaller. Fixing it requires either serializing who is allowed to repopulate (single-flight/locking), spreading expirations over time (jitter), or recomputing before expiry instead of only after (probabilistic early expiration).
Why does Redis being single-threaded not make it slow, and where does that model actually break down?
Redis operations are in-memory and CPU-bound at the microsecond scale, so there's little I/O wait for a second thread to usefully overlap with — the traditional justification for multithreading doesn't apply the same way it does to disk-bound systems. Single-threaded execution also buys atomicity for free: no command can be interrupted mid-execution by another command, eliminating a whole category of locking and race conditions inside Redis itself. An event loop (epoll/kqueue-based) lets one thread multiplex many client connections without blocking. The model breaks down when a single command takes a long time to execute — an unbounded KEYS *, a large SORT, or a huge DEL on a massive collection blocks the entire server for every other client for that command's duration, which is why cursor-based alternatives like SCAN exist and why expensive commands need to be paginated or avoided in production.
What consistency guarantee do you actually get when reading from a Redis replica, and why?
You get eventual consistency, not immediate consistency. Replication from a Redis primary to its replicas is asynchronous: the primary acknowledges a write to the client as soon as it's applied locally, then streams the write to replicas separately, with no guarantee about how quickly that stream is applied. A client that writes to the primary and then immediately reads from a replica can observe the old value, because the replica simply hasn't received and applied the write yet. This gap can widen arbitrarily under replica load or network delay, which is why read-your-own-writes requirements typically need to route the immediate post-write read back to the primary rather than a replica.
Why does Redis Cluster use a fixed 16384 hash slots instead of hashing keys directly onto nodes?
Hashing keys directly onto a set of N nodes (e.g., hash(key) mod N) means that changing N — adding or removing a node — reshuffles almost every key's target node, requiring a massive data migration for even a small topology change. By introducing a fixed intermediate layer of 16384 slots, resharding becomes a matter of reassigning ownership of a subset of slots from one node to another — the mapping of key to slot never changes, only the mapping of slot to node does. This makes scaling the cluster up or down an operation proportional to the slots being moved, not to the entire keyspace, and it lets migration happen incrementally and slot-by-slot rather than all at once.
Why is write-behind caching considered risky, and what kind of data is it appropriate for?
Write-behind acknowledges a write to the client as soon as it lands in the cache, then flushes it to the durable store asynchronously later, often batched with other writes. If the cache node crashes, restarts, or loses its in-memory state before that flush happens, the write is gone permanently — even though the caller already received a success response and has no reason to retry. This makes write-behind inappropriate for anything where losing an acknowledged write is unacceptable, such as financial transactions or order records. It's appropriate for data where a bounded window of loss is tolerable in exchange for lower write latency and reduced database write load — view counters, engagement metrics, or ephemeral rate-limiting state, where losing a few recent increments on a crash is a minor, self-correcting inaccuracy rather than a real inconsistency.
Why does Window TinyLFU outperform both plain LRU and plain LFU, and what's the actual mechanism?
Plain LRU and plain LFU each fail against a pattern the other handles well. LRU is vulnerable to a burst of one-off, never-to-repeat accesses (a viral marketing spike on a product nobody actually cares about long-term) evicting genuinely, steadily popular entries purely because they weren't touched in the last few milliseconds. Plain LFU is vulnerable to stale historical popularity — an item that was hot last month keeps a high lifetime counter that a genuinely hot new item can never catch up to, unless the implementation adds decay. Window TinyLFU sidesteps both by splitting responsibilities: a small admission-window LRU segment gives every new entry a fair, short trial period to prove itself without immediately competing against established entries, and a compact probabilistic frequency sketch (not a full per-key counter — a small fixed-size array of saturating counters, similar in spirit to a Bloom filter) decides, only when a window entry is about to graduate and would need to evict something from the main cache, which of the two has genuinely higher sustained frequency. The result approximates the hit rate of an ideal, much more expensive frequency-tracking policy at close to the memory cost of plain LRU, which is why Caffeine adopted it as its default.
