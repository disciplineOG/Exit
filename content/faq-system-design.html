Most Asked Interview Questions: System Design (HLD & LLD)

Scaling Load Balancing CAP Theorem Consistent Hashing Rate Limiting Design Patterns
Why this matters

System design rounds test a different muscle than coding rounds: instead of "does this compile," the interviewer is probing whether you can reason about trade-offs at scale — consistency versus availability, throughput versus latency, simplicity versus flexibility. Backend Java interviews almost always split this into a High-Level Design (HLD) round, about distributed system architecture, and a Low-Level Design (LLD) round, about class design and design patterns in a single service. This page covers the fundamentals interviewers expect you to rattle off without hesitation, plus quick-reference answers for the handful of case studies (URL shortener, rate limiter, notification system, flash sale) that come up in nearly every HLD interview loop.

High-Level Design (HLD) Fundamentals

What is system design, and what's actually being evaluated in an HLD interview?
System design is the practice of defining the architecture, components, and data flow of a software system before (or while) building it — deciding things like which services exist, how they talk to each other, where data lives, and how the system behaves under load or failure. A High-Level Design (HLD) interview specifically evaluates whether you can take an intentionally vague prompt ("design a URL shortener," "design ShopSphere's checkout") and turn it into a concrete architecture: clarifying requirements and scale, choosing between a monolith and microservices, picking a database and caching strategy, and identifying bottlenecks — all while explaining trade-offs out loud rather than presenting one "correct" answer. Interviewers are not grading whether you memorized a specific diagram; they're grading whether your reasoning is sound, whether you ask the right clarifying questions before designing (expected traffic, read/write ratio, consistency needs), and whether you can defend why you chose one option over another. This is why nearly every HLD answer in this FAQ ends with "it depends" plus the concrete factors that tip the decision — that's the actual skill being tested, not rote recall.
What's the difference between horizontal and vertical scaling, and when would you choose each?
Vertical scaling ("scaling up") means adding more resources — CPU, RAM, faster disks — to a single existing machine, while horizontal scaling ("scaling out") means adding more machines and distributing load across them. Vertical scaling is simpler operationally (no distributed coordination, no load balancer, no data partitioning) but hits a hard ceiling — there's a maximum size machine you can buy — and creates a single point of failure, since that one bigger box going down takes everything with it. Horizontal scaling has no theoretical ceiling and improves fault tolerance (one node dying doesn't take the whole system down), but it introduces real complexity: you now need a load balancer, you need your application to be stateless or to externalize state (sessions, caches) so any node can serve any request, and if there's a database involved you eventually need to think about sharding. In practice, most production systems do both — vertically size individual nodes to a reasonable, cost-effective point, then scale horizontally beyond that — and a service like ShopSphere's order-service is a good example of horizontal-scaling-friendly design, since it's stateless and can run as N identical replicas behind a load balancer.
What are the main load balancing algorithms, and how does each decide where to send a request?
Round robin sends each successive request to the next server in a fixed rotation, cycling back to the start — it's the simplest option and works well when all servers are equally sized and all requests are roughly equal cost, but it can overload a server that happens to be mid-way through several slow requests since it ignores current load entirely. Least connections sends each new request to whichever backend currently has the fewest active (in-flight) connections, which handles uneven request durations far better than round robin — if one backend is stuck processing a slow report-generation request, least connections naturally routes new traffic elsewhere instead of blindly continuing the rotation. Consistent hashing routes a request based on a hash of some request attribute (commonly a client ID or cache key) mapped onto a fixed hash ring, so the same key consistently lands on the same backend — this matters when the backend is stateful, such as routing all requests for a given customer's shopping cart to the same in-memory cache node. Weighted versions of round robin or least connections also exist, letting you send proportionally more traffic to bigger or newer instances. The choice generally comes down to: round robin for simple stateless equal-capacity fleets, least connections when request cost varies a lot, and consistent hashing whenever backend affinity (the same key should hit the same node) matters.
What's the difference between a Layer 4 (L4) and a Layer 7 (L7) load balancer?
A Layer 4 (L4) load balancer operates at the transport layer — it sees only IP addresses, ports, and TCP/UDP-level information, and makes its routing decision by forwarding packets to a backend without ever looking at the actual request content. This makes it extremely fast and low-overhead, since it doesn't need to parse or terminate the application-level protocol, but it also means it can't make smart, content-aware decisions — it can't route /orders/* differently from /products/*, because it never looks that deep. A Layer 7 (L7) load balancer operates at the application layer — it terminates the HTTP connection, reads the actual request (URL path, headers, cookies, even the request body), and can route based on that content: sending /checkout traffic to order-service and /search traffic to catalog-service from the same entry point, or routing based on a session cookie for sticky sessions. The trade-off is that L7 load balancing costs more CPU and latency per request because it has to fully parse the application protocol, while L4 is cheaper but blind to content. In practice, most production HTTP-based systems use an L7 load balancer or API gateway at the edge (since content-based routing and TLS termination are usually worth the overhead), while L4 load balancers show up for raw TCP workloads or as a cheap first layer in front of an L7 tier.
How does consistent hashing work, and why does it minimize remapping when nodes are added or removed?
Consistent hashing places both the servers (nodes) and the keys (requests, cache entries, etc.) onto the same conceptual ring of hash values — typically by hashing each node's identifier (like its IP address) to a position on the ring, and hashing each key the same way, then assigning a key to the first node found by walking clockwise from the key's position. The critical property is what happens when the node set changes: with naive hashing (e.g. hash(key) % N where N is the number of servers), adding or removing even one server changes N and therefore changes almost every key's assigned server, causing a near-total cache invalidation or data reshuffle. With consistent hashing, adding or removing a node only affects the keys that fall in the narrow ring segment immediately before that node — every other key's nearest clockwise node is unaffected, so on average only about 1/N of keys need to move. In practice, implementations also add "virtual nodes" — hashing each physical server to many points on the ring instead of one — to spread load more evenly and avoid one physical server owning a disproportionately large arc of the ring. This is exactly why consistent hashing is the standard choice for distributed caches and sharded stores, like routing ShopSphere product-cache lookups across a pool of Redis nodes that occasionally scales up or down.
What are the main caching strategies — cache-aside, write-through, write-back — and why is cache invalidation considered a hard problem?
Cache-aside (also called lazy loading) has the application check the cache first; on a miss, it reads from the database, then populates the cache for next time, and writes go directly to the database while the corresponding cache entry is invalidated or updated separately — this is the most common pattern because the cache only ever holds data that's actually been requested, but it means the first request for any key is always slow (a "cold" read) and there's a window where the cache and database can briefly disagree. Write-through has every write go through the cache first, which then synchronously writes to the database before acknowledging — reads are always fast because the cache is always up to date, but every write pays the latency cost of both the cache and database write, and data that's never read still consumes cache space. Write-back (write-behind) has writes land in the cache and get acknowledged immediately, with the actual database write happening asynchronously afterward — this gives the lowest write latency, but risks data loss if the cache crashes before the deferred write is flushed, so it's only appropriate when some data loss window is tolerable or the cache itself is made durable. Cache invalidation is considered one of the two hardest problems in computer science (alongside naming things) because it requires answering, correctly and quickly, "does this cached value still reflect reality" — with multiple services or instances able to write the underlying data, a time-to-live (TTL) that's too long serves stale data (a customer sees an out-of-stock item as available), while a TTL too short defeats the purpose of caching by hammering the database; explicit invalidation (deleting or updating the cache entry on write) is more precise but requires every writer to remember to do it, and race conditions between a write and a concurrent cache refresh can still leave a stale value in place.
What is the CAP theorem, and can you give a concrete trade-off example?
The CAP theorem states that a distributed data store can only guarantee two of three properties at the same time during a network partition: Consistency (every read receives the most recent write, or an error — all nodes see the same data at the same time), Availability (every request receives a non-error response, even if it isn't the most recent write), and Partition tolerance (the system continues operating even when network failures prevent some nodes from communicating with others). Because real networks do experience partitions (a switch fails, a data-center link drops), partition tolerance isn't really optional for a distributed system — the practical choice is between consistency and availability specifically during a partition. A concrete example: imagine ShopSphere's inventory-service is replicated across two data centers, and the network link between them goes down. A CP (consistent, partition-tolerant) design would have one side (or both) refuse writes until the partition heals, guaranteeing no two data centers disagree on stock count, at the cost of rejecting checkout requests during the outage. An AP (available, partition-tolerant) design would let both sides keep accepting writes independently during the partition, guaranteeing checkout keeps working, at the cost of both sides potentially decrementing the same unit of stock — an oversell that has to be reconciled once the partition heals. Systems like traditional relational databases with synchronous replication lean CP, while systems like Cassandra or DynamoDB (in their default configurations) lean AP, and the right choice depends on whether stale/conflicting data or downtime is the worse failure mode for that specific data.
What are the main database sharding strategies, and what is the "hot partition" problem?
Sharding splits a single logical database across multiple physical nodes so no single node has to hold or serve the entire dataset. Range-based sharding assigns each shard a contiguous range of the shard key (e.g. order IDs 1–1,000,000 on shard A, 1,000,001–2,000,000 on shard B) — it's simple and makes range queries efficient (fetching "all orders from last week" can hit one or two shards), but new data often concentrates at the tail end of the range, overloading whichever shard currently owns the newest IDs. Hash-based sharding applies a hash function to the shard key and uses the result to pick a shard, spreading data much more evenly at random, but it makes range queries expensive since a range of keys is now scattered across every shard. Geo-based sharding assigns shards by geographic region (e.g. a customer's country or data-residency requirement), which keeps data close to the users who access it most and can satisfy legal data-residency rules, but naturally creates uneven load if one region has far more traffic than others. The "hot partition" (or "hot shard") problem is when one shard receives disproportionately more traffic or data than the others regardless of strategy — a classic ShopSphere example is a single viral flash-sale product whose orders all hash or range onto the same shard, so that one database node becomes the bottleneck for the entire sale even though the other shards sit idle; mitigations include choosing a shard key with higher cardinality (spreading a hot product's writes across a composite key like product ID plus a random suffix), adding a caching layer in front of the hot shard, or dynamically splitting a shard that's grown too hot.
What is a CDN (Content Delivery Network), and what problem does it solve?
A CDN (Content Delivery Network) is a geographically distributed network of proxy servers ("edge" or "point-of-presence" nodes) that cache and serve content from a location physically closer to the end user, instead of every request traveling all the way back to the origin server. The core problem it solves is latency and origin load: the further a request has to travel over the network, the more round-trip time it accumulates, and every request served from an edge cache is one less request the origin server has to handle. CDNs are most naturally suited to static or infrequently-changing content — images, CSS/JavaScript bundles, videos — but modern CDNs also support caching API responses with short time-to-live (TTL) values and can absorb sudden traffic spikes (like a flash-sale product page going viral) without that load ever reaching the origin. For ShopSphere, catalog-service's product images and static category pages are ideal CDN candidates: a customer in Mumbai loading a product image fetches it from a nearby edge node rather than from an origin server sitting in a single primary data center, and the origin only has to serve that image once per edge location until the cache TTL expires.
What are the main rate limiting algorithms — token bucket, leaky bucket, sliding window — and how do they differ?
Token bucket maintains a bucket that holds up to a fixed number of tokens, refilled at a steady rate; each incoming request consumes one token, and a request is rejected (or queued) only when the bucket is empty — this naturally allows short bursts up to the bucket's capacity while still enforcing a long-run average rate, which is why it's the most commonly used algorithm for API rate limiting. Leaky bucket instead models requests as water poured into a bucket with a hole that drains at a fixed rate: requests are processed (or forwarded) at that constant, steady rate regardless of how bursty the incoming traffic is, and the bucket overflowing (queue filling up) causes new requests to be dropped — this smooths traffic to a strictly constant output rate but, unlike token bucket, doesn't allow legitimate bursts through even briefly. Sliding window counts requests within a moving time window rather than a fixed one; sliding window log keeps a timestamp per request and counts how many fall within the last window (precise but memory-heavy at scale), while sliding window counter approximates this by weighting the current and previous fixed windows proportionally to how much of each falls inside the sliding range (much cheaper, small approximation error) — this avoids the classic fixed-window bug where a client sends its full quota right at the end of one window and again right at the start of the next, doubling its effective rate right at the window boundary. In an interview, the practical framing is: token bucket if you want to allow bursts, leaky bucket if you need a strictly constant output rate (e.g. smoothing calls to a downstream partner API), and sliding window when precise, boundary-safe accuracy matters more than raw efficiency — ShopSphere's public order-service API commonly uses token bucket per API key, since it tolerates short legitimate bursts (a customer's page reload) without punishing normal usage.
How would you design a distributed unique ID generator, and why can't you just use an auto-increment column?
A single database's auto-increment column works fine until you shard that database or run multiple write nodes, at which point two independent auto-increment sequences can both produce the same ID (e.g., "1, 2, 3..." on shard A and "1, 2, 3..." on shard B), causing collisions once data from both shards has to coexist. The classic solution, popularized as Twitter's Snowflake algorithm, generates a 64-bit ID by packing together a timestamp (milliseconds since a custom epoch, occupying the most significant bits so IDs are roughly sortable by creation time), a machine or worker ID (identifying which node generated this ID, so concurrent nodes can never collide), and a per-millisecond sequence number (a local counter that increments if multiple IDs are requested within the same millisecond on the same node) — each node can generate IDs independently, with no coordination or network round-trip required, because the machine ID slice guarantees global uniqueness even when two nodes generate an ID in the exact same millisecond. This matters directly for the "centralized counter is a bottleneck" problem in short-code or order-ID generation: a Snowflake-style generator gives you roughly-sortable, globally unique, high-throughput IDs (millions per second across a fleet) without a single shared sequence that every request has to contend for. The trade-offs versus a plain auto-increment are added complexity (each node needs a stable, unique machine ID, often assigned via a coordination service like ZooKeeper at startup) and a dependency on reasonably synchronized clocks across nodes, since clock drift or an unexpected clock rewind can threaten the timestamp-ordering guarantee.
What's the difference between database replication and sharding, and what is leader-follower (master-replica) replication used for?
Sharding splits different data across different nodes (each shard holds a distinct subset of rows), so it scales both read and write throughput but means any given piece of data lives on exactly one shard (plus whatever replicas that shard has). Replication instead copies the same data onto multiple nodes, so it scales read throughput and improves availability, but every write still has to eventually reach every replica — it doesn't help write throughput at all. The most common replication topology is leader-follower (also called master-replica or primary-secondary): all writes go to a single leader node, which then streams its write-ahead log to one or more follower nodes that apply the same changes, and reads can be served from either the leader (always fresh) or a follower (fast, horizontally scalable, but potentially slightly stale). Replication can be synchronous (the leader waits for at least one follower to confirm before acknowledging the write, guaranteeing no data loss on leader failure but adding latency) or asynchronous (the leader acknowledges immediately and replicates in the background, which is faster but risks losing the last few writes if the leader crashes before followers catch up). A concrete ShopSphere example: catalog-service reads (browsing products) are overwhelmingly more frequent than writes (a seller updating a listing), so routing product-page reads to follower replicas while sending all writes to the leader is a standard, low-risk way to scale read capacity without touching the write path at all.
What's the difference between a monolith and a microservices architecture, and how do you decide between them?
A monolith is a single deployable application containing all the business logic — order handling, inventory, payments, notifications — as modules within one codebase and one process, while microservices split those same responsibilities into independently deployable services (order-service, inventory-service, payment-service, notification-service) that communicate over the network, typically via REST/HTTP calls or asynchronous messaging like Kafka. A monolith is simpler to develop, test, and deploy early on — one build, one deployment pipeline, no network calls between modules, and transactions across modules are trivial because they share one database connection — which is why most successful systems, including early ShopSphere, start as a monolith. Microservices earn their complexity once a system needs independent scaling (inventory-service handling far more read traffic than payment-service), independent deployability (shipping a notification-service fix without redeploying the entire platform), or team autonomy (separate teams owning separate services without stepping on each other's code); the cost is operational — network latency and partial failure between services, distributed transactions becoming genuinely hard (see the saga pattern), and needing service discovery, distributed tracing, and a much heavier deployment/observability stack. The honest interview answer is that microservices are a scaling response to organizational and technical growing pains, not a default starting point — "start monolith, extract services as bottlenecks and team boundaries demand it" reflects how most real systems, ShopSphere included, actually evolved.
What's the difference between a message queue and a publish-subscribe (pub-sub) system, and when do you reach for asynchronous messaging at all?
A traditional message queue (like RabbitMQ in classic queue mode) delivers each message to exactly one consumer — once a worker picks a message off the queue, it's gone for everyone else, which fits work-distribution use cases like processing a pool of pending orders. A publish-subscribe system (like Kafka topics, or RabbitMQ's fanout/topic exchanges) instead delivers each message to every subscriber independently, so multiple, unrelated consumers can each react to the same event without competing for it — this is the shape of ShopSphere's OrderPlaced event, which inventory-service, payment-service, and notification-service all need to see independently, not just one of them. You reach for asynchronous messaging (either shape) instead of a direct synchronous call whenever the producer shouldn't have to wait for every consumer to finish — the checkout request should return quickly once the order is accepted, not block until notification-service has actually sent an email — and whenever you want to decouple services so one being temporarily down (say, notification-service deploying) doesn't take down order placement entirely, since messages simply queue up and get processed once the consumer recovers. The trade-off versus a direct synchronous REST call is added infrastructure (a broker to run and monitor) and eventual rather than immediate consistency — the customer's order is placed immediately, but their confirmation email might arrive a few seconds later, which is an acceptable trade for most workflows but not for something like a synchronous payment authorization check.
What is an API gateway, and what responsibilities does it typically take off individual services?
An API gateway is a single entry point that sits in front of a set of backend services and handles cross-cutting concerns centrally instead of making every service reimplement them — typical responsibilities include authentication and authorization (verifying a token once, before routing to any backend), rate limiting (covered above), request routing (sending /orders/* to order-service and /products/* to catalog-service), response aggregation (combining calls to multiple services into one response for a client that shouldn't need to know the backend is split into microservices), and observability (centralized logging and metrics for every request that enters the system). For ShopSphere, a mobile app calling the gateway's single /checkout endpoint might trigger the gateway to internally call order-service, inventory-service, and payment-service and stitch together one response, so the client never needs to know those are three separate deployments. The trade-off is that the gateway becomes a critical path for every request — it needs to be highly available and low-latency itself, since an outage there takes down access to every backend service even if those services are individually healthy — which is why production gateways are typically deployed as a redundant, horizontally-scaled fleet rather than a single instance.
What's the difference between idempotency and retries, and why does an interviewer keep asking about idempotency keys?
An operation is idempotent if performing it multiple times has the exact same effect as performing it once — calling DELETE /orders/123 five times leaves the system in the same state as calling it once, so it's naturally idempotent, but calling POST /orders (create a new order) five times naively creates five separate orders. Retries are unavoidable in distributed systems — a network timeout doesn't tell you whether the request actually succeeded on the server before the response was lost, so the safe client behavior is often "retry" — but retrying a non-idempotent operation risks duplicate side effects, like charging a customer's card twice for one checkout because the payment confirmation response got lost in transit. The standard fix is an idempotency key: the client generates a unique key per logical operation (not per HTTP attempt) and sends it with the request; the server checks whether it has already processed that key and, if so, returns the original result instead of repeating the side effect. This comes up constantly in payment flows specifically — ShopSphere's payment-service would store the idempotency key alongside the payment record, so if order-service retries a timed-out payment-capture call, payment-service recognizes the key, does not double-charge the customer, and simply returns the already-completed result. Interviewers probe this because it's a genuinely common production incident (duplicate charges, duplicate order confirmation emails from at-least-once Kafka delivery) rather than an academic concern.
What is the circuit breaker pattern, and how does it prevent cascading failures?
A circuit breaker wraps a call to a downstream dependency (another service, a database, a third-party API) and tracks its recent failure rate; once failures cross a threshold, the breaker "trips" to an open state and starts failing fast — immediately returning an error (or a fallback) without even attempting the call — instead of letting every caller keep waiting on a dependency that's already struggling. After a cooldown period, the breaker moves to a half-open state and allows a small number of trial requests through; if those succeed, it closes again and resumes normal traffic, and if they fail, it reopens and waits longer. This directly prevents cascading failure: if payment-service starts timing out under load, without a circuit breaker every incoming checkout request from order-service would pile up waiting on those timeouts, exhausting order-service's own thread pool or connection pool and taking it down too, which then cascades to whatever calls order-service — a circuit breaker cuts that chain by failing fast once payment-service is clearly unhealthy, giving it room to recover instead of being buried under retried traffic. In a Java stack this is commonly implemented with Resilience4j (the modern standard) or the older Hystrix, usually combined with a fallback (e.g., "payment temporarily unavailable, please retry" returned immediately) and often paired with a timeout and bulkhead (isolating the thread/connection pool used for that one dependency) so one failing downstream call can't starve resources needed for unrelated requests.
How do you do back-of-envelope capacity estimation in a system design interview, and why does the interviewer care about the actual numbers?
Back-of-envelope estimation means translating a vague scale requirement ("design for ShopSphere's national scale") into concrete numbers for traffic, storage, and bandwidth before choosing an architecture — for example: 10 million daily active users, each placing an average of 0.2 orders/day, gives roughly 2 million orders/day, or about 23 orders/second on average — but interviewers usually push further and ask about peak load, since a flash sale might concentrate 10-20x that average into a short window, meaning the system needs to handle several hundred orders/second at peak, not just the daily average. The same exercise applies to storage: if each order record is roughly 1 KB and you store 2 million orders/day, that's about 2 GB/day or under 1 TB/year, which tells you immediately that a single well-indexed relational database can likely hold years of order history without needing to shard purely for storage volume (though write throughput or availability requirements might still justify sharding). Interviewers care about the actual numbers because "it depends" without quantification is untestable — the estimate is what tells you whether you need a CDN at all (irrelevant at 10 requests/second, essential at 100,000), whether a single Redis instance can hold your entire cache working set, or whether one database can handle the write load without partitioning. Getting the exact numbers slightly wrong is fine; the skill being evaluated is whether you reach for numbers at all before designing, rather than architecting for imaginary infinite scale.
A production service is falling over under load with real customers affected right now — how do you reason about horizontal scaling versus other fixes in the moment, and what's a scaling decision you'd actively avoid making under pressure?
In an active incident, the first move is rarely "add more architecture" — it's identifying the actual bottleneck (CPU-bound application servers, a saturated database connection pool, a single hot shard, an exhausted downstream dependency) because scaling the wrong tier wastes precious minutes and can even make things worse: adding more stateless order-service replicas behind a load balancer does nothing if the real bottleneck is the shared database those replicas all hit, and can actively worsen the outage by opening more concurrent database connections against an already-saturated connection pool. If application servers genuinely are the bottleneck (CPU or memory pressure per instance, not a shared downstream resource), horizontal auto-scaling is usually the safest lever precisely because it's reversible and incremental — you can add replicas without restarting existing ones. Vertical scaling (resizing an instance) is riskier mid-incident because it typically requires a restart, which briefly removes capacity at the worst possible time. What you actively avoid under pressure is an unreviewed structural change — resharding a hot database table, migrating to a different caching strategy, or flipping consistency guarantees (e.g., relaxing a CP system to AP) — live during the incident, since these are exactly the kind of high-blast-radius changes that are hard to reason about correctly under time pressure and hard to roll back if wrong; the disciplined move is to apply a fast, reversible mitigation first (scale out, shed load, enable a circuit breaker, add a temporary cache TTL) and defer any structural redesign — like actually fixing the hot-partition shard key — to a calm postmortem-driven follow-up.
How do you handle a transaction that spans multiple microservices, and what is the saga pattern?
A traditional ACID (Atomicity, Consistency, Isolation, Durability) transaction relies on a single database being able to lock rows and commit or roll back everything atomically, which works fine inside one service but breaks down the moment a business operation spans multiple services with their own separate databases — for example, ShopSphere's checkout needs to reserve inventory in inventory-service, charge the customer in payment-service, and create an order record in order-service, and there's no single database transaction that can span all three. The saga pattern solves this by breaking the operation into a sequence of local transactions, each committed independently in its own service, where every step also defines a compensating action that undoes it if a later step fails — so if inventory is reserved and payment succeeds but order creation fails, the saga runs compensating transactions (release the inventory reservation, refund the payment) to bring the system back to a consistent state, rather than relying on a lock that never existed across services in the first place. Sagas come in two coordination styles: choreography, where each service publishes an event when it finishes its step and the next service reacts to that event with no central coordinator (simpler, but the overall flow is implicit and harder to trace across services), and orchestration, where a central saga orchestrator explicitly calls each service in sequence and issues compensating calls on failure (easier to reason about and debug, but the orchestrator becomes a critical component). The key trade-off versus a real ACID transaction is that a saga only provides eventual consistency — there's a window where inventory has been reserved but payment hasn't been confirmed yet, which is visible to the rest of the system — so this pattern is appropriate specifically when strict cross-service atomicity isn't achievable at all, and the compensating-action logic (what does "undo a partially-sent notification" even mean) has to be designed as carefully as the happy path.

Low-Level Design (LLD) & Patterns

What is a design pattern, and what's the difference between an interface and an abstract class in Java?
A design pattern is a reusable, named solution to a recurring design problem — not a specific piece of code you copy, but a general shape of solution (like "decouple an algorithm's steps from its implementation" for Strategy) that's been proven useful across many unrelated codebases, which is why interviewers expect you to name and recognize the common ones rather than reinvent them from scratch each time. A closely related beginner-level question is the difference between an interface and an abstract class: an interface declares a contract — method signatures any implementing class must provide (plus, since Java 8, optional default methods with a body) — and a class can implement multiple interfaces, while an abstract class can hold actual state (instance fields) and partially-implemented methods alongside abstract ones, but a class can only extend one abstract class, since Java doesn't support multiple inheritance of implementation. The practical rule of thumb: use an interface to describe "what this type can do" when unrelated classes need to share a capability (e.g., Comparable, or ShopSphere's PaymentGateway implemented by several unrelated gateway classes), and use an abstract class when you have genuinely shared state or behavior among closely related subclasses (e.g., an abstract Shipment base class holding a common trackingId field and a shared calculateBaseCost() method, extended by StandardShipment and ExpressShipment).
What are the SOLID principles, in one line each?
S — Single Responsibility Principle: a class should have exactly one reason to change, meaning one clearly scoped responsibility (an OrderValidator should validate orders, not also send notifications). O — Open/Closed Principle: classes should be open for extension but closed for modification — you should be able to add new behavior (like a new payment method) without editing existing, already-tested code, typically by introducing a new implementation of an interface. L — Liskov Substitution Principle: a subtype must be substitutable for its base type without breaking the correctness of the program — if PriorityShipping extends Shipping, any code that works with a Shipping reference must keep working correctly when handed a PriorityShipping instance. I — Interface Segregation Principle: clients shouldn't be forced to depend on methods they don't use — many small, focused interfaces (like separate Readable and Writable interfaces) beat one large interface that forces every implementer to stub out irrelevant methods. D — Dependency Inversion Principle: high-level modules shouldn't depend on low-level modules directly; both should depend on abstractions — OrderService should depend on a PaymentGateway interface, not directly on a concrete StripePaymentGateway class, so the concrete implementation can be swapped or mocked without touching OrderService.
What is the Singleton pattern, and when is it actually appropriate to use?
Singleton ensures a class has exactly one instance for the entire application and provides a single global access point to it, typically by making the constructor private and exposing a static getInstance() method (or, in modern Java, using an enum with one value, which is inherently serialization-safe and thread-safe against reflection-based attacks). It's appropriate for genuinely singular, stateless or carefully-synchronized shared resources: a connection pool, a configuration loader, or a logging facade, where having two independent instances would be wasteful or actively incorrect. The pattern is heavily overused in practice and is often criticized for making unit testing harder (global mutable state is difficult to isolate between tests) and for hiding a class's dependencies (any code can silently reach out to the singleton instead of declaring it as a constructor dependency) — in a Spring Boot application specifically, most "singleton-like" needs are better served by declaring a regular @Service or @Component bean, since Spring's container already manages it as a singleton scope by default without any of the hand-rolled boilerplate or testability downsides.
What is the Factory pattern, and when would you reach for it over calling a constructor directly?
The Factory pattern centralizes object creation behind a method or class, so calling code asks for "an object that satisfies this need" instead of directly invoking new SomeConcreteClass() and hard-coding which concrete type it depends on. A simple factory method takes some input (often a type discriminator) and returns the appropriate implementation of a shared interface — for example, a PaymentGatewayFactory.create(paymentMethod) that returns a CreditCardGateway, UpiGateway, or WalletGateway instance depending on the requested payment method, without the caller ever needing to know those concrete class names. It's the right tool whenever object construction involves branching logic, requires assembling several dependencies, or you want the freedom to add new implementations later without touching every call site that creates one — pushed further, "Abstract Factory" generalizes this to a factory that creates whole families of related objects (e.g., a region-specific factory in ShopSphere that produces the correct tax calculator, shipping calculator, and payment gateway together for a given country). The trade-off versus a plain constructor call is an extra layer of indirection, which is worth it exactly when the creation logic is nontrivial or expected to grow.
What is the Builder pattern, and what problem does it solve that a constructor doesn't?
Builder solves the problem of constructing an object that has many optional fields or a long parameter list, where a plain constructor either forces callers to pass every parameter (many as null or default placeholders) or requires an explosion of overloaded constructors (the "telescoping constructor" anti-pattern). Instead, a builder exposes chained setter-style methods that each return the builder itself, ending with a build() call that assembles the final immutable object — for example, Order.builder().customerId(id).items(cartItems).shippingAddress(addr).couponCode(code).build() reads clearly at the call site and makes it obvious which fields are being set, regardless of order. This is especially valuable for immutable objects, since the object under construction can be validated once, fully, inside build(), and then never mutated afterward — Java records and libraries like Lombok's @Builder annotation generate this boilerplate automatically. Builder is the right choice specifically when an object has more than roughly three or four fields, several of which are optional, and you want construction to remain readable and self-documenting rather than a long positional argument list that's easy to get wrong.
What is the Strategy pattern, and how does it differ from a big if-else chain?
Strategy defines a family of interchangeable algorithms behind a common interface, and lets the calling code select and swap which concrete implementation to use at runtime — for example, a DiscountStrategy interface with implementations PercentageDiscount, FlatAmountDiscount, and BuyOneGetOneDiscount, all invoked polymorphically through strategy.apply(cart) from ShopSphere's checkout flow. Functionally, a big if-else or switch chain can express the same logic, but it violates the Open/Closed Principle: adding a new discount type means editing the existing conditional block (risking breaking existing cases) rather than adding a new, isolated class. Strategy also makes each algorithm independently unit-testable in isolation, and allows the active strategy to be chosen dynamically — even injected via configuration or determined by an A/B test — rather than being hard-coded into a branch. The trade-off is more classes and more indirection for what might otherwise be a few lines of conditional logic, so it's worth it once you have three or more genuinely distinct algorithms, or expect the set of algorithms to keep growing.
What is the Observer pattern, and where does it show up in real backend systems?
Observer defines a one-to-many dependency where a subject maintains a list of observers and notifies all of them automatically whenever its state changes, without needing to know any concrete details about who's listening. Classic in-process examples include Java's own event-listener style APIs and Spring's ApplicationEventPublisher, where publishing an OrderPlacedEvent triggers every registered @EventListener — such as one that reserves inventory and another that sends a confirmation email — without OrderService needing a direct reference to either. At a distributed-systems scale, the same pattern generalizes into publish-subscribe messaging systems like Kafka: order-service publishes an OrderPlaced event to a topic, and inventory-service, payment-service, and notification-service each independently subscribe and react, with the publisher completely decoupled from how many subscribers exist or what they each do. The core benefit either way is decoupling the "thing that happened" from "everything that needs to react to it," so new reactions (a new subscriber) can be added without modifying the code that triggers the event.
What is the Decorator pattern, and how is it different from just subclassing?
Decorator lets you attach additional behavior to an individual object dynamically, at runtime, by wrapping it in one or more decorator objects that implement the same interface as the object they wrap and delegate to it while adding their own logic before or after — Java's InputStream/OutputStream hierarchy (new BufferedInputStream(new FileInputStream(file))) is the textbook example, where buffering is layered onto a plain file stream without either class needing to know about the other. Subclassing, by contrast, fixes the added behavior at compile time and applies it to every instance of that subclass — you'd need a new subclass for every combination of behaviors you want (a BufferedGzipFileInputStream, a GzipFileInputStream, and so on), which explodes combinatorially. Decorator avoids that explosion because behaviors are composed by wrapping at runtime instead of baked into the class hierarchy — for example, wrapping a base NotificationSender with a RetryingNotificationSender and then a LoggingNotificationSender lets ShopSphere's notification-service mix and match retry and logging behavior per channel without a separate subclass for every combination. The cost is that a deeply nested stack of decorators can be harder to debug than a single concrete class, since the actual behavior is spread across several wrapping layers.
How should you approach an LLD machine-coding round methodically?
Start by clarifying requirements out loud before writing any code — an LLD prompt like "design a parking lot" or "design a rate limiter" is deliberately underspecified, and asking questions (What entities does this need to support? What are the read/write patterns? Is this single-threaded or does it need to be thread-safe? What's explicitly out of scope?) both produces a better design and signals to the interviewer that you don't just start typing on ambiguous requirements. Next, identify the core entities (nouns) in the problem — for a parking lot: Vehicle, ParkingSpot, ParkingFloor, Ticket — and separately identify the core actions (verbs) they need to support, like "park a vehicle" or "calculate fee on exit," since verbs often hint at which class should own a given method. Then define the relationships between entities — composition versus inheritance (is a CompactSpot a type of ParkingSpot, or does a ParkingFloor simply contain a list of them?), and which entities need to reference which others directly versus being looked up through a manager/service class. Only after that should you design the actual classes and interfaces, applying SOLID principles and reaching for a design pattern where it genuinely fits the problem (Strategy for "different fee calculation rules," Observer for "notify all subscribers when a spot frees up") rather than forcing a pattern in for its own sake. Throughout, narrate your trade-offs out loud — interviewers are scoring your reasoning process at least as much as the final class diagram.
Why do senior engineers often say "prefer composition over inheritance," and when is deep class inheritance actually a design smell in production code?
Composition means a class holds a reference to another object and delegates to it (a NotificationService that holds a RetryPolicy field), while inheritance means a class extends another and inherits its implementation directly. The problem with deep inheritance hierarchies in a long-lived production codebase is fragility: a change to a base class's behavior silently ripples into every subclass, sometimes breaking assumptions those subclasses made (the "fragile base class" problem), and hierarchies that looked clean at three levels (Shipment → DomesticShipment → ExpressDomesticShipment) become nearly impossible to reason about at five or six, especially once two independent dimensions of variation emerge (shipping speed and destination region) and you'd need a subclass for every combination. Composition avoids this because behaviors are assembled from independent, individually-testable pieces at runtime (a Shipment that composes a SpeedPolicy and a RegionPolicy rather than inheriting from a class that hard-codes both), which is exactly what patterns like Strategy and Decorator are doing structurally — favoring composition. This isn't an absolute rule (a shallow, genuinely "is-a" hierarchy with one level of specialization is fine and often clearer than an over-engineered composition), but a senior-level answer recognizes that inheritance should model a true, stable "is-a" relationship that isn't expected to grow new dimensions of variation, and reaches for composition the moment more than one independent axis of behavior needs to vary.

Common HLD Case-Study Quick Answers

Before designing any of these case studies, what basic requirements-gathering questions should you ask first?
Every HLD case study — a URL shortener, a rate limiter, a notification system, a flash sale — should start the same way: clarify functional requirements (what exactly does the system need to do — can short URLs expire? does the rate limiter need per-user and per-IP limits, or just one?), then clarify scale (how many requests per second at peak, how many total users, how much data needs to be stored and for how long), then clarify non-functional priorities (is strong consistency required, or is eventual consistency acceptable — does a duplicate notification matter more or less than a delayed one?), and finally identify what's explicitly out of scope so you don't spend interview time solving a problem that wasn't asked for. Skipping this step is one of the most common reasons candidates fail case-study rounds — jumping straight to "I'll use Kafka and Redis" without establishing why those tools fit this specific scale and these specific consistency needs reads as pattern-matching rather than reasoning, and interviewers will often deliberately leave scale unspecified just to see whether you ask. A good habit is to state your assumptions out loud even when the interviewer doesn't push back ("I'll assume roughly 100,000 short URLs created per day and a 100:1 read-to-write ratio, since URL shorteners are read-heavy") so the rest of your design has a stated, defensible foundation.
What are the core design decisions in a URL shortener — short-code generation and redirect handling?
Short-code generation has two mainstream approaches. Base62 encoding an auto-incrementing counter (using digits, lowercase, and uppercase letters, giving 62 possible characters per position) guarantees uniqueness by construction and produces a short code deterministically from a monotonically increasing ID, but requires a centralized (or carefully partitioned) counter to avoid collisions across multiple servers generating codes concurrently. Hashing the original URL (e.g. taking the first 6-7 characters of an MD5 or SHA hash) avoids needing a centralized counter, but introduces the possibility of collisions that must be detected and handled, typically by appending a salt and re-hashing until a free code is found. Redirect handling is a straightforward read path — look up the short code in a key-value store (a relational database with the short code indexed, or, more commonly at scale, a fast key-value store like Redis in front of it) and issue an HTTP redirect. The subtlety interviewers probe for is 301 (permanent) versus 302 (temporary) redirect: a 301 lets browsers cache the redirect and skip hitting the URL shortener service on repeat visits, which reduces load but means you can never change where that short code points and lose the ability to track click-through analytics on cached hits, while a 302 always round-trips through the service, costing more load but preserving both the ability to update the destination and accurate click analytics — most production shorteners choose 302 specifically to keep click tracking accurate.
What are the core design decisions in a rate limiter service?
The first decision is which algorithm to use (token bucket for bursty-but-bounded traffic, sliding window for precise boundary-safe limits — covered above), and the second is where state lives: an in-process rate limiter (counters held in each server's local memory) is trivially fast but gives each server its own independent limit, so a client hitting N servers behind a load balancer effectively gets N times the intended limit; a centralized rate limiter backed by a shared store like Redis gives one true global count per client, at the cost of a network round-trip per request and that store becoming a critical dependency and potential bottleneck. The common production answer is Redis specifically because it supports atomic increment-and-expire operations (via a small Lua script executed atomically, or built-in commands), so concurrent requests from the same client across multiple servers can't race past each other with a stale count. A further design decision is the rate-limiting key granularity — per API key, per user ID, per IP address, or a combination — and what happens on limit breach: reject immediately with an HTTP 429 (Too Many Requests) status and a Retry-After header, or queue the request briefly. Finally, rate limiting is usually implemented at the API gateway or a dedicated middleware layer in front of the actual services, like ShopSphere's public order-service API, so individual backend services don't each need to reimplement the same logic.
What are the core design decisions in a notification/messaging system — fan-out, retries, and delivery guarantees?
Fan-out is the decision of how one triggering event reaches multiple recipients or channels: fan-out-on-write pre-computes and pushes the notification to every recipient's queue or inbox immediately when the triggering event happens (fast reads later, but expensive and slow if the recipient count is huge, like a broadcast to every ShopSphere customer), while fan-out-on-read stores the event once and computes "what does this user need to see" at read time (cheap to write, more expensive per read) — most systems use write-side fan-out for normal cases (an OrderShipped event notifying one customer) and read-side or hybrid approaches for very large broadcast audiences. Retries need an explicit backoff policy — typically exponential backoff with jitter (increasing delay between attempts, with randomization added so many failed retries don't all retry at exactly the same instant and overwhelm the recipient service again) — plus a maximum retry count after which the message goes to a dead-letter queue for manual inspection rather than retrying forever. Delivery guarantees come in three flavors: at-most-once (send and forget, message can be lost, never duplicated), at-least-once (retry until acknowledged, message can be delivered more than once but never lost), and exactly-once (delivered precisely once — genuinely difficult to achieve end-to-end across a network and usually approximated via at-least-once delivery plus idempotency on the receiving side). Most real notification systems, including a Kafka-based flow from ShopSphere's order-service to notification-service, target at-least-once delivery and push the responsibility of handling duplicates onto the consumer via an idempotency key (e.g. deduplicating on orderId plus notification type before actually sending), since guaranteeing true exactly-once delivery across process and network boundaries is far more complex than deduplicating on the receiving end.
What are the core design decisions in an e-commerce flash-sale system — preventing oversell and handling checkout load?
Preventing oversell means ensuring the total number of units sold never exceeds available inventory even when thousands of concurrent requests are competing for the same limited stock. The standard approach is atomic conditional decrement at the data layer — a single SQL statement like UPDATE inventory SET quantity = quantity - 1 WHERE product_id = ? AND quantity > 0, checked via the number of rows affected, so the check-and-decrement happens as one atomic database operation instead of a separate read-then-write that two concurrent requests could both pass — or, at higher throughput, moving the hot counter into Redis and using an atomic decrement command (or a Lua script) so the database isn't hammered by every single request during the sale's peak second. Handling checkout load means absorbing a massive, short-lived traffic spike without the whole system falling over: a virtual "waiting room" or queue in front of checkout admits customers at a controlled rate rather than letting every customer hit the order-service simultaneously, and the actual order-creation step is often decoupled from the request path entirely — the request is accepted quickly and pushed onto a Kafka queue, with a pool of workers processing orders from that queue at a sustainable rate, so a burst of 100,000 simultaneous requests becomes a queue depth rather than 100,000 simultaneous database transactions. Combining both: the inventory check/reservation happens synchronously and fast (often in Redis) to give the customer an immediate yes/no, while the heavier order-creation, payment initiation, and notification steps happen asynchronously afterward — this is also why flash-sale systems commonly pre-scale (or use pre-warmed auto-scaling) ahead of a known sale start time rather than relying on reactive auto-scaling, since reactive scaling is too slow to respond to a spike that arrives in the first few seconds of the sale going live.
Say a case-study design you shipped five years ago (e.g. the URL shortener or notification system above) is now hitting scale limits in production — how do you approach evolving it without a risky big-bang rewrite?
The senior-level instinct is to identify the single actual bottleneck through metrics before touching anything — is it the datastore's write throughput, a hot shard, the cache hit rate degrading, or a downstream dependency that's slower than it used to be — because "it's slow, let's redesign it" without that diagnosis risks solving the wrong problem while the real one keeps degrading. From there, the standard approach is incremental migration behind existing interfaces rather than a rewrite: for example, if a URL shortener's single-node key-value store has outgrown its capacity, you introduce sharding by consistent hashing behind the existing lookup interface, migrate data shard by shard with dual-write or a background backfill, and cut over reads gradually (often via a feature flag or percentage-based rollout) so a bug in the new path affects 1% of traffic, not 100%. The same discipline applies to a notification system whose fan-out has outgrown write-side fan-out for a broadcast case — you'd introduce a hybrid model (write-side for normal per-user notifications, read-side computed feeds for mass broadcasts) as an additive change, not a wholesale replacement of the existing pipeline. Throughout, you'd keep the old path running and comparable (shadow traffic, metrics parity dashboards) until the new path has proven itself under real production load, because the actual risk in evolving a live system serving real customers is a regression during migration, not the elegance of the end-state architecture — a senior candidate is expected to talk about de-risking the migration path at least as much as the target design itself.
