Spring Core Mechanics: IoC, DI, AOP, Auto-Config

Inversion of Control Dependency Injection Bean Lifecycle Bean Scopes AOP Proxies Auto-Configuration
Why this matters

Almost every confusing Spring bug traces back to one of four mechanics: the order of bean lifecycle callbacks, the fact that AOP is proxy-based and therefore blind to self-invocation, the mismatch between a prototype bean's intended lifetime and the singleton it gets injected into, or a starter's conditional bean silently not activating. None of these are "framework magic" — they are consequences of specific, traceable design decisions. Once you can mentally simulate what the container does at startup and at call time, behaviors that look like bugs (a @Transactional method that doesn't roll back, a prototype bean that never changes) become predictable, and you stop treating Spring as a black box you fight against.

1. Inversion of Control as a Principle, Before Spring

Strip away the framework and ask a plain question: in a normal Java program, who is responsible for creating an object's dependencies? Normally, the object itself is. If an OrderService (ShopSphere's checkout orchestrator — it turns a Cart into an Order and drives it through CREATED → PAID → SHIPPED → DELIVERED) needs a PaymentClient to charge a Customer's card, the naive approach is:

public class OrderService {
    private final PaymentClient paymentClient = new StripePaymentClient();
}

OrderService now controls two things it shouldn't have to: which concrete implementation to use, and when to construct it. This is tight coupling — if you want to swap in a PaypalPaymentClient for a test, or wire in retry logic around flaky payment-provider calls, you must edit OrderService itself. As a codebase grows, every class ends up transitively wired to concrete classes several layers down, and a change to a constructor signature ripples outward through every caller.

Inversion of Control (IoC) is the general principle of taking that responsibility away from the object and handing it to something external — a container, a factory, a framework runtime. The object stops asking "who do I need to construct?" and instead declares "here is what I need" (usually via constructor parameters or an interface type), and something else decides what concrete instance to hand it and when. This is sometimes summarized as "don't call us, we'll call you" — the classic Hollywood Principle. The object's own code no longer drives the flow of construction; control has been inverted from the object to the container.

Dependency Injection (DI) is the specific technique Spring uses to implement IoC: instead of an object looking up or constructing its dependencies, the dependencies are handed ("injected") to it from outside — through a constructor, a setter, or a field. IoC is the principle; DI is one mechanism for achieving it (Service Locator is another, less desirable one, because the object still actively asks a registry for things, which keeps a dependency on the locator itself).

Why hand control to a container at all?

Once construction is externalized, you get three things almost for free: (1) you can swap implementations by changing configuration, not code — this is what makes profile-specific beans and test doubles trivial; (2) the container can manage cross-cutting concerns (proxying, scoping, lifecycle) uniformly, because it is the single place that owns object creation; (3) dependency graphs become declarative and inspectable — the container can validate the whole graph at startup rather than failing deep into a request at 2am because some manually-wired singleton was never assigned.

2. The IoC Container: BeanFactory vs ApplicationContext

Spring's IoC container is the runtime object graph that reads bean definitions (from annotations, XML, or Java @Configuration classes), decides how to instantiate them (e.g. OrderService, ProductRepository, the checkout-logging @Aspect introduced in section 7), resolves their dependencies, and manages their lifecycle from creation to destruction.

There are two layers to this, and the container's actual class hierarchy makes the "superset" relationship literal rather than metaphorical — ApplicationContext is a Java interface that extends BeanFactory (via several intermediate interfaces, each contributing one capability):

BeanFactory                                    (root container contract)
  ├── getBean(name) / getBean(Class)           lazy: bean created on first request
  │
  └── ListableBeanFactory                      + enumerate all bean definitions
        └── AutowireCapableBeanFactory         + autowire an externally-created object
              └── ApplicationContext           (the interface almost everything uses)
                    ├── EnvironmentCapable      + profiles, property sources (application.yml)
                    ├── ApplicationEventPublisher  + publish/listen for events (@EventListener)
                    ├── ResourceLoader          + classpath:/file: resource resolution
                    ├── MessageSource           + i18n message resolution
                    │
                    └── ConfigurableApplicationContext   + refresh()/close(), lifecycle control
                          └── AnnotationConfigServletWebServerApplicationContext
                                (the concrete class a Spring Boot web app actually runs —
                                 wires @Configuration classes, component scan, and an
                                 embedded Tomcat/Netty server together)
  • BeanFactory — the root interface, the minimal container contract. It supports lazy initialization by default: a bean is only instantiated the first time it's requested via getBean(). It's small and lightweight, but it does not support things like automatic BeanPostProcessor registration, internationalization, or event publishing out of the box.
  • ApplicationContext — a superset of BeanFactory that adds AOP integration, event publication (ApplicationEventPublisher — e.g. publishing an in-process OrderPlacedEvent that a notification-service listener bean reacts to), environment abstraction (profiles, property sources), internationalization, and — critically — eager initialization of all singleton beans at startup, not on first use.

In practice, every Spring Boot application uses an ApplicationContext implementation (typically AnnotationConfigServletWebServerApplicationContext for a web app — that's the leaf in the diagram above, the one class that actually gets instantiated when SpringApplication.run(...) is called). The eager-initialization behavior is a deliberate trade-off: it means misconfiguration (a missing bean, a circular dependency, a bad @Value placeholder — e.g. a missing payment.provider.api-key property that PaymentClient's constructor needs) fails fast at application startup rather than lazily at 3am when a rarely-used code path first calls getBean() in production. You can opt individual beans out of this with @Lazy, which reverts that one bean to on-first-use semantics — useful for expensive beans that aren't always needed, but it reintroduces the risk of a wiring failure surfacing at request time instead of startup time.

Fail fast is a feature, not a cost

A team that globally applies @Lazy to speed up startup is trading a loud, obvious, five-second failure at boot for a silent, delayed failure under production traffic. Understanding why ApplicationContext defaults to eager singleton instantiation explains why this is usually a bad trade outside of narrow cases (e.g., breaking a circular dependency, or genuinely optional integrations).

3. Dependency Injection Mechanics: Constructor, Setter, Field

Spring supports three injection styles, and they are not equivalent in the guarantees they give you.

StyleMechanismGuaranteesProblems
Constructor injectionDependencies passed as constructor parametersFields can be final; object is never in a partially-constructed state; missing dependency fails at object-creation time with a clear exceptionLong constructors are a signal (correctly) that a class has too many responsibilities
Setter injectionDependencies set via public setter methods after constructionAllows optional dependencies; supports reconfiguration after constructionObject exists in a valid-looking but incompletely-wired state between construction and the setter calls; fields can't be final
Field injection@Autowired directly on a field, set via reflectionLeast boilerplateFields can't be final; dependencies are invisible from outside without reflection (can't construct the object manually, e.g. in a plain unit test, without the container); hides circular dependencies (see below)

Constructor injection is preferred, and the reasons compose:

  • Immutability. Constructor-injected fields can be declared final, so once the object exists, its dependencies cannot change — this eliminates a whole class of concurrency bugs where one thread reassigns a field another thread is reading.
  • Guaranteed non-null dependencies. If the constructor requires a PaymentClient, you cannot construct an OrderService without one. With field injection, new OrderService() compiles fine and hands you an object with a null field that only blows up (with a confusing NullPointerException, not a wiring error) the first time it's used.
  • Easier testing. Constructor injection lets you instantiate the class directly in a plain unit test with mocks, no Spring context or reflection tricks required: new OrderService(mockPaymentClient). Field-injected classes require either a running ApplicationContext or reflection-based mocking frameworks to set private fields.
  • Circular dependencies surface immediately instead of being silently "resolved." This is the subtlest and most important reason.

3.1 Why field injection hides circular dependencies

Suppose OrderService depends on InventoryClient (to reserve stock during checkout) and, in a poorly-factored design, InventoryClient also depends back on OrderService (say, to look up order context for a reservation log). With constructor injection, Spring must fully construct OrderService (calling its constructor with a ready InventoryClient) before it can hand a reference back — but building InventoryClient requires a ready OrderService first. There is no valid order to do this in, so Spring throws BeanCurrentlyInCreationException at startup. This is exactly what you want: a circular dependency is almost always a design smell (two components with a mutual hard dependency should usually be merged, or one direction should be an event/callback instead — e.g. InventoryClient publishing an InventoryReserved event that OrderService listens for, rather than calling back directly), and constructor injection forces you to see it and fix it immediately.

Field injection can "resolve" the exact same cycle without complaint. Spring instantiates OrderService using its default/no-arg-like construction (fields aren't populated yet), registers the half-built instance in an internal early-reference cache, then while populating OrderService's fields it goes to build InventoryClient, which needs OrderService — and gets handed that same half-built instance from the cache. Both objects end up fully wired only after the fact. This works only because field/setter injection allows a bean to exist, be handed out, and be populated after the fact — a constructor-only cycle has no such window. So field injection doesn't fix circular dependencies; it just hides the smell that should have made you redesign the two classes.

4. The Bean Lifecycle, Step by Step

This is the sequence the container runs for every singleton bean during ApplicationContext startup (and, for prototype beans, every time one is requested). Knowing this order precisely is what lets you predict exactly when a proxy gets applied, when a field is guaranteed to be non-null, and what state is safe to assume inside any callback.

  1. Instantiation. The container calls a constructor (or a factory method) to create the raw object. Constructor-injected dependencies must already be fully resolved at this point.
  2. Populating properties. Setter- and field-injected dependencies are set via reflection/setters. (Constructor dependencies were already set in step 1.)
  3. Aware interfaces. If the bean implements marker interfaces like BeanNameAware, BeanFactoryAware, or ApplicationContextAware, the container calls their setter methods now (e.g., setBeanName(String name)), giving the bean access to container internals it wouldn't normally have.
  4. BeanPostProcessor.postProcessBeforeInitialization. Every registered BeanPostProcessor in the context gets a chance to inspect or wrap the bean before init callbacks run. This is where annotation-processing infrastructure (e.g., handling @Value, @Autowired on non-constructor members not already handled, or custom processors) typically runs.
  5. @PostConstruct / InitializingBean.afterPropertiesSet(). The bean's own initialization logic runs — @PostConstruct-annotated methods first (JSR-250, processed by CommonAnnotationBeanPostProcessor), then afterPropertiesSet() if the bean implements InitializingBean, then a custom init-method if one was declared. At this point all dependencies are guaranteed populated, so this is the correct place to do validation or eager warm-up work that depends on injected collaborators.
  6. BeanPostProcessor.postProcessAfterInitialization. Every BeanPostProcessor runs again, this time after init callbacks. This is where AOP proxies get created. AnnotationAwareAspectJAutoProxyCreator (itself a BeanPostProcessor) inspects the fully-initialized bean, checks whether any aspect's pointcut matches it (including annotation-driven advice like @Transactional/@Cacheable, which are implemented as aspects under the hood), and if so, returns a proxy object instead of the original. Everything downstream — every other bean that gets this bean injected — receives the proxy, not the raw instance.
  7. The bean is ready for use. It sits in the singleton cache and is handed out for the remainder of the application's life.
  8. @PreDestroy / DisposableBean.destroy(). On graceful container shutdown (JVM shutdown hook, or explicit context.close()), destruction callbacks run in roughly the reverse order of creation: @PreDestroy methods, then destroy() if the bean implements DisposableBean, then a custom destroy-method. This is where you release resources — connection pools, thread pools, file handles.
Instantiate constructor
  -> populate setter/field deps
  -> Aware callbacks (BeanNameAware, ApplicationContextAware, ...)
  -> BeanPostProcessor#postProcessBeforeInitialization  (for every registered BPP)
  -> @PostConstruct -> InitializingBean#afterPropertiesSet -> custom init-method
  -> BeanPostProcessor#postProcessAfterInitialization   (AOP proxy wrapping happens here)
  -> bean is live, handed out from context
  ... application runs ...
  -> @PreDestroy -> DisposableBean#destroy -> custom destroy-method (on shutdown)
The self-reference in @PostConstruct is the raw object, not the proxy

Because proxying happens in postProcessAfterInitialization, which runs after @PostConstruct, any call made from inside @PostConstruct through this to another method on the same bean bypasses whatever AOP advice would otherwise apply — the proxy doesn't exist yet at that point in the lifecycle. If a method needs its own @Transactional or @Cacheable behavior, it must never be invoked via this from inside initialization logic; it needs to go through the proxy (see the self-invocation section below), which by definition isn't available yet during @PostConstruct.

5. Bean Scopes and the Prototype-Into-Singleton Trap

ScopeLifetimeTypical use
singleton (default)One instance per container, created once, reused for the app's lifetimeStateless services, repositories, most beans
prototypeNew instance every time the bean is requested from the containerStateful, non-thread-safe objects — e.g., a builder or a per-use context object
requestOne instance per HTTP request (web-aware contexts only)Per-request state such as a request-scoped audit trail
sessionOne instance per HTTP sessionPer-user shopping cart, session-scoped preferences

The trap: a singleton bean is constructed exactly once, and dependency injection into it also happens exactly once. If that singleton has a prototype-scoped field injected the normal way, Spring resolves the dependency at the singleton's own construction time — it asks the container for "a" prototype instance once, injects that one object, and then the singleton holds onto that same instance forever. Every subsequent "new" prototype you thought you were getting is actually the same object from the first resolution. This defeats the entire purpose of declaring the bean prototype in the first place, and it's a purely structural bug: nothing throws an exception, nothing looks wrong in logs, and the code compiles and appears to work — until you notice state bleeding between logically separate uses is really the same object being mutated repeatedly.

@Component
@Scope("prototype")
class InvoiceBuilder { /* mutable, per-invoice state: line items, running total, discounts applied */ }

@Service
class OrderInvoiceService {
    private final InvoiceBuilder builder; // WRONG: resolved once, reused forever

    OrderInvoiceService(InvoiceBuilder builder) { this.builder = builder; }

    Invoice buildFor(Order order) {
        return builder.reset().addLineItems(order.getItems()).build(); // same instance every call
    }
}

There are two correct fixes, and they solve the problem by deferring resolution to call time instead of construction time:

  • Scoped proxy — annotate the prototype bean's definition with @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS). Spring then injects a proxy into the singleton; every method call on that proxy transparently fetches a fresh prototype instance from the container and delegates to it. The singleton holds a stable proxy reference, but every invocation is backed by a new underlying object.
  • ObjectProvider<T> (or the older ObjectFactory<T>/Provider<T>) — inject ObjectProvider<InvoiceBuilder> into the singleton instead of InvoiceBuilder directly, and call .getObject() at the point of use. This makes the deferred lookup explicit in code rather than hidden behind a proxy.
@Service
class OrderInvoiceService {
    private final ObjectProvider<InvoiceBuilder> builderProvider;

    OrderInvoiceService(ObjectProvider<InvoiceBuilder> builderProvider) {
        this.builderProvider = builderProvider;
    }

    Invoice buildFor(Order order) {
        InvoiceBuilder builder = builderProvider.getObject(); // fresh instance every call
        return builder.reset().addLineItems(order.getItems()).build();
    }
}
Same root cause as request/session scope in non-web contexts

The identical mismatch shows up if you inject a request-scoped bean into a singleton without a scoped proxy — except there it fails loudly at startup or first use, because there is no active HTTP request thread-bound during singleton construction, and Spring throws BeanCreationException / Scope 'request' is not active. The prototype case is more dangerous precisely because it fails silently instead of throwing.

6. Component Scanning, Stereotypes, and Autowiring Resolution

@Component is the base stereotype annotation: it marks a class as a candidate for auto-detection when component scanning runs (triggered by @ComponentScan, which @SpringBootApplication includes by default, scanning the package of the main class and everything below it). @Service, @Repository, and @Controller/@RestController are all meta-annotated with @Component — meaning they are components, but with added semantic meaning and, in @Repository's case, actual behavior: it enables Spring's persistence-exception-translation, converting JDBC/JPA-specific exceptions into Spring's unified DataAccessException hierarchy via a BeanPostProcessor registered by PersistenceExceptionTranslationPostProcessor. A ShopSphere ProductRepository (a Spring Data JPA interface backing the product catalog table) picks up exactly this behavior for free just by being annotated @Repository or extending JpaRepository.

Once beans are registered, @Autowired resolves dependencies through a specific, deterministic order:

  1. By type. Spring looks for a bean matching the declared type (interface or class). If exactly one candidate exists, it's injected — done.
  2. By qualifier/name, when multiple candidates match by type. If more than one bean implements the same interface, Spring falls back to matching the field/parameter name (or an explicit @Qualifier("beanName")) against bean names. If a bean is marked @Primary, that one wins regardless of name matching, unless a qualifier explicitly names a different one.
  3. Failure. If multiple candidates exist and none is @Primary, none matches by name, and no qualifier disambiguates, the container throws NoUniqueBeanDefinitionException at startup — again, fail-fast rather than an arbitrary silent pick.

Concretely: if ShopSphere registers both a StripePaymentClient and a PaypalPaymentClient as beans implementing the same PaymentClient interface (because checkout supports both providers), a plain @Autowired PaymentClient paymentClient in OrderService has two candidates and no way to pick — that throws NoUniqueBeanDefinitionException at startup. Marking StripePaymentClient with @Primary makes it the default for any injection point that doesn't explicitly ask for a different one; a checkout path that specifically needs PayPal disambiguates with @Qualifier("paypalPaymentClient") on that particular injection point.

7. AOP: Proxies, Advice Types, and the Self-Invocation Trap

Aspect-Oriented Programming lets you attach behavior (logging, transactions, caching, security checks) to methods matched by a pattern (a pointcut), without editing those methods' code. Spring implements this entirely through runtime proxies — there is no bytecode weaving into your original class files at compile time (that's what full AspectJ does; Spring AOP is a lighter-weight proxy-based subset).

7.1 How the proxy gets chosen

  • JDK dynamic proxies are used when the target bean implements at least one interface. The proxy is a runtime-generated class implementing the same interface(s), and every call to an interface method is routed through an InvocationHandler that runs the applicable advice and then delegates to the real object.
  • CGLIB proxies (subclass-based) are used when the target class implements no interface. CGLIB generates a runtime subclass of the target class itself, overriding its public/protected methods to insert advice before delegating to super.method(). This is why a class marked final, or a method marked final/private, cannot be proxied by CGLIB — you cannot override a final method or subclass a final class, so advice silently never applies to those methods, with no error raised.

7.2 Why self-invocation breaks AOP

The proxy sits in front of the real bean, intercepting calls that arrive at the bean from outside. But once you're executing code inside the real bean's own method, and that method calls another method using this.otherMethod() (or just otherMethod()), that call goes directly to the real object's own method table — it never passes back out through the proxy. There is nothing to intercept, because the call never leaves the object.

@Service
public class OrderService {

    public void placeOrder(Order order) {
        // ... reserve inventory, validate cart ...
        this.chargeCustomer(order); // calls the REAL object directly, not the proxy
    }

    @Transactional
    public void chargeCustomer(Order order) {
        paymentRepository.save(new Payment(order.getId(), "STRIPE", PENDING));
    }
}

If placeOrder is called from outside (say, a checkout controller), that call does go through the proxy. But the proxy's job for placeOrder is just to run whatever advice applies to placeOrder (none, here) and delegate. Once execution is inside the real placeOrder method, the call to chargeCustomer is a plain Java call on this, so the @Transactional advice on chargeCustomer never runs — no transaction is opened, and if chargeCustomer throws partway through writing the Payment row and updating Order.status, nothing rolls back, silently — you can end up with a Payment persisted but the order left in an inconsistent state. The exact same mechanism explains a @Cacheable method called internally never hitting the cache: the cache-check advice lives on the proxy, and self-invocation never reaches it.

This is not a bug in Spring — it's an inherent limit of proxy-based AOP

Fixes all work by forcing the call to route back through the proxy: (1) inject the bean into itself (via @Lazy to avoid a construction-time cycle) and call the method on that injected proxy reference instead of this; (2) call AopContext.currentProxy() inside the method (requires exposeProxy = true on @EnableAspectJAutoProxy); or (3), the cleanest, split the two methods into different beans — e.g. move chargeCustomer into a separate PaymentService bean — so the call from one to the other is always an inter-bean call that necessarily passes through the second bean's proxy.

7.3 Advice types and pointcuts

AdviceRunsCan it affect the return value / suppress exceptions?
@BeforeBefore the target method executesCannot change return value; can throw to prevent the method from running at all
@After (finally)After the method completes, whether it returned normally or threwNo access to return value or exception details
@AfterReturningAfter successful normal returnCan inspect (not replace) the return value; skipped entirely if an exception was thrown
@AfterThrowingOnly if the method threwCan inspect the exception; cannot suppress it (the exception still propagates)
@AroundWraps the entire invocationFull control — must explicitly call ProceedingJoinPoint.proceed(), can change arguments, replace the return value, or swallow exceptions

A pointcut expression selects which join points (method executions) the advice applies to, e.g. execution(* com.shopsphere.order.*.*(..)) matches any method on any class directly in the com.shopsphere.order package. @Transactional and @Cacheable are themselves implemented as pre-packaged aspects with pointcuts matching "any method/class annotated with this annotation" — you rarely write raw pointcut expressions yourself in application code, but understanding that they're aspects under the hood is exactly what explains the self-invocation limitation above.

7.4 A worked example: logging every checkout attempt with @Around

A concrete, realistic use of custom AOP in ShopSphere: log every call to OrderService.placeOrder — who called it, how long it took, and whether it succeeded or failed — without putting logging code inside OrderService itself. This is the kind of cross-cutting concern AOP exists for: every checkout-related method should log the same way, and you don't want that logic copy-pasted into (or tangled with) the business logic of each one.

@Aspect
@Component
public class CheckoutAuditAspect {

    private static final Logger log = LoggerFactory.getLogger(CheckoutAuditAspect.class);

    // Pointcut: any method on OrderService whose name starts with "placeOrder"
    @Around("execution(* com.shopsphere.order.OrderService.placeOrder(..))")
    public Object logCheckoutAttempt(ProceedingJoinPoint joinPoint) throws Throwable {
        Object[] args = joinPoint.getArgs();       // the Order (or Cart/Customer) passed in
        long start = System.nanoTime();
        try {
            Object result = joinPoint.proceed();    // actually invokes the real placeOrder(...)
            long tookMs = (System.nanoTime() - start) / 1_000_000;
            log.info("checkout succeeded args={} tookMs={}", args, tookMs);
            return result;
        } catch (Throwable ex) {
            long tookMs = (System.nanoTime() - start) / 1_000_000;
            log.warn("checkout FAILED args={} tookMs={} error={}", args, tookMs, ex.toString());
            throw ex; // must rethrow - swallowing it here would hide a real checkout failure
        }
    }
}

Mechanically, this is exactly the proxy mechanism from 7.1 and 7.2 applied on purpose: @EnableAspectJAutoProxy (auto-enabled by Spring Boot when spring-boot-starter-aop is on the classpath) causes AnnotationAwareAspectJAutoProxyCreator to notice, during postProcessAfterInitialization for the OrderService bean, that this aspect's pointcut matches placeOrder, and wraps OrderService in a proxy accordingly. ProceedingJoinPoint is the handle the @Around advice uses to actually continue the call into the real method — forgetting to call joinPoint.proceed() at all means placeOrder simply never runs, silently, which is the most common bug when hand-writing @Around advice. Because this is the exact same proxy-based mechanism as @Transactional, the exact same self-invocation limitation from 7.2 applies: a call to placeOrder made via this from inside another method on OrderService would bypass this aspect too.

8. Spring Boot Auto-Configuration Mechanics

@SpringBootApplication is not one mechanism — it's a meta-annotation bundling three:

  • @Configuration — marks the class itself as a source of bean definitions.
  • @ComponentScan — triggers classpath scanning for @Component-family beans starting at the annotated class's package.
  • @EnableAutoConfiguration — the piece that makes Boot "boot": it tells Spring to look for auto-configuration classes and conditionally apply them.

8.1 How a starter injects configuration without the app mentioning it

Historically, Boot discovered auto-configuration classes by reading META-INF/spring.factories from every JAR on the classpath, looking for entries under the key org.springframework.boot.autoconfigure.EnableAutoConfiguration. Modern Boot versions (2.7+) use a simpler dedicated file, META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, listing one fully-qualified auto-configuration class per line. Either mechanism achieves the same goal: a third-party dependency (a "starter," e.g. spring-boot-starter-data-redis) ships a file that Boot's classpath scanning at startup reads automatically — the application module never imports or references that configuration class directly. Adding the dependency to the build file is the entire integration step from the application's point of view.

8.2 Why auto-configuration doesn't just always register everything

If every auto-configuration class unconditionally registered its beans, adding any starter to the classpath would forcibly override beans you'd already defined, and unrelated starters would conflict constantly. Auto-configuration classes are guarded by conditional annotations evaluated once, at context-refresh time, by the SpringBootCondition infrastructure:

AnnotationBean registers only if...
@ConditionalOnClassa specific class is present on the classpath — e.g., a Redis auto-configuration only activates if RedisTemplate's class is actually on the classpath, meaning the driver dependency was pulled in
@ConditionalOnMissingBeanthe application (or an earlier-processed configuration) hasn't already defined a bean of that type — this is what lets you override any auto-configured bean simply by declaring your own @Bean of the same type; yours wins because auto-configuration classes are processed last, after user configuration
@ConditionalOnPropertya specific property is set (and optionally matches a specific value) in the environment — e.g., spring.datasource.hikari.* auto-configuration only fully applies when a corresponding property namespace is present
@ConditionalOnMissingClassa class is absent — used to avoid clashing with an alternative implementation

Auto-configuration classes are also ordered relative to each other (via @AutoConfigureAfter/@AutoConfigureBefore) and are always evaluated after the application's own @Configuration classes, which is precisely why @ConditionalOnMissingBean is a reliable override mechanism: by the time Boot gets to deciding whether to register its default DataSource, it can already see whether you defined your own.

This is IoC applied to configuration itself

Auto-configuration is the same inversion-of-control idea from section 1, one level up: instead of your application code deciding "if Redis is on the classpath, construct a RedisTemplate with these settings," a starter declares the intent conditionally and the container decides, at startup, whether the condition holds. You get to skip writing that wiring entirely for the common case, and you retain full override power for the uncommon one.

9. The Spring MVC Request Lifecycle, End to End

Everything in sections 1–8 explains how the container builds and wires the object graph. This section is about what happens to a single HTTP request once that graph already exists — the path a request takes from the servlet container down to a ShopSphere controller method and back out again. It's worth walking end to end because the names involved (DispatcherServlet, HandlerMapping, HandlerAdapter) are usually memorized as trivia without understanding why each one has to exist as a separate object.

9.1 DispatcherServlet as the front controller

A raw servlet container (Tomcat, embedded in a Spring Boot app by default) has no idea what a @RestController or an @GetMapping is — those are Spring concepts, not servlet-spec concepts. The bridge is DispatcherServlet, a single HttpServlet that Spring Boot registers to handle (by default) every request path. This is the Front Controller pattern: instead of the servlet container mapping different URLs to different servlet classes directly, it maps everything to one servlet, and that one servlet becomes the single funnel through which every request to the application passes. All of the routing intelligence — which controller method handles GET /orders/{id} versus POST /orders — lives inside Spring's own machinery behind that one servlet, not in the servlet container's own URL-mapping table.

Centralizing on one servlet is what makes it possible for Spring to apply uniform, cross-cutting request handling — argument resolution, exception handling via @ExceptionHandler/@ControllerAdvice, view resolution — in exactly one place, rather than duplicating that machinery across many hand-registered servlets.

9.2 HandlerMapping: deciding which method handles the request

Once DispatcherServlet receives a request, its first job is to figure out which code should handle it. It delegates this to a HandlerMapping — for annotation-based controllers, concretely RequestMappingHandlerMapping, which was built at startup by scanning every @Controller/@RestController bean for @RequestMapping-family annotations (@GetMapping, @PostMapping, etc.) and indexing them by URL pattern, HTTP method, headers, and content type. Given an incoming request like GET /orders/482, HandlerMapping matches the path against that index and returns a HandlerExecutionChain — not just the target method, but that method bundled together with any HandlerInterceptors (see 9.4) that should wrap the call.

The "handler" at this point is represented as a HandlerMethod — effectively a reference to a specific method on a specific controller bean (e.g. OrderController.getOrder(Long id)), plus the resolved path variables. Nothing has been invoked yet; HandlerMapping's only job is figuring out what should run, not running it.

9.3 HandlerAdapter: actually invoking the handler

DispatcherServlet doesn't call the handler method directly, because "handler" is a deliberately generic concept — historically Spring supported handlers that weren't annotated methods at all (implementing Controller or HttpRequestHandler directly), and DispatcherServlet shouldn't need to know the invocation mechanics for every possible handler shape. Instead it delegates to a HandlerAdapter — for annotated controllers, RequestMappingHandlerAdapter — whose job is specifically knowing how to invoke a HandlerMethod: resolving its arguments, calling it, and packaging its return value into something DispatcherServlet can act on. This is the Adapter pattern applied to request dispatch: DispatcherServlet talks to one stable interface (HandlerAdapter), and different handler types (annotated methods, legacy Controller implementations, WebFlux functional endpoints) each get their own adapter implementation behind it.

9.4 Argument resolution and HttpMessageConverters

Before the controller method can actually be called, its parameters need real values — a @PathVariable Long id, a @RequestBody CreateOrderRequest body, an @RequestParam String status. RequestMappingHandlerAdapter delegates each parameter to a chain of HandlerMethodArgumentResolvers, each of which knows how to satisfy one category of parameter (path variables, query parameters, request headers, the request/response objects themselves, or an @RequestBody-annotated object).

For an @RequestBody parameter specifically, the argument resolver (RequestResponseBodyMethodProcessor) doesn't do the byte-to-object conversion itself — it delegates to an HttpMessageConverter, chosen by matching the request's Content-Type header against each converter's supported media types (e.g. MappingJackson2HttpMessageConverter for application/json, backed by Jackson). The converter reads the raw request body bytes and deserializes them into the Java type the controller method declared — turning a raw JSON payload for a ShopSphere checkout into a fully-formed CreateOrderRequest object before OrderController.placeOrder(...) is even invoked. The same mechanism runs in reverse on the way out: whatever the controller method returns gets handed to a matching HttpMessageConverter, which serializes it back to bytes (JSON, by default, for a typical ShopSphere REST endpoint) and sets the response Content-Type accordingly.

@RestController
@RequestMapping("/orders")
public class OrderController {

    // HandlerMapping matches "GET /orders/482" to this method.
    // Argument resolvers turn "482" into a Long for `id`.
    // The returned Order is handed to an HttpMessageConverter,
    // which serializes it to JSON because of @RestController (see 9.5).
    @GetMapping("/{id}")
    public Order getOrder(@PathVariable Long id) {
        return orderService.findById(id);
    }

    // @RequestBody triggers an HttpMessageConverter on the way IN:
    // raw JSON bytes -> CreateOrderRequest, before this method runs.
    @PostMapping
    public Order placeOrder(@RequestBody CreateOrderRequest request) {
        return orderService.placeOrder(request);
    }
}

9.5 View resolution versus @ResponseBody

Once the handler method returns, DispatcherServlet has to decide what to actually send back. In classic Spring MVC (server-rendered HTML), a controller method returns a logical view name (a String, or a ModelAndView bundling a view name with model attributes), and a ViewResolver (e.g. InternalResourceViewResolver mapping a name like "orderConfirmation" to /WEB-INF/views/orderConfirmation.jsp) maps that logical name to an actual renderable View, which is then rendered with the model data to produce the HTML response body.

@ResponseBody — implied on every method of a class annotated @RestController, since @RestController is itself @Controller + @ResponseBody — skips view resolution entirely. It tells RequestMappingHandlerAdapter that the method's return value is the response body, not a view name, so it should be handed straight to an HttpMessageConverter (as in 9.4) instead of a ViewResolver. This is why virtually every ShopSphere REST controller is annotated @RestController rather than plain @Controller: a JSON API has no views to resolve, and the whole view-resolution machinery would simply never be exercised.

9.6 Servlet Filters versus Spring HandlerInterceptors

Both of these let you run code "around" a request, and it's a common point of confusion because they look similar from the outside — both can inspect a request before it's handled and both can act after a response is produced. But they operate at fundamentally different layers, and the distinction is a genuinely useful piece of architectural knowledge, not just interview trivia.

A Servlet Filter is a servlet-spec construct, registered with the servlet container itself, that sits entirely outside Spring's DispatcherServlet and has no knowledge that Spring, controllers, or handler methods even exist. Filters are chained: each one receives the request, the response, and a FilterChain, and is responsible for explicitly calling chain.doFilter(request, response) to pass control to the next filter (or, at the end of the chain, to DispatcherServlet itself). Because a filter runs before DispatcherServlet is even reached, it cannot know which controller method will eventually handle the request, and it has no access to Spring MVC concepts like the resolved HandlerMethod or a ModelAndView — by the time those exist, execution is already deep inside Spring's own dispatch logic, past the filter chain. Filters are the right tool for concerns that are legitimately request/response-level and framework-agnostic: authentication token validation, CORS headers, request/response logging at the wire level, compression, or wrapping the request/response streams (e.g. to make a request body re-readable).

public class RequestLoggingFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        long start = System.nanoTime();
        chain.doFilter(req, res); // MUST call this, or the request dead-ends here
        long tookMs = (System.nanoTime() - start) / 1_000_000;
        // no idea which controller method just ran - only the raw request/response
        log.info("{} {} took {}ms", ((HttpServletRequest) req).getMethod(),
                ((HttpServletRequest) req).getRequestURI(), tookMs);
    }
}

A Spring HandlerInterceptor, by contrast, lives entirely inside Spring MVC — it's registered with a HandlerMapping (via a WebMvcConfigurer's addInterceptors) and only ever runs for requests that reach DispatcherServlet and get matched to a handler. Unlike a filter's single doFilter method, an interceptor exposes three distinct lifecycle hooks tied directly to the MVC dispatch process:

  • preHandle(request, response, handler) — runs before the handler method is invoked, and critically, it receives the resolved handler object (the actual HandlerMethod/controller method that's about to run) as a parameter — something a filter can never see. Returning false here short-circuits the request; neither the handler nor any later interceptor runs.
  • postHandle(request, response, handler, modelAndView) — runs after the handler method returns but before the view is rendered, and it receives the ModelAndView the handler produced, so it can inspect or modify model attributes or even swap the view name before rendering happens. This hook is skipped entirely if the handler threw an exception.
  • afterCompletion(request, response, handler, ex) — runs after the view has been fully rendered (or, for a @ResponseBody/@RestController endpoint, after the response body has been written), regardless of whether the request succeeded or an exception propagated — ex is non-null in the failure case. This is the right place for cleanup that needs to run no matter what, analogous to @After advice in AOP.
public class AuditInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (handler instanceof HandlerMethod hm) {
            // full access to which controller method is about to run - a filter cannot do this
            log.info("about to invoke {}", hm.getMethod().getName());
        }
        return true; // false would stop the chain before the controller ever runs
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                 Object handler, Exception ex) {
        if (ex != null) {
            log.warn("request failed after handler execution: {}", ex.toString());
        }
    }
}

The practical dividing line: reach for a filter when the concern doesn't need to know anything about which Spring controller method is involved (security token checks, CORS, gzip, raw access logging) — it's inherently a servlet-container-level concern and Spring shouldn't even need to be in the picture. Reach for a HandlerInterceptor when the concern genuinely needs MVC context — the resolved handler method (to read a custom annotation on it, for example, like a @RequiresRole marker on specific ShopSphere admin endpoints), or the ModelAndView to adjust what gets rendered. Ordering also matters operationally: every registered filter runs (in chain order) before any interceptor's preHandle, because the entire filter chain — including the final chain.doFilter call that hands off to DispatcherServlet — completes its "before" portion prior to DispatcherServlet even starting to resolve a handler.

The full path, assembled

Putting sections 9.1–9.6 together, a single ShopSphere POST /orders request travels: servlet container → registered Filter chain (auth check, CORS, logging) → DispatcherServlet → HandlerMapping resolves the target HandlerExecutionChain (the OrderController.placeOrder method plus any matching interceptors) → registered HandlerInterceptor.preHandle hooks run → HandlerAdapter resolves arguments (path variables, and an HttpMessageConverter deserializing the JSON body into a CreateOrderRequest) → the controller method actually executes, invoking OrderService as covered in sections 1–8 → the returned Order is handed to an HttpMessageConverter for serialization (because @RestController implies @ResponseBody, skipping view resolution) → postHandle runs (no-op here, since there's no ModelAndView on a REST endpoint) → the response is written → afterCompletion runs on every interceptor → control unwinds back out through the filter chain.

Concepts Worth Being Able to Explain From First Principles

Why does constructor injection turn a circular dependency into a startup failure, while field injection can silently "work"?
Constructor injection requires a bean's dependencies to be fully resolved before the constructor runs, because they're passed as arguments. If A needs a ready B and B needs a ready A, there is no valid construction order — Spring detects this and throws BeanCurrentlyInCreationException. Field and setter injection separate "create the object" from "populate its dependencies" into two distinct steps, which opens a window: Spring can create a half-built A, register it in an early-reference cache, then while building B (which needs A) hand back that half-built A reference, and finish populating both objects afterward. The cycle still exists structurally — it's just papered over instead of surfaced, which is exactly why relying on it is a design smell rather than a solution.
At what exact point in the bean lifecycle does an AOP proxy replace the real bean, and what does that imply about @PostConstruct?
The proxy is created inside BeanPostProcessor.postProcessAfterInitialization, which is the very last step of initialization — it runs after property population, Aware callbacks, postProcessBeforeInitialization, and @PostConstruct/afterPropertiesSet. This means during @PostConstruct, the object you're operating on (including any call through this) is still the raw, unproxied instance. Any method call made from inside @PostConstruct to another method on the same object will not go through AOP advice — including @Transactional or @Cacheable — because the proxy that would carry that advice doesn't exist yet at that point.
Why does injecting a prototype-scoped bean directly into a singleton fail to give you "a new instance every time," and what are the two correct fixes?
Dependency injection into a singleton happens exactly once, at the singleton's own construction. If the injected field is a plain reference to a prototype bean, Spring resolves that reference once (asking the container for one prototype instance) and the singleton holds that same object for its entire lifetime — every "new" prototype it appears to use is actually the same mutable object being reused. The fix has to defer resolution to the moment of use rather than the moment of construction: either inject a scoped proxy (@Scope(proxyMode = ScopedProxyMode.TARGET_CLASS)), where each method call on the proxy internally fetches a fresh prototype and delegates to it, or inject an ObjectProvider<T> and call .getObject() explicitly at each point of use.
Why can't a proxy intercept a method calling another method on this?
Spring AOP works by wrapping the real bean in a separate proxy object (JDK dynamic proxy or CGLIB subclass) that sits between callers and the real object. External callers get a reference to the proxy, and any call that arrives at the proxy is intercepted, has advice applied, and is then delegated to the real object. But once execution is already running inside a method of the real object, a call like this.otherMethod() is a direct call on the real object's own method table — the JVM has no reason to route it back out through the proxy, because from inside the object, there is no proxy in the call chain at all. The advice only exists on the proxy, so a call that never reaches the proxy never triggers it.
Why does @ConditionalOnMissingBean reliably let you override an auto-configured bean just by declaring your own @Bean?
Boot processes the application's own @Configuration classes before it processes auto-configuration classes (auto-configuration is explicitly ordered to run last, near the end of context refresh). @ConditionalOnMissingBean is evaluated at the point the auto-configuration class is processed, by which point your own bean definition, if you declared one of the same type, already exists in the bean definition registry. The condition sees that a bean of that type is already present and simply skips registering the auto-configured default — no explicit exclusion or override syntax needed, just ordering plus a presence check.
What's the actual difference between a JDK dynamic proxy and a CGLIB proxy, and why does it matter for final classes?
A JDK dynamic proxy is a class generated at runtime that implements the same interface(s) as the target and routes every interface method call through an InvocationHandler, which runs advice and then delegates to the real object — it requires the target to implement at least one interface, since the proxy's type is defined purely in terms of interfaces. A CGLIB proxy instead generates a runtime subclass of the target's concrete class, overriding methods to insert advice before calling super.method(). Because CGLIB works by subclassing, it cannot proxy a class marked final (you cannot subclass it) or a method marked final or private (you cannot override it) — advice on such methods is silently never applied, with no runtime error, which is why final classes/methods are a quiet trap for anything relying on Spring AOP (transactions, caching, security).
Why does Spring's ApplicationContext eagerly instantiate all singletons at startup instead of lazily on first use like a plain BeanFactory?
A plain BeanFactory defers bean creation until getBean() is first called, which is simpler and lighter but means a broken bean definition (missing dependency, bad configuration value, circular dependency) only surfaces the first time that code path is actually exercised — potentially long after deployment, under production traffic, on a rarely-hit branch. ApplicationContext eagerly constructs every singleton during context refresh specifically so that these failures happen at startup, in a controlled window, with a clear stack trace tied to application boot rather than to whatever user request happened to trigger the first use. This fail-fast behavior is a deliberate design choice trading slightly slower startup for much safer, more predictable failure timing.
ApplicationContext is described as a "superset" of BeanFactory — what does that actually mean in terms of the Java interfaces involved?
ApplicationContext is not a separate, competing container design — it's a Java interface that itself extends BeanFactory (through intermediate interfaces like ListableBeanFactory, which adds the ability to enumerate all registered bean definitions rather than only fetch one by name, and AutowireCapableBeanFactory, which adds the ability to autowire dependencies into an object the container didn't create itself). On top of that base contract, ApplicationContext additionally mixes in EnvironmentCapable (profiles and property sources), ApplicationEventPublisher (publish/subscribe for events like an in-process OrderPlaced notification), ResourceLoader, and MessageSource (i18n). The concrete class Spring Boot actually instantiates at startup — AnnotationConfigServletWebServerApplicationContext — implements all of this plus ConfigurableApplicationContext's lifecycle control (refresh(), close()). So "superset" is literal: every method a BeanFactory exposes is also callable on an ApplicationContext, plus a large amount more, and the eager-singleton-instantiation behavior is specifically part of what refresh() does that plain BeanFactory usage never triggers on its own.
Walk through what happens, mechanically, between a request hitting Tomcat and a controller method actually running.
The embedded servlet container hands the request to DispatcherServlet, the single front-controller servlet Spring Boot registers for (typically) all paths. DispatcherServlet asks a HandlerMapping (RequestMappingHandlerMapping for annotated controllers) which handler matches the request's path/method/headers — this returns a HandlerExecutionChain wrapping a HandlerMethod plus any applicable interceptors, but nothing has executed yet. DispatcherServlet then delegates actual invocation to a HandlerAdapter (RequestMappingHandlerAdapter), because it doesn't know how to invoke arbitrary handler types itself. The adapter resolves each method parameter via HandlerMethodArgumentResolvers — path variables, query params, and, for an @RequestBody parameter, delegating to an HttpMessageConverter that deserializes the raw request bytes into a Java object based on Content-Type. Only after all arguments are resolved does the controller method actually run.
Why does DispatcherServlet delegate to both a HandlerMapping and a separate HandlerAdapter instead of just calling the handler method directly?
These are two genuinely separate responsibilities. HandlerMapping's job is purely to decide which handler should process a given request, based on URL pattern, HTTP method, headers, and content type matching — it returns a reference to a handler without invoking anything. HandlerAdapter's job is knowing how to actually invoke whatever kind of handler was returned, since Spring MVC has historically supported multiple handler shapes (annotated @RequestMapping methods, legacy Controller implementations, functional endpoints). By keeping "what handles this" and "how do I call that kind of thing" as separate interfaces, DispatcherServlet stays agnostic to handler type entirely — it just asks a HandlerMapping for a handler and hands that handler to whichever HandlerAdapter claims it supports it, without ever needing a big if/else over handler types itself.
What's the real difference between a Servlet Filter and a Spring HandlerInterceptor, beyond "they both run around a request"?
A Filter is a servlet-spec construct registered with the container itself; it runs before DispatcherServlet is even reached and has no visibility into Spring MVC concepts at all — it only ever sees the raw request/response and a FilterChain it must explicitly call doFilter on to continue. It cannot know which controller method will eventually run, because that hasn't been resolved yet at the point a filter executes. A HandlerInterceptor is a Spring MVC construct registered with a HandlerMapping; it only runs for requests that DispatcherServlet has already matched to a handler, and its preHandle hook receives that resolved handler object directly, letting it inspect the target controller method (e.g. read a custom annotation on it) — something a filter structurally cannot do. Interceptors also expose three distinct lifecycle points (preHandle, postHandle, afterCompletion) tied to specific moments in MVC dispatch, versus a filter's single before/after wrap around chain.doFilter.
Why is postHandle skipped when a controller throws, but afterCompletion always runs?
postHandle is defined to run after the handler method returns successfully and before the view is rendered, specifically so it can inspect or adjust the ModelAndView the handler produced — but if the handler threw an exception instead of returning normally, there is no ModelAndView to hand it, so the hook is skipped entirely rather than called with a meaningless null. afterCompletion exists specifically to be the guaranteed cleanup hook regardless of outcome — it runs after request processing completes whether that completion was a normal render or an exception, and it receives the exception (or null) as an explicit parameter so cleanup code can branch on success versus failure. This mirrors the same before/around/after-regardless-of-outcome split as AOP advice types (@Before/@AfterReturning vs. @After), just applied at the MVC dispatch layer instead of the method-invocation layer.
