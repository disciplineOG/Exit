Why this matters

Every backend Java interview eventually touches on how you actually work day-to-day, and for most teams that means Git. Interviewers ask about merge versus rebase, conflict resolution, and branching strategy not to test trivia but to see whether you can keep a shared history clean and safe when several engineers are pushing changes to the same order-service repository at once. Mishandling a rebase on a shared branch or panicking during a merge conflict is a real, common way to lose production code, so being fluent here signals you can be trusted with the team's history. This page covers the core Git commands, workflows, and pull request review practices that come up across nearly every backend role.

Git Fundamentals

What is Git, and what is the difference between Git and GitHub?
Git is a distributed version control system (DVCS) — a tool that tracks every change made to a set of files over time, letting multiple engineers work on the same codebase, see the full history of who changed what and why, and safely branch off to work on separate features in parallel without stepping on each other. "Distributed" is the key word: unlike older centralized systems where only one server holds the full history, every developer's local clone of a Git repository contains the entire project history, so you can commit, branch, and view history offline, and there's no single point of failure. GitHub (along with GitLab, Bitbucket, etc.) is a separate, cloud-hosted product built around Git — it stores a shared copy of a Git repository that a team pushes to and pulls from, and layers on collaboration features Git itself doesn't provide, like pull requests, code review UIs, issue tracking, and CI/CD pipeline integration. In short: Git is the version control tool that runs on your machine, GitHub is a hosting and collaboration platform for repositories that use Git — you could use Git entirely without ever touching GitHub (e.g. hosting your own server), but most teams use both together, for example hosting order-service's repository on GitHub while every engineer runs Git locally.
What is a .gitignore file, and why does every real project need one?
A .gitignore file lists file and directory patterns that Git should never track or offer to stage, even if they exist in your working directory — typical entries are build output (target/, build/), IDE metadata (.idea/, .vscode/), local environment files with secrets (.env), and compiled artifacts (*.class, *.jar). Without it, git status and git add . constantly surface noise from generated files that have nothing to do with the actual source change you're making, and it becomes easy to accidentally commit a large compiled binary or, worse, a file containing a database password or API key for payment-service straight into shared history. Patterns can use wildcards (*.log), directory-level ignores (node_modules/), and negation (!important.log to un-ignore a specific file inside an otherwise ignored pattern), and each subdirectory can have its own .gitignore that adds to the root one. It's worth knowing that .gitignore only prevents untracked files from being added — if a file was already committed before being added to .gitignore, Git keeps tracking it, and you have to explicitly run git rm --cached <file> to stop tracking it going forward.
What is the difference between git merge and git rebase, and when should you prefer each?
git merge combines two branches by creating a new "merge commit" that has two parents, preserving the exact history of both branches exactly as it happened — if you merge feature/add-coupon-support into main, you get a merge commit plus every original commit from the feature branch, in order, alongside main's own commits. git rebase instead takes the commits from your branch and replays them one by one on top of the latest commit of the target branch, producing a linear history with no merge commit, as if you had started your feature branch from today's main all along. The practical trade-off is that merge is non-destructive and safe on shared branches because it never rewrites existing commits, while rebase rewrites commit hashes, which is fine on a private feature branch you haven't pushed yet but dangerous on a branch others have already pulled, since their history will diverge from yours. A common team convention is: rebase your own local feature branch on the latest main before opening a pull request to keep history clean and avoid an unnecessary merge commit, but always merge (never rebase) when integrating a shared or already-published branch.
What does git cherry-pick do, and when would you use it?
git cherry-pick <commit-hash> takes a single specific commit from anywhere in the repository's history and re-applies just that commit's changes on top of your current branch, creating a new commit with the same content (and message, by default) but a new hash and new parent. This is useful when you need one specific fix without pulling in an entire branch's unrelated history — for example, a critical bug fix was committed on develop for a null pointer exception in payment-service's refund handling, and you need that exact fix backported onto a release/2.3 branch that is already frozen for other changes. Cherry-picking can produce conflicts just like a merge or rebase if the target branch has diverged from where the original commit was made, and those conflicts are resolved the same way — edit the conflicting files, stage them, then run git cherry-pick --continue. It's a targeted tool for moving isolated changes across branches; overusing it as a substitute for a proper merge strategy tends to create duplicate commits with different hashes representing the same logical change, which can confuse later merges.
What does git stash do, and how do you use it?
git stash temporarily saves your uncommitted changes (both staged and unstaged, by default) into a separate stack-like storage area and reverts your working directory back to match the last commit, giving you a clean working tree without having to make a throwaway commit. This is useful when you're in the middle of editing inventory-service code and need to urgently switch branches to fix a production bug — you stash your half-finished work, switch branches, fix the bug, switch back, and run git stash pop to reapply your changes and remove them from the stash stack (or git stash apply to reapply without removing them, useful if you want to apply the same stash to multiple branches). You can stash multiple times, and git stash list shows every saved stash with an index (stash@{0}, stash@{1}, etc.) so you can choose which one to restore with git stash pop stash@{1}. A stash can also conflict on pop/apply if the branch has changed underneath it in a way that overlaps with the stashed changes, in which case it's resolved exactly like a merge conflict.
How do you resolve a merge conflict, step by step?
A merge conflict happens when Git cannot automatically reconcile changes because both branches modified the same lines (or one branch modified a file the other deleted), so Git pauses the merge/rebase and marks the affected files rather than guessing. First, run git status to see exactly which files are listed as "both modified" (unmerged). Second, open each conflicted file and look for the conflict markers Git inserts: <<<<<<< HEAD marks the start of your current branch's version, ======= separates it from the incoming version, and >>>>>>> branch-name marks the end of the incoming branch's version — for example, both you and a teammate edited the discount calculation in the Order pricing logic, and Git shows both versions side by side. Third, manually edit the file to keep the correct combined logic (which might be one side, the other, or a hand-merged combination of both) and delete the conflict markers entirely; many editors and IDEs also offer a three-way merge view to do this visually. Fourth, run git add <file> to mark the conflict as resolved for that file, then once every conflicted file is staged, run git commit (for a merge) or git rebase --continue (for a rebase) to finish the operation — and if things go badly wrong, git merge --abort or git rebase --abort cleanly bails out back to the pre-conflict state.
What is the difference between git reset (soft, mixed, hard) and git revert, and why is revert safer on shared branches?
git reset moves your current branch pointer to a different commit and, depending on the mode, also changes your staging area and working directory: --soft moves the branch pointer but leaves all changes staged, effectively "uncommitting" while keeping everything ready to recommit; --mixed (the default) moves the pointer and unstages the changes but leaves the file contents in your working directory untouched; --hard moves the pointer and discards all changes in both the staging area and working directory, permanently losing any uncommitted work at those commits unless you have another reference to them. git revert <commit> instead creates a brand-new commit that applies the exact inverse of a previous commit's changes, leaving the original commit intact in history rather than removing it. This is why revert is the safe choice on a shared branch like main: since it adds a new commit instead of rewriting existing ones, everyone who already pulled the old history stays in sync and simply pulls the new revert commit, whereas a reset --hard pushed to a shared branch rewrites history that others have already based work on, forcing painful, error-prone history reconciliation for the whole team. The practical rule is: use reset freely on local, unpushed commits to clean up your own history, and use revert to undo something that has already been pushed and shared.
What is the difference between git fetch and git pull?
git fetch downloads new commits, branches, and tags from a remote repository into your local repository's remote-tracking branches (like origin/main) without touching your current working branch or working directory at all — it's a purely informational, safe operation that lets you see what changed upstream before deciding what to do about it. git pull is effectively git fetch immediately followed by a merge (or rebase, if configured with git pull --rebase) of the fetched remote branch into your current local branch, which does modify your working directory and can trigger a merge conflict on the spot. The practical difference matters when you want control: running git fetch then git diff main origin/main lets you review exactly what changed on the remote main before merging it into your local work, whereas git pull jumps straight to merging and can surprise you with an unexpected conflict in the middle of other work. Many experienced engineers default to fetch plus an explicit merge or rebase specifically to keep that inspection step, especially on a repo with many active contributors.
What is git bisect, and how do you use it to find which commit introduced a bug?
git bisect automates a binary search through your commit history to find the exact commit that introduced a regression, instead of manually checking out commits one at a time. You start it with git bisect start, then tell it one commit you know is broken (git bisect bad, usually the current commit) and one you know was fine (git bisect good v2.3.0, an older tag or commit); Git then checks out the commit exactly halfway between the two. You test that checked-out commit — for example, running the integration test that reproduces a checkout failure in order-service — and tell Git the result with git bisect good or git bisect bad, and it keeps halving the remaining range until it lands on the single first-bad commit, at which point git bisect reset returns you to where you started. For a history of a few hundred commits this typically takes under ten steps (log₂ of the range) instead of checking every commit linearly, and if you already have an automated test that reproduces the bug you can skip the manual back-and-forth entirely with git bisect run ./gradlew test --tests PaymentServiceIT, which runs the test at each step and interprets its exit code as good/bad automatically. This is one of the fastest ways to answer "when did this break?" on a large shared repository like a monolithic order-service codebase with years of history.
Why is git push --force dangerous on a shared branch, and what does --force-with-lease do differently?
After rebasing or resetting local commits that have already been pushed, a normal git push is rejected because the remote branch has commits your local branch no longer has (the histories have diverged); git push --force overrides that check and unconditionally overwrites the remote branch's history with your local branch, no matter what changed on the remote in the meantime. The danger is that if a teammate pushed a new commit to that same branch after you last fetched but before your force-push lands, --force silently discards their commit from the remote with no warning — their work isn't in your local history, so your force-push simply erases it upstream, and they only find out when their next pull produces a confusing divergence. git push --force-with-lease is a safer version of the same operation: before overwriting, it checks that the remote branch is still exactly where your local remote-tracking branch (e.g. origin/feature/add-coupon-support) last saw it, and refuses to push if someone else has updated the remote in between, forcing you to fetch and look at their changes first instead of blindly clobbering them. The practical rule is: never force-push to a shared branch like main at all, and on a personal feature branch that others might also be pushing to, always prefer --force-with-lease over plain --force as the default habit.
What is HEAD, and what does a "detached HEAD" state mean?
HEAD is a pointer that represents your current position in the repository — almost always it points to the tip of whichever branch you have checked out (so HEAD "follows" that branch as you make new commits), and commands like HEAD~1 or HEAD^ let you reference commits relative to your current position. A "detached HEAD" state happens when HEAD points directly to a specific commit instead of to a branch name, which occurs when you explicitly check out a commit hash, a tag, or a remote commit rather than a local branch (e.g. git checkout a1b2c3d or git checkout v2.3.0). In this state you can still look around and even make new commits, but those new commits aren't attached to any branch, so if you switch away to another branch without doing anything, those commits become unreachable and are eventually garbage-collected. The safe way out is: if you made changes worth keeping while detached, run git switch -c new-branch-name (or the older git checkout -b) to attach a real branch name to your current commit before leaving that state, so the work isn't silently lost.
What does git commit --amend do, and what is interactive rebase (git rebase -i) used for?
git commit --amend replaces your most recent commit with a new one, letting you fix a typo in the commit message or add a forgotten file change without creating an extra "oops, fix typo" commit — it does this by creating a brand-new commit with a new hash and discarding the old one, so like any history rewrite it should only be done on commits you haven't pushed yet (or that no one else has already pulled). Interactive rebase, git rebase -i <base-commit>, opens an editable list of the commits between <base-commit> and your current branch tip and lets you rewrite that stretch of history before replaying it: pick keeps a commit as-is, reword lets you edit just its message, edit pauses so you can amend its contents, squash or fixup merges it into the commit above (fixup discards its message, squash lets you combine messages), and drop removes it entirely. A common use on ShopSphere-style projects is cleaning up a feature branch before opening a pull request — squashing five "wip" and "fix test" commits into one well-described commit for order-service's new discount-code validation, so reviewers see a clean, logical change instead of your exact trial-and-error process. As with any rewrite, interactive rebase must only touch commits that haven't been shared, since it changes commit hashes for everything it rewrites.

Workflows & Branching Strategy

What is a pull request, and what does the basic day-to-day workflow around one look like?
A pull request (PR) — called a merge request (MR) on GitLab — is a formal request to merge the commits from one branch into another, typically into main, that acts as a checkpoint for review and automated checks before the change becomes part of the shared codebase. The basic flow is: create a branch off main for your change (e.g. feature/add-coupon-support), make commits on it, push the branch to the remote, and open a PR describing what changed and why; this triggers continuous integration (CI) checks like the build and automated tests, and notifies teammates to review the diff. Reviewers leave comments, request changes, or approve; the author addresses feedback with more commits on the same branch (which automatically update the open PR); and once approved and all checks pass, the PR is merged into main using whatever merge strategy the team has adopted, after which the feature branch is usually deleted. This workflow is the backbone of how most teams collaborate safely on a shared repository like order-service's, since nothing reaches main without at least one other engineer looking at it first.
What is the difference between Gitflow and trunk-based development, and what are the trade-offs?
Gitflow is a branching model with several long-lived, purpose-specific branches: main (production-ready code), develop (integration branch for the next release), plus temporary feature/*, release/*, and hotfix/* branches that eventually merge back into both develop and main. It gives strong structure and works well for products with scheduled, versioned releases (e.g. mobile apps or on-prem software with formal release cycles), but the extra branches and merge steps add process overhead and make continuous delivery harder, since code can sit on develop for a long time before reaching main. Trunk-based development instead keeps a single long-lived branch (main/trunk), with developers committing small, frequent changes directly to it or through very short-lived feature branches (often merged within a day), relying on feature flags to hide incomplete work rather than long-lived branches to isolate it. Trunk-based development trades some of that structure for much faster integration and fewer painful "big bang" merges, which is why it's the dominant model at companies practicing continuous deployment (like frequently shipping order-service changes multiple times a day) — the real cost is that it demands strong automated test coverage and feature-flagging discipline, since there's no long-lived branch acting as a safety buffer before production.
What is the difference between feature branches and long-lived branches, and why do long-lived branches cause problems?
A feature branch is created off main (or develop) to build one specific piece of work — say, adding seller payout support to payment-service — and is intended to be short-lived: merged back and deleted within days, not months. A long-lived branch is one that stays open and diverges from main for an extended period, whether that's an intentionally long-lived branch (like a Gitflow develop branch) or, more problematically, a feature branch that was supposed to be short but dragged on for weeks. The core problem with long-lived branches is merge drift: the longer a branch exists without being reconciled with main, the more both sides change independently, so the eventual merge accumulates more conflicting changes, touches more files, and becomes riskier and harder to review as a single unit. The practical mitigation is to keep feature branches as small and short-lived as possible, regularly merging or rebasing from main while the branch is still open, and if a feature genuinely needs longer development time, hide the incomplete functionality behind a feature flag on main rather than letting the branch itself grow stale.
What is a pull request (or merge request) review actually checking for, beyond "does it work"?
Opening a PR is only the mechanical half of the workflow — the value is in what a good reviewer actually checks, which goes far beyond whether the code runs. Correctness under edge cases is one axis: does the change handle a Cart with zero items, a Payment that times out mid-capture, or a race condition between two concurrent Order placements, not just the happy path the author tested manually. Readability and maintainability is another: will the next engineer (who has no context on why this was written) be able to understand and safely modify it, including sensible naming, comments where logic is non-obvious, and consistency with the codebase's existing patterns. Test coverage is checked directly: does the diff include tests for the new behavior and any bug being fixed, not just production code changes. Reviewers also look at architectural fit (does this change belong in order-service or should shared logic move to a common library), security implications (is user input validated, are secrets or PII being logged), and performance red flags (an unbounded query, an N+1 database call introduced inside a loop). Good review comments distinguish blocking issues from optional nitpicks, and a thorough reviewer is effectively acting as a second author accountable for what ships.
What is the difference between squash-and-merge, merge commit, and rebase-and-merge on a pull request?
These are the three common strategies a PR can use to actually integrate a branch once it's approved, and they differ in what the resulting history on the target branch looks like. A merge commit keeps every individual commit from the feature branch and adds one merge commit tying them together, preserving the most detail (useful if the branch's commit-by-commit history has real value) but cluttering main's history with work-in-progress commits like "fix typo" or "wip" that were never meant to be permanent. Squash-and-merge collapses every commit on the feature branch into a single new commit applied to main, discarding the intermediate commit history but keeping main's log clean, with exactly one commit per merged PR — this is popular specifically because it makes git log on main read like a list of shipped features/fixes rather than a messy work log, and makes reverting an entire PR trivial (one commit to revert). Rebase-and-merge replays each individual commit from the feature branch directly onto main without a merge commit, producing a fully linear history that still preserves each original commit individually, which is a middle ground: no merge commit clutter, but also no single-commit-per-PR simplification. Team choice usually comes down to how much they value granular history versus a clean, one-commit-per-feature log: squash-and-merge is the most common default for teams that don't want intermediate WIP commits polluting main.
What makes a good commit message, and what are conventional commits?
A good commit message has a short, imperative-mood summary line (under ~50-72 characters, e.g. "Fix null pointer in refund calculation" rather than "fixed bug" or "changes") followed, if needed, by a blank line and a body explaining why the change was made and any non-obvious trade-offs — the diff itself already shows what changed, so the message's job is to add context a diff can't: the bug symptom, the ticket reference, or why an alternative approach was rejected. "Conventional Commits" is a widely adopted convention that prefixes the summary with a type, such as feat: for a new feature, fix: for a bug fix, refactor:, docs:, or chore:, optionally with a scope like fix(payment-service): handle timeout on capture retry. Beyond readability, this convention is machine-parseable: tools like semantic-release use the commit type to automatically determine the next version bump (a fix: bumps a patch version, a feat: bumps a minor version, and a BREAKING CHANGE: footer bumps a major version) and to auto-generate changelogs. On a team with many contributors across microservices like inventory-service and notification-service, consistent commit messages make git log and git blame genuinely useful for later debugging instead of a wall of uninformative noise.
How do you handle a hotfix that needs to go straight to production while a release branch or long-lived develop branch is in progress?
A hotfix is an urgent, narrowly scoped fix — for example, payment-service is double-charging customers in production — that can't wait for the normal release cycle to reach main. The standard pattern is to branch directly off the current production tag or main (not off an in-progress develop or release branch, which may contain unfinished, unreleased work), make the minimal fix, get an expedited review, and merge it straight to main so it can be deployed immediately. Critically, that same fix must also be merged (or cherry-picked) into any active develop or release branch, otherwise the next regular release will silently reintroduce the bug because it was branched from before the hotfix existed — this is one of the most common real-world sources of "we fixed this already, why is it back in production." Teams following trunk-based development sidestep most of this complexity since there's no long-lived develop to resync: the hotfix simply lands on main like any other small change, behind a feature flag if it needs staged rollout, which is a large part of why trunk-based development has become popular for services with frequent deploys.
In a microservices setup with many independent services, would you use a monorepo or a polyrepo, and what are the trade-offs?
A polyrepo keeps each service in its own repository — order-service, inventory-service, payment-service, notification-service, and catalog-service each get their own Git history, their own access controls, and their own independent versioning and release cadence, which maps cleanly onto independently deployable microservices and keeps each team's CI fast since it only builds and tests its own service. A monorepo keeps all (or many) services in a single repository, which makes cross-service refactors atomic in one commit (e.g. changing a shared event schema on Kafka and updating every consuming service in the same pull request), makes it trivial to share common code and tooling, and gives a single source of truth for "what does the whole system look like right now" — at the cost of needing serious tooling investment (like Bazel or Nx) to keep build and CI times reasonable as the repo grows, and coarser access control since everyone typically has read access to everything. The trade-off in practice is organizational as much as technical: polyrepo suits teams that own services end-to-end with little cross-cutting change, while monorepo suits organizations that frequently need coordinated, atomic changes across service boundaries and are willing to invest in the build tooling to make that scale; most companies land somewhere in between, such as one repo per bounded context rather than strictly one-repo-per-microservice or one-repo-for-everything.
