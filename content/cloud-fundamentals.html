Cloud Fundamentals for Backend Engineers (AWS core services)

EC2 / ECS / EKS / Lambda VPC Networking S3 / EBS / EFS RDS / DynamoDB IAM Auto Scaling & ELB
Why this matters

Every distributed-systems concept you've studied — sharding, load balancing, health checks, replication — exists inside AWS as an actual named product with actual defaults, quotas, and failure modes, and those defaults quietly become part of your system's behavior whether you chose them deliberately or not. Not knowing that a default Lambda timeout is 3 seconds, or that a DynamoDB table without a well-distributed partition key will silently throttle, or that a database sitting in a public subnet is one misconfigured security group away from being internet-facing, is exactly the kind of gap that turns into a 2am incident. This page builds the mental model of "which building block for which job" so that reading a production architecture diagram — or drawing one — becomes an exercise in recognizing trade-offs you already understand.

1. The Compute Spectrum: EC2, Containers, and Lambda

Every cloud provider offers compute along a spectrum defined by one variable: how much of the stack you manage versus how much the provider manages. Moving up the spectrum trades control for reduced operational burden, and the "right" tier for a workload is almost always determined by how predictable its traffic and runtime characteristics are.

EC2 — virtual machines, maximum control

An EC2 instance is a virtual machine running on physical hardware in an AWS availability zone. You choose the instance family (compute-optimized c-series, memory-optimized r-series, general purpose m-series, burstable t-series), the operating system, and you are responsible for everything above the hypervisor: OS patching, runtime installation, process supervision, log rotation, security hardening. This is the same responsibility model as running your own physical server, minus the physical server. You get full control over the process lifecycle — useful when you need a specific kernel version, a licensed piece of software, or fine-grained control over resource isolation — but you also own every 2am page caused by disk filling up or a kernel CVE.

ECS / EKS — container orchestration, the middle ground

Elastic Container Service (ECS) and Elastic Kubernetes Service (EKS) sit in the middle: you package your application as a container image, and the orchestrator handles placement, restart-on-crash, and rolling deployment across a fleet of underlying compute. This is the same problem docker-kubernetes covers in provider-neutral terms — pods, replica sets, service discovery — and EKS is literally upstream Kubernetes, so everything you know about deployments, liveness probes, and horizontal pod autoscaling transfers directly. ECS is AWS's own simpler orchestrator with a smaller conceptual surface (tasks and services instead of pods and deployments) at the cost of being AWS-specific.

Within both, you additionally choose a launch type: EC2 launch type means you still manage the underlying instances the containers run on (you own capacity planning and patching of the host), while Fargate removes the host entirely — you specify CPU and memory for the task and AWS runs it on infrastructure you never see. Fargate is effectively "serverless containers," trading some cost efficiency and startup latency for eliminating host management altogether.

Lambda — serverless functions, minimum operational overhead

Lambda runs a single function in response to an event (an HTTP request via API Gateway, an S3 object creation, an SQS message, a scheduled cron) and you are billed per invocation and per millisecond of execution time. There is no server to patch, no fleet to size — AWS provisions an execution environment on demand. This is the extreme end of "least operational overhead," but it comes with two structural constraints worth internalizing rather than memorizing:

  • Cold starts. When no warm execution environment exists for your function, AWS must provision one: download your deployment package, initialize the runtime, run your static initializers. For a JVM-based Lambda this can add hundreds of milliseconds to several seconds before your handler code even runs, because JVM class loading and JIT warm-up are exactly as slow here as they are in any other JVM process — Lambda doesn't make the JVM start faster, it just controls how often you pay that cost. Provisioned Concurrency exists specifically to pre-warm a pool of environments and eliminate this for latency-sensitive paths, at the cost of paying for idle capacity, which partially defeats the "pay only for what you use" premise.
  • Execution time limits. A Lambda invocation is capped at 15 minutes. This isn't an arbitrary quota — it reflects the model's assumption that a function is a short-lived reaction to an event, not a long-running process. Anything that needs to hold state across a long computation, maintain a persistent connection (a database connection pool, a WebSocket), or run indefinitely (a queue consumer polling continuously) is structurally the wrong shape for Lambda and belongs on ECS/EKS or EC2 instead.
Choosing a tier: ask about variance, not just scale

The deciding question is rarely "how much traffic" — it's "how predictable and how bursty is the traffic, and how long does one unit of work take?" A steady, high-volume workload with well-understood peak load is usually cheaper and more predictable on EC2 or ECS, because you can right-size capacity and amortize the cost of a warm process across many requests. A spiky, unpredictable, or infrequent workload (a webhook handler invoked a few times an hour, a nightly batch job, an image-resize triggered by uploads) is a natural fit for Lambda, because you pay nothing between invocations and don't need to provision for a peak that rarely arrives. Long-running or stateful processes — anything holding open connections, in-memory caches, or requiring more than 15 minutes — rule Lambda out regardless of traffic shape.

2. Core Networking: VPC, Subnets, and Firewalls

VPC — your isolated network

A Virtual Private Cloud (VPC) is a logically isolated slice of the AWS network, defined by a CIDR block (for example 10.0.0.0/16), inside which you place every resource you launch. Nothing inside your VPC is reachable from outside it, and nothing outside is reachable from inside, unless you explicitly wire up a path — an internet gateway, a NAT gateway, a peering connection, a VPN. This "deny by default at the network boundary" posture is the cloud equivalent of putting your servers behind a firewall at a physical data center: isolation is the starting state, and every route in or out is a deliberate decision you can audit.

Public vs. private subnets

A VPC is subdivided into subnets, each pinned to a single availability zone. A subnet is "public" if its route table sends 0.0.0.0/0 traffic to an internet gateway — meaning resources in it can have a public IP and be reached directly from the internet. A subnet is "private" if it has no such route; its resources can only be reached from within the VPC (or reach the internet outward through a NAT gateway sitting in a public subnet, for things like downloading OS patches, without being reachable inbound).

Databases, application servers holding sensitive state, and internal caches belong in private subnets as a default posture, not an afterthought. The reasoning is the same principle behind least-privilege access generally: a resource that has no route to or from the public internet cannot be the entry point of an internet-originated attack, no matter what software bug or misconfigured credential might otherwise expose it. The public-facing layer — a load balancer, a bastion host, an API Gateway endpoint — is the only thing that needs a direct internet route, and it acts as the sole choke point you have to harden and monitor.

Security groups vs. NACLs

AWS gives you two layers of firewall, and conflating them is a common source of "why can't this connection get through" debugging sessions.

Statefulness is the detail that bites people

Because security groups are stateful, you typically only write inbound rules and never think about outbound rules for response traffic — which is correct, but it means people forget NACLs don't work that way. If you add a NACL rule allowing inbound traffic on a port but forget the corresponding outbound rule for ephemeral ports (typically 1024–65535, where the client side of a TCP connection lives), responses get silently dropped at the subnet boundary even though the security group looks completely correct. This is a classic case where the connection is allowed in but the reply can't get out, and nothing about the security group configuration will tell you that — you have to know NACLs are a second, independent, stateless layer to think to check them.

3. Storage: Choosing by Access Pattern, Not by Habit

The right storage service is determined by one question: does this data need to be block-level (mounted as a raw device to one machine), shared across many machines as files, or addressed as opaque objects over HTTP? These are genuinely different access patterns, not just marketing tiers of the same thing.

EBS — block storage, one instance at a time

An EBS volume is a virtual hard drive: a block device that attaches to exactly one EC2 instance (with rare multi-attach exceptions for specific clustered filesystems) and persists independently of the instance's lifecycle — you can stop the instance, and the volume's data survives, then reattach it or attach it to a different instance later. This is the right choice for anything that needs low-latency, POSIX-filesystem-backed storage local to a single compute node: a database's data directory, a local write-ahead log, application scratch space. It is not shareable across instances simultaneously in the general case, which is precisely the constraint that motivates EFS.

EFS — shared network file storage

EFS is a managed NFS filesystem that multiple EC2 instances (or containers) can mount concurrently and see the same consistent view of files. Reach for it when several compute nodes genuinely need to read and write the same files — a fleet of web servers sharing uploaded user content, a batch of worker nodes sharing intermediate output, a content-management system's shared media library. The trade-off versus EBS is latency (network-attached, not local block device) and cost per GB, in exchange for the sharing property EBS structurally cannot provide.

S3 — object storage and its consistency history

S3 stores unstructured blobs — images, backups, logs, static assets, data-lake files — addressed by key within a bucket, accessed over HTTP(S), with no filesystem semantics (no partial-file edits, no directory locking) and effectively unlimited scale. It is not a filesystem and not a database; it is closer to a distributed, replicated key-value store for large binary values, which is also why it's the substrate underneath many managed services (EBS snapshots, RDS backups, and Lambda deployment packages all ultimately live on S3-like storage).

A detail worth understanding precisely rather than glossing over: S3 originally offered eventual consistency for read-after-write on overwrite (PUT to an existing key) and delete operations — you could write a new version of an object and, for a brief window, still read the old version or a 404 from some replicas, because the write had to propagate across S3's internal replication before every read path reflected it. In December 2020, AWS changed this so that S3 provides strong read-after-write consistency for all operations, on all objects, in all regions, at no extra cost. This matters historically because a great deal of production code and cautionary folklore ("never immediately read a key you just wrote to S3, retry with backoff") was written against the old model, and that workaround is now unnecessary — but the underlying lesson generalizes far beyond S3: any system with replication has to make an explicit choice about the consistency window between a write landing on one replica and being visible on all of them, and that choice is a design decision with real cost, not an implementation detail you can ignore.

4. Managed Databases: RDS and DynamoDB

RDS — what "managed relational database" actually removes from your plate

RDS runs a standard relational engine (PostgreSQL, MySQL, MariaDB, or others) but takes over the operational layer that traditionally consumes real engineering time: automated backups and point-in-time recovery, minor-version patching, storage auto-scaling, and — critically — Multi-AZ failover, where a synchronously replicated standby in a second availability zone can be promoted automatically if the primary fails, with the connection endpoint staying the same so applications don't need reconfiguration. None of this changes the relational data model or query semantics you already understand; it changes who gets paged when a disk fills up or a patch needs applying. Self-hosting the same engine on EC2 is entirely possible and sometimes justified (specific extensions, exact version pinning, cost at very large scale) but means you own writing and testing that failover logic yourself.

DynamoDB — partition keys and the scaling model

DynamoDB is a managed NoSQL key-value/document store where every item lives in a partition determined by hashing the item's partition key, and DynamoDB distributes partitions across many physical nodes to scale throughput horizontally. This is the exact same idea covered in database-architecture as sharding — DynamoDB simply performs it for you, transparently, instead of you sharding a relational database by hand across multiple hosts.

The practical consequence is that your partition key choice determines your scaling ceiling. If a partition key has low cardinality or highly skewed access (an orderStatus field with only a few values, or a single "hot" tenant ID responsible for most traffic), most requests land on the same one or few physical partitions, and you hit that partition's throughput limit long before you hit any table-wide limit — the classic symptom is ProvisionedThroughputExceededException or throttling on a table that looks, in aggregate, nowhere near capacity. Choosing a high-cardinality, access-pattern-uniform partition key (a user ID, a UUID, a composite key) is the DynamoDB equivalent of choosing a good shard key in a hand-rolled sharded relational system, and it's a decision made at table-design time that's expensive to change later, exactly like a sharding key decision.

The general question: what does "managed" buy you?

Across RDS, DynamoDB, and every other managed service, the pattern is identical: the provider takes ownership of the operational tasks that don't differentiate your product — failover orchestration, patch management, replication topology, hardware replacement — while you keep ownership of the tasks that do: data modeling, schema/key design, query patterns, capacity planning inputs. Self-hosting is not "wrong," but it means explicitly signing up to own the operational half as well, and that trade-off should be a deliberate choice weighed against your team's actual operational capacity, not a default.

5. IAM: Identity, Roles, and Least Privilege

Identity and Access Management (IAM) answers two separate questions that are easy to conflate: who or what is making this request (authentication) and what are they allowed to do (authorization). IAM has three core building blocks:

  • Users represent a long-lived human or application identity with its own credentials (password, access keys).
  • Roles represent a set of permissions that can be temporarily assumed by a trusted principal — a human, an application, or (critically) an AWS compute resource itself — producing short-lived credentials that expire automatically.
  • Policies are JSON documents attached to users, roles, or resources that explicitly enumerate allowed (or denied) actions on specific resources, e.g. s3:GetObject on arn:aws:s3:::my-bucket/*.

The principle of least privilege means granting exactly the permissions a principal needs to do its job and nothing more — not "read/write access to everything" because it's convenient, but "read access to this one bucket prefix" because that's what the code actually does. The value of this isn't abstract hygiene: it bounds the blast radius when something goes wrong. If an application's credentials leak — through a logged stack trace, a misconfigured public repository, a compromised dependency — the damage is limited to whatever that narrow policy permits, rather than to your entire account.

Why an instance role beats an embedded access key

Attaching an IAM role to an EC2 instance, ECS task, or Lambda function is preferred over embedding a long-lived access key/secret pair in configuration or environment variables for a specific mechanical reason: a role's credentials are issued automatically to the resource by AWS's metadata service, rotated automatically behind the scenes, and never exist as a static string anyone could accidentally commit to a repository, print in a log line, or leave in a config file that outlives the employee who wrote it. A long-lived access key, by contrast, is a durable secret with no expiry by default — once it leaks, it's valid until someone notices and manually revokes it, which in practice can be months. This is the same "credentials as short-lived, narrowly-scoped tokens rather than durable shared secrets" pattern that shows up in OAuth access tokens and Kubernetes service account tokens — it's a general security pattern, not an AWS-specific quirk.

6. Auto Scaling Groups and Load Balancers

Horizontal scaling — adding more instances rather than making one instance bigger — is the concept covered generically in hld-basics-scaling; AWS's concrete implementation of it is the pairing of an Auto Scaling Group (ASG) with an Elastic Load Balancer (ELB).

An ASG maintains a fleet of EC2 instances (or, indirectly, ECS tasks via Service Auto Scaling) between a minimum and maximum count, launching new instances from a template when a scaling policy's trigger fires — commonly average CPU utilization crossing a threshold, a custom CloudWatch metric like queue depth, or a scheduled action anticipating a known traffic pattern. Crucially, the ASG also performs the inverse: it terminates instances when demand drops, which is the mechanism that actually realizes the cost benefit of elastic infrastructure — capacity that shrinks back down instead of a fleet sized permanently for peak load.

A Load Balancer (an Application Load Balancer for HTTP/HTTPS traffic, or a Network Load Balancer for raw TCP/UDP at very high throughput or when a static IP is required) sits in front of the ASG's instances and distributes incoming requests across whichever instances are currently healthy. The load balancer performs periodic health checks — an HTTP request to a configured path expecting a specific status code — and stops routing traffic to any instance that fails enough consecutive checks, which is what lets an ASG replace a crashed or degraded instance without that instance ever receiving traffic it can't serve. This pairing — dynamic fleet sizing plus health-aware traffic distribution — is what makes horizontal scaling operationally real rather than theoretical: it's not enough to be able to add capacity, the system also has to detect which capacity is currently healthy and route only to that.

7. Closing the Loop: Managed Services and Resilience/Observability

A theme runs through every service covered above: a meaningful fraction of what would otherwise be custom-built resilience and observability tooling comes bundled into the managed service by default. RDS Multi-AZ gives you cross-availability-zone failover without writing failover orchestration yourself. An ALB's health checks give you the failure-detection half of a circuit breaker pattern at the infrastructure layer, before a single line of application-level resilience code runs. CloudWatch automatically collects CPU, memory (with the agent installed), request counts, and latency metrics for most of these services without instrumenting your own code. ASGs replacing unhealthy instances is a form of automatic self-healing that, self-hosted, you'd have to build with your own supervisor process and health-check loop.

This doesn't eliminate the need for the practices in observability-production — you still need application-level tracing, structured logs, and business-level metrics that no infrastructure service can infer on your behalf — but it does mean part of the resilience and observability burden is already handled at the platform layer, and recognizing which part is the difference between duplicating effort and correctly layering your own instrumentation on top of what the platform already gives you for free.

Concepts Worth Being Able to Explain From First Principles

Why does Lambda have both a cold-start problem and a maximum execution time, and are these related?
They stem from the same underlying model but are independent mechanics. Cold start exists because Lambda has no dedicated server sitting idle waiting for your traffic — an execution environment (essentially a lightweight container plus your runtime and code) is provisioned on demand the first time it's needed, or whenever concurrency needs to increase beyond currently-warm environments, and that provisioning takes real time, especially for runtimes like the JVM that do meaningful work at class-load and JIT-warm-up time. The 15-minute execution cap is a separate, deliberate constraint reflecting Lambda's design as a reaction to discrete events rather than a long-running process host; it exists so AWS can reclaim and reuse execution environments predictably and so the billing/scheduling model stays simple. You can have a cold start with a fast function (cold start dominates total latency) or a warm function that still can't run past 15 minutes (a long batch job that needs Fargate or EC2 instead) — the two constraints solve different problems and you can hit either independently of the other.
A DynamoDB table is well within its overall provisioned/on-demand capacity but requests are still being throttled. What's the likely cause and why does aggregate capacity not protect against it?
The likely cause is a poorly chosen partition key causing a "hot partition" — DynamoDB physically splits a table's data and throughput across multiple partitions based on hashing the partition key, and each individual partition has its own throughput ceiling regardless of how much headroom exists table-wide. If one partition key value (or a small set of them) receives a disproportionate share of reads or writes, that specific partition can be throttled while the table's aggregate consumed capacity looks moderate. This mirrors sharding in a hand-rolled relational system: a shard key with skewed cardinality creates a hot shard even if the cluster overall has spare capacity, because load isn't actually distributed the way the aggregate number implies. The fix is the same in both cases — choose a key with high cardinality and access patterns spread roughly evenly across values, not just a key that's technically unique.
Why is it considered a mistake to place a database directly in a public subnet, even if its security group only allows connections from the application servers?
Defense in depth: a security group is a single layer of control, and relying on it alone means a database's actual protection depends entirely on that one configuration never being loosely set — a wildcard rule added temporarily for debugging and forgotten, an overly broad CIDR range, or a future engineer widening the rule without realizing the implication. Placing the database in a private subnet with no route to an internet gateway removes the network path entirely, so even a misconfigured security group cannot expose the database to the public internet, because there is no way to reach it from outside the VPC in the first place. This is the same reasoning behind least-privilege IAM policies: don't rely on a single access-control layer being perfectly maintained forever when a structural constraint can make an entire class of mistake impossible.
What's the actual difference between a security group and a network ACL, beyond "one is stateful and one isn't" — why does that distinction matter mechanically?
Statefulness determines whether the return leg of a connection needs its own explicit rule. A security group tracks the state of a connection: if you allow an inbound request on port 443, the corresponding outbound response is automatically permitted without any outbound rule at all, because the security group recognizes it as part of an already-permitted flow. A NACL has no such memory — it evaluates every packet against its inbound and outbound rule lists independently, so allowing inbound traffic on 443 does nothing for the response traffic; you also need an outbound rule allowing traffic on the client's ephemeral port range. This means the two layers are not redundant copies of the same idea — they operate on genuinely different semantics — and debugging a "connection refused" or a silently dropped connection sometimes requires checking both, because a NACL misconfiguration can break a data flow that looks entirely correct at the security-group layer.
Given a workload description, how would you reason through which compute tier (EC2, ECS/EKS, Lambda) fits?
Start with three questions rather than jumping to a default. First, how long does a single unit of work take, and is there a hard ceiling — anything approaching or exceeding 15 minutes, or requiring a persistent connection/in-memory state across invocations, rules out Lambda structurally. Second, how variable is the load — steady, well-understood traffic favors EC2 or ECS because you can right-size capacity and amortize a warm process's startup cost across many requests, while bursty, infrequent, or unpredictable traffic favors Lambda because you avoid paying for idle capacity between events. Third, how much do you need control over the runtime itself — a specific kernel module, licensed software, or unusual resource isolation needs pushes toward EC2, while a standard containerized service with no such requirement is a good fit for ECS/EKS (particularly on Fargate, to avoid host management even in the container tier). None of these tiers is strictly "better" — they represent different points on the same control-versus-overhead trade-off, and the right answer depends on the shape of the specific workload's traffic and runtime needs.
Why did S3's move to strong read-after-write consistency matter, and what does it teach about consistency in replicated systems generally?
Before this change, S3 replicated objects across multiple internal storage nodes for durability, and a read immediately following a write to an existing key could be served by a replica that hadn't yet received the update — producing a stale read or even a transient 404. Applications had to work around this with patterns like retrying reads with backoff or avoiding immediate read-after-overwrite entirely. AWS's engineering change made every read reflect the latest completed write across all replicas immediately, eliminating that workaround's necessity. The broader lesson is that consistency is never free in a replicated system — someone has to pay for it, either as write latency (waiting for replication to complete before acknowledging the write) or as engineering complexity in the client (handling staleness explicitly). S3's history is a concrete instance of a system moving that cost from "every client must handle staleness" to "the write path absorbs slightly more coordination cost," which is the same trade-off that shows up whenever you choose between synchronous and asynchronous replication in any database.
Why is an EBS volume the wrong choice for data that needs to be accessed by multiple EC2 instances at once, and what would actually break if you tried?
EBS presents a raw block device to a single instance, and the filesystem built on top of it (ext4, XFS, etc.) assumes it has exclusive ownership of that device's metadata — inode tables, free-space bitmaps, journal state. If two instances mounted the same volume as a normal filesystem simultaneously, each would maintain its own in-memory view of that metadata and write changes without knowledge of the other's changes, leading to filesystem corruption: overwritten inodes, files that appear in one instance's directory listing but not the other's, or a corrupted journal after a crash. This is a locking and cache-coherency problem, not a permissions problem — allowing the attachment doesn't solve it. EFS is built to solve exactly this by implementing NFS locking and coherency protocols so multiple clients can safely see a consistent view of the same files concurrently, which is the actual capability multi-instance access requires.
