Why this matters

Every distributed-systems concept you've studied — sharding, load balancing, health checks, replication, queuing, caching — exists inside AWS as an actual named product with actual defaults, quotas, and failure modes, and those defaults quietly become part of your system's behavior whether you chose them deliberately or not. Not knowing that a default Lambda timeout is 3 seconds, that a DynamoDB table without a well-distributed partition key will silently throttle, that an SQS message can be delivered more than once, or that a database sitting in a public subnet is one misconfigured security group away from being internet-facing, is exactly the kind of gap that turns into a 2am incident. Picture ShopSphere's actual production footprint — a storefront serving product images and category pages to millions of shoppers, an orders database that must never lose a row, a checkout flow that publishes events instead of making synchronous calls so a slow notification-service can't take down order placement — and nearly every architectural decision maps onto naming the right AWS building block for the job. This page builds that mental model so that reading a production architecture diagram, or drawing one for ShopSphere, becomes an exercise in recognizing trade-offs you already understand.

1. The AWS Service Landscape: Five Categories, One Question Each

AWS has hundreds of named services, which makes the catalog feel unbounded until you notice that almost every service you'll actually touch as a backend engineer answers one of five questions: where does code run, how do bytes get from one place to another, where does data live at rest, how do services hand work to each other without calling one another directly, and who's allowed to do what. The rest of this page is organized around exactly those five categories — the tree below is the map; each numbered section that follows is one branch of it, worked out in ShopSphere terms.

2. The Compute Spectrum: EC2, Containers, and Lambda

Every cloud provider offers compute along a spectrum defined by one variable: how much of the stack you manage versus how much the provider manages. Moving up the spectrum trades control for reduced operational burden, and the "right" tier for a workload is almost always determined by how predictable its traffic and runtime characteristics are.

EC2 — virtual machines, maximum control

An EC2 instance is a virtual machine running on physical hardware in an AWS availability zone. You choose the instance family (compute-optimized c-series, memory-optimized r-series, general purpose m-series, burstable t-series), the operating system, and you are responsible for everything above the hypervisor: OS patching, runtime installation, process supervision, log rotation, security hardening. This is the same responsibility model as running your own physical server, minus the physical server. ShopSphere's order-service and payment-service — long-running Spring Boot processes holding database connection pools open around the clock — are a natural fit here: you get full control over the process lifecycle, useful when you need a specific JVM version or fine-grained control over resource isolation, but you also own every 2am page caused by disk filling up on the instance running order-service or a kernel CVE needing a patch.

ECS / EKS — container orchestration, the middle ground

Elastic Container Service (ECS) and Elastic Kubernetes Service (EKS) sit in the middle: you package your application as a container image, and the orchestrator handles placement, restart-on-crash, and rolling deployment across a fleet of underlying compute. This is the same problem docker-kubernetes covers in provider-neutral terms — pods, replica sets, service discovery — and EKS is literally upstream Kubernetes, so everything you know about deployments, liveness probes, and horizontal pod autoscaling transfers directly. ECS is AWS's own simpler orchestrator with a smaller conceptual surface (tasks and services instead of pods and deployments) at the cost of being AWS-specific. In practice, ShopSphere would run each of its microservices — order-service, inventory-service, payment-service, notification-service, catalog-service — as its own ECS service or Kubernetes deployment, each independently scaled and deployed.

Within both, you additionally choose a launch type: EC2 launch type means you still manage the underlying instances the containers run on (you own capacity planning and patching of the host), while Fargate removes the host entirely — you specify CPU and memory for the task and AWS runs it on infrastructure you never see. Fargate is effectively "serverless containers," trading some cost efficiency and startup latency for eliminating host management altogether — a reasonable default for a service like notification-service, whose load is bursty and doesn't justify someone owning host patching for it specifically.

Lambda — serverless functions, minimum operational overhead

Lambda runs a single function in response to an event (an HTTP request via API Gateway, an S3 object creation, an SQS message, a scheduled cron) and you are billed per invocation and per millisecond of execution time. There is no server to patch, no fleet to size — AWS provisions an execution environment on demand. A concrete ShopSphere fit: a Lambda triggered by an S3 ObjectCreated event every time a Seller uploads a new product image, which resizes it into thumbnail/medium/full-size variants and writes them back to a different S3 prefix — a short-lived, bursty, event-shaped task with no need for a permanently-running server. This is the extreme end of "least operational overhead," but it comes with two structural constraints worth internalizing rather than memorizing:

  • Cold starts. When no warm execution environment exists for your function, AWS must provision one: download your deployment package, initialize the runtime, run your static initializers. For a JVM-based Lambda (say, a Java function validating and normalizing an uploaded product image's metadata) this can add hundreds of milliseconds to several seconds before your handler code even runs, because JVM class loading and JIT warm-up are exactly as slow here as they are in any other JVM process — Lambda doesn't make the JVM start faster, it just controls how often you pay that cost. Provisioned Concurrency exists specifically to pre-warm a pool of environments and eliminate this for latency-sensitive paths, at the cost of paying for idle capacity, which partially defeats the "pay only for what you use" premise.
  • Execution time limits. A Lambda invocation is capped at 15 minutes. This isn't an arbitrary quota — it reflects the model's assumption that a function is a short-lived reaction to an event, not a long-running process. Anything that needs to hold state across a long computation, maintain a persistent connection (a database connection pool, a WebSocket), or run indefinitely (a queue consumer polling continuously, like inventory-service draining an SQS queue of OrderPlaced events all day) is structurally the wrong shape for Lambda and belongs on ECS/EKS or EC2 instead.
Choosing a tier: ask about variance, not just scale

The deciding question is rarely "how much traffic" — it's "how predictable and how bursty is the traffic, and how long does one unit of work take?" A steady, high-volume workload with well-understood peak load — ShopSphere's order-service handling checkout traffic all day — is usually cheaper and more predictable on EC2 or ECS, because you can right-size capacity and amortize the cost of a warm process across many requests. A spiky, unpredictable, or infrequent workload (a product-image thumbnail generator invoked only when a Seller uploads something, a nightly batch job reconciling Payment records, a webhook handler for a payment provider's callback) is a natural fit for Lambda, because you pay nothing between invocations and don't need to provision for a peak that rarely arrives. Long-running or stateful processes — anything holding open connections, in-memory caches, or requiring more than 15 minutes — rule Lambda out regardless of traffic shape.

3. Core Networking: VPC, Subnets, and Firewalls

VPC — your isolated network

A Virtual Private Cloud (VPC) is a logically isolated slice of the AWS network, defined by a CIDR block (for example 10.0.0.0/16), inside which you place every resource you launch. Nothing inside your VPC is reachable from outside it, and nothing outside is reachable from inside, unless you explicitly wire up a path — an internet gateway, a NAT gateway, a peering connection, a VPN. This "deny by default at the network boundary" posture is the cloud equivalent of putting your servers behind a firewall at a physical data center: isolation is the starting state, and every route in or out is a deliberate decision you can audit. ShopSphere would run one VPC per environment (staging, production), with every microservice, database, and cache living inside it.

Public vs. private subnets

A VPC is subdivided into subnets, each pinned to a single availability zone. A subnet is "public" if its route table sends 0.0.0.0/0 traffic to an internet gateway — meaning resources in it can have a public IP and be reached directly from the internet. A subnet is "private" if it has no such route; its resources can only be reached from within the VPC (or reach the internet outward through a NAT gateway sitting in a public subnet, for things like downloading OS patches, without being reachable inbound).

Databases, application servers holding sensitive state, and internal caches belong in private subnets as a default posture, not an afterthought. For ShopSphere, that means the RDS orders database, the ElastiCache product-cache cluster, and the ECS tasks running order-service/inventory-service/payment-service all sit in private subnets with no direct internet route — the reasoning is the same principle behind least-privilege access generally: a resource that has no route to or from the public internet cannot be the entry point of an internet-originated attack, no matter what software bug or misconfigured credential might otherwise expose it. The public-facing layer — ShopSphere's Application Load Balancer fronting the storefront API, or CloudFront in front of static assets — is the only thing that needs a direct internet route, and it acts as the sole choke point you have to harden and monitor.

Security groups vs. NACLs

AWS gives you two layers of firewall, and conflating them is a common source of "why can't this connection get through" debugging sessions.

Statefulness is the detail that bites people

Because security groups are stateful, you typically only write inbound rules and never think about outbound rules for response traffic — which is correct, but it means people forget NACLs don't work that way. If you add a NACL rule allowing inbound traffic on a port but forget the corresponding outbound rule for ephemeral ports (typically 1024–65535, where the client side of a TCP connection lives), responses get silently dropped at the subnet boundary even though the security group looks completely correct. This is a classic case where the connection is allowed in but the reply can't get out, and nothing about the security group configuration will tell you that — you have to know NACLs are a second, independent, stateless layer to think to check them.

4. Storage: Choosing by Access Pattern, Not by Habit

The right storage service is determined by one question: does this data need to be block-level (mounted as a raw device to one machine), shared across many machines as files, or addressed as opaque objects over HTTP? These are genuinely different access patterns, not just marketing tiers of the same thing.

EBS — block storage, one instance at a time

An EBS volume is a virtual hard drive: a block device that attaches to exactly one EC2 instance (with rare multi-attach exceptions for specific clustered filesystems) and persists independently of the instance's lifecycle — you can stop the instance, and the volume's data survives, then reattach it or attach it to a different instance later. This is the right choice for anything that needs low-latency, POSIX-filesystem-backed storage local to a single compute node — for ShopSphere, that's the data directory underneath a self-managed database, or a service's local write-ahead log or scratch space. It is not shareable across instances simultaneously in the general case, which is precisely the constraint that motivates EFS.

EFS — shared network file storage

EFS is a managed NFS filesystem that multiple EC2 instances (or containers) can mount concurrently and see the same consistent view of files. Reach for it when several compute nodes genuinely need to read and write the same files — for example, a fleet of notification-service workers sharing a directory of generated PDF invoices before they're uploaded to S3, or a batch of catalog-import worker nodes sharing intermediate output while bulk-loading a Seller's product feed. The trade-off versus EBS is latency (network-attached, not local block device) and cost per GB, in exchange for the sharing property EBS structurally cannot provide.

S3 — object storage and its consistency history

S3 stores unstructured blobs addressed by key within a bucket, accessed over HTTP(S), with no filesystem semantics (no partial-file edits, no directory locking) and effectively unlimited scale. For ShopSphere, S3 is where every Product's images live — a Seller uploads a photo when listing a product, the browser/backend PUTs it to a key like products/{productId}/main.jpg in a bucket such as shopsphere-product-images, and that key (or, more precisely, a CloudFront URL wrapping it — see section 5) is what the storefront's catalog pages actually reference when rendering a product card. S3 is not a filesystem and not a database; it is closer to a distributed, replicated key-value store for large binary values, which is also why it's the substrate underneath many managed services (EBS snapshots, RDS backups, and Lambda deployment packages all ultimately live on S3-like storage) — and it's also naturally where ShopSphere would land its RDS automated backups and its data-lake exports of historical Order records for analytics.

A detail worth understanding precisely rather than glossing over: S3 originally offered eventual consistency for read-after-write on overwrite (PUT to an existing key) and delete operations — you could write a new version of an object and, for a brief window, still read the old version or a 404 from some replicas, because the write had to propagate across S3's internal replication before every read path reflected it. Concretely, this used to matter for ShopSphere: if a Seller replaced a product's main image (overwriting the same S3 key) and the storefront re-rendered that product page moments later, some requests could still see the stale image. In December 2020, AWS changed this so that S3 provides strong read-after-write consistency for all operations, on all objects, in all regions, at no extra cost — a Seller's image replace is now visible to every subsequent read immediately. This matters historically because a great deal of production code and cautionary folklore ("never immediately read a key you just wrote to S3, retry with backoff") was written against the old model, and that workaround is now unnecessary — but the underlying lesson generalizes far beyond S3: any system with replication has to make an explicit choice about the consistency window between a write landing on one replica and being visible on all of them, and that choice is a design decision with real cost, not an implementation detail you can ignore.

5. CDN, Cache, and Messaging: CloudFront, ElastiCache, SQS/SNS

These three services solve three different flavors of the same underlying problem — keeping ShopSphere fast and loosely coupled under load — and they're easy to conflate if you only know their one-line descriptions ("a CDN," "a cache," "a queue") without understanding exactly what each one removes from the request path.

CloudFront — caching the storefront at the network edge

CloudFront is AWS's Content Delivery Network (CDN): a global network of edge locations that cache content geographically close to the requester, so a shopper in Mumbai loading ShopSphere's product-listing page doesn't have to round-trip all the way to an origin server in us-east-1 for every request. Concretely, ShopSphere would put CloudFront in front of two different kinds of origin: the S3 bucket holding product images (so the same product photo isn't re-fetched from S3 on every single page view, worldwide), and the storefront's own load balancer for cacheable, mostly-static category/landing pages. A request for a product image resolves first against the nearest edge location's cache; only on a cache miss does CloudFront pull the object from the origin (S3) and cache it at that edge for subsequent requests, governed by a Time-To-Live (TTL) you configure per behavior/path pattern.

The mechanical payoff is threefold: lower latency (data travels a shorter physical distance), lower origin load (S3 and the ALB see a small fraction of the request volume that end users generate, because most requests are served from edge cache), and resilience against origin spikes (a flash sale hammering the product-listing page mostly hammers CloudFront's edge cache, not ShopSphere's own infrastructure). The cost of this is the same one every cache introduces: a cached, stale product image can be served for up to its TTL after the Seller uploads a replacement, unless you explicitly invalidate the CloudFront cache for that path on update — which is a direct instance of the cache-invalidation problem covered generically in caching-strategies.

ElastiCache — an in-memory cache in front of the database

ElastiCache is a managed in-memory data store (Redis or Memcached) that sits between your application and your database, purely to avoid re-running the same expensive read against RDS/DynamoDB over and over. For ShopSphere, the highest-traffic read by far is "fetch this Product's catalog data to render a page" — the same handful of popular products get requested constantly, especially during a flash sale, while the underlying data (price, description, stock count at a coarse level) changes relatively rarely. An ElastiCache Redis cluster in front of the orders/catalog database absorbs that read load: catalog-service checks Redis first (GET product:8841), and only on a miss does it fall through to RDS, then populates the cache for next time.

// catalog-service: cache-aside pattern in front of the RDS-backed catalog
Product getProduct(String productId) {
    String cached = redis.get("product:" + productId);
    if (cached != null) {
        return deserialize(cached);           // cache hit - no RDS round trip
    }
    Product product = productRepository.findById(productId); // cache miss - fall through to RDS
    redis.setex("product:" + productId, 300, serialize(product)); // cache for 5 minutes
    return product;
}

This is the exact same cache-aside pattern, and the exact same staleness trade-off, covered in full in caching-strategies — ElastiCache is simply AWS's managed way of running the Redis/Memcached process itself (patching, failover, replication) without you standing up and operating that cluster by hand. The mechanical reason it's fast is that ElastiCache serves entirely from memory (RAM), with no disk I/O and no query planning on the read path, which is why it can absorb read volume that would otherwise mean scaling the RDS instance itself.

SQS and SNS — decoupling services with queues instead of direct calls

Simple Queue Service (SQS) is a durable, managed message queue: a producer sends a message, SQS stores it (replicated across multiple availability zones) until a consumer polls for and processes it, then the consumer explicitly deletes the message to acknowledge completion. This is the concrete AWS implementation of the message-queue pattern covered generically wherever asynchronous, decoupled service communication comes up — the point of putting a queue between two services instead of calling one from the other directly (a synchronous REST call) is that the producer no longer needs the consumer to be up, fast, or even reachable at the moment the work is generated.

ShopSphere's checkout flow is the textbook case: when a Customer completes checkout, order-service doesn't call inventory-service, payment-service, and notification-service synchronously in a row (where any one being slow or down blocks the whole checkout). Instead, order-service publishes an OrderPlaced event and returns immediately; inventory-service and notification-service each consume that event from their own queue, independently and at their own pace.

// order-service, right after persisting the Order as CREATED
OrderPlacedEvent event = new OrderPlacedEvent(order.getId(), order.getCustomerId(), order.getItems());
sqsClient.sendMessage(new SendMessageRequest()
    .withQueueUrl(orderPlacedQueueUrl)
    .withMessageBody(toJson(event)));
// order-service returns HTTP 201 to the customer here - it does NOT wait for
// inventory-service or notification-service to actually process the event

// inventory-service, polling its own queue independently, whenever it's ready
Message msg = sqsClient.receiveMessage(inventoryQueueUrl).getMessages().get(0);
OrderPlacedEvent event = fromJson(msg.getBody());
reserveInventory(event.getOrderId(), event.getItems());   // -> publishes InventoryReserved next
sqsClient.deleteMessage(inventoryQueueUrl, msg.getReceiptHandle()); // ack: only after successful processing

Two mechanical properties of SQS are easy to get wrong if you assume it behaves like an in-process list: messages are at-least-once delivered (a consumer can receive the same message more than once — e.g., if it crashes after processing but before calling deleteMessage — so consumers must be idempotent, exactly the concern covered in depth in payment-systems-idempotency, which matters enormously here since a duplicate delivery of an OrderPlaced event must not double-reserve inventory or double-charge a payment), and standard queues do not guarantee strict ordering (a FIFO queue type exists specifically for cases — like a sequence of inventory adjustments for the same product that must apply in order — where ordering correctness matters more than the higher throughput standard queues offer).

SNS (Simple Notification Service) solves a related but different problem: fan-out. Where SQS is one queue with one (or a competing pool of) consumer(s) pulling from it, SNS is a pub/sub topic — a single published message is pushed to every subscriber, which is commonly an SQS queue per subscriber. ShopSphere's OrderPlaced event is exactly this shape in a fuller design: publish once to an SNS topic, and let inventory-service, notification-service, and an analytics pipeline each have their own SQS queue subscribed to that same topic — one publish, three independent consumers, none of which need to know the others exist.

SNS Topic: order-placed-topic
  ├── SQS queue: inventory-service's own queue   (reserve stock)
  ├── SQS queue: notification-service's own queue (send confirmation email)
  └── SQS queue: analytics pipeline's own queue   (record for reporting)
  // order-service publishes ONE message to the topic; SNS fans it out to all three queues
Queues buy you resilience to a slow or down consumer, not correctness for free

The moment you introduce a queue, you've traded synchronous, immediately-consistent behavior ("if checkout returned success, inventory has definitely been reserved by now") for eventual, decoupled behavior ("checkout succeeded, and inventory reservation will happen — soon, probably in milliseconds, but not provably before the HTTP response was sent"). This is a deliberate, worthwhile trade for resilience and throughput — a flash sale spike hammering checkout no longer means order-service falls over waiting on inventory-service — but it does mean the system now has to reason explicitly about what happens if inventory-service is behind by a few seconds (does the Customer see "order confirmed" before stock is actually reserved?) or if a message is processed twice (does reserveInventory need to be idempotent?). None of this is free just because SQS is "managed" — the managed part is durability and delivery, not the business-level correctness of what your consumers do with each message.

6. Managed Databases: RDS and DynamoDB

RDS — what "managed relational database" actually removes from your plate

RDS runs a standard relational engine (PostgreSQL, MySQL, MariaDB, or others) but takes over the operational layer that traditionally consumes real engineering time: automated backups and point-in-time recovery, minor-version patching, storage auto-scaling, and — critically — Multi-AZ failover, where a synchronously replicated standby in a second availability zone can be promoted automatically if the primary fails, with the connection endpoint staying the same so applications don't need reconfiguration. ShopSphere's orders database — the system of record for Order, OrderItem, Payment, and Customer rows, where losing data or serving stale reads on a financial transaction is not an acceptable failure mode — is exactly the workload RDS Multi-AZ exists for: if the primary instance backing order-service's database dies mid-flash-sale, AWS promotes the standby automatically, and order-service reconnects to the same endpoint without a config change or a human paged at 2am to fail it over by hand. None of this changes the relational data model or query semantics you already understand; it changes who gets paged when a disk fills up or a patch needs applying. Self-hosting the same engine on EC2 is entirely possible and sometimes justified (specific extensions, exact version pinning, cost at very large scale) but means you own writing and testing that failover logic yourself.

DynamoDB — partition keys and the scaling model

DynamoDB is a managed NoSQL key-value/document store where every item lives in a partition determined by hashing the item's partition key, and DynamoDB distributes partitions across many physical nodes to scale throughput horizontally. This is the exact same idea covered in database-architecture as sharding — DynamoDB simply performs it for you, transparently, instead of you sharding a relational database by hand across multiple hosts. A plausible ShopSphere fit for DynamoDB rather than RDS: a CartItem table (pre-checkout, high write volume, simple key-value access by customerId, no need for complex joins) or an Inventory reservation counter table under extreme flash-sale write concurrency.

The practical consequence is that your partition key choice determines your scaling ceiling. If a partition key has low cardinality or highly skewed access — imagine partitioning ShopSphere's Inventory table by warehouseId when one regional warehouse handles most order volume, or by orderStatus, a field with only a few possible values — most requests land on the same one or few physical partitions, and you hit that partition's throughput limit long before you hit any table-wide limit. The classic symptom is ProvisionedThroughputExceededException or throttling on a table that looks, in aggregate, nowhere near capacity — a flash sale spike hammering checkout for a handful of hot products would reproduce exactly this if Inventory were partitioned by something coarse like warehouseId instead of by productId. Choosing a high-cardinality, access-pattern-uniform partition key (productId, a customerId, a UUID) is the DynamoDB equivalent of choosing a good shard key in a hand-rolled sharded relational system, and it's a decision made at table-design time that's expensive to change later, exactly like a sharding key decision.

The general question: what does "managed" buy you?

Across RDS, DynamoDB, and every other managed service, the pattern is identical: the provider takes ownership of the operational tasks that don't differentiate your product — failover orchestration, patch management, replication topology, hardware replacement — while you keep ownership of the tasks that do: data modeling, schema/key design, query patterns, capacity planning inputs. Self-hosting is not "wrong," but it means explicitly signing up to own the operational half as well, and that trade-off should be a deliberate choice weighed against your team's actual operational capacity, not a default.

7. IAM: Identity, Roles, and Least Privilege

Identity and Access Management (IAM) answers two separate questions that are easy to conflate: who or what is making this request (authentication) and what are they allowed to do (authorization). IAM has three core building blocks:

  • Users represent a long-lived human or application identity with its own credentials (password, access keys).
  • Roles represent a set of permissions that can be temporarily assumed by a trusted principal — a human, an application, or (critically) an AWS compute resource itself — producing short-lived credentials that expire automatically.
  • Policies are JSON documents attached to users, roles, or resources that explicitly enumerate allowed (or denied) actions on specific resources, e.g. s3:GetObject on arn:aws:s3:::my-bucket/*.

The principle of least privilege means granting exactly the permissions a principal needs to do its job and nothing more — not "read/write access to everything" because it's convenient, but "read access to this one bucket prefix" because that's what the code actually does. The value of this isn't abstract hygiene: it bounds the blast radius when something goes wrong. If an application's credentials leak — through a logged stack trace, a misconfigured public repository, a compromised dependency — the damage is limited to whatever that narrow policy permits, rather than to your entire account.

Why an instance role beats an embedded access key

Attaching an IAM role to an EC2 instance, ECS task, or Lambda function is preferred over embedding a long-lived access key/secret pair in configuration or environment variables for a specific mechanical reason: a role's credentials are issued automatically to the resource by AWS's metadata service, rotated automatically behind the scenes, and never exist as a static string anyone could accidentally commit to a repository, print in a log line, or leave in a config file that outlives the employee who wrote it. A long-lived access key, by contrast, is a durable secret with no expiry by default — once it leaks, it's valid until someone notices and manually revokes it, which in practice can be months. This is the same "credentials as short-lived, narrowly-scoped tokens rather than durable shared secrets" pattern that shows up in OAuth access tokens and Kubernetes service account tokens — it's a general security pattern, not an AWS-specific quirk.

8. Auto Scaling Groups and Load Balancers

Horizontal scaling — adding more instances rather than making one instance bigger — is the concept covered generically in hld-basics-scaling; AWS's concrete implementation of it is the pairing of an Auto Scaling Group (ASG) with an Elastic Load Balancer (ELB).

An ASG maintains a fleet of EC2 instances (or, indirectly, ECS tasks via Service Auto Scaling) between a minimum and maximum count, launching new instances from a template when a scaling policy's trigger fires — commonly average CPU utilization crossing a threshold, a custom CloudWatch metric like queue depth (ShopSphere might scale inventory-service's ECS task count based on the SQS ApproximateNumberOfMessagesVisible metric for its OrderPlaced queue — more backlog, more consumer tasks), or a scheduled action anticipating a known traffic pattern like an announced flash sale. Crucially, the ASG also performs the inverse: it terminates instances when demand drops, which is the mechanism that actually realizes the cost benefit of elastic infrastructure — capacity that shrinks back down instead of a fleet sized permanently for peak load.

A Load Balancer (an Application Load Balancer for HTTP/HTTPS traffic, or a Network Load Balancer for raw TCP/UDP at very high throughput or when a static IP is required) sits in front of the ASG's instances and distributes incoming requests across whichever instances are currently healthy — for ShopSphere, an ALB in front of the ECS tasks running order-service, checking a /health endpoint on each task. The load balancer performs periodic health checks — an HTTP request to a configured path expecting a specific status code — and stops routing traffic to any instance that fails enough consecutive checks, which is what lets an ASG replace a crashed or degraded instance without that instance ever receiving traffic it can't serve. This pairing — dynamic fleet sizing plus health-aware traffic distribution — is what makes horizontal scaling operationally real rather than theoretical: it's not enough to be able to add capacity, the system also has to detect which capacity is currently healthy and route only to that. This is exactly the property that lets a flash-sale spike hammering ShopSphere's checkout endpoint be absorbed by the ASG adding order-service tasks, with the ALB routing traffic only to the tasks that are actually up and responding.

9. Closing the Loop: Managed Services and Resilience/Observability

A theme runs through every service covered above: a meaningful fraction of what would otherwise be custom-built resilience and observability tooling comes bundled into the managed service by default. RDS Multi-AZ gives ShopSphere's orders database cross-availability-zone failover without writing failover orchestration yourself. An ALB's health checks give you the failure-detection half of a circuit breaker pattern at the infrastructure layer, before a single line of application-level resilience code runs. CloudWatch automatically collects CPU, memory (with the agent installed), request counts, and latency metrics for most of these services without instrumenting your own code — including SQS queue depth, which is precisely the signal that would tell ShopSphere's on-call engineer that inventory-service is falling behind during a flash sale before customers notice delayed order confirmations. ASGs replacing unhealthy instances is a form of automatic self-healing that, self-hosted, you'd have to build with your own supervisor process and health-check loop.

This doesn't eliminate the need for the practices in observability-production — you still need application-level tracing, structured logs, and business-level metrics that no infrastructure service can infer on your behalf — but it does mean part of the resilience and observability burden is already handled at the platform layer, and recognizing which part is the difference between duplicating effort and correctly layering your own instrumentation on top of what the platform already gives you for free.

Concepts Worth Being Able to Explain From First Principles

Why does Lambda have both a cold-start problem and a maximum execution time, and are these related?
They stem from the same underlying model but are independent mechanics. Cold start exists because Lambda has no dedicated server sitting idle waiting for your traffic — an execution environment (essentially a lightweight container plus your runtime and code) is provisioned on demand the first time it's needed, or whenever concurrency needs to increase beyond currently-warm environments, and that provisioning takes real time, especially for runtimes like the JVM that do meaningful work at class-load and JIT-warm-up time. The 15-minute execution cap is a separate, deliberate constraint reflecting Lambda's design as a reaction to discrete events rather than a long-running process host; it exists so AWS can reclaim and reuse execution environments predictably and so the billing/scheduling model stays simple. You can have a cold start with a fast function (cold start dominates total latency) or a warm function that still can't run past 15 minutes (a long batch job that needs Fargate or EC2 instead) — the two constraints solve different problems and you can hit either independently of the other.
A DynamoDB table is well within its overall provisioned/on-demand capacity but requests are still being throttled. What's the likely cause and why does aggregate capacity not protect against it?
The likely cause is a poorly chosen partition key causing a "hot partition" — DynamoDB physically splits a table's data and throughput across multiple partitions based on hashing the partition key, and each individual partition has its own throughput ceiling regardless of how much headroom exists table-wide. If one partition key value (or a small set of them) receives a disproportionate share of reads or writes, that specific partition can be throttled while the table's aggregate consumed capacity looks moderate. This mirrors sharding in a hand-rolled relational system: a shard key with skewed cardinality creates a hot shard even if the cluster overall has spare capacity, because load isn't actually distributed the way the aggregate number implies. The fix is the same in both cases — choose a key with high cardinality and access patterns spread roughly evenly across values, not just a key that's technically unique.
Why is it considered a mistake to place a database directly in a public subnet, even if its security group only allows connections from the application servers?
Defense in depth: a security group is a single layer of control, and relying on it alone means a database's actual protection depends entirely on that one configuration never being loosely set — a wildcard rule added temporarily for debugging and forgotten, an overly broad CIDR range, or a future engineer widening the rule without realizing the implication. Placing the database in a private subnet with no route to an internet gateway removes the network path entirely, so even a misconfigured security group cannot expose the database to the public internet, because there is no way to reach it from outside the VPC in the first place. This is the same reasoning behind least-privilege IAM policies: don't rely on a single access-control layer being perfectly maintained forever when a structural constraint can make an entire class of mistake impossible.
What's the actual difference between a security group and a network ACL, beyond "one is stateful and one isn't" — why does that distinction matter mechanically?
Statefulness determines whether the return leg of a connection needs its own explicit rule. A security group tracks the state of a connection: if you allow an inbound request on port 443, the corresponding outbound response is automatically permitted without any outbound rule at all, because the security group recognizes it as part of an already-permitted flow. A NACL has no such memory — it evaluates every packet against its inbound and outbound rule lists independently, so allowing inbound traffic on 443 does nothing for the response traffic; you also need an outbound rule allowing traffic on the client's ephemeral port range. This means the two layers are not redundant copies of the same idea — they operate on genuinely different semantics — and debugging a "connection refused" or a silently dropped connection sometimes requires checking both, because a NACL misconfiguration can break a data flow that looks entirely correct at the security-group layer.
Given a workload description, how would you reason through which compute tier (EC2, ECS/EKS, Lambda) fits?
Start with three questions rather than jumping to a default. First, how long does a single unit of work take, and is there a hard ceiling — anything approaching or exceeding 15 minutes, or requiring a persistent connection/in-memory state across invocations, rules out Lambda structurally. Second, how variable is the load — steady, well-understood traffic favors EC2 or ECS because you can right-size capacity and amortize a warm process's startup cost across many requests, while bursty, infrequent, or unpredictable traffic favors Lambda because you avoid paying for idle capacity between events. Third, how much do you need control over the runtime itself — a specific kernel module, licensed software, or unusual resource isolation needs pushes toward EC2, while a standard containerized service with no such requirement is a good fit for ECS/EKS (particularly on Fargate, to avoid host management even in the container tier). None of these tiers is strictly "better" — they represent different points on the same control-versus-overhead trade-off, and the right answer depends on the shape of the specific workload's traffic and runtime needs.
Why did S3's move to strong read-after-write consistency matter, and what does it teach about consistency in replicated systems generally?
Before this change, S3 replicated objects across multiple internal storage nodes for durability, and a read immediately following a write to an existing key could be served by a replica that hadn't yet received the update — producing a stale read or even a transient 404. Applications had to work around this with patterns like retrying reads with backoff or avoiding immediate read-after-overwrite entirely. AWS's engineering change made every read reflect the latest completed write across all replicas immediately, eliminating that workaround's necessity. The broader lesson is that consistency is never free in a replicated system — someone has to pay for it, either as write latency (waiting for replication to complete before acknowledging the write) or as engineering complexity in the client (handling staleness explicitly). S3's history is a concrete instance of a system moving that cost from "every client must handle staleness" to "the write path absorbs slightly more coordination cost," which is the same trade-off that shows up whenever you choose between synchronous and asynchronous replication in any database.
Why is an EBS volume the wrong choice for data that needs to be accessed by multiple EC2 instances at once, and what would actually break if you tried?
EBS presents a raw block device to a single instance, and the filesystem built on top of it (ext4, XFS, etc.) assumes it has exclusive ownership of that device's metadata — inode tables, free-space bitmaps, journal state. If two instances mounted the same volume as a normal filesystem simultaneously, each would maintain its own in-memory view of that metadata and write changes without knowledge of the other's changes, leading to filesystem corruption: overwritten inodes, files that appear in one instance's directory listing but not the other's, or a corrupted journal after a crash. This is a locking and cache-coherency problem, not a permissions problem — allowing the attachment doesn't solve it. EFS is built to solve exactly this by implementing NFS locking and coherency protocols so multiple clients can safely see a consistent view of the same files concurrently, which is the actual capability multi-instance access requires.
ShopSphere's order-service publishes an OrderPlaced message to SQS, and inventory-service ends up reserving stock for the same order twice. What went wrong, and whose responsibility was it to prevent?
Nothing went wrong at the infrastructure layer — this is SQS behaving exactly as documented. SQS gives an at-least-once delivery guarantee, not exactly-once: a message can be redelivered if, for example, inventory-service pulled the message, started processing it, but crashed or timed out before calling deleteMessage to acknowledge it — SQS has no way to know the work actually completed, so after the visibility timeout expires it makes the message available for another consumer to pick up. This is a deliberate trade-off in the queue's design, favoring "might process twice" over "might silently lose a message," because losing an OrderPlaced event would mean an order that's paid for but never fulfilled, which is a worse failure than an extra, redundant reservation attempt. The fix is not something SQS can provide for you — it's the consumer's responsibility to make reserveInventory idempotent, typically by keying on the order's id (or a dedicated idempotency key) and checking or upserting against that key before applying the reservation, so a duplicate delivery is a no-op rather than a double-reservation. This is exactly the pattern covered in full in payment-systems-idempotency, and it generalizes: any at-least-once delivery mechanism pushes the exactly-once guarantee, if you need one, onto the consumer's own logic.
ShopSphere puts CloudFront in front of its S3 product-image bucket. A Seller replaces a product's main photo, but shoppers in a different region still see the old image for several minutes. Is this a bug?
No — it's the direct, expected consequence of what a CDN is for. CloudFront's entire value proposition is serving content from an edge location physically close to the requester instead of round-tripping to the origin (S3) on every request, and it can only do that by caching a copy of the object at each edge location for some Time-To-Live window. When the Seller overwrites the S3 object, S3 itself reflects the new image immediately (strong read-after-write consistency, as covered elsewhere on this page) — but any CloudFront edge location that already cached the old image under that URL will keep serving its cached copy until that TTL expires, because CloudFront has no way to know the origin changed unless it's told. The fix is to explicitly invalidate the CloudFront cache for that specific path when a Seller updates a product image (an API call ShopSphere's catalog-service would make right after the S3 write completes), or to design around it entirely by versioning image URLs (e.g., appending the image's own content hash or an updated-at timestamp to the key), so a changed image is automatically a new URL/cache entry rather than a stale cache hit on the old one. This is the exact same cache-invalidation problem that appears in any cache-aside design, just instantiated at the CDN layer instead of the application layer.
