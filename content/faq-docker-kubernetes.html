Most Asked Interview Questions: Docker, Kubernetes & Cloud

Containers Dockerfile Pods & Deployments Liveness/Readiness Auto-Scaling Cloud Basics
Why this matters

Backend Java interviews increasingly assume you can ship and operate a service, not just write one — even a "pure Java" role will ask at least one question about how your service gets packaged into a container, deployed onto Kubernetes, and scaled in the cloud. Interviewers use this cluster of questions to check whether you understand what happens to your Spring Boot application after mvn package: how it's containerized, how it stays healthy in production, and how traffic and load get routed to it. This page covers the exact Docker, Kubernetes, and cloud/DevOps questions that come up most often, at the depth expected of a backend engineer rather than a dedicated platform engineer.

Docker Fundamentals

What is the difference between an image, a container, and a registry?
An image is a read-only, immutable template — a set of filesystem layers plus metadata (entrypoint, exposed ports, environment defaults) — built once from a Dockerfile and never modified after that. A container is a running (or stopped) instance of an image: Docker adds a thin writable layer on top of the image's read-only layers, and any files the process creates or modifies at runtime go into that writable layer, which is discarded when the container is removed. You can run many containers from the same image simultaneously — for example, three replicas of order-service's image, each an isolated running process with its own writable layer and network namespace, but all sharing the same underlying read-only image layers on disk. A registry is a storage and distribution service for images — Docker Hub, Amazon ECR (Elastic Container Registry), or a private registry — that you push a built image to with a tag (e.g. order-service:1.4.2) and pull from on any host that needs to run it, which is how the exact same tested artifact moves from a CI pipeline to staging to production without being rebuilt.
What are Dockerfile layers, and why does layer ordering affect build cache efficiency?
Each instruction in a Dockerfile — FROM, RUN, COPY, ADD — produces a new filesystem layer stacked on top of the previous one, and Docker caches each layer keyed by that instruction plus its inputs. When you rebuild an image, Docker walks the instructions from the top and reuses the cached layer for any instruction whose inputs haven't changed; the moment one instruction's input changes (a file it copies, or the command text itself), that layer and every layer after it must be rebuilt from scratch, even if nothing in those later layers actually changed. This is why ordering matters: instructions that change rarely (installing OS packages, copying a pom.xml or build.gradle and running a dependency-resolution step) should come before instructions that change on every commit (copying your actual application source and compiled classes). A common Java-specific pattern is copying only pom.xml and running mvn dependency:go-offline first, then copying the source afterward — so a source-only code change reuses the cached dependency-download layer instead of re-downloading every Maven dependency on every build. Getting this ordering wrong doesn't break correctness, it just makes every build slow, which compounds badly in a CI pipeline that rebuilds on every push.
What are multi-stage builds, and why do they reduce the final image size?
A multi-stage build uses more than one FROM instruction in a single Dockerfile, where each FROM starts a new, independent build stage, and later stages can selectively copy specific files out of earlier stages with COPY --from=<stage> — everything else from the earlier stage is discarded. For a Java service, the first stage typically uses a full JDK (Java Development Kit) image with Maven or Gradle to compile the source and produce a JAR (Java ARchive), and the second stage starts fresh from a minimal JRE (Java Runtime Environment)-only base image and copies in just the built JAR from stage one. The final image ends up containing only the runtime and the compiled artifact — none of the build tools, source code, dependency-resolution caches, or intermediate compiled classes that the build stage needed — which can shrink an image from over a gigabyte down to well under a couple hundred megabytes. Smaller images matter concretely in production: they pull faster during a Kubernetes rolling deployment or a scale-out event, and they shrink the attack surface since a compiler and build toolchain sitting in a production image is unnecessary risk with no runtime benefit.
What's the difference between a Docker volume and a bind mount, and when would you use each for persistence?
Both let a container's data survive beyond the container's own lifecycle, but they differ in who manages the storage location. A bind mount maps a specific, user-chosen path on the host filesystem directly into the container (-v /home/user/data:/app/data) — the host path exists independently of Docker, Docker has no awareness of its structure, and the container gets exactly what's already there, which makes bind mounts convenient for local development (mounting your local source directory into a container for live-reload) but fragile in production, since it hard-codes a host-specific path and depends on that exact host having the right directory and permissions. A volume (docker volume create, or the shorthand -v myvolume:/app/data) is storage that Docker itself creates and manages, typically under /var/lib/docker/volumes, with no host path the application needs to know or care about — Docker handles the backing storage, and volumes can be backed by pluggable drivers for network or cloud storage. The practical rule: use bind mounts for local development convenience, and use named volumes (or, in Kubernetes, a PersistentVolume backed by cloud block storage) for anything that needs to persist reliably in a real deployment, such as a database container's data directory that must survive a container restart or replacement.
Why are containers considered more lightweight than virtual machines?
A virtual machine virtualizes hardware: a hypervisor runs multiple complete guest operating systems, each with its own full kernel, on top of the host, which means every VM carries the memory and CPU overhead of an entire OS boot and typically takes tens of seconds to minutes to start. A container, by contrast, shares the host machine's single kernel — it doesn't boot an OS at all, it's just an isolated process (or group of processes) on that shared kernel, which is why containers typically start in a fraction of a second and carry far less memory/CPU overhead per instance. The isolation that makes a container feel like its own machine — its own filesystem view, process tree, network interfaces, and resource limits — comes from two Linux kernel features rather than from virtualizing hardware: namespaces (which give a process its own isolated view of resources — PID namespace for process IDs, network namespace for network interfaces, mount namespace for the filesystem, and so on, so a container "sees" only its own processes and files even though it's really sharing the host kernel) and cgroups, or control groups (which enforce and account for resource limits — how much CPU, memory, and I/O a container or group of processes is allowed to consume — preventing one container from starving others on the same host). This is also why containers are less isolated than VMs in a security sense: a kernel-level vulnerability can potentially be exploited to escape a container's namespace isolation and affect the shared host, whereas a VM's guest kernel is a genuinely separate kernel from the host's.
Why can a containerized Java service get OOMKilled even when the JVM's heap settings look safe?
A container's memory limit is enforced by a cgroup (control group), and the cgroup accounts for the total memory used by every process and every kind of allocation inside the container — heap, thread stacks, metaspace, the JIT (Just-In-Time) compiler's code cache, direct/native byte buffers, and the JVM's own native bookkeeping — not just what -Xmx governs. Older JVMs (pre-JDK 10) weren't cgroup-aware and would size default heap fractions off the host's total physical memory, completely ignoring a much smaller container limit; modern JVMs (JDK 10+, with -XX:+UseContainerSupport on by default) correctly read the cgroup limit, but if -Xmx is still set close to that limit, there's no headroom left for the non-heap memory listed above. When the container's total usage crosses the cgroup limit, the kernel's OOM (Out-Of-Memory) killer terminates the process from outside the JVM — this shows up as a Kubernetes Pod status of OOMKilled and container exit code 137, with no Java-level OutOfMemoryError or heap dump, because the JVM itself never got a chance to detect or log anything. The practical fix is to always leave meaningful headroom between -Xmx and the container's memory limit — commonly capping heap at roughly 50-70% of the limit — so metaspace, thread stacks, and native buffers have room to fit inside the same cgroup.
What's the difference between CMD and ENTRYPOINT in a Dockerfile?
Both specify what runs when a container starts, but they compose differently. ENTRYPOINT sets the fixed executable that always runs — it's meant to be the container's "main command" and is hard to override without explicitly passing --entrypoint on docker run. CMD supplies default arguments, which can be overridden simply by appending arguments after the image name on the command line (docker run order-service --debug replaces the default CMD with --debug). The common production pattern combines both: ENTRYPOINT ["java", "-jar", "app.jar"] with CMD ["--spring.profiles.active=default"] as the default argument, so the image always runs the same JAR (Java ARchive) via the fixed entrypoint, but anyone starting the container can override just the trailing arguments — for example swapping the active Spring profile — without needing to know or repeat the full launch command. If only CMD is set with no ENTRYPOINT, the entire command is replaceable, which is fine for a generic base image but usually wrong for an application image where you want the runtime invocation locked down.
How does Docker networking work, and what's the difference between bridge and host mode?
By default, Docker creates a private virtual network called the bridge network on each host; every container gets its own network namespace and a virtual Ethernet interface attached to that bridge, giving it an internal IP address that's NAT'd (Network Address Translated) to the host for outbound traffic and reachable from other containers on the same bridge network by container name (Docker runs an embedded DNS resolver for this). Publishing a port (-p 8080:8080) creates an explicit forwarding rule from a host port to a container port — without it, nothing outside the host can reach the container directly. Host mode skips network namespace isolation entirely and lets the container share the host's network stack directly, so a process listening on port 8080 inside the container is literally listening on port 8080 of the host, with no NAT translation and no per-container IP — this removes a layer of isolation and gives up the ability to run two containers on the same port on one host, but avoids a small amount of NAT overhead, which occasionally matters for very latency- or throughput-sensitive workloads. In a Kubernetes cluster this manual Docker networking model is replaced entirely by the cluster's pod network (a CNI, or Container Network Interface, plugin) and Services, so this question is mostly relevant to plain Docker/Compose usage and to understanding what Kubernetes is abstracting away.
Why shouldn't you rely on Docker's own restart policies for production availability?
Docker supports a --restart policy (no, on-failure, always, unless-stopped) that tells the local Docker daemon to restart a container if it exits, but that's the entire scope of what it does — it only reacts to a container dying on a single host, with no concept of desired replica count, no ability to move a workload to a different, healthier host if the current one goes down, no load balancing across replicas, and no rollout/rollback mechanism for deploying a new version. This is precisely the gap Kubernetes fills: a Deployment continuously reconciles toward a desired replica count across the whole cluster, reschedules Pods onto other nodes if a node fails entirely, integrates with Services for load balancing, and understands versioned rollouts. In an interview, framing it this way is the useful signal: Docker's restart policy is single-host, single-container self-healing, while an orchestrator like Kubernetes is cluster-wide, fleet-level self-healing — which is exactly why nobody runs bare docker run --restart=always containers as a real production deployment strategy for anything that needs to survive a host failure.

Kubernetes Fundamentals

What is a Pod, and why is it the smallest deployable unit in Kubernetes rather than a container?
A Pod is the smallest deployable unit Kubernetes schedules and manages — it wraps one or more containers that are guaranteed to be co-located on the same node and share certain resources: a single IP address and network namespace (so containers in the same Pod reach each other over localhost), and optionally shared storage volumes. Most Pods run exactly one application container, but the "one or more" matters for the sidecar pattern — a second container in the same Pod that supports the main one, such as a log-shipping agent that tails order-service's log files, or a service-mesh proxy that intercepts all inbound/outbound traffic for mutual TLS (Transport Layer Security) and traffic policy. Kubernetes doesn't schedule bare containers directly because a Pod also carries the scheduling-relevant metadata a single container doesn't: shared network identity, restart policy, and the guarantee that tightly-coupled containers are always co-located rather than potentially landing on different nodes. Pods are also ephemeral and disposable by design — a Pod that dies is not resurrected, a replacement Pod with a new identity and new IP is created instead — which is exactly why you don't manage Pods directly in production and instead manage them through a Deployment.
What's the difference between a Deployment and a ReplicaSet?
A ReplicaSet has one job: ensure a specified number of identical Pod replicas, matching a label selector, are running at all times — if a Pod crashes or is deleted, the ReplicaSet's controller notices the actual count no longer matches the desired count and creates a replacement. A Deployment sits one level above a ReplicaSet and manages it, adding the capability a ReplicaSet alone doesn't have: declarative, versioned rollout of changes. When you update a Deployment's Pod template — say, bumping order-service's image tag from 1.4.2 to 1.4.3 — the Deployment creates a brand-new ReplicaSet for the new version and gradually scales it up while scaling the old ReplicaSet down, which is what implements a rolling update, and it retains old ReplicaSets (scaled to zero) so you can roll back to a previous revision with kubectl rollout undo. In practice you essentially never create a bare ReplicaSet directly in production; you create a Deployment, and Kubernetes manages the ReplicaSet(s) underneath it for you.
What are the Service types — ClusterIP, NodePort, and LoadBalancer — and what does each expose?
A Kubernetes Service gives a stable network identity (a fixed virtual IP and DNS name) in front of a set of Pods matched by a label selector, so callers never need to track individual Pod IPs, which change every time a Pod is replaced. ClusterIP (the default) allocates an IP reachable only from inside the cluster — this is the right type for internal service-to-service traffic, like inventory-service calling payment-service, where nothing outside the cluster ever needs to reach it directly. NodePort builds on ClusterIP and additionally opens a specific port (from a fixed range, typically 30000-32767) on every node in the cluster, so external traffic can reach the service by hitting any node's IP on that port — this is mostly used for development/testing or as a low-level building block, since it's clunky for real external traffic (clients need to know a node IP and non-standard port). LoadBalancer builds on NodePort and additionally asks the cloud provider to provision an actual external load balancer (an AWS ELB/ALB, for example) that routes to the NodePort across all nodes, giving external clients one stable public IP or hostname — this is the standard way to expose a service to the internet from a cloud-hosted cluster, such as exposing catalog-service's public product-browsing API.
What's the difference between an Ingress and a Service?
A Service load-balances traffic to a set of Pods and gives them one stable network identity, but a LoadBalancer Service provisions one external load balancer per Service — expensive and unwieldy if you have a dozen microservices each needing external HTTP access. An Ingress is a higher-level HTTP/HTTPS (HyperText Transfer Protocol / HTTP Secure) routing layer that sits in front of multiple Services and routes based on request content — hostname and URL path — to the right one: a single Ingress resource can route shopsphere.com/orders to order-service's ClusterIP Service and shopsphere.com/catalog to catalog-service's, all through one external entry point (one load balancer, one public IP/certificate). An Ingress resource itself is just routing rules; it requires an Ingress controller (such as NGINX Ingress Controller or an AWS ALB Ingress Controller) actually running in the cluster to read those rules and do the real proxying. The practical distinction interviewers want: a Service provides stable internal addressing and load balancing to a set of Pods, while Ingress provides smart, content-based external HTTP routing across many Services through a single consolidated entry point, along with things like TLS termination and path-based rewriting that Services alone don't offer.
What's the difference between a ConfigMap and a Secret?
Both let you externalize configuration from a container image so the same image can run in different environments without being rebuilt, and both can be injected into a Pod as environment variables or mounted as files. A ConfigMap is meant for non-sensitive configuration — a Spring profile name, a feature-flag value, a Kafka topic name, or an external service's base URL for notification-service to call. A Secret is meant for sensitive values — database passwords, API keys, TLS certificates — and is stored base64-encoded rather than plaintext by default; it's important to know in an interview that base64 is encoding, not encryption, so a Secret is not cryptographically protected at rest unless you additionally enable encryption at rest for the Kubernetes cluster's etcd datastore (where both ConfigMaps and Secrets are ultimately stored) or use an external secrets manager like AWS Secrets Manager or HashiCorp Vault integrated via a CSI (Container Storage Interface) driver. The functional API surface (create, mount as a volume, inject as env vars) is nearly identical between the two — the distinction is entirely about intent and about the additional access-control and handling conventions Kubernetes applies to the Secret object type.
What's the difference between a liveness probe and a readiness probe, and what happens when each one fails?
Both probes periodically check container health by hitting an HTTP endpoint, running a command, or opening a TCP socket, but they answer different questions and trigger different responses. A liveness probe asks "is this container still alive and functioning, or is it stuck?" — if it fails (past a configured failure threshold), the kubelet on that node kills and restarts the container, which is the right response to a genuinely wedged process, such as order-service deadlocked and no longer processing any requests. A readiness probe asks "is this container currently able to accept traffic?" — if it fails, Kubernetes does not restart the container; instead, it removes that Pod's IP from the Service's list of routable endpoints, so no new traffic is sent to it, while leaving the container running to recover on its own. The readiness probe is what protects against sending live traffic to a Pod that's still warming up (loading a cache, establishing a database connection pool at startup) or temporarily overloaded and shedding load — restarting it in that situation (what a liveness probe would do) would be actively counterproductive, since restarting resets any warm-up progress and just repeats the problem. A common production mistake is pointing both probes at the same trivial endpoint, or setting a liveness probe too aggressively so a temporarily slow (but not actually broken) service gets killed and restarted in a loop, worsening the exact overload it was already struggling with.
What's the difference between resource requests and limits on a container, and what happens if you exceed each?
Both are set per-container under resources.requests and resources.limits for CPU and memory, but they're used by two completely different mechanisms. A request is what the Kubernetes scheduler uses to decide where a Pod can be placed — it will only schedule order-service's Pod onto a node that has at least that much CPU/memory still unreserved (summed across the requests of every Pod already on that node); it's a scheduling-time guarantee, not something enforced while the container is running. A limit is what actually gets enforced at runtime via cgroups (control groups): exceeding a memory limit gets the container killed by the kernel's OOM (Out-Of-Memory) killer immediately, regardless of how much idle memory the node otherwise has, while exceeding a CPU limit doesn't kill anything — the kernel's CPU bandwidth controller instead throttles the container, denying it further CPU time for the rest of that scheduling period, which shows up as increased latency rather than a crash. A Pod with requests set well below its limits can burst into a node's spare capacity, but that also makes it one of the first candidates the kubelet's eviction manager sacrifices if the node comes under real memory pressure — so setting accurate requests isn't just about scheduling, it also determines which Pods get evicted first under contention.
What is the Horizontal Pod Autoscaler (HPA), and how does it decide when to scale?
The Horizontal Pod Autoscaler (HPA) automatically adjusts the number of Pod replicas in a Deployment (or ReplicaSet/StatefulSet) up or down based on observed metrics, most commonly average CPU or memory utilization across the Pods, though it can also scale on custom metrics (like queue depth or requests per second) via the Kubernetes metrics API. You configure it with a target — for example, "keep average CPU utilization across order-service's Pods at 60%" — and the HPA controller polls current utilization on an interval (by default every 15 seconds) and computes a desired replica count, scaling out when utilization is above target and scaling in when it's below, within a configured minimum and maximum replica bound. This is "horizontal" scaling — adding more Pod instances — as opposed to "vertical" scaling, which would mean giving an existing Pod more CPU/memory (handled separately by a Vertical Pod Autoscaler, which is less commonly used because it typically requires restarting the Pod to apply new resource limits). A practical nuance worth mentioning in an interview: HPA scaling reacts to metrics with some lag and has a default cooldown/stabilization window to avoid rapidly flapping replica counts up and down, so it's a tool for absorbing sustained load changes — like a gradual daily traffic ramp — rather than instantaneous spikes, which is why a flash-sale scenario is often handled with pre-emptive scaling in addition to relying on HPA alone.
What's the difference between a rolling update and a recreate deployment strategy in Kubernetes?
These are the two built-in Deployment strategy.type values, and they differ in whether old and new versions ever run simultaneously. RollingUpdate (the default) incrementally replaces old Pods with new ones — controlled by maxSurge (how many extra Pods above the desired count can be created during the rollout) and maxUnavailable (how many Pods can be down at once) — so at every point during the rollout there's a mix of old and new version Pods serving traffic together, meaning zero downtime as long as readiness probes correctly gate new Pods from receiving traffic before they're actually ready. Recreate terminates every existing Pod first, then creates all the new Pods — there's a guaranteed window where zero Pods are running and serving traffic, which is unacceptable for a customer-facing service like order-service but is sometimes required when the old and new versions genuinely cannot coexist, such as a schema-incompatible change to shared state that both versions read, or a singleton-style workload that cannot have two versions holding a lock simultaneously. The interview-ready distinction: RollingUpdate trades a brief period of mixed-version traffic for zero downtime, while Recreate trades guaranteed downtime for the certainty that old and new versions are never running at the same time.
What is a Kubernetes namespace, and what is it actually used for?
A namespace is a way to partition a single Kubernetes cluster into multiple virtual clusters for organizational and access-control purposes — most Kubernetes object types (Pods, Deployments, Services, ConfigMaps, Secrets) live inside exactly one namespace, and names only need to be unique within a namespace, not across the whole cluster. In practice, teams use namespaces to separate environments (shopsphere-staging vs shopsphere-prod in the same cluster) or to separate ownership boundaries between teams (an order-team namespace vs a catalog-team namespace), and namespaces are the unit that RBAC (Role-Based Access Control) permissions and ResourceQuotas (caps on total CPU/memory/object count) are typically scoped to — so you can grant a team full access within their own namespace without giving them any access to another team's resources, and prevent one team's workloads from starving the cluster of resources needed by everyone else. A few object types are cluster-scoped rather than namespaced — Nodes and PersistentVolumes, for example — because they represent physical/cluster-wide resources rather than something that logically belongs to one team's slice of the cluster. It's worth knowing that namespaces are not a hard security or network isolation boundary by default — Pods in different namespaces can still reach each other's Services over the network unless you additionally apply NetworkPolicies to restrict that.
What's the difference between a StatefulSet and a Deployment, and when would you need one?
A Deployment treats its Pods as interchangeable — any Pod can be killed and replaced by an identical new one with a new name and new IP, which works perfectly for stateless services like order-service or catalog-service where any replica can handle any request. A StatefulSet is for workloads where Pod identity matters: it gives each Pod a stable, predictable name (postgres-0, postgres-1, postgres-2 rather than randomly-suffixed names), creates and deletes Pods in a fixed order (0, then 1, then 2, and the reverse on scale-down), and gives each Pod its own dedicated PersistentVolumeClaim that follows that specific Pod across rescheduling rather than being shared or randomly reassigned. This matters for things like a self-managed database cluster or Kafka brokers, where node identity is tied to which data partition or replica role a given instance owns, and swapping in a differently-named replacement Pod with fresh empty storage would break the cluster's notion of who owns what. The practical interview signal: reach for a Deployment by default for any stateless service, and only reach for a StatefulSet when the workload itself has a genuine notion of "this specific instance, with this specific identity and this specific attached storage" — most backend Java services should never need one directly, since they typically offload state to a managed database or cache rather than running their own stateful cluster inside Kubernetes.
What is a startup probe, and how does it interact with liveness and readiness probes for slow-starting applications?
A startup probe exists specifically for containers with a slow or unpredictable initialization time — a Spring Boot service with a large application context, extensive @PostConstruct warm-up logic, or a cache that needs to preload a large dataset before it's ready to do anything at all. While a startup probe is configured and hasn't yet succeeded, Kubernetes disables the liveness and readiness probes entirely, so a slow-starting container isn't mistakenly killed by a liveness probe that assumes the process should already be responsive. Once the startup probe finally succeeds, liveness and readiness probes take over as normal for the rest of the container's life. Without a startup probe, teams are often forced into an awkward compromise: setting the liveness probe's own failure threshold and initial delay generously high enough to tolerate the slowest possible startup, which then also makes the liveness probe far too slow to react to a genuine post-startup hang. Separating "is this thing done starting" from "is this thing still healthy" lets each probe be tuned tightly for its own actual purpose.
What is a PodDisruptionBudget, and what production incident does it protect against?
A PodDisruptionBudget (PDB) sets a floor on availability during voluntary disruptions — events initiated by cluster operations rather than a Pod simply crashing on its own — such as draining a node for a Kubernetes version upgrade, a cluster autoscaler scaling down underutilized nodes, or an administrator running kubectl drain. You configure it with either minAvailable (at least this many or this percentage of matching Pods must stay up) or maxUnavailable (at most this many can be taken down at once), and the eviction API respects this budget by refusing or delaying an eviction that would violate it. Without a PDB, a well-intentioned node drain during a routine cluster upgrade could evict every single replica of order-service simultaneously if they happened to all be scheduled on the node(s) being drained at that moment — causing a self-inflicted outage from routine maintenance rather than from any actual application bug. This is a distinctly senior-level detail because it addresses a class of incident that only shows up at real operational scale: the failure isn't in the application code at all, it's in the interaction between cluster maintenance operations and how conservatively (or not) availability is protected during those operations.
What are the main components of Kubernetes architecture, and what happens when you run kubectl apply?
A Kubernetes cluster splits into a control plane (the "brain," typically running on dedicated nodes and fully managed for you in EKS/GKE/AKS) and one or more worker nodes (where your actual Pods run). The control plane has four key pieces: the API server (kube-apiserver) is the single front door — every command, including kubectl, and every other control-plane component talks only to it, never directly to each other; etcd is a distributed key-value store that holds the entire cluster's desired and current state (every object's spec and status); the scheduler (kube-scheduler) watches for newly created Pods with no node assigned and picks a node for them based on resource requests, constraints, and affinity rules; and the controller manager runs the reconciliation loops (the Deployment controller, ReplicaSet controller, and others) that continuously compare desired state in etcd against actual cluster state and take action to close any gap. Each worker node runs a kubelet (an agent that talks to the API server, is told which Pods should run on its node, and starts/stops/monitors their containers accordingly via the container runtime) and kube-proxy (which programs the node's networking rules so Service IPs correctly load-balance to the right backing Pods). Tracing kubectl apply -f deployment.yaml through this: kubectl sends the desired Deployment spec to the API server, which validates and persists it into etcd; the Deployment controller notices the new/changed object and creates or updates the underlying ReplicaSet; the ReplicaSet controller creates Pod objects to match the desired replica count; the scheduler assigns each unscheduled Pod to a node; and finally that node's kubelet sees the assignment and actually starts the containers. No single component "does" the deployment — it emerges from several independent controllers each reacting to state changes in etcd through the API server, which is the core design idea (a declarative, level-triggered control loop) worth naming explicitly in an interview.

Cloud & DevOps Basics

What is CI/CD, and what's the difference between continuous delivery and continuous deployment?
CI/CD stands for Continuous Integration and Continuous Delivery/Deployment, and it describes the automated pipeline that takes a code change from commit to running in production. Continuous Integration (CI) is the practice of merging code changes into a shared branch frequently and automatically building and testing every change, so integration problems between developers' work surface within minutes rather than being discovered weeks later during a painful manual merge — a pull request against order-service's repository triggering an automated build, unit tests, and static analysis is CI. Continuous Delivery extends this so that every change that passes CI is automatically packaged into a deployable artifact and verified as release-ready at all times, but a human still clicks a button to actually push it to production. Continuous Deployment goes one step further and removes that manual gate entirely — every change that passes the full pipeline (build, tests, security scans, staging verification) is deployed to production automatically with no human approval step. The distinction interviewers actually want: delivery keeps a human decision point before production, deployment doesn't — and teams often intentionally keep that manual gate for regulated or high-risk changes even when their pipeline is technically capable of fully automated deployment.
What is Infrastructure as Code, and why does it matter for reliability?
Infrastructure as Code (IaC) means defining infrastructure — servers, networks, load balancers, Kubernetes clusters, IAM (Identity and Access Management) permissions — as version-controlled configuration files rather than as manual clicks in a cloud console, using tools like Terraform, AWS CloudFormation, or Pulumi. The config is declarative: you describe the desired end state ("an EKS cluster with these three node groups, this VPC, these security groups"), and the tool computes and applies whatever create/update/delete operations are needed to make reality match that description, rather than you scripting the steps yourself. This matters for reliability for the same reason version-controlled application code matters: infrastructure changes go through code review, are reproducible (the exact same environment can be recreated for staging, DR (Disaster Recovery), or a new region without manual configuration drift), and are auditable (every infrastructure change has a commit, an author, and a diff, rather than being an untracked console click that nobody remembers making six months later during an incident investigation). The alternative — infrastructure configured by hand over time — is often called "configuration drift" or a "snowflake environment," and it's a common root cause of the "works in staging, breaks in production" class of incident, because the two environments silently diverged from whatever their original setup steps were.
How would you decide between EC2, ECS/EKS, and Lambda for a new backend workload?
This is a trade-off question about how much operational control you need versus how much operational burden you're willing to own, and the right answer depends on the workload's shape. Raw EC2 (Elastic Compute Cloud) instances give full control over the OS and runtime but mean you own patching, scaling, and orchestration yourself — reasonable for specialized workloads with unusual OS-level requirements, but rarely the right default for a standard containerized service today. ECS or EKS (container orchestration, self-managed or Kubernetes-based) is the right fit for a long-running, stateful-in-behavior service like order-service that needs to maintain warm connection pools, in-memory caches, and predictable latency, and that benefits from fine-grained control over rollout strategy, service mesh integration, and resource tuning — the trade-off is you're operating a cluster, even if the control plane itself is managed. Lambda fits short-lived, event-triggered, highly bursty work — resizing a product image after an S3 upload, or processing an SQS (Simple Queue Service) message a few times a minute — where paying per-invocation beats paying for always-on capacity, but it's a poor fit for anything requiring a long-lived connection pool, sub-millisecond warm-start latency guarantees, or execution beyond its maximum timeout (15 minutes). A senior-level answer names the concrete deciding factors — request duration and burstiness, statefulness, cold-start tolerance, and existing team operational expertise — rather than asserting one option is universally best.
How do you roll out a database schema change safely alongside a rolling deployment, without downtime?
The core problem is that a rolling update guarantees old and new versions of your application run simultaneously for a period, but a naive schema migration doesn't account for that — if you drop a column the old code still reads, or rename one the old code still writes to, the old Pods that haven't been replaced yet start failing the instant the migration runs. The standard safe pattern is the expand-contract (or parallel-change) pattern, done in separate deploys: first, expand — add the new column/table alongside the old one, deploy new application code that writes to both the old and new column but still reads from the old one, so both old and new Pod versions remain compatible with the current schema; once that's fully rolled out and stable, deploy a second change that reads from the new column and stops writing to the old one; only once every Pod is confirmed running that version do you finally contract — drop the now-unused old column in a separate, final migration. Skipping straight to a single deploy-and-migrate step is the classic way an on-call engineer discovers, mid-incident, that half their fleet is now crash-looping on a schema mismatch that the rolling update strategy was supposed to protect against. This expand-contract discipline is exactly why "just add a rolling update" is not by itself a complete answer to zero-downtime deployment whenever a database schema is involved — the schema change and the code change need to be sequenced as independent, backward-compatible steps.
What's the difference between blue-green and canary deployment strategies?
Both aim to release a new version with minimal risk and an easy rollback path, but they differ in how much traffic the new version gets and how the cutover happens. Blue-green keeps two complete, identical production environments — "blue" (currently live) and "green" (the new version) — running side by side; once the green environment is deployed and verified healthy, traffic is switched over atomically, typically by repointing a load balancer or updating DNS, so at any moment 100% of traffic is on exactly one environment. If a problem appears post-cutover, rollback is just switching the router back to blue, which is fast, but the strategy costs roughly double the infrastructure while both environments exist and doesn't catch every issue, since real production traffic never touched green before the full cutover. Canary instead releases the new version to a small subset of real traffic first — say, 5% of requests, or a specific subset of users — while the vast majority continues hitting the stable version, and gradually increases the new version's traffic share as metrics (error rate, latency, business KPIs) stay healthy, aborting and rolling back the canary slice if they don't. Canary's advantage over blue-green is a much smaller blast radius if the new version has a real bug — only a small fraction of real users are affected, and you find out from real traffic rather than only from pre-cutover testing — at the cost of a more gradual rollout and more sophisticated traffic-splitting infrastructure (a service mesh or a smart Ingress/load balancer) to implement well.
What are feature flags, and why do they decouple deployment from release?
A feature flag (also called a feature toggle) is a runtime conditional — typically backed by a config value or a dedicated feature-flag service — that gates whether a piece of code path is active, checked with something like if (featureFlags.isEnabled("new-checkout-flow", customer)) rather than being compiled in or out. The key idea is separating two things that a traditional deployment conflates into one event: deployment (getting new code onto production servers) and release (making that new code's behavior visible to users). With feature flags, you can deploy a new payment-service code path to 100% of production instances while the flag keeps it turned off for everyone, verify it's stable, then flip the flag on gradually — for specific internal users first, then a percentage of customers, then everyone — entirely at runtime, with no new deployment required for either the rollout or an instant rollback (just flip the flag back off). This also enables trunk-based development, where incomplete or risky features can be merged to the main branch and deployed continuously behind a flag without being visible to users until the team explicitly decides to release them, rather than living on a long-lived feature branch that risks a painful merge later.
What is auto-scaling in the cloud, and what are the basic ways it's triggered?
Auto-scaling is automatically adjusting the amount of compute capacity assigned to a workload in response to demand, instead of provisioning for a fixed peak capacity that sits mostly idle outside of peak times. The two basic axes are the same "horizontal vs vertical" split as in Kubernetes: horizontal scaling adds or removes instances/nodes (an AWS Auto Scaling Group adding EC2 — Elastic Compute Cloud — instances, or Kubernetes' HPA adding Pods), while vertical scaling resizes an existing instance to a bigger or smaller machine type, which usually requires a restart and has a hard ceiling once you've reached the largest available instance size. Scaling policies are commonly triggered one of three ways: metric-based/reactive (scale out when average CPU crosses 70%, or when a queue's backlog exceeds a threshold — the same idea as HPA), scheduled (pre-emptively scale out ahead of a known traffic pattern, such as scaling ShopSphere's checkout tier up an hour before a scheduled flash sale rather than waiting for reactive metrics to catch up), and predictive (cloud-provider machine-learning-based forecasting of upcoming load from historical patterns, scaling ahead of demand automatically). The general trade-off interviewers want you to articulate: reactive scaling always lags real demand by however long it takes to detect the metric change and boot new capacity, which is why latency-sensitive, spiky workloads often combine reactive scaling with a scheduled or manually pre-warmed baseline.
What are the common managed AWS services a backend engineer should recognize, and what does each do?
You're not expected to be a cloud architect, but recognizing the standard building blocks at a one-line level is table stakes. EC2 (Elastic Compute Cloud) provides resizable virtual machines — raw compute you configure and manage yourself, the traditional home for running a containerized service or a Kubernetes worker node. S3 (Simple Storage Service) is object storage for arbitrary files/blobs — think product images for catalog-service or generated invoice PDFs — accessed over HTTP (HyperText Transfer Protocol) rather than mounted as a filesystem, with effectively unlimited capacity and per-object durability rather than per-volume. RDS (Relational Database Service) is a managed relational database (Postgres, MySQL, and others) where AWS handles patching, backups, and failover, so you get a normal SQL database without operating the underlying instance yourself. SQS (Simple Queue Service) is a managed point-to-point message queue for decoupling producers and consumers — order-service could enqueue a "process refund" message that payment-service consumes and deletes once handled — while SNS (Simple Notification Service) is managed pub/sub (publish/subscribe) fan-out, where one published event can be delivered to multiple independent subscribers (an SQS queue, an email endpoint, a Lambda function) at once, which is the AWS-native alternative to a self-managed broker like Kafka for simpler fan-out needs. Lambda runs your code in response to an event (an HTTP request, an S3 upload, an SQS message) without you provisioning or managing any server at all — you're billed per invocation and execution time, making it a fit for short-lived, event-triggered work like resizing a product image after upload, rather than a long-running, stateful service like order-service itself.
