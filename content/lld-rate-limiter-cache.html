LLD #2: Rate Limiter / TTL Cache

Token Bucket Sliding Window Counter Striped Locking LRU via Doubly Linked List TTL Expiry Concurrent Eviction Caffeine / Guava Design
Why this matters

A rate limiter and a TTL cache look like unrelated exercises, but they are the same problem wearing two costumes: both bound an in-memory resource (requests allowed per unit time, or entries allowed in a table) and both must make the "am I over the bound?" check cheap even when a thousand threads ask it per second. If you build either one with a single synchronized block around all state, you will not see the bug in a single-threaded test — you will see it as a mysterious throughput ceiling in production once traffic fans out across cores, because every request is now serialized behind one lock regardless of whether it even touches the same client or key as the request ahead of it. Understanding how per-key state is isolated (striped locks, atomics, segment maps) is what explains why ConcurrentHashMap, Guava RateLimiter, and Caffeine all look the way they do internally.

1. The Shared Shape of Both Problems

Strip away the domain vocabulary and a rate limiter and a TTL cache are structurally identical:

  • Keyed state: a rate limiter tracks state per clientId (or API key, or IP); a cache tracks state per cache key. Both need O(1) lookup of "the state object for this key," which means both start from a Map<K, State>.
  • A bound that must be enforced cheaply: the rate limiter's bound is "no more than N permits per window"; the cache's bound is "no more than maxSize entries" and/or "no entry older than ttl." Both bounds must be checked on every single operation, so the check itself cannot be expensive or heavily contended.
  • Passive decay of state over time: a token bucket's tokens replenish as time passes even with no explicit "tick" thread; a cache entry becomes stale as time passes even with no explicit expiry thread. Both designs face the same question — do you recompute/check "is this still valid" lazily, only when someone touches the key, or do you run a background process that sweeps proactively?
  • Concurrent access to the same keyed state is the hard part, not the algorithm. The token bucket refill formula and the LRU eviction rule are each a few lines of arithmetic or pointer manipulation. What makes both of these genuine low-level design problems instead of one-line utilities is guaranteeing correctness when multiple threads hit the same client or the same cache key at once, without serializing unrelated keys behind each other.

Keeping this parallel explicit is useful because the concurrency techniques transfer directly: striping a lock array by clientId.hashCode() for a rate limiter is the same technique as striping by cache key for a cache, and both are the same idea segment locking in the pre-Java-8 ConcurrentHashMap used before it moved to per-bucket CAS operations.

2. Rate Limiter: Token Bucket as an Actual Class

The conceptual algorithm — tokens refill at a steady rate up to a capacity, each request consumes one token — is covered as a concept on resilience-fault-tolerance. Here the concern is different: what class actually holds this state per client, and what does allowRequest(clientId) do internally without a global lock serializing every client's requests through one critical section.

Per-client bucket state

Each client needs exactly two mutable fields: how many tokens are currently available, and when the bucket was last refilled. There is no need to run a background thread ticking every bucket — refill is computed lazily, on demand, as elapsed time since the last check:

class TokenBucket {
    private final long capacity;
    private final double refillTokensPerNano;
    private volatile double availableTokens;
    private volatile long lastRefillTimestampNanos;

    TokenBucket(long capacity, double refillRatePerSecond) {
        this.capacity = capacity;
        this.availableTokens = capacity;
        this.refillTokensPerNano = refillRatePerSecond / 1_000_000_000.0;
        this.lastRefillTimestampNanos = System.nanoTime();
    }

    synchronized boolean tryConsume() {
        refill();
        if (availableTokens >= 1.0) {
            availableTokens -= 1.0;
            return true;
        }
        return false;
    }

    private void refill() {
        long now = System.nanoTime();
        long elapsed = now - lastRefillTimestampNanos;
        double refilled = elapsed * refillTokensPerNano;
        if (refilled > 0) {
            availableTokens = Math.min(capacity, availableTokens + refilled);
            lastRefillTimestampNanos = now;
        }
    }
}

Note the synchronized here is scoped to one client's bucket object, not to the whole limiter. That distinction is the entire design.

The registry: where per-client buckets live and how they're cleaned up

class RateLimiter {
    private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    private final long capacity;
    private final double refillRatePerSecond;

    boolean allowRequest(String clientId) {
        TokenBucket bucket = buckets.computeIfAbsent(clientId,
            id -> new TokenBucket(capacity, refillRatePerSecond));
        return bucket.tryConsume();
    }
}

ConcurrentHashMap.computeIfAbsent is doing real work here: it guarantees that even if a thousand threads call allowRequest("client-42") for the very first time simultaneously, exactly one TokenBucket is created and every thread gets the same instance — the map's own internal per-bucket locking (not a global lock) arbitrates that race. Once the bucket exists, contention is scoped to threads hitting that specific client; a burst from client-99 never blocks on a lock held by client-42's bucket. This is the difference between "one global lock around all rate-limiting state" (which serializes all clients through one critical section, turning a multi-core service into an effectively single-threaded gate) and "one lock per client's own bucket" (where contention only exists among concurrent requests from the same client, which for most rate limiting use cases is a small number of threads).

A ConcurrentHashMap of buckets grows forever unless you clean it up

computeIfAbsent never removes entries. A rate limiter serving millions of distinct clients (real IPs, API keys, or worse, unauthenticated request fingerprints that an attacker can vary at will) will accumulate one TokenBucket object per distinct client forever, which is a slow, unbounded memory leak that won't show up until the map has been running for days. Two real fixes: (1) wrap entries with a last-access timestamp and run a low-frequency sweep (e.g. every few minutes) that removes buckets untouched for longer than some multiple of the window, or (2) back the map with time-bound eviction directly — which is precisely the TTL cache problem from the next section, applied to bucket storage instead of business data. In production this is usually solved by literally using a cache (Caffeine, with expireAfterAccess) as the bucket registry instead of a raw ConcurrentHashMap, folding the cleanup problem into infrastructure that already solves it.

Alternative: atomics instead of synchronized, when only a counter is needed

If the algorithm is a fixed or sliding window counter rather than a floating-point token bucket, the per-client state can often be reduced to a single mutable integer, and then AtomicLong/AtomicInteger with compare-and-swap replaces the lock entirely — no thread ever blocks, it just retries the CAS if another thread updated the counter first:

class SlidingWindowCounter {
    private final AtomicLong currentWindowCount = new AtomicLong();
    private final AtomicLong previousWindowCount = new AtomicLong();
    private volatile long currentWindowStartMillis;
    private final long windowSizeMillis;
    private final long limit;

    boolean allow() {
        long now = System.currentTimeMillis();
        rotateWindowIfNeeded(now);
        double elapsedFraction = (now - currentWindowStartMillis) / (double) windowSizeMillis;
        double estimated = previousWindowCount.get() * (1 - elapsedFraction)
                          + currentWindowCount.get();
        if (estimated >= limit) return false;
        currentWindowCount.incrementAndGet();
        return true;
    }
    // rotateWindowIfNeeded swaps current into previous and resets
    // current to 0 once now crosses into a new window boundary.
}

Compare-and-swap avoids blocking, but it is not free of coordination cost — under very high contention on the same atomic (many threads incrementing the same client's counter simultaneously), CAS retries can spin, and the cache line backing that counter bounces between CPU cores (false sharing at the hardware level even though there's no software lock). For a rate limiter this is rarely the bottleneck because the whole point of per-client keying is that only requests from one client contend on one counter — but it's worth knowing that "lock-free" is not synonymous with "contention-free."

Sliding window boundary swap and clock skew

The trickiest part of the sliding window counter to get right in code, not just in theory, is the window rotation: exactly one thread should perform the "shift current into previous, reset current to zero" transition when the clock crosses a boundary, not every thread that happens to observe now past the boundary simultaneously. A common bug is checking now >= currentWindowStartMillis + windowSizeMillis and unconditionally rotating — under concurrent access, multiple threads pass that check before any of them updates currentWindowStartMillis, so the window rotates multiple times and legitimate counts get discarded. The fix is the same compare-and-swap pattern used everywhere else: use an AtomicLong for currentWindowStartMillis and rotate only inside a successful compareAndSet(oldStart, newStart), so exactly one thread wins the rotation and the rest simply proceed with the (now current) window.

3. TTL Cache: The Data Structure Underneath LinkedHashMap, Built by Hand

A TTL cache with size bounding needs two things working together: O(1) lookup by key (a hash map) and O(1) knowledge of "which entry was least recently used" (an ordering). The mechanism that makes both O(1) simultaneously is a doubly linked list threaded through the hash map's own entry objects — each hash map value is also a linked-list node, so moving an entry to the front of the recency order is a pointer swap, not a search. This is exactly the internal mechanic LinkedHashMap uses in access-order mode; building it by hand here makes the pointer manipulation explicit instead of hidden behind removeEldestEntry.

The combined structure

class TtlLruCache<K, V> {
    private class Node {
        K key; V value;
        long expiryTimestampMillis;
        Node prev, next;
    }

    private final Map<K, Node> index = new HashMap<>();
    private final Node head = new Node(); // dummy sentinel, most-recently-used side
    private final Node tail = new Node(); // dummy sentinel, least-recently-used side
    private final int capacity;
    private final long ttlMillis;

    TtlLruCache(int capacity, long ttlMillis) {
        this.capacity = capacity;
        this.ttlMillis = ttlMillis;
        head.next = tail;
        tail.prev = head;
    }
    // get/put below
}

Using dummy sentinel head/tail nodes (rather than leaving head/tail as nullable references to real entries) removes every null check from the pointer-relinking code — every real node always has a non-null prev and next, even the first and last real entries, because the sentinels bracket them. This is the single biggest source of off-by-one and null-pointer bugs in hand-rolled linked-list LRU implementations, and it is worth internalizing as a general pattern for any doubly linked list you build yourself.

The general algorithm for get and put

get(key):

  1. Look up index.get(key). If absent, return miss.
  2. If present but node.expiryTimestampMillis < now (lazy expiry check), unlink the node from the list, remove it from the map, and return miss — the entry is logically dead even though it physically still occupied a slot until this access found it.
  3. Otherwise, unlink the node from its current position and re-insert it immediately after head (mark it most-recently-used), then return the value.

put(key, value):

  1. If key already exists in index, update its value and expiry timestamp, unlink and move it to the front (same as a successful get), and return.
  2. Otherwise create a new node with expiryTimestampMillis = now + ttlMillis, insert it immediately after head, and add it to index.
  3. If index.size() > capacity, evict: take the node immediately before tail (the actual least-recently-used entry), unlink it, and remove its key from index.

Worked example: interleaved gets, puts, TTL expiry, and eviction together

Consider capacity = 3, ttlMillis = 100, and this sequence of operations, timestamped from an arbitrary t = 0:

t=0    put(A, "a")     -> list (MRU..LRU): A
t=10   put(B, "b")     -> list: B, A
t=20   put(C, "c")     -> list: C, B, A      (at capacity: 3 entries)
t=30   get(A)          -> hit; A moves to front -> list: A, C, B
t=40   put(D, "d")     -> insert D at front -> list: D, A, C, B (size 4 > capacity 3)
                            evict LRU (node before tail) = B -> list: D, A, C
t=115  get(C)          -> C's expiry was set at t=20, ttl=100, expires at t=120.
                            now=115 < 120, so still valid -> hit; C moves to front
                            -> list: C, D, A
t=125  get(A)          -> A's expiry was refreshed at t=30 (put/get resets TTL here),
                            expires at t=130. now=125 < 130 -> hit -> list: A, C, D
t=135  get(D)          -> D's expiry set at t=40, expires at t=140. Still valid -> hit.
t=145  get(D)          -> now=145 > 140 -> expired. Lazily evicted here, not before.
                            Even though D "died" at t=140, it sat in the list,
                            still consuming a capacity slot, from t=140 to t=145
                            simply because nothing accessed it in that window.

This example exercises four mechanics at once worth noticing: TTL refresh on touch (whether a get/put resets the clock is a design choice you must state explicitly — a sliding TTL like above versus an absolute TTL fixed at creation are genuinely different caching semantics), LRU reordering happening independently of expiry, eviction firing purely on the size bound with no regard for how "fresh" the evicted entry was (B was evicted at t=40 despite not being expired — LRU and TTL are two independent bounds, and either one can trigger removal first), and the core trade-off of lazy expiration: an expired entry occupies memory and a map slot for as long as nothing touches it, which is exactly the risk called out in the next section.

Lazy expiration vs. a background sweep thread

AspectLazy (check-on-access)Background sweep
CPU cost when idleZero — no work happens unless something accesses the keyNonzero — a thread wakes periodically and scans, even if nothing changed
Memory behavior for keys never re-accessedStale entries linger indefinitely, holding memory and (if values are large or reference external resources) potentially leaking those resourcesReclaimed within one sweep interval regardless of access pattern
Lock contention profileContention only on keys actually being read/writtenSweep thread must lock (or briefly pause) the structure to safely walk and remove entries, adding a periodic contention spike even for keys under normal traffic
Worst caseA cache that's mostly write-once-read-never accumulates unbounded garbage until size-bound eviction (LRU) eventually forces it out — if there even is a size boundSweep interval too long: entries linger almost as badly as pure laziness; too short: wasted CPU scanning for little gain

Real caches combine both rather than choosing one: Caffeine and Guava check expiry lazily on every get (so a stale read is never returned), but also perform incremental cleanup piggybacked on ordinary write operations, and Caffeine additionally uses a scheduled expiration wheel-like mechanism for time-based eviction so that entries which are never touched again still get reclaimed without a dedicated always-on thread per cache. The size-bound (LRU/LFU) eviction acts as a backstop in both designs: even if TTL cleanup is imperfect or delayed, the map still cannot exceed its configured maximum size, because eviction on that bound is checked on every write, not on a timer.

4. Concurrency for the Cache: Why One Lock Around get/put Doesn't Scale

The naive thread-safe version of the hand-built cache above wraps every method in one synchronized block, because both the hash map lookup and the linked-list pointer surgery touch shared mutable state that must not be corrupted by concurrent writers. This works, and it is even the right starting point for a correctness-first implementation — but it means every single get(), including read-only cache hits, must acquire a mutex that serializes it against every other thread's get() and put(), on any key. A cache that is supposed to make hot paths faster becomes a bottleneck precisely under the high-concurrency conditions where caching matters most.

Segment striping

The first production-grade fix, historically used by Java's own ConcurrentHashMap before Java 8 and still used in many hand-rolled concurrent caches, is to split the single map into N independent segments, each with its own lock and (in the LRU case) its own linked list:

int segmentIndex = (key.hashCode() & 0x7fffffff) % segmentCount;
Segment<K, V> segment = segments[segmentIndex];
synchronized (segment.lock) {
    return segment.get(key);
}

With, say, 16 segments, two threads operating on keys that happen to hash into different segments never contend at all — they acquire different locks and proceed fully in parallel. The cost is that each segment now independently tracks its own LRU order and its own capacity fraction (capacity / segmentCount per segment), which means global LRU ordering across the whole cache is only approximate — an entry that's "hot" in one segment has no bearing on eviction decisions in another. This is an accepted trade-off: approximate LRU under real concurrency beats exact LRU that can't scale past one core's worth of throughput.

Lock-free reads via a concurrent map, with a separate eviction bookkeeping structure

The more modern approach — what Caffeine actually does — goes further: use a lock-free concurrent hash map (Java's ConcurrentHashMap, whose reads since Java 8 require no locking at all in the common case) for the key-to-value lookup, and keep the eviction policy's bookkeeping (the LRU/LFU ordering structure) as a logically separate data structure that is updated asynchronously rather than inline with every read.

Concretely, Caffeine's reads do not touch a linked list at all in the hot path. Instead, a get() records "this key was accessed" onto a lock-free ring buffer (a striped buffer per thread, to avoid write contention on the buffer itself), and a background maintenance step — triggered opportunistically by subsequent writes, not a dedicated always-spinning thread — drains that buffer and applies the recency/frequency updates to the actual eviction policy structure (a variant of LRU combined with a frequency sketch, called Window TinyLFU) in bulk. The effect: a cache hit under heavy concurrent read load costs one lock-free map lookup plus a cheap buffer write, never a lock acquisition and never a pointer-chasing linked-list update on the critical path. Writes are heavier — they do need to interact with the eviction structure more directly — but reads, which dominate in almost every cache workload, are effectively as cheap as a plain ConcurrentHashMap.get().

The general principle: decouple "is the answer correct" from "is the bookkeeping up to date"

The reason lock-free reads are safe here is that a cache's eviction bookkeeping is allowed to be slightly stale without breaking correctness — if the LRU order is a few accesses behind reality, the cache still returns correct values for every key it holds, it just might evict a slightly wrong entry once in a while under memory pressure. That's a tolerable, bounded imprecision. Compare this to the rate limiter's counter: an incorrect count there directly changes whether a request is allowed or rejected, which is why a rate limiter typically cannot tolerate the same kind of eventually-consistent bookkeeping and instead needs the count itself (not just its ordering metadata) to be exact at the moment of the check, via CAS or a per-client lock. This is the same read-vs-write, correctness-vs-bookkeeping distinction discussed for eventual consistency in distributed-systems-core, just applied inside a single process instead of across a cluster.

The unifying idea that makes both of these worth studying together is this: bounding a resource under concurrency is not primarily an algorithm problem — token bucket math and LRU pointer manipulation are each a few lines — it is a problem of scoping contention. The correct answer to "how do I make this bound cheap to check under concurrent access" is almost never "add a bigger lock"; it's "identify the smallest unit of state that actually needs to be consistent (one client's bucket, one cache key's value) and make everything outside that unit independent." Every technique covered here — striped locks, per-key atomics, segment maps, lock-free reads with deferred bookkeeping — is a variation on that one idea, and it is the same idea that motivates lock striping and CAS-based structures generally, and that governs how distributed caches shard state across nodes once a single process's memory isn't enough.

Concepts Worth Being Able to Explain From First Principles

Why does keying a rate limiter's state by client in a ConcurrentHashMap avoid the throughput ceiling that a single global lock would cause, even though the map itself has internal locking?
A single global lock around all rate-limiting state forces every request, regardless of which client it belongs to, through one critical section — the work is trivial, but the serialization means only one thread can even be checking a limit at any instant, capping total throughput at roughly one lock acquisition's worth of latency per request across the entire service, no matter how many cores are available. Keying by client with a ConcurrentHashMap<String, TokenBucket> changes what needs to be mutually exclusive: the map's own internal structure (its buckets and resize state) is protected by fine-grained per-bucket synchronization or CAS operations that only briefly lock a small slice of the map, and once a thread has retrieved the specific TokenBucket object for its client, further contention exists only among other threads acting on that same client's bucket. Two requests from different clients never wait on each other at all, because they're touching different bucket objects protected by different (or no) locks. The map's internal locking is real, but it's scoped to structural map operations, which are rare relative to the per-client `tryConsume()` calls, and even those are extremely brief.
Walk through what physically happens to the pointers when get(key) is called on a hand-built LRU structure and the key is found in the middle of the list.
First, the hash map lookup (`index.get(key)`) returns the `Node` object in O(1) — this step never touches the linked list at all. Once you have the node, you unlink it from its current position by taking its `prev` and `next` neighbors and pointing them directly at each other (`node.prev.next = node.next; node.next.prev = node.prev;`), which removes the node from wherever it was in the list in O(1) regardless of how deep in the list it was, because you never had to walk to find it — the map handed you the reference directly. Then you re-insert the same node object immediately after the sentinel `head`: point `head.next`'s old value's `prev` at the node, point the node's `next` at what used to be `head.next`, point the node's `prev` at `head`, and point `head.next` at the node. No new node is allocated and no data is copied — only six pointer assignments total, which is what makes "move to most-recently-used position" O(1) rather than O(n), even though logically it feels like it should require re-sorting.
What specifically goes wrong if you check the sliding window boundary with a plain if-statement instead of compare-and-swap on the window start timestamp?
If multiple threads concurrently evaluate `now >= currentWindowStartMillis + windowSizeMillis` right around the moment the window should roll over, all of them can see the condition as true before any of them has updated `currentWindowStartMillis`, because reading the condition and acting on it are two separate, non-atomic steps. Each of those threads then independently performs the "shift current into previous, reset current to zero" transition, which means the rotation logic runs multiple times for what should be a single boundary crossing — legitimate request counts recorded in the (very briefly) current window by other threads get wiped out by a second or third redundant reset, and the previous-window count gets overwritten multiple times, losing data needed for the sliding estimate. Wrapping the transition in `compareAndSet(oldStart, newStart)` fixes this because only the thread whose compare-and-swap succeeds (i.e., the one that still sees the pre-rotation timestamp at the exact instant it attempts the swap) actually performs the rotation; every other thread's CAS fails, so it simply proceeds using the timestamp some other thread already updated, without redoing the transition.
Why is it acceptable for Caffeine's LRU/LFU ordering to be updated asynchronously and slightly out of date, but not acceptable for a rate limiter's token count to be similarly stale?
A cache's eviction ordering is bookkeeping metadata about which entries are more or less valuable to keep — it does not affect whether a `get()` for a key currently in the map returns the right value. If the recency information is a few accesses behind reality, the worst outcome is that the cache evicts an entry that was actually accessed slightly more recently than the stale bookkeeping suggests, which costs one extra cache miss somewhere down the line, a hit-rate degradation, not a correctness violation. A rate limiter's token count, by contrast, is not metadata about something else — it *is* the thing being checked to decide whether to accept or reject a request right now. If that count is stale or under-synchronized, the limiter can let through more requests than intended (defeating the entire purpose of the limiter, potentially allowing a downstream to be overwhelmed) or reject requests that should have been allowed (a correctness-visible failure to the caller). This is why caches can afford deferred, batched, eventually-consistent bookkeeping for eviction while rate limiters need the actual counted value to be exact at the moment of the decision.
In the worked cache example, entry D expired at t=140 but wasn't removed until it was accessed again at t=145. Is this a bug?
No — it is the defining, expected trade-off of lazy (check-on-access) expiration, not a defect in the implementation. Lazy expiration deliberately does no work unless and until something touches the key; the cost of that laziness is that a logically-expired entry can continue occupying a map slot and its associated memory for an unbounded amount of time after its expiry instant, as long as nothing calls get/put on that specific key. The correctness guarantee lazy expiration actually provides is narrower than "expired entries are removed promptly" — it only guarantees "an expired entry is never *returned* as a valid hit," which the design still upholds, since the t=145 access correctly detects the expiry and reports a miss rather than serving stale data. If prompt reclamation (not just prompt invalidation on read) is a hard requirement — for example, because cached values hold expensive external resources that must be released quickly — that requirement has to be met by adding a background sweep, not by lazy expiration alone.
Why does treating capacity eviction (LRU) and time eviction (TTL) as two independent mechanisms, rather than trying to unify them into one rule, make the design easier to reason about?
LRU eviction answers "which entry should go if the table is too full," a question purely about relative recency of access, while TTL eviction answers "is this specific entry still allowed to be trusted as fresh," a question purely about elapsed wall-clock time since it was written or last touched. These are genuinely different questions with different failure modes: an entry can be extremely fresh (well within its TTL) yet still be the least recently used one and get evicted for space, and conversely an entry can be the most recently used one yet still be expired if enough time passed since it was set even without being touched. Trying to fold both into a single score (e.g., some weighted combination of recency and age) makes the eviction decision harder to reason about and harder to test, because you can no longer isolate "did this get evicted because of the size bound" from "did this get evicted because it went stale." Keeping them as two independent checks — the linked list purely for recency ordering, the expiry timestamp purely for staleness — means each mechanism can be tested, tuned, and explained in isolation, and the worked example's outcome (B evicted despite being fresh; D found stale despite being untouched since a moment before) is exactly what falls out of that separation.
