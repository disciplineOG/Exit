HLD Basics: Scaling & Load Balancers

Why this matters

Almost every "why is this service slow under load" or "why did adding more servers not help" investigation traces back to a wrong mental model of how scaling and load balancing actually work. If you don't understand why horizontal scaling demands statelessness, you'll ship a feature that stores session state in memory and then watch it randomly log users out the moment a second instance joins the fleet. If you don't understand consistent hashing, you won't understand why your cache hit rate collapsed the moment you resized a cluster. Picture ShopSphere on the morning of a flash sale: a coupon email goes out at 9:00am, checkout traffic on order-service jumps 40x in two minutes, and whatever assumptions your scaling story was built on get tested all at once. This page builds the reasoning from the ground up so those failures become predictable instead of mysterious.

1. Vertical vs Horizontal Scaling

Scaling means increasing a system's capacity to handle load — more requests per second, more data, more concurrent connections. There are exactly two axes along which you can do this, and they have fundamentally different failure modes and cost curves.

Vertical scaling (scale up)

Vertical scaling means giving a single machine more resources: more CPU cores, more RAM, faster disks (NVMe over spinning disk), a faster network interface. Nothing about the application's architecture changes — you still have one process, one memory space, one filesystem. This is why it's the first thing teams reach for: no code changes, no coordination logic, no new failure modes to reason about.

The problem is that it doesn't compose. Hardware has a ceiling — at some point you simply cannot buy a bigger machine, and even before that ceiling, cost stops scaling linearly. A machine with 2x the cores of a mid-range server frequently costs far more than 2x the price, because you're paying for exotic silicon binning, more DIMM channels, and higher-tier support contracts. And critically, vertical scaling gives you exactly one machine as your single point of failure — if it dies, panics, or needs a kernel patch and reboot, the entire service is down. There's no redundancy to fall back on.

Horizontal scaling (scale out)

Horizontal scaling means adding more machines and spreading load across all of them. This is the only strategy with no hard ceiling — you can keep adding commodity machines more or less indefinitely (subject to data-partitioning limits, which is a separate concern covered under sharding below). It also buys you fault tolerance for free: if one of ten instances crashes, you lose 10% of capacity, not 100% of it.

But horizontal scaling isn't free — it has a structural precondition that people frequently get wrong: any request must be able to be served by any instance. The moment that's true, a load balancer can freely route to whichever instance is healthiest or least loaded. The moment it's false — because instance B has some state in memory that instance A doesn't — you've built a system where correctness depends on routing, and routing is exactly the thing you wanted freedom to change.

Why "just add statelessness" is not a slogan, it's a constraint

If your application keeps anything in local process memory that a later request depends on — an HTTP session object, an in-memory cache of "which users are currently uploading," a mutex protecting a local counter — then horizontal scaling silently breaks correctness rather than failing loudly. A customer logs in on order-service instance A, their session cookie references cart state that lives only in instance A's heap, and their very next "place order" request gets routed to instance B, which has never heard of their cart. Checkout appears to silently lose their items. This class of bug is maddening because it works perfectly in local development (one instance) and in low-traffic staging (round robin gets lucky), and only manifests once you actually run 2+ replicas under real traffic — which, for ShopSphere, is exactly when a flash sale forces you to scale the checkout tier out from 2 instances to 20.

The fix is always the same shape: externalize the state. Move sessions and cart contents to Redis or a database (or eliminate them via JWTs, discussed below), move counters like "how many flash-sale units are left" to Redis with atomic INCR/DECR, move any "which node is doing X" coordination — like which instance owns reserving inventory for a given order — to a shared store or a proper distributed lock (see distributed-systems-core). Once state lives outside the process, every instance becomes interchangeable, and interchangeability is the actual thing that makes horizontal scaling work.

In practice, real systems do both: you pick a "reasonably sized" instance type (not the cheapest, not the biggest — usually driven by what fits your process's memory footprint and GC behavior, see jvm-architecture) and then scale that unit horizontally. Vertical scaling buys you headroom per node; horizontal scaling buys you the ability to grow without bound and to survive node failure.

2. What a Load Balancer Actually Does

Once you have more than one instance capable of serving a request, something has to decide, for each incoming request, which instance handles it. That's the entire job of a load balancer (LB): a component sitting in front of a pool of backend instances that (a) distributes traffic across them according to some algorithm, and (b) stops sending traffic to instances that are unhealthy.

The critical distinction that determines what an LB can and can't do is which layer of the network stack it operates at.

L4 load balancing (transport layer)

An L4 load balancer operates at the TCP/UDP level. It looks at the IP address and port in a packet's header and forwards the packet to a backend — it does not open, parse, or understand the payload. It doesn't know if the payload is HTTP, gRPC, raw TCP, or anything else. This makes it extremely fast (often line-rate, implemented in the kernel or in hardware/ASICs on managed offerings) because there's no need to terminate the connection, parse text, or buffer bytes — it's largely just rewriting packet headers and forwarding.

Because it can't see inside the payload, an L4 balancer typically makes one routing decision per TCP connection (or per flow, identified by the 5-tuple: source IP, source port, destination IP, destination port, protocol) and then keeps forwarding all packets on that connection to the same backend. A cloud Network Load Balancer (AWS NLB) is a canonical example.

L7 load balancing (application layer)

An L7 load balancer terminates the connection itself, actually parses the HTTP (or gRPC, WebSocket, etc.) request, and can therefore make routing decisions based on things like the URL path (/api/checkout vs /api/search going to different backend pools), the Host header (for multi-tenant routing), cookies, or custom headers. Because it understands HTTP, it can also do things an L4 balancer structurally cannot: retry a failed request against a different backend, rewrite headers, terminate TLS and re-encrypt (or not) to the backend, do content-based routing, and multiplex many logical HTTP requests from different clients over a smaller number of backend connections (connection pooling/keep-alive reuse). nginx, HAProxy (in HTTP mode), Envoy, and AWS's Application Load Balancer (ALB) are L7. In ShopSphere, this path-based routing is exactly what lets /api/checkout/** and /api/search/** be sent to entirely different backend pools (order-service vs catalog/search-service) sized and scaled independently — the search fleet doesn't need to double in size just because checkout is melting down during a flash sale, and vice versa. That same automatic-retry capability is exactly why a checkout request must be safe to receive twice: if the LB retries a place-order call against a second instance because the first was slow to respond (but had actually already succeeded), a payment-charging endpoint that isn't idempotent will double-charge the customer — see payment-systems-idempotency for how an idempotencyKey on the Payment makes retries safe.

The cost of that intelligence is CPU: parsing HTTP headers, running regex-based routing rules, and holding two separate TCP connections (client-to-LB and LB-to-backend) per request is materially more expensive per request than L4's header-rewrite-and-forward.

Why both layers still exist in the same stack

Large systems commonly stack them: an L4 balancer (or anycast + ECMP routing) absorbs massive volumes of raw traffic and DDoS-style floods cheaply at the edge, then hands healthy, load-spread TCP connections to a layer of L7 balancers that do the smart, content-aware routing to specific services. Using only L7 everywhere is wasteful of CPU at the edge; using only L4 everywhere means you lose the ability to do path-based routing, retries, and TLS termination where you need it.

3. Load Balancing Algorithms

Given a healthy pool of backends, how does the LB pick one for a given request? The algorithm matters because a bad choice under real traffic patterns (uneven request cost, uneven backend capacity, or a need for cache locality) directly causes hot-spotting — a handful of instances pegged at 100% CPU while the rest sit idle. Picture ShopSphere's checkout tier under a flash-sale spike: some requests are a cheap "check inventory" read, others are a slow "charge payment and write an order" transaction — an algorithm that ignores that difference will happily keep piling slow requests onto an already-struggling instance.

Broadly, the algorithms below split into two families: ones that only care about right now (how loaded is each backend), and one — consistent hashing — that cares about which key is being requested, because it needs the same key to keep landing on the same backend over time.

Round robin

Cycle through backends in fixed order: 1, 2, 3, 1, 2, 3, .... Simple, requires no state beyond a counter, and works well when requests are roughly uniform in cost and all backends have equal capacity. It falls apart when either assumption breaks — if backend 2 is handling a slow "charge payment" request while 1 and 3 are idle handling cheap catalog reads, round robin will still send the next checkout request to 2 in its turn, regardless of its current load.

Weighted round robin

Same idea, but each backend gets a weight proportional to its capacity, so a bigger instance receives proportionally more requests (e.g., weights 3:1:1 sends 3 requests to backend A for every 1 to B and 1 to C — useful if ShopSphere's checkout fleet is a mix of newly-added large instances and older smaller ones during a scale-out). This fixes the "unequal hardware" problem but not the "unequal request cost" problem — the weights are static and don't react to what's actually happening on each node right now.

Least connections

Route to whichever backend currently has the fewest active (in-flight) connections. This is a real-time, reactive strategy: it naturally avoids sending more work to a backend that's already bogged down handling long-running requests (like a checkout request blocked on payment-service), without needing to know anything about request cost in advance. It requires the LB to track connection state per backend, which is a small amount of overhead but a much better signal than a blind round-robin counter — which is why it's the default choice for a checkout tier where request cost varies request-to-request.

Least response time

An extension of least connections: pick the backend with the best combination of low active-connection count and low recent average response time. This reacts to backends that are technically accepting new connections but are slow to actually finish them (e.g., an order-service instance in GC pressure, or one whose connection pool to the orders database is exhausted). It's more expensive to compute (the LB has to continuously measure and average latencies) but catches degradation that a pure connection-count metric misses.

Consistent hashing

All of the algorithms above answer "which backend should handle this request" without caring which backend handled a similar or identical request before. But there's an important class of systems where that history matters: caches, sharded databases, and sticky-session-like scenarios, where you want the same key (customer ID, product ID, session ID) to consistently land on the same backend so that backend can build up warm, useful local state (a cache, an open connection, a session). Consistent hashing is the general technique for that — e.g., always routing "get product 8841's details" to the same catalog/search-service instance so its local in-memory product cache stays warm instead of being cold on every request.

Why naive modulo hashing fails

The obvious first approach is backend = hash(key) % N where N is the number of backends. This works fine as long as N never changes. The instant you add or remove a single backend, N changes, and because it's a modulus, almost every key's target backend changes — not just the keys that "belong" to the added/removed node. Say ShopSphere caches product detail pages (keyed by productId) across a 10-node cache cluster, and you add an 11th node to absorb flash-sale traffic. Roughly 90% of product keys now hash to a different node than before, meaning a near-total cache wipe and a stampede of requests to catalog/search-service and its database while the cache refills — at the exact moment you were trying to add capacity to survive the spike. This is precisely the kind of failure that looks like "we added capacity and the database fell over" — the capacity addition itself is what caused the spike.

The consistent hashing algorithm, in general

  1. Take a hash function with a large, fixed output range (e.g., a 32-bit or 64-bit hash), and treat that output range as a circle ("the ring") — the maximum value wraps back around to zero.
  2. Hash each backend node's identifier (e.g., its IP:port) to get a position on the ring, and place the node there.
  3. To find the backend for a given key, hash the key to get its position on the ring, then walk clockwise from that position until you hit the first node. That node owns the key.
  4. When a node is added, it takes a position on the ring and becomes responsible only for the slice of keys between its position and the previous node's position (walking counter-clockwise) — every other key's ownership is untouched.
  5. When a node is removed, its keys simply fall through to the next node clockwise on the ring — again, no other node's ownership changes.

This is the core property that fixes the modulo problem: adding or removing one node remaps only the keys that were adjacent to that node on the ring — on average K/N keys out of K total keys across N nodes — instead of remapping nearly everything.

Virtual nodes: fixing uneven distribution

Placing exactly one point per physical node on the ring has a practical problem: with only a handful of nodes, their hashed positions can land unevenly by chance, giving some nodes a much larger arc of the ring (and therefore much more traffic) than others. The fix is to give each physical node many positions on the ring — typically on the order of 100 to a few hundred "virtual nodes," each a differently-salted hash of the same physical node's identifier (e.g., hash("node-A#0"), hash("node-A#1"), ... hash("node-A#149")). With enough virtual nodes spread across the ring, the law of large numbers takes over and each physical node ends up owning a roughly equal total arc length, hence a roughly equal share of keys — while preserving the minimal-remapping property when nodes come and go.

Worked example: a 3-node cache ring growing to 4 nodes

Say ShopSphere runs a product-detail cache cluster with nodes A, B, C, and we use a hash space of 0–359 (thinking of it as degrees on a circle, for readability) with 3 virtual nodes per physical node. Suppose the virtual node hash positions land like this:

A0=10  A1=140 A2=260
B0=50  B1=190 B2=300
C0=90  C1=230 C2=340

Sorted around the ring: 10(A) 50(B) 90(C) 140(A) 190(B) 230(C) 260(A) 300(B) 340(C) — and it wraps back to 10(A).

A request key that hashes to position 100 walks clockwise and lands on 140(A) — so key 100 belongs to node A, even though the nearest smaller position (90) belonged to C; ownership is always determined by the next node clockwise, not proximity in either direction. A key at position 350 walks clockwise, wraps past 359 back to 0, and lands on 10(A) — this wrap-around is exactly why it's modeled as a ring rather than a line.

Now add node D — provisioned specifically to absorb the extra flash-sale load — and say its 3 virtual nodes hash to 30, 170, 320. The ring becomes: 10(A) 30(D) 50(B) 90(C) 140(A) 170(D) 190(B) 230(C) 260(A) 300(B) 320(D) 340(C).

Only the keys that fall between a newly inserted D-position and the node immediately counter-clockwise of it move — specifically: keys in (10,30] move from A to D; keys in (140,170] move from A to D; keys in (300,320] move from B to D. Every key outside those three narrow arcs — the vast majority of the keyspace — keeps exactly the same owner it had before D joined. That's the guarantee: adding the fourth node only reshuffled the slices adjacent to its own virtual node positions, roughly a quarter of the total keyspace (matching 1/N for the new N=4), not a near-total remap the way % N would have caused.

If instead node C were removed, its 3 arcs (90, 230, 340) would simply fall through to whichever node is next clockwise (140→A, 260→A, 10→A in the original 3-node ring) — again, only C's own keys move, everyone else's assignment is untouched.

Where this shows up beyond load balancers

Consistent hashing isn't just an LB algorithm — it's the backbone of how distributed caches (Memcached client-side sharding), distributed databases (Cassandra, DynamoDB's partitioning), and CDNs assign keys/requests to nodes at scale. Anywhere you see "adding a node only moves a small fraction of the data," consistent hashing (or a close relative, like Cassandra's token ranges) is almost certainly the mechanism underneath. See database-architecture for how this same idea drives horizontal partitioning of a data store, and caching-strategies for how it keeps a distributed cache's hit rate stable as the cluster resizes.

4. Health Checks: Routing Around Failure

A load balancer's algorithm only matters for backends that are actually able to serve traffic. Every production LB continuously health-checks its backend pool and removes unhealthy ones from rotation — otherwise a crashed or hung instance keeps receiving its share of traffic and every one of those requests fails or times out. During a ShopSphere flash sale, this is exactly when instances are most likely to buckle — a checkout instance whose connection pool to payment-service is exhausted needs to be pulled out of rotation fast, before it turns every request routed to it into a timeout the customer sees as a broken checkout.

There are two common styles:

  • Active health checks: the LB itself periodically sends a synthetic request — commonly an HTTP GET to a dedicated endpoint like /healthz or /actuator/health — and expects a 200 within some timeout. Miss N consecutive checks (an "unhealthy threshold") and the backend is pulled from rotation; pass M consecutive checks after that (a "healthy threshold") before it's added back. The two different thresholds exist deliberately: you want to pull a bad node out fast, but you don't want to flap a recovering node back in the moment it shows one good response, only to pull it again on the next blip.
  • Passive health checks: rather than sending separate probe traffic, the LB observes real request outcomes — a backend that returns a run of 5xx errors or times out repeatedly on live traffic gets marked unhealthy without a dedicated probe endpoint. This reacts faster (no waiting for the next probe interval) but requires enough live traffic to generate a signal.
A shallow health check lies to the load balancer

A health check endpoint that just returns 200 OK unconditionally tells you the process is alive, not that it can actually do useful work. A well-designed check verifies the dependencies that request-handling actually needs — can it reach its database connection pool, is its downstream dependency reachable, is it still accepting new work rather than draining. Get this wrong in the other direction, though — a health check that transitively checks a shared downstream dependency (like a shared database) — and one degraded dependency will cause every instance across the entire fleet to report unhealthy simultaneously, taking down the whole service instead of just the fraction actually affected. The right check verifies "can I do my job," not "is everything upstream of me perfect."

Health checks are also what makes rolling deploys safe: a new instance is only added to rotation once it starts passing health checks, and an instance being terminated is first marked unhealthy (or explicitly deregistered) so the LB stops sending it new requests while it finishes in-flight ones — this "connection draining" window is what prevents deploys from causing a burst of dropped requests.

5. DNS-Based Load Balancing vs Dedicated LB Layers

Before a request ever reaches a dedicated load balancer, there's usually a coarser, cheaper layer of load distribution happening at DNS resolution. It's worth understanding both because they solve different problems and are often combined.

DNS-based load balancing

A DNS server can return multiple IP addresses for the same hostname, or return different answers to different clients (round robin DNS, or geo-based DNS routing that returns the IP of the nearest regional data center). This is extremely cheap and happens before any packet even reaches your infrastructure, which makes it excellent for coarse-grained decisions — like routing a European user to a European region and a US user to a US region.

Its major limitation is that DNS answers are cached — by the client's OS, by intermediate resolvers, by ISPs — for however long the record's TTL says, and that caching is entirely outside your control. If a backend IP goes down, clients who cached that answer keep trying to connect to a dead IP until their TTL expires, regardless of how low you set the TTL, because plenty of resolvers ignore or clamp very low TTLs. DNS has no concept of "current load" or "current health" beyond whatever a DNS-integrated health-checking service (like Route 53 health checks) can enforce by pulling unhealthy IPs from the answer set — and even then, propagation is slow compared to a real LB's sub-second failover.

Dedicated load balancer layers

This is where nginx, HAProxy, Envoy, or a cloud provider's ALB/NLB come in — a long-lived piece of infrastructure that every request actually flows through, which means it can react in real time: sub-second health check failover, per-request algorithmic routing (least connections, consistent hashing), TLS termination, and observability (it sees every request, so it's a natural place to emit metrics and logs).

The practical pattern almost every real system uses is both, layered: DNS routes a client to the nearest region or cluster (coarse, cheap, cacheable), and once traffic lands in that region, a dedicated L4/L7 balancer handles the fine-grained, real-time distribution and failover across the actual instance pool.

6. Sticky Sessions and Their Tension with Horizontal Scaling

A "sticky session" (session affinity) means the load balancer intentionally routes all requests from a given client to the same backend instance — usually implemented via a cookie the LB sets (e.g., an ALB's AWSALB cookie) or, at L4, by hashing the client's source IP to a backend.

Teams reach for stickiness when a backend holds some in-memory state a request needs — most commonly HTTP session data (e.g., a customer's in-progress cart before checkout), or a WebSocket connection (e.g., pushing live "your order has shipped" notifications) which is inherently long-lived and pinned to whichever instance accepted it. And it does work for that narrow purpose. But it directly undermines several things horizontal scaling is supposed to give you:

  • Uneven load: if a disproportionate number of "sticky" clients happen to land on one instance (e.g., a handful of high-traffic customers hammering checkout during a flash sale all get pinned to the same instance by bad luck in the hash), that instance gets overloaded while others idle — and the LB can't rebalance without breaking affinity.
  • Fragile scale-down and deploys: removing an instance that many clients are stuck to forces all of those clients to lose their in-memory state at once — their carts, mid-flash-sale — right when you most wanted a clean, low-impact rolling operation.
  • It reintroduces the exact coupling statelessness was meant to remove: correctness now depends on routing, so a load balancer configuration change or a failover event can surface as an application bug (customers losing their cart, their session, their in-progress upload).
The usual resolution

Rather than pinning a client to a specific instance to preserve state, externalize the state so any instance can serve any request: move cart/session data to Redis or a database, or eliminate server-side session storage altogether with a signed, stateless token (a JWT — see spring-security for how JWT verification actually works) that the client carries and any instance can validate without a lookup. Stickiness then becomes an optimization reserved for genuinely connection-bound protocols (WebSockets, gRPC streams — see grpc-protobuf) rather than a crutch for session state that shouldn't have been in-process memory to begin with.

7. The Incremental Scaling Path

Real systems don't jump straight to a globally sharded, multi-region architecture. They grow through a fairly consistent sequence of stages, each one solving the specific bottleneck the previous stage exposed. Understanding this progression matters because it tells you what problem you're actually solving at each point, rather than reaching for sharding when you really just need a cache, or a cache when you really just need a second app server. Trace ShopSphere through it:

  1. Single server: one machine runs the ShopSphere application and its database. Simple, but every dimension — CPU, memory, disk I/O, and single-point-of-failure risk — is shared and contended, and there's no redundancy at all. A flash sale here doesn't degrade gracefully — it takes the whole site down.
  2. Load balancer + multiple app servers: the application tier — order-service, catalog/search-service, etc. — is pulled onto its own machines, replicated, and put behind an LB (per sections 2–4 above). This solves application-tier CPU/throughput limits and removes the app tier as a single point of failure. It requires the statelessness precondition from section 1. The database is usually still a single instance at this stage — so this stage alone doesn't fix database bottlenecks, and a flash sale can still take down checkout by overwhelming the one orders database even with 20 app instances in front of it.
  3. Read replicas: the orders/catalog database is replicated to one or more read-only followers; the application sends writes (placing an order) to the primary and reads (browsing the catalog, checking an order's status) to the replicas. This solves read throughput (most systems, including a storefront, are read-heavy — far more people browse products than complete checkout) without touching the write path. It introduces replication lag — a replica can be milliseconds to seconds behind the primary — which means a customer who places an order and immediately refreshes their order history could read from a replica that hasn't caught up yet and see a stale "no orders" state, a correctness trade-off you now have to design around explicitly. See database-architecture for how replication actually works underneath this.
  4. Caching: a cache (in-process, or a shared layer like Redis/Memcached) sits in front of the database to absorb repeated reads of the same data, cutting both load on the database and response latency — e.g., caching a flash-sale product's detail page, since the same handful of hot productIds get read by thousands of customers per second. This solves the case where the bottleneck isn't "not enough replicas" but "we keep recomputing/refetching the same thing." It introduces its own hard problem — cache invalidation and staleness — covered in caching-strategies.
  5. Sharding (horizontal partitioning): once a single database's write throughput or total data volume exceeds what one primary (even a big vertically-scaled one) can hold, the data itself is split across multiple database instances by some partition key (customer ID range, hash of an order ID, seller region), and each shard handles only its slice of the data. This is the stage that actually breaks the "single database" ceiling that replication and caching couldn't touch — e.g., sharding the orders table by customerId once ShopSphere's total order volume outgrows one primary — at the cost of losing easy cross-shard transactions and joins.
Why the order matters

Each stage targets a specific bottleneck: stage 2 fixes application compute, stage 3 fixes read throughput, stage 4 fixes redundant work against the database, and stage 5 fixes total data/write-volume ceiling. Sharding a database to fix what was actually an application-tier CPU problem, or adding read replicas to fix what was actually a hot single-key contention problem that only caching would solve, buys enormous operational complexity for no improvement in the metric that was actually the bottleneck. Identifying which resource is actually saturated — app CPU, DB reads, DB writes, or total data size — should always come before picking the next stage. When ShopSphere's flash sale hammers checkout, the first diagnostic question is exactly this: is order-service CPU pegged (scale app tier), is the orders database drowning in reads of the same product/inventory rows (add caching), or is it choking on write throughput for the flood of new orders (that's the one caching and read replicas can't fix — you're looking at sharding or queuing writes through Kafka instead).

Putting it together: ShopSphere's flash-sale playbook

A flash sale is a useful stress test because it exercises nearly every mechanism on this page at once: the L7 balancer's least-connections algorithm keeps checkout traffic from piling onto a few order-service instances stuck waiting on payment-service; consistent hashing keeps the flood of "check product 8841's stock" reads landing on the same cache node instead of stampeding the database; aggressive active health checks pull a struggling instance out of rotation within seconds instead of letting it fail every request routed to it; and because the cart/session state was externalized to Redis instead of kept in-process, auto-scaling the checkout fleet from 2 to 20 instances mid-spike doesn't log anyone out or lose anyone's cart. None of these individually solves "the flash sale," but together they're what turns a 40x traffic spike into a routine, boring scale-out event instead of an incident.

Concepts Worth Being Able to Explain From First Principles

Why does horizontal scaling require statelessness, specifically — what breaks, mechanically, if it isn't stateless?
A load balancer's ability to freely choose any backend for any request is what gives horizontal scaling its benefits (even distribution, seamless failover, painless scale up/down). If a backend holds request-relevant state only in its own process memory, then which backend handled a client's previous request becomes load-bearing information that the LB doesn't have. The load balancer will happily route the client's next request to a different, equally healthy instance, because from its perspective all instances are interchangeable — that's the whole point of horizontal scaling. The result is that state the client's next request needed (their session, an in-progress computation, a lock) simply isn't there. The fix isn't to make the LB smarter about routing (that's sticky sessions, which just reintroduces the coupling); it's to move the state somewhere every instance can reach — a shared cache or database, or a token the client carries itself.
Concretely, why does adding one node to a modulo-hashed (hash % N) cluster remap almost every key, while consistent hashing remaps only a small fraction?
With hash % N, a key's owner is a function of N itself, not just the key. Changing N from, say, 10 to 11 changes the divisor for every single key's modulo operation, and there's no reason a key's remainder mod 10 would have any relationship to its remainder mod 11 — so ownership essentially randomizes across the whole keyspace. Consistent hashing avoids this because a key's owner is defined purely geometrically — "the first node clockwise of this key's position on the ring" — and adding a node only inserts one new point on the ring. That insertion only changes the answer for keys that fall in the arc between the new point and the previous node counter-clockwise of it; every key elsewhere on the ring still finds the same node first when walking clockwise, because nothing about their local neighborhood on the ring changed. The number of nodes N never appears as a divisor anywhere in the lookup, which is exactly what decouples "how many nodes exist" from "which keys move when that number changes."
What specifically can an L7 load balancer do that an L4 load balancer structurally cannot, and why?
An L4 balancer only ever sees IP addresses, ports, and raw bytes — it doesn't parse the payload as HTTP or any application protocol, so it has no concept of a "request" as a distinct unit; it just forwards packets for a given connection/flow to the same backend. Because of that, it cannot route based on URL path, headers, or cookies (there's no parsed structure to inspect), and it cannot transparently retry a failed request against a different backend, because retrying requires understanding where one logical request ends and the next begins, which only a protocol-aware (L7) component can determine. An L7 balancer terminates the client's TCP connection itself, actually parses the HTTP request, and opens its own separate connection to a chosen backend — that termination is exactly what lets it inspect, route on, modify, or resend the request independently of the client's original connection.
Why do health checks typically use separate "unhealthy threshold" and "healthy threshold" counts instead of reacting to a single failed or passed check?
A single check is a noisy signal — a backend might miss one probe due to a transient GC pause, a momentary network blip, or a slow but otherwise fine response, none of which mean the instance is actually broken. Requiring several consecutive failures before marking a node unhealthy filters out that noise so the LB doesn't yank a perfectly good instance out of rotation over one bad sample. Symmetrically, requiring several consecutive successes before adding a recovering instance back in prevents "flapping" — a node that's borderline (e.g., still warming up a cache, or intermittently timing out under residual load) getting added back, immediately failing again, getting removed, and repeating, which thrashes the pool and makes capacity unpredictable. The two independent thresholds let you tune "pull out fast" and "only bring back once genuinely stable" separately, since the cost of a false negative (serving traffic to a bad node) and a false positive (keeping capacity out of rotation unnecessarily) are different.
Why does DNS-based load balancing have such slow failover compared to a dedicated load balancer, even if you set the DNS TTL very low?
A DNS answer, once returned, is cached at multiple layers you don't control — the client's OS resolver cache, intermediate recursive resolvers run by ISPs or corporate networks, and sometimes the application itself if it caches resolved IPs internally. The TTL you set is only a request for how long those caches should hold the answer, not an enforceable guarantee; some resolvers clamp minimum TTLs upward regardless of what you specify, and some clients simply don't re-resolve until they hit a connection error. A dedicated load balancer has none of this indirection: every request physically flows through it, so when it marks a backend unhealthy, the very next request is routed elsewhere immediately, with no cached intermediate answer anywhere in the path that needs to expire first.
Why is "identify which resource is actually saturated" the right first step before picking read replicas, caching, or sharding?
Each stage of the scaling path targets a specific, different bottleneck: read replicas increase read throughput by adding more machines capable of answering read queries, but do nothing for write throughput or total data volume, since writes still funnel through one primary. Caching reduces redundant repeated reads/computation, but if your problem is that writes are overwhelming the primary, or that your total dataset no longer fits your storage tier, a cache in front of reads doesn't touch either problem. Sharding solves write-throughput and total-data-volume ceilings by splitting the data itself across multiple independent database instances, but adds real complexity (no easy cross-shard joins or transactions) that's wasted effort if your actual bottleneck was application-tier CPU that a second app server behind a load balancer would have fixed far more cheaply. Applying the wrong stage doesn't just fail to help — it adds durable architectural complexity (extra replicas, cache invalidation logic, shard-routing logic) that has to be maintained indefinitely without addressing the metric that was actually maxed out.
Why does adding virtual nodes to a consistent hashing ring improve load distribution without giving up the "minimal remapping" property?
The minimal-remapping property comes from the ring/clockwise-lookup structure itself — inserting or removing a point on the ring only affects the arc adjacent to that point, regardless of how many points total are on the ring or how they got there. That property holds whether a physical node has one point on the ring or a hundred. What virtual nodes fix is a separate issue: with very few points on the ring, their positions (determined by hashing node identifiers) can by chance cluster unevenly, giving some physical nodes a much larger arc — and therefore a much larger share of keys — than others purely due to randomness in where the hash function happened to place them. Giving each physical node many differently-salted virtual positions spreads that node's total "presence" thinly and evenly around the entire ring, so statistically each physical node ends up owning close to an equal total arc length. Because each virtual node is still just an independent point subject to the same insertion/removal rule, adding or removing a physical node (all its virtual points at once) still only disturbs the arcs immediately adjacent to each of its virtual points — the two properties, even distribution and minimal remapping, are achieved by two different aspects of the same structure and don't trade off against each other.
