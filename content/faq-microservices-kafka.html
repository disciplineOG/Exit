Most Asked Interview Questions: Microservices, REST APIs & Kafka

Microservices Patterns Service Discovery API Idempotency Kafka Internals Saga Pattern Circuit Breaker
Why this matters

Once a backend interview moves past a single Spring Boot service, it almost always pivots to how that service behaves as one node in a larger distributed system: how it finds its neighbors, how it exposes a contract other teams can rely on, and how it survives a downstream failure without cascading. Microservices, REST API design, and Kafka are the three legs of that conversation, and interviewers use them to separate candidates who have only built inside a monolith from those who have actually operated a distributed system in production. This page collects the questions that come up over and over — from "why avoid two-phase commit across services" to "what does acks=all actually guarantee" — so you can give precise, example-backed answers instead of hand-waving about "eventual consistency."

Microservices Fundamentals

What are the trade-offs between a monolith and a microservices architecture?
A monolith deploys the entire application as a single unit with one codebase, one build, and typically one database, which makes local development, transactions, and end-to-end debugging simple because everything runs in one process. Microservices split the application along business-capability boundaries (order-service, inventory-service, payment-service, and so on in ShopSphere) into independently deployable services that communicate over the network, which buys you independent scaling, independent deployment cadence per team, and fault isolation — a bug in notification-service doesn't take down checkout. The cost is real, though: you trade in-process function calls for network calls (which are slower and can fail partway through), you lose easy ACID (Atomicity, Consistency, Isolation, Durability) transactions across service boundaries, and you take on substantial operational overhead — service discovery, distributed tracing, deployment pipelines per service, and monitoring across dozens of moving parts. The interview-ready framing: microservices solve organizational and scaling problems (many teams, independent release cycles, different scaling profiles per component) at the cost of distributed-systems complexity, and they're a poor choice for a small team or an early-stage product that doesn't have those problems yet.
What is service discovery, and what's the difference between client-side and server-side discovery?
In a microservices system, service instances come and go constantly due to auto-scaling, deployments, and failures, so a service can't hard-code the network address of another service it needs to call — it needs a way to look up healthy instances at runtime. A service registry (like Netflix Eureka or Consul) is the directory that solves this: instances register themselves on startup and send periodic heartbeats, and stale entries are evicted if heartbeats stop. In client-side discovery, the calling service (e.g. order-service) itself queries the registry, gets back a list of healthy inventory-service instances, and picks one using its own load-balancing logic (often via a library like Spring Cloud LoadBalancer) — this keeps the extra network hop out of the request path but means every client needs the discovery logic and library baked in. In server-side discovery, the client just calls a fixed address (a load balancer or API gateway), and that intermediary is the one that queries the registry and routes the request — this is simpler for clients (no discovery-aware library needed, works even for non-Java or legacy clients) but adds a hop and makes the load balancer itself a piece of infrastructure that must be highly available. Kubernetes' built-in Service abstraction is a common real-world example of server-side discovery, since kube-proxy handles the routing to healthy pod IPs transparently.
What is an API gateway, and what responsibilities does it typically own?
An API gateway is a single, centralized entry point that sits between external clients and the internal microservices, so a client of ShopSphere never talks directly to order-service or payment-service — it talks to the gateway, which routes the request onward. Its core responsibility is request routing: mapping an incoming path like /api/orders/* to the correct backend service. Beyond routing, gateways typically centralize cross-cutting concerns that would otherwise be duplicated in every service: authentication and authorization (validating a JWT (JSON Web Token) once at the edge rather than in every service), rate limiting and throttling per client, request/response logging and metrics collection, SSL (Secure Sockets Layer) termination, and sometimes response aggregation (fanning a single client request out to multiple backend services and composing the results, useful for a mobile client that wants order details plus payment status in one call). Centralizing these concerns at the gateway avoids reimplementing auth and rate-limiting logic in every one of ShopSphere's five services, but it also means the gateway itself becomes a critical piece of infrastructure that must be scaled and made highly available, since every request passes through it.
What is the circuit breaker pattern, and what do its closed, open, and half-open states mean?
A circuit breaker wraps a call to a potentially-failing remote dependency (like order-service calling payment-service) and stops making that call entirely once failures cross a threshold, instead of letting every request pile up waiting on a service that's already struggling — this prevents one slow or dead dependency from exhausting the caller's threads and cascading the failure upstream. It's implemented as a state machine with three states. Closed is the normal state: requests flow through to the real dependency, and the breaker just counts recent successes and failures. If the failure rate crosses a configured threshold (say, 50% of the last 20 calls to payment-service failed), the breaker trips to Open: for a configured wait duration, every call fails immediately (or falls back to a default/cached response) without even attempting the network call, giving the struggling dependency time to recover instead of piling on more load. After that wait duration elapses, the breaker moves to Half-Open, where it allows a small number of trial requests through to test whether the dependency has recovered — if those succeed, it closes again and resumes normal traffic; if they fail, it reopens and restarts the wait timer. Resilience4j is the standard Java library implementing this pattern, typically applied via an annotation or a wrapped functional call around the remote invocation.
Why are distributed transactions hard, and why is two-phase commit generally avoided across microservices?
A distributed transaction needs to atomically commit or roll back changes across multiple independent data stores — for example, ShopSphere placing an order needs to debit inventory in inventory-service's database and create a payment record in payment-service's database as a single all-or-nothing unit. Two-Phase Commit (2PC) is the classic protocol for this: a coordinator asks every participant to "prepare" (lock resources and confirm they can commit) in phase one, and only if every participant says yes does it tell them all to actually commit in phase two. The problem is that 2PC requires holding locks on rows/resources in every participating database for the entire duration of the coordination round trip, which kills throughput and creates a single point of failure — if the coordinator crashes after phase one, participants can be left blocked indefinitely holding locks, waiting for a commit or rollback instruction that never comes. It also requires every participating datastore to support the XA (eXtended Architecture) transaction protocol, which many modern databases, caches, and message brokers simply don't, and it fundamentally conflicts with the reason you split into microservices in the first place — independent, loosely-coupled services shouldn't need synchronous, blocking coordination just to complete a business operation. This is exactly why the industry standard answer is to give up strict ACID consistency across services and instead use the saga pattern for eventual consistency.
What is the saga pattern, and what's the difference between choreography and orchestration?
A saga breaks a distributed business transaction into a sequence of local transactions, each owned by a single service, where every step has a corresponding compensating action that can undo it if a later step fails — this replaces atomic all-or-nothing commits with eventual consistency achieved through forward progress plus rollback-by-compensation. For example, placing a ShopSphere order might be: order-service creates the order in a PENDING state, inventory-service reserves stock, payment-service charges the customer; if the payment step fails, the saga runs compensating actions in reverse — release the inventory reservation, then cancel the order — rather than relying on a database rollback that can't span services. Choreography implements this with no central coordinator: each service publishes an event when it finishes its step (inventory-service emits InventoryReserved), and the next service in the chain listens for that event and reacts (payment-service consumes it and attempts the charge), typically over Kafka. This keeps services fully decoupled but makes the overall flow hard to see in one place and hard to debug once there are many steps. Orchestration introduces a central saga orchestrator that explicitly tells each service what to do next and listens for the result, making the flow's logic live in one visible place (easier to trace and modify) at the cost of that orchestrator becoming a more tightly coupled, critical component. Choreography tends to fit simpler, shorter sagas; orchestration tends to win once a saga has many steps or complex conditional branching.
What is the database-per-service pattern, and why is a shared database across services considered an anti-pattern?
Database-per-service means each microservice owns its own database (or schema) exclusively, and no other service is allowed to read from or write to it directly — if order-service needs product pricing data that catalog-service owns, it must ask catalog-service through its API (or consume events it publishes), never query catalog-service's tables directly. Sharing one database across multiple services is an anti-pattern because it silently recreates the tight coupling microservices are supposed to eliminate: any service can change its own tables freely without breaking others only if no other service depends on those tables' internal structure, but a shared database makes that structure a de facto public contract that any service might depend on, so a schema migration in one team's code can break a completely unrelated team's service with no warning. It also destroys independent scalability and technology choice (every service is now stuck on one database engine and one connection pool budget) and makes it impossible to reason about which service is actually responsible for a given piece of data. The trade-off you accept for enforcing this boundary is that queries spanning multiple services' data (like "show me a customer's orders with current product names") can no longer be a single SQL join — you either denormalize data locally via events, aggregate at the API layer, or build a dedicated read-model/reporting service that stitches data together asynchronously.
Should services communicate synchronously (REST/gRPC) or asynchronously (Kafka), and how do you choose?
Synchronous communication means the caller sends a request and blocks waiting for a response before continuing — a typical REST or gRPC (Google Remote Procedure Call) call, like order-service calling payment-service directly to charge a card and needing the result immediately to decide whether the order succeeds. It's simple to reason about (the response tells you the outcome right away) but couples the caller's availability to the callee's: if payment-service is slow or down, order-service's request hangs or fails too, and chaining several synchronous calls multiplies latency and failure surface. Asynchronous communication means the caller publishes an event or message and moves on without waiting — order-service publishes an OrderPlaced event to Kafka, and inventory-service, payment-service, and notification-service each consume it independently on their own schedule. This decouples services in time (a consumer can be temporarily down and catch up later) and in availability (a slow notification-service can't block checkout), at the cost of giving up an immediate response — the caller can't know synchronously whether inventory-service actually succeeded, so the system has to be designed around eventual consistency, and error handling (what happens if a consumer fails to process an event) needs its own mechanisms like retries and dead-letter topics. The practical rule of thumb: use synchronous calls when the caller genuinely needs an immediate answer to proceed (checking whether a payment authorization succeeded before confirming an order to the customer), and use asynchronous messaging for anything that can happen "eventually" and where you want services decoupled from each other's uptime (sending a confirmation email, updating a recommendations index, notifying a warehouse system).
How do services find and verify each other's health in production — what's the difference between a liveness probe and a readiness probe?
A liveness probe answers "is this process still alive and functioning, or is it stuck/deadlocked and needs to be killed and restarted?" — orchestrators like Kubernetes call a liveness endpoint (often /health/live) on a schedule, and if it fails enough times in a row, Kubernetes kills the container and starts a fresh one, since a hung process that never recovers on its own needs to be forcibly restarted. A readiness probe answers a different question: "is this instance currently able to accept traffic?" — an instance can be perfectly alive but not ready, for example ShopSphere's order-service right after startup while it's still warming up its database connection pool or loading a local cache; if the readiness check (often /health/ready) fails, Kubernetes simply stops routing new requests to that instance without killing it, and resumes sending traffic once the check passes again. Conflating the two is a common production mistake: wiring a downstream dependency check (like "can I reach payment-service") into the liveness probe means a temporary outage in payment-service causes Kubernetes to repeatedly kill and restart order-service instances that are actually fine themselves, worsening an already-bad situation — that kind of downstream check belongs in readiness, not liveness. Getting this distinction right is exactly the kind of operational detail that separates candidates who've only read about Kubernetes from those who've actually run services in it.
How do you diagnose and prevent cascading failures across microservices in production?
A cascading failure starts when one service becomes slow or unavailable (say, inventory-service's database is under load) and that slowness propagates upstream: every caller (order-service) has threads or connections blocked waiting on inventory-service's slow responses, those threads pile up until order-service's own thread pool or connection pool is exhausted, and now order-service itself appears "down" to its callers even though its own code and database are perfectly healthy — the failure cascades outward from the original bottleneck. Diagnosing this in production relies on distributed tracing (a tool like Jaeger or Zipkin, propagating a correlation/trace ID through every hop) to see exactly where latency is accumulating across the call chain, combined with per-dependency metrics (latency and error-rate dashboards broken out by downstream call, not just an aggregate) so you can isolate which specific dependency started the problem instead of just seeing that "everything is slow." Prevention combines several patterns discussed elsewhere on this page working together: circuit breakers stop a caller from continuing to hammer a struggling dependency, bulkheads (isolating separate thread/connection pools per downstream dependency) ensure a slow inventory-service can't exhaust the same pool that calls to payment-service depend on, aggressive and consistent request timeouts prevent threads from blocking indefinitely, and load shedding (rejecting excess requests outright once a service is near saturation, rather than queueing them and getting slower for everyone) protects the service's own stability. The interview signal here is knowing that no single pattern fully solves this — production resilience comes from timeouts, circuit breakers, and bulkheads applied together, not any one of them alone.

REST API Design

What is idempotency in the context of a REST API, and which HTTP methods are idempotent by specification?
An operation is idempotent if making the same request multiple times produces the same end state as making it once — the side effect doesn't accumulate or change on repeated calls, even though the response itself might differ (e.g. a 200 the first time, a 404 on a later delete of an already-deleted resource). By the HTTP specification, GET, PUT, DELETE, HEAD, and OPTIONS are all idempotent: calling PUT /orders/123 with the same payload five times leaves the order in the exact same final state as calling it once, and calling DELETE /orders/123 repeatedly leaves the order deleted regardless of how many times you call it. POST is explicitly not idempotent by spec, because POST conventionally means "create a new resource" or "perform an action," so calling POST /orders twice with an identical body naturally creates two separate orders. This matters enormously in distributed systems because networks fail in ambiguous ways — if a client sends a request and the connection drops before the response arrives, the client can't tell whether the server actually processed it, so it must decide whether it's safe to retry; idempotent methods can always be safely retried, while POST requires an extra mechanism (like a client-supplied idempotency key) to be made safely retriable, which is exactly how ShopSphere's payment-service prevents a network-retried "charge card" request from double-charging a customer. A related but distinct concept is safety: a method is "safe" if it never modifies server state at all, which only GET, HEAD, and OPTIONS satisfy — every safe method is automatically idempotent (making the same read-only call repeatedly can't change the end state), but the reverse isn't true, since PUT and DELETE are idempotent yet clearly not safe, as they do modify state.
What are the main HTTP status code categories, and when should you use 400 vs 401 vs 403 vs 409 vs 422?
HTTP status codes fall into five categories by their leading digit: 1xx is informational (rarely seen at the application level), 2xx means success (200 OK, 201 Created, 204 No Content), 3xx means redirection, 4xx means the client made an error, and 5xx means the server failed to handle an otherwise-valid request. Within 4xx, the distinctions interviewers probe for are precise: 400 Bad Request means the request itself is malformed — invalid JSON syntax, a missing required field, a string where a number was expected — the server can't even meaningfully parse the intent. 401 Unauthorized actually means "unauthenticated" despite the confusing name — the request has no valid credentials at all (missing or expired token), and the fix is to log in or refresh the token. 403 Forbidden means the credentials are valid and the caller is authenticated, but that specific identity is not allowed to perform this action — a ShopSphere Customer trying to hit an Admin-only endpoint to delete a product. 409 Conflict means the request is well-formed and the caller is allowed to make it, but it conflicts with the current state of the resource — ordering the last unit of a product that another concurrent request just claimed, or a version mismatch on an optimistic-locked update. 422 Unprocessable Entity means the request is syntactically valid (well-formed JSON, right types) but semantically invalid against business rules — an order request with a negative quantity or an email field that fails format validation. The one-line distinguishing test: 400 is "I can't parse this," 401 is "I don't know who you are," 403 is "I know who you are and the answer is no," 409 is "this collides with existing state," and 422 is "I understood this perfectly and it's still invalid."
What are the main API versioning strategies, and what are the trade-offs between URI-based and header-based versioning?
API versioning exists because you inevitably need to make breaking changes to a contract while existing clients still depend on the old one, so you need a way for a client to request a specific version. URI-based versioning embeds the version directly in the path, like /api/v1/orders versus /api/v2/orders — it's the most common approach in practice because it's immediately visible, trivially cacheable by URL, easy to route at the gateway or load-balancer level, and easy to test by just hitting a different URL in a browser or curl. Header-based versioning keeps one canonical URI and specifies the version in a custom header (like X-API-Version: 2) or via content negotiation in the Accept header (like Accept: application/vnd.shopsphere.v2+json) — this keeps URLs clean and arguably more RESTful (the resource identity doesn't change just because its representation format did), but it's less discoverable, harder to test casually, and harder to route at infrastructure layers that don't inspect headers by default. Other options that come up include query-parameter versioning (/orders?version=2, simple but easy to omit accidentally) and no explicit versioning at all combined with strict backward-compatibility discipline (only ever adding optional fields, never removing or renaming). In an interview, the practical answer most companies converge on is URI-based versioning for its operational simplicity, reserving header-based approaches for teams that specifically prioritize URL purity and already have strong API-gateway tooling.
What's the difference between offset-based and cursor-based pagination?
Offset-based pagination uses a page number or a skip count plus a limit, like GET /products?offset=40&limit=20, and the database executes something like OFFSET 40 LIMIT 20. It's simple to implement and lets a client jump directly to an arbitrary page, but it has two real problems at scale: performance degrades as the offset grows because the database still has to scan and discard all the skipped rows before it can return the requested slice, and it's unstable under concurrent writes — if a new product is inserted while a client is paging through catalog-service's results, rows can shift between pages, causing the client to see a duplicate or skip an item entirely. Cursor-based pagination instead returns an opaque token (the cursor) pointing at the last item of the current page — typically encoding that item's sort key, like its ID or timestamp — and the next request says "give me the next 20 items after this cursor," which the database implements as an indexed WHERE id > :cursor ORDER BY id LIMIT 20 rather than a scan-and-discard. This stays fast regardless of how deep you page and is stable under concurrent inserts/deletes, which is why it's the standard choice for high-volume, frequently-changing feeds like an infinite-scroll product listing or an order history feed — the trade-off is that clients lose the ability to jump straight to "page 7," since a cursor only knows how to move forward (or backward) from a specific point.
What is HATEOAS, and what does it add to a REST API at a basic level?
HATEOAS (Hypermedia As The Engine Of Application State) is the constraint, from Roy Fielding's original REST definition, that a server's response should include links describing what actions or related resources are available next, so a client can navigate the API dynamically rather than having every possible URL hard-coded in advance. Concretely, instead of a response for GET /orders/123 just returning the order's fields, a HATEOAS-compliant response also embeds a links array pointing to related actions valid for that order's current state — a link to cancel it (only present if the order is still cancellable), a link to view its payment, a link to the customer who placed it. The practical benefit is that clients become less brittle to URL changes and can react to state (a shipped order simply won't include a "cancel" link, so the client doesn't need to hard-code that business rule itself), and API discovery becomes self-documenting. In practice, full HATEOAS is uncommon in real-world microservice APIs (most REST APIs, including typical ShopSphere-style services, are what's called "Level 2" on the Richardson Maturity Model — proper use of HTTP verbs and status codes, but no hypermedia links) because it adds real complexity for a benefit that mostly matters for public, long-lived APIs with many independent third-party clients rather than internal service-to-service calls where both sides deploy in lockstep.
What's the difference between PUT, PATCH, and POST?
POST is used to create a new resource (or trigger a non-idempotent action) when the client doesn't get to choose the resource's final identifier — POST /orders creates a new order and the server assigns its ID, and calling it twice creates two orders. PUT is used to replace a resource entirely at a known URI: the request body represents the complete desired state of that resource, so PUT /products/55 with a full product payload overwrites every field, and any field omitted from the request is treated as cleared/reset rather than left alone — this is also why PUT is idempotent, since sending the same full replacement twice leaves the resource in the same end state. PATCH applies a partial update: the request body only contains the fields that should change, like {"price": 29.99} to update just a product's price without touching its name, description, or stock count, leaving every other field untouched. The distinguishing question to lead with in an interview: POST is "create, server decides the ID," PUT is "replace the whole thing at this exact URI," and PATCH is "modify only these specific fields of the thing at this URI" — and mixing these up (like using PUT for a partial update) is a common code-review flag because it silently wipes fields the client didn't intend to touch.
What does it mean for a REST API to be "stateless," and why does that constraint matter?
Statelessness means the server keeps no memory of a client's previous requests between calls — every request must carry all the information the server needs to process it (an authentication token, any needed parameters), rather than the server relying on session data left over from an earlier request from that same client. Concretely, a stateless order-service doesn't keep an in-memory "current logged-in user" tied to a specific server instance; every request to GET /orders includes a bearer token in the header, and any of ShopSphere's order-service instances can validate that token and serve the request without needing to have seen that client before. This matters enormously for scaling a distributed system: because no server instance holds client-specific state, a load balancer can route any request to any healthy instance interchangeably, instances can be added, removed, or restarted without losing anyone's "session," and there's no need for sticky sessions or session replication across instances. The trade-off is that the client (or a token) has to carry more information on every request, and any state that legitimately needs to persist across requests (a shopping cart, for example) has to live in a shared, durable store like a database or Redis rather than in a server's memory — this is precisely why a stateless architecture is a prerequisite for horizontal scaling in a microservices system.
How do you design an API so you can evolve it without breaking existing clients — what counts as a breaking vs. non-breaking change?
A non-breaking change is one that existing, unmodified clients can safely ignore and keep working through: adding a new optional field to a response, adding a new optional query parameter, adding an entirely new endpoint, or adding a new enum value that old clients simply don't expect yet (as long as they're written to ignore unknown values rather than fail on them). A breaking change is one that requires clients to update their code to keep working: removing or renaming a field, changing a field's data type (a price field going from a number to a nested object), changing validation rules to reject previously-valid requests, or changing the meaning of an existing field. At scale, with dozens of independent client teams or third parties integrating against a public API, the senior-level judgment call is recognizing that most "necessary" breaking changes can be avoided by additive design: instead of changing an existing field's meaning, add a new field alongside it and deprecate the old one over a announced timeline; instead of tightening validation on an existing endpoint, introduce a new version or a new endpoint. When a genuine breaking change is unavoidable, the standard production playbook is to version the API (see the versioning strategies discussed above), run both versions in parallel, instrument the old version's usage so you know when it's safe to sunset, and give consumers a deprecation window with real lead time — a company the size of ShopSphere with external Seller-facing APIs would typically commit to a fixed deprecation window (e.g. 6-12 months) as a contractual expectation.
How would you design rate limiting for a public REST API, and what algorithms are commonly used?
Rate limiting caps how many requests a client (identified by API key, user ID, or IP address) can make in a given time window, protecting backend services from being overwhelmed by a single misbehaving or abusive client and enforcing fair usage across tenants — ShopSphere might allow a Seller's integration to call the catalog-service API 1,000 times per minute before returning 429 Too Many Requests. The fixed window algorithm counts requests in discrete time buckets (e.g. reset every minute on the clock) — simple to implement but allows a burst of up to 2x the limit right at the window boundary (a client sends the full quota at 11:00:59 and another full quota at 11:01:00). The sliding window algorithm smooths this out by weighting the previous window's count proportionally to how much of it overlaps the current moment, avoiding the boundary-burst problem with modest extra bookkeeping. The token bucket algorithm gives each client a bucket that refills with tokens at a steady rate up to a cap, and each request consumes one token — this is the most commonly used approach in real systems because it naturally allows short bursts (using up saved tokens) while still enforcing a steady-state average rate, and it's cheap to implement with a counter and a timestamp in Redis. At the architecture level, rate limiting is almost always enforced at the API gateway (a single, centralized layer) rather than duplicated inside every individual service, both to keep the logic in one place and because the gateway sees traffic from all clients before it's distributed to backend instances, making the counts accurate.

Kafka & Async Messaging

What is Kafka, and what are the roles of a producer, broker, and consumer at a basic level?
Apache Kafka is a distributed event-streaming platform: at its core it's a durable, high-throughput log that lets one part of a system publish a record of "something happened" and lets other parts read that record independently, without the publisher and the readers needing to talk to each other directly or be online at the same time. A producer is any application or service that writes (publishes) messages to Kafka — ShopSphere's order-service acting as a producer when it publishes an OrderPlaced event after saving a new order. A broker is a single Kafka server that stores data and serves read/write requests; a Kafka cluster is made up of multiple brokers working together, each holding a subset of the cluster's data, which is what gives Kafka both fault tolerance (data is replicated across brokers) and horizontal scalability (more brokers means more storage and throughput capacity). A consumer is any application that reads messages back out — inventory-service and notification-service both acting as independent consumers of the same OrderPlaced event, each processing it for their own purpose (reserving stock, sending a confirmation email) without knowing or caring about each other. This basic producer-broker-consumer shape is the foundation everything else about Kafka (topics, partitions, consumer groups, delivery semantics) builds on top of.
What are Kafka topics and partitions, and how does partition count relate to parallelism?
A Kafka topic is a named, durable log of messages — for example ShopSphere's order-events topic carrying every OrderPlaced event. Under the hood, a topic is split into one or more partitions, each of which is an independent, strictly-ordered, append-only log stored on disk; a topic with 6 partitions is really 6 separate logs, and Kafka distributes those partitions across the brokers in the cluster for both storage capacity and throughput. When a producer publishes a message, it's routed to exactly one partition — by default via a hash of the message key (so all events for the same order ID land in the same partition, in order), or round-robin if no key is given. Partition count is the fundamental unit of parallelism in Kafka: within a single consumer group, each partition can only be actively read by one consumer instance at a time, so if order-events has 6 partitions, you can have at most 6 consumer instances in one group actively processing in parallel — adding a 7th instance leaves it idle. This is why partition count is a capacity-planning decision made up front: too few partitions caps your maximum consumption parallelism, but partitions can only be increased later, never decreased, and increasing them reshuffles key-to-partition assignment, breaking ordering guarantees for existing keys.
What are consumer groups, and how do offset tracking and rebalancing work?
A consumer group is a named set of consumer instances that cooperate to consume a topic, with Kafka guaranteeing that each partition is assigned to exactly one consumer within the group at any given time — this is what turns partitions into a load-balancing mechanism, since ShopSphere could run 4 instances of a consumer group called inventory-service-group reading order-events, and Kafka spreads the topic's partitions across those 4 instances automatically. Each consumer group tracks its own offset per partition — a simple integer marking the position of the last message the group has processed — stored durably in an internal Kafka topic called __consumer_offsets, which is what lets a consumer resume exactly where it left off after a restart instead of reprocessing the entire log or losing its place. Rebalancing is the process of reassigning partitions among the live consumers in a group whenever group membership changes — a consumer crashes, a new instance joins, or one is scaled down — coordinated by a broker acting as the group coordinator; during a rebalance, consumption briefly pauses while partitions are reassigned, which is why frequent rebalances (often caused by consumers taking too long between polls and being kicked out as presumed-dead) are a common real-world Kafka performance problem worth knowing how to diagnose.
What's the difference between at-least-once, at-most-once, and exactly-once delivery semantics?
These three describe the guarantee a messaging system makes about how many times a message will be delivered and processed. At-most-once means a message is delivered zero or one times — if anything goes wrong (a consumer crashes after receiving but before finishing processing), the message is simply lost, never redelivered; this happens if a consumer commits its offset immediately upon receiving a message, before actually processing it. At-least-once means a message is guaranteed to be delivered one or more times — the consumer only commits its offset after successfully finishing processing, so if it crashes mid-processing and restarts, it re-reads and reprocesses that same message, meaning duplicate processing is possible and the consumer logic must be written to tolerate it (which is exactly why idempotent consumers matter). Exactly-once means each message affects the end state as if it were processed precisely one time, with no loss and no duplication — Kafka supports this end-to-end via idempotent producers (deduplicating retried sends) combined with transactional writes that atomically commit a consumer's offset and its produced output together, but it requires both producer and consumer to opt into the transactional API and only holds within Kafka itself, not automatically across a side effect like a database write or an external API call. In practice, most real systems, including a typical ShopSphere consumer, target at-least-once delivery paired with idempotent processing (e.g. checking whether an order ID has already been reserved before reserving inventory again) because it's simpler to reason about and operate than full exactly-once transactions.
How does Kafka differ architecturally from a traditional message broker like RabbitMQ?
RabbitMQ is a traditional message broker built around queues: a producer publishes a message to an exchange, which routes it into one or more queues, and once a consumer acknowledges a message, it's removed from the queue — the broker's job is to track "has this been delivered" per message and typically delete it after successful delivery. Kafka is fundamentally a distributed, append-only, partitioned commit log: messages are retained on disk for a configured retention period (or indefinitely) regardless of whether any consumer has read them, and consumers track their own position (offset) in that log rather than the broker deleting messages on acknowledgment — this means multiple independent consumer groups can each read the exact same topic at their own pace, and a new consumer group can replay the entire history from the beginning. This log-based model is why Kafka excels at high-throughput event streaming and event sourcing (ShopSphere could replay all historical OrderPlaced events to rebuild a new analytics service's state from scratch), while RabbitMQ's queue model, with richer routing logic (topic exchanges, fanout, direct routing, priority queues, per-message TTL (Time To Live)) and lower per-message latency, tends to fit classic task-queue and work-distribution use cases better. The practical rule of thumb: reach for Kafka when you need high-throughput event streams, replayability, or multiple independent consumers of the same event history; reach for RabbitMQ when you need complex routing rules or a straightforward, low-latency task queue.
What do Kafka's producer acknowledgment levels (acks=0, acks=1, acks=all) mean, and what durability trade-off does each make?
The acks producer setting controls how many brokers must confirm they've received a message before the producer considers the send successful, directly trading off durability against latency/throughput. acks=0 means the producer doesn't wait for any acknowledgment at all — it fires the message and moves on immediately, giving the lowest latency and highest throughput but the weakest guarantee, since a message can be silently lost if the broker never actually receives it (e.g. a network blip) and the producer would never know. acks=1 means the producer waits for acknowledgment only from the partition's leader broker, which is a reasonable middle ground, but if that leader crashes right after acknowledging and before the message has been replicated to any follower, the message is lost when a follower is promoted to leader. acks=all (equivalently acks=-1) means the producer waits for acknowledgment from the leader and every in-sync replica (a follower broker that is fully caught up with the leader) before considering the send successful, giving the strongest durability guarantee — a message survives even if the leader immediately crashes — at the cost of higher latency, since the producer waits on multiple brokers per send. For anything financially sensitive, like ShopSphere's payment-service publishing a PaymentCaptured event, acks=all is the correct choice despite the latency cost; a high-volume, loss-tolerant stream like page-view analytics might reasonably use acks=1 or even acks=0.
What is the outbox pattern, and what problem does it solve for publishing events alongside a database write?
The problem it solves is the "dual write" problem: if a service needs to both update its own database and publish an event about that change (order-service saving a new order row and then publishing an OrderPlaced event to Kafka), doing these as two separate operations is inherently unsafe — if the database commit succeeds but the Kafka publish fails (or the process crashes in between), the event is silently lost and downstream services like inventory-service never find out the order happened, even though it exists in the database. The outbox pattern solves this by writing the event into an outbox table in the same local database, as part of the exact same ACID transaction as the business data change — so either both the order row and its corresponding outbox row are committed together, or neither is, which is a guarantee a single database can make natively. A separate asynchronous process (either a polling job that reads new outbox rows and publishes them to Kafka, or more commonly Change Data Capture (CDC) tooling like Debezium tailing the database's write-ahead log) then reads those outbox rows and reliably publishes them as Kafka events, marking them as sent once the publish succeeds. This converts an unsafe dual write across two different systems into a safe single-system transaction plus a reliable, retryable relay step, at the cost of some added latency between the write and the event actually reaching Kafka, and it typically requires downstream consumers to be idempotent since the relay step can occasionally redeliver an event it already sent but failed to mark as sent.
What ordering guarantees does Kafka provide, and are messages ordered across an entire topic?
Kafka guarantees strict ordering within a single partition only: messages are appended to a partition's log in the order they're received, and any consumer reading that partition reads them back in that exact same order. Kafka makes no ordering guarantee across partitions — if order-events has 6 partitions, an event for order A on partition 2 and an event for order B on partition 5 have no defined relative ordering, and even multiple events for the same logical entity can end up out of order if they're routed to different partitions. This is precisely why the producer's partitioning key matters so much: by keying messages on something like the order ID (so every event related to a given order — OrderPlaced, InventoryReserved, PaymentCaptured — hashes to the same partition), you get a practical, per-entity ordering guarantee without needing global ordering across the entire topic, which wouldn't scale anyway since it would force everything through a single partition. The interview trap to watch for: choosing a partition key that's too coarse (like a fixed constant, forcing every message onto one partition) kills parallelism, while choosing one that's too fine or inconsistent (switching keys for what should be the same logical entity) silently breaks the ordering guarantee you actually needed.
Given Kafka's at-least-once delivery, how do you actually build an idempotent consumer?
Since Kafka's default operating mode redelivers a message whenever a consumer crashes after processing but before committing its offset, the consumer's business logic itself has to guarantee that processing the same message twice produces the same end state as processing it once — Kafka can't guarantee this for you at the application level. The standard technique is to track which messages (or which business operation) have already been applied, using a natural identifier already present in the message, like an order ID or a dedicated message ID, and check it before acting: inventory-service, before reserving stock for an OrderPlaced event, checks whether a reservation already exists for that order ID and skips the work if so. This check-and-act is usually implemented as a unique constraint in the database on that ID (so a duplicate insert fails safely and can be caught and ignored) rather than a separate "have I seen this" read-then-write, since the latter has its own race condition under concurrent processing. Another common pattern is making the operation itself naturally idempotent regardless of duplicates — an UPDATE inventory SET reserved = reserved + 5 WHERE order_id = ? AND NOT EXISTS (...) style guarded write, or simply designing the write as a "set to absolute value" rather than "increment by," since overwriting the same final state twice is safe by construction. The interview-ready summary: Kafka guarantees delivery, not exactly-once side effects, so idempotency has to be engineered into the consumer's own persistence layer, typically via a uniqueness constraint keyed on the message's business identifier.
How long does Kafka retain messages, and what is log compaction?
By default, Kafka retains messages in a topic for a configurable time window (commonly 7 days, set via retention.ms) or until the log reaches a configurable size limit, whichever comes first — after that, older log segments are deleted regardless of whether any consumer group has read them, since Kafka doesn't track "has everyone consumed this" the way a traditional queue does. This time/size-based retention is the right model for event streams like order-events, where you care about the sequence of things that happened. Log compaction is a different retention strategy, enabled per-topic, designed for topics that represent "current state per key" rather than a history of events: instead of deleting old messages by age, Kafka keeps only the most recent message for each distinct key and discards earlier ones with the same key, so a compacted product-inventory-levels topic keyed by product ID would always retain just the latest stock count per product, no matter how many updates were published over time. This makes a compacted topic usable as a durable, replayable snapshot of current state — useful for rebuilding a cache or a new service's local state from scratch by replaying the topic — while a time-retained topic is better understood as a rolling window of history. Choosing between them is a per-topic decision based on whether consumers need "everything that happened" or "just the latest value per key."
Your Kafka consumer group is falling behind (growing consumer lag), or one message keeps crashing the consumer — how do you handle it in production?
Consumer lag is the difference between the latest offset written to a partition and the offset a consumer group has actually processed — a growing lag on inventory-service's consumer group means events are arriving faster than they're being processed, and the fix depends on the root cause. If the consumer logic itself is slow (a slow downstream database call per message), the fix is usually optimizing that hot path or batching writes; if the consumer is healthy but under-provisioned, the fix is adding more consumer instances up to the partition count (recall that beyond the partition count, extra instances just sit idle, so scaling further requires increasing partitions too, which is a bigger operational change). A different, equally common production problem is a poison-pill message — a single malformed or unexpected message that throws an exception every time the consumer tries to process it, and if the consumer doesn't commit the offset past it, it retries the same message forever, completely blocking that partition while lag climbs behind it. The standard fix is a dead-letter topic: after a bounded number of retries, the consumer gives up on that specific message, publishes it (with error context) to a separate topic like order-events-dlq instead, commits past it, and moves on to unblock the partition — the poisoned message is then inspected and reprocessed manually or by a separate remediation job later, rather than being lost or blocking the whole partition indefinitely. Monitoring consumer lag per partition (via tools like Kafka's own consumer-group CLI or a metrics exporter feeding Prometheus/Grafana) with alerting on sustained growth is the standard way this gets caught before it becomes a customer-facing incident.
