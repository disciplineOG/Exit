Most Asked Interview Questions: Multithreading, Concurrency & JVM/GC

Threads Synchronization Executors JVM Memory Garbage Collection Volatile
Why this matters

Concurrency and JVM internals questions are where interviewers separate candidates who've memorized definitions from candidates who've actually debugged a stuck production service. Almost every backend Java interview probes at least one of: "is this code thread-safe," "why would this deadlock," "what happens when the heap fills up," or "which garbage collector would you pick and why." This page answers the exact questions that come up across those four areas, from the basic thread lifecycle up through choosing a garbage collector and diagnosing an OutOfMemoryError.

Threading Basics

What is the difference between a process and a thread, and why use multithreading at all?
A process is an independently running instance of a program with its own private memory address space — one process cannot directly read another process's memory, and the operating system isolates them from each other. A thread is a unit of execution that lives inside a process; every thread in the same process shares that process's heap memory, open file handles, and network sockets, while each thread still gets its own private call stack and program counter. This is exactly why multithreading is both powerful and dangerous: threads can communicate cheaply by just reading and writing the same shared objects (no inter-process communication needed), but that same shared access is what causes race conditions, visibility bugs, and the entire category of problems this page covers. You reach for multithreading for two distinct reasons that are easy to conflate: to use multiple CPU cores in parallel for CPU-bound work (like computing pricing across a large batch of ShopSphere orders faster), or to keep a single core productive while other work is blocked waiting on I/O (like an order-service instance handling thousands of concurrent requests that each spend most of their time waiting on a database or a downstream call to payment-service, not actually computing).
What is the difference between Thread, Runnable, and Callable?
Thread is a concrete class representing an actual thread of execution — you either extend it and override run(), or (far more commonly) construct one by passing it a task. Runnable is a functional interface with a single method, void run(), that takes no arguments and returns no value and cannot throw a checked exception — it describes "a unit of work," not a thread, and is the type you pass into a Thread constructor or an ExecutorService. Callable<V> is the more capable sibling: its single method V call() can return a result of type V and can throw a checked exception, which is why it's used with ExecutorService.submit() when you need a Future<V> back. The practical rule of thumb: prefer implementing Runnable or Callable and submitting the task to an executor rather than extending Thread directly, because extending Thread ties your task to Java's single-inheritance model and couples "what work to do" with "how it's scheduled," which an executor should own instead.
What are the states in the thread lifecycle, and how does a thread move between them?
A Java thread's lifecycle is represented by the enum Thread.State with six values. NEW is a Thread object that has been constructed but not yet started. RUNNABLE means eligible to run — this covers both a thread actually executing on a CPU core and a thread sitting in the operating system's run queue waiting its turn, which Java doesn't distinguish as separate states. BLOCKED specifically means the thread is waiting to acquire a synchronized monitor lock that another thread currently holds. WAITING means the thread called Object.wait() (no timeout), Thread.join() (no timeout), or LockSupport.park(), and is waiting indefinitely for another thread to explicitly wake it up. TIMED_WAITING is the same idea but with a bound — Thread.sleep(ms), wait(ms), or join(ms) — so it resumes either when notified or when the timeout elapses. TERMINATED means run() has returned or thrown, and the thread cannot be restarted. The distinction that trips people up in interviews is BLOCKED versus WAITING: BLOCKED is the JVM arbitrating contention for a lock, while WAITING is a thread that voluntarily parked itself and depends on another thread's explicit signal to resume.
How does the synchronized keyword work, and what's the difference between a synchronized method and a synchronized block?
Every Java object carries an associated monitor, also called an intrinsic lock. A synchronized instance method locks on this (the object the method is called on); a synchronized static method locks on the Class object for that class (shared across all instances); and a synchronized(someObject) { ... } block lets you lock on any object you choose, over just the statements inside the block rather than the whole method. Acquiring the lock and entering the protected code, then releasing the lock on exit — including exit via an exception — happens atomically as a pair, which is why synchronized is exception-safe without needing an explicit finally. A synchronized block is generally preferred over a synchronized method because it lets you keep the "critical section" (the code that actually needs mutual exclusion) as small as possible; locking an entire method when only two lines inside it touch shared state needlessly serializes unrelated work. Intrinsic locks are also reentrant: a thread that already holds a monitor can enter another synchronized block guarded by the same monitor without blocking on itself, which is what lets a synchronized method safely call another synchronized method on the same object.
What do wait(), notify(), and notifyAll() do, and why must they be called from inside a synchronized block?
wait(), notify(), and notifyAll() are methods on Object (not Thread) used for inter-thread signaling: a thread calls wait() to release the monitor it holds and go to sleep until another thread calls notify() (wakes one arbitrary waiting thread) or notifyAll() (wakes all waiting threads) on that same object. They must be called while holding the object's monitor — i.e., inside a synchronized(obj) block on that same object — because the JVM throws IllegalMonitorStateException otherwise, and more fundamentally because the check-then-wait sequence has to be atomic with respect to the condition being checked: without holding the lock, another thread could change the condition and call notify() in the gap between your check and your call to wait(), causing you to sleep forever on a signal that already happened (a "missed signal"). In ShopSphere, a worker pool draining an internal task queue is a typical pattern: a consumer thread does synchronized(queue) { while (queue.isEmpty()) queue.wait(); return queue.poll(); }, and a producer does synchronized(queue) { queue.add(task); queue.notifyAll(); }. Note the while loop, not if — a woken thread must re-check the condition because notifyAll() wakes every waiter, and by the time this particular thread gets scheduled, another thread may have already consumed the item (this is called a "spurious wakeup" defense, and it's mandatory correct usage, not defensive paranoia).
What does the volatile keyword guarantee, and what does it NOT guarantee?
volatile guarantees visibility and ordering, not atomicity. Visibility means every read of a volatile field is guaranteed to see the most recent write to it by any thread — without volatile, a thread could cache a stale value in a CPU register or core-local cache indefinitely and never observe another thread's update. Ordering means the compiler and CPU cannot reorder other reads/writes across a volatile read or write (it acts as a memory barrier). What it does not give you is atomicity for compound (multi-step) operations: counter++ on a volatile int is actually three separate steps — read, increment, write back — and two threads can each read the same value before either writes back, silently losing an update. A concrete failure case: a volatile int availableQty caching stock for a hot ShopSphere product, checked with if (availableQty > 0) availableQty--; — two concurrent checkout threads can both read 1, both pass the check, and both decrement, overselling a unit of stock that didn't exist. The fix for compound operations is an atomic class (AtomicInteger), a full synchronized block around the check-and-mutate sequence, or an explicit lock — not "more volatile."
What's the difference between deadlock, livelock, and starvation, and how do you avoid deadlock?
All three are threads failing to make progress, but for different reasons. Deadlock is two or more threads each permanently blocked, waiting for a resource the other holds — for example, thread A holds a lock on inventoryWarehouseA and wants a lock on orderBeingCancelled, while thread B holds the lock on orderBeingCancelled and wants inventoryWarehouseA; neither can proceed and neither ever will without outside intervention. Livelock is threads that are actively running and changing state, but never making real progress, because they keep reacting to each other symmetrically — like two people in a hallway both stepping aside in the same direction repeatedly; in code this often happens when a deadlock-avoidance retry policy is too synchronized (both threads back off and retry at the same instant, forever). Starvation is a thread that is technically able to run but is perpetually denied access to a resource because other threads are consistently favored, such as a non-fair lock repeatedly granting access to threads that arrived later. Deadlock is prevented by lock ordering — always acquiring multiple locks in the same globally agreed order (e.g., always lock the entity with the lower ID first) so a circular wait can never form — or by using tryLock() with a timeout so a thread that can't get a second lock releases what it holds and retries instead of blocking forever. Livelock is mitigated with randomized backoff (jitter) so retries desynchronize, and starvation is mitigated with fairness policies, such as constructing a ReentrantLock with new ReentrantLock(true).
What is a daemon thread, and how is it different from a normal (user) thread?
A daemon thread is a background thread that does not prevent the JVM from exiting — once every non-daemon (user) thread has finished, the JVM shuts down immediately even if daemon threads are still running, without waiting for them and without running their finally blocks. You mark a thread as a daemon by calling setDaemon(true) before starting it; this must be done before start(), or it throws IllegalThreadStateException. Typical uses are background housekeeping that should never block application shutdown: a periodic cache-eviction sweep, a metrics-reporting thread, or a connection-pool idle-reaper — none of these should keep the JVM alive on their own if the actual application work is done. The practical danger is putting anything that needs guaranteed cleanup (like flushing a buffered write to disk, or committing an in-flight database transaction) on a daemon thread, since it can simply be killed mid-operation with no warning when the last user thread exits.
What is a race condition, and how does that differ from Thread.sleep() versus wait()?
A race condition is any situation where the correctness of a result depends on the unpredictable timing or interleaving of multiple threads — two threads racing to read-modify-write shared state, where the outcome differs depending on which thread's steps happen to interleave with the other's. It's the general problem; a "lost update" (like the volatile stock-decrement example above) and a "check-then-act" bug (checking containsKey then calling put separately on a map) are both specific instances of a race condition. Thread.sleep(ms) and Object.wait() are often confused because both pause a thread, but they behave completely differently with respect to locks: sleep() is a static Thread method that pauses the current thread for a fixed duration without releasing any monitor it holds, and it doesn't require being inside a synchronized block at all. wait() is an instance method on Object that releases the monitor it's called under so other threads can acquire it, and it only resumes when explicitly notified (or, if a timeout is given, when that timeout elapses) — and it throws IllegalMonitorStateException if called outside a synchronized block on that object. The practical consequence: calling sleep() while holding a lock blocks every other thread waiting on that lock for the full sleep duration, which is a common accidental cause of a service looking "deadlocked" when it's really just a lock held across an unnecessary sleep.
How do you safely stop a running thread, and what does interrupt() actually do?
Java deliberately has no safe way to force-kill a running thread — the old Thread.stop() method is deprecated because it releases all the monitors a thread holds immediately and unconditionally, which can leave shared objects in a half-updated, corrupted state for any other thread still using them. The correct mechanism is cooperative cancellation via interrupt(): calling someThread.interrupt() just sets an internal "interrupted" flag on that thread and does not stop anything by itself. If the target thread is currently blocked in an interruptible wait — Thread.sleep(), Object.wait(), Thread.join(), or blocking on a java.util.concurrent API like lockInterruptibly() — that call immediately wakes up and throws InterruptedException, clearing the flag in the process. If the thread is doing plain CPU-bound work with no blocking call in the loop, nothing happens automatically — the thread's own code has to periodically check Thread.currentThread().isInterrupted() and exit its loop voluntarily when it sees the flag set. This is why a well-behaved long-running task looks like while (!Thread.currentThread().isInterrupted()) { doWork(); }, and why swallowing an InterruptedException with an empty catch block is considered a serious bug — it silently discards a cancellation request, so the convention is to either exit the loop/method right there or call Thread.currentThread().interrupt() to re-set the flag for an outer caller to notice.

Concurrency Utilities

What is the Java Memory Model, and what does "happens-before" mean?
The Java Memory Model (JMM) is the specification that defines when a write to a variable made by one thread is guaranteed to become visible to a read of that variable by another thread — without it, the compiler, the CPU, and the cache hierarchy would all be free to reorder and locally cache memory operations in ways that make single-threaded reasoning break down across threads. "Happens-before" is the core ordering guarantee the JMM defines: if action A happens-before action B, every effect of A (every write A made) is guaranteed visible to B, and the JVM is not allowed to reorder them in a way that violates that guarantee. The JMM establishes several concrete happens-before rules that come up constantly in interviews: a write to a volatile field happens-before every subsequent read of that same field by any thread; unlocking a monitor happens-before any later thread locking that same monitor; and a call to Thread.start() happens-before anything the started thread does, while everything a thread does happens-before another thread's successful Thread.join() on it. This is the actual theoretical basis for why volatile, synchronized, and thread lifecycle methods provide the visibility guarantees described elsewhere on this page — without a happens-before edge between a write and a read on different threads, there is no guarantee the read ever sees the write, no matter how "obviously sequential" the code looks.
What is ExecutorService, and what are the differences between the fixed, cached, and scheduled thread pool types?
ExecutorService decouples "submitting a task" from "how and when it actually runs" — instead of manually creating and managing Thread objects (expensive, since each platform thread reserves an OS stack, typically several hundred KB to a few MB), you submit Runnable/Callable tasks to a pool that reuses a bounded set of worker threads. The factories in java.util.concurrent.Executors are just presets over the same underlying ThreadPoolExecutor class with different constructor arguments. newFixedThreadPool(n) keeps exactly n threads alive and backs them with an unbounded queue by default — meaning if tasks arrive faster than n threads can drain them, they queue up indefinitely rather than being rejected, which can silently grow memory and latency under sustained overload. newCachedThreadPool() starts with zero core threads, creates a new thread per task if none are idle, and reuses idle threads after that (killing ones idle for 60 seconds) — this can spawn effectively unlimited threads under a burst, which fails loudly (memory exhaustion or thread-creation errors) rather than quietly. newScheduledThreadPool(n) supports schedule() for one-off delayed execution and scheduleAtFixedRate/scheduleWithFixedDelay for recurring execution, useful for something like a periodic ShopSphere job that expires abandoned carts every few minutes. In production code, it's usually safer to construct a ThreadPoolExecutor directly with a bounded queue and an explicit rejection policy rather than relying on the unbounded-queue or unbounded-thread defaults of these factories.
What's the difference between shutdown() and shutdownNow() on an ExecutorService?
shutdown() initiates a graceful shutdown: the executor stops accepting new tasks (any further submit() call throws RejectedExecutionException), but every task already queued or running is allowed to finish normally before the pool's threads terminate. shutdownNow() is the aggressive version: it also stops accepting new tasks, but additionally attempts to stop all actively executing tasks by calling interrupt() on their threads, and returns a List<Runnable> of the tasks that were still sitting in the queue and never got to start. Neither call blocks waiting for termination to actually finish — that's what awaitTermination(timeout, unit) is for, which blocks the calling thread until either all tasks complete or the timeout elapses. The standard production pattern combines all three: call shutdown() to stop new work, call awaitTermination() with a reasonable timeout to give in-flight work a chance to finish cleanly, and if that times out, call shutdownNow() as a forceful fallback — for example, order-service draining its checkout-processing pool during a rolling deployment so in-flight orders aren't abandoned mid-write.
What is CompletableFuture, and how do you chain operations on it?
CompletableFuture<T> represents a value that will become available at some point in the future and lets you compose transformations on it without blocking the calling thread to wait. thenApply(fn) takes a plain synchronous transformation, T -> U, for when you just need to convert an already-in-flight result. thenCompose(fn) takes a function that itself returns another CompletableFuture<U> and flattens the result into one CompletableFuture<U> instead of a nested CompletableFuture<CompletableFuture<U>> — this is the asynchronous equivalent of flatMap, used when the next step is itself an asynchronous call (e.g., after fetching an Order, asynchronously fetch its Payment status). thenCombine(other, fn) merges the results of two independent futures once both complete, useful for fanning out two unrelated calls — like fetching a Customer profile and an Order's line items in parallel — and combining them once both are done. exceptionally(fn) supplies a fallback value only on failure, while handle(fn) runs unconditionally on both success and failure, useful for logging or normalizing to a result wrapper regardless of outcome. Appending Async to any of these methods (e.g. thenApplyAsync) submits the callback to a thread pool instead of possibly running it inline on the thread that completed the previous stage, which matters when you don't want to risk blocking that thread.
What is ThreadLocal, and what's the common misuse to watch out for?
ThreadLocal<T> gives each thread its own independent copy of a variable — calling get()/set() on the same ThreadLocal instance from different threads never sees each other's values, which makes it useful for per-thread context that would otherwise need to be threaded through every method call, such as the current request's authenticated Customer ID or a per-request correlation ID for logging across a call chain in order-service. The common misuse is with thread pools: because pool threads are long-lived and reused across many tasks, a ThreadLocal value set during one task and never explicitly cleared with remove() will "leak" into the next unrelated task that happens to run on the same pooled thread, causing subtle correctness bugs (a later request seeing a stale customer ID) or, in web containers, classloader-related memory leaks if the value holds a reference to something tied to a previous application deployment. The rule is: any code using ThreadLocal in combination with a thread pool must call remove() in a finally block once the task using it is done, not rely on the value simply going out of scope.
Why are immutable objects thread-safe, and why does that matter for concurrent code?
An immutable object is one whose observable state can never change after construction — every field is set once in the constructor and never reassigned, and any field that's a mutable type (like a collection or array) is either copied defensively or never exposed for mutation. This makes immutable objects inherently thread-safe with zero synchronization: there's no "current state" for two threads to race over, no compound check-then-act sequence to interleave badly, and no need for volatile or locking to publish visibility, because a properly-constructed immutable object (all fields final) is guaranteed to be fully visible to any thread that obtains a reference to it, thanks to the Java Memory Model's guarantees around final-field initialization. This is exactly why String is immutable in Java: it can be freely shared across threads — cached, pooled, passed as a map key — without any thread ever needing to coordinate over it. The practical implication for concurrent code: prefer designing value-like classes (a Money amount, an OrderLineItem snapshot, a configuration object) as immutable wherever possible, since "no shared mutable state" eliminates the entire category of races, deadlocks, and visibility bugs this page is otherwise about — you can't get a data race on a value nothing ever mutates.
What's the difference between CountDownLatch and CyclicBarrier?
Both coordinate a group of threads waiting on each other, but they differ in reusability and in who is waiting for whom. CountDownLatch is initialized with a fixed count; any thread can call countDown() to decrement it, and any number of threads calling await() block until the count reaches zero — after that, the latch is permanently open and cannot be reset or reused. It's a one-time gate, useful for something like order-service waiting for several independent startup tasks (warming a cache, establishing a Kafka consumer connection, validating configuration) to all finish before accepting traffic. CyclicBarrier is initialized with a fixed number of parties; each participating thread calls await() and blocks until that exact number of threads has all called await(), at which point all of them are released simultaneously and the barrier automatically resets for reuse — optionally running a supplied barrier action once, right when the last thread arrives. Use CountDownLatch when one or more threads need to wait for a set of events to happen (an event might come from threads not otherwise coordinated), and use CyclicBarrier when a fixed set of cooperating threads need to repeatedly synchronize at a shared checkpoint before all continuing together, such as parallel workers each processing a batch of orders and needing to sync up after each batch before moving to the next.
What is a Semaphore and when would you use one?
A Semaphore maintains a fixed number of "permits" — threads call acquire() to take a permit (blocking if none are available) and release() to return one. Unlike a lock, which allows exactly one thread into a critical section, a semaphore allows up to N concurrent threads through, making it the right tool for bounding concurrency against a limited resource rather than enforcing pure mutual exclusion. A typical ShopSphere use case is capping the number of concurrent outbound calls from order-service to payment-service to, say, 20 at a time, even though the calling thread pool itself is much larger, to avoid overwhelming payment-service during a traffic spike: Semaphore paymentCallLimiter = new Semaphore(20); paymentCallLimiter.acquire(); try { callPaymentService(); } finally { paymentCallLimiter.release(); }. A semaphore initialized with a single permit (new Semaphore(1)) behaves like a lock, but without the reentrancy and ownership semantics of ReentrantLock — any thread can release a permit it didn't acquire, which is a feature for some producer/consumer patterns and a foot-gun if you actually wanted lock-like discipline.
How does ReentrantLock compare to synchronized — fairness, tryLock, and interruptibility?
ReentrantLock offers everything synchronized does — mutual exclusion and reentrancy (a thread already holding the lock can re-acquire it without blocking on itself) — plus capabilities the synchronized keyword structurally cannot provide. tryLock() attempts to acquire the lock without blocking and immediately returns true/false, and tryLock(timeout, unit) gives a bounded wait — synchronized has no non-blocking or timed option at all. lockInterruptibly() allows a thread blocked waiting for the lock to be interrupted and throw InterruptedException instead of waiting forever, whereas a thread blocked on a synchronized monitor ignores interrupts entirely. Fairness is configurable: new ReentrantLock(true) approximates first-in-first-out ordering among waiting threads (at some throughput cost), while synchronized gives the JVM no fairness guarantee at all and can starve a waiting thread indefinitely. The trade-off is safety by construction: synchronized is released automatically by the JVM on block exit, including via an exception, so it can never be "forgotten," while ReentrantLock requires disciplined manual release in a finally block — a missed unlock() leaks the lock permanently with no compiler warning. The practical guidance: use synchronized by default for its simplicity, and reach for ReentrantLock specifically when you need tryLock, interruptibility, fairness, or multiple independent condition queues via newCondition().
How does ConcurrentHashMap achieve thread safety without locking the entire map?
Unlike a legacy Hashtable, which synchronizes every single method on one lock for the whole map (serializing all reads and writes against each other, even unrelated ones), ConcurrentHashMap splits the map into fine-grained regions and only locks the specific region a given write touches. In modern JDKs, this is done at the level of individual bucket nodes: a write acquires a lock (implemented via synchronized blocks on the first node of the bucket, combined with compare-and-swap, or CAS — Compare-And-Swap, an atomic CPU instruction that writes a new value only if the current value still matches an expected value — operations for simpler cases) only on the bucket it's modifying, so writes to different buckets can proceed fully in parallel. Reads are largely lock-free, using volatile-backed reads of bucket contents so they see a consistent, published view without blocking on any writer. This is also why compound operations like computeIfAbsent(key, fn) are important on ConcurrentHashMap: they perform a check-and-insert atomically under that bucket's lock, whereas composing a separate containsKey check and a put call in application code reintroduces a race even though the underlying map is thread-safe. A practical example: inventoryCache.computeIfAbsent(productId, id -> loadFromDb(id)) guarantees only one thread actually loads a given hot product from the database even under heavy concurrent access, whereas checking then putting separately does not.
What are atomic classes like AtomicInteger, and how does CAS (Compare-And-Swap) make them thread-safe without locks?
Classes like AtomicInteger, AtomicLong, and AtomicReference provide atomic (indivisible) compound operations — such as incrementAndGet(), compareAndSet(), or updateAndGet(fn) — on a single variable without requiring a lock. They're built on CAS (Compare-And-Swap), an atomic CPU instruction with the semantics "write this new value into this memory location, but only if it still currently holds the value I expect; otherwise fail and let me retry." Internally, methods like incrementAndGet() loop: read the current value, compute the new value, attempt a CAS from old to new, and if another thread's CAS won the race in between, retry the whole read-compute-CAS cycle. This makes atomics much cheaper under low-to-moderate contention than locking, because there's no OS-level thread suspension involved — just a tight retry loop that usually succeeds on the first or second try — though under very high contention, the retry loop itself can become a bottleneck. This is the correct fix for the classic volatile-decrement-oversell bug: replacing availableQty-- on a plain volatile field with AtomicInteger.updateAndGet(q -> q > 0 ? q - 1 : q) makes the whole check-and-decrement a single atomic operation instead of three separate, interleavable steps.
What is the fork/join framework, and how is it different from a regular thread pool?
The fork/join framework (ForkJoinPool, backing parallel streams and, since Java 21, virtual threads by default) is designed specifically for divide-and-conquer workloads: a large task is recursively split ("forked") into smaller subtasks until they're small enough to compute directly, and the results are combined ("joined") back up. Its defining feature versus a regular fixed or cached thread pool is work-stealing: each worker thread has its own local double-ended queue of subtasks, and a thread that finishes its own work early can "steal" a task from the tail of another thread's queue instead of sitting idle waiting for the pool's shared queue. This keeps all CPU cores busy even when the initial split of work is uneven, which a regular ThreadPoolExecutor — with one shared task queue and no rebalancing between busy and idle workers — does not do. Fork/join is best suited to CPU-bound, recursively decomposable work, such as computing an aggregate discount calculation across a huge in-memory batch of OrderItems by splitting the batch, computing partial sums in parallel, and merging them — it is not the right tool for I/O-bound tasks, where blocking on network calls just ties up fork/join's typically small, CPU-core-sized thread count.
What are virtual threads (Project Loom), and how do they differ from regular platform threads?
A platform thread is a thin wrapper around an actual operating system thread — a 1:1 mapping, with an OS-reserved stack (typically several hundred KB to a few MB) and OS-level context switching — which caps realistic concurrency at a few thousand live threads before scheduling overhead and memory dominate. A virtual thread (finalized in Java 21 under JEP 444) is instead a Thread object scheduled entirely by the JVM: it's "mounted" onto one of a small pool of "carrier" platform threads only while it has actual CPU work to do, and when it performs a blocking operation the JDK recognizes (socket I/O, Thread.sleep, lock acquisition, JDBC calls in supporting drivers), the JVM "unmounts" it — parking its captured execution state as a cheap heap object and freeing the carrier thread to run a different virtual thread — then remounts it once the blocking call completes. This lets a service handle hundreds of thousands of concurrent, mostly-I/O-waiting requests (such as ShopSphere checkout calls fanning out to inventory-service and payment-service) using simple, synchronous-looking blocking code, without needing a reactive/callback-based programming model, because the cost of "waiting" drops from a fully-reserved OS thread to a small parked heap object. The important nuance: virtual threads don't make any single piece of CPU-bound work faster — they only remove the cost of idle waiting — and code that blocks while holding a synchronized monitor (as opposed to a ReentrantLock) can "pin" a virtual thread to its carrier thread, which reintroduces the exact scalability problem virtual threads are meant to solve.
How do you size and configure a production ThreadPoolExecutor — corePoolSize, maxPoolSize, queue, and rejection policy?
A ThreadPoolExecutor is built from four decisions the Executors factory methods make for you (often badly): corePoolSize (threads kept alive even when idle), maximumPoolSize (the hard cap on threads), the work queue implementation, and a RejectedExecutionHandler for when the pool is saturated. The actual runtime behavior surprises people: the executor only grows past corePoolSize toward maximumPoolSize once the queue is completely full, not simply when tasks are arriving faster than corePoolSize threads can drain them — so an unbounded queue (the default in newFixedThreadPool) means maximumPoolSize is effectively dead code, and the pool never grows, it just queues indefinitely and latency silently climbs. Sizing depends on the workload: CPU-bound work (like scoring pricing rules) should size the pool close to the number of available cores, since more threads than cores just adds context-switch overhead with no throughput gain, while I/O-bound work (like calling payment-service over the network) benefits from a much larger pool, since most threads are parked waiting rather than consuming CPU. For the queue and rejection policy, production code should use a bounded queue (e.g., new ArrayBlockingQueue<>(1000)) so a downstream slowdown produces a fast, visible signal instead of unbounded memory growth, paired with an explicit rejection policy — CallerRunsPolicy (makes the submitting thread run the task itself, a natural backpressure valve) is often preferred over the default AbortPolicy (throws and drops the task) for services like order-service that would rather slow down than silently lose a checkout request.
What is a BlockingQueue, and how does it implement the producer-consumer pattern?
BlockingQueue<E> is a queue interface where put() blocks the calling thread if the queue is full (for bounded implementations) instead of failing, and take() blocks if the queue is empty instead of returning null — it builds the exact wait/notify coordination shown earlier directly into the data structure, so application code never has to write manual synchronized/wait/notifyAll logic for a producer-consumer setup. ArrayBlockingQueue is a fixed-capacity, array-backed implementation good for applying firm backpressure; LinkedBlockingQueue can be bounded or effectively unbounded and is the default queue behind Executors.newFixedThreadPool; and SynchronousQueue has no internal capacity at all — every put() must be handed off directly to a waiting take(), making it a direct thread-to-thread handoff rather than a buffer. A typical ShopSphere producer-consumer setup uses a bounded BlockingQueue<OrderEvent> between a Kafka consumer thread (the producer, calling queue.put(event) for each record) and a pool of worker threads (the consumers, each looping on queue.take()) — the bound on the queue is what prevents an unusually fast producer from piling up unbounded in-memory work if the consumers fall behind, converting a potential out-of-memory failure into simple, visible backpressure on the producer side instead.

JVM Architecture & Garbage Collection

What are the main JVM memory areas — heap, stack, metaspace, and PC register — and what lives in each?
The heap is where all objects and arrays are allocated, is shared across all threads, and is the area the garbage collector manages. Each thread has its own private stack, made up of stack frames — one per active method call — holding local variables, method parameters, and the return address; a stack is never shared between threads, which is exactly why local variables are inherently thread-safe without any synchronization. Metaspace (which replaced the old "permanent generation" or PermGen starting in Java 8) stores class metadata: the structure of loaded classes, method bytecode, and constant pool data — unlike PermGen, metaspace is allocated from native (off-heap) memory and by default grows dynamically rather than being a small fixed size, though it can still be capped with -XX:MaxMetaspaceSize. The PC (program counter) register is a small, per-thread structure holding the address of the JVM instruction currently being executed by that thread, letting execution resume at the right point after a context switch back to that thread. Both the stack and PC register are per-thread and created/destroyed with the thread; the heap and metaspace are shared JVM-wide resources that live for the process's lifetime.
How is the heap organized into generations — Eden, Survivor, and Old — and why does that layout exist?
The heap is split based on the empirical observation that most objects die young (the "generational hypothesis") — a huge share of allocations, like a short-lived request DTO (Data Transfer Object) built for a single ShopSphere API call, become garbage almost immediately, while a smaller share, like a long-lived cache entry, survive for a long time. The young generation is subdivided into Eden, where nearly all new objects are initially allocated, and two Survivor spaces (commonly called S0 and S1), used as a copy-back-and-forth staging area. When Eden fills up, a minor garbage collection copies all still-reachable objects out of Eden into one Survivor space; each time an object survives a collection, its "age" counter increments, and once an object's age crosses a threshold (or a Survivor space fills up), it gets "promoted" into the Old generation (also called tenured), which holds long-lived objects and is collected far less often, by a "major" or "full" garbage collection. This layout makes minor collections in the young generation fast and cheap — they only need to scan a small, mostly-garbage region — while confining the more expensive full-heap scans to the smaller share of objects that actually survive long enough to matter.
What are the major garbage collectors — Serial, Parallel, G1, and ZGC — and when would you choose each?
The Serial collector uses a single thread for all garbage collection work and stops all application threads (a "stop-the-world" pause) while it runs; it's appropriate only for small heaps or single-core environments — like a lightweight client tool — where pause time doesn't matter and simplicity/low memory overhead does. The Parallel collector (the default in older JDKs) uses multiple threads to do the collection work faster, but still stops all application threads during that work — it optimizes for maximum application throughput (total useful work done over time) at the cost of longer, though fewer, stop-the-world pauses, making it a fit for batch jobs where overall runtime matters more than any single pause. G1 (Garbage-First, the default since Java 9) divides the heap into many equally-sized regions instead of one contiguous young/old split, and prioritizes collecting the regions with the most garbage first, aiming to keep pauses within a configurable target (-XX:MaxGCPauseMillis) — this is the right general-purpose default for most backend services like ShopSphere's order-service, where predictable, moderate pause times matter more than squeezing out maximum throughput. ZGC (production-ready since Java 15) does almost all of its work concurrently with the application, targeting sub-millisecond pause times even on heaps in the hundreds of gigabytes, at the cost of somewhat more CPU overhead and memory usage — this is the choice for large-heap, latency-sensitive services where even G1's pause times would be unacceptable, such as a hot in-memory pricing or fraud-scoring service that cannot tolerate even a 50ms hiccup.
What is a stop-the-world pause?
A stop-the-world pause is a period during garbage collection when the JVM suspends every application thread so the collector can safely inspect and move objects without the running program changing the object graph underneath it. It happens at a "safepoint" — a point in execution where every thread's state is consistent and safe to inspect. Not every collector pauses for the same amount of work: the Serial and Parallel collectors stop the world for the entire collection, while G1 and ZGC are designed to minimize stop-the-world time by doing most of the work (marking reachable objects, in particular) concurrently alongside running application threads, only briefly pausing for smaller, bounded phases. From a service's perspective, a stop-the-world pause shows up as every in-flight request on that JVM instance freezing simultaneously — no thread makes progress, no matter how many CPU cores are free — which is why pause time, not just total collector throughput, is a critical metric for latency-sensitive services like checkout in a flash sale.
Java has automatic garbage collection, so how can a Java application still have a memory leak?
The garbage collector only reclaims objects that are unreachable — it cannot free an object that some live reference chain still points to, even if the application will never actually use that object again. A "memory leak" in Java, then, is really unintentional, unbounded retention: something keeps a reference alive long after the object is logically done being needed, so the heap grows over time even though the GC is working correctly. Common real causes: a static field used as a cache that's only ever added to and never evicted (e.g., a static Map<Long, Product> caching every product ever looked up, with no size cap or expiration); listeners or callbacks registered on a long-lived object (like an event bus) and never unregistered, keeping the registering object alive indefinitely; ThreadLocal values never cleared in a pooled-thread environment, as covered above; and unclosed resources — a ResultSet, connection, or file handle whose enclosing object stays reachable, pinning native or off-heap memory that GC doesn't track at all. Fixing a leak means finding and breaking the unwanted reference chain, typically diagnosed by taking a heap dump and looking at what's keeping the suspect objects reachable (the "dominator tree" or "path to GC roots" in a tool like the Eclipse Memory Analyzer).
What's the difference between strong, weak, soft, and phantom references?
A strong reference is an ordinary Java reference (Product p = new Product();) — as long as one exists, the object can never be garbage collected, no matter how much memory pressure exists. A soft reference (SoftReference<T>) allows the object to be collected, but only when the JVM is actually running low on memory — the collector clears soft references as a last resort before throwing OutOfMemoryError, which makes them suitable for memory-sensitive caches, like a large image or rendered-catalog-page cache in ShopSphere's catalog-service, that should shrink under pressure rather than cause an outage. A weak reference (WeakReference<T>) is collected at the very next garbage collection cycle as soon as no strong references remain, regardless of memory pressure — the canonical use is WeakHashMap, where entries should disappear automatically once their key is no longer referenced elsewhere, useful for metadata caches keyed by objects whose lifecycle you don't control. A phantom reference (PhantomReference<T>) is the weakest: calling get() on it always returns null (you can never actually retrieve the object through it), and it exists purely so you can be notified, via an associated ReferenceQueue, exactly when an object has been finalized and its memory is about to be reclaimed — used for precise cleanup of off-heap or native resources, and is effectively the modern replacement for the deprecated finalize() method.
How does the class loading process work, and what is classloader delegation?
Class loading happens in three broad phases: loading (finding the .class bytecode — from the filesystem, a JAR, or the network — and creating an in-memory representation of the class), linking (which itself breaks into verification of bytecode correctness and security constraints, preparation of static fields with default values, and optional resolution of symbolic references to other classes), and initialization (running static initializers and assigning actual values to static fields, which happens lazily, the first time the class is actually used). Classloaders are arranged hierarchically — the bootstrap classloader (loads core JDK classes like java.lang.*), the platform classloader, and the application classloader (loads your own application's classes from the classpath) — and each classloader, before attempting to load a class itself, delegates the request up to its parent first. This is the delegation model: only if the parent can't find the class does the child attempt to load it itself. The reason this matters is security and consistency: it prevents a malicious or accidental application-level class named, say, java.lang.String, from ever shadowing the real JDK String class, because the bootstrap loader always gets first chance and always wins for core JDK classes.
What are the common types of OutOfMemoryError, and what does each one actually mean?
java.lang.OutOfMemoryError: Java heap space means the heap is full of reachable (non-garbage) objects and the JVM cannot allocate a new one even after a full garbage collection — this is the classic memory-leak symptom, or simply an undersized heap for legitimate load, such as ShopSphere's order-service trying to hold an entire day's orders in memory at once for a batch report. OutOfMemoryError: GC overhead limit exceeded means the JVM is spending the vast majority of its CPU time (by default, more than 98%) doing garbage collection while reclaiming very little heap each time — the application is technically still running but is thrashing, which usually indicates a genuine leak rather than a simple undersized heap, since a one-time spike would still eventually recover memory. OutOfMemoryError: Metaspace means the JVM has run out of space for class metadata, commonly caused by a classloader leak — dynamically loading many classes and never releasing their defining classloader, such as repeatedly redeploying an application in an application server without the old classloader and its classes ever becoming unreachable. OutOfMemoryError: Unable to create new native thread means the OS refused to create another thread for the process, typically because the process has hit the OS's maximum thread (or process) limit — a classic sign of unbounded thread creation, such as a misconfigured cached thread pool spawning a new thread per incoming request under sustained load. StackOverflowError (not technically an OutOfMemoryError, but frequently asked in the same breath) means a single thread's stack has exceeded its size limit, almost always from uncontrolled or missing-base-case recursion, such as a recursive category-tree traversal in catalog-service that never hits a leaf node.
What's the difference between a minor GC, a major GC, and a full GC?
A minor (or "young") GC collects only the young generation — Eden and the Survivor spaces — copying surviving objects into a Survivor space or promoting them to Old, and is fast and frequent because the young generation is small and mostly garbage by design. A major GC collects the Old generation specifically, which is far more expensive because Old is typically much larger and has a much lower proportion of garbage to reclaim per pass. A full GC collects the entire heap — young generation, Old generation, and often metaspace — in one pass, and on collectors like Parallel this is a stop-the-world pause across the whole heap, which is the single most disruptive GC event a service experiences; a burst of full GCs back-to-back (visible in GC logs as full GCs recovering little memory each time) is one of the strongest signals of an actual memory leak rather than routine collection. In practice, "major" and "full" are used loosely and sometimes interchangeably in casual conversation, but the distinction interviewers are actually checking for is whether you understand that Old-generation collections are categorically more expensive than young-generation ones, which is precisely why the generational split (and promotion tuning) exists in the first place.
How do you approach tuning and monitoring GC in a production service?
Tuning starts with visibility, not guessing: enabling GC logging (-Xlog:gc* on modern JDKs) and feeding it into a tool like GCViewer or a GC-aware APM (Application Performance Monitoring) dashboard to see pause frequency, pause duration, and how much memory each collection actually reclaims. The two levers that matter most are heap size and collector choice: -Xms and -Xmx set the initial and maximum heap size — setting them equal is common in containerized production services (like a ShopSphere microservice on Kubernetes) to avoid the latency spike and CPU cost of the JVM dynamically resizing the heap under load, at the cost of reserving that memory up front. Collector choice follows the trade-off already covered: G1's -XX:MaxGCPauseMillis lets you state a target pause time directly and let the collector adapt region-collection work to hit it, which is usually the first tuning knob to reach for before anything more exotic. The failure pattern to recognize in monitoring: rising full-GC frequency with shrinking memory reclaimed per cycle, and average pause time creeping upward release over release, are both leading indicators of a memory leak or genuine undersizing, and should be caught in staging load tests before they page someone at 2am during a flash sale.
What was the CMS collector, and why was it deprecated and removed in favor of G1?
CMS (Concurrent Mark Sweep) was the collector designed before G1 to reduce stop-the-world pauses on the Old generation by doing most of its marking work concurrently with the running application, only briefly pausing the world for initial-mark and remark phases. It had two structural problems G1 was built to fix: it never compacted the Old generation (it only swept away dead objects in place), so long-running services would accumulate memory fragmentation until an allocation couldn't find a large enough contiguous block, forcing a full, uncompacted, stop-the-world fallback GC that was far worse than the pauses CMS was designed to avoid; and it required careful, brittle manual tuning to avoid "concurrent mode failure," where the Old generation filled up faster than CMS's concurrent cycle could keep pace. G1 addressed both by design: its region-based layout always compacts as part of normal collection (eliminating the fragmentation failure mode) and it tracks garbage density per region to prioritize work adaptively rather than relying on manually-tuned thresholds. CMS was deprecated in Java 9 and fully removed in Java 14; a candidate bringing it up unprompted is a mild signal of experience with older production systems, but G1 (or ZGC for very large, latency-critical heaps) is the correct answer for "what would you use today."
