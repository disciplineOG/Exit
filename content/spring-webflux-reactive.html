Reactive Spring: WebFlux & Project Reactor

WebFlux Project Reactor Mono & Flux Backpressure Reactive Streams Netty WebClient R2DBC
Why this matters

Imagine ShopSphere's notification-service during a flash sale: an OrderShipped event needs to fan out to push notifications, emails, and SMS across millions of devices, each delivery a slow, high-latency call to a third-party gateway. Built the traditional way, one thread gets tied up per in-flight call, and the service runs out of threads long before it runs out of CPU. Reactive programming exists to solve exactly this shape of problem, and WebFlux is Spring's answer to it — but it is a genuinely different programming model, not just a faster version of what you already know, and using it where it isn't needed (a typical CRUD order-service) adds real complexity for no benefit. Understanding where the line is, and what is actually happening under the hood, is what separates cargo-culting "reactive is faster" from making a sound architectural call.

1. The Problem Reactive Programming Exists to Solve

Classic Spring MVC, running on Tomcat, uses a thread-per-request model: every incoming HTTP request is assigned a thread from a pool, and that thread stays dedicated to that request from the moment it arrives until a response is written back, including for every millisecond the thread spends blocked waiting on a downstream call — a JDBC query, a REST call to another microservice, a disk read. This model is simple to reason about (the code reads top to bottom, exceptions propagate normally, a debugger shows one coherent call stack) and it works well when requests are handled quickly. It breaks down under a specific load shape: many concurrent requests, each of which spends most of its time waiting rather than computing.

This is a variant of the classic C10K problem — the observation, dating back to early 2000s web server design, that a naive server struggles to handle ten thousand concurrent connections not because the CPU is out of capacity, but because the per-connection cost (a thread, with its megabyte-scale stack, plus OS-level context-switching overhead) becomes the bottleneck before the CPU does. In ShopSphere terms: imagine notification-service holding a request thread open for each of 5,000 concurrent deliveries, where each delivery call to an external push-notification gateway takes 200ms to respond. With a thread pool of, say, 200 threads, only 200 deliveries can be in flight at once — the other 4,800 requests queue up, not because the machine lacks CPU cycles (it's mostly idle, waiting on network I/O) but because every thread is parked waiting on a slow socket read. Adding more threads only helps up to a point: each OS thread costs real memory for its stack and adds scheduler and context-switch overhead, so at some scale (tens of thousands of threads) the machine spends more effort managing threads than doing useful work. This is thread-per-request exhaustion — the pool is saturated by waiting, not by computing.

The reactive answer is to stop dedicating a thread to a request for its entire lifetime. Instead, a small, fixed number of threads (an event loop) handles many concurrent operations by never blocking: when an operation would have to wait (a network call, a database round-trip), the thread registers a callback for "let me know when this is ready" and immediately moves on to do other work, rather than sitting idle holding a stack frame. When the slow operation finally completes, some thread from the pool picks up where it left off and continues processing. The same 5,000 concurrent notification deliveries can now be juggled by a handful of event-loop threads, because none of them are ever blocked waiting — they're all either actively computing or not existing as a distinct unit of work until there's something to do.

2. The Reactive Streams Specification and Backpressure

Non-blocking asynchronous code existed in Java long before Reactor, largely through callbacks and Future/CompletableFuture chains, but callback-heavy async code has a well-known problem: composing many async operations together produces deeply nested callback chains ("callback hell") that are hard to read, hard to compose generically, and have no standard way to signal "slow down, I can't keep up." Reactive Streams is a specification (not a library) that a group of engineers from Netflix, Pivotal, Lightbend, and others standardized specifically to fix this: a small set of interfaces — Publisher, Subscriber, Subscription, and Processor — that any reactive library can implement, so that reactive code written against one library (Reactor, RxJava, Akka Streams) can interoperate with another without adapter code, and so that backpressure is part of the contract rather than an afterthought.

The four interfaces work together as follows. A Publisher<T> is a source of a potentially unbounded sequence of values of type T; it does nothing on its own until something subscribes to it. A Subscriber<T> is what consumes those values, receiving callbacks for each item (onNext), for successful completion (onComplete), and for failure (onError). When a Subscriber subscribes to a Publisher, the Publisher hands back a Subscription — an object representing that specific subscribing relationship, through which the Subscriber calls request(n) to say "send me up to n more items" or cancel() to stop early. A Processor is simply something that is both a Subscriber and a Publisher at once — it sits in the middle of a pipeline, consuming from an upstream source and republishing (possibly transformed) values downstream.

The defining feature this specification exists to guarantee is backpressure: the Subscriber, not the Publisher, controls the rate of data flow, by calling request(n) to explicitly ask for only as much as it can currently handle. Without this, a fast producer (say, inventory-service streaming stock-level updates for every SKU as they change) could overwhelm a slower consumer (a downstream analytics job that batches and writes to a data warehouse) by pushing data faster than the consumer can process it, forcing the consumer to either buffer unboundedly (risking an out-of-memory condition under sustained pressure) or drop data silently. With backpressure, the consumer says "send me 100 at a time," processes them, and only then requests the next 100 — the flow-control signal travels backward through the pipeline, all the way to the original source if needed, so the whole chain naturally throttles itself to the pace of its slowest link.

Backpressure is cooperative, not preemptive

It's worth being precise that Reactive Streams backpressure is a pull-based, cooperative protocol — the Subscriber asks for exactly as much as it wants via request(n), rather than the Publisher proactively detecting that the consumer is falling behind and throttling itself. This matters because a Publisher that genuinely cannot be slowed down at the source (like live sensor data that keeps arriving regardless of whether anyone is ready to consume it) still has to make a policy decision when demand runs out — buffer, drop, or error — and Reactor's operators (onBackpressureBuffer, onBackpressureDrop, onBackpressureLatest) exist precisely to make that policy explicit rather than leaving it to chance.

3. Project Reactor: Mono and Flux

Project Reactor is Spring's chosen implementation of the Reactive Streams specification, and it is the reactive library WebFlux is built on. Reactor's API is built around two core types that both implement Publisher, distinguished purely by cardinality — how many elements they can ever emit.

Mono<T> represents a stream that emits at most one value, followed by completion, or an error — never more than one item. It's the reactive equivalent of a CompletableFuture<T> or an Optional<T> combined with asynchrony: a call to fetch a single Order by ID naturally returns a Mono<Order>, because there's either exactly one order, no order (empty Mono), or an error (order lookup failed).

Flux<T> represents a stream that can emit zero, one, or many values (0 to N, including unbounded), followed by completion or an error. A query for all OrderItems belonging to a given order naturally returns a Flux<OrderItem>, since there can be any number of line items. Flux is also the right type for genuinely unbounded, ongoing streams — for example, a live feed of InventoryReserved events being pushed to a dashboard never technically "completes" in normal operation.

Both types share the same rich set of composable operators, which brings us to the next section, and both are lazy in exactly the way described there: creating a Mono or a Flux does not do any work by itself.

4. The Operator Chain Model and Laziness

Reactor code is written as a chain of operators applied to a Mono or Flux, each one returning a new, transformed publisher rather than mutating anything in place. The common operators map directly onto the same ideas as the Java Streams API, but applied to asynchronous, potentially time-delayed data rather than an in-memory collection:

  • map transforms each emitted value synchronously, one-to-one — for example, converting an internal Order entity into an OrderResponseDto.
  • flatMap transforms each emitted value into a new Publisher and flattens the results into the output stream — this is how you chain a dependent asynchronous call: given an Order, call inventory-service to check stock and flatten the resulting Mono<InventoryStatus> into the pipeline, rather than ending up with a Mono<Mono<InventoryStatus>>.
  • filter drops emitted values that don't match a predicate, exactly like its Streams counterpart.
  • zip combines multiple independent publishers, waiting for one value from each before emitting a combined result — useful when order-service needs both the payment status and the inventory status for an order and wants to fire both calls concurrently rather than sequentially, then combine their results once both arrive.
  • retry resubscribes to the upstream publisher when it errors, up to some configured number of attempts (or with a backoff strategy via retryWhen) — directly useful when a call to payment-service's reactive endpoint fails due to a transient network blip.
  • onErrorResume catches an error and substitutes a fallback publisher, letting the pipeline degrade gracefully — for example, falling back to a cached shipping estimate if a live carrier-rate lookup fails, instead of propagating the error all the way to the customer-facing response.

The single most important thing to internalize about this operator chain is that nothing executes until something subscribes. Writing Mono<Order> orderMono = orderRepository.findById(id).map(this::toDto); does not query the database. It builds a description of a pipeline — a recipe for what should happen when someone eventually asks for the result — and no work happens until a Subscriber calls subscribe() on it (which, inside a WebFlux controller, is done for you by the framework once it has a subscriber for the HTTP response). This is why a Mono or Flux built this way is called a cold publisher: each new subscription re-triggers the underlying work from scratch, exactly the way a fresh database query runs every time you subscribe, rather than reusing a previous execution's result. This contrasts with a hot publisher, such as a Sinks-backed Flux broadcasting live InventoryReserved events — subscribers that arrive late simply miss whatever was already emitted before they subscribed, the same way tuning into a live radio broadcast partway through means you missed the beginning, because the source is producing values on its own schedule regardless of whether anyone is listening.

A Mono or Flux you never subscribe to never runs

Because nothing executes until subscribe(), a very common bug for developers new to Reactor is building a pipeline, discarding the resulting Mono/Flux without ever subscribing to it (directly or by returning it from a WebFlux handler, which subscribes on your behalf), and being confused when a downstream call — say, publishing an OrderPlaced event — silently never happens, with no exception and no log line. Reactor even ships a diagnostic, Hooks.onOperatorDebug() and the BlockHound and "dropped Mono" style warnings in newer Reactor versions, specifically because this class of bug is so easy to introduce and so silent when it happens.

5. WebFlux's Runtime: Netty and the Non-Blocking Rule

Spring MVC's default embedded server is Tomcat, running the thread-per-request model described in section 1. WebFlux's default embedded server is Netty, an asynchronous, event-driven network application framework built directly on Java NIO's non-blocking Channel/Selector model — a small pool of event-loop threads multiplexes across many open sockets, reading and writing data only when a socket is actually ready, rather than dedicating a thread to sit and wait on each connection. WebFlux can technically also run on Tomcat, Jetty, or Undertow in a non-blocking servlet 3.1+ mode, but Netty is the default and the runtime most commonly associated with it, precisely because it was purpose-built for this non-blocking style rather than adapted to it.

This runtime choice comes with a rule that is not optional: you must never block inside a reactive pipeline. Every operator in a WebFlux request's chain runs, by default, on one of a small number of Netty event-loop threads shared across potentially thousands of concurrent requests. If any operator in that chain calls something blocking — a synchronous JDBC query via a traditional DataSource, a Thread.sleep(), a blocking call to a legacy synchronous HTTP client, or even certain kinds of heavy synchronous file I/O — that one blocking call ties up an event-loop thread for its entire duration. Because there are only a handful of these threads (commonly one per CPU core), blocking even a few of them can stall a very large number of unrelated, otherwise-ready requests that happen to be scheduled on the same event loop, since those threads are exactly the shared resource every concurrent request depends on to make progress. This is worse than the thread-per-request model's slowness under blocking — in MVC, a blocked thread only stalls its own request; in WebFlux, a blocked event-loop thread can stall many unrelated requests at once. Blocking inside a reactive pipeline doesn't just underperform, it defeats the entire premise WebFlux exists for.

In practice this means every I/O-bound step in a WebFlux pipeline — database access, HTTP calls to other services, message publishing — has to be done through a library that itself speaks Reactive Streams (R2DBC instead of JDBC, WebClient instead of RestTemplate, reactive Kafka producers instead of the standard blocking KafkaProducer API used synchronously). If ShopSphere's notification-service needs to call a legacy blocking SDK for one particular SMS gateway that has no reactive client, the correct pattern is to explicitly offload that call to a separate, bounded thread pool via Mono.fromCallable(() -> legacySmsClient.send(msg)).subscribeOn(Schedulers.boundedElastic()) — isolating the blocking call onto threads set aside for exactly this purpose, so it cannot starve the shared event loop that every other request depends on.

6. WebClient: The Reactive HTTP Client

WebClient is Spring's non-blocking, reactive HTTP client, and it is the reactive-world replacement for the older, blocking RestTemplate (which Spring has in fact deprecated in favor of it for new code, even in non-reactive applications, though RestTemplate remains blocking regardless of which stack calls it). Where RestTemplate.getForObject(...) blocks the calling thread until the HTTP response arrives and returns a plain Java object, WebClient returns a Mono<T> or Flux<T> immediately, describing the eventual response without blocking anything, and composes naturally into a larger reactive pipeline via the same operators covered in section 4.

WebClient client = WebClient.builder()
        .baseUrl("http://inventory-service")
        .build();

Mono<InventoryStatus> statusMono = client.get()
        .uri("/api/inventory/{sku}", sku)
        .retrieve()
        .bodyToMono(InventoryStatus.class)
        .timeout(Duration.ofSeconds(2))
        .retryWhen(Retry.backoff(3, Duration.ofMillis(200)))
        .onErrorResume(ex -> Mono.just(InventoryStatus.unknown()));

// Nothing above has executed a network call yet — it runs when a WebFlux
// handler returns statusMono and the framework subscribes to write the response.

Notice how naturally the resilience operators from section 4 attach to a single downstream call here — a timeout so a slow inventory-service response doesn't hang the pipeline indefinitely, a bounded retryWhen with backoff for transient failures, and an onErrorResume fallback so a persistent failure degrades gracefully rather than propagating an error to the customer. This is also exactly the shape of call that benefits most from WebFlux's model: order-service fanning out to inventory-service, payment-service, and catalog-service concurrently via Mono.zip(...), none of them blocking a thread while waiting, is a textbook case for reactive composition.

7. R2DBC: Reactive Relational Database Access

Standard JDBC, the API underlying nearly all Java relational database access (including what Spring Data JPA and Hibernate ultimately call down to), is fundamentally blocking — a call to execute a query blocks the calling thread until the database responds, full stop, with no non-blocking mode in the specification at all. This makes JDBC directly incompatible with the non-blocking rule from section 5: calling a JDBC repository from inside a WebFlux pipeline blocks an event-loop thread exactly as badly as a raw Thread.sleep() would.

R2DBC (Reactive Relational Database Connectivity) is a separate specification and driver ecosystem purpose-built to close this gap — it defines a genuinely non-blocking API for relational databases, with drivers available for Postgres, MySQL, SQL Server, and others, and Spring Data R2DBC provides repository abstractions over it that return Mono/Flux instead of blocking types, fitting naturally into a WebFlux pipeline without ever tying up an event-loop thread on a database round-trip.

Despite this, most teams do not reach for R2DBC by default, even when they've committed to WebFlux for the web layer, and that hesitation is well-founded rather than mere inertia. R2DBC is a considerably less mature ecosystem than JDBC: it lacks the decades of tooling, connection-pool battle-testing, and ORM sophistication that Hibernate/JPA offers, many of Hibernate's convenience features (lazy loading, the first-level cache, cascading persistence operations, complex entity graph fetching) either don't have a clean reactive equivalent or work meaningfully differently under R2DBC's model, and the pool of engineers who deeply understand R2DBC's failure modes is far smaller than for JDBC. A common, pragmatic middle ground at companies operating at ShopSphere's kind of scale is to run WebFlux for the web/HTTP layer to get non-blocking fan-out to other services, while still using blocking JDBC/JPA for actual database access, deliberately isolated onto a bounded elastic scheduler (Schedulers.boundedElastic()) rather than the shared event loop — accepting a smaller, contained blocking region in exchange for keeping the mature, well-understood JDBC/JPA stack for persistence. R2DBC is reached for selectively: when database-call volume and concurrency are themselves the bottleneck being solved for, not automatically just because the rest of the stack is reactive.

8. A Decision Framework: When WebFlux Earns Its Complexity

Reactive programming is not a strict upgrade over the imperative, thread-per-request model — it is a trade, and like any trade it needs to be justified by the actual load shape a service faces, not adopted because it's the newer or more "advanced"-sounding option. The trade is real on both sides: in exchange for markedly better resource efficiency under a specific kind of load, WebFlux imposes a steeper learning curve (operator-chain thinking is a genuinely different mental model from sequential code), and materially harder debugging — a stack trace captured when an exception surfaces in a reactive pipeline often shows Reactor's internal scheduling and operator-assembly machinery rather than a clean, readable call path through your own business logic, which is why Reactor ships opt-in tooling like assembly-time tracing specifically to make this bearable.

The concrete question to ask is: does this service spend most of its time waiting on many concurrent, slow, high-latency I/O operations, at a volume where thread-per-request would exhaust the thread pool before it exhausts the CPU? notification-service fanning out an OrderShipped event to millions of devices through several external push/email/SMS gateways, each individually slow and each needing to happen for a huge number of concurrent orders, is close to the textbook case reactive programming was built for — the bottleneck is genuinely thread-count-under-waiting, not CPU, and WebFlux's ability to juggle enormous concurrency on a small thread pool directly addresses that bottleneck.

Contrast that with a typical order-service handling standard CRUD operations — create an order, look one up, list a customer's order history — under moderate concurrency. Each request here does a small, bounded amount of work: a database read or write, maybe one or two downstream calls, then a response. Spring MVC on Tomcat handles this shape of load perfectly well; the thread pool is never under the kind of sustained many-thousands-of-concurrent-slow-waits pressure that makes thread-per-request break down, and the code stays simple, debuggable with an ordinary stack trace, and approachable to any engineer who reads sequential Java. Rewriting this service in WebFlux would add real complexity — operator-chain composition, careful auditing of every dependency for blocking calls, harder-to-read stack traces — in exchange for a resource-efficiency benefit the service will likely never actually need, since it isn't hitting the constraint WebFlux relieves in the first place.

The rule of thumb

Reach for WebFlux when a service's concurrency is dominated by waiting on many slow, high-latency downstream calls at a scale where thread-per-request would run out of threads before it runs out of CPU — high fan-out notification systems, API gateways aggregating many backend calls, streaming/real-time feeds. Stay with Spring MVC when a service does a bounded amount of work per request at moderate concurrency, which describes the large majority of ordinary CRUD services. Virtual threads (see Concurrency & Virtual Threads) are increasingly a third option worth weighing here too — they let thread-per-request-style code scale past the traditional platform-thread ceiling without switching to the reactive programming model at all, which for many teams closes much of the gap that used to be WebFlux's main justification.

Concepts Worth Being Able to Explain From First Principles

Why does the C10K problem hurt thread-per-request servers even when the CPU is mostly idle?
Thread-per-request ties up one OS thread for the entire duration of a request, including all the time that thread spends blocked waiting on I/O rather than actually computing anything. Each thread costs real resources regardless of whether it's doing work or waiting — typically a megabyte-scale stack allocation and OS scheduler bookkeeping — so a service handling many concurrent, slow requests (like notification-service waiting on thousands of slow push-gateway calls at once) runs out of usable threads long before it runs out of CPU cycles, because the CPU sits idle while thousands of threads sit parked waiting on network sockets. The fix isn't more CPU, it's not tying up a whole thread for the waiting part at all — which is exactly what an event-loop model does.
What guarantee does the Reactive Streams Publisher/Subscriber/Subscription contract actually provide, beyond "async callbacks"?
Plain async callbacks give you a way to be notified when something completes, but nothing standardizes how a slow consumer tells a fast producer to slow down, and different libraries built incompatible ad hoc solutions to this before the spec existed. Reactive Streams standardizes both interoperability (any conforming Publisher can be consumed by any conforming Subscriber, across library boundaries, without adapter glue) and backpressure as a first-class part of the contract: the Subscription object exposes request(n), giving the Subscriber explicit, ongoing control over how many items it is asking for next, rather than the Publisher unilaterally deciding the pace. That's the concrete guarantee — not just "you'll be told when data arrives," but "you control how much data arrives before you're ready for more."
Concretely, why does a Mono or Flux do nothing until subscribe() is called, and why does that matter in practice?
Building a chain of operators on a Mono or Flux constructs a description of work — a pipeline definition — rather than executing anything immediately; Reactor defers actually running any of it until a Subscriber attaches via subscribe() (which a WebFlux controller does for you once it has something to write a response with). This laziness is what makes operators like retry and timeout meaningful at all — retry has to be able to re-run the upstream work from scratch, which only works if that upstream is a re-runnable description rather than an already-executed result. In practice it also means that a Mono or Flux built but never subscribed to (directly, or via being returned from a WebFlux handler) silently never runs, with no exception, which is a very easy and very quiet class of bug to introduce.
What's the practical difference between a cold and a hot publisher, and where would ShopSphere hit that difference?
A cold publisher re-runs its underlying work from scratch for every new subscriber — a Mono wrapping a database query via findById() queries the database again each time something subscribes, so two subscribers get two independent executions and, potentially, two different results if the data changed between them. A hot publisher, by contrast, is producing values on its own schedule regardless of whether anyone is subscribed, the way a Sinks-backed Flux broadcasting live InventoryReserved events keeps emitting as inventory events actually occur; a subscriber that attaches late simply misses everything emitted before it subscribed, the same way tuning into a live broadcast partway through means missing the beginning. ShopSphere would hit this distinction directly if it built a live inventory-level dashboard: subscribers need to understand they're only seeing events from the moment they connect onward, not a full replay of history, unless the pipeline explicitly adds replay/caching semantics on top.
Why is blocking inside a WebFlux pipeline worse than the same blocking call inside a Spring MVC controller?
In Spring MVC's thread-per-request model, a blocking call inside one request's handler only stalls that one request's dedicated thread — every other request has its own thread and is unaffected. In WebFlux, all requests share a small, fixed pool of Netty event-loop threads (commonly one per CPU core), and a blocking call inside any one request's pipeline ties up one of those shared threads for its entire duration, which can stall every other request currently scheduled on that same event-loop thread, not just the one that made the blocking call. This is the concrete reason "never block in a reactive pipeline" isn't a style preference — a single blocking JDBC call or Thread.sleep() buried in a dependency can quietly degrade throughput for a large number of unrelated concurrent requests at once, in a way that's easy to miss in testing (which typically runs at far lower concurrency than production) and painful to diagnose in production.
Why don't most teams adopt R2DBC by default even after committing to WebFlux for the web layer?
R2DBC closes the specific gap that JDBC's blocking nature creates inside a reactive pipeline, but it does so by trading away a large amount of ecosystem maturity: JDBC and Hibernate/JPA have decades of tooling, well-understood failure modes, connection-pool battle-testing, and ORM conveniences (lazy loading, first-level caching, entity graph fetching) that R2DBC either lacks entirely or implements with meaningfully different semantics. Unless a service's database access pattern is itself the actual concurrency bottleneck being solved for, many teams find it more pragmatic to keep JDBC/JPA for persistence — explicitly isolated onto a bounded elastic scheduler so it can't block the shared event loop — while still getting WebFlux's benefits for the web/HTTP fan-out layer where the real waiting-on-I/O problem lives. R2DBC earns its own added complexity specifically when database call volume and concurrency, not just HTTP fan-out, are the bottleneck.
Give the concrete decision rule: when does WebFlux earn its complexity for a ShopSphere service, and when doesn't it?
The deciding factor is whether a service's concurrency is dominated by waiting on many slow, high-latency downstream calls at a volume where thread-per-request would exhaust its thread pool before exhausting the CPU. notification-service fanning an OrderShipped event out to millions of devices through several slow external gateways fits this precisely — the bottleneck is thread-count-under-waiting, which is exactly what WebFlux's small-event-loop model relieves. A typical order-service doing bounded CRUD work (create, look up, list orders) under moderate concurrency does not fit this profile — Spring MVC on Tomcat handles that load comfortably without ever approaching thread exhaustion, so switching to WebFlux there would add operator-chain complexity, blocking-call auditing burden, and harder-to-read stack traces in exchange for a resource-efficiency benefit the service will never actually need.
Why is debugging a WebFlux pipeline harder than debugging equivalent Spring MVC code, mechanically speaking?
In Spring MVC, an exception's stack trace reflects the actual sequential call path through your own code, because one thread executed the whole request start to finish. In a Reactor pipeline, execution is handed off across operators and, often, across different threads and schedulers as work moves between the event loop and any explicitly-used bounded elastic pool, so a stack trace captured at the point of failure frequently shows Reactor's internal operator-assembly and subscription machinery rather than a clean path through your business logic — the code that logically "called" the failing operator may not even be on the same thread anymore by the time the exception is thrown. This is exactly why Reactor ships opt-in assembly-time tracing (Hooks.onOperatorDebug() and related tooling) specifically to reconstruct a more useful trace at a real but non-trivial performance cost, which is itself a sign of how much default debuggability is traded away by the reactive model.
