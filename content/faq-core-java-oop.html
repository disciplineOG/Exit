Most Asked Interview Questions: Core Java & OOP

OOP Pillars Java Basics Exception Handling Strings Generics Object Methods
Why this matters

Core Java and OOP (Object-Oriented Programming) questions are the opening round of almost every backend Java interview — they're used to filter out candidates who can write code that compiles but can't explain why it behaves the way it does. Interviewers lean on this material because it's foundational to everything else: the way you reason about a String's immutability or a checked exception's design is the same reasoning you'll need later for concurrency, JPA (Java Persistence API) entity equality, or designing a clean service layer. This page consolidates the exact questions that come up most often on encapsulation, inheritance, generics, exceptions, and the Object class contract, with direct, interview-ready answers.

OOP Fundamentals

What is encapsulation and why does it matter?
Encapsulation is the bundling of data (fields) and the behavior that operates on that data (methods) into a single unit — a class — while restricting direct access to the internal state from outside that unit. In Java this is done by declaring fields private and exposing controlled access through public getters/setters or, better, through methods that enforce invariants rather than plain pass-through accessors. The benefit is that the class can change its internal representation without breaking callers, and it can guard against invalid state: a ShopSphere Order class can keep its status field private and only allow transitions through a method like markShipped() that checks the order was previously PAID, rather than letting any caller set the field to an arbitrary value. Without encapsulation, every caller becomes coupled to the internal shape of the class, and invariants can be violated from anywhere in the codebase.
What is inheritance and what problem does it solve?
Inheritance lets a class (the subclass) acquire the fields and methods of another class (the superclass) using the extends keyword, modeling an "is-a" relationship. It solves code duplication: if Customer and Seller both need an id, email, and getDisplayName(), they can both extend a common User base class instead of repeating that code. It also enables polymorphism, since a variable typed as the superclass can hold a reference to any subclass instance, letting calling code work uniformly over a family of related types. The trade-off is tight coupling between subclass and superclass — a change to the superclass can ripple into every subclass — which is why "favor composition over inheritance" is a common guideline discussed separately below.
What is polymorphism, and what's the difference between compile-time and runtime polymorphism?
Polymorphism means the same method call can produce different behavior depending on the actual object or arguments involved. Compile-time polymorphism (also called static binding) is achieved through method overloading, where the compiler picks the correct method based on the argument types and count at compile time — for example, an InvoiceService with both generateInvoice(Order order) and generateInvoice(Order order, Coupon coupon). Runtime polymorphism (dynamic binding) is achieved through method overriding: when a PaymentProcessor reference actually points to a StripePaymentProcessor or PaypalPaymentProcessor instance, the JVM (Java Virtual Machine) resolves which overridden charge() method to invoke based on the object's actual runtime type, not its declared (reference) type. Runtime polymorphism is what makes interfaces and abstract classes useful for writing code against an abstraction while letting concrete behavior vary per implementation.
What is abstraction, and how does it differ from encapsulation?
Abstraction is the practice of exposing only the essential behavior of a component while hiding the implementation details of how that behavior is achieved — it's about designing a simplified interface to a complex system. Encapsulation is the mechanism (access modifiers, bundling data with behavior) used to achieve information hiding at the level of a single class. In practice they work together: a NotificationSender interface abstracts away whether a notification goes out over email, SMS, or push, and each concrete implementation (EmailNotificationSender, SmsNotificationSender) encapsulates its own internal client configuration and connection details that callers never see. The distinction interviewers look for is that abstraction is about the "what" (design-level simplification), while encapsulation is about the "how" (implementation-level protection of state).
When should you use an interface versus an abstract class?
An interface declares a contract — a set of method signatures any implementing class must provide — and since Java 8 it can also include default and static methods with actual bodies, but it still cannot hold instance state (fields other than public static final constants). An abstract class can hold instance fields, constructors, and a mix of implemented and unimplemented (abstract) methods, and a class can extend only one abstract class but implement multiple interfaces. Use an interface when you're defining a capability that unrelated classes might share, like Payable being implemented by both an Order and a SellerPayout; use an abstract class when there's real shared state and partially-implemented behavior across closely related types, like an abstract AbstractNotificationSender that stores a shared retry-count field and implements common retry logic, leaving only send(Notification n) abstract for subclasses. In modern Java, interfaces with default methods have narrowed this gap, but the "can it hold shared mutable state and a constructor" question still decides it.
Why is "favor composition over inheritance" a common design guideline?
Composition means a class holds a reference to another class as a field and delegates to it, rather than extending it — an "has-a" relationship instead of "is-a". Inheritance creates a rigid, compile-time-fixed relationship: subclasses are tightly coupled to superclass internals (the "fragile base class" problem, where changing the superclass can silently break subclass behavior), and Java's single-inheritance-of-classes rule means you're locked into one hierarchy. Composition is more flexible because the composed behavior can be swapped at runtime and combined freely — a ShopSphere Order can compose a PricingStrategy and a ShippingCalculator as injected fields, letting you change pricing logic without touching the Order class or creating an explosion of subclasses like DiscountedExpressOrder. The rule isn't "never use inheritance" — it's that inheritance should be reserved for genuine is-a relationships with stable contracts, while composition should be the default for reusing behavior.
What is the difference between method overloading and method overriding?
Overloading is defining multiple methods with the same name but different parameter lists (different type, number, or order of parameters) within the same class; it's resolved at compile time based on the static (declared) types of the arguments, and it has nothing to do with inheritance. Overriding is a subclass redefining a method it inherited from its superclass with the exact same signature (name, parameter types, and a covariant or identical return type); it's resolved at runtime based on the object's actual type, requires the method not be final, static, or private in the superclass, and is typically annotated with @Override so the compiler can catch signature mistakes. A concrete example: CartService.addItem(Product p) and CartService.addItem(Product p, int quantity) is overloading, while StripePaymentProcessor overriding PaymentProcessor.charge(Order order) with its own implementation is overriding.
What is constructor chaining, and how do this() and super() enable it?
Constructor chaining is the practice of one constructor calling another constructor — either in the same class via this(...) or in the superclass via super(...) — so that shared initialization logic lives in one place instead of being duplicated across overloaded constructors. A call to this(...) or super(...) must be the first statement in a constructor, and if neither is written explicitly, the compiler inserts an implicit no-argument super() call. For example, a ShopSphere Order(String customerId) constructor might chain to this(customerId, Collections.emptyList()) to reuse the full constructor's validation logic, and a GuestOrder subclass constructor would call super(customerId, items) to ensure the base Order state is properly initialized before adding guest-specific fields. This guarantees the entire inheritance chain is initialized top-down exactly once per object construction.
What's the difference between super and this?
this refers to the current instance of the class the code is running in, and is used to disambiguate a field from a constructor/method parameter of the same name (this.email = email;), to invoke another constructor in the same class, or to pass the current object as an argument. super refers to the immediate superclass, and is used to call a superclass constructor (super(id, email)), to invoke a superclass method that's been overridden (super.toString()), or to access a superclass field that's been shadowed by a subclass field of the same name. Both are contextual keywords, not variables — this is unavailable in a static context because there's no instance to refer to, and super in a class with no explicit extends clause implicitly refers to java.lang.Object.
What's the difference between static and instance members?
A static member (field or method) belongs to the class itself, with exactly one copy shared across all instances, and is accessed via the class name (Order.TAX_RATE) rather than an object reference; it's loaded into memory once when the class is loaded and doesn't require an object to exist. An instance member belongs to each individual object, so every Order instance has its own separate copy of fields like orderId or status. A static method cannot access instance members directly (there's no implicit this), which is why utility methods like a PriceUtils.applyDiscount(BigDecimal price, double pct) that don't need per-object state are typically static, while behavior like order.calculateTotal() that depends on that specific order's items must be an instance method.
Why doesn't Java support multiple inheritance of classes, and how do interfaces solve part of that problem?
Java disallows a class from extending more than one class specifically to avoid the "diamond problem" — ambiguity that arises when two parent classes define a method or field with the same signature and the compiler can't unambiguously decide which one a subclass should inherit, along with the general complexity C++-style multiple inheritance introduces around constructor call order and state duplication. Java sidesteps this by allowing a class to implement multiple interfaces, since (prior to Java 8) interfaces carried no implementation or state, so there was nothing ambiguous to resolve — only method signatures, and the implementing class had to supply the single, unambiguous implementation itself. This gives you the practical benefit of multiple inheritance — a class conforming to several contracts, like a DigitalProduct implementing both Shippable and Downloadable — without the ambiguity, since only one of those interfaces can ever contribute actual field state (none can) or a concrete method body that's automatically inherited without the class's involvement.
Since Java 8 added default methods to interfaces, doesn't the diamond problem come back? How is it resolved?
Default methods (introduced in Java 8, declared with the default keyword and a method body inside an interface) do reintroduce a version of the diamond problem: if a class implements two interfaces that both declare the same default method signature, there's now a genuine ambiguity about which implementation to inherit. Java resolves this by refusing to guess — if a class implements two interfaces with a colliding default method and doesn't explicitly resolve it, the code fails to compile with a "class inherits unrelated defaults" error. The developer must explicitly override the method in the implementing class, optionally delegating to one of the parents via InterfaceName.super.methodName() — for example, if both Shippable and Trackable declared a default estimatedDelivery(), a class implementing both would need to override it and could call Shippable.super.estimatedDelivery() to pick one explicitly. This makes the ambiguity a compile-time error the developer must resolve, rather than a silent runtime surprise.
Can an abstract class have a constructor, and can you instantiate it directly?
Yes, an abstract class can (and often should) have a constructor, even though you can never call new directly on the abstract class itself. The constructor exists so that shared initialization logic runs for every concrete subclass — an abstract AbstractNotificationSender(String senderId) constructor can validate and store a senderId field, and every concrete subclass like EmailNotificationSender is required to call it via super(senderId) as part of normal constructor chaining. What Java actually forbids is instantiating the abstract type on its own — new AbstractNotificationSender("x") is a compile error — precisely because an abstract class is defined as incomplete: it may declare one or more abstract methods with no body, so there is no way to guarantee a fully-working object without a concrete subclass supplying those implementations. This trips people up because they conflate "cannot be instantiated" with "cannot have a constructor," but the two are unrelated — the constructor runs only as part of a subclass's object creation, never on its own.
Is Java a purely object-oriented language?
No, and this is a deliberate trick question interviewers use to check whether you understand OOP (Object-Oriented Programming) as a spectrum rather than a binary label. Java relies on eight primitive types (int, double, boolean, and so on) that are not objects at all — they have no methods, no identity, and live outside the normal object model, which is exactly why wrapper classes like Integer exist to bridge the gap when an object is required. Java also has static members that belong to the class rather than to any object instance, which cuts against the pure OOP idea that everything should be a message sent to an object. A "purely" object-oriented language, like Smalltalk, treats even integers and booleans as objects with no primitive escape hatch. The practical takeaway for an interview is to say Java is object-oriented but not purely so, and that this is a pragmatic performance trade-off (primitives avoid object overhead for extremely hot-path values), not an accident.

Java Language Core

What's the difference between JDK, JRE, and JVM?
The JVM (Java Virtual Machine) is the runtime engine that executes compiled Java bytecode (.class files), handling class loading, memory management, and just-in-time compilation to native machine code — it's what makes Java "write once, run anywhere," since each platform has its own JVM implementation but the bytecode is identical. The JRE (Java Runtime Environment) is the JVM plus the core class libraries (java.lang, java.util, and so on) needed to actually run a compiled Java application — if you only need to run a .jar, the JRE is sufficient. The JDK (Java Development Kit) is the full development package: the JRE plus the compiler (javac), debugger, and other tools needed to write and build Java code. In short: JDK ⊇ JRE ⊇ JVM, and you need the JDK to build a ShopSphere microservice but only the JRE (or a JDK, since standalone JRE downloads are less common in modern distributions) to run its compiled artifact in production.
What's the difference between primitive and wrapper types, and what are the common autoboxing/unboxing pitfalls?
Primitives (int, long, double, boolean, and so on) are fixed-size value types stored directly on the stack or inline in an object, with no object overhead and no ability to be null. Wrapper types (Integer, Long, Double, Boolean) are full objects that box a primitive value and are needed anywhere Java requires an object — generic type parameters like List<Integer>, or a field that must represent "unknown/absent" as null. Autoboxing/unboxing is the compiler's automatic conversion between the two, and it has real pitfalls: unboxing a null Integer (say, a quantity field never set on a CartItem) throws a NullPointerException at the point of unboxing; comparing two boxed Integer objects with == works correctly only for cached values from -128 to 127 (the JVM's Integer cache) and silently compares object references outside that range, which is a classic interview trap; and repeated autoboxing inside a tight loop creates unnecessary object allocation and garbage collection pressure compared to using primitives directly.
Is Java pass-by-value or pass-by-reference? What actually happens when you pass an object to a method?
Java is strictly pass-by-value, always — this is one of the most commonly misunderstood facts in the language. For primitives, the value itself is copied into the method's parameter. For objects, what gets copied is the value of the reference (essentially a pointer to the object on the heap) — not the object itself. This means a method can mutate the object's internal state through that copied reference (calling order.setStatus(SHIPPED) inside a method genuinely changes the original Order, since both the caller's reference and the parameter point to the same heap object), but reassigning the parameter itself to a new object (order = new Order();) inside the method has no effect on the caller's variable, because only the copy of the reference was reassigned, not the original. This is why passing an object reference "feels like" pass-by-reference for mutation purposes but is provably pass-by-value once you test reassignment.
What's the difference between final, finally, and finalize?
final is a modifier keyword: on a variable it means the reference (or primitive value) can be assigned only once; on a method it prevents overriding by subclasses; on a class it prevents the class from being extended at all (like String or a modern record). finally is a block attached to a try statement that executes after the try (and any catch) completes, whether or not an exception was thrown, typically used to release resources like closing a database connection. finalize() is an Object method, deprecated for removal since Java 9, that the garbage collector could call before reclaiming an object's memory — it was unreliable (no guarantee of when, or even if, it would run, and exceptions thrown from it were silently ignored) and has been superseded by try-with-resources and the Cleaner API for deterministic resource cleanup. These three are unrelated except for sharing similar spelling, which is exactly why interviewers ask about them together.
What's the difference between a static initializer block and an instance initializer block?
A static initializer block (static { ... }) runs exactly once, when the class is first loaded by the JVM, before any instance is created — it's used to initialize static fields that need more than a simple assignment, like populating a static Map of supported currency codes for a PaymentProcessor class. An instance initializer block (a bare { ... } block, not attached to any method) runs every time a new instance is created, immediately before the constructor body executes, after the superclass constructor has already run — it's less commonly used than a constructor but is useful for initialization logic shared across multiple overloaded constructors. The execution order for a new object is: static blocks (once, at class-load time) → superclass constructor → instance initializer blocks → the constructor's own body.
What are Java's access modifiers, and what does each one actually restrict?
Java has four access levels. private restricts access to within the same class only. Package-private (the default, when no modifier is written) allows access from any class in the same package. protected allows access from the same package plus subclasses in other packages (through inheritance). public allows access from anywhere. A typical layering in a ShopSphere service keeps entity fields private (accessed only through the entity's own methods), keeps internal helper classes package-private so they can't leak outside the module, and exposes only the service's façade methods as public — this is the encapsulation principle applied at the package/module level, not just the class level.
Why is the main method declared as public static void main(String[] args)?
It's public so the JVM, which is calling in from outside the class entirely, can invoke it. It's static because the JVM needs to call this method before any object of the class exists — there's no instance to call it on yet, so it can't be an instance method. It's void because the method communicates its result to the operating system via System.exit(int code) or simply by returning, not via a Java return value. And it takes a String[] parameter to receive command-line arguments passed when the program is launched, such as a config profile name passed to a ShopSphere batch job. Every part of that signature is a hard requirement — the JVM specifically looks for a method matching public static void main(String[]) to know where to start execution, and will refuse to launch the class otherwise.
What is a marker interface, and are they still relevant?
A marker interface is an interface with no methods at all — its sole purpose is to "tag" a class with metadata that other code can check for via instanceof, signaling that the class opts into some special behavior. Classic examples from the standard library are Serializable (tells the JVM's serialization machinery this object's state can be converted to a byte stream) and Cloneable (tells Object.clone() that cloning this type is permitted, otherwise it throws CloneNotSupportedException). They're less commonly designed into new APIs today because annotations (like a custom @Auditable annotation processed via reflection) achieve the same tagging purpose with more flexibility, such as attaching parameters to the tag — but marker interfaces remain relevant because Serializable and Cloneable are still everywhere in existing code and libraries, and the concept is a common interview check on whether you understand that an interface's value doesn't always come from the methods it declares.
How does class loading work, and what's the practical difference between ClassNotFoundException and NoClassDefFoundError in production?
Class loading is the process by which the JVM (Java Virtual Machine) locates a compiled .class file, reads its bytecode, and turns it into a Class object usable at runtime; it happens lazily, on first active use of a class, through a delegating hierarchy of classloaders (bootstrap, for core Java classes; platform/extension; and application/system, for your own code and dependencies), where each classloader asks its parent to load a class first before trying itself, so core classes can never be silently shadowed by application code. ClassNotFoundException is a checked exception thrown when code explicitly asks a classloader to load a class by name at runtime (via Class.forName(), a JDBC driver registration, or a reflection-based plugin lookup) and that class genuinely isn't found on the classpath — common in production when a JDBC driver JAR (Java ARchive) or a Kafka serializer class configured only by string name is missing from the deployed artifact. NoClassDefFoundError is a more subtle production incident: it means the class was present and successfully compiled against at build time, but is missing (or its static initializer failed) when the JVM tries to link it at runtime — the classic cause is a dependency version mismatch, where a service was built against one version of a library JAR but a different, incompatible version ends up on the runtime classpath, or a partial deployment where a shared JAR was updated but not fully rolled out everywhere. The practical debugging distinction is: ClassNotFoundException means "look at what string-based class lookup or plugin config is wrong," while NoClassDefFoundError means "diff the compile-time classpath against the actual runtime classpath," which is exactly the kind of build/deploy mismatch that shows up when a ShopSphere service's shaded JAR silently pulls in a different transitive dependency version than what it was built and tested against.

String Handling

What is the String pool, and what does interning mean?
The String pool (also called the string intern pool) is a special region of the heap where the JVM stores unique String literal values so that identical literals can be reused instead of duplicated in memory. When you write String a = "ORDER"; and String b = "ORDER";, both references point to the exact same object in the pool rather than two separate objects, because the compiler automatically interns string literals. Calling .intern() explicitly on a string built at runtime (say, via concatenation or new String(...)) forces the JVM to check the pool for an equal value and return the pooled reference if one exists, adding it to the pool otherwise — this is useful when you're going to hold onto and compare many repeated runtime-built strings (like normalized product SKUs) and want to save memory. The pool exists specifically because strings are so heavily reused (as literals, map keys, and constants) that deduplicating them has a meaningful memory payoff.
Why is String immutable in Java, and what benefits does that give you?
Once a String object is created, its internal character data can never be changed — any operation that looks like modification (concat, substring, replace, toUpperCase) actually returns a brand-new String object, leaving the original untouched. This is deliberate for several reasons: it makes the String pool safe (since pooled strings can be shared across the whole JVM only if no one can mutate one out from under another reference holder), it makes String safe to use as a HashMap key (a mutable key could change its hash code after insertion, corrupting the map's internal bucket structure), it makes strings inherently thread-safe with no synchronization needed since concurrent readers can never observe a partial write, and it's a security boundary (file paths, class names, and network hosts are frequently represented as strings, and immutability prevents a downstream method from being tricked by a value changing after it was validated). The cost is that heavy string manipulation, like building up a large SQL query or a long log line piece by piece, generates a lot of intermediate garbage — which is exactly what StringBuilder exists to avoid.
What's the difference between StringBuilder and StringBuffer?
Both are mutable, resizable sequences of characters used to build up strings efficiently without creating a new object on every append, unlike concatenating String objects with + in a loop. The difference is thread safety: StringBuffer's methods are synchronized, making it safe to share across multiple threads at the cost of lock-acquisition overhead on every call, while StringBuilder has the identical API but no synchronization, making it faster in the overwhelming majority of cases where the builder is a local variable used by a single thread (such as constructing one order confirmation message inside a single request-handling thread). The practical guidance is simple: default to StringBuilder everywhere; only reach for StringBuffer if you have a specific, verified case of the same builder instance being mutated by multiple threads concurrently — which is rare in practice since most code builds a string within one thread's local scope.
What's the difference between == and .equals() for Strings?
== compares object references — whether two variables point to the exact same object in memory — while .equals() is overridden by String to compare the actual character sequence content, returning true whenever two strings have the same characters in the same order regardless of whether they're the same object. Two string literals with identical content ("ORDER" == "ORDER") will often be ==-equal due to string pool interning, but a string built at runtime, such as new String("ORDER") or the result of concatenating variables, is a distinct heap object and will be ==-false against a pooled literal even though .equals() returns true. Because pooling behavior is a JVM implementation detail you shouldn't rely on for correctness, the rule is absolute: always use .equals() (or .equalsIgnoreCase()) to compare string content, and reserve == for the rare case where you deliberately need reference identity.
Why does overriding equals() require also overriding hashCode()? What's the contract?
The contract, documented on Object, states that if two objects are equal according to equals(), they must return the same value from hashCode() — but the reverse isn't required, meaning unequal objects are allowed to (rarely) share a hash code. Hash-based collections like HashMap and HashSet use hashCode() first to locate the correct bucket, and only then use equals() to check for an exact match within that bucket; if you override equals() to say two Product objects with the same sku are equal but leave the default identity-based hashCode() in place, two logically equal products can hash into different buckets, and a lookup like productSet.contains(sameProductDifferentInstance) will incorrectly return false even though an equal object is present in the set. The practical rule is to always override both together, base both on the same set of fields, and in modern Java let the IDE, Objects.equals()/Objects.hash(), or a record generate them consistently rather than writing them by hand.
Why is String such a popular choice for HashMap keys?
String satisfies every property a good hash key needs simultaneously: it's immutable, so its hash code (which String actually caches internally after first computing it, since the value can never change) is guaranteed stable for the object's lifetime, meaning it can never "go missing" in a map due to a key mutating after insertion. It also has well-defined, well-tested equals() and hashCode() implementations that satisfy the equals/hashCode contract correctly out of the box. And strings are a natural fit for real identifiers — order IDs, product SKUs, customer emails, HTTP header names — which is exactly the kind of value applications need to key lookups on. Combined, this is why you'll see Map<String, Product> or Map<String, Order> constantly in real backend code, versus custom mutable objects, which require careful, deliberate handling to be used safely as keys.
What was the String.substring() memory-leak bug in older Java versions, and what does it teach about designing immutable classes?
Before Java 7 update 6, String.substring() was implemented to share the original string's underlying char[] array, with the new String object just storing a different offset and length into that same array — an optimization that made substring extraction O(1) instead of copying characters. The production landmine this created was a subtle memory leak: if you extracted a short substring (say, a 5-character order-status code) out of a huge string (a multi-megabyte API response body or log line) and kept only the substring around, the entire original multi-megabyte char[] stayed reachable in memory — and therefore un-garbage-collectible — for as long as the small substring reference lived, because both objects pointed at the same backing array. Java 7u6 fixed this by making substring() always copy the relevant characters into a new, appropriately-sized array, trading a small amount of extra copying cost for eliminating the hidden retention risk. The broader lesson interviewers are checking for is that an immutable class's internal sharing optimizations are only safe if they can never let a small, long-lived object accidentally keep a much larger object graph alive — the same category of bug shows up today with things like List.subList() views or streams holding onto a backing collection longer than intended.

Exception Handling

What's the difference between checked and unchecked exceptions?
Checked exceptions extend Exception (but not RuntimeException) and are enforced by the compiler: any method that can throw one must either handle it with a try/catch or declare it in its throws clause, forcing callers to consciously deal with recoverable, expected failure conditions like IOException (a file or network operation failing) or a custom InsufficientInventoryException. Unchecked exceptions extend RuntimeException and require no such declaration or handling — they typically represent programming errors or unrecoverable conditions the caller shouldn't be forced to catch everywhere, like NullPointerException, IllegalArgumentException, or IndexOutOfBoundsException. The design intent is that checked exceptions model "this can fail in ways the caller should plan for" (like a PaymentDeclinedException from payment-service that a caller genuinely needs a fallback for), while unchecked exceptions model "this indicates a bug or an unrecoverable state" — though in modern practice many teams lean toward unchecked exceptions even for business failures, to avoid checked-exception boilerplate spreading through every method signature and lambda.
What is try-with-resources, and how does AutoCloseable enable it?
Try-with-resources is a try statement variant, try (Resource r = ...) { ... }, where any resource declared in the parentheses is guaranteed to have its close() method called automatically when the block exits, whether normally or via an exception — eliminating the need for manual finally { r.close(); } boilerplate and the bugs that come from forgetting it. It works because the resource type implements the AutoCloseable interface, which declares a single close() method; the compiler generates the equivalent of a finally block behind the scenes. This matters for anything that holds an external resource — a JDBC (Java Database Connectivity) Connection, a FileInputStream, or a Kafka consumer/producer client in order-service — since leaking these causes connection pool exhaustion or file handle leaks in a long-running server. You can declare multiple resources in one try-with-resources statement, and they're closed in reverse order of declaration; if both the try block and the automatic close throw, the close's exception is "suppressed" and attached to the original exception rather than replacing it, retrievable via getSuppressed().
How and why would you create a custom exception?
You create a custom exception by extending Exception (for a checked exception) or RuntimeException (for unchecked), typically providing constructors that accept a message and/or a cause, so the exception type itself communicates precise, domain-specific failure information instead of forcing callers to inspect a generic exception's message string. A ShopSphere example is InsufficientInventoryException extends RuntimeException, thrown by inventory-service when a requested quantity exceeds available stock — this lets order-service catch that specific type and trigger a targeted response (notify the customer, release a reservation) instead of a broad, ambiguous catch (Exception e). Custom exceptions are most valuable when the exception type itself needs to carry structured data relevant to handling it, such as the requested and available quantities, and when you want calling code to be able to distinguish this failure mode from others via its type rather than by parsing a message.
What is exception chaining (wrapping), and why is it good practice?
Exception chaining is catching a lower-level exception and wrapping it inside a new, higher-level exception via a constructor that accepts a cause parameter (throw new OrderProcessingException("Failed to reserve inventory", e);), rather than either swallowing the original exception or letting a low-level, implementation-specific exception type leak across an abstraction boundary. The wrapped exception preserves the original stack trace and exception object (accessible via getCause()), so nothing is lost for debugging, while giving callers a more meaningful, higher-level type to catch — order-service's callers should see an OrderProcessingException, not a raw SQLException or KafkaException from an internal dependency. This is especially important at architectural boundaries (service layer wrapping repository-layer exceptions, for instance) so that internal implementation details, like which database driver or message broker is in use, don't leak into the public contract of a class or service.
What happens if a finally block contains a return statement?
A return (or throw, break, or continue) inside a finally block unconditionally overrides any return or exception from the try or catch block — the value or exception from try/catch is discarded entirely, even if an exception was actively propagating. For example, if a try block returns true but the finally block also has a return false;, the method returns false, and if the try block threw an exception but finally returns a value, the exception is silently swallowed and never seen by the caller. This is almost universally considered a bug magnet rather than a useful pattern, because it can silently hide failures — the strong convention, and something linters typically flag, is to never put a return, break, continue, or throw inside a finally block, and to reserve finally purely for cleanup code like closing resources or releasing locks.
What's the difference between throw and throws?
throw is a statement used inside a method body to actually raise a specific exception instance at that point in execution — throw new InsufficientInventoryException(productId, requested, available); — and execution immediately stops flowing normally and starts propagating up the call stack looking for a handler. throws is a clause in a method's signature — public void reserveStock(String productId, int qty) throws InsufficientInventoryException — that declares which checked exceptions the method might propagate to its caller, without itself raising anything; it's purely a compile-time declaration required for checked exceptions so callers know what to handle. In short, throw does the throwing, throws just documents (and, for checked exceptions, is required by the compiler to document) that throwing might happen.
Can you describe Java's exception class hierarchy?
At the root is Throwable, which splits into two branches. Error represents serious problems an application generally shouldn't try to catch or recover from, because they typically indicate the JVM itself is in trouble — OutOfMemoryError or StackOverflowError are examples. Exception represents conditions an application might reasonably want to catch and handle; it further splits into checked exceptions (any subclass of Exception that isn't a RuntimeException, like IOException) and RuntimeException, the root of all unchecked exceptions (NullPointerException, IllegalStateException, and custom unchecked exceptions like InsufficientInventoryException). Knowing this hierarchy matters practically because a broad catch (Exception e) will not catch an Error, which is deliberate — you generally don't want application code pretending it can recover from a JVM-level failure — and catching Throwable directly is almost always a code smell since it also swallows those unrecoverable errors.
Can you catch multiple exception types in one block, and does the order of catch blocks matter?
Yes — Java's multi-catch syntax, catch (IOException | TimeoutException e), lets one block handle several unrelated exception types identically without duplicating code, as long as the listed types aren't in a subtype/supertype relationship with each other (if they were, only the supertype would be needed). Catch block order absolutely matters when the types are related by inheritance: subclasses must be caught before their superclasses, because the JVM matches the first catch clause whose type is assignable from the thrown exception, and once a broader type like Exception has matched, a more specific clause listed after it, like IllegalArgumentException, becomes unreachable — which the compiler actually flags as an error, not just a warning. A practical example is catching a custom InsufficientInventoryException before a general RuntimeException in the same try statement, so the specific inventory-failure branch (release a reservation, notify the customer) runs instead of falling into a generic catch-all.
In a production microservice, how do you decide what to do when a downstream call fails — retry, fail fast, or fall back?
This is a design-judgment question interviewers use to see if you think about exceptions as a reliability concern, not just a language feature. The first split is whether the failure is transient or permanent: a network blip or a momentary connection-pool exhaustion calling payment-service is worth retrying, ideally with exponential backoff and a cap, but a 400-style validation failure or a business rule rejection like InsufficientInventoryException will never succeed on retry and should fail immediately. The second consideration is idempotency — retrying a chargeCard() call blindly can double-charge a customer unless the operation is idempotent (for example, keyed by an idempotency token), so retries are only safe to add once that's guaranteed. The third is blast radius: wrapping a flaky dependency call in a circuit breaker (open the circuit after a failure threshold, so calls fail fast instead of piling up and exhausting threads while a downstream service is degraded) protects the caller from cascading failure, and pairing that with a sensible fallback — like queuing the order for later reconciliation via Kafka instead of failing the whole checkout — is often better than either a bare retry loop or an unhandled exception bubbling to the customer. The wrong answer here is "wrap everything in try/catch and log it," because that treats every failure the same regardless of whether it's recoverable, idempotent, or safe to retry.

Generics & Type System

What are generics, and why were they added to Java?
Generics let you parameterize a class, interface, or method with a type, so the same code works across many types while the compiler still enforces type safety at compile time. Before generics (pre-Java 5), a collection like List could only hold plain Object references, so reading an item back required an explicit cast, and nothing stopped you from accidentally putting the wrong type into the list — that mistake would only surface as a ClassCastException at runtime, often far away from where the bad value was inserted. With generics, List<Order> declares up front that the list only holds Order objects, the compiler rejects any attempt to add something else, and no cast is needed when reading items back out. The core motivation was moving a whole category of type errors from "discovered at runtime, possibly in production" to "caught at compile time," while also making APIs self-documenting about what types they operate on.
What is type erasure, and what does it mean in practice?
Type erasure is the mechanism Java uses to implement generics: generic type information (like the String in List<String>) exists only at compile time, for the compiler to enforce type safety, and is then "erased" from the compiled bytecode — replaced with the type's bound (Object if unbounded, or the bound type otherwise) plus inserted casts where needed. This was a deliberate backward-compatibility decision so generic code could interoperate with pre-generics ("raw type") code compiled before Java 5. The practical consequences show up constantly in interviews: at runtime, List<String> and List<Integer> are both just List — you cannot do if (list instanceof List<String>), you cannot create a new T[10] inside a generic class (discussed below), and you cannot overload two methods that would only differ after erasure, like process(List<String> s) and process(List<Integer> i) in the same class, because after erasure both have the identical signature process(List).
What is a bounded type parameter?
A bounded type parameter restricts what types can be substituted for a generic type variable using the extends keyword (which, for generics, means "extends or implements"), letting the generic code call methods defined on the bound rather than only the methods on Object. For example, class PriceRange<T extends Comparable<T>> guarantees that any type used for T supports compareTo(), so the class's internals can safely compare two T values to determine a min/max range, which wouldn't be possible with an unbounded <T>. You can also specify multiple bounds with &, like <T extends Product & Comparable<T>>, meaning T must satisfy both — be a subtype of Product and implement Comparable — though at most one bound can be a class (and it must come first), while the rest must be interfaces.
What do the wildcards ? extends and ? super mean, and what is PECS?
? extends T (an upper-bounded wildcard) means "some unknown subtype of T," and is used when you only need to read from a generic structure — you can safely call methods that return T, but you cannot add anything to it (beyond null) because the compiler doesn't know the exact subtype. ? super T (a lower-bounded wildcard) means "some unknown supertype of T," and is used when you only need to write into a structure — you can safely add T instances, but reading only guarantees you get back an Object. PECS is the mnemonic for remembering which to use: "Producer Extends, Consumer Super" — if a parameter is a data source your method reads from (a producer of T), use ? extends T, like void processAll(List<? extends Product> products); if a parameter is a data sink your method writes into (a consumer of T), use ? super T, like void collectDiscontinued(List<? super DiscontinuedProduct> sink). This is exactly the pattern behind Collections.copy(List<? super T> dest, List<? extends T> src) in the standard library.
What's the difference between a generic method and a generic class?
A generic class declares its type parameter(s) on the class itself, like class Repository<T> { T findById(String id) { ... } }, and that type parameter is fixed for the lifetime of any given instance — a Repository<Order> only ever works with Order. A generic method declares its own type parameter(s) on the method signature, independent of the enclosing class, like static <T> List<T> singletonList(T item) { ... }, which can be called with a different type argument on every single invocation, and the type is typically inferred by the compiler from the arguments rather than specified explicitly. A generic method is useful specifically when the generic behavior doesn't need to persist across multiple calls or be tied to instance state — a utility like static <T extends Comparable<T>> T max(List<T> items) in a pricing utility class is a generic method even though the class containing it isn't itself generic.
Why can't you create a generic array directly in Java, like new T[10]?
Java arrays are covariant and reify (retain) their component type at runtime — an array knows what type it holds and enforces it with an ArrayStoreException if you try to store the wrong type into it — but generics use type erasure, so at runtime the JVM has no idea what T actually is. If new T[10] were allowed, the array wouldn't have a real component type to check against at runtime, which would silently break the array's own runtime type-safety guarantee and could let incompatible types get stored without any ArrayStoreException ever firing. This is why generic classes that internally need array-like storage, such as a hand-rolled generic stack, typically create an Object[] internally and perform an unchecked cast to T[] (suppressing the compiler warning deliberately), or more commonly just use List<T> backed by an ArrayList instead of a raw array, sidestepping the problem entirely.
Why can't you use a primitive type as a generic type argument, and what's the performance cost of that in production?
Generics are implemented via type erasure, and after erasure an unbounded type parameter is replaced with Object — but primitives like int aren't objects and can't be stored where an Object reference is expected, so the language simply disallows List<int> and requires the wrapper type List<Integer> instead, with the compiler inserting automatic boxing and unboxing at each read/write. The production cost of this is real at scale: a List<Integer> holding a million values isn't a million ints packed contiguously the way an int[] would be — it's a million separate Integer objects scattered across the heap, each with object header overhead, plus the pointer array holding references to them, which multiplies both memory footprint and garbage collector workload compared to a primitive array. This is exactly why hot-path numeric code — a pricing engine recalculating totals across a large in-memory batch of OrderItem quantities, for instance — often deliberately drops down to primitive arrays or a specialized primitive-collection library instead of List<Integer>, and why Project Valhalla's long-running goal of adding true generic specialization (avoiding boxing entirely) is frequently cited as one of the most anticipated future changes to the Java type system.

Object Class & Equality

What do equals(), hashCode(), toString(), and clone() do, and when should you override them?
All four are methods on java.lang.Object that every Java class inherits by default. equals(Object o) defaults to reference identity (==) and should be overridden when two distinct objects should be considered logically equal based on their field values, like two Product instances with the same sku. hashCode() defaults to a JVM-assigned identity-based value and must be overridden consistently whenever equals() is overridden, per the contract discussed earlier. toString() defaults to an unhelpful ClassName@hexHashCode string and should almost always be overridden to produce a human-readable representation useful for logging and debugging, like Order[id=ord-4471, status=PAID, total=59.98]. clone(), defined on Object but only usable if the class implements the Cloneable marker interface, creates a field-for-field copy of an object; it's rarely overridden in modern code because its contract is famously awkward (it throws a checked CloneNotSupportedException, and the default implementation only does a shallow copy), and most codebases prefer copy constructors, static factory methods, or a builder instead.
What's the difference between a shallow copy and a deep copy?
A shallow copy creates a new object and copies each field's value as-is — for primitive fields that means an independent copy, but for reference-type fields it just copies the reference, so the original and the copy end up pointing to the same underlying nested object. This means mutating a nested object through the copy is visible through the original too, which is often not what's intended. A deep copy recursively copies every referenced object as well, so the copy is fully independent of the original at every level. Concretely, shallow-copying an Order that has a List<OrderItem> items field gives you a new Order object but the exact same underlying List (or a new list with the same OrderItem object references) — modifying an item's quantity through the copy would also change it in the "original" order — whereas a true deep copy would create brand-new OrderItem objects too. The default behavior of both Object.clone() and simple copy constructors is shallow unless you deliberately write recursive copying logic for every mutable nested field.
What's the difference between Comparable and Comparator?
Comparable<T> is implemented by the class itself, defining a single "natural ordering" via compareTo(T other) — a Product class might implement Comparable<Product> to sort products by price by default. Comparator<T> is a separate, external object implementing compare(T a, T b), letting you define one or more alternative orderings without modifying the class itself — useful when you need multiple sort orders (by price, by rating, by name) or when you don't own the class's source code at all. In modern Java, comparators are typically built fluently, like Comparator.comparing(Product::getRating).reversed().thenComparing(Product::getName), which sorts by rating descending and breaks ties alphabetically by name. The rule of thumb: implement Comparable for the one "obvious default" ordering a type has, and use Comparator instances for every other ordering you need at a particular call site.
What's the difference between instanceof and getClass() for type checks, and when should you use each?
obj instanceof SomeType returns true if obj is an instance of SomeType or any of its subtypes — it respects the inheritance hierarchy, so a DigitalProduct extends Product instance passes instanceof Product. obj.getClass() == SomeType.class checks for an exact class match only, returning false for subclasses even though they're logically related. Use instanceof (commonly combined with modern pattern matching, like if (obj instanceof DigitalProduct dp), which both checks and casts in one step) when polymorphic behavior is intended and subclasses should be treated the same way as the base type. Use getClass() comparisons specifically inside an equals() override when you want strict symmetry — many correct equals() implementations use getClass() rather than instanceof precisely because instanceof-based equality can break the symmetry requirement of the equals contract (an instance of a subclass could be considered equal to a superclass instance one direction but not the other) when a subclass adds fields relevant to equality.
What are the formal rules (the contract) that a correct equals() implementation must satisfy?
Object.equals() documents five properties any override must satisfy. It must be reflexive (x.equals(x) is always true), symmetric (x.equals(y) must equal y.equals(x) — a common bug is one direction returning true because it uses instanceof while the reverse fails a type check), transitive (if x.equals(y) and y.equals(z) are both true, x.equals(z) must be true too), consistent (repeated calls return the same result as long as the fields used in the comparison haven't changed), and x.equals(null) must always return false rather than throwing. A concrete way this breaks in practice: if DiscountedProduct extends Product adds a discountPct field and its equals() considers two objects equal whenever the sku matches (ignoring the subclass field), a Product and a DiscountedProduct with the same sku can end up equal in one direction but not the other once the subclass's equals() also checks discountPct, violating symmetry. This is precisely why the earlier instanceof vs getClass() question matters, and why effective Java guidance generally favors composition over subclassing when a class needs value-based equality with additional fields.
