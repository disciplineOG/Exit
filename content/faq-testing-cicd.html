Most Asked Interview Questions: Testing (JUnit/Mockito) & CI/CD

Testing Pyramid JUnit 5 Mockito TestContainers CI/CD
Why this matters

Almost every backend Java interview probes whether you can actually verify your own code, not just write it — expect at least one question about JUnit 5, Mockito, or how you'd structure tests for a Spring Boot service, and often a follow-up about how that code gets safely into production through a CI/CD (Continuous Integration / Continuous Delivery or Deployment) pipeline. Interviewers use this cluster of questions to distinguish engineers who can write a compiling test from engineers who understand what a test is actually proving, when a mock is the wrong tool, and why a pipeline is structured the way it is. This page covers the exact testing and CI/CD questions that come up most often, from first-role basics through the production-judgment questions asked of senior and staff candidates.

Unit & Integration Testing

What is the testing pyramid, and what trade-off does it describe?
The testing pyramid is a model for how a healthy test suite should be shaped: a large base of fast, cheap unit tests (testing a single class or method in isolation), a smaller middle layer of integration tests (testing how several components work together — a service class talking to a real or near-real database), and a small top layer of end-to-end (E2E) tests (testing a full user-facing flow across the whole running system, often through the actual API or UI). The trade-off it captures is speed versus confidence: a unit test runs in milliseconds and pinpoints exactly which class broke, but it proves very little about whether the whole system actually works together; an end-to-end test proves the real flow works — placing an order in ShopSphere actually reserves inventory and charges a card — but it's slow (seconds to minutes), flaky (more moving parts means more ways to fail for reasons unrelated to the code under test), and expensive to run on every commit. The pyramid shape is a recommendation to invest most of your effort where feedback is fastest and cheapest, and use the slower, higher-confidence layers sparingly to cover the critical paths that unit tests structurally can't verify, rather than inverting the pyramid into an "ice cream cone" of mostly slow E2E tests and few unit tests, which is a common anti-pattern that makes CI (Continuous Integration) painfully slow and unreliable.
What are the core JUnit 5 annotations you use in almost every test class?
@Test marks a method as a test case that the JUnit 5 (the standard Java testing framework, made up of the JUnit Platform, Jupiter API, and Vintage engine for backward compatibility) runner will execute independently. @BeforeEach marks a method that runs before every single @Test method in the class — typically used to reset or re-create fresh test fixtures (like instantiating the class under test and its mocks) so tests don't leak state into one another; @AfterEach is its mirror, running cleanup after every test. @BeforeAll and @AfterAll run once for the whole class (and must be on a static method unless the class uses @TestInstance(Lifecycle.PER_CLASS)), useful for expensive one-time setup like starting a shared TestContainers database. @ParameterizedTest, combined with a source annotation like @ValueSource, @CsvSource, or @MethodSource, runs the same test logic repeatedly against a table of different inputs — for example, verifying that OrderValidator.isValid() correctly rejects a list of different malformed order payloads — which avoids copy-pasting near-identical test methods that differ only in input and expected output.
What's the difference between a mock, a stub, and a spy?
These terms describe different roles a "test double" (any object standing in for a real dependency in a test) can play, and Mockito (the standard Java mocking framework) blurs some of the lines in practice, but the classic distinction is about intent. A stub is a test double that returns canned, pre-programmed answers to calls made during the test and is not typically checked afterward — you use it purely to get the code under test into the state you want, for example making a stubbed InventoryClient return a fixed stock quantity so OrderService can proceed. A mock is a test double you additionally make behavioral assertions against after the fact — you don't just care what it returns, you verify it was actually called, how many times, and with what arguments (Mockito's verify()), which shifts the test's focus from "what does the code under test return" to "did the code under test behave correctly toward its collaborator." A spy wraps a real object instead of a fully fake one — Mockito's spy() calls through to the real methods by default, and you selectively override just the specific methods you need faked with when(...), which is useful when you want most of an object's real behavior but need to fake one expensive or side-effecting method, though it's used far less often than plain mocks because it can silently invoke real logic (including real I/O) if you forget to stub a method you assumed was faked.
When should you mock a repository versus spin up a real database with TestContainers?
Mocking the repository (Mockito's @Mock or @MockBean on a Spring Data JpaRepository) is right for pure unit tests of the service/business-logic layer, where you want to isolate and verify your own logic — for example, that OrderService.placeOrder() correctly rejects an order when the mocked InventoryRepository reports zero stock — without paying the cost or complexity of a real database, and it runs in milliseconds with no external dependency to start. TestContainers (a library that spins up real, disposable Docker containers — a real Postgres, MySQL, or Kafka instance — for the duration of a test run) is right when what you're actually trying to verify is the database interaction itself: whether your JPA (Java Persistence API) entity mappings, custom @Query annotations, cascade behavior, unique constraints, or transaction boundaries behave correctly against the real database engine's real SQL dialect and locking semantics. A mocked repository can never catch a bug like a query that's syntactically valid against H2 (an in-memory database sometimes used for tests) but fails against real Postgres due to a dialect difference, or a unique-constraint violation that only the real database enforces — this is precisely the class of bug TestContainers exists to catch, at the cost of a slower test (seconds to start a container versus milliseconds for a mock). The practical rule: mock the repository to unit-test business logic in isolation; use TestContainers in a smaller set of integration tests that specifically validate the persistence layer against the real database engine you run in production.
What is contract testing, and why does it matter between independently deployed microservices?
Contract testing verifies that a consumer service and a provider service agree on the shape of the API or message between them — the request/response schema, required fields, status codes, or event payload structure — without either side needing the other's full system running in a test environment. A common approach (Pact is the most widely used framework) has the consumer team write tests against a mock of the provider that record the exact expectations as a "contract" file (for example, order-service expects payment-service's POST /payments to return a JSON body with a transactionId field and one of a fixed set of status enums); that contract is then replayed against the real provider's code in the provider's own pipeline to verify the provider still honors it. This matters specifically in a microservices architecture because each service is built, tested, and deployed independently — a full end-to-end test suite that spins up order-service, inventory-service, payment-service, and notification-service together is slow, flaky, and doesn't scale as the number of services grows, and it also doesn't stop payment-service from being deployed with a breaking change discovered only when order-service breaks in production hours later. Contract tests catch that exact class of breaking API change at CI (Continuous Integration) time, in the provider's own fast pipeline, well before a costly, hard-to-debug cross-service integration failure in a shared staging environment or production.
What's the difference between @SpringBootTest, @WebMvcTest, and @DataJpaTest?
These are Spring Boot's "slice testing" annotations, and they differ in how much of the application context they load — which directly trades off realism for speed. @SpringBootTest boots the entire Spring application context, exactly as it would run in production (all beans, all configuration, optionally a real embedded servlet container with webEnvironment = RANDOM_PORT), making it the most realistic but also the slowest, since a full context with every @Service, @Repository, and @Configuration bean can take real seconds to start. @WebMvcTest(OrderController.class) loads only the web layer — the specified controller, Spring MVC (Model-View-Controller) infrastructure, filters, and JSON serialization — while explicitly excluding @Service and @Repository beans, so you use it to test request mapping, validation, and HTTP status codes in isolation, typically combined with @MockBean to fake the service layer the controller depends on. @DataJpaTest loads only the JPA-related infrastructure — your @Entity classes, Spring Data repositories, and (by default) an in-memory database, auto-configured with each test wrapped in a rolled-back transaction — so you use it to test repository queries and entity mappings without pulling in controllers or services at all. The interview-ready takeaway: pick the narrowest slice annotation that still tests what you actually care about, and reserve full @SpringBootTest for the smaller set of tests that genuinely need the real, fully-wired application.
What does @MockBean do, and how is it different from a plain Mockito @Mock?
A plain Mockito @Mock (used with @ExtendWith(MockitoExtension.class)) creates a fake object entirely outside of Spring — there's no application context involved at all, which is what you want for a pure unit test of a single class. @MockBean is a Spring Boot Test annotation that does something different: it creates a Mockito mock and registers it into the Spring application context, replacing whatever real bean of that type would otherwise have been wired in — so if OrderController autowires an OrderService, annotating a field of type OrderService with @MockBean in a @WebMvcTest swaps out the real (or normally-would-be-absent) service bean with a mock that Spring injects wherever it's needed. You reach for @MockBean specifically when the test needs a real, running (even if partial) Spring context — like a controller slice test where the framework itself performs the dependency injection — and for plain @Mock when there's no Spring context involved at all and you're wiring dependencies together manually or via a test constructor. A practical caution worth mentioning in an interview: overusing @MockBean can force Spring to create a new, slightly different application context per test class (since the context cache is keyed partly by which beans are mocked), which silently defeats Spring Test's context caching and can make a test suite significantly slower.
Why do teams use AssertJ instead of JUnit's built-in assertions, and what does a typical assertion look like?
JUnit 5's built-in assertions (assertEquals(expected, actual), assertTrue(condition)) work, but they're limited: argument order is easy to get backwards, failure messages are often just "expected X but was Y" with no context, and there's no fluent way to chain multiple checks or express intent readably. AssertJ is a fluent assertion library that reads close to natural language and produces much richer failure output — for example, assertThat(order.getStatus()).isEqualTo(OrderStatus.CONFIRMED), or chained on a collection: assertThat(order.getLineItems()).hasSize(3).extracting(LineItem::getSku).contains("SKU-100"). Its main advantages over plain JUnit assertions are: no argument-order confusion (there's only one argument to assertThat, everything else is a fluent method), purpose-built assertions for collections, exceptions, optionals, and dates that would otherwise require verbose manual code, and failure messages that show exactly which element or field didn't match rather than a generic equality failure. AssertJ doesn't replace JUnit — JUnit 5 still provides the @Test runner and lifecycle — it simply replaces the assertion layer, and the two are used together in the overwhelming majority of modern Java test suites.
How do you use Mockito's verify, times, and ArgumentCaptor, and what do they let you check that a return-value assertion can't?
verify(mock).someMethod(...) asserts that a specific method was actually called on the mock during the test — useful when the method under test doesn't return anything you can assert on directly, but has an important side effect, such as verifying that OrderService.placeOrder() actually called inventoryClient.reserve(...) rather than silently skipping it. verify(mock, times(2)).someMethod(...) additionally asserts the call count — catching bugs like a retry loop accidentally calling a downstream service twice when it should call it once, which a simple "was it called" check would miss entirely; related variants include never(), atLeastOnce(), and atMost(n). An ArgumentCaptor<T> goes a step further and actually captures the real argument(s) passed into a mocked call so you can assert on their contents afterward — for example, capturing the PaymentRequest object passed to a mocked paymentClient.charge(...) to assert the exact amount and currency were computed correctly, which plain verify(mock).charge(any()) can't check since any() deliberately ignores the argument's actual value. Together these three let you verify behavior and interaction with collaborators — what was called, how often, and with exactly what data — which is the whole point of using a mock in the first place, as opposed to state-based assertions on a return value.
How do you test that a method throws the expected exception in JUnit 5?
JUnit 5's assertThrows(ExpectedException.class, () -> methodUnderTest()) executes the supplied lambda and asserts that it throws an instance of the given exception type, failing the test if no exception is thrown or if a different exception type is thrown instead; it also returns the caught exception so you can chain further assertions on its message or fields, for example assertEquals("Insufficient stock", exception.getMessage()). This is the standard way to verify a business-rule failure path — for instance, that OrderService.placeOrder() throws an InsufficientStockException when a mocked inventory check reports zero available units — and it's important that the assertion targets the exact method call expected to throw, not the whole test body, so the test fails clearly if the exception is thrown from the wrong line or not at all. AssertJ offers an equivalent, more fluent style with assertThatThrownBy(() -> methodUnderTest()).isInstanceOf(InsufficientStockException.class).hasMessage("Insufficient stock"), which reads more naturally when chaining multiple checks on the thrown exception. Either way, testing failure paths and thrown exceptions is just as important as testing the happy path — a service that only has tests for success cases has no protection against regressions in its validation or error-handling logic, which is often where the highest-value bugs live.
What is the Given-When-Then (or Arrange-Act-Assert) structure, and why does it matter for test readability?
Both names describe the same three-part structure for organizing the body of a single test method, making its intent readable at a glance without needing external comments. Given (or Arrange) sets up the preconditions and test data — constructing the object under test, stubbing its collaborators' return values, building the input. When (or Act) is the single action being tested — calling the one method under test, ideally exactly once per test. Then (or Assert) verifies the outcome — the return value, the resulting state, or an interaction with a mock. Enforcing this structure (often with blank lines or comments marking each section) keeps individual tests focused on verifying one behavior at a time rather than sprawling into a test that sets up state, performs several unrelated actions, and asserts a pile of unrelated things — a test like that is hard to read, and worse, when it fails it's unclear which of several actions actually caused the failure. This convention also naturally discourages testing multiple unrelated behaviors in a single test method, which is a common source of brittle, hard-to-maintain test suites.
What do code coverage tools actually measure, and why is high coverage not the same as a well-tested codebase?
A code coverage tool (JaCoCo is the standard one in the Java ecosystem) instruments your bytecode and reports what percentage of lines, branches, or methods were executed at least once while the test suite ran. The critical limitation interviewers want you to articulate: coverage measures whether a line was executed, not whether its result was actually verified by an assertion — a test that calls orderService.placeOrder(order) and asserts nothing at all still marks every line inside that method as "covered," even though it proves absolutely nothing about correctness. Line coverage is also weaker than branch coverage: a line containing if (a && b) can show as "covered" after a single test run that only ever exercises one combination of a and b, leaving the other logical branches completely unverified. This is why chasing a specific coverage percentage as a target (a common anti-pattern: "we require 90% coverage") can actively produce worse tests — teams write shallow tests purely to move the needle, rather than tests that meaningfully verify behavior — and why coverage is best used as a tool to find untested code you forgot about, not as a proxy for test quality or a gate that guarantees correctness.
What is mutation testing, and what gap does it close that line/branch coverage leaves open?
Mutation testing (PIT, also called Pitest, is the standard Java tool) takes a different approach to measuring test quality: instead of asking "did my tests execute this line," it deliberately introduces small artificial bugs — "mutants" — into your compiled code, such as flipping a > to >=, changing a + to a -, or negating a boolean condition, and then re-runs your existing test suite against each mutated version. If at least one test fails against a given mutant, that mutant is "killed," meaning your tests actually would have caught that specific bug; if every test still passes despite the introduced bug, the mutant "survives," which reveals that your tests execute that code but don't actually assert anything meaningful about its behavior. This directly closes the gap that line and branch coverage leave open: a test suite can have 100% branch coverage and still let most mutants survive, proving the tests run the code without truly verifying its logic. Mutation testing is powerful but expensive — running a full test suite once per mutant, potentially thousands of mutants across a codebase, is computationally heavy — so in practice teams run it selectively (on a critical module, or as a periodic job rather than on every commit) rather than as a routine part of every CI (Continuous Integration) run.
As a senior engineer, how do you approach testing asynchronous, event-driven code — for example, a Kafka consumer in notification-service — and how do you keep a growing test suite from becoming slow and unreliable?
Asynchronous code breaks the simple "call a method, assert the return value" model because the effect you care about — a notification actually being sent after an OrderPlaced event is consumed — happens on a separate thread or process after the test's main thread has already moved on, so a naive test that asserts immediately after publishing the event will be flaky, sometimes passing and sometimes failing depending on scheduling. The right approach is to unit-test the consumer's business logic in isolation by calling the @KafkaListener-annotated method directly with a hand-built event object and asserting on its output or interactions synchronously — no real Kafka involved — and separately run a smaller number of integration tests using TestContainers' Kafka module to verify the actual wiring (serialization, topic names, consumer group configuration), using a polling assertion library like Awaitility (await().atMost(Duration.ofSeconds(5)).until(...)) instead of a fixed Thread.sleep() so the test proceeds the moment the condition is true rather than waiting a fixed, arbitrary duration or risking a too-short sleep. On the broader question of suite health at scale: I'd track and enforce a build-time budget per pipeline stage, aggressively push slow tests down the pyramid or into a separate nightly job rather than every-commit CI, quarantine (not delete) newly flaky tests into a non-blocking job while they're fixed so they don't erode trust in the main signal, and periodically audit for @SpringBootTest overuse and accidental Spring context-cache misses, since a handful of unnecessarily heavy tests are often responsible for the majority of total suite time in a codebase that's grown organically for years.

CI/CD Basics

What are the typical stages of a CI/CD pipeline, and what does each stage verify?
CI/CD stands for Continuous Integration and Continuous Delivery/Deployment — the automated process that takes a code change from a developer's commit to running in production, and a typical pipeline runs these stages in order, failing fast at the earliest possible stage to save time. Build compiles the source code and resolves dependencies (for a Java project, mvn compile or ./gradlew build), catching compilation errors immediately. Test runs the automated test suite — typically fast unit tests first, then slower integration tests — verifying the change doesn't break existing behavior; a failure here stops the pipeline before anything is packaged or deployed. Package produces the deployable artifact — a JAR (Java ARchive) or WAR (Web application ARchive) file, and usually a Docker image built on top of it, tagged with a version or commit hash. Deploy ships that exact artifact to an environment — typically staging first, then production — using whatever deployment strategy the team has chosen (rolling update, blue-green, or canary). Some pipelines add further gates between these stages, like static code analysis, security/dependency scanning, or a manual approval step before production deployment, but build, test, package, and deploy are the stages every backend engineer should be able to describe without hesitation.
What's the difference between blue-green and canary deployment?
Both aim to release a new version with a controlled blast radius and an easy rollback path, but they differ in how much real traffic the new version receives and how the cutover happens. Blue-green runs two complete, identical production environments side by side — "blue" (currently live) and "green" (the new version) — and once green is deployed and verified healthy, traffic is switched over atomically (typically by repointing a load balancer), so at any given moment 100% of traffic is on exactly one environment; rollback is just switching the router back to blue, which is fast, but the approach costs roughly double the infrastructure while both environments exist, and real production traffic never touches green before the full switch. Canary instead releases the new version to a small slice of real traffic first — say 5% of requests — while the rest continues on the stable version, and gradually increases that share as error rate, latency, and business metrics stay healthy, aborting and rolling back the slice if they don't. The practical distinction: blue-green gives an instant, all-or-nothing cutover with a simple rollback but a larger blast radius if a bug slips past pre-cutover verification, while canary gives a much smaller blast radius by exposing the new version to real traffic gradually, at the cost of needing traffic-splitting infrastructure (a service mesh or a smart load balancer/Ingress) and a slower rollout.
Why do feature flags decouple deployment from release, and why does that distinction matter?
A feature flag (or feature toggle) is a runtime conditional — commonly backed by a config value or a dedicated feature-flag service — that gates whether a code path is active, checked with something like if (featureFlags.isEnabled("new-checkout-flow", customer)) rather than the code path being compiled in or out. The key distinction is between two things a traditional deployment conflates into a single event: deployment is getting new code onto production servers, and release is making that new code's behavior actually visible to users. With a feature flag, you can deploy a new payment-service code path to 100% of production instances while the flag keeps it off for everyone, confirm it's stable under real production conditions with no user-visible risk, then turn it on gradually — internal users first, then a small percentage of customers, then everyone — entirely at runtime, with no new deployment needed for either the rollout or an instant rollback (just flip the flag back off, no redeploy, no waiting for a new build to go through the pipeline). This also enables trunk-based development, where incomplete or risky features merge into the main branch and deploy continuously behind a flag without being visible to users, avoiding the long-lived feature branch and painful late merge conflict that the alternative tends to produce.
What is a flaky test, and what are the most common causes?
A flaky test is one that sometimes passes and sometimes fails against the exact same code, with no actual code change between runs — the outcome is nondeterministic rather than a genuine, reproducible signal of a bug. Flaky tests are a serious problem for a CI/CD pipeline specifically because they erode trust: once a team has flaky tests, a red build stops meaning "something is broken" and starts meaning "maybe rerun it," which trains people to ignore failures, including real ones. Common causes include: relying on real wall-clock time or Thread.sleep() instead of properly waiting for an async operation to complete, which fails intermittently under system load when the sleep duration turns out to be too short; shared mutable state leaking between tests that pass individually but fail depending on execution order (a static field, a shared database row, or a singleton not reset between tests); tests that depend on an external network call or a genuinely shared resource, like a real third-party API or a shared staging database another test suite is also mutating; and race conditions in the code under test itself surfacing intermittently under concurrent test execution. The fix is almost never "just rerun it until it passes" — it's isolating shared state per test (fresh fixtures in @BeforeEach), replacing sleep-based waits with polling or proper async test utilities, and using TestContainers or mocks instead of real external dependencies so tests are fully self-contained and deterministic.
As a senior engineer, how would you decide between blue-green, canary, and a plain rolling update for a given service, and what would make you push back on a proposed deployment strategy?
The decision comes down to blast radius tolerance, infrastructure cost, and how observable the service is in production, not a single "best" strategy. A plain rolling update is the right default for most internal or low-risk services — it's the cheapest (no doubled infrastructure) and gives zero-downtime as long as readiness probes correctly gate traffic, but it exposes 100% of the eventual traffic to the new version incrementally with no automatic abort-on-bad-metrics mechanism, so a subtle bug can still reach every user, just staggered over the rollout window. I'd push for canary specifically for a high-traffic, high-blast-radius path — ShopSphere's checkout or payment flow is the textbook case — because limiting a bad change to 5% of real traffic while automated metrics (error rate, p99 latency, payment failure rate) gate the ramp-up catches a class of bug that passes all pre-production testing but only shows up under real production traffic patterns or real payment gateway responses. I'd reach for blue-green specifically when a fast, deterministic, all-or-nothing rollback matters more than gradual exposure — for example, a change that's difficult to run safely in two versions simultaneously against shared state — accepting the doubled infrastructure cost as the price of that guarantee. Where I'd push back: a proposed strategy with no automated rollback trigger tied to real metrics (canary that "someone eyeballs a dashboard for 10 minutes" isn't canary, it's a manual approval gate with extra steps), a rolling update on a stateful service where old and new Pod versions can't safely coexist against the same schema or shared cache, or any strategy applied to a change that also requires a backward-incompatible database migration — no deployment strategy alone solves that; it requires the expand/contract migration pattern (add the new column/table, deploy code that writes both, backfill, then deploy code that only uses the new shape, then drop the old one) regardless of how traffic is cut over.
