Most Asked Interview Questions: SQL, Databases & Indexing

JoinsIndexingNormalizationACIDIsolation LevelsSQL vs NoSQL
Why this matters

Every backend Java service eventually boils down to how well it reads and writes a database, and interviewers use SQL (Structured Query Language) and database questions to check whether you understand what happens underneath your JPA (Java Persistence API) repository calls. A candidate who can explain why a query is slow, what an isolation level actually protects against, or when to reach for NoSQL instead of a relational database is signaling production readiness, not just textbook knowledge. This page covers the core SQL, indexing, transaction, and scaling questions that come up in nearly every mid-to-senior backend interview.

SQL Fundamentals

What are the different types of SQL joins and what does each one return?
An inner join returns only the rows where the join condition matches in both tables — for example, joining Orders to Customers on customer_id returns only orders that have a valid, matching customer. A left join (left outer join) returns every row from the left table plus matching rows from the right table, filling in NULL for right-side columns when there is no match — joining all Customers to their Orders this way would still return customers who have never placed an order, with NULL order columns. A right join is the mirror image, keeping every row from the right table and filling NULL on the left; it is used less often in practice because you can always rewrite a right join as a left join by swapping table order. A full outer join returns the union of both: every row from both tables, with NULLs wherever there is no match on either side, useful for finding mismatches in both directions at once (e.g., orphaned Payments with no Order and Orders with no Payment). A self join joins a table to itself, treating it as two logical copies with different aliases, which is how you'd model a Category table with a parent_category_id column and query each category alongside its parent category in one row.
What is the difference between WHERE, GROUP BY, and HAVING?
WHERE filters individual rows before any grouping happens, so it can only reference columns that exist on the raw row, not aggregate results — for example, WHERE status = 'DELIVERED' on an Orders table. GROUP BY collapses the filtered rows into groups based on one or more columns, typically so an aggregate function (COUNT(), SUM(), AVG()) can be computed per group, such as grouping Orders by customer_id to get each customer's total spend. HAVING filters those groups after aggregation, which is why it can reference aggregate values that WHERE cannot — for example, HAVING SUM(total) > 1000 to find customers whose combined order value exceeds a threshold. The logical execution order is WHERE first (row-level filter), then GROUP BY (collapse into groups), then HAVING (group-level filter), and mixing them up — like trying to use an aggregate in WHERE — is a very common early SQL mistake.
What is the difference between a primary key, a foreign key, and a unique key?
A primary key uniquely identifies each row in a table, cannot be NULL, and a table can have only one (though it may span multiple columns as a composite key) — for example, an order_id column on the Orders table. A foreign key is a column (or set of columns) in one table that references the primary key of another table, enforcing referential integrity so you cannot insert an Order with a customer_id that does not exist in the Customers table, and databases can also be configured to cascade or restrict deletes/updates through that relationship. A unique key (or unique constraint) enforces that all values in a column are distinct, just like a primary key, but a table can have several unique keys, and unlike a primary key a unique column is generally allowed to contain a single NULL value depending on the database — a good example is a Customer's email column, which must be unique but is not what you'd use to physically identify the row internally. In short: primary key is "the" identity of a row, foreign key is a reference to another table's identity, and unique key is any other column (or combination) that must not repeat.
What are the normalization forms (1NF, 2NF, 3NF), and when would you deliberately denormalize?
Normalization is the process of structuring tables to reduce data redundancy and avoid update anomalies. 1NF (First Normal Form) requires that every column hold atomic (indivisible) values and that there be no repeating groups — a Product table storing "red,blue,green" as a single comma-separated colors column violates 1NF and should instead be a separate ProductColor table. 2NF (Second Normal Form) builds on 1NF by requiring that every non-key column depend on the entire primary key, not just part of it, which only matters for tables with composite keys — for example, in an OrderItem table keyed on (order_id, product_id), a product_name column would violate 2NF because it only depends on product_id, not the full key. 3NF (Third Normal Form) further requires that non-key columns depend only on the key and not on other non-key columns (no transitive dependencies) — storing a Customer's city and zip_code together on the Orders table would violate 3NF if city is actually derivable from zip_code, since that data really belongs to a separate lookup. In practice, teams deliberately denormalize (duplicate data or pre-aggregate it) on read-heavy paths where join cost outweighs redundancy risk — for example, storing a denormalized customer_name directly on an Order row so displaying order history never needs to join Customers, accepting that the name could drift if the customer later renames their account.
What is the difference between UNION and UNION ALL?
UNION combines the result sets of two or more SELECT queries and removes duplicate rows from the combined output, which requires the database to do an implicit sort or hash-based deduplication pass across the entire combined result. UNION ALL combines the result sets without removing duplicates, simply concatenating them, which skips that deduplication step entirely and is therefore significantly faster and cheaper on large result sets. For example, combining "orders placed today" and "orders flagged for review" with UNION would silently collapse an order that is in both categories into a single row, while UNION ALL would show it twice. The rule of thumb is: use UNION ALL by default unless you specifically know duplicates are possible and unwanted, since reaching for UNION out of habit on large tables adds unnecessary sorting/hashing overhead.
When does a subquery perform worse than a join, and how should you reason about the two?
A join and a subquery can often express the same logical question, but they don't always execute the same way. A correlated subquery — one that references a column from the outer query, like SELECT * FROM Orders o WHERE EXISTS (SELECT 1 FROM Payments p WHERE p.order_id = o.id) — can force the database to logically re-evaluate the inner query once per outer row if the query planner cannot rewrite it into a join internally, which becomes expensive on large tables. A join generally gives the query optimizer more freedom to choose an efficient execution strategy (hash join, merge join, nested loop) and to use indexes on both sides at once, because the relationship between the two tables is explicit rather than hidden inside a nested query. Modern query optimizers (PostgreSQL, MySQL 8+) are often smart enough to rewrite a simple IN or EXISTS subquery into an equivalent join automatically, so the gap has narrowed, but a non-correlated subquery used purely for filtering (like WHERE customer_id IN (SELECT id FROM Customers WHERE region = 'US')) is usually fine either way. The practical interview answer: prefer a join when you need columns from both tables or when the subquery is correlated, and always check the actual execution plan rather than assuming one form is always faster.
What is the N+1 query problem, and how do you fix it in a Java/JPA (Java Persistence API) application?
The N+1 query problem happens when code fetches a list of N parent entities with one query, then lazily triggers a separate query for each parent's related child collection, resulting in 1 + N total round trips instead of a small, fixed number — for example, loading 100 Orders and then accessing order.getItems() on each one inside a loop fires 100 additional queries against OrderItem if the association is lazily fetched. This is easy to miss in development with small datasets and only becomes visible as a production latency spike once the parent list grows large, which is why it's a classic "worked fine in staging, fell over in production" bug. The standard JPA/Hibernate fixes are: a JOIN FETCH in JPQL (Java Persistence Query Language) to pull the association in the same query, an @EntityGraph to declare which associations to eagerly load for a specific query, or batch fetching (@BatchSize / hibernate.default_batch_fetch_size) which groups the follow-up queries into a handful of WHERE id IN (...) calls instead of one per row. The interview-ready diagnostic is: turn on SQL logging (or use a tool like Hibernate's statistics or a query counter in tests) and watch for a suspiciously large, list-size-proportional number of queries for what looks like one logical fetch.

Indexing & Query Performance

What is a database index, and why do we need one?
An index is a separate on-disk data structure (almost always a B-tree, sometimes a hash or other structure) that stores a sorted or otherwise fast-to-search copy of one or more columns' values along with a pointer back to the full row, so the database can locate matching rows without reading every row in the table. Without an index, looking up a Customer by email requires a full table scan — the database checks every single row in order, which is fine for a hundred rows but far too slow once a table has millions. An index trades extra disk space and slightly slower writes (since the index has to be updated too) for dramatically faster reads on the columns it covers, similar to how a book's index lets you jump to a page instead of reading cover to cover to find a topic. The columns worth indexing are the ones frequently used in WHERE clauses, JOIN conditions, and ORDER BY clauses — indexing everything "just in case" is a common beginner mistake that quietly slows down every write instead.
What is the difference between a clustered and a non-clustered index?
A clustered index determines the actual physical storage order of the table's rows on disk — the table data itself is organized as the index, which is why a table can have only one clustered index (you can't physically sort the same rows two different ways at once). In most databases, the primary key is the clustered index by default, so an Orders table clustered on order_id physically stores rows in ascending order_id order. A non-clustered index is a separate structure that stores the indexed column's values alongside a pointer (or the primary key value) back to the actual row location, and a table can have many non-clustered indexes — for example, a non-clustered index on Orders.customer_id lets you quickly find that customer's orders without scanning the whole table, but the database still needs an extra lookup step to fetch the full row once it finds a match. The practical trade-off is that clustered index lookups (especially range scans) are generally faster because matching rows are physically adjacent, while non-clustered indexes add flexibility for querying by other columns at the cost of that extra indirection.
How does a B-tree index actually speed up a query?
A B-tree (balanced tree) index organizes indexed column values into a sorted, multi-level tree structure where each node holds a range of key values and pointers either to child nodes or, at the leaf level, to the actual row data. Without an index, finding a specific Customer by email requires a full table scan — checking every row one by one, an O(n) operation. With a B-tree index on email, the database instead starts at the root node and repeatedly compares the target value to a small number of keys per node to decide which branch to descend into, reaching the matching leaf in O(log n) comparisons regardless of table size, because the tree stays balanced (all leaves at the same depth) as data is inserted and deleted. Because the tree is sorted, B-tree indexes are also efficient for range queries (WHERE created_at BETWEEN ? AND ?) and for ORDER BY, since a contiguous range of the sorted leaves can be walked directly without re-sorting. This is the default index type in essentially every relational database precisely because it handles both equality lookups and range scans well.
Why can having too many indexes hurt write performance?
Every index on a table is a separate data structure that must be kept in sync with the table's data, so every INSERT, UPDATE, or DELETE has to update not just the table's heap/clustered storage but also every index that covers a changed column. A Product table with five indexes means a single price update potentially triggers up to five additional B-tree rebalancing operations (if the price column is indexed) or at minimum requires the database to locate and touch each index entry pointing at that row. This is why write-heavy tables (like an Inventory table taking constant stock decrements during a flash sale) should carry only the indexes that are actually earning their keep on the read side, and why "just add an index" is not a free performance fix — it directly trades read speed for write speed and extra storage. The practical guidance is to index columns used in frequent WHERE, JOIN, or ORDER BY clauses, and periodically audit for indexes that are never used by the query planner but are still silently taxing every write.
How does column order matter in a composite index?
A composite (multi-column) index builds a single sorted structure keyed on the concatenation of its columns in the order they are declared, which means the index is only efficiently searchable as a left-to-right prefix of that column list — this is often called the "leftmost prefix rule." An index defined as (customer_id, order_date) can efficiently serve a query filtering only on customer_id, or on both customer_id and order_date together, but it cannot efficiently serve a query that filters only on order_date, because within the index, order dates are only sorted locally within each customer's block, not globally. This means the column order should generally be chosen based on query patterns: put the column used for equality filtering first (or the one with higher selectivity, i.e. that narrows the result set the most), and range-filtered or sorted columns later. Getting this backwards is a very common real-world cause of a query silently falling back to a full table scan despite an index technically existing on the right columns.
How do you read an EXPLAIN plan at a basic level?
EXPLAIN (or EXPLAIN ANALYZE, which actually runs the query and reports real timings) shows the execution plan the database's query optimizer chose, letting you see whether it used an index or fell back to scanning the whole table. The main thing to look at first is the access method per table: a Seq Scan/Full Table Scan means every row was read, which is expected on small tables but a red flag on large ones, while an Index Scan or Index Only Scan means the database used a B-tree to jump directly to matching rows. The plan is typically read from the innermost/bottom operation outward, since outer operations (joins, sorts, aggregates) consume the output of inner ones, and each node usually reports an estimated row count and cost, which you compare against the actual row count (in ANALYZE output) to spot cases where the optimizer's statistics are stale and it's making a bad plan choice as a result. In an interview, the key signal to give is: "I'd check whether it's doing a sequential scan on a large table where I expected an index scan, and compare estimated versus actual row counts to catch bad statistics or a missing index."
What is a covering index?
A covering index is an index that contains every column a particular query needs, either as part of the indexed key or as additional non-key columns included alongside it, so the database can satisfy the entire query directly from the index without a further lookup into the actual table (this extra lookup is often called a "bookmark lookup" or is what turns an Index Scan into a slower Index Scan plus row fetch). For example, a query like SELECT customer_id, status FROM Orders WHERE customer_id = ? can be fully covered by an index defined as (customer_id) INCLUDE (status) (or simply a composite index on (customer_id, status) in databases without an explicit INCLUDE syntax), because both the filter column and the selected column live in the index itself. This shows up in an EXPLAIN plan as an "Index Only Scan," which is faster than a regular index scan because it avoids the random-I/O cost of jumping back to the heap/table storage for every matching row. The trade-off is the usual one: a covering index is larger and costs more to maintain on writes than a narrower index, so it's worth doing deliberately for hot, frequently-run queries rather than everywhere.
What is database connection pooling, and why does a backend Java service need it?
Opening a raw database connection (TCP handshake, authentication, session setup) is expensive — often tens of milliseconds — so opening and closing a brand-new connection for every single request would make a busy service painfully slow and could exhaust the database's max-connections limit under load. A connection pool (HikariCP is the default in Spring Boot) solves this by opening a fixed set of connections once at startup and handing them out to threads on demand: a thread borrows a connection, runs its queries, and returns the connection to the pool instead of closing it, so the next request reuses it. This turns connection acquisition from a slow network round-trip into a fast in-memory checkout, and it also protects the database by capping the maximum number of concurrent connections any one service instance can open. Sizing the pool matters in an interview-worthy way: a pool that's too small causes threads to queue up waiting for a connection (visible as connection-acquisition timeouts under load), while a pool that's too large can overwhelm the database with more concurrent work than it can efficiently execute — HikariCP's own guidance is that pool size should be modest (roughly matching available database CPU cores plus some headroom), not scaled up to match application thread count. In ShopSphere, order-service and payment-service would each maintain their own pool against their database, and a leaked connection (one borrowed but never returned, usually from a missing close() or an uncaught exception around a JDBC (Java Database Connectivity) call) is a classic production bug that slowly starves the pool until every request times out.
How would you safely add an index to a huge, high-traffic production table without an outage?
A naive CREATE INDEX on a large table can take a full exclusive (or heavily blocking) lock on the table for the entire build, which for a hot table like Orders in ShopSphere could mean every write blocks for minutes, effectively causing an outage on the write path. Most production databases offer a non-blocking or "online" index build for exactly this reason — PostgreSQL's CREATE INDEX CONCURRENTLY and MySQL's online DDL (Data Definition Language, e.g. ALGORITHM=INPLACE) build the index in the background while still allowing reads and writes, at the cost of taking longer overall and requiring roughly double the disk I/O (input/output) during the build. The trade-off to call out in an interview is that concurrent/online builds are not fully atomic the way a blocking build is: if the build fails partway through, PostgreSQL can leave behind an invalid index that has to be manually dropped and retried, so it needs monitoring rather than a fire-and-forget assumption. The senior-level judgment call is timing and staging: run the build during a low-traffic window if one exists, verify replica lag and disk headroom beforehand, and validate the new index is actually being picked up by EXPLAIN before dropping any old index it's meant to replace.

Transactions, ACID & Consistency

What is a database transaction, and how do you demarcate one in a Spring Boot application?
A transaction is a group of one or more database operations that are treated as a single unit of work — they either all commit together or all roll back together, so the database never ends up in a state where only some of them took effect. In plain JDBC (Java Database Connectivity) you'd demarcate one manually with connection.setAutoCommit(false), then call commit() or rollback() yourself, but in Spring Boot you almost always use the declarative @Transactional annotation on a service method instead, which wraps the method body in a transaction automatically using a proxy that Spring generates around your bean. For example, an order-service method that inserts an Order row and decrements Inventory stock would be annotated @Transactional so that if the inventory update fails, the order insert is rolled back too, rather than leaving an Order with no corresponding stock reservation. The one beginner trap worth knowing: @Transactional only works through Spring's proxy, so calling an @Transactional method from another method on the *same* class (self-invocation) bypasses the proxy entirely and silently runs without a transaction.
What do the ACID properties mean concretely?
ACID stands for Atomicity, Consistency, Isolation, and Durability, and together they define what a transaction guarantees. Atomicity means a transaction's operations either all succeed or all fail as a single unit — if placing an Order involves inserting the Order row, decrementing Inventory, and creating a Payment record, and the payment step fails, atomicity guarantees the Order and Inventory changes are rolled back too, not left half-applied. Consistency means a transaction can only move the database from one valid state to another valid state, respecting all constraints (foreign keys, unique constraints, check constraints) — you can never end up with an OrderItem referencing a Product that doesn't exist. Isolation means concurrent transactions should not see each other's uncommitted intermediate state, so two customers checking out at the same time don't interfere with each other's view of Inventory stock. Durability means once a transaction commits, its changes survive even a subsequent crash or power loss, typically implemented via a write-ahead log that is flushed to disk before the commit is acknowledged. These four properties are why relational databases are the default choice whenever correctness under concurrent, failure-prone conditions matters more than raw throughput.
What are the transaction isolation levels, and which anomalies does each one prevent?
There are three classic read anomalies to know: a dirty read is seeing another transaction's uncommitted changes (which might later be rolled back); a non-repeatable read is re-reading the same row within one transaction and getting a different value because another transaction committed a change to it in between; a phantom read is re-running the same range query within one transaction and getting a different set of rows because another transaction inserted or deleted rows matching that range in between. READ UNCOMMITTED prevents none of these — it allows dirty reads and is rarely used in practice. READ COMMITTED (the default in PostgreSQL and Oracle) prevents dirty reads by only ever showing committed data, but still allows non-repeatable reads and phantoms. REPEATABLE READ (the default in MySQL/InnoDB) additionally prevents non-repeatable reads by guaranteeing that any row you've already read stays the same for the rest of your transaction, though it can still technically allow phantoms in some implementations. SERIALIZABLE is the strictest level and prevents all three, effectively making concurrent transactions behave as if they ran one after another in some order, at the cost of the most blocking/aborting under contention. A payment-service capturing a Payment against an Order would typically want at least READ COMMITTED, with stronger guarantees considered specifically around balance or stock checks where a race condition would cause real financial or inventory damage.
What is MVCC (Multi-Version Concurrency Control), and how does it relate to isolation levels?
MVCC is the mechanism most modern relational databases (PostgreSQL, MySQL/InnoDB, Oracle) use to implement isolation without simply locking every row a transaction reads. Instead of overwriting a row in place on UPDATE, the database keeps multiple versions of that row tagged with the transaction ID (or timestamp) that created them, and each transaction sees a consistent "snapshot" of the data as of when it started (or as of each statement, depending on isolation level), ignoring versions created by transactions that started later or haven't committed. This is why readers don't block writers and writers don't block readers under MVCC — a long-running report query reading Orders doesn't need to wait for a concurrent Order insert to finish, because it's simply looking at an earlier snapshot rather than fighting over a lock. The trade-off is that old row versions have to be cleaned up eventually (PostgreSQL's VACUUM process, or InnoDB's purge thread) or the table and its indexes bloat with dead versions, which is a real operational concern on high-write tables like Inventory that get frequent updates. In an interview, connecting MVCC back to isolation levels shows depth: REPEATABLE READ and SERIALIZABLE are commonly implemented on top of MVCC snapshots rather than pure locking, which is part of why they can prevent non-repeatable reads without blocking every reader.
How does @Transactional propagation and rollback behavior work, and what's a common mistake with it?
Spring's @Transactional has a propagation setting that controls what happens when an already-transactional method calls another @Transactional method: the default, REQUIRED, joins the existing transaction so both methods commit or roll back together as one unit, while REQUIRES_NEW suspends the outer transaction and starts a brand-new, independent one that commits or rolls back on its own — useful when you want an audit-log write (like recording a failed Payment attempt) to persist even if the surrounding business transaction later rolls back. The common mistake is around rollback rules: by default, Spring only rolls back a transaction on an unchecked exception (a RuntimeException or Error) and does *not* roll back on a checked exception, so a method that throws a checked Exception subtype to signal failure will silently commit the partial work unless you explicitly declare @Transactional(rollbackFor = Exception.class). This surprises engineers coming from a "checked exceptions mean explicit error handling" mindset, and it's a real production bug pattern: an order-service method that throws a checked InsufficientStockException partway through can leave an Order row committed with no matching Inventory decrement, exactly the inconsistency ACID (Atomicity, Consistency, Isolation, Durability) is supposed to prevent, purely because the exception type didn't match Spring's default rollback rule.
What is the difference between optimistic and pessimistic locking?
Optimistic locking assumes conflicts between concurrent transactions are rare, so it doesn't block anything upfront — instead it detects a conflict at write time, commonly using a version column: every update includes a WHERE version = :expectedVersion clause, and if another transaction already changed that row (bumping the version), zero rows match and the application knows to retry or surface a conflict to the user. Pessimistic locking assumes conflicts are likely and prevents them upfront by acquiring an actual database lock on the row as soon as it's read (SELECT ... FOR UPDATE), blocking any other transaction from reading (with intent to write) or writing that row until the lock-holder commits or rolls back. Optimistic locking scales better under low contention because nothing ever blocks, making it a good fit for something like a Seller editing a Product's description, where collisions are rare. Pessimistic locking is safer under high contention on a single hot row — for example, decrementing Inventory stock for a single Product during a flash sale, where dozens of concurrent Orders are racing for the same row and you'd rather serialize access than have most attempts fail optimistically and need to retry.
What is a deadlock, and how do databases detect and resolve it?
A deadlock occurs when two or more transactions are each holding a lock the other one needs, so none of them can proceed — classically, Transaction A locks Order row 1 and then tries to lock Order row 2, while Transaction B has already locked row 2 and is waiting on row 1. Databases detect this by maintaining a "waits-for" graph of which transactions are blocked waiting on locks held by which other transactions, and periodically checking that graph for a cycle; if a cycle exists, a deadlock has occurred. Once detected, the database picks one transaction as the "victim" (usually the one that has done the least work, or the one that would be cheapest to roll back) and forcibly aborts it with a deadlock error, releasing its locks so the other transaction(s) can proceed; the aborted transaction's application code is expected to catch that error and retry. The practical way to avoid triggering deadlocks in application code is to always acquire locks on multiple rows in a consistent, agreed-upon order across the whole codebase — for example, always locking Orders before Inventory rows, never the reverse — so two transactions can never form a waiting cycle in the first place.

SQL vs NoSQL & Scaling

What is the basic difference between a relational (SQL) database and a NoSQL database?
A relational database organizes data into tables with a fixed, predefined schema (named columns with declared types), enforces relationships between tables via foreign keys, and is queried with SQL (Structured Query Language) — PostgreSQL, MySQL, and Oracle are all relational. A NoSQL ("not only SQL") database covers several different data models — document stores like MongoDB, key-value stores like Redis, wide-column stores like Cassandra — that generally allow a flexible or schema-less structure, don't require joins to be efficient, and are designed to scale out horizontally across many machines more easily than a traditional relational database. A simple way to frame it for an interview: a Customer's Order history with strict relationships between Orders, OrderItems, and Payments naturally fits a relational schema, while a Product catalog entry with wildly different attributes per category (a T-shirt has a size and color; a laptop has RAM and storage) fits more naturally as a flexible document. Neither is strictly "better" — they make different trade-offs around schema flexibility, consistency guarantees, and how they scale, which is why real systems often use both side by side.
What are the trade-offs between SQL and NoSQL databases, and when would you choose each?
SQL (relational) databases enforce a fixed schema, support ACID (Atomicity, Consistency, Isolation, Durability) transactions across multiple tables, and use SQL joins to model relationships, which makes them the natural fit whenever data integrity and complex relationships matter more than raw write throughput — an Order/OrderItem/Payment structure with strict referential integrity is a textbook relational use case. NoSQL databases (document stores like MongoDB, key-value stores like Redis or DynamoDB, wide-column stores like Cassandra) generally trade strict schema and strong consistency for horizontal scalability and flexible, often denormalized data models, making them a better fit for very high write volumes, rapidly evolving schemas, or data that is naturally accessed as a single self-contained document rather than joined across tables — for example, storing a Product's full catalog listing (title, images, variable attributes per category) as a single flexible document rather than a rigid set of relational columns. Most NoSQL systems also favor eventual consistency over strict ACID guarantees, which is a deliberate trade-off for availability and partition tolerance. In practice, ShopSphere would use a relational database for order-service and payment-service where correctness and transactions are non-negotiable, while catalog-service (flexible per-category product attributes) or a session/cart cache might reasonably use a NoSQL or key-value store.
What is the difference between database sharding and replication?
Sharding (horizontal partitioning) splits a single logical table's data across multiple independent database instances based on a shard key, so each shard holds a distinct subset of the rows — for example, sharding the Orders table by customer_id range or hash, so customers 1–1M live on shard A and customers 1M–2M live on shard B. Its purpose is to scale write throughput and total data volume beyond what a single machine can hold, since each shard only handles a fraction of the total load. Replication instead copies the entire dataset (or entire shard) onto multiple database instances, so every replica holds the same data — its purpose is redundancy (surviving a node failure) and scaling read throughput, since read queries can be spread across replicas. The two are complementary and commonly combined: a large system might shard Orders across several shards for write scalability, while each individual shard also has its own set of read replicas for read scalability and failover.
What are read replicas, and what is replication lag?
A read replica is a copy of a primary (or "leader") database that continuously applies the same stream of writes the primary receives, and is used to serve read-only queries so they don't compete with write traffic on the primary. Replication is typically asynchronous for performance reasons — the primary doesn't wait for a replica to confirm it applied a write before acknowledging the write as committed — which introduces replication lag: a small window of time during which a replica's data is behind the primary's actual current state. Replication lag becomes a real bug source when an application writes data on the primary and then immediately reads it back from a replica expecting to see it, such as a Customer placing an Order and the confirmation page querying a replica that hasn't caught up yet, appearing to show no order at all. Common mitigations are routing "read your own write" queries to the primary for a short window, using synchronous replication for critical data at a latency cost, or designing the UI to tolerate brief staleness.
What is the difference between vertical and horizontal database scaling?
Vertical scaling ("scaling up") means increasing the resources (CPU, RAM, faster disks) of a single database server to handle more load, which is simple — no application changes, no distributed data — but has a hard ceiling, since there is a maximum size of machine you can buy or rent, and it usually means downtime to resize. Horizontal scaling ("scaling out") means adding more database instances (via replication for reads, or sharding for writes) to spread load across multiple machines, which scales much further in theory but introduces real complexity: cross-shard queries and joins become hard, replication lag has to be managed, and the application needs shard-awareness or routing logic. The typical progression for a growing system like ShopSphere is to scale vertically first because it's cheap and simple, add read replicas once read traffic outgrows a single instance, and only shard the write path once a single primary's write throughput genuinely becomes the bottleneck, since sharding is the most operationally expensive step to reverse.
What is the CAP theorem, and how does it apply to database choices?
CAP theorem states that a distributed data system can only guarantee two of three properties at the same time during a network partition: Consistency (every read sees the most recent write, or an error), Availability (every request receives a non-error response, even if it isn't the latest data), and Partition tolerance (the system keeps working despite network failures splitting nodes from each other). Because network partitions are a real possibility in any distributed system, partition tolerance is effectively mandatory, which means the real-world choice is between prioritizing consistency (a "CP" system, like a strongly consistent config store) or availability (an "AP" system, like a distributed cache) when a partition actually happens. Most traditional relational databases run as a single primary node handling writes, so CAP mostly becomes relevant once you introduce distributed replicas or a distributed NoSQL store — for example, a multi-region Cassandra cluster backing a Product catalog might be tuned AP (stay available and resolve conflicting writes later) since briefly showing a stale product description is low-risk, while an Inventory or Payment system would lean CP, since briefly being unavailable is preferable to letting two customers both believe the last unit of stock is available.
What does BASE (Basically Available, Soft state, Eventually consistent) mean, and how is it different from ACID?
BASE is the consistency philosophy most AP (Availability + Partition tolerance)-leaning NoSQL systems favor, and it's deliberately framed as the opposite end of the spectrum from ACID (Atomicity, Consistency, Isolation, Durability). Basically available means the system prioritizes always responding to requests, even during a failure, rather than blocking or erroring out to guarantee correctness. Soft state means the system's state can change over time even without new input, because background replication is still converging data between nodes. Eventually consistent means that if no new writes occur, all replicas will eventually converge to the same value, but there's no guarantee about exactly when — a read immediately after a write might see stale data. A concrete ShopSphere example: a Product's view count or a Review's "helpful" tally stored in a Cassandra-style store is a fine candidate for eventual consistency, since a few seconds of staleness costs nothing, whereas an Order's payment status is not, since customers and support staff would be confused (or worse, double-charged) by an inconsistent view. The interview-ready framing: ACID makes correctness the default and asks you to opt into relaxed guarantees for performance; BASE makes availability the default and asks you to design around the fact that data might briefly be stale or inconsistent.
