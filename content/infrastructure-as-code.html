Infrastructure as Code: Terraform Fundamentals for Backend Engineers

Terraform Infrastructure as Code State Management Declarative Provisioning Drift Detection Remote Backends Modules
Why this matters

Every AWS resource covered in cloud-fundamentals — the RDS instance backing order-service, the SQS queue carrying OrderPlaced events, the ECS service running payment-service — has to actually come into existence somehow, and "someone clicked through the console" is a description of how ShopSphere's production infrastructure quietly becomes undocumented, unreproducible, and different from staging in ways nobody can explain during an incident. Terraform is how backend teams treat infrastructure the same way they treat application code: written down, reviewed, versioned, and applied through a repeatable process rather than a person's memory of which checkboxes they ticked. A Spring Boot engineer who understands Terraform can read a pull request that changes an RDS instance's size, see exactly what will happen before it happens, and know why the state file locked when a teammate tried to apply at the same time — this page builds that understanding from first principles.

1. Why Infrastructure as Code Exists

Before tools like Terraform existed, provisioning cloud infrastructure meant a person logging into the AWS console, clicking through a series of forms, and creating a resource — an RDS instance, a VPC, an ECS cluster — by hand. This works the first time. It fails as an operating model the moment a team has more than one engineer, more than one environment, or needs to do it again. A console click leaves no record of what was clicked, in what order, or with what settings, beyond whatever CloudTrail happens to log at the API level, which is not the same as a readable specification of intent. If the engineer who provisioned ShopSphere's original inventory-service database leaves the company, the only way to know its exact configuration — the instance class, the parameter group, the backup retention window, the subnet it lives in — is to go inspect it after the fact, and even then you can't easily tell which of those settings were deliberate decisions versus accidents of whatever the console defaulted to that day.

This unreproducibility compounds into a second, quieter problem: environments drift apart from each other without anyone deciding they should. Staging gets a manual tweak to fix an urgent test failure. Production gets a different manual tweak six months later to work around a different urgent problem. Nobody updates a shared source of truth, because there isn't one — the infrastructure's true state lives only inside AWS itself, scattered across dozens of resources, and the only way to compare "what does staging look like" to "what does production look like" is manual, error-prone console archaeology. Bugs that "only happen in production" are frequently exactly this: an unrecorded configuration difference that accumulated silently over time.

Infrastructure as Code (IaC) solves this by making infrastructure into a text-based artifact — files that live in a Git repository, get reviewed in pull requests, and are executed through a tool rather than a human clicking buttons. The infrastructure's definition and its actual state can now be compared, diffed, and reasoned about the same way application code is. Terraform is the most widely used general-purpose IaC tool, precisely because it isn't tied to a single cloud — it manages AWS, GCP, Azure, Kubernetes, and even SaaS platforms like Datadog or GitHub through the same core workflow, using per-provider plugins that translate a shared configuration language into that provider's API calls.

2. Declarative Model vs. Imperative Scripts

The single most important conceptual shift Terraform asks of an engineer used to writing code is moving from imperative thinking to declarative thinking. An imperative provisioning script — a Bash script full of aws CLI calls, or a sequence of Ansible tasks — describes a series of steps to execute: create this VPC, then create this subnet inside it, then create this security group, then launch this RDS instance using that security group. The script is a recipe. If you run it twice, you either need it to be carefully written to check "does this already exist?" before every step, or it fails the second time because the VPC already exists, or worse, it silently creates a second VPC. The correctness of the outcome depends entirely on the script author having anticipated every possible starting state.

Terraform's configuration language, HCL (HashiCorp Configuration Language), instead describes the desired end state — not the steps to get there. A resource block says "there should exist an RDS instance with these properties," full stop. It does not say whether to create it, modify it, or leave it alone; Terraform figures that out by comparing the declared configuration against what it currently believes exists (more on how it knows that in the next section) and computing the minimal set of actions needed to reconcile the two. Run the same configuration a hundred times against infrastructure that already matches it, and Terraform does nothing on all hundred runs — this property is called idempotency, and it's the reason declarative tools are dramatically safer to operate at scale than imperative scripts. You never have to reason about "what state is this environment currently in and will my script handle that specific starting point correctly" — you only have to reason about "what do I want to be true," and Terraform handles the reconciliation.

resource "aws_sqs_queue" "order_placed_queue" {
  name                       = "shopsphere-order-placed-${var.environment}"
  visibility_timeout_seconds = 60
  message_retention_seconds  = 86400

  tags = {
    Service     = "order-service"
    Environment = var.environment
  }
}

Notice what this block does not say: it does not say "call CreateQueue," it does not say "check if a queue with this name already exists first," and it does not say what to do if the queue already exists but with a different retention period. It simply asserts a fact about the desired world — an SQS queue with this name and these properties should exist — and leaves the reconciliation logic entirely to Terraform's engine. That separation of "what I want" from "how to get there" is the entire declarative model in one example.

3. The Core Workflow: init, plan, apply, destroy

Terraform's day-to-day usage revolves around four commands, and understanding what each one does — and does not do — is the foundation of using the tool safely.

terraform init

terraform init prepares a working directory for use. It downloads the provider plugins referenced in the configuration (the AWS provider, for instance, which knows how to translate HCL resource blocks into actual AWS API calls), and it configures the backend — where Terraform will store its state file, covered in the next section. This is the command you run once when you first clone a Terraform project, and again whenever you add a new provider or change the backend configuration. It makes no changes to any real infrastructure at all; it only prepares the local tooling.

terraform plan

terraform plan is the command that makes Terraform trustworthy enough to run against production. It computes a diff: given the configuration files as written, and Terraform's current record of what exists (the state file), what would need to change to reconcile the two? The output lists every resource Terraform would create, modify in place, or destroy and recreate, along with the specific attributes that would change — annotated with + for additions, - for removals, and ~ for in-place updates. Critically, plan makes no actual changes. It is a pure dry-run, safe to run at any time, as often as you like, including automatically on every pull request in CI.

This dry-run property is the central safety mechanism of the entire tool. Because plan shows you precisely what will happen before anything happens, a reviewer can read a Terraform pull request's plan output and know, with certainty, whether "resize this RDS instance" is going to be a routine parameter change or whether it will secretly require destroying and recreating the database — some attribute changes, like changing an RDS instance's engine, force replacement rather than an in-place update, and that fact is exactly the kind of thing you want surfaced in a diff before it happens to a production database holding real orders, not discovered after the fact from a support ticket asking where all the order history went.

terraform apply

terraform apply re-runs the same plan computation and then, after an interactive confirmation (or automatically, if run with -auto-approve in a pipeline), actually executes the necessary provider API calls to bring real infrastructure into alignment with the configuration. This is the only one of the four commands that changes anything in the real world. In any serious CI/CD pipeline, apply against production is gated behind a manual approval step specifically because it is irreversible in a way plan is not — you can run plan a thousand times with zero risk, but each apply is a real action against real infrastructure serving real traffic.

terraform destroy

terraform destroy is the inverse operation: it computes and executes a plan to tear down every resource the current configuration manages. It's genuinely useful for ephemeral environments — a short-lived integration-test environment for order-service that's spun up for a CI run and torn down afterward — but it's also the single most dangerous command in the toolset if run against the wrong workspace or directory, since a mistaken destroy against production has no built-in notion of "are you sure you meant all of it."

Plan is a promise, not a guarantee

A plan computed at 2:00pm and applied at 2:05pm is usually accurate, but if another process modifies the same infrastructure in between — someone else's apply, or a manual console change — the actual apply can differ from what the plan showed, or fail outright. Terraform re-validates against current state at apply time, but the window between plan and apply is not a transaction in the database sense; treat a stale plan with suspicion rather than blind trust.

4. The State File: Terraform's Memory

Terraform's entire reconciliation model depends on it knowing what it believes already exists, and that belief is recorded in a state file — by default a JSON file named terraform.tfstate. Every resource Terraform has created is tracked here, along with the full set of attributes Terraform last observed for it: an RDS instance's ARN, its endpoint address, its current instance class, and dozens of other fields the provider returns. When you run terraform plan, Terraform is not re-deriving "what exists" from scratch by querying AWS for everything — it primarily consults this state file and, depending on configuration, refreshes it against real infrastructure, then compares that against your HCL configuration to compute the diff.

This makes the state file simultaneously indispensable and dangerous. It is indispensable because without it, Terraform has no way to know that the aws_db_instance block in your configuration corresponds to the specific RDS instance already running in AWS with a specific identifier — lose the state file, and Terraform's honest answer to "does this resource exist" becomes "I don't know, so I'll try to create it," which for a resource that already exists produces a naming collision error at best and, in some provider/resource combinations, an actual duplicate resource at worst. It is dangerous because the state file often contains sensitive data in plaintext — database passwords set via a resource attribute, for instance, can end up recorded in state even if they never appear in the HCL itself — which is one of several reasons state files should never be committed to a Git repository or handled casually.

Why state must be remote and shared

A brand-new Terraform project defaults to storing state as a local file in the working directory. This is fine for a solo experiment, but it breaks down the moment more than one engineer touches the same infrastructure. If two engineers each have their own local copy of terraform.tfstate for ShopSphere's shared infrastructure, each of them has a different, increasingly stale belief about what exists — engineer A applies a change, their local state file updates, but engineer B's local state file has no idea that happened. The next time engineer B runs plan, Terraform compares the HCL against B's outdated state and produces a plan that's wrong — it might propose destroying a resource A just created, or recreating one that already exists, because as far as B's copy of Terraform's memory is concerned, that resource doesn't exist yet.

The fix is a remote backend: a shared, centrally accessible location where the state file lives, that every engineer's Terraform CLI and every CI pipeline run reads from and writes to. The standard AWS pattern is an S3 bucket for the state file itself, paired with a DynamoDB table for state locking.

terraform {
  backend "s3" {
    bucket         = "shopsphere-terraform-state"
    key            = "order-service/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "shopsphere-terraform-locks"
    encrypt        = true
  }
}

What state locking actually prevents

Storing state in S3 alone solves the "everyone reads and writes the same file" problem, but it introduces a new one: what happens if two engineers run terraform apply at the same moment? Without locking, both processes could read the same state file, compute their own plans against it, and then both write their results back to S3 — the second write simply overwrites the first, silently discarding whatever the first apply just did to Terraform's record of reality, even though the first apply's changes actually happened in AWS. Worse, both applies could be actively modifying the same resource concurrently, since neither process has any way of knowing the other is running.

DynamoDB state locking closes this gap. Before an apply (or plan, in most configurations) begins, Terraform attempts to write a lock record to the designated DynamoDB table. If that write succeeds, Terraform proceeds, holding the lock for the duration of the operation, then releases it when finished. If another apply is already in flight and holds the lock, the second attempt fails immediately with a clear "state is locked" error rather than silently proceeding — it tells the second engineer exactly who holds the lock and when it was acquired, so they know to wait rather than force through a conflicting change. This is the same fundamental problem a database's row-level lock solves — preventing two concurrent writers from corrupting a shared resource by interleaving their updates — applied to Terraform's own bookkeeping instead of application data.

5. Modules: Reusable, Parameterized Infrastructure

Once a Terraform configuration grows past a handful of resources, copy-pasting the same block of HCL for every similar piece of infrastructure becomes exactly the same anti-pattern as copy-pasting the same method body across several Java classes instead of extracting a shared method. Terraform's answer to this is the module: a self-contained directory of .tf files that accepts input variables and exposes output values, callable from other configurations the same way a parameterized function is callable from other code.

ShopSphere's order-service, inventory-service, and payment-service are all deployed as ECS services with the same underlying shape — a task definition, a service, an Application Load Balancer target group, an auto-scaling policy — differing only in specifics like the container image, the desired count, and the CPU/memory allocation. Writing that ECS boilerplate three separate times invites the same class of bug three separate times: someone updates the health-check grace period for order-service after an incident, forgets to make the equivalent change for inventory-service, and now the two services silently behave differently under the same failure mode for no principled reason. A shared shopsphere-ecs-service module written once and parameterized solves this structurally, the same way extracting a common base class or a shared utility method does in application code — the fix, once made in the module, applies everywhere the module is used the next time someone runs apply.

module "order_service" {
  source          = "../../modules/shopsphere-ecs-service"
  service_name    = "order-service"
  container_image = "123456789.dkr.ecr.us-east-1.amazonaws.com/order-service:1.4.2"
  cpu             = 512
  memory          = 1024
  desired_count   = 3
  environment     = var.environment
}

module "inventory_service" {
  source          = "../../modules/shopsphere-ecs-service"
  service_name    = "inventory-service"
  container_image = "123456789.dkr.ecr.us-east-1.amazonaws.com/inventory-service:2.1.0"
  cpu             = 256
  memory          = 512
  desired_count   = 2
  environment     = var.environment
}

Both calls invoke the exact same module code — the same underlying task definition, service, target group, and auto-scaling logic — supplying only the values that legitimately differ between the two services. Any future improvement to that shared module, such as adding a standard set of CloudWatch alarms or tightening a default security group rule, is written once and takes effect for every service that consumes the module the next time its configuration is applied.

6. Variables and Outputs: Parameterizing Environments

Modules solve reuse across services; input variables and output values solve reuse across environments. ShopSphere needs dev, staging, and production versions of essentially the same infrastructure, differing in scale, redundancy, and a handful of environment-specific settings — production's RDS instance needs Multi-AZ replication and a larger instance class, while dev's equivalent database can be a single small instance nobody will notice if it briefly restarts. Writing three entirely separate Terraform configurations for these three environments reintroduces the exact duplication problem modules were meant to solve, just one level up.

The idiomatic pattern is a single module (or root configuration) exposing input variables for everything that legitimately differs by environment, with each environment supplying its own small file of variable values.

variable "environment" {
  description = "Deployment environment name"
  type        = string
}

variable "db_instance_class" {
  description = "RDS instance class for the orders database"
  type        = string
  default     = "db.t3.medium"
}

variable "multi_az" {
  description = "Whether to enable Multi-AZ failover for RDS"
  type        = bool
  default     = false
}

resource "aws_db_instance" "orders_db" {
  identifier        = "shopsphere-orders-${var.environment}"
  instance_class    = var.db_instance_class
  multi_az          = var.multi_az
  engine            = "postgres"
  engine_version    = "15.4"
  allocated_storage = 100
}

output "orders_db_endpoint" {
  description = "Connection endpoint for the orders RDS instance"
  value       = aws_db_instance.orders_db.endpoint
}

Production's terraform.tfvars sets db_instance_class = "db.r6g.xlarge" and multi_az = true; dev's leaves both at their defaults. The resource block itself never changes between environments — only the values fed into it do, which means the actual infrastructure logic (how an RDS instance for ShopSphere's orders should be shaped) is defined exactly once and reviewed exactly once, even though it's applied three times with different inputs. Outputs close the loop by exposing values other configurations or modules need to consume — order-service's application configuration needs the orders database's actual endpoint address, which isn't known until after Terraform creates the instance, and the output block is how that value gets surfaced for consumption elsewhere, whether that's a separate Terraform configuration reading it via a remote state data source, or a CI pipeline injecting it into an application's environment variables.

7. Configuration Drift and Why Manual Changes Are a Process Failure

Configuration drift is what happens when the real state of an infrastructure resource diverges from what Terraform's configuration says it should be, without Terraform having made that change itself. The most common cause is a human making a manual change directly in the AWS console or CLI — an on-call engineer, mid-incident, bumps ShopSphere's payment-service ECS task count from 3 to 8 directly in the console to handle an unexpected traffic spike, because it's faster than writing a pull request, waiting for review, and running apply while customers are actively affected. The traffic spike passes, the incident is resolved, and the manual change is never reverted or reflected back into the Terraform configuration.

The next time anyone runs terraform plan against that configuration, Terraform refreshes its understanding of the resource's actual current state from AWS, compares it against the HCL (which still says desired_count = 3), and surfaces the drift directly in the plan output as a proposed change — Terraform doesn't know an incident happened; it only knows the configuration says 3 and reality says 8, and by its normal reconciliation logic, that's a change it should propose making, which in this case means proposing to scale payment-service back down to 3. If whoever runs that apply doesn't recognize what's happening, drift silently gets "fixed" by undoing the well-intentioned manual change — potentially re-introducing the exact capacity problem the manual change was made to solve, at a moment nobody's watching for it.

This is precisely why manual changes to Terraform-managed infrastructure are treated as a process failure rather than a convenient shortcut, even when they're well-intentioned and made under real time pressure. The whole value proposition of IaC — that the Git history of the configuration is an accurate, reviewable record of what infrastructure looks like and why — breaks down the instant reality and configuration are allowed to silently diverge. The sustainable version of the incident-response scenario above is: make the emergency change manually if genuinely necessary to stop the bleeding, but treat updating the Terraform configuration to match as an immediate follow-up task, not an optional one, specifically so the next plan reflects informed intent rather than surfacing an unexplained diff that someone might reflexively "fix" by reverting the very change that helped.

Drift detection as an ongoing practice

Teams operating Terraform at scale don't wait for someone to manually run plan to discover drift — they run terraform plan on a schedule (a nightly CI job, for instance) purely to detect and alert on unexpected diffs, treating a non-empty plan against unchanged configuration as a signal worth investigating, not just a precursor to an apply. This is the connection to production observability more broadly: drift is an infrastructure-level anomaly, and like any anomaly, it's far cheaper to catch via routine monitoring than to discover mid-incident.

8. A Worked Example: Provisioning ShopSphere Infrastructure

Bringing the previous sections together, here is a small but realistic slice of what provisioning part of ShopSphere's actual infrastructure looks like in Terraform — an ECS service for order-service, reading its container image and scaling parameters from variables, alongside the SQS queue it consumes from and outputs other configurations can depend on.

resource "aws_ecs_service" "order_service" {
  name            = "order-service-${var.environment}"
  cluster         = aws_ecs_cluster.shopsphere.id
  task_definition = aws_ecs_task_definition.order_service.arn
  desired_count   = var.order_service_desired_count
  launch_type     = "FARGATE"

  network_configuration {
    subnets         = var.private_subnet_ids
    security_groups = [aws_security_group.order_service.id]
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.order_service.arn
    container_name   = "order-service"
    container_port   = 8080
  }
}

resource "aws_sqs_queue" "order_placed" {
  name                       = "shopsphere-order-placed-${var.environment}"
  visibility_timeout_seconds = 60
}

output "order_placed_queue_url" {
  value = aws_sqs_queue.order_placed.id
}

Running terraform plan against this configuration for the first time, with nothing yet created, shows two resources to add and nothing to modify or destroy. Running it again immediately after a successful apply shows no changes at all — the definition of idempotency in practice. Change order_service_desired_count from 3 to 5 in a pull request, and the next plan shows exactly one in-place update, to exactly one attribute, on exactly one resource — the kind of small, legible, reviewable diff that is the entire point of managing infrastructure this way instead of through the console.

Concepts Worth Being Able to Explain From First Principles

Why is Terraform's declarative model considered safer than an imperative provisioning script, concretely?
An imperative script encodes a sequence of steps and is only as correct as the assumptions it makes about the starting state — run it against an environment that doesn't match those assumptions (a partially-created VPC, a resource that already exists) and it can fail unpredictably or, worse, silently do the wrong thing. A declarative tool like Terraform instead computes the difference between the desired end state and the currently observed state every time it runs, so it never needs to assume a starting point — it derives the necessary actions fresh from whatever state actually exists. This makes re-running the same configuration idempotent: applying it against infrastructure that already matches produces zero changes, whereas re-running an imperative script often either fails outright or requires the script author to have anticipated every possible prior state explicitly.
What is terraform plan actually computing, and why is it the central safety mechanism of the tool?
Plan performs a three-way comparison: it refreshes its record of what currently exists in real infrastructure, compares that against the state file's prior record, and compares both against the HCL configuration as written, then reports the specific create/update/destroy actions needed to reconcile the configuration with reality. Crucially, it does all of this without executing any of those actions. This makes it a zero-risk operation you can run as often as you like — in local development, in CI on every pull request, before every apply — and it means a human (or a required approval gate) can review the exact, concrete consequences of a change, including surfacing dangerous cases like an attribute change that forces a resource to be destroyed and recreated, before any of it actually happens against production.
Why can't Terraform just ask AWS "what exists" every time instead of keeping a separate state file?
Partly performance — querying every possible resource type across an account on every plan would be prohibitively slow at scale — but more fundamentally, correctness. AWS can tell Terraform that an RDS instance with a given identifier exists and what its current attributes are, but it cannot tell Terraform which specific resource block in your HCL that instance corresponds to, especially when multiple resources could plausibly match, or when you want Terraform to track a resource's history of attribute values over time (to detect drift, for instance). The state file is Terraform's own mapping between "the logical resource named aws_db_instance.orders_db in my configuration" and "the physical thing with this specific ARN in AWS," and that mapping doesn't exist anywhere in AWS itself — Terraform has to maintain it.
Two engineers both run terraform apply against ShopSphere's shared infrastructure at nearly the same time, with a properly configured S3 backend but no DynamoDB locking. What specifically can go wrong?
Without locking, both Terraform processes can read the same starting state file from S3, independently compute their own plans against it, and then independently execute their changes against real AWS resources and write their own updated state back to S3 afterward. If both plans happen to touch the same resource, the two applies can race against AWS's own APIs, with unpredictable results depending on exact timing — one apply's changes might be partially or fully overwritten by the other's. Separately, whichever process's state-file write to S3 completes last simply overwrites the other's, meaning the earlier apply's real, already-executed changes to AWS can become undocumented in Terraform's own state — a state file now silently out of sync with what's real, i.e., self-inflicted drift.
Why does storing Terraform state locally stop working once more than one engineer touches the same infrastructure?
A local state file is only ever seen by the machine it lives on. The moment a second engineer needs to run Terraform against the same real infrastructure, their local Terraform CLI has no way to see changes the first engineer's applies have already made, because that information only ever got written to the first engineer's laptop. Each engineer's local copy of "what I believe exists" silently diverges from the others' the moment either of them applies a change, and every subsequent plan computed from a stale local state file risks proposing to redo work that's already done, or to destroy something the other engineer just created. A remote backend fixes this by making the state file the one shared source of truth every engineer's CLI and every CI run reads from and writes to.
An on-call engineer manually bumps an ECS service's desired count in the AWS console during an incident. What happens the next time someone runs terraform plan, and why is this treated as a process failure rather than a helpful save?
Terraform refreshes its view of the resource's actual state from AWS and compares it against the HCL configuration, which still declares the old desired count. It has no way to know an incident happened or that the manual change was intentional and beneficial — from its perspective, reality has simply diverged from the declared configuration, and its normal reconciliation logic proposes changing the resource back to match the configuration, i.e., undoing the manual fix. It's a process failure, not a convenient shortcut, because the entire value of IaC is that the Git history of the configuration accurately describes what infrastructure looks like and why; a manual change that's never reflected back into that configuration creates an invisible discrepancy that can be silently and unintentionally reverted by the very next routine apply, at a time when nobody is specifically watching for it.
What problem do Terraform modules solve that plain copy-pasted resource blocks don't, using ShopSphere's microservices as an example?
order-service, inventory-service, and payment-service all need essentially the same shape of ECS infrastructure — a task definition, a service, a target group, an auto-scaling policy — differing only in specifics like image, CPU/memory, and desired count. Writing that boilerplate three separate times means any future fix or improvement (adding a standard CloudWatch alarm, tightening a default security group rule, fixing a misconfigured health check) has to be applied in three separate places, and it's easy for one to be missed, producing services that silently behave differently under the same failure mode for no principled reason. A shared module parameterizes the differences and centralizes the shared logic in one place, so a fix made once in the module takes effect everywhere the module is used the next time its consumers are applied — the same motivation as extracting a shared method instead of duplicating a method body across classes.
How do input variables and outputs let the same Terraform module represent dev, staging, and production without three separate configurations?
Input variables parameterize exactly the things that legitimately differ between environments — instance class, Multi-AZ replication, desired count — while the resource logic itself (what an RDS instance or ECS service for this workload should look like structurally) is written once, inside the module, and never duplicated. Each environment supplies its own small file of variable values (a tfvars file, typically) rather than its own copy of the actual resource definitions, so a change to the underlying infrastructure logic is reviewed and applied exactly once even though it's used by all three environments. Outputs then expose values that are only known after resources are created — like an RDS instance's endpoint address — so that other configurations or the application's own deployment pipeline can consume them without needing to duplicate or hardcode values that Terraform itself is the authoritative source for.
Why does terraform destroy deserve to be treated with more caution than the other three core commands?
Init, plan, and (to a lesser extent) apply all have a natural safety valve: init changes nothing real, plan changes nothing real, and apply's changes are visible in the preceding plan output before they happen. Destroy's entire purpose is to remove every resource a configuration manages, and while it also shows a plan before executing, the category of mistake it enables — running it against the wrong workspace, or against a directory that manages more than the engineer intended — is uniquely unforgiving, because deleted infrastructure (a database, most catastrophically) is not always recoverable even with backups, and the blast radius of "destroy everything this configuration manages" is much larger than a typical apply's incremental change.
