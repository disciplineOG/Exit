Database Architecture: SQL/NoSQL, Indexing, Sharding

SQL vs NoSQL B-Trees LSM-Trees Composite Indexes Replication Sharding Locking
Why this matters

Almost every "the database is slow" incident traces back to one of a handful of mechanical facts: an index that doesn't match the query's sort order, a write-heavy table backed by the wrong storage engine, a replica that's minutes behind primary, or two transactions racing on the same row. None of these are exotic — they are direct, predictable consequences of how B-Trees, LSM-Trees, replication logs, and locks actually work. Picture ShopSphere on a normal Tuesday versus the two minutes after a flash sale opens: the same orders table that serves a trickle of point lookups by order_id all day suddenly has ten thousand customers hitting checkout at once, all writing to whichever partition holds the newest rows, while a dashboard job scans orders by status for the fulfillment queue. If you understand the mechanics in this page, you can look at that slow query plan or a stale-read bug report ("my order still shows CREATED, not PAID") and know exactly which structural choice caused it — the wrong index, the wrong shard key, a lagging replica — rather than guessing and adding indexes until something sticks.

1. SQL vs NoSQL Is a Spectrum, Not a Binary Choice

The framing "SQL for structured data, NoSQL for unstructured data" is misleading. Every database — relational or not — makes a set of engineering trade-offs along several independent axes. Understanding those axes lets you place any database (Postgres, MongoDB, Cassandra, DynamoDB, Neo4j) on a map instead of memorizing a category.

The axes

  • Schema rigidity vs flexibility. A relational table enforces a schema at write time: every row has the same columns with the same types, checked by the engine before the write commits. This catches bugs early (you cannot accidentally write a string into ShopSphere's orders.total_amount numeric column) but makes evolving the schema across a large table an operational event (though modern engines like Postgres and MySQL 8 support fast metadata-only ADD COLUMN in most cases). Document stores defer that validation to the application: a ShopSphere products collection in MongoDB can have documents with wildly different shapes — a clothing product with a sizeChart field, an electronics product with a warrantyMonths field — which is powerful for a rapidly evolving multi-category catalog but pushes correctness checking into the seller-service code instead of the database.
  • Join support. Relational engines implement joins natively and optimize them (hash joins, merge joins, nested loop joins with index lookups) because normalization assumes you'll reassemble related data at query time — ShopSphere's orders JOIN order_items JOIN products to render an order confirmation page is a textbook example. Most NoSQL stores either don't support joins at all or support them poorly, because their scaling model assumes data for one logical entity lives on one node — a join across shards would mean fanning a query out across the network, which the engine avoids by design, not by oversight.
  • Horizontal scalability. A single-leader relational database scales reads via replicas but scales writes only by getting a bigger machine (vertical scaling) unless you add manual sharding on top. Many NoSQL systems (Cassandra, DynamoDB, MongoDB with sharding) build horizontal partitioning into the core engine from day one, because they were designed after teams had already been burned trying to bolt sharding onto MySQL.
  • Consistency guarantees. Relational databases default to strong consistency: a committed write is immediately visible to the next read on that node, and transactions give you atomicity across multiple rows — ShopSphere's checkout, which must decrement inventory.available_qty and insert an order row atomically, leans on exactly this. Many distributed NoSQL stores trade this for availability and partition tolerance (the CAP theorem trade-off), offering tunable or eventual consistency instead — see distributed-systems-core for why this trade-off is forced, not optional, once you replicate across nodes.
A more useful question than "SQL or NoSQL?"

Ask instead: does my access pattern need multi-row transactions and ad-hoc joins (favor relational — ShopSphere's orders/payments/inventory core, where checkout must touch several tables atomically), is my data naturally a self-contained document that's always read/written as a whole (favor document store — a Product with its nested attributes and images), do I need sub-millisecond lookups by a single key at massive scale (favor key-value — a Redis cart:{customerId} lookup during browsing), do I need to write huge volumes of time-ordered or wide-row data (favor column-family — order-status-change events or clickstream logs feeding search-service), or is the domain itself a graph of relationships I need to traverse (favor graph — "customers who bought this also bought" traversal). The category follows from the access pattern, not the reverse.

2. B-Tree Indexes: The Default for Disk-Backed Storage

An index exists to avoid scanning every row to answer a query. Consider ShopSphere's orders table with 500 million rows: without an index, SELECT * FROM orders WHERE id = 8841923 would mean reading every row until the engine happens to find the one it wants — a full table scan. The interesting engineering question is: what data structure should back the index that avoids this, given that the data lives on disk (or, more precisely, is read in fixed-size pages, typically 4KB–16KB, and each page read is orders of magnitude slower than an in-memory pointer dereference)?

Why not a binary search tree?

A balanced binary search tree gives you O(log₂ n) comparisons, which sounds fine until you account for what each "comparison" costs. If each node lives on its own disk page, then a tree over one billion rows needs about log₂(10⁹) ≈ 30 levels, meaning up to 30 random disk seeks per lookup. On a spinning disk (~10ms seek) that's 300ms for one lookup — unusable. Even on SSDs, random reads are far slower than sequential ones and you still pay 30 page faults per query.

The B-Tree fix: maximize fanout, minimize height

A B-Tree (specifically, databases use B+Trees, where all values live in leaf nodes and internal nodes hold only routing keys) restructures the problem: instead of 2 children per node, each node holds hundreds to thousands of keys and pointers, sized so that one node fits exactly in one disk page. This gives a very high branching factor (fanout), often 100–1000, which means the tree height for a billion rows drops from ~30 to 3–4. Since each level is one disk page read, a lookup that used to cost 30 seeks now costs 3–4 — and because the top 2–3 levels are almost always cached in the buffer pool (see caching-strategies), a real lookup often costs a single physical disk read.

Root page (fanout ~500): [ 10 | 800 | 4200 | ... ]
        |          |            |
   points to   points to    points to
   child page  child page   child page
   for keys    for keys     for keys
   < 800       800-4200     > 4200

Leaf pages (sorted, linked list):
[1..799] <-> [800..4199] <-> [4200..9999] <-> ...
   each leaf holds the actual row pointer (or the row itself, clustered index)

Why this helps both equality and range queries

Because keys within a node are sorted, and leaf nodes are additionally linked together as a doubly-linked list, a B+Tree serves two access patterns well with the same structure:

  • Equality lookup (WHERE id = 8841923 on ShopSphere's orders table): walk down from root to leaf using binary search within each page, ~3-4 page reads total.
  • Range query (WHERE created_at BETWEEN '2026-08-01' AND '2026-08-25' — a seller pulling last month's orders): walk down to the starting leaf once, then walk sideways along the linked leaf pages until the range is exhausted — no need to revisit the root for each row.

This dual capability is precisely why B-Trees remain the standard index structure in Postgres, MySQL/InnoDB, Oracle, and SQL Server: a hash index could theoretically beat a B-Tree on pure equality lookups (O(1) vs O(log n)), but it provides no ordering, so it cannot serve range scans, ORDER BY, or prefix matches at all.

Every write touches the tree, not just the row

An index is not free storage on the side — it is a second (or third, or tenth) data structure that must stay consistent with the table. Every INSERT, UPDATE of an indexed column, or DELETE has to also locate and modify the corresponding B-Tree leaf, potentially triggering a page split if the leaf is full. This is why tables with many indexes have measurably slower write throughput than the same table with fewer indexes — you're paying a write-amplification cost proportional to the number of indexed columns, not just the number of rows.

Index types are not interchangeable: a taxonomy

"Add an index" is not one operation — different index structures are matched to different query shapes, and picking the wrong one either does nothing for performance or silently fails to apply at all. ShopSphere's schema uses several of these side by side:

3. LSM-Trees: Optimizing for Write Throughput

B-Trees are excellent for read-heavy, range-query-heavy workloads, but they have an inherent weakness for writes: an in-place update to a B-Tree leaf means a random write to a random disk location, and if that leaf is full, a page split that rewrites and re-links multiple pages. For workloads dominated by very high write volume — think ShopSphere's inventory-change event stream during a flash sale, where every one of ten thousand concurrent checkouts fires an InventoryReserved write, or a raw clickstream/page-view log feeding analytics — this random-write cost becomes the bottleneck. The Log-Structured Merge Tree (LSM-Tree) is the structural answer, used by Cassandra, RocksDB, LevelDB, HBase, and as an optional storage engine in some MySQL forks (MyRocks).

The structure: memtable + immutable SSTables

  1. Writes go to an in-memory sorted structure (the memtable) — typically a skip list or balanced tree — and are simultaneously appended to a write-ahead log on disk for durability. Because the write-ahead log write is a sequential append (not a random write to a specific offset), it's extremely fast even on spinning disks, and near-optimal on SSDs.
  2. When the memtable reaches a size threshold, it is flushed to disk as an SSTable (Sorted String Table) — an immutable, sorted file. "Immutable" is the key word: once written, an SSTable is never modified in place, only read, merged, or deleted wholesale.
  3. Reads must check the memtable first, then each SSTable, typically from newest to oldest, until the key is found (or confirmed absent). To avoid checking every SSTable on disk for every read, engines use Bloom filters — a probabilistic structure that can say "definitely not in this SSTable" cheaply, skipping most files, at the cost of occasional false positives (never false negatives).
Write path:
  client write -> append to WAL (sequential disk write, durable)
              -> insert into memtable (in-memory sorted structure)
              -> [memtable full] -> flush as new immutable SSTable on disk

Read path:
  check memtable -> check Bloom filter of SSTable_N (newest)
                 -> if maybe-present, check SSTable_N
                 -> else check SSTable_N-1 ... until found or all exhausted

Why writes are fast: no in-place update, ever

The entire performance advantage of LSM-Trees comes from converting random writes into sequential ones. A B-Tree write means "find the right page, possibly on disk, and mutate it in place." An LSM-Tree write means "append to a log and insert into an in-memory structure" — no disk seek is on the critical path of the write at all. This is why LSM-backed engines can sustain dramatically higher write throughput than B-Tree engines under heavy insert load.

Compaction: the bill that comes due later

Because SSTables are immutable and accumulate over time, the same key can exist in multiple SSTables (an insert, then a later update, then a delete — represented as a "tombstone" marker rather than an actual removal). Left unchecked, this means: reads get progressively slower (more files to check), and disk usage grows even though the logical dataset hasn't. Compaction is a background process that merges multiple SSTables into fewer, larger ones, discarding overwritten values and resolving tombstones. It's the mechanism that pays back the cost deferred at write time — the LSM-Tree strategy is fundamentally "defer and batch the expensive part."

Compaction is not optional maintenance — it's load-bearing

If compaction falls behind write volume (common when a write spike coincides with compaction being CPU/IO-throttled), read latency degrades because queries must check more and more SSTables, and disk usage climbs. This is the most common operational failure mode of LSM-backed systems like Cassandra: "compaction is falling behind" is a first-class alert, not a curiosity, because it directly predicts an oncoming read-latency and disk-space crisis.

The three amplification metrics: how to actually compare B-Tree vs LSM-Tree

MetricDefinitionB-TreeLSM-Tree
Write amplification Bytes actually written to disk per logical byte written by the application Moderate — in-place updates plus occasional page splits Higher — the same data is rewritten repeatedly across compaction levels
Read amplification Number of disk reads needed to answer one logical read Low and predictable — bounded by tree height (~3-4) Higher and more variable — may need to check memtable plus several SSTables unless compaction keeps file count low
Space amplification Disk space used relative to the logical size of the data Low — one copy per row, plus index overhead Higher until compaction runs — obsolete versions and tombstones accumulate
The one-line summary to internalize

B-Trees pay a small, consistent cost on every write to keep reads uniformly fast. LSM-Trees pay almost nothing on the write itself and defer the cost to a background compaction process, trading some read latency and disk space for dramatically higher write throughput. Choose B-Tree-backed engines (Postgres, MySQL/InnoDB) for read-heavy or range-query-heavy workloads; choose LSM-backed engines (Cassandra, RocksDB) for write-heavy, append-mostly workloads like event ingestion or time-series data.

4. Composite Indexes, the Leftmost-Prefix Rule, and Covering Indexes

Composite indexes and leftmost-prefix

A composite (multi-column) index, e.g. CREATE INDEX idx ON orders (customer_id, status, created_at), is physically one B-Tree where the sort key is the concatenation of the columns in the order they were declared — first sorted by customer_id, then within each customer_id group sorted by status, then within each of those groups sorted by created_at. This has a direct and non-obvious consequence: the index can only be used efficiently for queries that filter on a left-to-right prefix of the declared columns.

  • WHERE customer_id = ? — uses the index (prefix of length 1).
  • WHERE customer_id = ? AND status = ? — uses the index fully (prefix of length 2).
  • WHERE customer_id = ? AND created_at > ? — uses the index only for the customer_id part; it cannot skip to arbitrary created_at values without also filtering by status, because created_at is not sorted independently of status within the tree.
  • WHERE status = ? alone — cannot use this index at all, because without knowing customer_id first, the matching rows are scattered arbitrarily throughout the tree.
The general rule for composite indexes

Order columns by: (1) columns used in equality filters first, (2) then at most one column used for a range filter or sort, since a range filter breaks the sorted contiguity for any column after it. If you commonly query by both (customer_id, status) and (customer_id, created_at) independently, you likely need two separate indexes, not one composite index reused cleverly — trying to force one index to serve both access patterns usually means one of the two queries falls back to a much less selective scan.

Covering indexes

A covering index is one that contains every column a query needs — both the filter columns and the selected columns — so the engine can answer the query directly from the index's leaf pages without a second lookup back to the full row (called a "bookmark lookup" or "table access by rowid"). For example, if you frequently run SELECT status FROM orders WHERE customer_id = ?, an index on (customer_id, status) covers the query entirely: both the filter and the selected column live in the index leaf, so the engine never touches the underlying table's heap/clustered structure. This can turn a query that costs one index read plus one row read per matching row into a query that costs only the index read, which matters enormously when a query matches thousands of rows.

When an index hurts

Indexes are not free wins; each one is a trade of write cost and storage for read speed, and that trade isn't always worth it.

  • Write amplification per indexed column. Each additional index on a table means each INSERT/UPDATE/DELETE must also update that index's B-Tree, so a table with eight indexes pays roughly eight times the index-maintenance cost of a table with one index, on every write.
  • Index bloat. Frequent updates and deletes leave behind dead entries in B-Tree leaves (particularly visible in Postgres, where an UPDATE is implemented as a delete-plus-insert due to MVCC — Multi-Version Concurrency Control, where readers see a consistent snapshot of a row as it existed at their transaction's start by keeping older row versions around instead of locking the row, so writers never block readers — leaving old row versions that must be vacuumed). An un-vacuumed, bloated index can become larger than the table itself and paradoxically slower than a full table scan.
  • Low-selectivity columns rarely earn their cost. An index on a boolean column or a column with three possible values doesn't narrow the search space enough to be worth the write and storage overhead — the planner will often ignore it and scan the table anyway.

5. Replication: Leader-Follower, Sync vs Async, and Replication Lag

Replication exists to solve two separate problems that are easy to conflate: durability/availability (if one node dies, another has the data) and read scalability (spread read load across multiple copies). The dominant pattern in relational systems is leader-follower (primary-replica): all writes go to a single leader, which then streams a log of changes (the write-ahead log, or a logical replication stream) to one or more followers, which replay it to stay in sync. ShopSphere's order-service is a canonical case for the second problem: every checkout writes to the leader, but "order history" pages, seller dashboards, and admin reporting queries are read-heavy and tolerant of a little staleness, so they get routed to dedicated order-history read replicas instead of competing with checkout writes for the same node's resources.

Synchronous vs asynchronous replication

SynchronousAsynchronous
How it works Leader waits for at least one follower to confirm it received (and often applied) the write before acknowledging the client Leader acknowledges the client immediately after committing locally, and ships the change to followers in the background
Durability guarantee A confirmed write cannot be lost even if the leader dies immediately after, since a follower already has it A leader crash between local commit and replication can lose the last few writes
Latency cost Every write pays the network round-trip to the follower(s), which is why fully synchronous replication to a geographically distant follower can add tens to hundreds of milliseconds per write Writes are as fast as the local commit; replication is fully off the write's critical path
Common deployment Semi-synchronous — one nearby follower is synchronous for durability, the rest are asynchronous for reach Most read replicas in typical deployments — e.g., ShopSphere's order-history replicas, which exist purely to absorb read traffic and can tolerate a second or two of staleness

Replication lag and read-after-write consistency

Replication lag is simply the delay between a write committing on the leader and that write becoming visible on a given follower. It is not a bug — it's the direct, unavoidable cost of asynchronous replication, and it's why "read your own writes" is a named consistency problem rather than an assumed default: a ShopSphere customer who just paid for an order and is then immediately routed to a lagging order-history replica will see status CREATED instead of PAID, because the replica genuinely hasn't received the update yet.

Concrete failure mode: the phantom revert

A customer completes checkout, payment-service publishes PaymentCaptured, order-service's leader commits the status update to PAID — but the order confirmation page's next read is load-balanced to an order-history replica still 200ms behind. The customer sees CREATED, reasonably assumes the payment failed, and hits "place order" again, sometimes creating a duplicate order (this is exactly the class of bug payment-systems-idempotency covers from the payment side). The fix is architectural, not a bigger box: route the read-after-write case (the immediate post-checkout confirmation read) to the leader, or a replica the application can verify has caught up (e.g., via a monotonic sequence/LSN check), and let only the tolerant reads (order-history list pages, seller dashboards) hit the lagging replicas.

6. Sharding: Horizontal Partitioning and Its Costs

Replication copies the same data onto multiple nodes to scale reads and provide redundancy; it does nothing for write scalability because every write still has to go through the single leader. Sharding (horizontal partitioning) solves a different problem: splitting the dataset itself across multiple nodes so that no single node holds all of it, letting both storage and write throughput scale by adding nodes. This is the eventual answer to ShopSphere's orders table outgrowing a single machine as the marketplace grows past a few hundred million rows.

Choosing a sharding key

The sharding key determines which shard a given row lives on, and this single decision dominates the entire system's behavior. Suppose ShopSphere shards orders by customer_id: every row for a given customer lands on the same shard, which is exactly what you want for the most common query ("show me this customer's order history") — it becomes a single-shard lookup instead of a scatter-gather across every node. A poorly chosen key creates a hot shard: if ShopSphere instead sharded by seller_id and one seller (say, a large brand running a flash sale) generates 100x the order volume of a typical seller, that seller's shard absorbs a disproportionate share of write load while other shards sit idle — you've added machines but not actually distributed the work.

Sharding strategies

StrategyHow it worksTrade-off
Range-based Each shard owns a contiguous range of key values (e.g., customer_id 1–1M on shard 1, 1M–2M on shard 2) Efficient range queries within a shard, but new data (e.g., always-increasing order IDs, or newly-registered customer IDs) piles onto the newest shard, creating a hot shard for write-heavy, append-style workloads like order creation
Hash-based A hash function maps each key to a shard — e.g., shard = hash(customer_id) % N — spreading customers uniformly across shards regardless of signup order Excellent write distribution during flash-sale spikes (no single shard absorbs all the newest checkouts), but a query like "all orders placed last week across all customers" must fan out to every shard, since consecutive customer IDs are deliberately scattered
Directory-based A separate lookup service/table maps each key (or key range) to a specific shard explicitly — e.g. a customer_id -> shard_id directory order-service consults before routing a query Maximum flexibility — you can rebalance by moving individual customers' data between shards without touching a hash formula — but the directory itself becomes a critical, latency-sensitive dependency and potential single point of failure

Resharding pain and consistent hashing

With naive hash-based sharding (shard = hash(customer_id) % N), adding or removing a single node changes N, which changes the modulus result for nearly every key — in practice, close to 100% of customers' orders would need to move to a different shard just to add one machine to handle ShopSphere's growth, which is operationally unacceptable at scale. Consistent hashing fixes this by mapping both shards and keys onto a fixed hash ring (e.g., 0 to 2³²−1); each key belongs to the first shard found walking clockwise from its hash position. Adding or removing one shard now only affects the keys between that shard and its immediate neighbor on the ring — roughly 1/N of all customers' data moves, not nearly all of it. Virtual nodes (each physical shard is assigned many points on the ring) further smooth the distribution so that one shard doesn't end up owning a disproportionate arc just by chance.

Cross-shard queries and transactions: the fundamental cost

Sharding's core trade-off is this: anything that needs to touch data across more than one shard becomes dramatically harder. A query filtered on customer_id (the sharding key) becomes a single targeted lookup on one shard; a query that doesn't filter on it — an admin dashboard aggregate like "total revenue across all sellers this month" — has to scatter-gather across every shard and merge results in the application or a coordinating layer, paying the latency of the slowest shard and losing the ability to push sorting/filtering fully down to one engine. Transactions are worse: a relational transaction's ACID guarantees (Atomicity, Consistency, Isolation, Durability — a transaction's changes either all happen or none do, it never leaves data in a state that violates the database's constraints, concurrent transactions can't see each other's half-finished work, and once committed the result survives a crash) are native within one node's engine, but a transaction that must atomically update rows on two different shards — say, transferring loyalty points between two customers who happen to land on different shards — requires a distributed transaction protocol (e.g., two-phase commit) or a compensating-transaction/saga pattern, both of which trade simplicity and latency for cross-shard atomicity. This is precisely why schema design for a sharded system usually starts from "what needs to be transactional together" and picks a sharding key that keeps those things co-located — sharding orders by customer_id works well specifically because a single order's own rows (its order_items, its own status transitions) never need a cross-shard transaction, since they all belong to one customer and therefore one shard — rather than picking a key first and discovering the transactional boundaries don't fit. See distributed-systems-core for the deeper mechanics of distributed transactions and consensus.

7. Optimistic vs Pessimistic Locking

Both strategies solve the same problem — preventing two concurrent transactions from corrupting each other's updates to the same row (a lost update) — but they make opposite bets about how often conflicts actually happen.

Pessimistic locking

Pessimistic locking assumes conflicts are likely, so it prevents them upfront by acquiring an exclusive lock before reading data it intends to modify, typically via SELECT ... FOR UPDATE. Any other transaction that tries to read (for update) or write that same row blocks until the lock holder commits or rolls back.

Concrete scenario: last item in stock

Two customers try to buy the last unit of a product at nearly the same instant during a flash sale. With pessimistic locking, the first transaction runs SELECT * FROM inventory WHERE product_id = ? AND warehouse_id = ? FOR UPDATE, which locks that row; the second transaction's identical query blocks and waits. Once the first transaction commits (decrementing available_qty to 0 and inserting the order) and releases the lock, the second transaction proceeds, re-reads the now-updated row, and correctly sees available_qty = 0 — no overselling is possible because the second transaction was never allowed to read stale inventory state while a conflicting write was in flight.

The cost is contention: every transaction that wants the locked row must wait, and if lock acquisition order isn't carefully controlled across multiple tables, you risk deadlocks (transaction A holds lock 1 and waits for lock 2, while transaction B holds lock 2 and waits for lock 1), which the database eventually detects and resolves by forcibly aborting one of the transactions.

Optimistic locking

Optimistic locking assumes conflicts are rare, so it lets transactions proceed without locking and instead checks, at commit time, whether the data changed since it was read. The standard mechanism is a version column (or a timestamp) on the row: read the row along with its current version, and when writing, issue UPDATE t SET data = ?, version = version + 1 WHERE id = ? AND version = ? using the version value you originally read. If no other transaction modified the row in between, the WHERE clause matches and the update succeeds, incrementing the version. If another transaction won the race and already updated the row, the version no longer matches, zero rows are affected, and the application detects this and retries (typically by re-reading and reapplying the change, or surfacing a conflict to the user).

Concrete scenario: a seller editing their product listing

A seller updates a product's price in one browser tab while an admin, moderating flagged listings, edits the same product's category in another tab. With optimistic locking, both reads succeed immediately with no blocking. Whoever saves first succeeds and bumps the version. When the second save arrives, its UPDATE products SET ... WHERE id = ? AND version = 3 matches zero rows because the version is now 4, so the application detects the conflict and either re-fetches the latest row for a merge, or in low-contention cases simply retries with the new data. Because conflicts here are genuinely rare (a seller and an admin touching the exact same product within seconds is uncommon), paying an occasional retry is far cheaper than pessimistically locking the row on every single read — contrast this with the inventory row above, which is deliberately handled with pessimistic locking instead, precisely because contention on that row during a flash sale is not rare at all.

Optimistic (version/CAS)Pessimistic (SELECT ... FOR UPDATE)
Best whenConflicts are rare; contention is low; retries are cheapConflicts are frequent or the cost of a failed/retried operation is high (e.g., financial postings)
Cost modelNo blocking, but wasted work and a retry loop on conflictNo wasted work, but transactions queue up waiting for locks

This same choice reappears at the application layer whenever an ORM manages entity state — Hibernate's @Version annotation implements exactly this optimistic pattern natively, throwing OptimisticLockException on a version mismatch, which is worth understanding alongside how Hibernate tracks entity state more broadly in jpa-hibernate.

8. Query Execution Plans and Optimizer Mechanics

Every SQL statement you write is a description of what you want, not how to get it — the query optimizer's job is to translate that declarative request into a concrete, ordered sequence of physical operations (which index to use, which join algorithm, in which order to join the tables) called a query plan. Understanding how the optimizer arrives at a plan is what separates "I added an index and it didn't help" from being able to read EXPLAIN ANALYZE output and know exactly why a query is slow. This is the same B-Tree and LSM-Tree machinery from earlier sections, but now viewed from the query planner's perspective: given several possible ways to execute a query, all of which are correct, which one is cheapest?

Statistics and histograms: how the planner knows anything about the data

The optimizer cannot afford to actually run a query multiple ways and time each one — it has to estimate the cost of each candidate plan before executing anything, and that estimate is only as good as its knowledge of the data's shape. Every relational engine periodically samples each table (Postgres via ANALYZE, either run manually or by the autovacuum daemon; MySQL/InnoDB similarly recomputes index statistics) and stores, per column: the total row count, the number of distinct values (cardinality), the fraction of rows that are NULL, and a histogram — a bucketed approximation of the column's value distribution, typically built by sorting a sample of values and recording the boundary value at regular percentile intervals. For ShopSphere's orders.status column, a histogram might record that 2% of rows are CREATED, 5% are PAID, 90% are SHIPPED, and 3% are CANCELLED — this is exactly the information the planner needs to know that WHERE status = 'CANCELLED' is a highly selective filter (touches ~3% of rows, an index scan is cheap) while WHERE status = 'SHIPPED' is not (touches ~90% of rows, where a full sequential scan is usually cheaper than paying for millions of individual index-then-heap lookups).

Selectivity and row-count estimation

Selectivity is the fraction of rows a predicate is expected to match, and the entire plan hinges on it: the optimizer combines per-column statistics into an estimated row count for every intermediate step of the query, then chooses join algorithms and join order to minimize the total estimated cost across those steps. For a single equality filter like WHERE customer_id = ?, the planner divides the table's row count by the column's distinct-value count (assuming roughly uniform distribution, or consulting the histogram directly if the value falls in a skewed bucket). For combined predicates like WHERE customer_id = ? AND status = 'PAID', most planners multiply the individual selectivities together under an assumption of independence between columns — which is a real source of misestimation when columns are correlated (e.g., products.category = 'Electronics' AND products.brand = 'Apple' are far more correlated than independent, so multiplying their selectivities badly underestimates how many rows actually match). This estimated row count then determines everything downstream: how much memory a hash join's build side needs, whether a sort will fit in memory or spill to disk, and which join algorithm is cheapest.

Join algorithms: nested loop, hash join, and merge join

Given two tables to join — say ShopSphere's orders and order_items to render an order confirmation page — there are three fundamentally different physical strategies to actually produce the joined rows, and the optimizer picks based on estimated row counts, available indexes, and whether the join columns are already sorted.

  • Nested loop join. For each row in the outer (driving) table, scan or index-probe the inner table for matches. This is O(outer_rows × cost_per_inner_lookup) — cheap when the outer side is small and the inner side has an index on the join column (each inner lookup becomes a fast B-Tree probe instead of a scan), which is exactly the shape of SELECT * FROM orders o JOIN order_items oi ON oi.order_id = o.id WHERE o.id = 8841923: one outer row, one indexed inner lookup, done. It degrades badly when the outer side is large and there's no usable index on the inner join column, because then every outer row triggers a full scan of the inner table.
  • Hash join. Build an in-memory hash table on the smaller ("build") side keyed by the join column, then scan the larger ("probe") side once, hashing each row's join key to find matches in O(1) per probe. This is the workhorse for joining two large tables with no useful index and no pre-existing sort order — e.g., a reporting query joining a month's worth of orders against payments with no filter narrowing either side first. Its cost is dominated by whether the build-side hash table fits in memory; if it doesn't, the engine spills partitions to disk and the join gets substantially slower.
  • Merge join. If both inputs are already sorted on the join key (because of an ORDER BY, an index that provides the sort for free, or a preceding sort step), the engine can walk both sorted streams with two pointers, advancing whichever side has the smaller current key, producing matches in a single linear pass with no hash table and no repeated lookups. This is the cheapest possible join when the sort is free (e.g., both sides are read via a B-Tree index on the join column, so they emerge pre-sorted), but if the engine has to explicitly sort one or both sides first just to enable a merge join, that sort cost can make it more expensive than a hash join would have been.

The optimizer chooses among these the same way it chooses indexes: by comparing estimated costs given the row-count estimates from the statistics step. A small outer table with a well-indexed inner table almost always wins with nested loop; two large, unsorted, unindexed tables almost always favor hash join; and merge join wins specifically when sortedness is already available "for free" from an index or a required ORDER BY.

Why stale statistics produce catastrophically bad plans

The optimizer's cost model is only a prediction, built entirely from the statistics captured at the last ANALYZE. If ShopSphere's orders table triples in size after a statistics snapshot was taken — say, after a marketing push onboards a wave of new sellers — the planner still believes the table has its old, smaller row count, and may choose a nested loop join expecting to touch a few thousand rows when it's actually touching millions, turning what should be a hash join into millions of individual indexed lookups. Even more subtly, if a column's value distribution shifts (a new status value like BACKORDERED becomes 40% of rows overnight, but the histogram still reflects the old distribution where it didn't exist), the planner underestimates selectivity and picks an index scan where a sequential scan would actually be cheaper. This is precisely why "run ANALYZE" or "the autovacuum/auto-stats job fell behind" is one of the first things to check when a previously-fast query suddenly gets a bad plan with no code change at all — the query didn't change, the data's shape did, and the optimizer's knowledge of that shape didn't keep up.

Reading a multi-table EXPLAIN ANALYZE tree

An execution plan is a tree of physical operators, and the way to read it is bottom-up: the leaves are the actual data-access operations (index scans, sequential scans), and each parent node consumes its children's output. Consider a ShopSphere reporting query joining orders, order_items, and products, then aggregating total revenue per category:

EXPLAIN ANALYZE
SELECT p.category, SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.created_at >= '2026-08-01'
GROUP BY p.category;

HashAggregate  (cost=98234.10..98234.55 rows=45 width=40) (actual time=612.331..612.340 rows=42 loops=1)
  Group Key: p.category
  ->  Hash Join  (cost=45102.00..92110.30 rows=816760 width=24) (actual time=201.442..540.115 rows=798213 loops=1)
        Hash Cond: (oi.product_id = p.id)
        ->  Hash Join  (cost=41200.00..85310.20 rows=816760 width=20) (actual time=180.005..470.882 rows=798213 loops=1)
              Hash Cond: (oi.order_id = o.id)
              ->  Seq Scan on order_items oi  (cost=0.00..38210.00 rows=2400000 width=16) (actual time=0.020..210.401 rows=2400000 loops=1)
              ->  Hash  (cost=39800.00..39800.00 rows=112000 width=8) (actual time=179.550..179.550 rows=109874 loops=1)
                    ->  Index Scan using idx_orders_created_at on orders o  (cost=0.43..39800.00 rows=112000 width=8) (actual time=0.031..142.207 rows=109874 loops=1)
                          Index Cond: (created_at >= '2026-08-01')
        ->  Hash  (cost=2400.00..2400.00 rows=60000 width=12) (actual time=21.200..21.200 rows=60000 loops=1)
              ->  Seq Scan on products p  (cost=0.00..2400.00 rows=60000 width=12) (actual time=0.010..12.884 rows=60000 loops=1)

Reading this bottom-up: the innermost Index Scan on orders uses idx_orders_created_at to find the ~110K orders since August 1st (estimated 112000, actual 109874 — a close, healthy estimate) rather than scanning the whole table. That result becomes the build side of a Hash Join against a full Seq Scan of order_items (2.4M rows, no filter, so a sequential scan is correctly chosen over an index — there's nothing selective to index-probe with). The result of that join (798K matching line items) then becomes the probe side of a second Hash Join against products, matched on product_id. Finally, HashAggregate groups the joined rows by category and sums revenue. The two numbers to compare at every node are estimated rows (the planner's prediction, used to choose this plan) versus actual rows (what really came out at execution time) — when these diverge by an order of magnitude or more at some node, that node's statistics were wrong, and everything built on top of that node (every join above it in the tree) inherited a bad estimate and potentially chose the wrong algorithm as a result. A plan where estimated and actual row counts track closely at every level, as in this example, is the signature of healthy, up-to-date statistics.

9. NoSQL Data Modeling Patterns: Beyond the Category Overview

Section 1 covered why you'd reach for a document store, key-value store, or column-family store instead of a relational database. But choosing the category is only the first decision — actually modeling data well inside a document store or a partitioned wide-column store requires a different mental model than normalization, because these systems are designed access-pattern-first rather than schema-first: you model around the queries you know you'll run, not around eliminating redundancy.

Embedding vs referencing in document stores

A document store lets you nest related data directly inside a parent document instead of normalizing it into a separate collection and joining at query time (which most document stores don't support well or at all — see Section 1). The choice between embedding (nesting the related data inline) and referencing (storing just an ID and looking the related document up separately) is the document-modeling equivalent of the normalization decision in a relational schema, and it's driven by how the data is read and how large it can grow.

ShopSphere's Review document is a good embedding candidate: a review's replies are always read together with the review itself (there's no access pattern that needs "give me this reply without its parent review"), replies rarely number more than a few dozen per review, and the whole thing is naturally read and written as one unit — so nesting replies: [...] directly inside the review document avoids a second round-trip for something you always need anyway. A ShopSphere Customer document's order history is the opposite case: a customer can accumulate thousands of orders over years, each order itself contains nested line items, and order history is frequently queried independently of the customer profile (order-service, not customer-service, owns lookups like "all orders in a date range"). Embedding orders inside the customer document here would mean every read of a customer's profile — even a simple "get their name and email for a support ticket" — pays the cost of loading a document that keeps growing without bound.

The document size limit is a hard constraint, not a style preference

MongoDB enforces a 16MB hard limit per document; a document that would exceed it fails to write entirely, not just slowly. An embedding decision that looked fine at launch — "each product has a few reviews, embed them" — becomes a production incident once a popular ShopSphere product accumulates tens of thousands of reviews and a write to add one more review starts failing outright because the document has hit the ceiling. This is why the rule of thumb is: embed one-to-few relationships that are bounded and always read together, and reference one-to-many-or-unbounded relationships, even if that costs you an extra read — a growing array with no natural cap (reviews, order history, activity logs) is a strong signal that the data belongs in its own collection referenced by ID, not nested inline.

Partition keys, clustering keys, and access-pattern-first modeling

In a partitioned wide-column store like Cassandra or DynamoDB, the choice of key isn't one decision but two, and they serve entirely different purposes. The partition key determines which physical node/partition a row lives on — it's the unit of horizontal distribution, functioning like the sharding key discussed in Section 6. The clustering key (Cassandra's term; DynamoDB calls it the sort key) determines the sort order of rows within a given partition, enabling efficient range scans over that ordering without touching any other partition. For ShopSphere's inventory-change event log from Section 3, partitioning by productId and clustering by timestamp means "all changes for product X" live together and come back pre-sorted by time with a single-partition range query — exactly the access pattern the fulfillment and inventory-audit services actually run.

This leads to the defining discipline of modeling for these stores, usually called access-pattern-first design: rather than modeling entities and their relationships first and then figuring out how to query them (the relational instinct), you enumerate every query the application actually needs to run before choosing keys, because a partitioned store generally cannot serve a query efficiently unless it was designed in from the start — there is no query planner that will improvise a decent join or reshuffle data across partitions on your behalf at query time.

Single-table design

DynamoDB's single-table design pattern takes access-pattern-first modeling to its logical extreme: instead of one table per entity type (as you'd do relationally), you store multiple different entity types — a ShopSphere Order, its OrderItems, and even the Customer it belongs to — in a single table, using generic, overloaded partition-key/clustering-key attributes (conventionally named something like PK and SK) whose actual meaning depends on the item type stored in that row. A common layout:

PK                  SK                    (attributes...)
CUSTOMER#8841       PROFILE               name, email, tier
CUSTOMER#8841       ORDER#2026-08-01#001  status, totalAmount
CUSTOMER#8841       ORDER#2026-08-05#002  status, totalAmount
ORDER#2026-08-01#001  ITEM#sku-123        productId, quantity, unitPrice
ORDER#2026-08-01#001  ITEM#sku-456        productId, quantity, unitPrice

Querying PK = CUSTOMER#8841 with an SK prefix condition retrieves the customer's profile and every order in one single-partition request — no join needed, because the "join" was pre-computed at write time by co-locating related items under a shared key structure. The trade-off is real: the table becomes far less readable in isolation (you can't tell what it "is" just by looking at the schema, the way you could with a normalized relational schema), every access pattern must be known upfront since adding a genuinely new query shape later may require a new index or a data-model change rather than just writing a new SQL query, and the design only pays off if your access patterns are actually stable and well understood in advance — which is precisely why this pattern is a deliberate trade of schema clarity and query flexibility for the single-digit-millisecond, single-partition latency DynamoDB is built to guarantee.

Hot partitions from a skewed key choice

This is the NoSQL-modeling restatement of the hot-shard problem from Section 6, but it bites harder here because the partition key is usually baked into the access pattern rather than an operational knob you can change later. If ShopSphere partitioned an order-events table by sellerId, one large brand running a flash sale generates an outsized fraction of all writes, and every one of those writes lands on the same partition — in Cassandra this means one set of replica nodes absorbs disproportionate load while the rest of the cluster idles; in DynamoDB this means throttling, since each partition has its own throughput ceiling regardless of how much provisioned or on-demand capacity the table has overall. The standard fix is a write-sharded or salted key: append a random or hashed suffix to the logical partition key (e.g., sellerId#0 through sellerId#9, chosen round-robin or by hashing the event ID) so that one seller's writes spread across ten partitions instead of one, at the cost of needing to fan a read for "all of this seller's events" out across those same ten partitions and merge the results — the same scatter-gather trade-off from Section 6's hash-based sharding strategy, just applied one level lower, at the partition-key layer.

Secondary indexes and their eventual-consistency caveat

A partitioned NoSQL store's primary key (partition key plus clustering/sort key) is the only lookup path guaranteed to be both fast and strongly consistent, because it's the same key the data is physically organized by. Any other query — "find the order with this orderNumber" when the table's partition key is customerId — needs a secondary index, and these come with a structural caveat that a relational secondary index does not: DynamoDB's Global Secondary Indexes (GSIs) and Cassandra's secondary indexes are maintained asynchronously, updated after the base table write completes, not as part of the same atomic operation. This means a write to the base table can be immediately visible on a primary-key lookup while the corresponding secondary-index entry is still propagating, so a query against the GSI immediately after the write can return stale or missing results — the same replication-lag read-after-write problem from Section 5's discussion of leader-follower replication, but occurring between a table and its own index rather than between a leader and a follower. This is exactly why the fix pattern is identical too: reads that require strict correctness immediately after a write (e.g., "confirm this order number now exists" right after creating it) should go through the base table's primary key, not the secondary index, while reads that can tolerate a short propagation delay (search/filter dashboards, "list orders by status") are exactly what secondary indexes are for.

Concepts Worth Being Able to Explain From First Principles

Why does a B-Tree's high branching factor matter more than its being "balanced"?
Balance alone (as in a red-black tree) guarantees O(log₂ n) height, but the base of that logarithm is what matters when each level costs a disk seek. A binary tree over a billion rows needs ~30 levels; a B-Tree with a branching factor of 500 needs only ~4 levels for the same billion rows, because each level does far more work (a sorted scan through hundreds of keys in one page, which is cheap once that page is already in memory) in exchange for needing far fewer levels. The entire design is shaped around the fact that a disk/page read costs orders of magnitude more than an in-memory comparison, so the right strategy is to do more comparisons per page fetched, not fewer levels of anything.
If LSM-Trees make writes so much faster, why doesn't every database use them by default?
Because the write speedup is paid for with read cost and operational complexity. A read might have to check the memtable plus several SSTables before it can be sure a key doesn't exist (mitigated but not eliminated by Bloom filters), and this variability is worse for latency-sensitive, read-heavy or range-scan-heavy workloads than a B-Tree's predictable, bounded-height lookup. Compaction also consumes background CPU and I/O that competes with foreground traffic, and if it falls behind, both read latency and disk usage degrade simultaneously. Postgres and MySQL/InnoDB default to B-Trees because most application workloads (CRUD apps, dashboards, anything with meaningful read/range-query volume) are better served by predictable reads than by maximum write throughput.
Why can't a composite index on (a, b, c) serve a query that filters only on b?
The index is one physical B-Tree sorted first by a, then by b within each a group, then by c within each b group. Rows with a given b value are scattered across every a group rather than being contiguous anywhere in the tree, so there is no way to jump directly to "all rows where b = x" without effectively examining every a group — which is no better than scanning the whole table. This is why the leftmost-prefix rule isn't an arbitrary restriction imposed by the database, it's a direct geometric consequence of how the keys are physically ordered on disk.
Why does asynchronous replication make "read-after-write" a real design problem instead of an edge case?
Asynchronous replication acknowledges the client as soon as the leader commits locally, before any follower has necessarily received the change. The replication stream then applies on its own schedule, which can lag by milliseconds to seconds depending on network conditions and follower load. If the very next read from that same client is routed to a lagging follower — which is likely in any system that load-balances reads across replicas for scalability — it will see stale data. This isn't a rare timing coincidence; it's the expected behavior any time a write and a subsequent read happen close together and land on different nodes, so systems that need read-your-own-writes semantics have to explicitly route those specific reads to the leader or a caught-up replica rather than relying on luck.
Why does sharding by a naive hash-and-modulo scheme cause a full data reshuffle when you add one node?
With shard = hash(key) % N, the shard assignment for almost every key depends on the exact value of N. Changing N from, say, 4 to 5 changes the modulo result for the vast majority of keys, not just the ones that "should" move to balance the new node — because the formula has no structural relationship between old and new assignments. Consistent hashing avoids this by placing shards and keys on a fixed-size ring independent of the node count; adding a shard only reassigns the keys in the arc between that shard and its neighbor, leaving every other key's assignment untouched.
In what situation would optimistic locking actually perform worse than pessimistic locking?
When contention on the same row is high and frequent — for example, a single hot counter row being updated by thousands of concurrent transactions per second. Optimistic locking would cause the vast majority of updates to fail their version check and retry, and under enough concurrency, the retry storm itself can consume more work and produce lower effective throughput than simply queuing transactions with a lock would have. Optimistic locking's advantage (no blocking) is only a win when conflicts are the exception rather than the norm; once conflicts become common, pessimistic locking's queuing behavior is actually more work-efficient because it doesn't throw away completed work on a failed compare-and-swap.
Why is a covering index sometimes a bigger performance win than just "having an index" at all?
A non-covering index still requires, for every matching row, a second lookup from the index's leaf entry back to the actual row in the table's heap or clustered structure (a bookmark lookup) to fetch any column not present in the index. That second lookup is effectively a separate, often random, page read per row. A covering index eliminates that step entirely because every column the query needs — filter and select — already lives in the index's own leaf pages, so the engine can answer the query by reading only the index, cutting the number of page accesses roughly in half or more for queries returning many rows.
Why can't you just put a B-Tree index on a text column and get fast full-text search out of it?
A B-Tree index stores and compares whole values in sorted order — it can answer "does this column equal exactly this string" or "what values fall between these two strings" very efficiently, because those are both operations on the value as a single sorted unit. Full-text search asks a fundamentally different question: "which rows contain this word anywhere inside a larger block of text," which requires the text to have already been broken into individual tokens, each mapped to the set of rows (or documents) that contain it — a postings list. A B-Tree has no mechanism for looking inside a value to find a substring match without a full scan; an inverted index solves exactly this by making the token itself the indexed key. This is why ShopSphere's product search over products.description is not served by adding a B-Tree index in Postgres — it needs a dedicated inverted-index structure such as Postgres GIN over a tsvector, or an external engine like Elasticsearch built entirely around inverted indexes and relevance ranking.
Why does the query optimizer need statistics at all — why can't it just pick the "obviously correct" plan?
There usually isn't one obviously correct plan independent of the data's actual shape — the same query structure (a filter plus a join) can be cheapest as a nested loop with an index probe if the filter is highly selective, or cheapest as a hash join if the filter barely narrows anything down. The optimizer has to choose before running anything, so it needs a numeric estimate of how many rows each step will produce, and that estimate only comes from statistics: row counts, distinct-value counts, and histograms captured by sampling the table. Without statistics, the optimizer would be choosing blind, defaulting to worst-case assumptions or arbitrary heuristics instead of a cost estimate grounded in the data's real distribution — which is exactly why a table with zero statistics (e.g., immediately after a bulk load, before ANALYZE runs) can produce a wildly bad plan for a query that runs fine once statistics exist.
Why does a hash join beat a nested loop join for two large, unindexed tables, but lose to nested loop for a small filtered result joined to an indexed table?
A nested loop join's cost is driven by how expensive each inner-side lookup is, multiplied by how many outer rows there are. When the outer side is small (a handful of rows after a selective filter) and the inner side has an index on the join column, each inner lookup is a cheap, near-constant-time B-Tree probe, so the total cost stays low even though it's technically "one lookup per outer row." When both tables are large and there's no index to make the inner lookup cheap, that same per-row lookup becomes a full scan repeated once per outer row — catastrophically expensive. A hash join sidesteps this by paying a one-time cost to build a hash table over the smaller side, then doing a single O(1)-per-row probe pass over the larger side, which is far cheaper than repeating a scan for every outer row. The crossover point is exactly where the nested loop's "cost per lookup times outer rows" stops being cheaper than the hash join's "build cost plus one linear pass" — which is precisely the kind of comparison the optimizer's cost model is built to make using the row-count estimates from statistics.
Why does embedding versus referencing in a document store map so directly onto the document size limit?
Embedding means the nested data physically lives inside the same document as its parent, so the parent document's size grows every time you add an embedded item, with no independent ceiling of its own — a review with a bounded number of replies stays small forever, but an order history embedded inside a customer document grows without bound as the customer keeps ordering. Referencing breaks that coupling entirely: the related data lives in its own document/collection with its own size budget, and the parent only stores a small, fixed-size ID. This is why the size limit isn't a separate concern from the embedding decision — it's the mechanism that turns "embed unbounded, frequently-growing collections" from a bad practice into an outright write failure once the document crosses the limit, which is exactly the failure mode that forces a redesign to referencing after the fact if it wasn't chosen upfront.
Why can a secondary index in a partitioned NoSQL store return a result that contradicts what the base table already shows?
The base table's primary key and a secondary index are two physically separate data structures, and in a partitioned store like DynamoDB or Cassandra, the index is not updated as part of the same atomic write as the base table — it's propagated asynchronously afterward. This is structurally identical to leader-follower replication lag: the "leader" (the base table write) commits and is immediately visible via a primary-key lookup, while the "follower" (the secondary index) is still catching up. A read against the secondary index immediately after the write can therefore see the old state or no entry at all, even though a primary-key read on the exact same underlying data already reflects the write. The fix is also identical in shape to the replication-lag fix: route reads that need immediate correctness to the base table's primary key, and reserve secondary-index reads for access patterns that can tolerate a short, usually sub-second, propagation delay.
