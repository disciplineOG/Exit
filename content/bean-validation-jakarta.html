Bean Validation Deep-Dive: Custom Validators & Validation Groups

Jakarta Validation @Valid vs @Validated Custom Constraints Validation Groups Cascading Validation Error Responses
Why this matters

Almost every ShopSphere endpoint that accepts a request body — a Seller creating a Product, a Customer submitting an Order, an Admin editing a Coupon — has to answer the same question before any business logic runs: is this input even shaped correctly? Bean Validation is the standard, declarative answer to that question, and it's deceptively easy to use shallowly (slap @NotNull on everything) while missing the parts that actually come up in real systems and in interviews: the difference between @Valid and @Validated, how to reuse one DTO across flows with different required fields, how to validate nested collections, and how to turn a pile of constraint violations into an error response a frontend can actually render field-by-field. Getting this layer right means a ProductDto with a blank name or a negative price never reaches ProductService at all — it dies at the controller boundary, before a single line of business logic executes.

1. The Jakarta Bean Validation Model and Where It Runs

Jakarta Bean Validation (the specification formerly known as JSR 380, and before that Bean Validation 2.0/1.1 under the javax namespace) defines a standard way to declare constraints on a Java object's fields as annotations, and a standard engine — a Validator — that walks an object graph, evaluates every constraint it finds, and reports the ones that fail as a set of ConstraintViolation objects. Spring does not implement this specification itself; spring-boot-starter-validation pulls in Hibernate Validator, which is the reference implementation almost everyone actually runs in production. Spring's contribution is the integration layer that wires this engine into the places where validation is actually useful: method arguments, request bodies, and JPA entities before persistence.

The mechanism that matters most for a REST API is what happens when a controller method parameter is annotated @Valid:

@PostMapping("/sellers/{sellerId}/products")
public ResponseEntity<ProductDto> createProduct(
        @PathVariable Long sellerId,
        @Valid @RequestBody ProductDto productDto) {
    Product saved = productService.create(sellerId, productDto);
    return ResponseEntity.status(HttpStatus.CREATED).body(toDto(saved));
}

This looks like a small annotation on a parameter, but it changes when validation actually happens. Spring MVC resolves controller method arguments through a chain of HandlerMethodArgumentResolver implementations — one resolver per kind of parameter (@PathVariable, @RequestParam, @RequestBody, and so on). For a @RequestBody parameter, the resolver is RequestResponseBodyMethodProcessor: it reads the raw HTTP body, deserializes it into a ProductDto using Jackson, and — critically — before returning that object to the framework to be passed into your controller method, it checks whether the parameter is annotated @Valid (or any annotation meta-annotated with Spring's @Validated stereotype). If it is, the resolver invokes the Bean Validation Validator against the freshly deserialized object right there, inside argument resolution.

This ordering is the single most important fact in this entire topic: validation happens as part of turning the HTTP request into a Java method call, strictly before the controller method body starts executing. If any constraint fails, the argument resolver never returns control to your controller method at all — it throws MethodArgumentNotValidException immediately, which propagates up and is handled (by default, or by your own @ControllerAdvice, covered in section 6) before createProduct's first line ever runs. A common misconception is that validation is "middleware" running in a filter or interceptor ahead of the DispatcherServlet; it isn't — it's woven directly into the argument-resolution step of the MVC handler pipeline, which is why it only fires for arguments actually annotated for validation, and why the validated object your controller method receives is guaranteed to already satisfy every declared constraint by the time you touch it.

Deserialization happens before validation, not instead of it

Jackson and Bean Validation solve different problems and run in sequence. If the JSON body has "price": "not-a-number" against a BigDecimal price field, that fails during Jackson deserialization itself — you get an HttpMessageNotReadableException, not a constraint violation, because the object never successfully comes into existence for the validator to inspect. Bean Validation only ever runs against an object that already deserialized successfully; it checks values that exist, not whether the JSON was syntactically or type-compatible with the target class.

2. Built-In Constraints and the @NotNull / @NotEmpty / @NotBlank Distinction

Jakarta Validation ships a standard library of constraint annotations covering the overwhelming majority of everyday field validation, and Hibernate Validator adds several more on top. The ones you'll reach for constantly on a ShopSphere ProductDto, OrderRequest, or CustomerRegistrationDto:

public class ProductDto {

    @NotBlank(message = "Product name is required")
    @Size(min = 2, max = 120)
    private String name;

    @NotNull(message = "Price is required")
    @Min(value = 0, message = "Price cannot be negative")
    private BigDecimal price;

    @Email
    private String supportContactEmail;

    @Pattern(regexp = "^[A-Z0-9]{6,12}$", message = "SKU must be 6-12 uppercase alphanumeric characters")
    private String sku;

    @Min(0)
    @Max(100000)
    private Integer stockQuantity;
}

@NotNull only rejects a literal Java null. An empty string "" or a string of pure whitespace " " both pass @NotNull just fine, because neither is null — they're perfectly valid, non-null String references that happen to carry no useful content. This is exactly the gap that trips people up when they reach for @NotNull on a String field expecting it to reject blank input.

@NotEmpty is stricter: in addition to rejecting null, it also rejects a value whose size is zero — for a String, that means rejecting "", and for a Collection, Map, or array, it means rejecting an empty one (e.g. an Order DTO's List<OrderLineItemDto> items being an empty list). But @NotEmpty still doesn't look at whitespace-only content — a String of " " has a nonzero length, so it passes @NotEmpty even though there's nothing meaningful in it.

@NotBlank is the strictest of the three, and it only applies to CharSequence types (String and friends), not collections. It rejects null, rejects the empty string, and additionally trims the value and rejects it if what's left is empty — so " " fails @NotBlank where it would pass both @NotNull and @NotEmpty. For any human-entered text field where whitespace-only input is meaningless — a Seller's Product name, a Customer's shipping addressLine1, a Coupon's code — @NotBlank is almost always the constraint you actually want, and reaching for @NotNull out of habit on a String field is a common, subtle bug: it silently accepts " " as a valid product name.

A few other built-ins worth knowing precisely rather than by vibe: @Size(min, max) constrains the length of a String or the size of a collection/array/map (not the numeric value — a common confusion with @Min/@Max, which constrain the numeric value of a number-typed field, not its string length). @Email checks a reasonably permissive email-shaped pattern — it is deliberately not a full RFC 5322 validator, so treat it as a sanity filter, not a guarantee of deliverability. @Pattern(regexp = ...) is the escape hatch for anything with a specific textual shape, such as a ShopSphere coupon code format or a SKU convention. All of these are field-shape checks — they know nothing about your database or any other field's value, which is precisely the limitation the next section exists to lift.

3. Writing a Custom Constraint End to End

Built-in constraints validate a single field in isolation using information available on the spot. Real business rules are frequently not like that — "this coupon code must exist and currently be active" or "the requested quantity must not exceed available inventory" both require querying something outside the object itself. Bean Validation supports this cleanly through custom constraints: an annotation plus a ConstraintValidator implementation that Spring manages as a bean, meaning it can autowire a repository or service exactly like any other Spring-managed component.

3.1 The annotation: @ValidCouponCode

A custom constraint is defined as a Java annotation with three mandatory elements — message, groups, and payload — plus a @Constraint meta-annotation pointing at the validator class that will implement the logic:

@Target({ ElementType.FIELD, ElementType.PARAMETER })
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = CouponCodeValidator.class)
public @interface ValidCouponCode {

    String message() default "Coupon code is invalid or no longer active";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};
}

The three elements aren't optional boilerplate — Bean Validation's engine reflectively inspects every constraint annotation for exactly these members and will fail to even start up if they're missing. message() supplies the default error text (overridable per usage, and resolvable against a message bundle for i18n). groups() is what makes this constraint participate in the validation-groups mechanism covered in section 4 — by default an empty array, meaning "the default group." payload() exists to attach arbitrary metadata classes to a violation (commonly used to carry a severity level) — most applications never populate it but must still declare it for the annotation to be spec-compliant.

3.2 The validator: querying a service safely

@Component
public class CouponCodeValidator implements ConstraintValidator<ValidCouponCode, String> {

    private final CouponRepository couponRepository;

    public CouponCodeValidator(CouponRepository couponRepository) {
        this.couponRepository = couponRepository;
    }

    @Override
    public boolean isValid(String code, ConstraintValidatorContext context) {
        if (code == null) {
            return true; // let @NotBlank/@NotNull own the null/blank case; this validator only checks existence+status
        }
        return couponRepository.findByCode(code)
                .map(Coupon::isActive)
                .orElse(false);
    }
}

ConstraintValidator<A, T> takes two type parameters: the annotation it implements (ValidCouponCode) and the Java type it can validate (String, here). Because @Component makes this class a Spring bean, @Autowired/constructor injection of CouponRepository works exactly as it would in any other Spring bean — Spring's own LocalValidatorFactoryBean is configured (automatically, by Spring Boot's auto-configuration) to use a SpringConstraintValidatorFactory that resolves validator instances through the application context instead of via a bare no-arg reflective instantiation. Without that integration, a ConstraintValidator would only ever be able to run pure, self-contained logic; with it, a validator can consult a database, a cache, or another service.

Notice the null-handling convention: a ConstraintValidator should almost always treat null as valid and delegate the "is this required at all" question to @NotNull/@NotBlank stacked alongside it. This keeps each constraint doing exactly one job and composes cleanly — you can make the coupon code optional in one context and required in another just by adding or removing @NotBlank, without touching CouponCodeValidator at all.

3.3 A second example with a real side-effect trap: @SufficientInventory

A more ShopSphere-specific case: validating that a requested order quantity does not exceed what inventory-service currently has on hand for a SKU. This looks like the same pattern as above, but it has a sharper trade-off worth calling out explicitly.

@Component
public class SufficientInventoryValidator
        implements ConstraintValidator<SufficientInventory, OrderLineItemDto> {

    private final InventoryClient inventoryClient;

    public SufficientInventoryValidator(InventoryClient inventoryClient) {
        this.inventoryClient = inventoryClient;
    }

    @Override
    public boolean isValid(OrderLineItemDto item, ConstraintValidatorContext context) {
        if (item == null || item.getSku() == null || item.getQuantity() == null) {
            return true; // other constraints own null/required checks
        }
        int available = inventoryClient.getAvailableQuantity(item.getSku()); // remote call
        return item.getQuantity() <= available;
    }
}
A ConstraintValidator that calls out to another service is a read, not a reservation

This validator makes a network call to inventory-service on every validation pass, which has two consequences worth being deliberate about. First, performance: if this constraint is applied to every OrderLineItemDto inside a cascaded List<OrderLineItemDto> (section 5), an order with twenty line items triggers twenty remote calls purely for request validation, before checkout logic has even started — this needs to be a fast, well-isolated lookup (ideally backed by a cache), not a call that itself does business work. Second, and more subtle: because request validation and the actual checkout can be separated in time by network latency, a quantity that was available at validation time can be sold to a different Customer microseconds later — bean validation can only ever check inventory was sufficient at the moment it looked, not guarantee it stays sufficient. The two problems compose into one rule: keep ConstraintValidator logic to reads with no side effects, and never treat "validation passed" as a substitute for an atomic, transactional inventory reservation inside OrderService itself. A validator that decremented stock as a side effect of validating would be actively dangerous — a request that fails validation for an unrelated reason (say, a missing shipping address) could still have silently consumed inventory.

4. Validation Groups: Reusing One DTO Across Different Flows

A recurring, very real design pressure: the same ProductDto shape is used both when a Seller first creates a Product (where sku must be present, because the catalog needs it immediately) and when an Admin later edits pricing or description on an existing product (where sku is already fixed and shouldn't be required in the request body at all). Slapping @NotBlank on sku unconditionally makes the Admin-update endpoint reject perfectly valid requests that omit it; leaving it off entirely means the Seller-creation endpoint silently accepts products with no SKU.

Validation groups solve this by attaching each constraint to one or more named "groups" and then telling a given validation call which group(s) it cares about. Groups are just marker interfaces — empty, with no methods, existing purely as distinct types to tag constraints and validation calls with:

public interface SellerCreate {}
public interface AdminUpdate {}
public class ProductDto {

    @NotBlank(message = "Product name is required", groups = { SellerCreate.class, AdminUpdate.class })
    private String name;

    @NotBlank(message = "SKU is required at creation", groups = SellerCreate.class)
    @Pattern(regexp = "^[A-Z0-9]{6,12}$", groups = { SellerCreate.class, AdminUpdate.class })
    private String sku;

    @NotNull(groups = { SellerCreate.class, AdminUpdate.class })
    @Min(value = 0, groups = { SellerCreate.class, AdminUpdate.class })
    private BigDecimal price;
}

Here, sku's @NotBlank only belongs to the SellerCreate group, while its @Pattern (if a SKU is present at all, it must still be well-formed) belongs to both groups. name and price are required in both flows. A constraint with no explicit groups attribute implicitly belongs to the built-in Default group — worth remembering, because it means ungrouped constraints and constraints explicitly grouped are easy to accidentally mix in ways that don't validate what you think.

The controller side is where @Valid and Spring's own @Validated diverge in a way that trips people up in interviews: plain @Valid, from the Jakarta specification, only ever validates against the Default group — it has no mechanism for specifying a different one. To validate against a specific group, you need Spring's own @Validated annotation (from org.springframework.validation.annotation.Validated, not to be confused with Jakarta's @Valid), which accepts a value() of one or more group classes:

@PostMapping("/sellers/{sellerId}/products")
public ResponseEntity<ProductDto> createProduct(
        @PathVariable Long sellerId,
        @Validated(SellerCreate.class) @RequestBody ProductDto productDto) {
    // sku is required here
}

@PutMapping("/admin/products/{productId}")
public ResponseEntity<ProductDto> updateProduct(
        @PathVariable Long productId,
        @Validated(AdminUpdate.class) @RequestBody ProductDto productDto) {
    // sku is not required here, but if present, must still match the pattern
}

Mechanically this works because the exact same RequestResponseBodyMethodProcessor argument-resolution step from section 1 looks for either @Valid or any annotation meta-annotated with Spring's @Validated, and — if it's @Validated — reads the group classes off it and passes them through to the underlying Validator.validate(object, groups...) call. @Valid simply has no attribute to carry that information, because it's defined by the Jakarta spec, which doesn't mandate any Spring-specific integration; Spring's own annotation is a superset built specifically to plug that gap for MVC use.

Groups don't have to be single-purpose markers

A group interface can extend other group interfaces to compose ("OnCreate extends Default, SellerCreate"), and a single @Validated call can list multiple groups (@Validated({SellerCreate.class, Default.class})) when you want both the grouped and the ungrouped constraints checked together. The main discipline worth keeping is to not let group interfaces multiply uncontrolled — if a DTO needs more than two or three flows, it's often a signal that flow-specific request DTOs (a distinct ProductCreateRequest versus ProductUpdateRequest) would be a clearer design than groups pushed further and further.

5. Cascading Validation into Nested Objects and Collections

Constraints declared directly on a DTO's own fields only ever look at that DTO's immediate, top-level fields. An OrderRequestDto that contains a ShippingAddressDto field, or a List<OrderLineItemDto>, needs an explicit signal to tell the validator to descend into those nested objects — otherwise a completely empty or malformed ShippingAddressDto passes validation cleanly, because the validator never looked inside it.

That signal is @Valid placed directly on the nested field (not to be confused with @Valid on a controller parameter from section 1 — same annotation, different position, related but distinct effect):

public class OrderRequestDto {

    @NotNull
    @Valid
    private ShippingAddressDto shippingAddress;

    @NotEmpty(message = "Order must contain at least one line item")
    @Valid
    private List<OrderLineItemDto> items;
}

public class ShippingAddressDto {
    @NotBlank private String addressLine1;
    @NotBlank private String city;
    @Pattern(regexp = "^[0-9]{5,6}$") private String postalCode;
}

public class OrderLineItemDto {
    @NotBlank private String sku;
    @Min(1) private Integer quantity;
}

With @Valid on the shippingAddress field, once the top-level OrderRequestDto validates its own fields, the engine recurses into shippingAddress and validates ShippingAddressDto's own constraints too, contributing its own ConstraintViolations (with a nested property path like shippingAddress.postalCode) into the same overall violation set. The same is true for @Valid on the List<OrderLineItemDto> items field: Bean Validation understands collection cascading, meaning it validates every element of the list individually, not just whether the list itself is non-null or non-empty. An Order with five line items where the third one has quantity: -1 produces a violation whose property path looks like items[2].quantity, correctly identifying exactly which element in the collection failed — this is what makes it practical to build a precise, per-item error response rather than a vague "something in your order is wrong."

It's worth being precise about what @NotEmpty and @Valid are each doing on the items field, because they're independent and easy to conflate: @NotEmpty checks that the list itself isn't null or zero-length; @Valid separately triggers cascading into whatever elements do exist. Removing @Valid while keeping @NotEmpty would still correctly reject a missing or empty order, but would silently stop catching a line item with an invalid SKU or a negative quantity — the list-level check and the element-level check are two different, composable guarantees, and dropping the cascade annotation is a quiet, easy-to-miss way to regress coverage on nested data.

6. From ConstraintViolations to a Structured API Error Response

When @Valid/@Validated validation on a @RequestBody parameter fails, Spring MVC does not hand you a raw set of ConstraintViolation objects to sort out yourself — it packages them into a specific exception, MethodArgumentNotValidException, which carries a Spring BindingResult (or, more precisely, the Errors/BindingResult that WebDataBinder produced during validation) containing one FieldError per failed field-level constraint and one ObjectError per failed class-level constraint. Left unhandled, Spring Boot's default error handling turns this into a generic 400 Bad Request with a fairly unhelpful, uniform JSON body — technically correct, but useless for a frontend that wants to show "Price cannot be negative" directly under the price input rather than a single opaque message.

The fix is a @ControllerAdvice (or @RestControllerAdvice, which combines @ControllerAdvice with @ResponseBody) with an @ExceptionHandler specifically for MethodArgumentNotValidException, translating it into whatever structured error contract the rest of the API already uses:

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiErrorResponse handleValidation(MethodArgumentNotValidException ex) {
        List<FieldErrorDetail> fieldErrors = ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> new FieldErrorDetail(
                        fe.getField(),          // e.g. "items[2].quantity"
                        fe.getDefaultMessage(), // e.g. "must be greater than or equal to 1"
                        fe.getRejectedValue()))
                .toList();

        return new ApiErrorResponse(
                "VALIDATION_FAILED",
                "One or more fields are invalid",
                fieldErrors,
                Instant.now());
    }
}

record FieldErrorDetail(String field, String message, Object rejectedValue) {}

record ApiErrorResponse(
        String errorCode,
        String message,
        List<FieldErrorDetail> fieldErrors,
        Instant timestamp) {}

fe.getField() is what carries the nested/indexed property path built during cascading validation (section 5) — "items[2].quantity" rather than a bare "quantity" — which is exactly what lets a frontend map a single violation back to a specific row in a dynamically rendered order form. This handler is one instance of a broader, general pattern: an API should have one coherent error-response shape (an error code, a human-readable message, optionally a list of field-level details, a timestamp, maybe a trace ID) used consistently across every kind of failure — validation errors, not-found errors, conflict errors — not a different ad hoc JSON shape per exception type. Bean Validation's MethodArgumentNotValidException is just one specific, very common source feeding into that same general contract; a well-designed @ControllerAdvice will have sibling @ExceptionHandler methods for things like ProductNotFoundException or InsufficientInventoryException that populate the same ApiErrorResponse shape with different errorCode values, so a client only ever has to learn one envelope.

Method-level validation on non-controller beans throws a different exception

Everything above concerns @RequestBody arguments validated at MVC's argument-resolution layer, which is Spring-specific and throws MethodArgumentNotValidException. If instead you put @Validated at the class level on a plain @Service bean and annotate its method parameters directly with constraints (e.g. @NotNull on a service method argument, enforced via AOP the same way @Transactional is — see the proxy mechanics in Spring's core container model), a violation instead throws ConstraintViolationException, the plain Jakarta exception, not the Spring MVC one. A @ControllerAdvice that only handles MethodArgumentNotValidException will not catch this — it needs its own separate @ExceptionHandler(ConstraintViolationException.class) if service-layer method validation is in play anywhere in the call path, which is an easy gap to leave unhandled in a codebase that also does field-level request validation.

Concepts Worth Being Able to Explain From First Principles

At exactly what point in a Spring MVC request does @Valid on a @RequestBody parameter trigger, and why does that timing matter?
It triggers inside RequestResponseBodyMethodProcessor, the HandlerMethodArgumentResolver responsible for @RequestBody parameters, immediately after Jackson deserializes the JSON into a Java object and before that object is handed to the controller method as an argument. This means validation happens during argument resolution, not inside the controller body, and a failure short-circuits the whole call — MethodArgumentNotValidException is thrown from within argument resolution itself, so the controller method's first line never executes. Anyone reading a controller method that takes a @Valid @RequestBody ProductDto can therefore assume, correctly, that every declared constraint has already passed by the time execution reaches that method.
Why doesn't @NotNull catch a blank string, and when would you actually want @NotEmpty over @NotBlank?
@NotNull only checks Java reference identity against null — an empty string or a whitespace-only string is a perfectly valid non-null object reference, so both pass. @NotBlank additionally trims the string and rejects what's left if it's empty, making it the right choice for almost any human-entered text field. @NotEmpty sits in between and is most useful on collections rather than strings — for example, requiring a ShopSphere Order's items list to contain at least one element, where "blank after trimming" doesn't even apply, but "zero elements" clearly should be rejected.
Why should a custom ConstraintValidator that queries a service (like checking inventory) avoid having side effects?
A ConstraintValidator can run multiple times, in contexts you don't fully control — once per cascaded collection element, potentially re-run if validation is triggered again, and always strictly before the business logic that would actually act on the result. If the validator itself mutated state (for example, decrementing inventory as a side effect of checking it), a request that ultimately fails for an unrelated reason — a missing shipping address, say — could still have caused that mutation, leaving the system in a corrupted state despite the overall request being rejected. Validators should be treated as pure reads: check a condition and report true or false, and leave any actual state change (like an atomic inventory reservation) to the transactional business logic that runs only after validation has already succeeded.
What's the concrete difference between @Valid and Spring's @Validated, and why does it matter for validation groups?
@Valid is defined by the Jakarta Bean Validation specification and carries no ability to specify which validation group to check against — it always validates against the implicit Default group. Spring's own @Validated annotation is a superset built specifically to plug that gap for Spring-managed code: it accepts a value() of one or more group marker interfaces, and Spring's MVC argument-resolution layer reads those groups off the annotation and passes them into the underlying Validator.validate(object, groups...) call. This is why reusing one DTO like ProductDto across a Seller-creation flow (where SKU is required) and an Admin-update flow (where it isn't) requires @Validated(SellerCreate.class) and @Validated(AdminUpdate.class) on the respective controller parameters — plain @Valid has no attribute to express that distinction at all.
How does @Valid on a nested field or a List field actually trigger cascading, and what happens if you forget it on a collection?
Bean Validation only inspects the fields it's told to inspect. Placing @Valid directly on a nested object field (like ShippingAddressDto shippingAddress) or a collection field (like List<OrderLineItemDto> items) tells the validator to recurse into that value and validate its own declared constraints, contributing additional violations under a nested or indexed property path such as items[2].quantity. If you annotate the collection field with @NotEmpty but omit @Valid, the validator will correctly reject a null or empty list, but it will never look inside the elements that do exist — a line item with a negative quantity or a blank SKU would pass validation completely undetected, because the two annotations check genuinely independent things: list-level shape versus element-level content.
What does a @ControllerAdvice handler for MethodArgumentNotValidException actually need to extract to build a useful field-level error response?
The exception carries a BindingResult with a list of FieldError objects, one per failed field-level constraint (plus ObjectErrors for any class-level constraints). Each FieldError exposes the property path via getField() — which correctly reflects nested and indexed paths like shippingAddress.postalCode or items[2].quantity when cascading validation was involved — along with getDefaultMessage() for the human-readable reason and getRejectedValue() for what was actually submitted. Mapping this list into a project-wide error-response DTO (an error code, a message, and this list of field details) is what turns a generic 400 into something a frontend can bind directly to individual form fields.
Why can't a single @ControllerAdvice that only handles MethodArgumentNotValidException catch every validation failure in an application?
MethodArgumentNotValidException is specific to Spring MVC's handling of @Valid/@Validated on @RequestBody (and similar) controller arguments. If method-level validation is applied elsewhere — for instance, a @Validated class-level annotation on a plain @Service bean with constrained method parameters, enforced via an AOP proxy in the same style as @Transactional — a violation there throws the plain Jakarta ConstraintViolationException instead, because that code path never goes through Spring MVC's argument resolution at all. A complete error-handling setup needs a separate @ExceptionHandler(ConstraintViolationException.class) alongside the one for MethodArgumentNotValidException if service-layer method validation is used anywhere in the call graph.
Why is a custom ConstraintValidator able to autowire a Spring bean like a repository, when a plain Bean Validation implementation couldn't?
Bean Validation's specification only requires that a ConstraintValidator be instantiable, typically via a no-argument constructor through reflection, which gives it no way to receive external dependencies. Spring Boot's auto-configuration replaces the default validator-instantiation strategy with a SpringConstraintValidatorFactory, which resolves each ConstraintValidator through the application context rather than via bare reflection — meaning a validator annotated @Component is a genuine Spring-managed bean, eligible for constructor injection of a CouponRepository, an InventoryClient, or any other collaborator exactly as it would be for a controller or service bean.
