Why this matters

Most "clean code" advice is aesthetic preference dressed up as law, but SOLID and the classic Gang-of-Four patterns describe something more mechanical: they predict which parts of a codebase will require a rewrite versus an edit when a new requirement lands. A class that violates Single Responsibility doesn't just "feel messy" — it means two unrelated teams will eventually edit the same file for unrelated reasons, and one of their changes will silently break the other's tests. Understanding these principles precisely, rather than as slogans, is what lets you predict where a design will crack under a specific kind of future change before you've written that change.

1. Single Responsibility Principle (SRP)

The formal statement — "a class should have only one reason to change" — is easy to misread as "a class should do one thing," which is too vague to apply. The precise, mechanical test is: enumerate the distinct actors or business concerns that could each independently demand a change to this class. If that list has more than one entry, the class has more than one responsibility, and those responsibilities will eventually be pulled in different directions by different callers.

// VIOLATION: three unrelated reasons to change live in one class
class OrderInvoiceService {
    Invoice createInvoice(Order order) { /* pricing + tax logic */ }

    void saveInvoice(Invoice invoice) {
        // JDBC connection handling, SQL strings
        Connection conn = DriverManager.getConnection(DB_URL);
        // ... raw SQL INSERT
    }

    String renderInvoiceHtml(Invoice invoice) {
        // HTML templating logic mixed into the same class
        return "<html>...</html>";
    }
}

Ask "what would force OrderInvoiceService to change?" and you get three unrelated answers: the finance team changes how tax is calculated on an Order's totalAmount, the DBA changes the schema or switches from JDBC to a JPA repository, and a designer changes the invoice's HTML layout for the confirmation email. None of these three people should need to touch, recompile, or re-review the other two concerns' code — but because they're in one class, a schema migration and a tax-calculation bug fix now show up in the same diff, and a unit test for pricing logic has to spin up a database connection just to instantiate the class.

// FIX: one reason to change per class
class InvoicePricingService {
    Invoice createInvoice(Order order) { /* pricing + tax only, off order.getItems() */ }
}
class InvoiceRepository {
    void save(Invoice invoice) { /* persistence only */ }
}
class InvoiceRenderer {
    String toHtml(Invoice invoice) { /* presentation only, for the order-confirmation email */ }
}

Concretely, what breaks when SRP is violated is testability (you can't unit test tax logic without a live database), maintainability (a merge conflict between the DBA's schema change and the finance team's tax fix, in a file neither fully understands), and reusability (you can't reuse the pricing logic in a nightly settlement batch job without dragging along HTML rendering code and its templating dependency).

SRP is about actors, not line count

A 500-line class that only ever changes for one reason (say, a state machine with many transitions) is not an SRP violation. A 20-line class that two unrelated teams need to modify for unrelated reasons is. Don't use size as a proxy — use "who asks for changes here."

2. Open/Closed Principle (OCP)

A module should be open for extension but closed for modification: you should be able to add new behavior by adding new code, not by editing code that already works and is already covered by regression tests. The mechanism that makes this possible is polymorphism — you replace a conditional that branches on type with a common interface, and each new case becomes a new implementation rather than a new branch.

// VIOLATION: adding a payment gateway means editing this method again
class ShopSpherePaymentProcessor {
    void process(String provider, Payment payment) {
        if (provider.equals("STRIPE")) {
            // charge via Stripe's API
        } else if (provider.equals("LEGACY_BANK_GATEWAY")) {
            // call the legacy bank gateway's SOAP endpoint
        }
        // every new payment provider edits this same method
    }
}

Every time ShopSphere onboards a new payment provider, you re-open a method that was already tested and working for Stripe and the bank gateway, risking a regression in code unrelated to the new feature. The fix inverts the direction of the dependency: define an abstraction, and let each case supply its own implementation.

interface PaymentGateway {
    Payment charge(Payment payment);   // returns Payment with status CAPTURED or FAILED
}
class StripeGateway implements PaymentGateway {
    public Payment charge(Payment payment) { /* Stripe API call */ }
}
class LegacyBankGateway implements PaymentGateway {
    public Payment charge(Payment payment) { /* adapted legacy SOAP call — see Adapter, section 7 */ }
}
// Adding RazorpayGateway later requires zero edits to existing classes.
class ShopSpherePaymentProcessor {
    Payment process(PaymentGateway gateway, Payment payment) {
        return gateway.charge(payment);
    }
}

Note that OCP is never absolute — somewhere, something has to map an order's chosen provider to a concrete PaymentGateway (a factory, a Spring bean lookup by qualifier, a registry populated at startup). OCP doesn't eliminate that decision point; it isolates it to one small, well-understood piece of wiring code instead of spreading the branching logic through business methods. This is also precisely the principle that the Strategy pattern (covered below) exists to implement mechanically. Making that charge() call safe to retry when payment-service's response is lost mid-network-call is a separate, equally important concern — see Payment Systems & Idempotent Transactions.

3. Liskov Substitution Principle (LSP)

LSP says a subtype must be usable through its supertype's reference without the caller noticing anything is different — the subtype must honor the supertype's contract, not merely its method signatures. This is a stronger requirement than "compiles without errors," because Java's type checker verifies signatures but has no way to verify behavioral promises like "this method never mutates the object's width independently of its height."

The classic Square-extends-Rectangle trap

Modeling Square as a subclass of Rectangle looks correct geometrically — a square is a rectangle with equal sides — but it is an LSP violation in code, because Rectangle's implicit contract is "setting width does not change height, and vice versa." A Square must break that contract to remain a valid square.

class Rectangle {
    protected int width, height;
    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {
    @Override void setWidth(int w)  { width = height = w; }  // must keep sides equal
    @Override void setHeight(int h) { width = height = h; }
}

// Caller written against the Rectangle contract:
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);
    assert r.area() == 50;   // holds for any real Rectangle...
}
resize(new Square(...));      // ...but fails for Square: area() == 100

The caller made a "reasonable assumption about the supertype's contract" — that width and height are independent — and that assumption is exactly what Square had to violate to satisfy its own invariant (equal sides). This is not a bug in the caller; it's a bug in the inheritance modeling. The fix is to stop expressing "is described by the same shape hierarchy" as "is a subtype of." Either make both immutable value types with no setters (so there's no mutation contract to violate), or don't use inheritance between them at all — model both as implementations of a Shape interface exposing only area(), with no shared mutable state or setters whose independence is assumed.

The mechanical test for LSP, generalized beyond this example: for every method a subclass overrides, ask whether it (a) throws exceptions the superclass method didn't promise to throw, (b) returns a narrower or incompatible range of values, (c) weakens a precondition callers rely on, or (d) strengthens a postcondition in a way that surprises code written only against the supertype. Any "yes" is an LSP violation, regardless of whether the code compiles.

4. Interface Segregation Principle (ISP)

ISP says many small, client-specific interfaces beat one large interface that forces every implementer to provide (or stub out) methods it has no use for. The cost of violating ISP is concrete: implementers throw UnsupportedOperationException from methods they can't meaningfully support, and every caller of the fat interface is coupled to methods it doesn't call — meaning a change to an unrelated method's signature forces a recompile of code that never used it.

// VIOLATION: one fat interface for every kind of notifiable order event handler
interface OrderEventHandler {
    void sendEmail(Order order);
    void sendSms(Order order);
    void updateAnalyticsDashboard(Order order);
}

class SmsOnlyNotifier implements OrderEventHandler {
    public void sendSms(Order order) { /* fine */ }
    public void sendEmail(Order order) { throw new UnsupportedOperationException(); }         // this provider only does SMS
    public void updateAnalyticsDashboard(Order order) { throw new UnsupportedOperationException(); } // not its job either
}
// FIX: segregate by capability
interface EmailNotifiable     { void sendEmail(Order order); }
interface SmsNotifiable       { void sendSms(Order order); }
interface AnalyticsUpdatable  { void updateAnalyticsDashboard(Order order); }

class FullOrderEventHandler implements EmailNotifiable, SmsNotifiable, AnalyticsUpdatable { ... }
class SmsOnlyNotifier implements SmsNotifiable { public void sendSms(Order order) { ... } } // no stubs needed

Code in notification-service that only needs to trigger an SMS on OrderShipped should depend on SmsNotifiable, not OrderEventHandler — that way, adding a new method to AnalyticsUpdatable (e.g., void recordConversionFunnelStep(Order order)) never forces a recompile of code that only ever called sendSms(). This composes directly with dependency inversion (next section): the whole point of depending on an abstraction is undermined if that abstraction is bloated enough to require irrelevant methods.

5. Dependency Inversion Principle (DIP)

DIP is the principle most people conflate with dependency injection, but they are not the same thing — DIP is the design rule, DI is one mechanical technique for satisfying it. DIP states: high-level modules (business policy) should not depend on low-level modules (implementation detail); both should depend on an abstraction. The abstraction is owned by the high-level module, not the low-level one — this reversal of ownership is why it's called "inversion."

// VIOLATION: high-level policy depends directly on a low-level concrete class
class OrderService {
    private final MySqlOrderRepository repository = new MySqlOrderRepository();
    void placeOrder(Order order) {
        repository.save(order);   // hard-wired to MySQL, and to `new`
    }
}

Two things break here. First, testability: unit-testing OrderService means either running a real MySQL instance or leaving the test coupled to persistence details entirely unrelated to order-placement logic. Second, extensibility: switching to DynamoDB, or adding a caching layer in front of MySQL, means editing OrderService itself — a class that has nothing conceptually to do with which database is in use.

// FIX: high-level module depends on an abstraction it defines
interface OrderRepository {           // owned by the high-level module's package
    void save(Order order);
}
class OrderService {
    private final OrderRepository repository;
    OrderService(OrderRepository repository) { this.repository = repository; } // injected
    void placeOrder(Order order) { repository.save(order); }
}
class MySqlOrderRepository implements OrderRepository { ... }  // low-level detail, depends on the abstraction too

Now both OrderService (high-level) and MySqlOrderRepository (low-level) depend on OrderRepository — neither depends on the other directly. Swapping persistence technology means writing a new class that implements the interface; OrderService never changes. Testing means passing an in-memory fake or a Mockito mock that implements OrderRepository. This is precisely why Spring's dependency injection container is meaningful rather than a convenience: it doesn't cause you to follow DIP, it just automates the wiring once your code already follows DIP. Injecting a concrete class directly (new MySqlOrderRepository() via @Autowired on the concrete type) gives you Spring's object graph management but none of DIP's actual decoupling — see Spring Core Mechanics for how the container resolves interface-typed dependencies to concrete beans at runtime.

6. The Gang-of-Four Taxonomy

The 23 patterns in the original "Gang of Four" (Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides) catalog are grouped by what question they answer, not by how they look in UML. Creational patterns answer "how do I get an object without hard-wiring which concrete class or how many objects get built?" Structural patterns answer "how do I compose existing classes/objects into a larger shape without changing them?" Behavioral patterns answer "how do objects that already exist coordinate and communicate at runtime?" Sections 6–8 below cover the ones most likely to show up in a Java/Spring codebase — this tree places them against the full catalog so you can see what's deliberately out of scope.

Gang-of-Four Design Patterns
│
├── Creational  — controls HOW and WHEN objects get constructed
│     ├── Factory Method     — one method decides which subclass to instantiate   [section 6]
│     ├── Abstract Factory   — produces a whole family of related objects         [section 6]
│     ├── Builder            — assembles a complex object step by step            [section 6]
│     ├── Singleton          — exactly one instance, globally reachable           [section 6]
│     └── Prototype          — creates new objects by cloning an existing one     (rare in Java; see note below)
│
├── Structural  — controls HOW existing classes/objects are composed
│     ├── Adapter            — translates one interface into another             [section 7]
│     ├── Decorator          — layers behavior onto an object, same interface     [section 7]
│     ├── Facade             — one simplified entry point over a complex subsystem
│     ├── Composite          — treats a tree of objects and single objects uniformly
│     ├── Proxy              — stands in for another object (lazy load, access control, remote call)
│     ├── Bridge             — separates an abstraction from its implementation so both vary independently
│     └── Flyweight           — shares immutable state across many logically-distinct objects to save memory
│
└── Behavioral  — controls HOW objects interact and share responsibility at runtime
      ├── Strategy           — swappable algorithm/behavior behind one interface  [section 8]
      ├── Observer           — subject notifies decoupled listeners of a change   [section 8]
      ├── State              — behavior changes as an object's internal state changes [section 8]
      ├── Template Method    — superclass fixes an algorithm's skeleton, subclasses fill in steps
      ├── Chain of Responsibility — a request passes along a chain until something handles it
      ├── Command            — encapsulates a request as an object (undo/redo, queuing)
      ├── Iterator           — sequential access to a collection without exposing its structure
      ├── Mediator           — centralizes how a set of objects communicate, so they don't reference each other directly
      ├── Visitor            — adds a new operation over a class hierarchy without editing the hierarchy
      └── Memento            — captures/restores an object's internal state without violating encapsulation
Why Prototype is rare in idiomatic Java

Prototype solves "creating a new instance is more expensive than copying an existing one" by cloning a pre-configured prototype object instead of running its constructor from scratch. Java exposes a built-in hook for this (Object.clone() plus the Cloneable marker interface), but that mechanism is widely considered a design mistake in the language itself — clone() performs a shallow copy by default, Cloneable declares no actual clone method, and getting deep-copy semantics right requires overriding clone() carefully in every subclass. Most modern Java code gets the same effect more safely via a copy constructor or a static factory method (e.g. Product.copyOf(existing)), which is why Prototype rarely appears by name in Java codebases even though the underlying need — cheap duplication of a pre-built object, such as cloning a seller's "template" Product listing into a new one with a different SKU — still comes up.

The rest of this page covers Creational, Structural, and Behavioral patterns in that order, focusing on the subset that recurs constantly in Spring/Java backend code: Factory Method, Abstract Factory, Singleton, and Builder (Creational); Adapter and Decorator (Structural); Strategy, Observer, and State (Behavioral).

Factory Method & Abstract Factory

Reach for a factory when the exact concrete type needed isn't known until runtime — it depends on configuration, user input, or a request parameter — and you want callers to depend only on an interface, never on a constructor of a specific implementation (which would itself be a DIP violation).

interface ShippingProvider {
    ShippingLabel createLabel(Order order, Address destination);
    Duration estimatedTransitTime(Address destination);
}

class ShippingProviderFactory {
    static ShippingProvider create(String carrierCode) {
        return switch (carrierCode) {
            case "FEDEX"  -> new FedExProvider();
            case "UPS"    -> new UpsProvider();
            case "USPS"   -> new UspsProvider();
            default -> throw new IllegalArgumentException("Unknown carrier: " + carrierCode);
        };
    }
}

// order-service picks a provider per shipment without ever naming a concrete class:
ShippingProvider provider = ShippingProviderFactory.create(order.getSelectedCarrier());
ShippingLabel label = provider.createLabel(order, order.getShippingAddress());

Factory Method defers creation to a single method (often overridden per-subclass); Abstract Factory goes one level further and produces an entire family of related objects that must stay consistent with each other. In ShopSphere terms: a RegionalCheckoutFactory interface with UsCheckoutFactory and EuCheckoutFactory implementations, each producing a matching TaxCalculator, PaymentGateway, and InvoiceFormatter for that region — so checkout never accidentally combines EU VAT rules with a US-only payment gateway. Use Abstract Factory specifically when creation decisions need to be made as a coordinated group, not independently per object.

Singleton — and why it's dangerous

Singleton restricts a class to exactly one instance, reachable globally. It's tempting for things like configuration readers or connection pools — e.g. a single ShopSphereFeatureFlags object read by every service instance to decide whether a new checkout flow is enabled — but it comes with real costs: it introduces global mutable state (any code, anywhere, can read or mutate the single instance, making reasoning about state changes non-local), it makes testing harder (tests can't easily substitute a fake instance, and state leaks between tests unless explicitly reset), and naive lazy-initialization implementations have subtle thread-safety bugs.

// BROKEN under concurrency: two threads can both see instance == null
class FeatureFlags {
    private static FeatureFlags instance;
    static FeatureFlags getInstance() {
        if (instance == null) {           // race window here
            instance = new FeatureFlags();
        }
        return instance;
    }
}

Synchronizing the whole method works but serializes every call forever, even after the instance exists. The standard fix in Java is the initialization-on-demand holder idiom, which leans on the JVM's own classloading guarantees instead of explicit locking:

class FeatureFlags {
    private FeatureFlags() {}
    private static class Holder {
        static final FeatureFlags INSTANCE = new FeatureFlags();  // built lazily, thread-safely
    }
    static FeatureFlags getInstance() {
        return Holder.INSTANCE;
    }
}

The JVM guarantees a class is initialized at most once, and that initialization happens-before any subsequent access from any thread (JLS class-initialization semantics) — so Holder isn't loaded (and INSTANCE isn't constructed) until getInstance() is first called, and every thread that calls it afterward sees the fully-constructed instance with no explicit synchronized block on the hot path.

Singleton versus a Spring singleton-scoped bean

Spring's default bean scope is also called "singleton," but it means something narrower and safer: one instance per ApplicationContext, not one instance per JVM process. You get the "shared instance" benefit without a hard-coded static accessor, and tests can spin up an independent context with its own instance — sidestepping most of classic Singleton's testing pain.

Builder

Builder solves telescoping constructors — the pattern where a class with many optional fields grows an ever-longer chain of overloaded constructors to cover every combination of "which optional fields are set."

// VIOLATION: telescoping constructors
new ShippingLabel(order.getId(), carrier, null, null, true, false);   // what do these positions mean?

// FIX: builder makes each optional field self-documenting and omittable
ShippingLabel label = ShippingLabel.builder()
    .orderId(order.getId())
    .carrier("FEDEX")
    .insured(true)
    .build();  // trackingNumber and signatureRequired default sensibly, no positional guessing

Builder is most valuable exactly when a class has several optional constructor parameters with sensible defaults — it turns an error-prone positional call into a readable, self-validating sequence, and lets the class remain immutable (all fields set once, at build(), rather than via mutable setters scattered through calling code).

7. Structural Patterns: Composing Existing Interfaces

Adapter

Adapter solves a narrow, specific problem: you have a class whose interface doesn't match what your code expects, and you cannot (or should not) modify that class — it's a third-party library, a legacy class with other callers, or a class you don't own the source of. ShopSphere's payment-service hits this constantly: onboarding a new acquiring bank almost never means that bank's SDK happens to expose the exact PaymentGateway shape defined in section 2's OCP fix.

// Legacy bank gateway SDK you can't change — synchronous, SOAP-style, its own status enum:
class LegacyBankGatewaySdk {
    BankGatewayResponse submitPayment(String merchantAccount, long amountInCents, String currencyCode) { ... }
    // BankGatewayResponse.getStatusCode() returns "00" (success), "05" (declined), "96" (system error) - not our Payment.Status
}

// Your code expects this interface (defined in section 2's OCP fix):
interface PaymentGateway {
    Payment charge(Payment payment);
}

// Adapter bridges the mismatch without touching LegacyBankGatewaySdk:
class LegacyBankGatewayAdapter implements PaymentGateway {
    private final LegacyBankGatewaySdk legacySdk = new LegacyBankGatewaySdk();

    public Payment charge(Payment payment) {
        BankGatewayResponse resp = legacySdk.submitPayment(
            MERCHANT_ACCOUNT, payment.getAmountInCents(), payment.getCurrencyCode());
        return payment.withStatus(translateStatus(resp.getStatusCode())); // "00" -> CAPTURED, "05"/"96" -> FAILED
    }
}

The signal that you need Adapter, specifically, is "the shapes are incompatible but the underlying capability is the same" — the legacy SDK genuinely can charge a card, it just speaks in merchant accounts, cents-as-long, and two-digit status codes instead of ShopSphere's Payment domain object and Payment.Status enum. Contrast this with Decorator below, where the interface already matches and you're adding behavior, not translating it. Making sure the same Payment is never double-charged if submitPayment's response is lost after the call actually succeeded is a distinct concern the adapter itself doesn't solve — see Payment Systems & Idempotent Transactions for how an idempotencyKey on Payment makes retries safe.

Decorator

Decorator attaches new behavior to an individual object at runtime, wrapping it behind the same interface, as an alternative to a combinatorial explosion of subclasses. If ShopSphere needed a StripeGateway, a RetryingStripeGateway, a LoggingStripeGateway, and a RetryingLoggingStripeGateway — one subclass per combination of cross-cutting concerns — every new concern (metrics, circuit-breaking) would double the number of subclasses again. Decorator instead lets you compose independent wrappers at construction time, each implementing the same PaymentGateway interface from section 2 as the gateway it wraps:

class RetryingPaymentGateway implements PaymentGateway {
    private final PaymentGateway wrapped;
    RetryingPaymentGateway(PaymentGateway wrapped) { this.wrapped = wrapped; }
    public Payment charge(Payment payment) {
        for (int attempt = 1; attempt <= 3; attempt++) {
            try {
                return wrapped.charge(payment); // same idempotencyKey every attempt — safe to retry
            } catch (TransientGatewayException e) {
                if (attempt == 3) throw e;
            }
        }
        throw new IllegalStateException("unreachable");
    }
}

class LoggingPaymentGateway implements PaymentGateway {
    private final PaymentGateway wrapped;
    LoggingPaymentGateway(PaymentGateway wrapped) { this.wrapped = wrapped; }
    public Payment charge(Payment payment) {
        log.info("charging payment {}", payment.getIdempotencyKey());
        Payment result = wrapped.charge(payment);
        log.info("payment {} resulted in status {}", payment.getIdempotencyKey(), result.getStatus());
        return result;
    }
}

// Compose freely at the call site — no new class needed for this combination:
PaymentGateway gateway = new RetryingPaymentGateway(new LoggingPaymentGateway(new StripeGateway()));

Each decorator implements the exact same PaymentGateway interface as the object it wraps, so ShopSpherePaymentProcessor.process from section 2 can't tell — and doesn't need to know — whether it was handed a bare StripeGateway or three layers of decorators around one; it just calls gateway.charge(payment). This is precisely why the constructor chaining above looks nested rather than flat — you're stacking decorators, not calling a single constructor with many arguments. Java's own I/O library is the canonical real-world instance of this same pattern: new BufferedReader(new InputStreamReader(new FileInputStream(file))) wraps a raw byte stream first with character-decoding behavior, then with buffering behavior, each layer implementing the same Reader/InputStream surface as the layer it wraps — structurally identical to stacking RetryingPaymentGateway and LoggingPaymentGateway around StripeGateway above.

8. Behavioral Patterns: Coordinating Runtime Interactions

Strategy

Strategy encapsulates a family of interchangeable algorithms behind one interface and lets the caller select (or be configured with) whichever implementation applies, without the caller's code branching on type. This is the direct mechanical implementation of the Open/Closed Principle described in section 2 — the PaymentGateway refactor earlier in this page is the Strategy pattern; OCP is the principle, Strategy is the reusable shape that satisfies it.

interface DiscountStrategy { double apply(double subtotal); }
class NoDiscount implements DiscountStrategy { public double apply(double subtotal) { return subtotal; } }
class PercentageDiscount implements DiscountStrategy {
    private final double pct;
    PercentageDiscount(double pct) { this.pct = pct; }
    public double apply(double subtotal) { return subtotal * (1 - pct); }
}
class CouponDiscount implements DiscountStrategy {
    private final Coupon coupon;   // e.g. code "FLASH25", percentOff=0.25, validUntil=...
    CouponDiscount(Coupon coupon) { this.coupon = coupon; }
    public double apply(double subtotal) {
        return coupon.isExpired() ? subtotal : subtotal * (1 - coupon.getPercentOff());
    }
}

class Cart {
    private DiscountStrategy strategy = new NoDiscount();   // swappable at runtime
    void applyCoupon(Coupon coupon) { this.strategy = new CouponDiscount(coupon); }
    double checkoutTotal(double subtotal) { return strategy.apply(subtotal); }
}

The signal for Strategy specifically (versus Factory) is that you're choosing behavior, potentially swapping it more than once during an object's lifetime (a customer can apply, then remove, then apply a different coupon before checking out), rather than choosing which concrete object to construct once. In Spring, this shows up constantly as multiple beans implementing one interface, injected as a List<DiscountStrategy> or selected via a @Qualifier.

Observer

Observer decouples a subject (the thing whose state changes) from the objects that need to react to those changes, so the subject never needs to know the concrete types — or even the number — of things watching it.

interface OrderListener { void onOrderPlaced(Order order); }

class OrderSubject {
    private final List<OrderListener> listeners = new ArrayList<>();
    void subscribe(OrderListener l) { listeners.add(l); }
    void placeOrder(Order order) {
        // ... persist order, set status CREATED ...
        for (OrderListener l : listeners) l.onOrderPlaced(order);  // subject doesn't know or care who's listening
    }
}

class EmailNotifier implements OrderListener {
    public void onOrderPlaced(Order order) { /* send order-confirmation email via notification-service */ }
}
class InventoryReserver implements OrderListener {
    public void onOrderPlaced(Order order) { /* reserve stock in inventory-service for each OrderItem */ }
}

Adding a new reaction to "order placed" (say, triggering a fraud check) means writing a new OrderListener and subscribing it — OrderSubject itself never changes, which is Observer and OCP reinforcing each other. This is the same shape underlying Java's own event listener interfaces (ActionListener, PropertyChangeListener), Spring's ApplicationEventPublisher/@EventListener mechanism, and — at a larger scale — the publish/subscribe model behind message brokers: in a microservices framing of ShopSphere, order-service doesn't call InventoryReserver or EmailNotifier directly at all — it publishes an OrderPlaced event onto a Kafka topic, and inventory-service and notification-service each consume it independently as their own consumer group. The "subject" is the topic, "listeners" are consumer groups that can be added or removed without order-service's code changing at all — the exact same decoupling Observer gives you in-process, just crossing a process boundary.

State

State lets an object change its behavior as its internal state changes, by giving each state its own class that implements a shared interface, rather than scattering if (status == X) checks across every method that needs to behave differently per state. The signal for State, specifically, is that you have an object whose set of legal operations and legal transitions genuinely differs by state — not just a value that happens to vary.

An Order's lifecycle is the canonical example: CREATED → PAID → SHIPPED → DELIVERED, with CANCELLED reachable from some but not all of those states.

          pay()          ship()          deliver()
CREATED --------> PAID --------> SHIPPED ----------> DELIVERED   (terminal)
   |                |
   | cancel()        | cancel()
   v                v
        CANCELLED   (terminal — unreachable once SHIPPED)

Modeling this with a raw enum field and conditionals scattered across OrderService means every new status or every new rule about which transitions are legal touches many unrelated methods:

// VIOLATION: transition legality logic scattered across the service, easy to get wrong per-method
class OrderService {
    void cancel(Order order) {
        if (order.getStatus() == OrderStatus.SHIPPED || order.getStatus() == OrderStatus.DELIVERED) {
            throw new IllegalStateException("Cannot cancel a shipped order");
        }
        order.setStatus(OrderStatus.CANCELLED);
    }
    void markPaid(Order order) {
        if (order.getStatus() != OrderStatus.CREATED) {
            throw new IllegalStateException("Only a CREATED order can be paid");
        }
        order.setStatus(OrderStatus.PAID);
    }
    // ... markShipped(), markDelivered() each re-implement their own ad hoc legality check
}
// FIX: each state is a class that knows its own legal transitions
interface OrderState {
    OrderState pay(Order order);
    OrderState ship(Order order);
    OrderState cancel(Order order);
    default OrderState deliver(Order order) { throw new IllegalStateException("Cannot deliver from " + this); }
}

class CreatedState implements OrderState {
    public OrderState pay(Order order) { order.setStatus(OrderStatus.PAID); return new PaidState(); }
    public OrderState ship(Order order) { throw new IllegalStateException("Cannot ship before payment"); }
    public OrderState cancel(Order order) { order.setStatus(OrderStatus.CANCELLED); return new CancelledState(); }
}
class PaidState implements OrderState {
    public OrderState pay(Order order) { throw new IllegalStateException("Already paid"); }
    public OrderState ship(Order order) { order.setStatus(OrderStatus.SHIPPED); return new ShippedState(); }
    public OrderState cancel(Order order) { order.setStatus(OrderStatus.CANCELLED); return new CancelledState(); }
}
class ShippedState implements OrderState {
    public OrderState pay(Order order) { throw new IllegalStateException("Already paid"); }
    public OrderState ship(Order order) { throw new IllegalStateException("Already shipped"); }
    public OrderState cancel(Order order) { throw new IllegalStateException("Cannot cancel after shipping"); }
    public OrderState deliver(Order order) { order.setStatus(OrderStatus.DELIVERED); return new DeliveredState(); }
}
// DeliveredState and CancelledState are terminal: every method throws, by inheriting the default or overriding similarly.

// Order delegates instead of branching:
class Order {
    private OrderState state = new CreatedState();
    void pay()    { this.state = state.pay(this); }
    void ship()   { this.state = state.ship(this); }
    void cancel() { this.state = state.cancel(this); }
}

Adding a new status (say, RETURN_REQUESTED) means writing one new OrderState implementation and deciding which existing states' transition methods should return it — no existing state class needs to change unless it should now also allow transitioning into the new state, which is Open/Closed reinforcing State exactly the way it reinforces Strategy. The legality of every transition also now lives in exactly one place per state, instead of being re-derived (and potentially re-derived inconsistently) in every service method that happens to touch Order.

State versus Strategy: same shape, different intent

Structurally, State and Strategy look identical — both are "an interface with a family of implementations, held as a field and delegated to." The difference is entirely about who changes the field and why. With Strategy, the caller explicitly picks a strategy from the outside based on its own criteria (a customer applies a specific coupon), and the strategy object itself never causes a change to some other strategy. With State, the current state object itself decides and returns the next state as a direct consequence of the operation performed on it (calling pay() is what causes the transition from CreatedState to PaidState) — the object's behavior is intrinsically tied to a lifecycle, and transitions are usually constrained (not every state can reach every other state), whereas Strategy implementations are typically freely interchangeable with no such constraint.

Patterns are named shapes, not goals

None of these patterns are things to apply for their own sake — each one is a named answer to a specific recurring problem shape (unknown-type-until-runtime, one-instance-needed, many-optional-fields, incompatible-interfaces, behavior-composition, algorithm-swapping, decoupled-reaction, lifecycle-constrained-behavior). The skill worth building is recognizing the problem shape in an unfamiliar codebase and reaching for the matching pattern — not memorizing UML diagrams.

Concepts Worth Being Able to Explain From First Principles

Why is "a class should do one thing" a bad restatement of the Single Responsibility Principle?
"One thing" is subjective and scales arbitrarily — a class that "parses a file" could be described as doing one thing, yet still mix parsing, validation, and error-formatting concerns that change for different reasons. The precise, actionable test is enumerating the distinct actors or business concerns that could independently trigger a change to the class. If a database schema change and a tax-rule change both require editing the same class, it has two responsibilities regardless of how you'd describe its "one thing" in English. This actor-based framing is also what makes SRP testable in code review: ask "who would ask for this change?" for every method, and group by answer.
Why exactly does Square extending Rectangle violate Liskov Substitution, when a square genuinely is a rectangle mathematically?
LSP is about behavioral contracts, not set-theoretic truth. Geometrically a square is a rectangle, but the Java Rectangle class as typically implemented carries an implicit contract that width and height can be set independently — code written against Rectangle reasonably assumes calling setWidth doesn't change height. A Square subclass must violate that independence to preserve its own invariant (equal sides), which means any caller relying on the supertype's contract gets wrong answers when handed a Square through a Rectangle reference. The fix isn't to "model reality correctly" — it's to recognize that mutable setters with an independence contract and a subtype with an equal-sides invariant are fundamentally incompatible, and to model both as immutable value types or siblings under a narrower interface instead.
What's the actual difference between Dependency Inversion and Dependency Injection?
Dependency Inversion is a design principle: high-level and low-level modules should both depend on an abstraction that the high-level module owns, rather than the high-level module naming a concrete low-level class directly. Dependency Injection is one mechanical technique for supplying an object with its collaborators from outside (via constructor, setter, or field) rather than having it construct them itself. You can do DI without DIP — for example, injecting a concrete MySqlOrderRepository directly into a constructor still satisfies "the object doesn't construct its own dependency," but the high-level class is still coupled to a concrete low-level implementation, so swapping databases still requires editing it. DIP is what makes DI worth doing; DI is just the plumbing.
Why does the initialization-on-demand holder idiom avoid explicit synchronization, and what guarantee is it relying on?
It relies on the JVM's class-initialization semantics defined in the Java Language Specification: a class is initialized at most once, initialization is guaranteed to complete before any thread can observe a static field of that class, and the JVM itself handles the necessary locking during that one-time initialization. By putting the singleton instance in a nested static holder class that isn't referenced anywhere except inside getInstance(), the JVM doesn't load or initialize Holder — and therefore doesn't construct INSTANCE — until the first call to getInstance(). Every subsequent access, from any thread, is a plain static field read with no lock, because the happens-before relationship from class initialization already guarantees visibility of the fully-constructed instance.
How can you tell whether a situation calls for Adapter versus Decorator, since both wrap another object behind an interface?
The distinguishing question is whether the interfaces already match. Adapter exists because the wrapped object's interface is incompatible with what the caller expects — the adapter's job is translation between two different shapes, and you typically use exactly one adapter per incompatible class, added once. Decorator exists when the interface already matches perfectly, and the goal is to layer additional behavior (buffering, encryption, compression, logging) onto an object transparently — decorators are designed to be stacked in arbitrary combinations, each one both implementing and wrapping the same interface. If you find yourself asking "how do I make this fit," it's Adapter; if you're asking "how do I add a capability without subclassing," it's Decorator.
Why is Strategy described as a mechanical implementation of the Open/Closed Principle, rather than just an unrelated pattern that happens to use interfaces?
Open/Closed says new behavior should be addable via new code, not edits to existing tested code, and that this is achieved through abstraction and polymorphism. Strategy is precisely that: it defines an interface for a family of algorithms, and adding a new algorithm means writing a new class implementing that interface — nothing about the interface, the caller that invokes it, or the other existing strategies needs to change. The two are not analogous, they are the same mechanism described at two levels: OCP is the principle (what property the design should have), Strategy is the reusable structural pattern that produces that property whenever the "different case" you're handling is a swappable algorithm rather than, say, a swappable object type (which would instead point you toward Factory Method).
Concretely, what goes wrong in production if a fat interface (violating Interface Segregation) is left unaddressed as a system grows?
Two compounding problems appear as more implementers and callers accumulate. First, implementers that can't meaningfully support every method end up throwing UnsupportedOperationException or returning silent no-ops, which turns compile-time type safety into a runtime landmine — code compiles cleanly against the interface but fails only when a specific method is actually invoked on a specific implementer. Second, every caller of the fat interface becomes coupled to methods it never calls: adding or changing a method signature anywhere on the interface forces recompilation and re-review of callers that only ever used a different, unrelated method, which slows down otherwise-unrelated changes and increases the blast radius of code review. Splitting into focused interfaces bounds both problems to only the callers and implementers that actually care about each capability.
State and Strategy have nearly identical class diagrams. What actually distinguishes when to reach for one versus the other?
Both are "an interface, a family of implementations, one held as a field and delegated to" — the UML diagrams genuinely look the same. The distinguishing question is who changes the field, and why. With Strategy, the object holding the field never changes it itself as a side effect of doing its work — some external caller picks a strategy based on its own criteria (a customer chooses to apply a specific coupon), and the strategies are normally freely interchangeable with no ordering constraint between them. With State, the current state object itself returns the next state as a direct, intrinsic consequence of the operation being performed — calling pay() on an Order in CreatedState is precisely what causes the transition to PaidState, and the transitions are constrained: you cannot jump from CreatedState to ShippedState directly. If the "different cases" you're modeling are freely swappable and chosen from outside, it's Strategy. If they represent stages of a lifecycle where the current stage dictates both behavior and which stages can come next, it's State.
Why does modeling Order status as a State-pattern class hierarchy scale better than a single enum field with scattered if-checks, once an Order gains more than two or three statuses?
With a raw enum plus conditionals, the rule "which transitions are legal from this status" is not stored anywhere as a single fact — it's implicitly re-derived, separately, inside every method that happens to touch the Order (cancel(), pay(), ship(), refund(), and any future method). Each of those re-derivations can drift out of sync with the others as the system evolves, which is exactly how a bug like "a DELIVERED order can still be cancelled because someone forgot to add that check to the newest method" gets introduced. Modeling each status as its own class implementing a shared OrderState interface consolidates that fact into exactly one place per state — CreatedState's methods are the single source of truth for everything that's legal from CREATED — so adding a new status or a new legal transition means writing or editing one class, not auditing every method that touches Order for a missed case. It's the same benefit Open/Closed and Strategy provide, applied specifically to lifecycle-shaped state rather than to swappable algorithms.
