HLD #3: Distributed Messaging / Notification Engine

Kafka Partitioning Delivery Guarantees Idempotency Dead Letter Queues Provider Abstraction Rate Limiting Retry Scheduling State Machines
Why this matters

A notification engine looks trivial — "text the customer when their order ships" — until you ask what happens when the SMS provider is down for four minutes during a flash sale, or when the same OrderShipped Kafka message gets redelivered and a customer gets the same "your order has shipped" text twice, or when a PaymentFailed and a PaymentCaptured event for the same order arrive at notification-service out of order and the customer sees a success push notification followed by a failure one. Every one of those is a design decision, not a bug you patch later, and getting them right is what separates a system that silently corrupts a customer's perception of their own order state from one that doesn't. This page builds the reasoning for each decision from first principles so you can defend it, not just recite it.

1. Why a Separate Notification Service Exists

The naive design has every ShopSphere service that needs to notify a customer or seller — order-service, payment-service, inventory-service — call an SMS, email, or push provider's API directly whenever something happens: order-service calls Twilio directly when an order ships, payment-service calls SendGrid directly when a card is declined. This works for a demo and fails in production for reasons that have nothing to do with notifications specifically and everything to do with what happens when you duplicate a cross-cutting concern across N services.

  • Rate limiting becomes impossible to enforce globally. If order-service, payment-service, and inventory-service can each independently decide to text a customer, no single service has visibility into how many messages that customer has received in the last hour. A shared notification-service is the only place a per-customer, per-channel rate limit (say, max 3 SMS per hour, max 10 push notifications per day) can actually be enforced, because it is the only component that sees every notification for that customer, regardless of which upstream service triggered it.
  • Template and content management is duplicated. Marketing wants to change the wording of the "your order is delayed" email without a code deploy in order-service. If templates live inside every producing service, that requires N deploys for one wording change. A shared service can expose templates as data (versioned, in a database or config store) so wording changes are operational, not code changes.
  • Provider abstraction and failover logic would otherwise live in every service. If Twilio is down, every service that calls Twilio directly needs its own fallback to a secondary SMS provider, its own circuit breaker, its own retry policy. Centralizing this means you write and operate that resilience logic exactly once.
  • The business operation must not be coupled to notification delivery. If order-service calls the SMS provider synchronously during checkout and that call takes 8 seconds or times out, the customer's checkout request is now blocked on an SMS gateway that has nothing to do with whether the order itself succeeded. This is the most important reason of all, and it drives the entire architecture below.
The dependency direction matters

The core architectural principle is: business-critical operations must never have a hard runtime dependency on notification delivery succeeding. A ShopSphere order can complete, be paid, and ship even if the "your order has shipped" SMS never sends. The reverse — notification delivery depending on order-service still being up to retry — is fine, and is in fact how retry works here.

2. Core Architecture: Events, Not Synchronous Calls

Given the constraint above, upstream ShopSphere services do not call notification-service's API and wait for a response. Instead, they publish a notification-intent event to a message broker — Kafka in this design — and move on immediately. This is the same event-driven decoupling covered in async messaging, applied to a concrete domain. The three concrete events driving this page's examples are the ones every ShopSphere customer actually experiences: OrderPlaced (checkout succeeded, order is CREATED), OrderShipped (order-service/inventory-service confirmed dispatch), and PaymentFailed (payment-service's card charge was declined).

order-service / payment-service        Kafka topic: notification-events        notification-service
     |                                          |                                       |
     | produce(OrderPlaced / OrderShipped /     |                                       |
     |         PaymentFailed) ----------------> |                                       |
     |   (fire-and-forget, async)               |  <---------------- poll/consume ----- |
     | <-- ack (partition, offset) -------------|                                       |
     |                                          |                                       |
  [checkout/shipping/payment flow returns       |                          [dispatch to email/SMS/push
   to the customer here, independent of         |                           provider, retry, DLQ, etc.]
   notification outcome]                        |

A notification-intent event carries everything notification-service needs to act without calling back into the originating service: a notification type (ORDER_PLACED, ORDER_SHIPPED, PAYMENT_FAILED), the customer ID, channel preference hints, template variables, and a unique event ID.

{
  "eventId": "evt_9f3a2b7c-...",       // used to build the idempotency key
  "customerId": "cust_48213",
  "type": "PAYMENT_FAILED",
  "occurredAt": "2026-08-24T09:15:03Z",
  "templateVars": { "orderId": "ORD-77213", "amount": "49.00" },
  "channelHint": ["SMS", "PUSH"]
}

This buys three things simultaneously: the producing service's latency is unaffected by notification-provider latency, a burst of events (a flash-sale spike producing thousands of OrderPlaced events in seconds) is absorbed by the broker instead of overwhelming the provider API, and notification-service can be scaled, deployed, and even taken down for maintenance independently of every service that triggers notifications.

Fire-and-forget still needs a delivery guarantee from the producer

"Async" does not mean "best effort and forget." The producer should still wait for the broker's acknowledgment (Kafka acks=all for a durability-sensitive event like a PaymentFailed notification) before considering its own write-then-publish sequence complete, typically via the transactional outbox pattern so the database write (e.g. order-service persisting Order.status = PAID) and the event publish are atomic. Otherwise a crash between committing the order and publishing the event silently drops the notification forever — decoupling doesn't remove the need for reliability, it just moves where you engineer it.

3. Partition-Key Design: Ordering Per Customer

Kafka guarantees ordering only within a partition, not across an entire topic. If you partition notification-events by, say, a round-robin or by event type, then a PaymentFailed event for customer 48213 and a PaymentCaptured event for the same customer (perhaps a retried card charge that succeeded seconds later) can land on different partitions, be consumed by different consumer-group members, and be processed in either order — including the wrong one, where the customer sees "your payment failed" arrive after they already saw "payment successful."

The fix is to choose customer ID as the partition key:

producer.send(new ProducerRecord<>(
    "notification-events",
    String.valueOf(customerId),   // partition key
    eventPayload
));

Kafka hashes the key to deterministically select a partition, so every event for a given customer always lands on the same partition, and a single partition is only ever consumed by one consumer within a consumer group at a time. That combination — same partition, single consumer — is what actually delivers per-customer ordering. It is not the partitioning alone; a partition being read by two threads out of order would break the guarantee just as badly, so the consumer-side processing for a given partition must also be strictly sequential (or if you parallelize downstream work, you must re-serialize by customer ID before dispatch).

Partition key choiceOrdering guaranteeConsequence for this domain
Random / round-robinNone across events for the same customerOut-of-order delivery notifications; unacceptable for status-transition messages like OrderPlaced → OrderShipped
Event typeOrdered within a type, not across typesDoesn't fix the PaymentFailed/PaymentCaptured interleaving since both are different types published by different producer instances of payment-service
Customer IDAll events for one customer strictly orderedCorrect choice; trade-off is potential hot partitions for very high-volume customers (e.g. a large B2B account placing bulk orders)
Hot partitions are the price of ordering

Keying by customer ID means a small number of very active customers (a bulk-ordering B2B account) can create a hot partition, since Kafka doesn't let you split a single key's traffic across partitions without breaking the ordering guarantee you just paid for. This is an accepted trade-off: you monitor per-partition consumer lag and, if genuinely necessary, apply a secondary bucketing key (e.g., customerId % N combined into a composite key) only for identified high-volume accounts where perfect ordering matters less than throughput.

4. Idempotency: The Central Correctness Concern

4.1 Delivery-guarantee taxonomy

Before talking about idempotency, it's worth being precise about what "delivery guarantee" even means, because the three options form a strict taxonomy and every messaging design (Kafka, SQS, RabbitMQ, a webhook retry system) sits at exactly one leaf of it for any given hop:

Message Delivery Guarantees
  |
  ├── At-most-once
  |     Send/consume, then immediately commit (offset advances) BEFORE processing
  |     completes. A crash after commit but before processing finishes means the
  |     message is gone forever. No duplicates, but silent loss is possible.
  |     -> Acceptable only for notifications where a missed one is truly harmless
  |        (a "you might like this product" marketing nudge, not an OrderShipped SMS).
  |
  ├── At-least-once   <-- Kafka consumer's default, and this page's baseline
  |     Process first, THEN commit the offset. A crash/rebalance between processing
  |     and committing causes the same message to be redelivered and reprocessed.
  |     No message is ever silently lost, but duplicates are a routine, expected event.
  |     -> This is what notification-service actually gets from Kafka; idempotency
  |        (section 4.2) is the mandatory countermeasure that makes duplicates safe.
  |
  └── Exactly-once
        Every message is processed, and processed exactly one time, no duplicates,
        no loss. Kafka provides this ONLY for Kafka-to-Kafka pipelines (consuming from
        one topic and producing to another) via idempotent producers + transactions,
        where both the consumed offset commit and the produced record are part of one
        atomic transaction. It CANNOT extend this guarantee to an external side effect
        like "call Twilio's API" or "call SendGrid's API," because that API call and the
        Kafka offset commit are two separate systems with no shared atomic transaction.
        -> This is why notification-service cannot simply "turn on exactly-once mode" —
           the moment a non-Kafka side effect enters the picture, the best achievable
           guarantee is at-least-once delivery plus application-level idempotency,
           which is functionally equivalent to exactly-once from the customer's
           point of view (they see one SMS) without requiring an impossible primitive.
"Exactly-once processing" is engineered, not provided

What notification-service actually achieves for the customer — one SMS, not zero, not two — is often loosely called "exactly-once," but it is not the same primitive as Kafka's internal exactly-once semantics. It's at-least-once delivery from Kafka, plus an idempotent consumer, which produces an outcome indistinguishable from true exactly-once as far as the external side effect (the SMS actually sent) is concerned. This distinction matters in an interview: claiming "we use exactly-once delivery" for a design that calls an external SMS provider is a red flag, because it's not achievable — the correct claim is "at-least-once delivery, made safe by an idempotent send."

4.2 At-least-once plus idempotency: the mechanism

Kafka consumers offer at-least-once delivery by default: a consumer processes a message, and only after processing commits its offset. If the process crashes, or the commit fails, or a consumer-group rebalance happens between processing and committing, the same message is redelivered and processed again by whichever consumer picks up that partition next. This is not an edge case — rebalances during rolling deploys happen constantly in a live system — so "the same notification event will occasionally be processed twice" is a guaranteed occurrence, not a rare one.

Without a countermeasure, this means a customer occasionally gets the same "your order has shipped" SMS twice. For that it's mildly annoying; for a "your card was charged $49.00" message it actively damages trust — it can look like a double charge even when payment-service only charged the card once. The fix is to make the send step idempotent, not to try to make delivery exactly-once (per the taxonomy above, Kafka does not offer exactly-once delivery to an external system like an SMS gateway — it only offers exactly-once processing within Kafka-to-Kafka pipelines using transactions).

The general procedure

  1. Derive a deterministic idempotency key from the event itself — not generated fresh on each processing attempt. A natural choice is the event ID from the producer (if the producer guarantees uniqueness per logical notification), or a composite like hash(customerId + notificationType + eventId).
  2. Before dispatching to the provider, check a durable store (a table or Redis with a long TTL) for that idempotency key.
  3. If the key is already present and marked "sent" or "in-flight," skip the dispatch — this is a duplicate delivery of a message you already handled.
  4. If the key is absent, atomically insert it (e.g., an INSERT ... ON CONFLICT DO NOTHING or a Redis SETNX) as a claim on doing the work, then dispatch to the provider, then update the record with the outcome.
  5. Commit the Kafka offset only after this whole sequence completes, so a crash mid-sequence causes redelivery — which is now safe, because the idempotency check will catch it.
// notification-service consuming an OrderShipped event for order ORD-77213
String idempotencyKey = event.getEventId() + ":" + event.getType();

boolean claimed = idempotencyStore.tryClaim(idempotencyKey, Duration.ofDays(7));
if (!claimed) {
    // Already processed (or currently being processed) — safe no-op.
    log.info("Duplicate notification event {} skipped", idempotencyKey);
    return;
}

try {
    DeliveryResult result = deliveryProvider.send(notification);
    idempotencyStore.markComplete(idempotencyKey, result);
} catch (Exception e) {
    idempotencyStore.markFailed(idempotencyKey);
    throw e; // let retry/backoff logic handle it
}
The claim must be atomic with respect to concurrent consumers

If two consumer instances briefly both hold the same partition during a rebalance (a real, if short-lived, possibility), a plain "check then insert" without atomicity is a race: both check, see nothing, and both send. The claim step must be a single atomic operation at the storage layer (a unique constraint, a conditional write, a Redis SET key val NX) — never a separate read followed by a separate write from the application.

5. Dead Letter Queues: Bounding Failure

Some notification events will fail to process no matter how many times you retry immediately — a malformed templateVars.orderId causes a rendering exception every time, or a provider returns a permanent rejection (invalid phone number format on file for a customer). If the consumer simply throws and refuses to commit the offset, it will re-consume and re-fail the same message forever, which stalls that partition and blocks every subsequent event for every customer hashed to it — a single bad OrderShipped message taking down shipping notifications for potentially thousands of unrelated ShopSphere customers.

The Dead Letter Queue pattern bounds this blast radius:

  1. Track a retry count for the message (either in a header the consumer increments and republishes with, or in an external store keyed by idempotency key).
  2. On failure, retry with exponential backoff — e.g., attempt again after 1s, then 5s, then 30s — rather than hammering a struggling provider immediately.
  3. After a bounded number of attempts (commonly 3–5), stop retrying inline. Publish the message, along with the failure reason and stack trace, to a separate notification-events-dlq topic, and commit the original offset so the partition is unblocked.
  4. The DLQ is monitored (alerting on non-zero depth, or depth growing past a threshold) and messages there are inspected and either manually reprocessed after a fix, or discarded if they represent genuinely invalid data.
@KafkaListener(topics = "notification-events")
public void onMessage(ConsumerRecord<String, NotificationEvent> record) {
    // record.value() is e.g. an OrderShipped event for order ORD-77213
    try {
        processWithRetry(record.value());
    } catch (NonRetryableException e) {
        dlqProducer.send("notification-events-dlq", record.key(), toDlqPayload(record, e));
    } catch (Exception e) {
        if (attemptCount(record) >= MAX_ATTEMPTS) {
            dlqProducer.send("notification-events-dlq", record.key(), toDlqPayload(record, e));
        } else {
            retryTopicProducer.send(delayTopicFor(attemptCount(record)), record.key(), record.value());
        }
    }
    // offset commit happens either way — the partition is never blocked
}
Retry topics vs. in-process retry loops

A common refinement is to implement the backoff using separate delayed retry topics (notification-events-retry-1s, -5s, -30s) rather than sleeping inside the consumer thread. Sleeping in the consumer blocks that thread from making progress on the rest of the partition and risks tripping max.poll.interval.ms (the maximum time Kafka allows between successive poll() calls before assuming the consumer is dead), which triggers a rebalance. Routing failed messages through dedicated retry topics with their own consumers keeps the main topic's consumer loop fast and non-blocking.

6. Delivery-Provider Abstraction and Fallback

Each channel needs a provider-agnostic interface so the rest of notification-service doesn't care whether SMS for a "your order has shipped" alert is currently going through Twilio or a backup vendor:

public interface NotificationProvider {
    DeliveryResult send(NotificationPayload payload);
    Channel channel(); // SMS, EMAIL, PUSH
}

public class PrimarySmsProvider implements NotificationProvider { /* Twilio */ }
public class SecondarySmsProvider implements NotificationProvider { /* Vonage */ }

Above this sits a dispatcher that tries the primary provider and falls back to a secondary if the primary is unavailable, using exactly the circuit breaker mechanics already established for any unreliable downstream dependency: the breaker trips open after a threshold of consecutive failures against the primary, requests are routed to the secondary while it's open, and the breaker periodically half-opens to test whether the primary has recovered.

public DeliveryResult sendSms(NotificationPayload payload) {
    if (circuitBreaker.isOpen("primary-sms")) {
        return secondaryProvider.send(payload);
    }
    try {
        DeliveryResult result = primaryProvider.send(payload);
        circuitBreaker.recordSuccess("primary-sms");
        return result;
    } catch (ProviderException e) {
        circuitBreaker.recordFailure("primary-sms");
        return secondaryProvider.send(payload); // fail over immediately, don't wait for the breaker
    }
}

Two details matter here that are easy to get wrong. First, failover on a single request failure should happen immediately for that request, independent of whether the breaker has tripped yet — the breaker's job is to stop future requests from hitting a provider that's known to be down, not to gate the current request's fallback. Second, cost and deliverability differ meaningfully between providers, so fallback should usually be logged and monitored distinctly, since silently routing all of ShopSphere's SMS traffic to a more expensive secondary provider for hours during a flash sale because nobody noticed the primary was down is its own kind of incident.

7. Customer Preferences and Rate Limiting

Before a notification is dispatched, two checks happen that have nothing to do with delivery mechanics and everything to do with respecting the customer (or seller):

  • Preference check. A preference record (per customer, per notification type, per channel) determines whether this notification should be sent at all, and on which channel. A customer who disabled marketing emails but not transactional emails needs the notification type checked against their specific opt-out — an OrderShipped email must still go out even if "promotional emails" is off, but a "flash sale starting soon" push must not.
  • Rate limiting. Independent of preference, a per-customer-per-channel rate limit caps volume — e.g., a token bucket with a capacity of 5 SMS per hour per customer, refilling continuously. This protects the customer from being flooded by a bug in an upstream service (an infinite retry loop in order-service that fires the same OrderPlaced event a thousand times) and protects ShopSphere from provider costs spiraling from a misbehaving producer.
if (!preferenceService.isEnabled(customerId, notification.getType(), channel)) {
    return DeliveryResult.skipped("customer preference");
}
if (!rateLimiter.tryAcquire(rateLimitKey(customerId, channel))) {
    return DeliveryResult.skipped("rate limited");
}

Rate limiting here is a good illustration of why this logic belongs in one shared place: it is only enforceable if every notification for a customer passes through the same limiter state, which is only guaranteed if there's a single service — notification-service — on the send path for order-service, payment-service, and every other producer alike.

8. Delivery-Status Tracking and Retry Scheduling

Each notification has a lifecycle that should be modeled explicitly as a state machine rather than as scattered boolean flags, because the transitions themselves carry the retry and monitoring logic:

QUEUED --> SENT --> DELIVERED
   |         |
   |         +--> FAILED (transient) --> retry with backoff --> SENT (next attempt)
   |         |
   |         +--> FAILED (permanent) --> DLQ, no further retry
   |
   +--> SKIPPED (preference / rate-limit)
StateMeaningTrigger for next transition
QUEUEDEvent consumed, preference/rate-limit checks passed, not yet dispatchedProvider call initiated
SENTProvider accepted the request (e.g., Twilio returned a message SID)Provider delivery callback/webhook, or timeout
DELIVEREDProvider confirmed receipt on the recipient's device/carrierTerminal state
FAILED (transient)Provider timeout, 5xx, or rate-limited responseScheduled retry with exponential backoff
FAILED (permanent)Invalid recipient, provider rejected the contentRouted to DLQ, no retry

This state is persisted (a notifications table keyed by notification ID, or the idempotency store extended to carry state) so that a support engineer can answer "did this customer actually receive their order-shipped SMS" without guessing, and so the scheduled-retry job has something concrete to query: "find all notifications in FAILED(transient) state whose next-retry-at timestamp has passed."

nextRetryAt = now + baseDelay * (2 ^ attemptNumber) + jitter
// attempt 1: ~2s, attempt 2: ~4s, attempt 3: ~8s, capped at e.g. 5 minutes

The jitter term matters as much as the exponential term: without it, a provider outage that fails a large batch of notifications simultaneously produces retry storms where every failed notification retries at exactly the same computed delay, hitting the recovering provider with another synchronized spike. Randomizing the delay by a small percentage spreads that retry traffic out.

Status tracking is also how you observe the system

The state machine doubles as the foundation for production observability: a dashboard tracking the count of notifications in each state over time surfaces a provider degradation (a spike in FAILED-transient) long before a user complaint does, and DLQ depth alarms catch systematic failures — a bad template deploy, a provider API contract change — within minutes instead of being discovered when someone notices a whole class of notifications silently stopped.

Concepts Worth Being Able to Explain From First Principles

What's the practical difference between at-most-once, at-least-once, and exactly-once delivery, and which one does ShopSphere's notification pipeline actually achieve end to end?
At-most-once commits the offset before (or without regard to) whether processing succeeded, so a crash between commit and completion silently drops the message — zero duplicates, but real loss is possible; this is only tolerable for notifications where losing one is harmless, like a "you might like this" recommendation nudge. At-least-once (Kafka's consumer default, and the baseline for this design) commits the offset only after processing completes, so a crash or rebalance between those two steps causes redelivery and reprocessing of the same message — no message is ever silently lost, but duplicates are routine. Exactly-once — every message processed exactly one time, no loss, no duplicates — is only achievable end to end within a pure Kafka-to-Kafka pipeline, using idempotent producers and transactions to atomically tie together a consumed offset and a produced record. The moment an external, non-transactional side effect enters the picture — calling Twilio, SendGrid, or APNs — there is no way to make that call and the Kafka offset commit part of one atomic operation, so true exactly-once delivery to an external system is not achievable. What ShopSphere's notification-service actually achieves is at-least-once delivery from Kafka plus an idempotent consumer (section 4), which produces an outcome — the customer sees exactly one "your order has shipped" SMS — that looks like exactly-once from the outside without requiring the impossible primitive.
Why does publishing to a queue instead of calling notification-service directly actually prevent notification failures from affecting the business operation?
Because the producing service's responsibility ends at a successful publish to the broker, which is a local, fast, and highly available operation compared to calling an external SMS/email/push provider. Order-service's checkout flow only needs Kafka to accept the write (with acks tuned for the durability you need); it never waits on Twilio, APNs, or SendGrid, whose latency and availability are outside its control. The failure mode shifts from "checkout is slow because SMS is slow" to "checkout is fine, and notification-service deals with SMS being slow using its own retry and backoff machinery," which is exactly where that concern belongs.
If Kafka only guarantees ordering within a partition, and you key by customer ID, can a single customer's notifications still ever be processed out of order?
Yes, if the consumer doesn't preserve that order downstream. Partitioning by customer ID guarantees all of a customer's events (say, their OrderPlaced followed by their PaymentFailed) arrive at the same consumer in produced order, but if that consumer hands off processing to a thread pool for parallel dispatch, two events for the same customer can finish (and dispatch) out of order even though they were read in order. To preserve ordering end to end, either process a partition's messages strictly sequentially, or if you parallelize, re-serialize per customer ID downstream (e.g., route to a per-customer in-memory queue or use a single-threaded executor keyed by customer ID) before actually sending.
Why is idempotency the consumer's responsibility rather than something Kafka can guarantee for you?
Kafka's exactly-once semantics apply only to Kafka-to-Kafka pipelines (producing to one topic based on consuming from another, using transactions and idempotent producers) — it has no way to make an external, non-transactional side effect like "call the Twilio API" exactly-once, because that API call and the Kafka offset commit are two separate systems that can't be committed atomically. The only way to get correct behavior is to make the side effect itself safe to repeat: check-then-claim a deterministic key before dispatching, so a duplicate delivery of the same event (say, a redelivered OrderShipped message) is detected and skipped rather than resulting in a duplicate SMS to the customer.
What specifically goes wrong if you retry a failing message inline, in a loop, instead of using a Dead Letter Queue?
A Kafka consumer only advances past a message by committing its offset, and it processes messages from a given partition in order. If a message keeps failing and the consumer refuses to commit until it succeeds, no later message in that partition can ever be processed — the consumer is stuck retrying the same poisoned message forever. Since a partition is keyed by customer ID here, that one bad message (a malformed templateVars.orderId, say) doesn't just fail for one customer; it halts notification delivery — order confirmations, shipping updates, payment failures — for every customer whose ID happens to hash to that partition, for as long as the bug persists. A DLQ, combined with committing the offset once the message is routed there, unblocks the partition immediately and confines the damage to the single bad message.
Why does failover to a secondary provider happen on the failing request itself, rather than waiting for the circuit breaker to trip?
The circuit breaker's purpose is to stop sending future requests to a provider once it's established (via a threshold of recent failures) that the provider is unhealthy — it protects against wasting time and resources on requests likely to fail, and gives the provider room to recover by cutting off traffic. It says nothing about what to do with the request that just failed. If you only failed over once the breaker trips, every request during the ramp-up to that threshold — including, say, a burst of PaymentFailed alerts during a flash sale — would still fail outright with no notification sent. Failing over immediately on a per-request basis handles the individual failure; the breaker is a separate, longer-horizon mechanism for deciding when to stop trying the primary at all.
Why add random jitter to an exponential backoff schedule instead of just doubling the delay each time?
Exponential backoff alone solves the problem of hammering a struggling dependency with immediate retries, but it doesn't solve synchronization: if a provider outage causes a thousand ShopSphere order-shipped notifications to fail at roughly the same moment (say, during a flash-sale spike), pure exponential backoff means all thousand compute the same delay and retry at the same moment again, and again, effectively turning into periodic synchronized traffic spikes against a system that's trying to recover. Adding a random jitter term to each computed delay spreads those retries out over a window instead of a point in time, so the aggregate retry traffic is smooth rather than spiky — which is often the difference between a provider recovering cleanly and being knocked back down by the retry wave itself.
Why does rate limiting have to live in the shared notification-service rather than in each upstream producing service?
A per-customer rate limit is only meaningful if it's checked against a single, shared count of everything sent to that customer. If order-service and a marketing campaign service each maintain their own independent rate-limit counters, a customer can receive the full quota from each service simultaneously — the limits don't compose, they just multiply. The only way to enforce "this customer gets at most 5 SMS per hour, period" is to have exactly one component sit on the send path for every notification to that customer and check a single shared counter (a token bucket keyed by customer and channel) before any dispatch happens, which is only achievable with a centralized notification-service.
