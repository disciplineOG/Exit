CI/CD & Deployment Strategies: Blue-Green, Canary, Feature Flags

CI vs CD Pipeline Design Rolling Deployment Blue-Green Canary Releases Feature Flags Expand-Contract Migrations
Why this matters

Most production incidents that get blamed on "a bad deploy" are actually failures in the deployment strategy, not the code — a schema change that isn't backward-compatible during a rolling rollout, a Blue-Green switch that forgets long-lived database connections pin clients to the old environment, or a canary that ships to 5% of traffic but is judged against metrics that take ten minutes to aggregate. Picture ShopSphere shipping a rewritten checkout flow in order-service — the exact same team that gets this wrong will pin the outage on "the new checkout code," when the actual root cause is that the rollout let a request from a customer whose browser tab is mid-checkout hit an old-version instance expecting a different response shape than what the new code returns. Understanding how these mechanisms actually route traffic and manage state lets you predict exactly which class of bug survives each strategy and design migrations that never require the deploy and the schema change to be atomic — because they never actually are.

0. The Deployment-Strategy Taxonomy

Before the detailed walkthroughs below, it helps to see all the strategies as answers to two separable questions: how does traffic get routed to old vs. new code during the transition (the deployment-strategy branch), and does a piece of already-deployed code even affect users yet (the feature-flag / release branch, which is orthogonal to all of the deployment strategies — you can combine a feature flag with any of them).

The two branches compose: ShopSphere's new checkout flow could be deployed via a rolling update (traffic-routing strategy) while also being gated behind a new-checkout-flow feature flag (release mechanism) — the rolling update controls which physical instances are running the new binary, and the flag independently controls which requests actually exercise the new code path once it's running everywhere. Shadow traffic is worth naming explicitly because it's the only strategy in this list with zero user-facing risk by construction: order-service-v2 receives a mirrored copy of real checkout requests, computes a real response, but that response is thrown away rather than returned to the customer's browser — useful for load-testing a rewritten pricing calculation against real traffic shapes before it's trusted to answer for real, but it can't validate anything that depends on the response actually reaching the user (it can't catch a bug in how the frontend renders the new response, for instance).

1. Continuous Integration, Delivery, and Deployment — precise distinctions

These three terms describe an increasing amount of trust placed in the automated pipeline, and conflating them (as marketing material routinely does) hides the actual engineering question, which is: how much of the release process is a human still gating, versus how much has been proven safe enough to automate?

Continuous Integration (CI)

CI is a practice about the codebase, not about releasing. It means every developer merges their changes into a shared trunk (or a short-lived branch that merges quickly) frequently — multiple times a day rather than in long-lived feature branches — and every merge automatically triggers a build and test run. The problem CI solves is integration cost: if ten developers each work in isolation for two weeks and then try to merge, the combined diff is enormous, conflicts are numerous, and nobody remembers why a particular line changed. Merging small diffs constantly and verifying each one immediately means integration problems are caught within minutes of being introduced, when the change causing them is still small and fresh in the author's mind.

Continuous Delivery

Continuous Delivery extends CI with the guarantee that every change that passes the pipeline produces an artifact that is deployable to production at any time — but a human still decides when to actually deploy it. The pipeline builds, tests, and packages automatically; a release manager or the on-call engineer clicks a button (or runs a command) to push a specific, already-verified artifact live. The trust boundary here is: the pipeline is trusted to produce something safe to ship, but the business decision of timing (avoid Friday afternoon, wait for a marketing announcement, batch several changes) is still manual.

Continuous Deployment

Continuous Deployment removes that manual gate entirely: every change that passes the automated pipeline is deployed to production automatically, with no human in the loop. This is a strictly stronger claim than Continuous Delivery — it requires trusting the pipeline's test suite, static analysis, and any canary/rollback automation enough that a human review step adds no real safety, only latency. Teams that reach this stage typically compensate for the removed manual gate with automated progressive rollout (canary analysis, automatic rollback on error-rate spikes) rather than dropping safety altogether — the gate moves from "a person looks at it" to "the system watches metrics and decides."

A common misreading

People often say "we do CI/CD" to mean nothing more than "we have a Jenkins job." The distinction that actually matters operationally is whether a human is a required step between a green pipeline and code running in production. If yes, you have Continuous Delivery at best. If a merge to trunk can reach production users within minutes with zero human click, you have Continuous Deployment — and that has real implications for how much you invest in automated progressive rollout and rollback, covered below.

2. Anatomy of a pipeline: ordering stages by cost and confidence

A pipeline is a sequence of gates, and each gate should be ordered so that the cheapest, fastest checks that catch the most common failures run first. The reason this ordering matters is feedback latency: if a trivial typo that would be caught by a linter in two seconds only gets caught after a twenty-minute integration test suite, every contributor who makes that mistake burns twenty minutes waiting for something a compiler or linter could have told them near-instantly. A well-ordered pipeline fails fast.

  1. Build / compile. Does the code even compile (or, for interpreted languages, does static parsing succeed)? This is seconds to low minutes and catches syntax and type errors before anything else runs.
  2. Static analysis / linting. Style violations, banned API usage, obvious null-safety issues, dependency vulnerability scans (e.g., a Software Composition Analysis step checking for known-CVE libraries). These tools run against source without executing anything, so they're cheap and can run in parallel with the build.
  3. Unit tests. Fast, isolated, no network or database — a suite of thousands of unit tests should complete in well under a few minutes. They catch logic errors in a single class or function in isolation.
  4. Integration tests. Slower — they spin up a real (or containerized) database, message broker, or call between services, so they take longer and are flakier. They validate that components actually cooperate correctly, which unit tests with mocks cannot guarantee. See testing-strategies for the deeper trade-offs between these test levels and where contract tests fit.
  5. Artifact packaging. Once tests pass, build the actual deployable unit — a container image, a JAR, a native package — and push it to an artifact registry with an immutable version tag. This artifact is what every later stage will reference; you never rebuild it from source again, because rebuilding risks a different result (a dependency resolving to a newer patch version, for instance) than what was tested.
  6. Deployment. The packaged, already-tested artifact is rolled out to an environment using one of the strategies in the next section, typically progressing through a staging or pre-production environment before production.
Why packaging must come after tests, not before

A subtle but important invariant: the artifact that gets deployed to production must be the exact same binary that was tested, not a fresh build from the same source. If your pipeline rebuilds the artifact separately for the deploy stage, you lose the guarantee that "what we tested is what we're shipping" — a dependency version could float, a non-deterministic build step could produce different bytecode, or a flag could differ between environments. Build once, test that one artifact, promote it unchanged through every environment.

3. Rolling deployment — the default, and its hidden requirement

A rolling deployment replaces old instances with new ones gradually: take one instance (or a small batch) out of the load balancer pool, terminate it, start an instance running the new version, wait for its health check to pass, add it back to the pool, then repeat for the next batch until all instances are on the new version. This is the default strategy in most orchestration systems — it's what Kubernetes does with a Deployment object's default RollingUpdate strategy, controlled by maxSurge (how many extra instances beyond the desired count can exist temporarily) and maxUnavailable (how many instances can be down at once).

Concretely, rolling out a new build of ShopSphere's order-service (say, 6 pods behind a load balancer) with maxSurge=1, maxUnavailable=0: Kubernetes starts 1 new pod (7 running momentarily), waits for its readiness probe to pass, routes traffic to it, then terminates 1 old pod (back to 6) — and repeats until all 6 are on the new version. At no point does capacity drop below 6, but for the several minutes this takes, some fraction of POST /api/orders/checkout requests are being served by the old binary and some by the new one, split purely by whichever pod the load balancer happened to route to.

Its appeal is that it requires no extra infrastructure: you don't need double the servers, just enough headroom to take one batch out of rotation at a time. The cost is the one non-obvious requirement it imposes: for the entire duration of the rollout, both the old and new version are simultaneously live and serving real traffic. If a checkout request built against the new checkout flow's response schema hits an old-version order-service pod behind a shared cache or a stale API contract, or if the new version writes an Order row shape the old version's read path can't parse, you get intermittent, load-balancer-dependent failures that are maddening to reproduce because they only occur on requests that happen to be routed to the "wrong" pod. This is why every change deployed via rolling strategy must be backward- and forward-compatible for the rollout window — the database schema, the message formats on any Kafka topic (OrderPlaced, PaymentCaptured), and any shared cache entries must all be readable by both the version being replaced and the version replacing it.

4. Blue-Green deployment — atomic cutover, doubled cost

Blue-Green deployment maintains two complete, independent production environments — call them Blue (currently live) and Green (idle, or being prepared). To deploy, you provision the new version fully into Green, run smoke tests against it directly (bypassing the main traffic router), and once you're confident it's healthy, you flip a router or load balancer configuration to send all traffic to Green atomically. Blue is left running, untouched, for some soak period.

For ShopSphere's order-service, this looks like: Green is a full second fleet running the rewritten checkout flow, wired to the same production database and the same Kafka cluster as Blue. You smoke-test Green directly — hit its internal load-balancer address, run a synthetic checkout end-to-end (add a test Product to a Cart, checkout, confirm an OrderPlaced event lands on Kafka) — without a single real customer request touching it yet. Once satisfied, you flip the router: every new incoming checkout request now hits Green's pods instead of Blue's, in one configuration change, not a gradual pod-by-pod replacement.

The mechanic that makes rollback effectively instant is that Blue never stopped running — rolling back is just flipping the router back to Blue, which takes as long as a DNS or load-balancer config change propagates (seconds, not the minutes a redeploy-and-restart would take). This is qualitatively different from rolling deployment's rollback, which requires re-rolling the previous version through every instance again.

The cost is that during the overlap window you are running (and paying for) two full copies of your production capacity. For a fleet of a few instances this is trivial; for a large fleet it's a real capacity and cost concern, which is why Blue-Green is more common for services with modest fleet sizes or for infrastructure where the "environment" is defined at a coarser grain (an entire cluster, a whole region) rather than per-instance.

The atomic cutover is a lie for stateful clients

"All traffic switches atomically" is true at the router level, but any client holding a long-lived connection — a persistent database connection pool, a WebSocket, a gRPC stream with keep-alive — may not immediately reconnect through the new route. A load balancer flip doesn't forcibly sever existing TCP connections unless you configure it to (or set a short keep-alive/max-connection-age). Concretely: if a ShopSphere customer's browser opened a WebSocket to Blue's order-service for live order-status updates right before the cutover, that connection keeps talking to Blue until it's explicitly closed or times out — if Green expects a new message field on that channel that Blue never sent, the customer's still-open connection to Blue just silently never sends it, which looks like the cutover "didn't work" for that one customer even though the router config is correct for every new connection. Plan explicit connection draining, not just a router flip.

5. Canary deployment — limiting blast radius instead of switching atomically

Canary deployment routes a small percentage of real production traffic — say 1% or 5% — to the new version while the rest continues to hit the old version, then compares metrics (error rate, p99 latency, CPU, business metrics like conversion rate) between the canary and the baseline. If the canary looks healthy, the percentage is increased in steps (5% → 25% → 50% → 100%); if it looks unhealthy, traffic is routed away from it and the rollout is aborted, with only a small fraction of users ever having been exposed to the bad version.

For the rewritten checkout flow, a canary rollout of order-service might route 5% of POST /api/orders/checkout requests to the new pods and watch, per-version: checkout error rate, p99 latency on the checkout endpoint, and a business metric like cart-abandonment rate immediately after starting checkout. If the canary's checkout error rate spikes — say, the new flow has a bug that fails to reserve Inventory correctly for orders with more than one OrderItem — you catch it after a few hundred real checkouts misbehave rather than after all of ShopSphere's traffic hits the bug during a full rollout.

The core difference from Blue-Green is the shape of the risk being managed. Blue-Green gives you fast rollback from a full cutover — everyone is exposed the instant you flip, but you can un-expose them quickly. Canary instead limits the blast radius of the initial exposure itself — only a small slice of traffic ever sees the new code before you've gathered evidence it's safe. These aren't mutually exclusive: many real pipelines run a canary phase first (to catch the errors that only show up under real production traffic patterns, not synthetic smoke tests) and then perform a Blue-Green-style or rolling cutover for the remaining bulk of traffic once the canary passes.

Canary analysis is only as good as the metrics it compares against — if you don't already have solid dashboards for error rate, latency percentiles, and saturation broken down per-version, you have no way to judge whether the canary is actually healthy, which is why this strategy is inseparable from the practices in observability-production. A canary rollout with no per-version metrics segmentation is really just a rolling deployment with extra steps and a false sense of safety.

Statistical significance at low traffic percentages

A subtlety worth internalizing: at 1% traffic on a moderately busy service, your canary might be handling only a few checkout requests per second. Comparing a raw error count between a canary pool of 50 checkout requests and a baseline pool of 5,000 is not a fair comparison — a single failed request in the canary (maybe an unrelated, pre-existing flaky Payment-provider timeout) is a 2% error rate, which might look alarming purely from small-sample noise, and could trigger an automatic rollback of a perfectly good new checkout flow. Real canary analysis tools (like Kayenta, used in Netflix's Spinnaker) use statistical comparison methods that account for sample size, not naive threshold checks, precisely because naive comparisons produce false aborts at low traffic percentages.

6. Feature flags — decoupling deployment from release

All the strategies above answer "how do we get new code running on production servers safely." Feature flags answer a different question entirely: "when does a piece of already-deployed code actually start affecting users." A feature flag is a runtime conditional, typically backed by an external configuration service (LaunchDarkly, Unleash, a simple database-backed flag table, or even a config file reloaded without restart) rather than a compiled-in constant. Here's ShopSphere's order-service deciding, per-request, whether a given checkout should use the rewritten flow:

@PostMapping("/api/orders/checkout")
public Order checkout(@RequestBody CheckoutRequest request, Authentication auth) {
    String customerId = ((ShopSphereUserPrincipal) auth.getPrincipal()).getCustomerId();

    if (featureFlags.isEnabled("new-checkout-flow", customerId)) {
        return newCheckoutService.process(request, customerId);   // rewritten flow
    } else {
        return legacyCheckoutService.process(request, customerId); // existing, battle-tested flow
    }
}

The code for newCheckoutService is deployed to every order-service instance the moment its containing build ships (via whichever strategy from sections 3-5 rolled it out) — but it is dormant, unreachable, until someone flips the flag, whether for 100% of customers, a specific percentage, or a named allow-list (ShopSphere employees testing internally, a beta cohort of customers, a specific high-value Seller's storefront). This is the crucial decoupling: deployment (code physically present and running on production hardware) and release (code actually affecting user-visible behavior) become two independent events, controlled by two different mechanisms and, often, two different teams — engineering controls when order-service gets redeployed, product management controls when and how fast new-checkout-flow ramps from 0% to 100% of customers.

This decoupling is what makes true Continuous Deployment tractable for features that take weeks to build. Instead of maintaining a long-lived feature branch for the checkout rewrite (reintroducing exactly the integration pain CI exists to avoid), the ShopSphere team merges incomplete newCheckoutService work to trunk continuously behind a flag that defaults to off. The half-built checkout flow ships to production dozens of times over its development — fully integrated with order-service's other code, exercised by the build/test pipeline, invisible to real customers — the entire time. When it's finally ready, "releasing" it is a configuration change (flip new-checkout-flow to 100%), not a deployment — which also means it can be turned back off instantly if it misbehaves in production, without any redeploy or rollback of code at all. This is also exactly where feature flags and canary/Blue-Green rollouts complement rather than duplicate each other: a canary rollout of a new order-service binary validates that the new code doesn't crash or leak memory; a feature-flag ramp of new-checkout-flow validates that the new checkout behavior doesn't hurt conversion — you can canary the binary to 100% of pods while still keeping the flag at 1% of customers, because deploying the code and releasing the behavior are genuinely separate axes.

Flags are a source of combinatorial complexity, not a free lunch

Every live flag doubles the number of code paths that can execute in production (flag on vs. off), and flags accumulate — an order-service with fifteen active flags theoretically has 2^15 possible behavioral combinations, though in practice most combinations are never actually tested. Stale flags left in "temporarily" long past their feature's full rollout are one of the most common sources of code that's dead in production practice but still live in source, silently rotting because nobody remembers which branch is actually exercised — a legacy-checkout-service left wired up two years after new-checkout-flow went to 100% is exactly this failure mode, quietly bloating the binary and confusing every future reader who doesn't know it's unreachable. Treat flag removal (deleting the old code path once a flag is permanently on) as a required, scheduled follow-up task, not an optional cleanup.

7. Database migrations: the part that isn't really solved by any deployment strategy above

Every strategy discussed so far assumes the application code can be swapped, split-traffic, or rolled back independently. A database schema cannot be treated the same way, because a schema migration and an application deployment are never truly atomic together — the migration runs against one shared database while application instances roll over one at a time (or, in Blue-Green, while both Blue and Green potentially point at the same database). There is always a window where old code, new code, old schema, or new schema coexist in some combination, and if any combination in that window is invalid, you have an outage regardless of how careful your deployment strategy is.

The pattern that resolves this is usually called expand-contract (also "parallel change"), and it works by breaking one logical schema change into multiple independently-safe deployments:

  1. Expand. Add the new column, table, or index in a way that is purely additive and backward-compatible — the old code, which doesn't know the new column exists, keeps working unmodified because nothing it depends on was removed or renamed. Example: adding a nullable shipping_address_v2 column to ShopSphere's orders table alongside the existing shipping_address, to support the new checkout flow's structured-address format.
  2. Migrate/dual-write. Deploy application code that writes to both the old and new shape simultaneously (or backfills the new column from the old one via a background job), while still reading from whichever shape is authoritative. This version of the code must tolerate the old schema, the new schema, and rows that exist in only one shape (written before vs. after this deploy), because rolling or canary deployment guarantees exactly that mix will exist transiently.
  3. Cut over reads. Once you're confident the new column/table is fully and correctly populated for all rows, deploy a version that reads from the new shape as authoritative, still writing to both for safety.
  4. Contract. Only in a later, separate deployment — after you're certain no running instance and no in-flight rollback path depends on the old shape anymore — drop the old column or table and stop dual-writing.
Worked example: reshaping order-service's shipping address under a rolling deployment

Suppose the new checkout flow needs a structured shipping_address_v2 (separate street/city/postal-code columns) instead of the legacy free-text shipping_address column on the orders table, and order-service deploys via rolling update with three pods. If you naively run ALTER TABLE orders ADD COLUMN shipping_address_v2 ... and deploy new checkout code that reads/writes only shipping_address_v2 at the same time, here's what actually happens: pod 1 is updated and restarted first while pods 2 and 3 are still running the old checkout code, which never wrote anything to shipping_address_v2 in the first place. The moment a customer's checkout request happens to land on pod 1 for an Order that was created by pod 2 or 3 moments earlier, pod 1 reads a null shipping_address_v2 and either fails validation or ships an order with no address — a real customer-facing bug caused not by broken logic in either version individually, but by the schema cutover and the pod rollout racing each other with no ordering guarantee between "which pod restarts first" and "which column is authoritative."

The expand-contract way: (1) add shipping_address_v2 as a new nullable column, deploy — old checkout code ignores it, nothing breaks. (2) deploy checkout code that writes to both shipping_address and shipping_address_v2 on every new order, and backfill existing Order rows in a background job — at this point every pod, old or new, mid-rollout or not, can still read shipping_address successfully. (3) once backfill is confirmed complete, deploy the new checkout flow reading from shipping_address_v2 exclusively (still dual-writing for one more cycle as a safety margin). (4) in a later deploy, stop writing to shipping_address and drop the column. Four deployments instead of one, but zero windows where any live pod can be running code incompatible with the schema it's querying.

8. Rollback strategy must be decided before you deploy, not during the incident

A rollback plan improvised in the middle of an active incident is a plan written by someone under stress, with an incomplete view of what state has already changed, trying to reason about second-order effects in real time — exactly the conditions under which people make mistakes. Deciding the rollback mechanism in advance, as part of the deployment plan itself, converts "what do we do now" into "execute the pre-agreed runbook," which is faster and safer precisely because no judgment calls are needed under pressure.

Concretely, planning rollback in advance means answering, before the deploy ships, questions like:

  • Is this deploy backward-compatible with the previous version's database expectations? If you followed expand-contract properly, rolling back the application code to the previous version should never require rolling back the schema too — the previous code never depended on the old shape being the only one present. If a rollback would require an accompanying schema rollback, you no longer have an instant rollback; you have a second migration, with all the same coexistence hazards as the forward migration.
  • What is the automatic trigger for rollback, if any? In canary rollouts, this usually means codifying "abort and roll back automatically if error rate exceeds baseline by X% for Y minutes" rather than relying on someone noticing a dashboard.
  • Does rolling back also require reverting a feature flag, independently of the code rollback? If a bug is actually in flagged-off code that got accidentally enabled — say, new-checkout-flow was ramped to 25% and is now double-charging a small fraction of customers because it doesn't check Payment.idempotencyKey correctly before retrying — the fix is flipping the flag back to 0%, not redeploying order-service. Flipping a flag propagates in seconds and requires no build pipeline at all; redeploying, even via the fastest available strategy, is strictly slower and riskier while a real bug is actively harming customers. This should be an explicit, separately-documented first response step, not something the on-call engineer has to reconstruct under pressure.
  • How long does the previous version's artifact remain available and deployable? If your artifact registry garbage-collects old container images after seven days, and you don't discover a regression until day ten, "roll back to the last known-good order-service image" requires rebuilding it from source, which reintroduces exactly the non-determinism risk that build-once/promote-everywhere was meant to avoid.

This is also where deployment strategy composes directly with resilience thinking more broadly — a rollback is really just a deliberate, controlled failover to a known-good state, and the same principles about limiting blast radius, having fast detection, and avoiding cascading failure covered in resilience-fault-tolerance apply to planning it.

Concepts Worth Being Able to Explain From First Principles

Why does Continuous Deployment require more investment in canary analysis and automated rollback than Continuous Delivery does?
In Continuous Delivery, a human decides when to deploy an already-verified artifact, and that human is implicitly a final safety check — they can hold off if something feels off, check recent changes, or coordinate timing around known-risky periods. Continuous Deployment removes that check entirely: the moment a change passes automated tests, it goes live with nobody looking at it first. Automated tests are good at catching logic errors against known scenarios, but they can't catch every failure mode that only appears under real production traffic patterns, real data distributions, or real infrastructure interactions. To compensate for removing the human gate, teams practicing Continuous Deployment push the safety check later, into production itself, via canary analysis (only expose a small fraction of real traffic first) and automated rollback (detect regressions in that small fraction and revert without waiting for a person). Without this, Continuous Deployment isn't actually safer than Continuous Delivery with a careless human clicking deploy immediately — it's just faster and blinder.
Why can't a rolling deployment simply be made "instant" by increasing maxSurge and reducing the batch count to one big batch?
Even if you replace every instance in a single batch (maxUnavailable equal to the whole fleet, or maxSurge large enough to stand up the entire new fleet before tearing down the old one), there is still a window — however short — where in-flight requests that started against an old instance are completing while new instances are already accepting new requests, and where any shared state (database rows, cache entries, messages already enqueued in the old format) was written under the old version's assumptions. Reducing the batch size to one changes the duration of version coexistence, not whether it exists. The only way to get a truly instant, non-overlapping cutover is to route all traffic to a separate, fully-provisioned environment atomically — which is exactly what Blue-Green does, at the cost of running two environments rather than reusing the same fleet.
If Blue-Green gives an instant rollback, why would anyone choose canary deployment instead?
Blue-Green's rollback is fast, but it doesn't limit how many users are affected before you notice the problem and decide to roll back — everyone hits Green the instant the switch flips. If the bug is subtle (a slow memory leak, an edge case that only 2% of requests trigger, a data-corruption bug that isn't visible until a batch job runs hours later), 100% of your users were exposed to it, and "fast rollback" doesn't undo requests that were already served incorrectly or data that was already written wrong. Canary deployment trades rollback speed for a smaller blast radius up front: even if detection is slow, only the small percentage of traffic routed to the canary was ever exposed, so the total harm is bounded from the start rather than bounded only after the fact. The two strategies optimize for different failure shapes — Blue-Green for "fix it fast once we notice," canary for "limit exposure even if we're slow to notice."
How does a feature flag differ from an environment variable or a config file setting checked at startup?
The defining property of a feature flag, as used in progressive delivery, is that it can change value at runtime without restarting or redeploying the process, and it can vary per-request based on attributes like user ID, account tier, or a randomized bucket — not just be a single global on/off value for the whole fleet. A startup-time environment variable requires a restart (and typically a coordinated one across the fleet) to change, which reintroduces exactly the deployment risk flags are meant to avoid, and it can't easily express "on for 10% of users" or "on for this specific beta cohort" without extra machinery. Flag systems like LaunchDarkly or Unleash maintain this targeting logic and push updates to running processes (via streaming or periodic polling), which is what lets a flag change propagate to the whole fleet in seconds without any deployment event at all.
Walk through why "add a column, deploy, migrate data, deploy again, drop the old column" needs to be four separate deployments rather than combined into fewer steps.
Each step exists to guarantee that every version of the application code that could possibly be running at any moment during a rollout is compatible with whatever schema shape the database currently has. If you combined the "add column" and "migrate data" steps, you'd have old code (which knows nothing about the new column) running concurrently with a backfill job that assumes the new column is the source of truth — any old instance still reading only the old column would see stale or partial data during the backfill window, and if the old code writes to only the old column and does not know to also update the new column, later dual-write logic wouldn't be present yet to keep them in sync. If you combined "cut over reads" and "drop old column," instances that are rolling back (or simply mid-rollout on a lagging batch) that still expect the old column to exist would break the instant it's dropped. Each deployment boundary exists specifically to make sure the previous deployment's assumptions have fully "landed" across the whole fleet before the next assumption is introduced — collapsing steps reintroduces exactly the race condition expand-contract is designed to eliminate.
Why is a rollback plan considered part of the deployment itself, rather than a separate incident-response concern?
Whether a rollback is actually safe and fast depends on decisions made at deploy time, not at incident time — by the time an incident is underway, it's too late to retroactively make a schema change backward-compatible or to make an artifact that was already garbage-collected reappear. If the deploy didn't follow expand-contract, rolling back the code might require also rolling back a migration, which has its own coexistence hazards and is not something you want to be improvising for the first time under pressure. Planning rollback in advance means the rollback path was already exercised in your head (or in a staging environment) with the same rigor as the forward path, so executing it during an actual incident is just following a pre-validated runbook rather than performing novel engineering under time pressure.
Why does canary analysis fundamentally depend on having good observability, rather than just being a routing configuration?
Routing a percentage of traffic to a new version is only half of what "canary" means — the other half is deciding, based on evidence, whether that traffic is healthy enough to proceed. That decision requires metrics broken down per-version (error rate, latency percentiles, saturation) with enough granularity and low enough delay that you can compare the canary pool against the baseline pool while the canary is still small and the blast radius is still limited. Without per-version metric segmentation, a canary deployment is just a routing rule with no actual analysis behind it — you're exposing a fraction of users to unverified code and calling it safe purely because the fraction is small, not because you've confirmed it's healthy. The quality of a canary process is bounded entirely by the quality of the observability feeding its analysis step.
Why are deployment strategies (rolling, Blue-Green, canary) and feature flags described as "orthogonal" rather than as competing options?
A deployment strategy answers "how does new code physically get onto production servers and start receiving traffic" — it's about binaries, pods, and routers. A feature flag answers a completely different question: "given that the new code is already running everywhere, does it actually execute for this particular request." These are genuinely independent axes because you can hold either one fixed while varying the other: you could roll out a new order-service binary to 100% of pods via a rolling update (deployment strategy fully complete) while the new-checkout-flow flag inside that binary is still at 1% of customers (release still barely started) — the binary is everywhere, but the behavior is almost nowhere. Conversely, you could canary a binary to only 5% of pods, and within that 5%, the flag could already be at 100% for a specific beta cohort. Conflating the two leads to a specific mistake: assuming that because a canary rollout "completed successfully" (the binary is healthy on all pods), the new behavior itself has been validated at scale — when in fact the flag might have kept the new behavior dormant for nearly all of that traffic the whole time, and the canary only ever exercised the old, unflagged code path.
