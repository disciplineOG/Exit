JVM Performance Profiling & Production Troubleshooting

Why this matters

JVM architecture and GC theory tell you what the heap, Metaspace, and collectors are and how they behave in principle; this page is about what you actually do at 2am when order-service's p99 checkout latency triples during a flash sale, or a pod starts getting OOM-killed every few hours. Reading a stack trace is not the same skill as reading a full thread dump under contention, and knowing GC theory is not the same skill as correlating an actual GC log against an actual latency graph to prove (or rule out) that GC caused a specific incident. These are the tools that turn "the service is slow" or "the service leaks memory" from a vague complaint into a specific, provable root cause — a deadlock between two synchronized blocks, a thread pool exhausted waiting on a slow payment-gateway call, an unbounded Product lookup cache that never evicts. Without them you're guessing and redeploying; with them you're looking directly at what every thread was doing, or which object graph is retaining the memory, at the exact moment things went wrong.

1. Thread Dumps: Seeing What Every Thread Is Actually Doing

A thread dump is a snapshot, captured at one instant, of every live thread in the JVM along with its current stack trace, its state (RUNNABLE, BLOCKED, WAITING, TIMED_WAITING), and — critically — which lock (if any) it currently holds or is waiting to acquire. It answers exactly one question, but answers it completely: at this instant, what is every thread in this process doing, and what is it blocked on? This is the first tool to reach for whenever a service appears to hang — requests stop completing, but the process is still alive, CPU usage may even be near zero, and nothing has crashed.

1.1 Taking a thread dump

# Attach by PID (the process must be a JVM you can signal/attach to)
jstack <pid> > threaddump.txt

# Equivalent, sent directly to a running process's stdout/log (Unix only)
kill -3 <pid>

# jcmd is the modern, unified alternative to jstack/jmap/jinfo as separate binaries
jcmd <pid> Thread.print > threaddump.txt

Take at least two or three dumps, a few seconds apart, rather than one. A single dump only proves a thread was blocked at that instant; it can't distinguish a permanent deadlock from a thread that happens to be mid-wait on something that resolves a moment later. If the same threads are stuck on the exact same lock across three consecutive dumps taken seconds apart, that's strong evidence of a genuine stall rather than an ordinary transient wait.

1.2 Reading thread state

StateMeaningShopSphere example

A pile of TIMED_WAITING threads is not automatically a bug — a pile of BLOCKED threads usually is

Seeing many threads in TIMED_WAITING on a socket read is completely normal for a healthy pool of HTTP client threads waiting on a slow downstream — that's just concurrency doing its job. What's diagnostic is the ratio: if every single request-handling thread in the pool is simultaneously TIMED_WAITING on the same downstream call with none left RUNNABLE to accept new work, the service has exhausted its pool waiting on someone else, which shows up to callers exactly like a hang even though no individual thread is doing anything wrong. A pile of threads genuinely BLOCKED on the same monitor, however, means something is holding a lock for far longer than expected — that's the shape of both a deadlock and an ordinary lock-contention bottleneck, and the dump's "waiting to lock" / "locked" annotations (section 1.3) tell you which.

1.3 Diagnosing a deadlock: two synchronized blocks in order-service

Suppose ShopSphere's order-service has two methods that each lock an Order and an Inventory record, but acquire them in opposite orders — a classic lock-ordering bug:

// Thread A path: cancelOrder() locks Order first, then Inventory
public void cancelOrder(Order order, Inventory inventory) {
    synchronized (order) {
        synchronized (inventory) {
            order.setStatus(OrderStatus.CANCELLED);
            inventory.release(order.getItems());
        }
    }
}

// Thread B path: adjustStock() locks Inventory first, then Order
public void adjustStock(Inventory inventory, Order order) {
    synchronized (inventory) {
        synchronized (order) {
            inventory.decrement(order.getItems());
            order.touchLastModified();
        }
    }
}

If Thread A locks order and is about to lock inventory at the exact moment Thread B locks inventory and is about to lock order, both threads now hold one lock the other needs and neither will ever release its own — a permanent deadlock. Neither thread crashes; both simply sit BLOCKED forever, and every request routed to either code path piles up behind them. This is precisely the failure mode a thread dump is built to expose, because the JVM itself detects cycles in monitor ownership among Java-level synchronized locks and prints them explicitly:

Found one Java-level deadlock:
=============================
"http-nio-8080-exec-3":
  waiting to lock monitor 0x00007f2b... (object 0x000000071a2b3c40, a com.shopsphere.order.Inventory),
  which is held by "http-nio-8080-exec-7"
  at com.shopsphere.order.OrderService.cancelOrder(OrderService.java:42)
  - locked <0x000000071a2b1d10> (a com.shopsphere.order.Order)

"http-nio-8080-exec-7":
  waiting to lock monitor 0x00007f2c... (object 0x000000071a2b1d10, a com.shopsphere.order.Order),
  which is held by "http-nio-8080-exec-3"
  at com.shopsphere.order.OrderService.adjustStock(OrderService.java:58)
  - locked <0x000000071a2b3c40> (a com.shopsphere.order.Inventory)

Found 1 deadlock.

The JVM literally names it "Found one Java-level deadlock" and shows the exact cycle: exec-3 waits on a lock exec-7 holds, and exec-7 waits on a lock exec-3 holds. There is nothing to guess here — the fix is purely structural: always acquire locks in the same global order everywhere in the codebase (e.g., always lock Order before Inventory, never the reverse), or, better, avoid holding two independent locks across a call at all by consolidating the operation behind a single lock or an atomic/optimistic update.

Not every hang is this kind of deadlock

The JVM's built-in deadlock detector only finds cycles among synchronized monitors (and, in newer JDKs, java.util.concurrent.locks.ReentrantLocks it can also inspect). It cannot detect a "deadlock" that instead involves, say, two threads each waiting on a CompletableFuture the other is supposed to complete, or a thread pool that's simply exhausted (section 1.4) — those don't print "Found one Java-level deadlock" at all, because no monitor cycle exists; they just look like every thread being stuck, and you have to read the actual stack frames to see what each thread is really waiting on.

1.4 Diagnosing thread-pool exhaustion: a slow payment gateway

A more common production hang than an actual deadlock: order-service's checkout endpoint calls out to an external payment gateway over HTTP, and that gateway starts responding slowly (or not at all) during an incident on its side. If every thread in the request-handling pool ends up blocked waiting on that one slow call, the pool has no threads left to accept new requests — new checkout attempts queue up and eventually time out, even though nothing has technically deadlocked. A thread dump taken during this makes the pattern obvious: many threads, same stack trace, same downstream call:

"http-nio-8080-exec-12" #47 TIMED_WAITING
  at java.net.SocketInputStream.socketRead0(Native Method)
  at java.net.SocketInputStream.read(SocketInputStream.java:...)
  at ...
  at com.shopsphere.payment.PaymentGatewayClient.charge(PaymentGatewayClient.java:31)
  at com.shopsphere.order.CheckoutService.processPayment(CheckoutService.java:88)
  at com.shopsphere.order.CheckoutController.checkout(CheckoutController.java:22)

"http-nio-8080-exec-13" #48 TIMED_WAITING
  at java.net.SocketInputStream.socketRead0(Native Method)
  ... (identical stack)

"http-nio-8080-exec-14" #49 TIMED_WAITING
  ... (identical stack — 40 more threads look exactly like this)

Seeing forty near-identical stacks, all parked in PaymentGatewayClient.charge, is the signature of pool exhaustion caused by one slow downstream dependency — not a bug in ShopSphere's own code, but a resilience gap in how it calls out to a dependency that can be slow. The fix isn't in the thread dump itself; it's applying timeouts, circuit breakers, and bulkheads so a slow payment-gateway call fails fast and releases the thread back to the pool instead of holding it indefinitely, and sizing the pool with enough headroom (or using a fully async/non-blocking HTTP client) that one dependency's slowness can't single-handedly starve every other request type sharing the same pool.

2. Heap Dumps: Finding What's Actually Retaining Memory

A heap dump is a complete snapshot of every live object on the heap at the moment it's taken — every object's fields, every reference between objects, and (depending on how it was captured) every GC root that's keeping each object reachable. Where a thread dump answers "what is every thread doing right now," a heap dump answers "what does memory actually contain right now, and what's holding onto it." This is the tool for a memory leak — a service whose heap usage climbs steadily and never comes back down even after a Full GC, eventually ending in an OutOfMemoryError or repeated pod restarts.

2.1 Taking a heap dump

# On demand, against a running process
jmap -dump:live,format=b,file=heap.hprof <pid>

# jcmd equivalent (preferred on modern JDKs)
jcmd <pid> GC.heap_dump heap.hprof

# Automatic capture at the exact moment an OutOfMemoryError is thrown —
# this is the single most valuable flag for production, because by the time
# you notice a leak and try to reproduce it live, the evidence is often gone
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps

The live qualifier in the jmap command triggers a full GC first and dumps only objects that survive it — objects genuinely reachable, not garbage waiting to be collected. This matters because without it, a heap dump is cluttered with dead objects the collector simply hasn't gotten around to yet, making the "what's actually leaking" signal much noisier. The cost is that forcing a full GC on a live production process pauses it — capturing a heap dump is inherently disruptive, which is exactly why HeapDumpOnOutOfMemoryError (capturing automatically, only at the moment of actual failure) is preferred over routinely taking manual dumps against a healthy, running process.

2.2 Reading a dump: the dominator tree and retained size

A raw heap dump is enormous — potentially millions of objects and references — so no one reads it as a flat list. Eclipse MAT (Memory Analyzer Tool) and similar tools (VisualVM, YourKit) organize it around two ideas that make the analysis tractable:

  • Shallow size — the memory an object itself occupies (its own fields), ignoring anything it points to. A HashMap instance's shallow size is small and roughly constant regardless of how many entries it holds, because the entries live in separate Node objects the map merely references.
  • Retained size — the total memory that would become garbage if this one object became unreachable, i.e. this object plus everything only reachable through it. A HashMap field holding a million cached Product objects has a tiny shallow size but an enormous retained size, because all million cached products are only reachable through that one map reference.

The dominator tree is the structure MAT builds to compute retained size efficiently: object A "dominates" object B if every path from any GC root to B necessarily passes through A — meaning A is genuinely responsible for keeping B alive, not merely one of several paths that happen to reach it. MAT's "Leak Suspects" report walks this tree looking for objects with disproportionately large retained size relative to the rest of the heap — that's almost always where a leak surfaces first, because a genuine leak is, by definition, one object graph that keeps growing and is never released.

2.3 A concrete ShopSphere leak: an unbounded Product lookup cache

Suppose a well-intentioned but incomplete optimization in ShopSphere's catalog-service adds an in-memory cache to avoid repeatedly hitting the database for frequently-viewed products:

// THE BUG: a plain static HashMap used as a cache, with no eviction policy at all
public class ProductLookupCache {
    private static final Map<String, Product> cache = new HashMap<>();

    public static Product get(String productId, Supplier<Product> loader) {
        return cache.computeIfAbsent(productId, id -> loader.get());
    }
}

Every distinct productId ever looked up — across the entire lifetime of the process, across every customer, every search, every catalog page view — gets inserted and never removed. In a catalog with millions of products and constant traffic churning through different ones, this map's retained size grows monotonically. A single Full GC reclaims nothing from it, because every entry is still strongly reachable from a live static field — static fields are one of the JVM's GC roots by definition, so anything transitively reachable from one is never eligible for collection regardless of how long ago it was last used.

2.4 What the dump actually shows

Loading the heap dump into MAT and running "Leak Suspects" surfaces exactly this shape: one object — ProductLookupCache.cache, a HashMap — with a retained size that dwarfs everything else on the heap, and a dominator-tree path straight from a GC root (the static field itself) down through every cached Product entry. The histogram view corroborates it independently: sorting all live instances by total retained size shows millions of live Product and HashMap$Node instances, far more than the number of products a reasonable working set should ever need cached at once.

Class Name                     | Shallow Heap | Retained Heap
--------------------------------|--------------|---------------
com.shopsphere.catalog.Product | 15,832,000   | 1,240,500,000   <- huge retained, obviously wrong
java.util.HashMap$Node         | 15,832,000   | 1,180,000,000
java.lang.String                | 8,120,400    | 60,200,000
...

The fix is not a bigger heap — that only delays the same OutOfMemoryError — it's giving the cache an actual eviction policy. Replacing the plain HashMap with a bounded structure (a LinkedHashMap-based LRU, or, in production, a purpose-built cache like Caffeine with a max size and/or a time-based expiry) caps retained size at a known ceiling regardless of how many distinct products are ever looked up over the process's lifetime — the cache trades a small amount of avoidable cache-miss cost for a heap footprint that stops growing.

Classic leak culprits worth recognizing by shape, not just this one example

Beyond an unbounded cache, the same "retained forever because still strongly reachable from a GC root" pattern recurs in a few other common shapes: listeners registered against a long-lived event bus (an OrderPlaced subscriber added per-request but never unregistered) that keep every subscribing object alive for the life of the bus; a ThreadLocal that stores per-request context but is never explicitly cleared, so a thread reused from a pool keeps referencing the previous request's data indefinitely (and, worse, the next request on that thread may silently read stale context); and inner classes or lambdas that implicitly capture an enclosing instance (this) longer than intended, keeping that whole outer object graph alive through a reference the code never explicitly wrote down.

2.5 Distinguishing a leak from a sizing problem

A heap dump alone can be ambiguous — a large heap could mean an actual leak, or it could just mean the working set is legitimately larger than the heap was sized for (more concurrent in-flight orders than expected, say). The way to tell them apart is to look at the trend across multiple GC cycles, not a single snapshot:

3. Low-Overhead Production Profiling: JFR and async-profiler

Thread dumps and heap dumps are point-in-time snapshots — excellent for "what's stuck right now" or "what's leaking right now," but useless for the question "which specific method is burning the most CPU across a five-minute window under real production load," because a snapshot only ever shows one instant. Answering that requires sampling the running process repeatedly over an interval and building up a statistical picture — which is exactly what a profiler does — but traditional instrumenting profilers (that rewrite bytecode to record every method entry/exit) add enough overhead that they distort the very behavior you're trying to measure, and are rarely safe to run against live production traffic at all.

3.1 Java Flight Recorder (JFR): built into the JVM

JFR is a profiling and event-recording framework shipped inside the JDK itself (OpenJDK 11+, and backported to 8u), designed from the start to run continuously in production with low enough overhead (typically low single-digit percent) that it's safe to leave on by default. It doesn't work by instrumenting bytecode; it hooks into the JVM's own internal event points — safepoints, allocation, GC pauses, lock contention, thread state transitions — and periodically samples stack traces from those points, writing everything into a compact binary .jfr file for later analysis.

# Start order-service with continuous JFR recording enabled from boot
java -XX:+FlightRecorder \
     -XX:StartFlightRecording=filename=recording.jfr,duration=60s,settings=profile \
     -jar order-service.jar

# Attach to an already-running process and start a recording without a restart
jcmd <pid> JFR.start duration=60s filename=recording.jfr

# Inspect a recording's contents from the command line
jfr print --events jdk.ExecutionSample recording.jfr

A JFR recording captures CPU-sample stack traces (which method was on top of the stack, sampled periodically), allocation events (which call sites are allocating the most, and how much — directly relevant to diagnosing the GC allocation-pressure story during a ShopSphere flash sale), lock contention events (which monitors threads spend the most time waiting to acquire — a lower-overhead, aggregate complement to the point-in-time view a thread dump gives), and GC pause events with their duration — all correlated by timestamp in one file, which is what makes it possible to answer questions like "during the exact five minutes checkout latency spiked, what was actually consuming CPU, and did GC pause frequency change at the same time." Tools like JDK Mission Control (JMC) open a .jfr file and render this as flame graphs, hot-method tables, and timeline views.

3.2 async-profiler: sampling that survives safepoint bias

async-profiler is a separate, widely-used open-source sampling profiler for the JVM, notable for using OS-level signal-based sampling (on Linux, via perf_events) rather than relying purely on JVM safepoints to take a stack sample. This matters because older, naive sampling approaches can only safely inspect a thread's stack when that thread happens to be at a JVM safepoint (a point where all thread state is in a consistent, inspectable condition) — and certain code paths reach safepoints far more often than others, which skews naive sampling toward over-representing whichever methods happen to hit safepoints frequently and under-representing tight loops that don't. This distortion is called safepoint bias. async-profiler's signal-based approach can sample a thread's native call stack at essentially any point in its execution, producing a much more accurate picture of where time is actually going, including inside JIT-compiled native code and even native (JNI) library calls that a purely JVM-level profiler can't see into at all.

# Attach to a running ShopSphere order-service process and capture a 30-second CPU flame graph
./profiler.sh -d 30 -e cpu -f checkout-cpu-flamegraph.html <pid>

# Allocation profiling: which call sites allocate the most during a flash sale
./profiler.sh -d 30 -e alloc -f checkout-alloc-flamegraph.html <pid>

The output is typically rendered as a flame graph — a horizontal stack of bars where each bar is a stack frame, width proportional to the fraction of samples in which that frame appeared, and stacking upward represents the call chain from caller (bottom) to callee (top). A wide, flat plateau near the top of a flame graph is the visual signature of a hot method — one where a large fraction of all samples land, meaning a disproportionate share of CPU time is spent there. For ShopSphere, a checkout-path CPU flame graph that shows an unexpectedly wide bar in, say, a coupon-discount recalculation method run on every cart item, on every checkout, is a direct, evidence-backed pointer at exactly which method to optimize — not a guess.

4. Correlating GC Logs With a Latency Spike

GC pauses are stop-the-world (or, for the young/concurrent phases of modern collectors, partially concurrent but still pause-inducing) events, and every pause is real, measurable latency added to whatever request happened to be in flight when it occurred. Structured GC logging (-Xlog:gc*, per JVM tuning) records every collection with a timestamp, duration, and the before/after heap occupancy — which means a GC log is, itself, a time series that can be directly overlaid against an application latency graph to answer a very specific question: did a GC pause actually cause this particular latency spike, or was it something else?

4.1 What to line up

# A GC log line for a Young GC during a ShopSphere flash sale (G1, abbreviated)
[2026-08-25T14:32:07.481+0000][gc] GC(842) Pause Young (Normal) (G1 Evacuation Pause)
    Eden regions: 42->0 Survivor regions: 6->8 Old regions: 118->121
    12582912K->9823744K(16777216K) 41.203ms

# Roughly the same moment, in the request-latency dashboard
14:32:07.470  POST /api/checkout  -> 41ms slower than the surrounding baseline p99

The workflow is mechanical: take the timestamp of a latency spike from the application's own metrics/tracing (a checkout request whose duration is a clear outlier against its neighbors), and check the GC log for a pause whose timestamp overlaps that request's actual execution window. A 41ms Young GC pause starting at 14:32:07.481 lining up almost exactly with a checkout request that was in flight at 14:32:07.470 and finished 41ms slower than its neighbors is strong, specific evidence that this particular request's latency was caused by GC — not application code, not a downstream dependency, not network — because the extra time matches the pause duration almost exactly.

4.2 Distinguishing "GC caused this one spike" from "GC is a systemic problem"

  • One-off correlation: a single request happened to be executing exactly when a pause landed. This is expected background behavior for any collector — pauses happen, and a request unlucky enough to overlap one will show it. It's only actionable if pauses are frequent/long enough that a meaningful fraction of requests are affected, not just the unlucky few.
  • Systemic pattern: p99 (or worse, p50) latency is elevated across an entire time window, and the GC log for that same window shows either abnormally frequent Young GCs (allocation rate spiked, as in a flash sale — see the GC-theory page's allocation-pressure discussion) or Old-gen occupancy climbing pause over pause (premature promotion or an active leak, section 2.5). This is the signature that GC tuning, heap sizing, or an allocation hotspot (found via the allocation profiling in section 3) is the actual root cause, not an unlucky coincidence for one request.
A GC pause showing up in the log doesn't automatically mean GC is the bug

The correlation only has evidentiary value once you've confirmed the timestamps genuinely overlap the affected request's execution window, and — for a systemic claim — that the pattern repeats across many requests during the same window rather than being cherry-picked from one. A service can show plenty of ordinary Young GC activity throughout a healthy day with zero user-visible impact; the question is never "did any GC happen," it's "did a GC pause overlap specifically the request(s) whose latency you're trying to explain, and does that overlap actually account for the size of the observed spike."

5. A Practical Incident-Response Checklist

The order below is deliberate: cheapest and least-disruptive checks first, most disruptive (heap dumps, restarts) last, so a fast recovery path is never blocked on a slow diagnostic step.

  1. Confirm the symptom's shape first. Is the service completely unresponsive (hang — go to thread dumps), throwing OutOfMemoryError or steadily climbing in memory (leak — go to heap dumps), or just measurably slower under load with no hard failure (go to GC-log correlation and profiling)? Misidentifying which of these three shapes you're facing wastes the most time in an incident.
  2. Check dashboards and existing metrics before attaching anything new. CPU, heap occupancy, GC pause frequency/duration, and thread-pool queue depth (all things already instrumented via Micrometer/Actuator) often already show the shape of the problem — a saturated thread pool, a climbing Old-gen floor, a spike in Young GC frequency — without needing to attach a new tool to the live process at all.
  3. For a hang: take 2-3 thread dumps a few seconds apart (jstack/jcmd Thread.print). Look first for the JVM's own "Found one Java-level deadlock" block; if absent, look for many threads sharing an identical stack trace parked on the same downstream call (pool exhaustion, section 1.4) or BLOCKED on the same monitor (contention, not deadlock, but still a bottleneck).
  4. For a leak: capture a heap dump — ideally one was already captured automatically via HeapDumpOnOutOfMemoryError; if not, and the process is still alive and climbing, take one now (accepting the pause it causes) before restarting anything, because a restart destroys the exact evidence needed to diagnose it. Load it into MAT, run Leak Suspects, and confirm with a dominator-tree walk which single object graph is disproportionately large.
  5. For "slow but not broken": pull GC logs for the incident window and overlay against latency metrics (section 4) to rule GC in or out, and attach JFR or async-profiler for a short window (30-60 seconds is often enough) to get an evidence-backed CPU/allocation flame graph rather than guessing which method is hot.
  6. Mitigate before you finish root-causing, if there's a safe lever. Scaling out (more pods/instances) buys time for a leak or a load spike without losing the diagnostic evidence already captured; restarting the specific stuck process clears a hang once dumps are already safely saved; a feature flag or circuit breaker can shed load from a known-expensive path (e.g. temporarily disabling a non-critical coupon-recalculation feature during a flash sale) while the real fix is developed.
  7. Fix at the right layer, and write down what the evidence actually showed. A lock-ordering fix for a deadlock, a bounded cache for a leak, a circuit breaker for pool exhaustion, or a heap/GC tuning change for allocation pressure — each of section 1-4's failure modes has a distinct, specific fix, and the dump/log/profile you captured is the proof that you fixed the actual cause rather than a plausible-sounding guess.
Capture evidence before you restart

The single most common way an incident becomes permanently undiagnosable is restarting the affected process before capturing a thread or heap dump. A restart clears the symptom instantly, which is exactly why it's tempting under pressure — but it also destroys the one artifact that could have proven what actually happened. Automatic capture flags (-XX:+HeapDumpOnOutOfMemoryError, continuous JFR recording) exist specifically so this evidence is saved without requiring anyone to remember to capture it manually in the middle of an incident.

Concepts Worth Being Able to Explain From First Principles

Why does the JVM's built-in deadlock detector reliably find a Java-level deadlock in a thread dump, but not every kind of application "hang"?
The JVM tracks ownership of its own synchronized monitors (and, on modern JDKs, java.util.concurrent locks it can inspect) internally, so it can walk the graph of "thread X waits for a lock held by thread Y" edges and detect a cycle directly — that's a fully mechanical, guaranteed-correct check over a well-defined data structure the JVM itself maintains. A broader "hang," though, can arise from things that never touch a JVM monitor at all: two threads each waiting on a CompletableFuture the other side is supposed to complete, an exhausted thread pool with no threads left to make progress, or an external dependency that simply never responds. None of these produce a cycle in monitor ownership, so the deadlock detector has nothing to report — the dump will show every thread's exact stack and state regardless, but recognizing the problem in those cases requires a human to read the stacks and notice the pattern (e.g., many identical stacks parked on the same call), rather than the JVM handing you a pre-labeled diagnosis.
What is the practical difference between a thread's shallow state (BLOCKED vs WAITING vs TIMED_WAITING) and what actually matters when diagnosing a hang?
BLOCKED specifically means a thread is trying to enter a synchronized block/method and another thread currently holds that exact monitor — it is inherently about mutual exclusion contention. WAITING and TIMED_WAITING mean a thread has voluntarily parked itself (via Object.wait, Thread.join, LockSupport.park, or a bounded variant with a timeout) and is not competing for a lock at all; it's simply idle until something else wakes it. A single thread in any of these states proves nothing by itself — a thread pool having idle WAITING workers is completely healthy. What's diagnostic is the aggregate shape across the whole dump: many threads BLOCKED on the same monitor points at lock contention or a deadlock (check for a monitor-ownership cycle first); many threads TIMED_WAITING on the identical downstream call with zero threads left RUNNABLE to accept new work points at pool exhaustion caused by a slow dependency. The state name alone never tells you which one you're looking at — the pattern across all threads together does.
Why is "retained size" the number to look at in a heap dump rather than "shallow size," and what does the dominator tree actually compute?
Shallow size is just how many bytes an object's own fields occupy — for something like a HashMap instance, that's small and nearly constant no matter how many entries it holds, because the entries are separate Node objects the map merely references. It tells you almost nothing about where memory is actually going. Retained size is the total memory that would become garbage if that one object became unreachable — the object plus everything reachable only through it — which is the number that actually answers "how much memory is this thing responsible for." The dominator tree is the structure that makes computing this efficient and, more importantly, correctly attributable: object A dominates object B if every path from any GC root to B passes through A, meaning A is genuinely, not just incidentally, keeping B alive. Leak-detection tools rank objects by retained size computed over this tree specifically so a single, small-looking field (a static HashMap reference) can be correctly identified as responsible for gigabytes of retained memory, rather than that memory being invisibly spread across millions of individually small-looking Node and Product objects with no obvious common cause.
Why can a static field turn an ordinary cache into a permanent memory leak, when the exact same HashMap used as a local/instance field would just get garbage collected normally?
Garbage collection reclaims any object that is not transitively reachable from a GC root — a set of starting points the collector treats as inherently alive, which includes static fields, live thread stacks, and JNI references, among others. A HashMap held in a local variable becomes unreachable, and therefore eligible for collection, the moment the method that created it returns and nothing else references it. A HashMap assigned to a static field, however, is reachable for as long as its owning class remains loaded, which for a class like a cache utility is effectively the entire lifetime of the process — there is no natural point at which that static reference itself becomes unreachable. Every entry ever inserted into it is therefore transitively reachable from a permanent GC root, and a garbage collector's correctness guarantee (never collect something still reachable) means it will never reclaim any of those entries no matter how many Full GCs run, regardless of how stale or unused any individual entry has become. The fix is never about GC tuning — it's giving the structure itself a bounded size or a time-based eviction policy so old entries actually get removed and become unreachable on their own.
What does async-profiler's signal-based sampling actually fix compared to naive safepoint-based sampling, concretely?
A naive sampling profiler that relies on JVM safepoints can only inspect a thread's stack at moments when that thread has voluntarily reached a safepoint — a JVM-defined point where all thread state is in a consistent, inspectable condition, typically inserted at method-return boundaries, loop back-edges, and similar points by the JIT compiler. Some code reaches safepoints far more frequently than other code (a method with many loop iterations or frequent calls versus a tight, heavily-inlined numeric loop that the JIT compiled without frequent safepoint checks), so naive sampling systematically over-samples the former and under-samples the latter regardless of how much actual CPU time each consumes — this distortion is safepoint bias, and it can make a genuinely hot tight loop look cold in a flame graph simply because it rarely presents a safe moment to sample. async-profiler instead uses OS-level signal delivery (perf_events on Linux) to interrupt a thread and capture its native call stack at essentially any point in its execution, independent of safepoints, which removes this specific source of systematic distortion and additionally lets it see into JIT-compiled native code and JNI calls that a purely JVM-internal mechanism has no visibility into at all.
Given a GC log timestamp that overlaps a slow request's timestamp, what additional evidence turns "correlation" into an actually-justified causal claim?
Timestamp overlap alone is weak on its own, because GC pauses happen continuously in any running JVM and some request will always be executing during some pause purely by chance. Three things strengthen the claim from coincidence to causation: first, the magnitude should roughly match — if a request is 41ms slower than its neighbors and a 41ms GC pause occurred during its execution window, that specific match (not just "some pause happened sometime nearby") is what ties the extra latency to that particular pause rather than to some other cause. Second, for a systemic (not one-off) claim, the pattern needs to repeat across many affected requests within the same time window, not just the one example you happened to look at — a single coincidence proves nothing about a broader trend. Third, ruling out alternative explanations matters: checking that the same slow request didn't also coincide with, say, a downstream dependency's own slowdown, a thread-pool queuing delay, or a CPU spike from an unrelated process on the same host. Only once the magnitude lines up and the pattern is broad and other causes are checked and absent does the correlation actually support "GC caused this," rather than merely "GC happened to be running at the same time."
Why does the incident-response checklist insist on capturing evidence (dumps, JFR recordings) before restarting a stuck or leaking process, even under pressure to restore service quickly?
A thread dump and a heap dump are both snapshots of transient, in-memory state that exists only while the offending process is still running — the exact stack traces, lock-ownership graph, and live object graph that caused the incident. Restarting the process immediately and irreversibly discards all of that state; the new process starts clean, with no trace of whatever condition caused the original failure. This creates a specific, common failure mode: the symptom disappears (which feels like success), but the actual root cause is never identified, so nothing prevents the exact same failure from recurring under the same conditions later — often at the next traffic spike. Capturing a dump first costs a brief, bounded delay (and, for a heap dump, a real pause), but it preserves the only evidence that can turn "it happened again" into "we know precisely why, and we fixed the actual cause." This is precisely why automatic-capture flags like -XX:+HeapDumpOnOutOfMemoryError and continuous JFR recording exist — they remove the human decision entirely from the critical moment, so evidence is saved by default rather than depending on someone remembering to capture it while already under incident pressure.
