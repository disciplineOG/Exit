Reflection & Custom Annotations: How Spring Works Under the Hood

Reflection API Custom Annotations Retention Policy Annotation Processing Proxies Spring Internals
Why this matters

Every ShopSphere engineer eventually writes @Autowired private PaymentClient paymentClient; or slaps @Transactional on an OrderService.placeOrder() method without ever asking how a plain Java annotation — which by itself does absolutely nothing — ends up wiring a dependency or wrapping a database commit. The answer is not magic: it is the Reflection API reading metadata that annotations expose at runtime, combined with dynamic proxies that intercept method calls. Once you can trace that chain yourself, you stop treating Spring as a black box, you can explain why a self-invoked @Transactional call silently doesn't roll back, and you can build the same trick — a custom @LogExecutionTime annotation — in about twenty lines of code.

1. The Reflection API: Inspecting Code at Runtime

Reflection is the ability of a running Java program to examine and manipulate its own structure — classes, methods, fields, constructors, annotations — as data, rather than as compiled-in references the compiler resolved for you. Normally, when you write orderService.placeOrder(cart), the compiler binds that call to a specific method at compile time. With reflection, you instead ask the JVM at runtime: "give me the Class object for OrderService, list its methods, find one named placeOrder, and invoke it" — all as a sequence of object references and method calls on metadata, discovered dynamically. This is precisely the capability a generic framework like Spring needs: Spring's source code has never heard of OrderService, PaymentClient, or any other ShopSphere class, yet it needs to construct them, inject their dependencies, and wrap their methods. It can only do that by treating your classes as introspectable data.

Every class loaded by the JVM has exactly one corresponding java.lang.Class object, obtainable via OrderService.class, someInstance.getClass(), or Class.forName("com.shopsphere.order.OrderService") (the string-based form is what classpath scanning uses, since it discovers class names from .class files before ever holding an instance). From a Class object you can walk the entire structural picture of a type: its superclass and interfaces, its annotations, and — most importantly for a DI container — its constructors, methods, and fields, each represented by its own reflective object: Constructor, Method, and Field. Each of these exposes further metadata: a Method object can tell you its name, parameter types, return type, declared exceptions, and — critically — which annotations are present on it, via getAnnotation(Class) or getAnnotations().

1.1 getDeclaredFields vs getFields, getDeclaredMethods vs getMethods

The Reflection API draws a sharp, easy-to-forget distinction between "declared" and plain accessors, and it trips people up constantly. Class.getFields() and Class.getMethods() return only public members, but they include inherited ones — walk up the superclass chain, and any public field or method from a parent class shows up too. Class.getDeclaredFields() and Class.getDeclaredMethods() do the opposite trade: they return members of every visibility (public, protected, package-private, private) but only the ones declared directly on that class — nothing inherited. Neither method gives you "everything, regardless of visibility, including inherited members" in one call; if you need that, you have to walk the class hierarchy yourself, calling getDeclaredFields() on the class and then repeating it on getSuperclass() up to Object.

This distinction is exactly why Spring's field-injection processor can find and populate a private PaymentClient paymentClient field on OrderService: it calls getDeclaredFields() (not getFields()), because a private field would never show up in the public-only list. If Spring only used getFields(), @Autowired would only ever work on public fields — which would be a strange and leaky API to force on every Spring user. Instead, the injection machinery walks the declared fields of the bean's class (and its superclasses, since getDeclaredFields() doesn't recurse upward either) looking for the @Autowired annotation on each one.

1.2 setAccessible and the private-member problem

Finding a private field via getDeclaredFields() is only half the problem — the JVM's normal access-control checks still apply when you try to read or write it. Calling field.set(orderServiceInstance, paymentClientBean) on a private field throws IllegalAccessException unless you first call field.setAccessible(true), which tells the JVM to suppress Java language access checks for that specific reflective object. This is the mechanism that lets Spring set a private final-looking field from outside the class entirely, something that would be a compile error if you tried to write it as ordinary Java code anywhere outside OrderService itself.

setAccessible(true) is powerful and slightly dangerous: it is a deliberate escape hatch from encapsulation, and it is also the exact mechanism the Java Platform Module System (from Java 9 onward) restricts for classes in modules that haven't explicitly "opened" themselves for reflection — which is why some reflection-heavy libraries need --add-opens JVM flags when running on the module path. For ShopSphere's own code (unnamed module, classpath-based, the overwhelmingly common setup for a Spring Boot service), this friction rarely surfaces, but it's worth knowing it exists as a boundary reflection can hit.

1.3 The real performance cost of reflection

Reflective calls are slower than direct calls, and it's worth being precise about why, rather than just repeating "reflection is slow" as folklore. A direct method call like paymentClient.charge(order) can be inlined and optimized aggressively by the JIT (Just-In-Time compiler) — the JVM knows the exact target at the call site (or can speculate on it via inline caching) and can even eliminate the call entirely for small hot methods. A reflective call via method.invoke(paymentClient, order) goes through extra layers: argument arrays get boxed/unboxed and packed into an Object[], access checks may run on every call (unless bypassed via setAccessible), and — for a long time — the call went through a slower JNI-based (Java Native Interface) native invocation path before the JVM eventually generates a specialized bytecode accessor after enough invocations (a JIT-level optimization called inflation). None of this makes a single reflective call catastrophically slow in absolute terms — modern JVMs have narrowed the gap to roughly single-digit-nanoseconds-to-low-microseconds per call for warmed-up code — but it is measurably and consistently slower than a direct call, and the gap compounds when reflection sits inside a hot loop, such as reflectively reading every field of every OrderItem in a large order for every request.

Reflection cost is a startup-time cost, mostly

The practical lesson isn't "avoid reflection" — Spring's entire component model depends on it — it's "don't perform raw reflective lookups inside a per-request hot path." Frameworks solve this by doing the expensive reflective discovery (scanning for @Autowired fields, finding @Transactional methods) exactly once, at application startup or bean-creation time, and caching the resulting Field/Method objects so that runtime invocation reuses them instead of re-resolving them per call. Section 8 below covers this caching pattern directly.

2. Defining Custom Annotations: @interface, Retention, and Target

An annotation is declared with the @interface keyword, which despite looking like a normal interface declaration produces a distinct kind of type — one whose sole purpose is to attach structured metadata to code elements. A minimal custom annotation looks like this:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface LogExecutionTime {
    String value() default "";
}

The body can declare "elements" that look like abstract methods (String value() default "";) — these become the annotation's configurable attributes, usable as @LogExecutionTime("checkout-flow"). By itself, this declaration compiles, attaches to whatever it's placed on, and does absolutely nothing at runtime — an annotation has no behavior of its own. Whatever effect you associate with @LogExecutionTime or @Transactional comes entirely from a separate piece of code that reads the annotation reflectively and reacts to its presence. This single fact is the whole "Spring is not magic" thesis in one sentence: annotations are inert data, and frameworks are just code that goes looking for that data.

2.1 @Retention: SOURCE, CLASS, RUNTIME

@Retention controls how long an annotation survives past the point you wrote it, and picking the wrong one is a common way to accidentally build an annotation that "does nothing" for beginners writing their first custom annotation.

  • RetentionPolicy.SOURCE — the annotation is discarded by the compiler and never makes it into the .class bytecode at all. It exists purely for compile-time tooling: @Override and @SuppressWarnings use this, because their entire job is to let the compiler check something (does this method really override a superclass method? should this warning be suppressed?) and then vanish — there's nothing left to inspect once the class file exists.
  • RetentionPolicy.CLASS — the annotation is written into the compiled .class file's bytecode, but the JVM does not load it into memory as part of the runtime reflective model, so it is invisible to getAnnotation() calls at runtime. This is the default retention policy if you omit @Retention entirely, which is exactly why forgetting @Retention(RetentionPolicy.RUNTIME) is the single most common reason a hand-rolled annotation silently "does nothing" when read reflectively — the annotation is present in the class file, but Method.getAnnotation(MyAnnotation.class) returns null because the JVM never loaded it into its runtime-visible annotation table. Some bytecode-manipulation tools read CLASS-retained annotations directly from the class file without going through the JVM's reflective annotation API, but that's a different, much rarer mechanism than what Spring uses.
  • RetentionPolicy.RUNTIME — the annotation is retained in the class file and loaded by the JVM into an in-memory structure that reflection can query via getAnnotation()/getAnnotations()/isAnnotationPresent(). This is the only retention policy that makes an annotation discoverable at runtime, and it is why @Component, @Autowired, @Transactional, @RequestMapping, and effectively every Spring annotation you've ever used is declared with @Retention(RetentionPolicy.RUNTIME). Spring's entire component model is built on reflectively asking "does this class/field/method have annotation X on it?" at application startup and at bean-creation time — none of that is possible if the annotation didn't survive into the runtime reflective model.
Why not just make everything RUNTIME-retained?

There's a real, if small, cost: RUNTIME-retained annotations occupy extra space in the class file and take a small amount of extra time to load at class-loading time, and more importantly they leak an implementation detail (that this piece of metadata should be introspectable at runtime) into every consumer of the class file forever. SOURCE retention is the right choice whenever an annotation's entire job is finished by the time compilation ends, and reaching for RUNTIME by habit for annotations nobody will ever reflectively query is a minor but real form of unnecessary bloat.

2.2 @Target: constraining where an annotation can be applied

@Target restricts which kinds of program elements an annotation is legal on, using values from the ElementType enum: TYPE (classes/interfaces), METHOD, FIELD, PARAMETER, CONSTRUCTOR, ANNOTATION_TYPE (for meta-annotations, covered next), and a few others. @Component targets TYPE because it marks a whole class as a Spring-managed bean; @Autowired targets FIELD, METHOD, and CONSTRUCTOR because dependency injection can happen through any of those three channels; a custom @LogExecutionTime annotation intended to wrap method calls should target METHOD only — applying it to a field would be nonsensical (there's no "call" to time), and @Target lets the compiler reject that misuse at compile time rather than leaving it to a confusing runtime failure.

2.3 Meta-annotations: annotations that annotate annotations

A meta-annotation is simply an annotation applied to the declaration of another annotation — @Retention and @Target themselves are meta-annotations, since they annotate your @interface declaration. The more powerful use of the idea is composition: Spring lets you build a new annotation that is itself annotated with several existing Spring annotations, and — as long as the consuming code is written to look for meta-annotations, not just directly-present ones — using the new composed annotation behaves as if all of its constituent annotations were applied directly.

@SpringBootApplication is the canonical real example of this. It is not a special case the framework hardcodes; it's a plain annotation, declared roughly like this (simplified):

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@SpringBootConfiguration   // itself meta-annotated with @Configuration
@EnableAutoConfiguration
@ComponentScan(excludeFilters = { ... })
public @interface SpringBootApplication {
    // attributes that proxy through to the constituent annotations,
    // e.g. scanBasePackages(), exclude(), proxyBeanMethods()
}

When Spring processes a class annotated @SpringBootApplication, its annotation-metadata-reading code (built on Spring's own AnnotatedElementUtils, a reflection-based utility layered on top of the raw JDK Reflection API) doesn't just check "is @Component directly present here?" — it recursively walks the annotations on the annotations that are present, discovering that @SpringBootApplication is itself meta-annotated with @SpringBootConfiguration (which is meta-annotated with @Configuration, which is meta-annotated with @Component), @EnableAutoConfiguration, and @ComponentScan. This is exactly why one annotation on your ShopSphere OrderServiceApplication class simultaneously makes it a configuration class, a component-scan root, and an auto-configuration trigger — it's three (really more, once you follow the whole meta-annotation tree) separately meaningful annotations bundled behind one readable name, discovered by reflection walking annotation-of-annotation relationships, not by special-casing the string "SpringBootApplication" anywhere in Spring's source.

3. Component Scanning: Finding @Component Classes on the Classpath

Before Spring can instantiate a single bean, it has to find the candidate classes in the first place, and it does this without ever having a compile-time reference to OrderService, ProductRepository, or any other ShopSphere class. @ComponentScan (implied by @SpringBootApplication, rooted at the package of the main application class by default) works by walking the classpath as a directory/JAR structure — resolving package names to directory paths or JAR entries, listing every .class file found in and under the scan-root packages — without loading a single one of them as a full runtime Class object at this stage, because fully loading every class on the classpath just to check for an annotation would be needlessly slow and would trigger static initializers prematurely.

Instead, Spring uses ASM (a low-level Java bytecode-manipulation library) to peek at each .class file's bytecode directly, reading just enough of the class file format to answer "what annotations does this class carry, and with what retention?" without the overhead and side effects of full class loading. Only for the classes that pass this bytecode-level filter — the ones that actually carry @Component or one of its meta-annotated derivatives (@Service, @Repository, @Controller, @RestController — all meta-annotated with @Component, using the exact composition mechanism from section 2.3) — does Spring proceed to actually load the class via the JVM's classloader and build a full BeanDefinition for it. This is the reflection/bytecode-scanning combination that turns "every .class file under com.shopsphere" into "the specific set of classes that should become Spring beans," and it's why a plain POJO with no @Component-family annotation sitting in the same package is simply invisible to the container — it's still on the classpath, but component scanning never registers a BeanDefinition for it.

Once a class is selected, Spring does use full reflection on it — reading its declared constructors (to pick which one to call, and with what arguments, at bean-creation time), its declared fields and methods (to find @Autowired/@Value targets), and any class-level annotations relevant to scope, laziness, or proxying. Bytecode scanning is the cheap first-pass filter across potentially thousands of classes; full Class-object reflection is the more expensive, detailed introspection reserved for the much smaller set of classes that actually matter.

4. @Autowired: Dependency Injection as a Reflective Act

Once a bean's BeanDefinition exists, actually creating the object and wiring its dependencies is where reflection stops being a discovery mechanism and starts being a construction mechanism. The exact steps differ slightly for constructor injection versus field injection, and walking both makes the underlying machinery concrete.

4.1 Constructor injection

For a ShopSphere OrderService declared with a single constructor taking PaymentClient and InventoryClient, Spring's AutowiredAnnotationBeanPostProcessor (a specialized BeanPostProcessor that participates early, during instantiation rather than after it) inspects the class's declared constructors reflectively via getDeclaredConstructors(). If there's exactly one constructor, Spring treats it as the injection point automatically (no @Autowired needed on it since Spring Framework 4.3, as long as it's the sole constructor); with multiple constructors, one must be marked @Autowired to disambiguate. For each constructor parameter, Spring resolves a matching bean from the container by type (and by qualifier/name when there's ambiguity, e.g. two beans implementing PaymentClient), assembles the resolved dependencies into an Object[] array in parameter order, and calls constructor.newInstance(paymentClientBean, inventoryClientBean) — the reflective equivalent of new OrderService(paymentClientBean, inventoryClientBean), except the constructor being called was discovered as data, not written as source code anywhere in Spring's own codebase.

4.2 Field injection

For a field-injected dependency like @Autowired private PaymentClient paymentClient;, the sequence is exactly what section 1.1 and 1.2 described in the abstract, now applied concretely: Spring instantiates OrderService first (via its no-arg or otherwise-resolvable constructor), then walks the class's declared fields via getDeclaredFields(), finds the one carrying @Autowired, calls field.setAccessible(true) to get past the private access modifier, resolves a matching PaymentClient bean from the container, and calls field.set(orderServiceInstance, paymentClientBean) to push the value directly into memory, bypassing any constructor or setter entirely. This is also precisely why field injection makes plain (non-Spring) unit testing awkward — there is no ordinary Java syntax to populate that field from outside the class; you either need a running ApplicationContext, or you need to reach for the same reflective trick yourself (which is exactly what @Mock/@InjectMocks in Mockito do under the hood).

Field injection isn't slower at runtime — the cost is all at startup

It's tempting to assume field-injected beans pay a reflection tax on every method call because "reflection is involved." They don't: the reflective work (finding the field, calling setAccessible, calling set) happens exactly once, during that bean's creation at container startup. After that, orderService.paymentClient is read by ordinary, fully-optimized JVM field access for the rest of the bean's lifetime — the field, once set, is just a normal object reference. The real cost of field injection is a design cost (testability, hidden circular dependencies, as covered in the Spring Core Mechanics deep dive), not a runtime performance cost.

5. @Transactional and @Async: Dynamic Proxies Intercepting Method Calls

Reflection alone explains how Spring finds annotations and injects dependencies, but it does not explain how @Transactional makes a method run inside a database transaction, or how @Async makes a method run on a separate thread — because reflection can inspect and construct objects, but it has no built-in notion of "run some code before and after this specific method call." That's a different mechanism: dynamic proxies.

A proxy, in this context, is an object that implements the same type as a target object (the real OrderService) but sits in front of it, intercepting every method call before optionally delegating to the real object. When Spring's AnnotationAwareAspectJAutoProxyCreator (itself a BeanPostProcessor, running in the "after initialization" step of the bean lifecycle) notices that a bean has at least one method annotated @Transactional, @Async, @Cacheable, or matches any other AOP (Aspect-Oriented Programming) pointcut, it does not modify OrderService's bytecode or hand out the raw instance — it constructs a proxy object and registers that in the container instead. Every other bean that gets OrderService injected receives the proxy, indistinguishable from the real thing at the call-site level.

5.1 JDK dynamic proxies vs CGLIB proxies

Spring has to build this proxy using one of two fundamentally different mechanisms, and which one applies depends entirely on whether the target class implements an interface.

  • JDK dynamic proxies — built entirely from the standard library (java.lang.reflect.Proxy), and they can only proxy interfaces. Proxy.newProxyInstance() generates, at runtime, a new class that implements the given interface(s) and routes every method call through a single InvocationHandler.invoke(Object proxy, Method method, Object[] args) callback. If PaymentClient is an interface and StripePaymentClient is its implementation bean, Spring can build a JDK dynamic proxy that implements PaymentClient and wraps the real StripePaymentClient — but only calls made through the PaymentClient interface type are intercepted; this is reflection-adjacent machinery (it hands you a Method object per call, exactly like manual reflection would) rather than reflection itself.
  • CGLIB proxies (Code Generation Library, bundled with Spring) — used when the target class does not implement an interface, or when Spring is configured to always prefer class-based proxying. CGLIB generates an actual bytecode subclass of the target class at runtime (e.g., a generated subclass of a concrete OrderService class with no interface), overriding its public and protected methods to route through an interceptor before optionally calling super.placeOrder(cart) to invoke the real logic. Because it works by subclassing, CGLIB cannot proxy final classes or final methods — there's nothing to override — which is one of the more common "why isn't my @Transactional working" bugs in real codebases.

Spring Boot's default behavior (since Spring Boot 2.x) is to always use CGLIB-style class proxies, even for interface-implementing beans, because it makes proxying behavior consistent regardless of whether a class happens to implement an interface — but the two mechanisms remain conceptually distinct, and understanding both is what lets you reason correctly about a legacy or explicitly-configured (proxyTargetClass = false) codebase that still relies on interface-based JDK proxies.

5.2 What actually happens on a @Transactional call

Put the two mechanisms (reflection for discovery, proxies for interception) together and the full sequence for a call like orderService.placeOrder(cart) on a @Transactional-annotated method looks like this: the caller invokes a method on what it believes is OrderService, but is actually the proxy. The proxy's interceptor (a TransactionInterceptor in Spring's case) receives control first, and — using reflection — checks whether the target Method (or its declaring class) carries a @Transactional annotation via method.getAnnotation(Transactional.class). If it does, the interceptor opens a database transaction (or joins an existing one, depending on the configured propagation), reflectively invokes the real method on the underlying target object (method.invoke(realOrderService, cart), or the CGLIB-generated equivalent of a super call), and then commits the transaction if the method returns normally or rolls it back if it throws a runtime exception matching the configured rollback rules. If the annotation isn't present, the interceptor simply passes the call straight through with no transactional behavior at all. @Async follows the identical shape, except the interceptor submits the reflective invocation to a thread pool (an Executor) and returns immediately (or returns a Future/CompletableFuture) instead of wrapping the call in a transaction.

Why self-invocation breaks @Transactional

This mechanism explains a famously confusing bug directly: if OrderService.placeOrder() internally calls this.recordAuditLog(), and recordAuditLog() is separately annotated @Transactional, that inner transaction never actually starts. The call this.recordAuditLog() is a plain Java method call on the raw object — it never passes back through the proxy that wraps OrderService, because this refers to the real, unproxied instance, not the container-managed proxy the caller originally went through. Since the annotation is only ever checked by the proxy's interceptor, and this call bypasses the proxy entirely, the annotation is silently ignored. The fix is structural (move recordAuditLog() to a separate bean and call it through an injected reference, which does go through that bean's own proxy), not a Spring configuration flag — which is exactly why understanding "proxies only intercept calls that arrive through them" matters more than memorizing the symptom.

6. Worked Example: A Custom @LogExecutionTime Annotation

To make the mechanism fully concrete, here is a minimal, framework-free version of what Spring does, built from nothing but the annotation you already saw in section 2 and a hand-written reflective processor. First, the annotation itself:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface LogExecutionTime {
}

Applied to a method on a plain ShopSphere service class:

public class PricingService {

    @LogExecutionTime
    public BigDecimal calculateOrderTotal(Cart cart) {
        // sum line items, apply Coupon discounts, add tax
        return total;
    }

    public void refreshCatalogCache() {
        // not annotated -> not timed
    }
}

By itself, this does nothing at all — calling new PricingService().calculateOrderTotal(cart) directly runs the method with zero timing behavior, because (as section 2 emphasized) an annotation carries no code. The behavior comes entirely from a separate processor that uses reflection to find annotated methods and wrap their invocation:

public class TimingInvoker {

    public static Object invoke(Object target, String methodName, Object... args) throws Exception {
        Class<?> targetClass = target.getClass();
        Method method = findMethod(targetClass, methodName, args.length);

        if (method.isAnnotationPresent(LogExecutionTime.class)) {
            long start = System.nanoTime();
            method.setAccessible(true);
            try {
                return method.invoke(target, args);
            } finally {
                long elapsedMs = (System.nanoTime() - start) / 1_000_000;
                System.out.printf("%s.%s took %dms%n",
                        targetClass.getSimpleName(), methodName, elapsedMs);
            }
        }
        method.setAccessible(true);
        return method.invoke(target, args);
    }

    private static Method findMethod(Class<?> cls, String name, int paramCount) {
        for (Method m : cls.getDeclaredMethods()) {
            if (m.getName().equals(name) && m.getParameterCount() == paramCount) {
                return m;
            }
        }
        throw new NoSuchElementException(name);
    }
}

TimingInvoker.invoke(pricingService, "calculateOrderTotal", cart) now prints a timing line for that one method and does nothing extra for refreshCatalogCache, purely because of the reflective isAnnotationPresent check. This toy processor is deliberately doing by hand, in about fifteen lines, the same conceptual steps Spring's TransactionInterceptor performs: find the target method reflectively, check for an annotation, and conditionally wrap the reflective invocation with extra behavior. The only pieces missing to make this feel like real Spring are (a) a proxy so that ordinary-looking calls like pricingService.calculateOrderTotal(cart) get intercepted automatically instead of requiring an explicit TimingInvoker.invoke(...) call, and (b) a container that decides which classes get proxied in the first place — both of which are exactly what sections 3 through 5 already covered.

Turning this into a real Spring aspect

In an actual Spring application you would not hand-roll a TimingInvoker; you'd write a Spring AOP @Aspect with an @Around("@annotation(com.shopsphere.LogExecutionTime)") pointcut, and Spring's own proxying infrastructure (section 5) would apply it automatically to every @LogExecutionTime-annotated method on any Spring bean, with none of the manual findMethod plumbing. The point of building the manual version first is that once you've written it yourself, the @Aspect version stops looking like framework magic and starts looking like "the same idea, with the proxy-creation and method-discovery boilerplate handled for you."

7. Reflection at Scale: Caching, Cost, and When to Avoid It

A production Spring Boot application with a few hundred ShopSphere beans performs an enormous amount of reflective work — but almost all of it is front-loaded into application startup, not spread across request-handling. Component scanning inspects every classpath class once; BeanPostProcessors find every @Autowired field and @Transactional method once, per bean, at bean-creation time; proxy classes are generated once per proxied bean, not once per call. This is why a Spring Boot application's startup time (something ShopSphere engineers do notice, especially in local dev loops and in Kubernetes readiness-probe budgets) is dominated by reflective discovery and bean graph construction, while steady-state request handling barely touches raw reflection at all — it's calling ordinary Java methods on already-constructed proxies whose target methods were resolved long ago.

Frameworks lean hard on caching to keep this true. Spring internally caches resolved Method, Field, and Constructor objects (and the metadata derived from them, like which parameters need autowiring) per class, the first time a class is processed, rather than re-running getDeclaredFields()/getDeclaredMethods() and re-scanning for annotations on every single bean creation or every single method call. Once a Method object has been resolved and (if needed) made accessible via setAccessible(true), reusing that same object for repeated invocations is both correct and dramatically cheaper than re-resolving it — this caching is precisely what keeps reflection's cost concentrated at startup instead of leaking into every request.

The practical guidance for code you write yourself follows directly: it's entirely reasonable to use reflection for one-time setup work — reading configuration-driven metadata off a class, building a mapping of DTO fields to database columns once at application startup, implementing a plugin-discovery mechanism. It becomes a real problem when reflective lookups (Class.forName, getDeclaredMethod, annotation scanning) are performed fresh inside a hot path — for instance, inside the per-item loop that serializes every OrderItem in a large order for every checkout request. The fix is never "avoid reflection entirely" (frameworks like Jackson, Hibernate, and Spring itself would be impossible without it); it's "resolve once, cache the Method/Field reference, invoke many times" — the same pattern the frameworks themselves use internally.

Records and sealed types reduce, but don't eliminate, the need

Modern Java features like records give reflection-based frameworks more structured, predictable metadata to work with (a record's components are discoverable via getRecordComponents(), a purpose-built reflective API, rather than needing heuristics over fields and accessor-method naming conventions) — but they don't remove reflection from the picture; they make what reflection needs to inspect narrower and more mechanical, which is a meaningfully different claim from "frameworks no longer need reflection."

Concepts Worth Being Able to Explain From First Principles

Why does Method.getAnnotation() return null for a correctly-written custom annotation that compiles fine and is visibly present in the source code?
The overwhelmingly likely cause is a missing or wrong @Retention. If the annotation has no @Retention declared at all, it defaults to RetentionPolicy.CLASS, which means it's written into the compiled bytecode but never loaded into the JVM's runtime-visible annotation table — so reflective lookups like getAnnotation() correctly return null, even though the annotation is genuinely present if you were to inspect the raw class file. The fix is adding @Retention(RetentionPolicy.RUNTIME) to the annotation's own declaration, which is the only retention level the reflective annotation API can see at runtime.
Why does Spring's field-injection processor use getDeclaredFields() instead of getFields(), and what would break if it used getFields() instead?
getFields() only returns public members (including inherited ones), while getDeclaredFields() returns members declared directly on that class regardless of visibility, including private ones. Since @Autowired is overwhelmingly used on private fields in real code (@Autowired private PaymentClient paymentClient;), a processor using only getFields() would simply never find those fields, and dependency injection would silently fail to populate them, leaving them null. Using getDeclaredFields() plus setAccessible(true) is the only combination that lets a general-purpose framework populate a private field it has no compile-time relationship to.
Concretely, why does a self-invoked call to another @Transactional method on the same object not start a new transaction?
Spring's transactional behavior is implemented entirely by a proxy that wraps the bean; the transaction-checking logic lives in the proxy's interceptor, not inside the bean's own bytecode. When code inside OrderService calls this.someOtherMethod(), that call is an ordinary Java call resolved directly against the real, unproxied OrderService instance — it never passes through the proxy object that the container actually manages and that every other bean was given a reference to. Since the annotation is only ever inspected by the proxy's interceptor before delegating to the real object, and self-invocation never reaches the proxy, the annotation is invisible for that particular call, regardless of how correctly it's declared.
What is the actual difference between a JDK dynamic proxy and a CGLIB proxy, and which one does Spring pick for a concrete OrderService class with no interface?
A JDK dynamic proxy is built from java.lang.reflect.Proxy and can only implement interfaces — it generates a class that implements the target interface(s) and funnels every call through an InvocationHandler. A CGLIB proxy instead generates an actual bytecode subclass of the target class, overriding its methods to route through an interceptor before optionally calling the real (superclass) implementation. Since a concrete OrderService class with no interface has nothing for a JDK proxy to implement, Spring has no choice but to use CGLIB, generating a runtime subclass of OrderService itself — which is also why a final class or final method can't be proxied this way, since CGLIB relies on being able to override it.
What actually goes wrong, mechanically, if you forget @Retention(RUNTIME) on a hand-written annotation intended to be read by a custom AOP-style processor?
Without RUNTIME retention (defaulting instead to CLASS), the annotation is compiled into the class file but the JVM discards it before exposing runtime reflective metadata for the class, so any reflective check like method.isAnnotationPresent(LogExecutionTime.class) returns false unconditionally, for every method, even ones where the annotation is visibly present in the source. The processor doesn't throw an error or warn you — it simply behaves as though none of the target methods were ever annotated, which in practice looks like "my custom processor doesn't work" with no obvious diagnostic pointing at the retention policy as the cause.
How does @SpringBootApplication being a meta-annotation actually change what Spring's classpath scanning code has to do, compared to a framework that only checked for directly-present annotations?
If Spring only checked "is @Component directly present on this class," a class annotated only with @SpringBootApplication would never be recognized as a component, because @Component isn't written directly on it — it's written on @SpringBootConfiguration, which @SpringBootApplication is itself annotated with. Spring's annotation-metadata utilities are written to recursively search the meta-annotation tree: given a class, they inspect the annotations on it, and then the annotations on each of those annotations, and so on, until they find (or fail to find) the annotation they're actually looking for. This recursive walk is exactly what makes annotation composition useful in the first place — without it, meta-annotations would just be inert documentation rather than something the framework actually interprets.
Why is reflection's performance cost usually not a real problem in a typical Spring Boot request-handling path, even though the framework clearly uses reflection heavily?
Almost all of the expensive reflective work — classpath scanning, finding annotated fields and methods, resolving which constructor to call, generating proxy classes — happens exactly once per class, during application startup or the one-time creation of each singleton bean, and the resolved Method/Field/Constructor objects are cached rather than re-discovered. By the time the application is serving traffic, a proxied method call is invoking an already-resolved reflective handle (or, in many cases, a JIT-optimized generated accessor) rather than repeating discovery work, so the per-request cost looks much closer to a direct call than raw Method.invoke benchmarks in isolation would suggest. The real risk is application code that performs fresh reflective lookups — not reuse of already-resolved handles — inside a per-request hot path.
Why can't a custom ConstraintValidator or a plain reflection-based library autowire a Spring-managed dependency the same way a @Component can, unless something special is done?
Being discoverable by reflection and being managed by Spring's IoC container are two different things: a class only gets its dependencies injected if the container itself constructed it and ran its BeanPostProcessor pipeline (including the AutowiredAnnotationBeanPostProcessor) over it. An object instantiated by plain new SomeClass() or by a non-Spring-aware reflective mechanism (like the default Bean Validation instantiation strategy for ConstraintValidator) never passes through that pipeline, so any @Autowired fields on it are simply never populated — reflection alone doesn't retroactively wire a bean, it only lets Spring's own container code find and populate fields on objects it is actively constructing.
