Why this matters

Almost every confusing Hibernate bug — an update that silently didn't happen, a LazyInitializationException thrown in a view template, a service method that logs "saved" three times because of a hidden N+1 query, or a rollback that erased an audit log you thought was already committed — traces back to one of exactly four mechanisms: the persistence context's identity map, dirty checking, lazy proxy resolution, and transaction propagation boundaries. None of these are exotic; they are direct, load-bearing consequences of how Hibernate and Spring's transaction proxy work together. Once you can trace an entity's state and a transaction's boundary by hand, these bugs stop looking mysterious and start looking inevitable given the code that produced them.

1. The Persistence Context: Identity Map and First-Level Cache

A Session (Hibernate) or EntityManager (JPA — EntityManager is the JPA-standard interface; Hibernate's native Session extends it, so almost everything below applies to both names for the same object) is backed by a persistence context — a per-transaction (by default) in-memory map from entity identity (entity type + primary key) to a managed Java object. This is not a general-purpose cache in the sense of "reduce database load across requests"; it exists to guarantee a much stricter property: within one persistence context, there is exactly one Java object representing a given row.

Concretely: if you call entityManager.find(Order.class, 5L) twice inside the same transaction, the second call does not hit the database at all — it returns the exact same object reference as the first call, verifiable with ==. This is called the identity map pattern, and it exists to solve a real problem: without it, loading the same row twice would give you two different Java objects, and if you mutated both, whichever got flushed last would silently win, with no way to detect the conflict at the object-graph level. The identity map guarantees that "the same row" and "the same object" are the same statement anywhere within a transaction, which is what lets Hibernate track changes coherently.

Where Session/EntityManager sits: the object hierarchy

These names — SessionFactory, Session, EntityManagerFactory, EntityManager, persistence context — are frequently used loosely. They map onto a small, fixed hierarchy with very different lifetimes and cardinalities:

The practical consequence of this shape: a SessionFactory/EntityManagerFactory is safe to hold as a long-lived singleton bean and share across every thread in your application, but a Session/EntityManager it hands out is a short-lived, single-threaded, single-unit-of-work object — which is exactly why Spring wires one EntityManager per transaction behind the scenes rather than reusing one across requests. Trying to reuse a Session across threads (e.g. caching it as a field on a singleton @Service) is a correctness bug waiting to happen, since two threads would be silently sharing one identity map, one dirty-check snapshot set, and one pending-action queue.

What actually lives in the persistence context

  • The identity map itself (id → managed entity).
  • A snapshot of each managed entity's state as it was when loaded (or last flushed) — this is what dirty checking diffs against.
  • A list of pending actions (inserts, updates, deletes) that have not yet been written to the database.
First-level cache is not optional and not shareable

Unlike a second-level cache (e.g. Ehcache/Redis configured via @Cacheable), the first-level cache is always on, cannot be disabled, and is strictly scoped to one persistence context — it is never shared across threads or transactions. This is why it doesn't help with cross-request performance; its job is correctness (identity + change tracking) within a unit of work, not throughput.

2. Dirty Checking: How Hibernate Knows What to Write

You never call entity.save() on a managed entity to persist a field change. You mutate a setter, and at flush time Hibernate compares the entity's current field values against the snapshot it took when the entity became managed. Any field that differs gets included in an UPDATE statement — this comparison is called dirty checking.

This is why the following works without any explicit save call inside a @Transactional method:

@Transactional
public void renameCustomer(Long id, String newName) {
    Customer c = customerRepository.findById(id).orElseThrow();
    c.setName(newName); // no save() call
} // flush happens here, at commit

The same mechanism is what makes order-status transitions work without an explicit save:

@Transactional
public void markShipped(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.setStatus(OrderStatus.SHIPPED); // managed entity, mutated via setter
    // no repository.save(order) anywhere -- Hibernate detects the changed
    // 'status' field at flush time and issues UPDATE orders SET status = ? WHERE id = ?
}

findById returns a managed entity — one attached to the persistence context. Mutating it marks the context dirty for that entity. At transaction commit, Hibernate flushes: it walks every managed entity, diffs against its stored snapshot, and generates the necessary UPDATE for any entity whose fields changed. If you had instead called a query method that returns a DTO or a detached entity, this would not work — there'd be nothing to dirty-check.

Dirty checking cost scales with entity size and field count

The snapshot comparison is a field-by-field diff done in Java, not SQL. For entities with many columns or large embedded objects, this has a real, measurable cost when a persistence context holds thousands of managed entities (a common trap in batch jobs that load a huge list and mutate a few of them). This is one reason batch-processing code is usually written to periodically call entityManager.flush() followed by entityManager.clear() — clearing detaches everything and resets the persistence context so it doesn't grow unbounded.

3. Entity Lifecycle States

Every JPA entity instance is, at any moment, in exactly one of four states. The state determines what Hibernate will do with it and whether dirty checking applies at all.

StateMeaningHow it got thereTracked by persistence context?
TransientA plain Java object; Hibernate has never seen itnew Order()No
Managed / PersistentHas a persistence context tracking it; changes are dirty-checked and flushedpersist(), find()/getReferenceById(), result of a query, or merge()'s return valueYes
DetachedHas a database identity but is no longer tracked; mutations are silently ignored by HibernatePersistence context closed/cleared, or entityManager.detach(e)No
RemovedScheduled for deletion at next flush; still tracked until flush executesentityManager.remove(e) on a managed entityYes (until flushed)

The transitions, precisely

  • Transient → Managed: persist(entity). Assigns the entity to the persistence context; the INSERT is queued, not necessarily executed immediately (see write-behind, below).
  • Managed → Detached: happens implicitly when the persistence context ends (transaction commits and the EntityManager closes, in a typical Spring Data setup where each transaction gets its own context), or explicitly via detach()/clear().
  • Detached → Managed: never automatically. You must call merge(detachedEntity), which copies the detached entity's state onto a (possibly newly loaded) managed entity and returns that managed copy — the original detached object you passed in remains detached. Calling a setter on the original object after merge() does nothing.
  • Managed → Removed: remove(entity); the entity must be managed first (calling remove on a detached entity throws IllegalArgumentException, unless you re-attach via merge first).
The classic merge() mistake

A very common bug: loading an entity in one request, sending it to a client, receiving a modified version back, and then calling repository.save(modifiedEntity) on it. Spring Data's save() delegates to persist() for new entities and merge() for entities with a non-null id that JPA considers "existing." If the incoming object has fields you didn't intend to overwrite (e.g. a stale createdAt or an omitted collection), merge() will happily overwrite the persisted row's columns with whatever came in — there's no partial-update semantics here. This is why DTO-based updates (load the managed entity fresh, apply only the specific field changes) are usually safer than merging a whole detached graph from the wire.

4. The N+1 Query Problem

This is the most common Hibernate performance defect in production code, and it is a direct consequence of lazy loading combined with iteration.

@Entity
class Seller {
    @Id Long id;
    String businessName;

    @OneToMany(mappedBy = "seller", fetch = FetchType.LAZY)
    List<Product> products;
}

@Entity
class Product {
    @Id Long id;
    String name;
    BigDecimal price;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "seller_id")
    Seller seller;
}

List<Seller> sellers = sellerRepository.findAll(); // 1 query
for (Seller s : sellers) {
    System.out.println(s.getProducts().size()); // 1 query PER seller
}

findAll() issues one SELECT * FROM seller. Because products is LAZY, Hibernate populates each Seller with a proxy collection that has not been initialized. The moment you call .size() (or iterate it, or call any method that forces initialization), Hibernate issues a fresh SELECT * FROM product WHERE seller_id = ? for that one seller. With 50 sellers on an admin "sellers overview" dashboard, that's 1 + 50 = 51 queries — the "N+1." The failure mode is insidious precisely because it's invisible in unit tests with a handful of test sellers and only becomes a visible latency problem at production scale, where N is in the hundreds or thousands — e.g. an admin screen listing every seller alongside their live product count during a catalog audit.

The fixes, and their trade-offs

FixMechanismTrade-off
JOIN FETCHExplicit JPQL that eagerly loads the association in the same query, via a SQL join — e.g. SELECT s FROM Seller s JOIN FETCH s.productsFast, one round trip; but combining JOIN FETCH with pagination on the "many" side produces incorrect or memory-exploding results (Hibernate warns and, in some cases, paginates in memory) — don't paginate a query that fetch-joins a collection
@EntityGraphDeclarative annotation telling Spring Data which associations to eagerly fetch for a specific repository method, without hand-writing JPQL joinsCleaner and composable per-query, but under the hood still generates a join (or a secondary SELECT depending on the graph type), so the same pagination caveat can apply
Batch fetching (@BatchSize or hibernate.default_batch_fetch_size)Instead of one query per parent, Hibernate groups pending lazy initializations and issues one query per batch using WHERE seller_id IN (?, ?, ..., ?)Turns N+1 into roughly N/batchSize+1 queries; doesn't eliminate extra round trips entirely but drastically reduces them, and works fine with pagination since it doesn't change the shape of the original query
Picking between them

JOIN FETCH / @EntityGraph are best when you know, for a specific use case, that you always need the association and there's no pagination involved — e.g. rendering a single seller's full storefront with all products in one screen. Batch fetching is the pragmatic default for list-then-paginate screens where you sometimes need the association and can't safely fetch-join — e.g. a paginated admin sellers list where an expand-to-view-products interaction is optional. A DTO projection (see below) sidesteps the whole question by never loading the entity graph at all.

The same problem, one level deeper: Order → OrderItem → Product

N+1 compounds across chained associations. Loading a customer's order history and then, for each order, iterating its line items and then, for each line item, touching the referenced product is a textbook two-level N+1:

@Entity
class Order {
    @Id Long id;
    Long customerId;
    OrderStatus status;
    BigDecimal totalAmount;

    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY, cascade = CascadeType.ALL)
    List<OrderItem> items;
}

@Entity
class OrderItem {
    @Id Long id;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id")
    Order order;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_id")
    Product product;
    int quantity;
    BigDecimal unitPriceAtPurchase;
}

// order history screen: 1 (orders) + N (items per order) + M (product per item) queries
for (Order o : orderRepository.findByCustomerId(customerId)) {
    for (OrderItem item : o.getItems()) {        // N+1 #1: items per order
        System.out.println(item.getProduct().getName()); // N+1 #2: product per item
    }
}

The fix composes the same way the problem does — a single JPQL query can fetch-join both levels at once: SELECT DISTINCT o FROM Order o JOIN FETCH o.items i JOIN FETCH i.product WHERE o.customerId = :customerId (the DISTINCT matters here because a fetch join across a one-to-many produces one result row per OrderItem, which would otherwise duplicate the parent Order in the returned list once per item).

5. Lazy vs Eager Loading and LazyInitializationException

FetchType.LAZY defers loading an association until it's actually accessed; FetchType.EAGER loads it immediately as part of the owning entity's query (via a join or a secondary select). JPA's defaults are easy to get backwards from memory: @ManyToOne and @OneToOne default to EAGER; @OneToMany and @ManyToMany default to LAZY. In practice, almost everyone overrides the defaults to make every association LAZY explicitly, because eager loading composes badly: if Product eagerly loads its Seller, and Seller eagerly loads its full products list, fetching a single Product can silently pull in that seller's entire catalog, and that cost is invisible at the call site — nothing in productRepository.findById(id) tells you how much data is about to come back.

The cost of choosing LAZY everywhere is the risk of LazyInitializationException: Hibernate represents a lazy association with a proxy object (for @ManyToOne/@OneToOne) or a lazy-loading collection wrapper (for @OneToMany/@ManyToMany). That proxy holds a reference back to the Session that created it. If you try to access the association after that session has closed — which, in a typical Spring Data setup, happens right after your @Transactional method returns — there is no active session left to run the initialization query, and Hibernate throws rather than silently returning null or stale data.

@Transactional(readOnly = true)
public Seller getSeller(Long id) {
    return sellerRepository.findById(id).orElseThrow();
} // session closes here

// later, in a controller or view:
seller.getProducts().size(); // LazyInitializationException — no session

The standard fixes

  • Fetch joins: write the query to eagerly bring in exactly the associations the caller needs, scoped to that one use case (e.g. a "seller storefront" query that fetch-joins products), rather than changing the mapping's global fetch type.
  • DTO projections: query directly into a flat DTO (via JPQL constructor expressions, Spring Data projections, or a mapping library) so the controller/view never touches a managed entity or its proxies at all. This is generally the most robust fix because it also avoids over-fetching and decouples your API shape from your entity graph.
  • Open Session in View (OSIV): a servlet filter (enabled by default in Spring Boot via spring.jpa.open-in-view=true) that keeps the Hibernate session open for the entire HTTP request, not just the @Transactional method, so lazy associations can still be initialized while rendering a view.

Worked example: a product page's reviews

A product detail page needs Product plus its Reviews plus, for each review, the reviewing customer's display name — a case where a naive lazy-loaded entity graph and a DTO projection produce visibly different query counts for the exact same page:

@Entity
class Review {
    @Id Long id;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_id")
    Product product;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    Customer customer;
    int rating;
    String comment;
}

// naive: 1 (product) + 1 (reviews) + N (customer per review) if customer.getName() is touched
Product product = productRepository.findById(productId).orElseThrow();
for (Review r : product.getReviews()) {
    render(r.getRating(), r.getComment(), r.getCustomer().getName()); // N+1 on customer
}

// DTO projection: exactly one query, no proxies, no risk of LazyInitializationException later
interface ReviewSummary {
    int getRating();
    String getComment();
    String getCustomerName();
}

@Query("""
    select r.rating as rating, r.comment as comment, c.name as customerName
    from Review r join r.customer c
    where r.product.id = :productId
    """)
List<ReviewSummary> findSummariesByProductId(@Param("productId") Long productId);

The projection interface's getter names (getRating, getComment, getCustomerName) are matched by Spring Data against the query's column aliases — this is a closed projection: Spring Data generates a proxy implementing the interface backed directly by the query's result row, with no Product, Review, or Customer entity ever loaded into the persistence context at all. This is why DTO projections sidestep both N+1 and LazyInitializationException simultaneously — there's no lazy proxy to forget about, because there's no managed entity in the first place.

Why Open Session in View is controversial

OSIV makes the symptom disappear without fixing the cause: it hides N+1 problems by moving lazy-initialization queries out of your service layer and into whatever happens to touch the entity later (a JSON serializer, a template engine), where they're harder to see, profile, and reason about. It also holds a database connection checked out from the pool for the full duration of request processing — including view rendering and any slow downstream calls — which under load can exhaust the connection pool much faster than a design where connections are held only for the duration of the actual transaction. Spring Boot ships it enabled by default specifically for developer convenience, and logs a warning about it on startup; most production-hardened setups explicitly disable it and use fetch joins or DTOs instead.

6. @Transactional Mechanics: Proxies, Propagation, and Self-Invocation

@Transactional is not a language feature — it's implemented the same way as the rest of Spring's declarative behavior, described in Spring Core Mechanics: an AOP proxy wraps the bean, and the transactional advice runs before the proxy delegates the call to the real method. This has one direct, frequently-surprising consequence: self-invocation bypasses the proxy.

@Service
public class OrderService {
    public void placeOrder(Order o) {
        // called directly on 'this' — no proxy involved
        saveOrder(o); // @Transactional is silently ignored here
    }

    @Transactional
    public void saveOrder(Order o) { ... }
}

Calling saveOrder from within placeOrder in the same class invokes the method directly on the raw this reference, never passing through the CGLIB/JDK dynamic proxy that Spring created around the bean. The transactional interceptor lives on the proxy, not on the object itself, so it never runs — saveOrder executes with no transaction whatsoever, and if it throws halfway through, whatever it already wrote stays written. The fix is either to call through a self-injected proxy reference, split the method into a separate bean, or use AopContext.currentProxy() (which requires exposing the proxy explicitly).

Propagation types

Propagation controls what happens when a @Transactional method is called while a transaction is already active.

PropagationBehavior when a transaction already existsBehavior when none exists
REQUIRED (default)Joins the existing transaction — same connection, same commit/rollback unitStarts a new one
REQUIRES_NEWSuspends the outer transaction, opens a brand-new, fully independent transaction on a separate connection, commits/rolls it back independently, then resumes the outer oneStarts a new one (same as REQUIRED in this case)
NESTEDCreates a savepoint within the same physical transaction/connection; rolling back the nested part rolls back only to that savepoint, not the whole transactionStarts a new one (behaves like REQUIRED)

The distinction between REQUIRES_NEW and NESTED is the one most often blurred, and it matters mechanically: REQUIRES_NEW uses a second physical database connection and a genuinely separate commit — once it commits, that data is durable even if the outer transaction later rolls back completely. NESTED uses the same connection and the same underlying transaction, just with a savepoint marker (via JDBC's Connection.setSavepoint()); if the outer transaction rolls back entirely, everything inside the nested savepoint rolls back with it, because it was never a separate commit — it's still one physical transaction. NESTED also requires a JDBC driver and connection pool that support savepoints (Spring's DataSourceTransactionManager supports it; not all transaction managers do, e.g. JTA-based ones typically don't).

Concrete scenario where the choice matters: audit logging

Suppose processPayment() calls auditLogService.logAttempt(...) and then does the actual charge, which might throw. You want the audit log entry to survive even if the payment fails and the outer transaction rolls back — for example, to have a durable record that an attempt was made. If logAttempt is REQUIRED, it joins the same transaction as the payment logic; when the payment fails and the outer transaction rolls back, the audit row rolls back with it — you lose exactly the record you needed. Marking logAttempt as REQUIRES_NEW forces it onto an independent transaction that commits on its own as soon as logAttempt returns, so the log entry is durably written regardless of what happens afterward in the caller. This is the standard justification for REQUIRES_NEW: any write that must survive independently of the outer unit of work's outcome.

Isolation levels

@Transactional(isolation = Isolation.READ_COMMITTED) is a Spring-level request; Spring doesn't implement isolation itself — it sets the isolation level on the underlying JDBC Connection (connection.setTransactionIsolation(...)) before the transaction begins, and the actual guarantees are then enforced entirely by the database engine, as covered in Database Architecture. This means the same Isolation.REPEATABLE_READ annotation can behave differently across database vendors — Postgres's REPEATABLE READ is snapshot-based and prevents phantom reads in practice, while MySQL/InnoDB's REPEATABLE READ (its default) uses next-key locking with somewhat different phantom-read behavior. Spring also can't retroactively raise isolation above what the underlying connection pool or database default allows; if you don't set it explicitly, Isolation.DEFAULT just means "whatever the database's default is," which is READ COMMITTED on Postgres and Oracle but REPEATABLE READ on MySQL.

7. Write-Behind Flushing: When SQL Actually Runs

A very common misconception is that calling a setter, or even calling repository.save(), immediately issues an UPDATE/INSERT to the database. It usually does not. Hibernate uses write-behind semantics: it queues pending inserts/updates/deletes in the persistence context's action queue and only actually sends SQL to the database at specific, well-defined flush points:

  1. Before executing a query that could be affected by pending changes — Hibernate auto-flushes so the query sees consistent data. For example, if you've modified an entity's status field and then run a JPQL query filtering on status, Hibernate flushes first so the query doesn't return stale results from before your in-memory change.
  2. At transaction commit — the most common trigger; everything pending gets flushed right before the underlying JDBC transaction commits.
  3. On an explicit call to entityManager.flush() — used deliberately, e.g. to get a generated ID back immediately, or in batch processing to periodically push the action queue to the database and then clear() the context.
Why write-behind exists

Batching writes lets Hibernate group same-shape statements together (with hibernate.jdbc.batch_size configured, several INSERTs can be sent to the driver as one JDBC batch instead of N round trips), and it lets dirty checking do its job once per entity per transaction rather than issuing an UPDATE on every individual setter call. The cost is exactly the confusion this section addresses: "I called setStatus() — why doesn't the database show the new value yet?" The answer is always: because nothing has forced a flush yet, and the object in memory is already correct even though the row isn't.

Auto-flush and native queries

The auto-flush-before-query behavior applies to JPQL/Criteria queries that Hibernate can statically analyze. It generally does not apply to native SQL queries run via createNativeQuery unless you explicitly configure a FlushModeType or manage it yourself — a frequent source of "I updated the entity, then ran a native query, and it still shows the old value" bugs.

8. Concurrency Control: Optimistic Locking and Pessimistic Locking

Both mechanisms solve the same underlying problem — two transactions reading and then writing the same row without either being aware of the other, resulting in a lost update — but they solve it with opposite philosophies about whether conflicts are rare or expected. The canonical ShopSphere example is a flash sale: many concurrent checkout requests all trying to decrement the same product's Inventory.availableQty at once.

Optimistic locking via @Version

@Entity
class Inventory {
    @Id Long id;
    Long productId;
    Long warehouseId;
    int availableQty;
    int reservedQty;
    @Version
    Long version;
}

Hibernate adds a version column and rewrites every UPDATE for that entity to check-and-increment it atomically:

UPDATE inventory SET available_qty = ?, reserved_qty = ?, version = version + 1
WHERE id = ? AND version = ?  -- the version value read at load time

If another transaction updated the row (and thus incremented version) between when this transaction read the row and when it tries to write, the WHERE version = ? clause matches zero rows. Hibernate checks the JDBC update count; when it's 0 where 1 was expected, it throws OptimisticLockException (wrapped as ObjectOptimisticLockingFailureException in Spring Data). No row-level database lock is held while the transaction is thinking — the check happens entirely at write time, which is why it's called optimistic: it assumes conflicts are uncommon and pays the cost of detecting them only when they actually occur, rather than paying a locking cost on every read.

Pessimistic locking via @Lock(PESSIMISTIC_WRITE)

Pessimistic locking instead prevents the conflict from being possible at all, by taking a database row lock at read time:

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select i from Inventory i where i.productId = :productId and i.warehouseId = :warehouseId")
Inventory findForReservation(@Param("productId") Long productId, @Param("warehouseId") Long warehouseId);

This compiles down to SELECT ... FROM inventory WHERE product_id = ? AND warehouse_id = ? FOR UPDATE. The database itself blocks any other transaction that tries to acquire a conflicting lock on that row (another FOR UPDATE, or in some databases even a plain write) until this transaction commits or rolls back. This trades throughput for certainty: it eliminates the race but means every reader-then-writer serializes on that row for the duration of the transaction, which is exactly the kind of contention that causes connection pool exhaustion and timeouts under load if the transaction holding the lock is slow or long-running — precisely the risk during a flash sale, where thousands of checkout requests might all want a FOR UPDATE lock on the same hot product's inventory row within the same second.

Optimistic (@Version)Pessimistic (SELECT ... FOR UPDATE)
Where the conflict is caughtAt write time, via a failed WHERE version = ? matchNever happens — contenders block until the lock is released
Cost when conflicts are rareVery low — no locks held during readUnnecessary serialization even when nobody actually collides
Cost when conflicts are frequentHigh — retries pile up, users see failuresPredictable, but throughput drops as lock hold time grows

Optimistic locking composes with retry, not with silence

@Version only helps if something actually catches OptimisticLockException and retries the read-modify-write cycle (typically with a bounded number of attempts and possibly a backoff, echoing the retry patterns in Resilience & Fault Tolerance). If nothing catches it, the exception just propagates up as a failed request — which is correct behavior (you did prevent two concurrent checkouts from both decrementing the same stale availableQty and overselling the product) but is often mistaken for a bug rather than the locking mechanism doing exactly its job.

Concepts Worth Being Able to Explain From First Principles

Why is SessionFactory/EntityManagerFactory safe to share across threads while Session/EntityManager is not?
SessionFactory (and its JPA-standard counterpart EntityManagerFactory) holds application-wide, read-mostly state: the parsed entity mappings, the metamodel, and the optional second-level cache — none of which changes per request, so many threads reading it concurrently is safe by construction, which is exactly why it's built once at startup and held as a singleton. A Session/EntityManager is the opposite: it wraps exactly one persistence context, which is a mutable identity map plus a set of dirty-check snapshots plus a queue of pending writes, all specific to one unit of work. If two threads shared one Session, their writes and reads would interleave into the same identity map and action queue with no coordination at all, silently corrupting which entity's changes get flushed and when. This is why the factory is a long-lived singleton and the Session/EntityManager it opens is a short-lived, single-threaded object scoped to one transaction (or one request, under Open Session in View).
Why does calling find() twice on the same id return the identical object reference, and why does that matter for correctness, not just performance?
The persistence context maintains an identity map keyed by (entity type, primary key). The first call loads the row and registers the resulting object in that map. The second call checks the map first, finds an entry, and returns that exact reference without touching the database. This matters beyond avoiding a redundant query: if two calls returned two different objects representing the same row, and code mutated both independently, Hibernate would have no way to know which set of changes should win at flush time, and you could silently lose one side's changes with no error at all. Guaranteeing one object per row within a unit of work makes "the object" and "the row" synonymous for the duration of the transaction, which is what dirty checking and the overall unit-of-work model depend on.
Why is FetchType.LAZY considered the safer default even though it introduces the risk of LazyInitializationException?
EAGER loading's cost is invisible and unbounded at the call site: fetching one entity can transitively pull in an arbitrarily large graph through chained eager associations, and there's no way to tell from repository.findById(id) how much data is about to load. That cost shows up as a production slowdown that's hard to trace back to a single annotation. LAZY loading's cost, by contrast, is visible and immediate: accessing an uninitialized association outside a session throws a specific, unambiguous exception at a specific line, which is far easier to diagnose and fix (with a fetch join, an entity graph, or a DTO) than a graph that's simply larger than expected. Failing loudly and immediately is preferable to failing silently and slowly.
Walk through exactly why calling an @Transactional method from another method in the same class does not start a transaction.
Spring implements @Transactional using an AOP proxy — either a JDK dynamic proxy (if the bean implements an interface) or a CGLIB subclass proxy (otherwise) — that wraps the target bean. The transactional interceptor logic lives on that proxy, not inside the target class's bytecode. When Spring wires the bean into other beans, it injects the proxy, so calls arriving from outside the class go through the proxy and trigger the interceptor. But a call made from one method to another *within the same class* is a plain Java method call on this, which refers to the raw target object, never the proxy that wraps it. The call bypasses the proxy entirely, so the transactional advice around it never executes, and the method runs with whatever transaction (if any) was already active in the caller — often none.
What's the mechanical difference between REQUIRES_NEW and NESTED, and why does that difference determine whether an outer rollback can undo the inner work?
REQUIRES_NEW suspends the current transaction and opens a second, physically independent transaction on a separate database connection. That inner transaction commits or rolls back completely on its own; once it commits, the data is durable no matter what the outer transaction later does, because there was never a shared commit unit between them. NESTED, by contrast, stays on the same physical connection and the same outer transaction, just marking a savepoint with the JDBC driver. Rolling back to that savepoint undoes only the work after it, but if the outer transaction itself rolls back entirely, everything — including everything inside the nested savepoint — rolls back too, because it was always part of one physical transaction that never separately committed.
Why does an N+1 query problem often pass unnoticed in tests but cause real latency in production?
The number of extra queries scales with the number of parent rows fetched, N. In a unit test or a local demo, N is often 1-5, so the "extra" queries add a few milliseconds nobody notices, and the returned data is correct, so the test passes. In production, N might be in the hundreds or thousands for a busy list endpoint, so the same code pattern turns into hundreds of extra sequential round trips to the database, each paying full network and query-planning latency, easily turning a sub-100ms endpoint into a multi-second one. Nothing about the code's correctness changed between test and production — only the cardinality of the loop that triggers the lazy loads, which is exactly why load or scale testing (not just correctness testing) is what actually surfaces this class of bug.
If dirty checking automatically detects field changes, why does JPA still provide an explicit merge() method?
Dirty checking only works on entities the current persistence context is already tracking as managed. A detached entity — one that arrived from outside the current unit of work, such as an object deserialized from a previous request or held across two separate transactions — has no snapshot in this persistence context to diff against, so mutating its fields does nothing observable to Hibernate. merge() exists to bridge that gap: it takes the detached object's state, loads (or locates) the corresponding managed entity in the current context, copies the detached state onto it, and returns that managed copy. From that point on, ordinary dirty checking applies to the returned object — but critically not to the original detached object you passed in, which is a common source of confusion when code keeps mutating the original reference after calling merge().
Why does Open Session in View reduce visible LazyInitializationExceptions without actually fixing the underlying performance problem?
OSIV keeps a Hibernate session (and the database connection backing it) open for the full duration of an HTTP request rather than closing it when the @Transactional service method returns. This means lazy associations touched later — in a JSON serializer or a template — can still be initialized on demand, because there's still a live session to run the query. It removes the exception, but it does nothing to reduce the number of queries being issued; an N+1 pattern still issues N+1 queries, they've simply moved to wherever serialization happens, outside the boundaries of the transaction and often outside of what gets measured as "the transaction's" cost. It also extends how long a connection is checked out from the pool to cover rendering time, which under concurrent load increases the odds of exhausting the pool — trading a loud, easy-to-find exception for a quieter, harder-to-diagnose throughput problem.
