Why this matters

Every backend service is, underneath its business logic, a machine for moving data between arrays, linked structures, hash tables, and trees. If you don't know that a HashMap resize rehashes every entry, you won't understand why a service that inserts a million entries into a freshly-constructed map without a sized constructor spends a visible chunk of its startup time in resize(). If you don't know that HashMap iteration order is a function of bucket index rather than insertion order, you'll write a test that passes today and fails after a JDK upgrade changes the hash spreading function. This page builds the mental model — array vs. pointer-chasing trade-offs, hashing, balanced trees, heaps — that explains why the framework's classes behave the way they do, not just what methods they expose.

1. Arrays vs. Linked Structures: The Foundation of Every Trade-off

Almost every design decision in the collections framework traces back to one physical fact: an array is a single contiguous block of memory, and a linked structure is a set of separately-allocated nodes connected by references. Everything else — complexity numbers, cache behavior, resize costs — falls out of that.

ArrayList: contiguous, index-addressable storage

ArrayList wraps a plain Object[]. Because the array is contiguous, the address of element i is computed directly as baseAddress + i * elementSize — no traversal needed. That gives:

  • get(i) / set(i, v): O(1) — one arithmetic computation, one memory read.
  • add at the end: amortized O(1). The backing array grows by 50% (via Arrays.copyOf, newCapacity = oldCapacity + (oldCapacity >> 1)) when full, and that growth is amortized because most inserts don't trigger it — the cost of an occasional O(n) copy is spread across the n cheap inserts that preceded it.
  • insert/remove at an arbitrary index: O(n) — every element after the index has to be shifted one slot via System.arraycopy, because the array's contiguity requires that there be no gaps.

LinkedList: pointer-chasing storage

LinkedList is a doubly-linked list of Node objects, each holding item, prev, and next. Insertion or removal at a known node is O(1) — you just relink three pointers. But that's the theoretical claim that misleads people: to remove element at index k you first have to find it, and finding it means walking the list from whichever end is closer, which is O(n). So both structures are O(n) for "delete the element at index k" — ArrayList pays with a shift, LinkedList pays with a walk.

Why ArrayList wins in practice despite LinkedList's "O(1) insert"

The O(1) insert claim for LinkedList only holds if you already have a reference to the node (e.g., via a ListIterator mid-traversal). For ordinary usage — list.add(index, value) — you pay O(n) to locate the node either way. And even when both are O(n), ArrayList's O(n) is a tight loop over contiguous memory that the CPU prefetches efficiently (cache-friendly, no pointer indirection), while LinkedList's O(n) walk chases pointers scattered across the heap, each dereference a potential cache miss. In measured workloads this often makes ArrayList faster even for "insert in the middle" patterns unless the list is huge and you're holding an iterator. LinkedList also pays ~16 bytes of object header + 2 references per node in overhead that a plain array simply doesn't have. This is why ArrayDeque has effectively replaced both Stack and LinkedList as the default queue/deque implementation.

2. HashMap Internals: The Core Mechanism

HashMap is the single most load-bearing class in the framework, and its internals explain a large fraction of subtle production bugs. The structure is an array of buckets, Node<K,V>[] table, where each slot holds either nothing, a linked list of colliding entries, or (since Java 8) a red-black tree of colliding entries.

The hash() function and why it spreads bits

You do not use key.hashCode() directly as the bucket index. HashMap.hash(key) does:

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

This XORs the top 16 bits of the hash code into the bottom 16 bits. Why? Because the bucket index is computed as (n - 1) & hash, where n is the table length (always a power of two). Masking with (n-1) only ever looks at the low bits of the hash — for a table of size 16, only the low 4 bits matter. If a key's hashCode() implementation produces good entropy in the high bits but the low bits are mostly constant (a genuinely common pattern — e.g., hash codes built by shifting fields into different byte ranges), every key would collide into the same handful of buckets despite having "good" hash codes overall. XOR-folding the high 16 bits into the low 16 bits mixes that high-order entropy down into the bits that actually decide the bucket, at the cost of only two cheap operations. This is a deliberate, cheap defense against a specific, otherwise-invisible class of hash-quality bug.

Index calculation: (n − 1) & hash

Because table length n is always a power of two, n - 1 is a bitmask of all 1s (e.g., 15 = 0b1111 for n=16). hash & (n-1) is exactly equivalent to hash % n for a power-of-two n, but a bitwise AND is far cheaper than a modulo (division) instruction — this is why the table size is forced to be a power of two (via tableSizeFor, which rounds any requested capacity up to the next power of two).

Collision handling: chaining, then treeification

When two keys hash to the same bucket, Java 8+ first stores them as a singly-linked chain of Node objects (append at the tail). If that chain grows past TREEIFY_THRESHOLD (8) and the table itself has at least MIN_TREEIFY_CAPACITY (64) buckets, the bucket is converted from a linked list into a red-black tree of TreeNodes, which are ordered by hash code (and, as a tiebreaker, by a class-name comparison or identity hash).

Why treeify only past 8 AND only when the table has ≥ 64 buckets

A linked-list bucket lookup is O(k) for k colliding entries; a red-black tree bucket lookup is O(log k). For small k (say, 8), the constant-factor overhead of tree operations (more pointers, rebalancing) isn't worth it over a simple linear scan — 8 comparisons is nothing. Treeification exists as a defense against pathological hash collisions (accidental or, worse, adversarially crafted hash-flooding input, e.g., attacker-controlled map keys from HTTP request parameters designed to all hash to one bucket) that would otherwise degrade a bucket to O(n) linear search, turning an O(1) amortized map into an O(n) one under attack. The 64-bucket minimum exists because if the table is still small, the real fix is simply to resize the table (spreading entries into more buckets) rather than pay tree overhead — resize() is tried first via treeifyBin, which resizes instead of treeifying if capacity is under 64.

Load factor and resizing

The table resizes when size > capacity * loadFactor. The default load factor is 0.75. This is a deliberate space/time trade-off: a lower load factor (say 0.5) wastes half the array on empty slots but keeps chains short and lookups fast; a higher load factor (say 0.9) packs the array tightly but lets chains grow, degrading average lookup time. 0.75 is the empirically-chosen point where, for a table following the Poisson distribution of random hashing, the expected bucket occupancy stays low (mostly 0 or 1 entries per bucket) while keeping memory reasonably dense.

Resizing doubles the table capacity (newCap = oldCap << 1) and then rehashes every existing entry into the new table — this is the expensive part people underestimate. Because capacity is always a power of two, Java 8 optimized this: instead of recomputing hash & (newCap - 1) from scratch for every entry, it observes that in the new (doubled) table, each old bucket's entries split into exactly two new buckets — the original index, or the original index + oldCapacity — depending on whether the newly-relevant bit of the hash is 0 or 1. This lets resize split each bucket's chain into a "low" and "high" list in one pass without recomputing full hashes.

Resize cost in practice

Constructing a HashMap with the no-arg constructor and then inserting a million entries triggers roughly 17 resize operations (16 → 32 → 64 → ... → ~1.4M), each one rehashing everything inserted so far. This is entirely avoidable: if you know the approximate final size up front, construct with new HashMap<>(expectedSize) (or better, account for load factor: capacity should be expectedSize / 0.75 rounded up) to allocate the right-sized table once. This is a real, measurable startup-latency fix in services that bulk-load caches or lookup tables at boot.

put() and get() step by step

  1. put(key, value): compute hash(key); compute bucket index i = (n-1) & hash; if the bucket is empty, insert a new Node there; if not, walk the chain (or tree) comparing hash first (cheap int comparison) and then equals() (only if hashes match) to find an existing key to overwrite, otherwise append; if the chain length after append hits the treeify threshold, treeify; finally check if size > threshold and resize if so.
  2. get(key): compute hash(key), compute bucket index, then scan the bucket's chain or tree comparing hash and equals() until found or exhausted.

3. Ordered and Sorted Variants: LinkedHashMap and TreeMap

LinkedHashMap: threading a list through the hash table

LinkedHashMap extends HashMap and adds a second data structure on top: a doubly-linked list threading through all entries via before/after pointers on each node (its Entry subclasses HashMap.Node). This costs two extra references per entry but buys predictable iteration order. By default that order is insertion order; passing accessOrder = true to the constructor switches it to access order, where every get() moves the accessed entry to the end of the linked list.

Access-order mode plus one override is exactly how you build an LRU cache from a general-purpose map:

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) {
        super(16, 0.75f, true); // accessOrder = true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

removeEldestEntry is called by put()/putAll() right after insertion; returning true evicts the head of the linked list — the least-recently-used entry, because access-order mode keeps moving recently-touched entries to the tail. This is the textbook building block behind bounded in-memory caches, though production caches (Caffeine, Guava) use more sophisticated eviction (window-TinyLFU, segmented LRU) for better hit rates under skewed access patterns.

TreeMap: red-black tree backing

TreeMap is backed by a red-black tree — a self-balancing binary search tree that guarantees O(log n) for get/put/remove by maintaining an invariant (no root-to-leaf path is more than twice as long as any other) via node recoloring and rotations on insert/delete. Unlike HashMap, there is no hashing at all: ordering is determined entirely by the keys' natural ordering (they must implement Comparable) or by a Comparator supplied at construction. This ordering is what buys you the navigation methods HashMap cannot offer:

  • floorKey(k) — greatest key ≤ k
  • ceilingKey(k) — smallest key ≥ k
  • lowerKey(k) — greatest key strictly < k
  • higherKey(k) — smallest key strictly > k
  • firstKey()/lastKey(), and range views via subMap, headMap, tailMap

These make TreeMap the right tool whenever you need range queries or "nearest key" lookups — e.g., mapping timestamps to events and finding the event active at a given time — something a hash table structurally cannot do, because hashing intentionally destroys any relationship between key ordering and storage location.

4. ConcurrentHashMap: Concurrency Without a Global Lock

Pre-Java-8, ConcurrentHashMap partitioned the table into a fixed number of segments, each with its own lock — a writer only blocked other writers touching the same segment. Java 8 redesigned this entirely around per-bucket, per-node concurrency primitives, eliminating segments:

  • Inserting into an empty bucket uses a CAS (compare-and-swap) operation (Unsafe.compareAndSwapObject / VarHandle in later versions) to atomically set the bucket's head node — no lock at all if the bucket was empty.
  • Inserting into a non-empty bucket (a collision, or a treeified bucket) synchronizes only on that specific bucket's head node — synchronized(node) — so writers to different buckets never contend with each other. This is much finer-grained than segment locking: contention only happens between two threads writing to the exact same bucket at the exact same time.
  • Resizing is cooperative: multiple threads can help move nodes from the old table to the new one concurrently (via transfer()), each claiming a range of buckets to migrate, using a ForwardingNode marker to tell concurrent readers/writers "this bucket has already moved, look in the new table."
  • size() doesn't lock anything — it sums a set of striped LongAdder-style counters (CounterCell[]) that are updated with low contention during puts/removes, then combined on demand. This trades perfect accuracy for the ability to never block.
  • Iteration walks the table directly without copying it and without blocking writers, meaning a structural change during iteration is possible and visible mid-traversal.
Weakly consistent, not "wrong"

Because there is no global lock and no snapshot taken, ConcurrentHashMap iterators and bulk operations (size(), isEmpty(), forEach) are weakly consistent: they reflect the state of the map at some point during the operation, are guaranteed to traverse each element that was present for the entire duration at most once, but may or may not see elements inserted or removed concurrently, and never throw ConcurrentModificationException. This is a deliberate trade-off — you give up "exactly what did the map look like at instant T" in exchange for never blocking readers behind writers and never blocking writers behind readers. Contrast this with a synchronized HashMap wrapped by Collections.synchronizedMap, where you get a single consistent view at any instant but pay for it with a single lock serializing every access. See concurrency fundamentals for how CAS and synchronized interact with the Java Memory Model to make this safe.

5. Fail-Fast vs. Weakly Consistent Iterators

The non-concurrent collections (ArrayList, HashMap, HashSet, etc.) use a fail-fast iteration strategy built on a modCount field — an integer incremented every time the collection is structurally modified (add/remove; a plain set() doesn't count as structural). When you create an iterator, it captures the current modCount as expectedModCount. Every call to next() checks modCount == expectedModCount, and throws ConcurrentModificationException if they diverge.

Fail-fast is a bug detector, not a concurrency control

ConcurrentModificationException is not thrown to keep your data safe during concurrent access — it's a best-effort debugging aid that catches the common mistake of mutating a collection while iterating it, typically on a single thread (e.g., calling list.remove(x) inside a for-each loop over list). It offers no real guarantee: the JavaDoc explicitly states it should never be used for correctness, only to detect bugs, because a modification can, in rare cases, go undetected if timing happens to leave modCount unchanged in the way the check expects. The correct way to remove during iteration is Iterator.remove() (which updates expectedModCount to match) or Collection.removeIf().

The concurrent collections (ConcurrentHashMap, CopyOnWriteArrayList, ConcurrentSkipListMap) instead use weakly consistent iteration, as described above — no exception is ever thrown, because the whole point of these classes is to support concurrent structural modification during traversal as a normal, expected use case, not a bug.

6. PriorityQueue: The Binary Heap

PriorityQueue is backed by a binary heap stored in a plain array (Object[] queue), not by actual tree nodes. The heap property (min-heap by default: every parent ≤ its children) is maintained implicitly through index arithmetic: for a node at index i, its children live at 2i + 1 and 2i + 2, and its parent lives at (i - 1) / 2. This array-as-tree encoding avoids pointer overhead entirely.

  • offer(e) (insert): append the element at the end of the array, then sift up — repeatedly compare it to its parent and swap if it's smaller (for a min-heap), until the heap property holds or it reaches the root. O(log n).
  • poll() (remove min): the root (index 0) is the minimum and is what's returned. Move the last element in the array into index 0, shrink the array, then sift down — repeatedly compare it to its smaller child and swap if the child is smaller, until the heap property holds. O(log n).
  • peek(): return index 0 directly. O(1).

Passing a Comparator to the constructor simply changes the comparison used during sift-up/sift-down — a Comparator.reverseOrder() turns it into a max-heap without changing any of the underlying mechanics. PriorityQueue is explicitly not synchronized; the concurrent equivalent is PriorityBlockingQueue, which wraps the same heap logic in a single lock plus a Condition for blocking consumers when the queue is empty.

7. Copy-on-Write and Wrapper Collections

CopyOnWriteArrayList

Every mutating operation (add, set, remove) allocates an entirely new backing array, copies the existing elements into it, applies the change, and then atomically swaps the volatile array reference. Readers always operate on whatever array reference they observed at the start of their operation (typically captured by the iterator at creation time), so reads never block and never see a torn or partially-updated array. This is only appropriate for read-heavy, write-rare workloads — e.g., a list of listeners that's iterated constantly but modified only at startup/shutdown — because every single write is O(n) in both time (full array copy) and space (a full duplicate array is allocated and the old one becomes garbage). Under frequent writes this produces significant allocation pressure and GC churn, potentially triggering more young-generation collections; see how the JVM heap and garbage collector handle allocation-heavy workloads.

HashSet, TreeSet, LinkedHashSet: thin wrappers

All three Set implementations are, internally, just a Map whose keys are your elements and whose values are all a shared dummy constant (private static final Object PRESENT = new Object();). HashSet.add(e) literally calls map.put(e, PRESENT) under the hood. TreeSet wraps a TreeMap, giving it the same sorted-order and navigation guarantees (red-black tree, O(log n)). LinkedHashSet wraps a LinkedHashMap, giving it predictable insertion-order iteration. Understanding this collapses "three data structures" into "one data structure applied three times with different backing maps."

ArrayDeque as the Stack/Queue replacement

ArrayDeque is a resizable circular array (a ring buffer) with head and tail indices that wrap around using modulo arithmetic. It supports O(1) amortized insertion/removal at both ends, making it strictly better than the legacy Stack class (which extends the antiquated, needlessly-synchronized Vector) for stack usage, and generally faster than LinkedList for queue usage because, again, contiguous-array access beats pointer-chasing. The JDK documentation itself recommends ArrayDeque over both Stack and LinkedList for stack/queue use cases.

8. The equals()/hashCode() Contract

Every hash-based collection depends on a strict contract: if a.equals(b) is true, then a.hashCode() == b.hashCode() must also be true. The reverse is not required — different objects may share a hash code (that's just a collision, handled by chaining). The reason this contract exists is entirely mechanical: HashMap.get(key) first computes hash(key) to jump straight to a bucket, then uses equals() only to disambiguate among entries within that bucket. If two equal objects produced different hash codes, they could land in different buckets, and a lookup for one would never find an entry stored under the other — silently, with no exception, just a wrong answer.

A mutable key silently corrupts a HashMap

A closely related, extremely common bug: using a mutable object as a HashMap key and then mutating a field that participates in hashCode() after insertion. The entry is stored in the bucket matching the old hash code. After mutation, map.get(key) recomputes the new hash code, looks in the wrong bucket, and reports the key as absent — even though containsKey and iteration will still show the entry sitting there if you walk the whole table. The fix is to only use immutable objects (or objects whose equality fields never change post-insertion) as map keys and set members.

Also worth internalizing: if you override equals() without overriding hashCode(), you inherit Object's identity-based hash code, which breaks the contract immediately — two "equal" objects will almost certainly hash differently, and a HashSet will happily store duplicates that your equals() considers the same.

9. Collectors: Building Collections from Streams

The Collectors utility class (used with Stream.collect()) is fundamentally a set of recipes for assembling the collections covered above out of a stream of elements. Understanding the collections underneath makes these far less mysterious.

groupingBy — building a Map<K, List<V>>

Single-level grouping produces a HashMap keyed by your classifier function, with each value being a List (by default, an ArrayList) of all elements that mapped to that key — internally, this is implemented as a repeated computeIfAbsent(key, k -> new ArrayList<>()).add(element).

Map<Department, List<Employee>> byDept =
    employees.stream().collect(Collectors.groupingBy(Employee::getDepartment));

Multi-level grouping nests a downstream groupingBy inside the outer one, producing a Map<K1, Map<K2, List<V>>>:

Map<Department, Map<Boolean, List<Employee>>> byDeptThenRemote =
    employees.stream().collect(
        Collectors.groupingBy(Employee::getDepartment,
            Collectors.groupingBy(Employee::isRemote)));

Any downstream collector can replace the implicit toList() — counting() to get group sizes, summingInt() to sum a field per group, or another Collectors.mapping(...) to transform elements before collecting them.

partitioningBy — a specialized binary groupingBy

partitioningBy(predicate) always produces exactly two entries, keyed by Boolean.TRUE/Boolean.FALSE, backed internally by a dedicated lightweight map implementation rather than a general HashMap — because the key space is known to have exactly two values, there's no need for hashing at all.

mapping — transforming elements within a downstream collection

mapping(function, downstream) applies a transformation to each element before it reaches a downstream collector — most useful nested inside groupingBy when you want, say, only employee names grouped by department rather than full Employee objects:

Map<Department, List<String>> namesByDept =
    employees.stream().collect(Collectors.groupingBy(
        Employee::getDepartment,
        Collectors.mapping(Employee::getName, Collectors.toList())));

toMap — building a Map directly, and the merge-function trap

Collectors.toMap(keyFn, valueFn) builds a HashMap by applying both functions to each element. If two elements produce the same key, this throws IllegalStateException: Duplicate key by default — because without a merge strategy, silently overwriting one value with another would hide a correctness bug. The three-argument overload takes a BinaryOperator<V> merge function to resolve collisions explicitly:

Map<Department, Double> totalSalaryByDept =
    employees.stream().collect(Collectors.toMap(
        Employee::getDepartment,
        Employee::getSalary,
        Double::sum));

joining — StringBuilder under the hood

Collectors.joining(delimiter, prefix, suffix) is effectively a StringBuilder accumulator that appends each element (with the delimiter between elements) and wraps the result in the given prefix/suffix at the end — the collections-and-Big-O analogue here is trivial (O(n) total, same as manual string building), but it's worth knowing it avoids the O(n²) trap of repeated naive String concatenation (+= in a loop) precisely because it defers to a single mutable buffer, the same reason ArrayList's amortized growth beats repeatedly reallocating a fixed array by hand.

Concepts Worth Being Able to Explain From First Principles

Why does HashMap XOR the hash code's upper 16 bits into the lower 16 bits instead of using hashCode() directly?
Because the bucket index is computed as (n-1) & hash, which for a power-of-two table size only ever examines the low-order bits of the hash. Many hashCode() implementations concentrate their entropy in higher-order bits (e.g., fields combined via multiplication and shifting), so using the raw hash code directly could send many distinct keys into a small number of buckets even though the hash codes look well-distributed overall. XOR-folding h ^ (h >>> 16) mixes the high bits down into the low bits that actually decide bucket placement, spreading collisions more evenly across the table for the cost of one shift and one XOR — cheap insurance against a whole class of bad-hash-code bucket clustering.
Walk through exactly what happens, step by step, when a HashMap resizes.
Once size exceeds capacity * loadFactor (default 0.75) after an insert, resize() runs: it allocates a new array of double the old capacity (capacity always stays a power of two), then migrates every existing entry. Because the new capacity is double the old one, migrating a bucket at old index i only ever sends its entries to one of two places in the new table: index i, or index i + oldCapacity — determined by checking whether the bit at position oldCapacity (in binary) of each entry's stored hash is 0 or 1. This lets the JDK split each old bucket's chain into a "low" list and a "high" list in a single pass without recomputing hashes from scratch, then place the low list at index i and the high list at index i+oldCapacity in the new table. If a bucket had been treeified, the same split happens on the tree, and if the resulting split makes either resulting group small enough, it's un-treeified back into a plain list.
Why does ConcurrentHashMap not need a single global lock the way early synchronized Maps did?
Because concurrent access to different buckets doesn't actually conflict — two threads writing to key A and key B only need to coordinate if A and B happen to hash into the same bucket. Java 8's ConcurrentHashMap exploits this by using CAS to place the first node in an empty bucket lock-free, and a `synchronized` block scoped to only that bucket's head node when appending to a non-empty bucket or during a resize migration of that bucket. This means the only threads that ever actually block each other are two threads simultaneously touching the exact same bucket — everything else proceeds in parallel. Reads never take any lock at all; they rely on the fields being `volatile` so a freshly-written node is guaranteed visible to a subsequent reader.
Why does removing an element from a List while iterating it with a for-each loop throw ConcurrentModificationException, and what's the correct way to do it?
A for-each loop desugars to using the list's Iterator. `ArrayList` maintains a `modCount` counter incremented on every structural change; the iterator snapshots that count when created and checks it on every `next()` call. Calling `list.remove(x)` directly (rather than through the iterator) bumps `modCount` without informing the iterator, so the next `next()` call sees a mismatch and throws — this is a deliberate fail-fast check meant to surface a likely bug rather than let the iterator silently skip an element or throw an IndexOutOfBoundsException later. The correct approaches are to call `Iterator.remove()` (which updates the iterator's own expected count), use `ListIterator` if you need to add during traversal, or use `Collection.removeIf(predicate)`, which handles the removal internally without exposing you to the hazard at all.
Why is 0.75 the default load factor for HashMap, and what would change if it were 0.5 or 1.0?
Load factor controls the density of the table before a resize is triggered. At 0.5, half the array slots are always empty, wasting memory but keeping the expected number of entries per bucket very low (mostly 0 or 1), which keeps lookups close to true O(1). At 1.0, the table isn't resized until it's completely full, which saves memory but lets the expected bucket occupancy climb, increasing the average number of comparisons per lookup. 0.75 is the empirically chosen middle ground: for hash codes that spread roughly uniformly (a reasonable assumption under Poisson distribution modeling), it keeps the probability of any bucket having many entries low while not wasting an excessive fraction of the array as permanently unused capacity.
How does LinkedHashMap's removeEldestEntry hook let you build an LRU cache with no custom eviction logic?
LinkedHashMap already maintains a doubly-linked list through all its entries; constructing it with `accessOrder = true` makes every `get()` (and `put()` on an existing key) move that entry to the tail of the list, so the head of the list is always the least-recently-used entry. `removeEldestEntry(eldest)` is invoked automatically by `put()`/`putAll()` right after a new entry is added, passed the current head (eldest) entry, and if it returns true, that head entry is removed immediately. Overriding it to return `size() > capacity` turns the map into a fixed-capacity cache that evicts the least-recently-used entry every time a new insertion would push it over capacity — no separate tracking structure required, because the linked list ordering already encodes recency.
Why are HashSet, TreeSet, and LinkedHashSet described as "thin wrappers," and what does that actually buy you as a reader of the source?
Each of these Set implementations holds an internal Map instance (HashMap, TreeMap, and LinkedHashMap respectively) and stores your set elements as that map's keys, with every value pointing to the same shared dummy object. `add(e)` is literally `map.put(e, PRESENT) == null`. This means all the complexity, ordering behavior, and complexity guarantees you already understand for the Map side apply directly and unchanged to the Set side — TreeSet's O(log n) navigation methods and sorted iteration come purely from TreeMap's red-black tree, and LinkedHashSet's predictable iteration order comes purely from LinkedHashMap's threaded list. There isn't a second, separate implementation to learn.
