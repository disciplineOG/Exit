Why this matters

Splitting a monolith into services doesn't remove complexity — it relocates it from your codebase into the network, and the network is a far less forgiving place to have bugs. A method call that used to be a guaranteed, sub-microsecond stack frame push is now a request that can be slow, can partially fail, can hit an instance that no longer exists, and can't tell you on its own which of the six services it touched was the one that actually broke. Every pattern on this page — discovery, gateways, distributed tracing — exists to answer one of the questions a monolith never had to ask: which instance do I even call, who is allowed to call it, and when it's slow, which of the many hops was actually the slow one.

1. What Microservices Actually Trade Away

A monolith is one deployable unit: one process, one memory space, one codebase, usually one database. A method call between two "modules" inside it is a language-level function call — synchronous, in-process, and essentially free (nanoseconds, no serialization, no network, and if it fails it fails as an exception you can catch in the same stack). The cost of a monolith is organizational and architectural: every team's code ships together, a bug in one module can crash the entire process, and scaling means scaling the whole thing even if only one code path is actually hot.

Microservices split that single deployable unit into many independently deployable, independently scalable services, each usually owning its own data store. This buys real things: a team can deploy its service on its own schedule without coordinating a monolith-wide release train; a service under heavy load (say, a search service during a flash sale) can be scaled out without also scaling the billing service that isn't under any load; a failure in one service doesn't necessarily crash the whole system's process space.

But that in-process function call is now a network call, and the network is fundamentally unreliable in ways a function call never is:

  • It can be slow for no reason connected to the work being done — a network hop adds latency that varies with congestion, and that variance compounds across every hop in a request's path.
  • It can fail partially — the request might never arrive, or it might arrive and be processed but the response might be lost, leaving the caller unable to distinguish "it never happened" from "it happened but I didn't hear back" (this is the core problem resilience-fault-tolerance is built around).
  • The callee's address isn't fixed — unlike calling a method on an object reference you already hold, calling another service means first figuring out which host and port currently represents "the payments service," and that answer changes constantly as instances scale up, scale down, crash, and get replaced by deployments.
  • A single user-facing request now fans out across many processes — so when it's slow or wrong, the evidence is scattered across several services' logs instead of one call stack.

Service discovery solves the second problem. API gateways and BFFs manage the complexity of many services being called by external clients. Distributed configuration solves the operational cost of many independently deployed services each needing config. Distributed tracing solves the fourth problem — reconstructing what actually happened to one request across all the services it touched. Each of the sections below is really answering: "what new problem did splitting into services create, and what's the mechanism that manages it?"

2. Service Discovery

The problem: instance identity is no longer fixed

In a monolith, "call the pricing module" means calling a method — the address is resolved at compile time and never changes. In a microservice architecture, "call the pricing service" means picking one specific network address (an IP and port) out of a set that is constantly in flux: instances are added by autoscaling, removed by scale-in, replaced during rolling deploys, and occasionally just crash. Hardcoding IPs in configuration doesn't just require a redeploy every time the fleet changes — it's actively wrong the moment any instance restarts and gets a new IP, which in a containerized environment (a new pod, a new container) is essentially every time.

Service discovery is the general mechanism for resolving a stable, logical name (payments-service) to the current, live set of network locations that can serve it. It has two structurally different shapes.

Client-side discovery

The calling service itself asks a registry "who are the current instances of payments-service?", gets back a list of live addresses, and then picks one itself (typically using a client-side load-balancing algorithm — round robin, least connections, or a weighted variant, the same family covered in hld-basics-scaling, just now executed inside the calling process rather than at a network appliance). Netflix's original Eureka + Ribbon combination is the canonical example: Ribbon plugged into an HTTP client and, before every call, asked Eureka for the current instance list and load-balanced across it in-process.

The advantage is that there's no extra network hop for load balancing — the decision happens locally, in memory, using a list the client already cached. The cost is that every client needs discovery-aware logic and a client library for whatever language/framework it's written in, which becomes a real tax in a polyglot environment where not every language has a mature client for your registry.

Server-side discovery

The calling service just sends its request to a fixed, well-known address (a load balancer or a service mesh sidecar proxy), and that intermediary is the one that queries the registry and picks an instance. The caller never sees the instance list at all — it just knows "send payments requests to this one stable address." AWS's Application Load Balancer combined with ECS/Kubernetes service discovery works this way, as does a service mesh data plane (an Envoy sidecar, as used by Istio) sitting next to every service instance and handling discovery and routing on its behalf.

This removes the client-library dependency entirely — any client that can make an HTTP call can participate, regardless of language — at the cost of an extra network hop through the intermediary and a piece of shared infrastructure that itself needs to be highly available.

How a registry-based system like Eureka actually works

A registry-based approach introduces one new component — the service registry — that every other service both writes to and reads from.

  1. Registration: when a service instance starts up, it registers itself with the Eureka server, sending its logical service name (e.g., ORDER-SERVICE), its host, port, and health-check URL. The registry now has one entry for this instance.
  2. Heartbeats: the instance then sends a periodic heartbeat (Eureka's default is every 30 seconds) to the registry to say "I'm still alive." This is a deliberate design choice — rather than the registry actively polling every instance's health endpoint (which doesn't scale well as instance counts grow and creates a fan-out problem for the registry itself), each instance proactively renews its own lease. This is a lease-based model: registration grants a lease with a TTL (default 90 seconds in Eureka), and each heartbeat renews that lease. If a lease isn't renewed within the TTL, the registry evicts the instance from the list it hands out to clients.
  3. Resolution: when service A wants to call ORDER-SERVICE, it queries the registry for the current instance list. In client-side discovery, the client library caches this list locally (Eureka clients refresh their local cache roughly every 30 seconds by default) and picks an instance from the cache for each call, rather than hitting the registry on every single request — a registry lookup per request would turn the registry into a bottleneck and single point of failure for the entire system's request path.
  4. Deregistration: on a graceful shutdown, an instance should explicitly tell the registry to remove it immediately, rather than waiting for its lease to expire. This matters because the lease TTL is tuned to tolerate transient network blips without false evictions, which means it's also slow to react to an instance that intentionally went away — a clean shutdown without deregistration leaves that instance in other clients' cached lists for up to the TTL window, causing calls to route to a dead address until eviction catches up.
Self-preservation mode: why Eureka sometimes refuses to evict dead instances

Eureka has a mechanic that looks like a bug the first time you encounter it: if a large fraction of instances stop sending heartbeats within a short window, Eureka assumes this isn't real failure but a network partition between it and its clients, and it stops evicting instances at all — even ones that genuinely died — until the heartbeat rate recovers. This exists because the alternative is worse: if the registry itself lost network connectivity to a healthy fleet, blindly evicting everyone whose heartbeat didn't arrive would mean discovery hands out an empty instance list to the rest of the system, and every service call fails — a total outage caused by the discovery layer being falsely confident about a partial network problem. Self-preservation trades a small risk (occasionally routing to an instance that's actually dead, which a caller then has to handle as a normal failed request and retry) for avoiding a much larger one (the registry itself causing a cascading outage). It's the discovery-layer analogue of the same tension the resilience-fault-tolerance topic covers for circuit breakers: when a signal is ambiguous between "definitely broken" and "network noise," aggressive corrective action can do more damage than a temporarily stale view of the world.

The registry is itself a distributed system, and it has to stay up when everything else is failing

Discovery is on the critical path of almost every inter-service call, which means the registry has the strictest availability requirement in the entire architecture — if it's down, no service can find any other service, which is a worse outage than any single business service being down. This is exactly why registries favor availability over strict consistency (an AP choice in CAP terms): a Eureka client that can't reach the registry keeps using its last known cached instance list rather than refusing to make calls, on the reasoning that a slightly stale list is far better than no list at all.

3. The API Gateway Pattern

Once you have more than a handful of services, external clients (a mobile app, a web frontend, a third-party integrator) shouldn't be calling each service's individual address directly. Doing so means every client needs to know about every service's location, every service needs to independently implement authentication, rate limiting, and TLS termination, and any change to how services are decomposed internally becomes a breaking change for every external client. The API Gateway pattern fixes this by putting one component in front of the entire system that owns the concerns that are genuinely cross-cutting rather than specific to any one service's business logic.

A gateway typically owns:

  • Routing — mapping an external-facing path (/api/orders/*) to the correct internal service, using service discovery under the hood to find a live instance.
  • Authentication and authorization — validating a token (a JWT, a session cookie) once, at the edge, so individual services don't each need to re-implement token validation and can instead trust a header the gateway injects after validating (e.g., X-User-Id), or re-verify a lighter-weight signed claim.
  • Rate limiting and throttling — enforcing per-client or per-API-key request quotas in one place, rather than every service tracking its own counters and having no visibility into a client's total usage across services.
  • Request aggregation — for a single external call that logically needs data from multiple internal services (render a product page: needs the catalog service, the pricing service, and the reviews service), the gateway can fan out to all three internally and return one combined response, sparing the external client from making three round trips itself, each subject to full internet latency instead of low-latency internal network hops.
  • Cross-cutting operational concerns — TLS termination, request/response logging, and often the origination point for distributed trace IDs (section 6).

The reason this matters architecturally, not just operationally, is that it keeps individual services simple: a service can be written assuming the request that reaches it is already authenticated, already rate-limited, and already whatever protocol the gateway normalized it to — it just implements its own domain logic. Without a gateway, every one of those cross-cutting concerns either gets duplicated across every service (inconsistent, error-prone, and a maintenance burden multiplied by the number of services) or gets skipped somewhere, which is a security or reliability gap.

A gateway concentrates risk exactly where it concentrates value

Putting authentication, routing, and rate limiting for the entire system into one component means that component is now a single point of failure and a single point of compromise for everything behind it — if the gateway is down, external traffic can't reach any service at all, even ones that are perfectly healthy. This is why gateways are run as a horizontally scaled, independently deployed tier in their own right (many stateless instances behind a load balancer, exactly per hld-basics-scaling), not as a single box, and why gateway logic itself needs to be simple and heavily tested — a bug in gateway-level auth logic is a bug that affects every service simultaneously, unlike a bug in one service's own code, which is contained to that service.

4. Backend-for-Frontend (BFF)

A single, general-purpose gateway works well when all clients want roughly the same shape of data. It starts to strain when a mobile app and a web frontend genuinely need different things from the same underlying services — a mobile client on a metered, higher-latency connection wants a small, denormalized payload with exactly the fields its screen renders, aggregated server-side to avoid multiple round trips over a slow radio link; a web client with a rich UI might want a larger, more general response it can slice up differently across several components, or might want data shaped closer to how its component tree is structured.

Trying to satisfy both from one generic gateway API tends to produce one of two bad outcomes: either the API becomes a lowest-common-denominator, heavily parameterized endpoint stuffed with conditional fields and query flags that every client has to know how to use correctly, or one client's specific needs quietly leak into what's supposed to be a shared, general contract, and now a change requested by the mobile team risks breaking the web team's integration.

The Backend-for-Frontend pattern resolves this by giving each class of client (or sometimes each individual client application) its own dedicated aggregation layer — a mobile BFF and a web BFF — each calling the same underlying domain services, but each shaping, filtering, and combining the responses specifically for its own client's needs. The domain services underneath stay generic and don't need to know or care how many different front ends consume them; the client-specific shaping logic lives in the BFF, owned (ideally) by the team that owns that client, so a mobile-specific change doesn't require coordinating with or risking the web team's contract.

In practice these compose rather than compete: a single outer API gateway still often handles the truly universal cross-cutting concerns — TLS termination, global rate limiting, coarse routing, trace ID injection — and routes to the appropriate BFF based on which client is calling (often via a header or subdomain), and each BFF then does the client-specific aggregation against the underlying domain services. The decision to introduce a BFF at all should be driven by evidence that different clients' needs are actually diverging enough to justify the extra deployable units — introducing one prematurely, before that divergence is real, is just duplicated aggregation logic with no payoff yet.

5. Distributed Configuration

A monolith typically has one configuration file or one set of environment variables for the one process. A microservice architecture might have dozens of independently deployed services, each needing configuration (database URLs, feature flags, timeout values, third-party API keys), and — critically — needing it to be consistent and auditable across environments (dev, staging, production) without baking environment-specific values into a build artifact that then has to be rebuilt to change a single timeout value.

The config-server pattern (Spring Cloud Config is the standard implementation in the Spring ecosystem) centralizes this: configuration for every service and environment lives in one place — typically a Git repository, so that config changes are versioned, reviewable, and revertable exactly like code — and a dedicated config server exposes it over HTTP. Each service, on startup, fetches its own configuration from the config server rather than reading a local file, keyed by its service name and active profile (e.g., order-service-production.yml).

The more interesting capability is updating configuration without a redeploy. Because config now lives outside the service's packaged artifact, changing a value in the central Git repo doesn't require rebuilding or redeploying the service that uses it — it just requires that service to notice the change and refresh its in-memory configuration. Spring Cloud Config's typical mechanism for this is a /actuator/refresh endpoint (backed by @RefreshScope on beans that should pick up new values) that re-fetches config from the server and rebinds any @RefreshScope-annotated beans, without restarting the JVM. In a fleet with many instances, this refresh can be broadcast to all of them at once via a lightweight event bus (Spring Cloud Bus, typically riding on the same message broker used for async-messaging) rather than having to hit every instance's actuator endpoint individually.

What this buys beyond convenience

The deeper value isn't just "don't redeploy for a config change" — it's that config changes become auditable and consistent the same way code changes are: every change is a Git commit with a diff, an author, and a history, which matters enormously when trying to answer "what changed right before this incident" during an investigation. It also removes an entire class of deployment-coupling bugs where a service's behavior silently depends on whatever config happened to be baked into the artifact that was deployed, which is impossible to inspect or diff without redeploying an old version to compare.

6. Distributed Tracing

The problem: one request, many processes, one connected story to reconstruct

In a monolith, when a request is slow, you profile one process and get one call stack — the answer to "what was slow" is right there. In a microservice architecture, a single user-facing request might fan out to a gateway, which calls an order service, which calls an inventory service and a pricing service in parallel, and the pricing service calls a currency-conversion service. If the whole thing takes 800ms and the user complains, that 800ms is now scattered across five separate services' logs, each with its own timestamp format and no inherent way to tell you those five log lines were even part of the same user request, let alone which one of them accounted for most of the 800ms.

Distributed tracing solves this by attaching an identifier to a request at the moment it enters the system and propagating that identifier through every subsequent call the request triggers, so that after the fact, every log line and every timing measurement across every service can be joined back together into one reconstructed timeline.

Trace IDs, span IDs, and propagation

The two core identifiers:

  • Trace ID: one identifier generated when a request first enters the system (usually at the gateway or the first service it hits), shared by every operation performed anywhere in the system as a consequence of that single original request. Every log line and every span belonging to this request carries the same trace ID.
  • Span ID: an identifier for one specific unit of work within that trace — typically one service handling one request (or one significant internal operation, like a database query). A span records a start time, an end time (or duration), and metadata (which service, which operation, success/failure, relevant tags).

Spans form a tree via parent-child relationships: when service A calls service B, the span representing that call in A is the parent of the span B creates to represent its own handling of the request. This is what lets a tracing tool reconstruct not just "these five spans belong to the same trace" but the actual causal shape of the request — which call triggered which other call, and which calls happened in parallel versus in sequence.

Propagation is the mechanical part: the trace ID and the current span ID (which becomes the parent ID for whatever the callee creates) have to travel across every network boundary the request crosses. This is done via HTTP headers on every outbound call — the B3 propagation format (originated by Zipkin) is the common convention, using headers like X-B3-TraceId, X-B3-SpanId, and X-B3-ParentSpanId; the newer W3C Trace Context standard uses a single traceparent header carrying the same information in one packed value. Whichever format is used, the mechanic is identical: a service receiving a request reads these headers, and if it makes further downstream calls, it generates a new span ID for each of those calls, sets the parent to its own span ID, keeps the same trace ID, and sends all of that along in the outgoing headers.

Gateway         (trace=T1, span=S1,           parent=none)
  -> OrderSvc   (trace=T1, span=S2,           parent=S1)
       -> InventorySvc (trace=T1, span=S3,    parent=S2)
       -> PricingSvc   (trace=T1, span=S4,    parent=S2)
            -> CurrencySvc (trace=T1, span=S5, parent=S4)
Instrumentation has to happen at every hop, or the trace has a hole in it

Propagation is not automatic just because a tracing library is on the classpath somewhere in the system — every service in the chain has to both read the incoming trace headers and forward them on every outbound call it makes, including calls made from background threads, scheduled jobs triggered by the request, or messages published to a queue as a side effect. A common failure mode is a service that instruments its inbound HTTP handling (via something like Spring Cloud Sleuth or Micrometer Tracing auto-instrumenting a `RestTemplate`/`WebClient`) but then makes an additional outbound call using a raw, uninstrumented HTTP client, or hands work off to an executor that doesn't propagate the current trace context onto its new thread. The result isn't an error — it's a silent gap: the trace simply stops at that point, and everything downstream of the gap either gets no trace ID at all (starting a brand-new, disconnected trace) or loses its parent-child link back to the rest of the request, making the exact hop you most needed visibility into invisible.

How a tool like Zipkin turns this into something usable

Individually propagating IDs only gets you correlated data scattered across services; you still need somewhere to send it and something to visualize it. Each service, as it completes a span, reports it (usually asynchronously, batched, over HTTP or via a message queue, so tracing overhead doesn't sit on the request's critical path) to a collector — Zipkin is a widely used example, with Jaeger and various vendor-hosted equivalents (Datadog APM, honeycomb.io) filling the same role.

Zipkin stores spans keyed by trace ID and reconstructs, for any given trace, a waterfall/Gantt-style timeline: each span rendered as a horizontal bar, positioned by its start time and sized by its duration, nested under its parent span. This visualization directly answers the question a monolith's stack trace used to answer for free: looking at the waterfall for a slow request, you can see at a glance that, say, the gateway and order service and inventory service all finished quickly, but the pricing service's call to the currency service took 600 of the total 800 milliseconds — pinpointing exactly which downstream hop caused the slowness, rather than having to guess or add ad hoc timing logs to five services one at a time.

Tracing tells you where; it doesn't replace logs or metrics for why

A trace waterfall is extremely good at answering "which hop was slow" or "which service in the chain actually failed," but a span typically carries only coarse metadata (duration, status, a handful of tags) — it won't show you the specific exception stack trace or the exact input that triggered a failure. The practical pattern is to include the trace ID in every structured log line a service emits (this is what Spring Cloud Sleuth / Micrometer Tracing does automatically via MDC), so that once a trace waterfall points you at "the pricing service span failed," you can pivot directly to that service's logs filtered by that same trace ID and see the actual error. Tracing, logging, and metrics are complementary layers of the same observability problem, covered together in observability-production — tracing gives you the shape of the request across services, logs give you the detail within one span, and metrics give you the aggregate trend across many requests.

7. Synchronous vs Asynchronous Service Communication

Everything described above — discovery, gateways, tracing — has been framed around synchronous request/response calls (REST over HTTP, or gRPC for lower-latency, strongly-typed, binary communication). That's the right default for anything where the caller genuinely needs a result before it can proceed: an order service checking real-time inventory availability before confirming a purchase can't meaningfully continue without that answer, so a synchronous call, with the caller blocked (or its thread otherwise occupied) until the response arrives, models the actual dependency correctly.

But synchronous calls have a structural cost: the caller is coupled to the callee's availability and latency in that exact moment. If the inventory service is slow or down, the order service's request is slow or fails too, right then — and if this pattern repeats across a chain of synchronous calls, one slow downstream service can produce cascading latency or outages up the entire call chain (the specific failure modes and mitigations — timeouts, circuit breakers, bulkheads — are covered in resilience-fault-tolerance).

Asynchronous messaging (publishing an event to a broker like Kafka or RabbitMQ rather than calling a service directly) is the alternative when the caller doesn't actually need an immediate answer to proceed — it needs to guarantee the work eventually happens. When an order is placed, the order service doesn't need email confirmation, warehouse notification, and analytics tracking to complete before it can tell the customer "order placed" — those are all things that need to happen eventually and reliably, not synchronously and immediately. Publishing an OrderPlaced event and letting each interested service consume it independently decouples the order service from needing to know how many downstream consumers exist, decouples its own latency from theirs entirely, and lets a temporarily-down consumer catch up later from the broker's retained messages instead of causing the original request to fail.

Synchronous (REST/gRPC)Asynchronous (messaging)
Caller needs an immediate resultYes — this is the pointNo — caller only needs eventual completion
Coupling to callee's availabilityTight — callee down means caller affected nowLoose — broker buffers until consumer is ready

Typical useRead-your-result-now calls: availability checks, auth, price lookupsFire-and-eventually-process: notifications, analytics, cross-service side effects

Distributed tracing spans this boundary too, though it's harder: propagating a trace ID through an HTTP header on a synchronous call is straightforward, but propagating it through a message that gets published now and consumed seconds or minutes later means embedding the trace context in the message's own headers/metadata (Kafka message headers, for instance) so that whenever the consumer eventually processes it, it can pick the trace back up and record its own span as a (temporally disconnected) child of the original request's trace. Real systems typically end up using both communication styles side by side — synchronous for anything the current request depends on, asynchronous for anything that can and should happen independently — and that combination, along with the specific delivery guarantees and failure semantics of message brokers, is where async-messaging picks up.

Concepts Worth Being Able to Explain From First Principles

Why can't a service just hardcode the IP addresses of the other services it depends on?
A hardcoded IP assumes the thing on the other end of it is a stable, fixed resource, which was true for a monolith's in-process function calls but is false for independently deployed service instances. Autoscaling adds and removes instances in response to load, rolling deploys replace instances (in a containerized environment, typically with an entirely new IP each time), and crashes remove instances unpredictably. A hardcoded address would need to be updated, and the depending service redeployed, every single time any of that happens on the other side — which defeats the entire premise of independent deployability that microservices are supposed to provide. Service discovery replaces a fixed address with a live query against a registry that's always current, so the calling service is decoupled from needing to know or care how the callee's instance fleet is currently shaped.
What actual problem does Eureka's heartbeat-and-lease model solve that a simpler "registry pings every instance" model wouldn't?
If the registry were responsible for actively polling every registered instance's health, its own load would scale with the total number of instances in the entire system, turning it into a bottleneck exactly as the fleet it's supposed to serve grows — the component with the strictest availability requirement in the whole architecture would also be the one with the worst scaling characteristics. Flipping the responsibility so each instance proactively renews its own lease means the registry's workload per instance is just "receive and record a small heartbeat," which is cheap and scales linearly and passively rather than requiring the registry to actively manage a polling schedule against every instance. It also means an instance that can't reach the registry (a network partition on the instance's side) naturally times out and gets evicted without the registry needing to distinguish "instance is dead" from "instance can't reach me" — both cases just look like a missed lease renewal.
Why does an API gateway make individual services simpler, rather than just moving complexity somewhere else for free?
It's genuinely moving complexity, not eliminating it, but it moves duplicated complexity into shared complexity, which is a real reduction in total system complexity even though the gateway itself has to do real work. Without a gateway, every service would need to implement its own token validation, its own rate-limiting counters, its own TLS termination — logic that's identical in intent across every service but has to be written, tested, and kept consistent N times, and any inconsistency between two services' implementations of "validate this token" is a security gap. Centralizing it means it's implemented once, tested once, and every service downstream can simply trust that a request reaching it has already been authenticated and rate-limited, reducing what each individual service actually needs to reason about to just its own domain logic. The trade is that the gateway becomes a single, higher-stakes point of failure and a single target whose correctness now matters for the whole system at once — a trade that's usually worth it, but not a free one.
How does a parent-child span relationship let a tracing tool reconstruct the shape of a request, not just which spans belong to it?
A shared trace ID alone only tells you which spans are part of the same overall request — it's an unordered set. The parent-child relationship, recorded via each span carrying the span ID of whichever call caused it to exist, adds the causal structure on top: it tells you that the order service's call to the inventory service was triggered by (and is nested inside) the gateway's original span, and that the pricing service's call to the currency service was triggered by, and nested inside, the pricing service's own span. Reconstructing this tree from the flat set of spans is what lets a visualization show which operations were sequential (a child that starts only after its parent has been running for a while, with a sibling span squeezed in before or after) versus genuinely parallel (two children of the same parent with overlapping time ranges), which is exactly the information you need to tell "this service waited on that service" apart from "these ran independently and both contributed to total time."
Why is a Backend-for-Frontend a different pattern from just adding more parameters or optional fields to one shared gateway API?
Adding parameters and optional fields to satisfy divergent client needs keeps everyone on one shared contract, but the contract itself becomes a superset of every client's requirements, forcing every client to understand fields and flags that exist only for a different client's benefit, and forcing any change to one client's needs through a review process that has to consider whether it breaks every other client sharing that same endpoint. A BFF instead gives each client class its own contract, entirely tailored to what it needs, with no obligation to remain generic or backward-compatible with a different client's usage. The underlying domain services stay untouched by any of this client-specific shaping — they're called the same way regardless of which BFF is calling them — so the churn and specialization needed to satisfy one client's UI never pressures the shared services or any other client's integration.
Why does Eureka's self-preservation mode intentionally stop being accurate under certain conditions, rather than always evicting instances that miss their heartbeat?
A registry has no direct way to distinguish "a large number of instances actually died" from "the registry itself lost network connectivity to a healthy fleet" — both produce the identical symptom of many missed heartbeats arriving at once. If the registry always trusted the missed-heartbeat signal literally, a transient network partition on the registry's side would cause it to evict most or all of a perfectly healthy fleet, and then hand out an empty or near-empty instance list to every client doing discovery — turning a temporary, partial network problem into a total outage across the whole system, since nothing could discover anything. Self-preservation mode treats "an unusually large fraction of the fleet missed a heartbeat in a short window" as more likely to indicate a problem with the registry's own connectivity than with the fleet, and chooses to keep serving its last known (possibly slightly stale) list rather than confidently but wrongly emptying it out. The cost is that some calls may occasionally route to an instance that is actually dead, but that failure is local and recoverable (the caller's request fails and can retry against a different instance), whereas the alternative failure mode is global and much harder to recover from.
Given a request that touches five services, why would you choose synchronous calls for some of those hops and asynchronous messaging for others, rather than picking one style for the whole request?
The deciding question for each individual hop is whether the caller's own ability to proceed and respond genuinely depends on that specific downstream result. Checking whether an item is in stock before confirming a purchase is a hard dependency — the order service cannot correctly respond to the customer without that answer, so it has to be a synchronous call it waits on. Sending a confirmation email, updating an analytics pipeline, or notifying a warehouse system are not hard dependencies of being able to tell the customer "your order is placed" — those things need to happen reliably, but not before the response is returned, and not even necessarily by the time the response is returned. Modeling those as synchronous calls would make the customer's checkout latency include the sum of the email service's, the analytics service's, and the warehouse service's response times, and a slow or momentarily down email service would make checkout itself fail or hang for a completely unrelated reason. Publishing an event for those and letting each downstream consumer process it independently and asynchronously correctly matches the actual dependency structure of the work, rather than artificially serializing unrelated concerns into one blocking chain.
