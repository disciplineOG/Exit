Most Asked Interview Questions: Hibernate, JPA & ORM

Why this matters

Almost every backend Java role touches a relational database through JPA (Java Persistence API) and Hibernate, and interviewers use this topic to separate people who can annotate an entity from people who understand what happens underneath — flush timing, lazy loading, N+1 queries, and lock contention are exactly the things that cause real production incidents. Questions here also double as a proxy for "do you understand transactions," since ORM (Object-Relational Mapping) behavior and transaction boundaries are inseparable in practice. Expect at least a few questions from this page in almost any mid-to-senior backend interview.

JPA & Hibernate Basics

What is ORM, and why use it instead of writing plain JDBC?
ORM (Object-Relational Mapping) is a technique for automatically translating between Java objects and relational database rows/tables, so application code works with domain objects like Order and Customer instead of manually writing SQL (Structured Query Language) and mapping ResultSet columns by hand. Plain JDBC (Java Database Connectivity) requires you to write every SQL statement yourself, manually map each result column into an object field, manage connections and prepared statements explicitly, and hand-roll caching and dirty-tracking if you want them — all of this is repetitive, error-prone boilerplate that has to be redone for every entity. An ORM like Hibernate generates that SQL for you, tracks which objects have changed and issues only the necessary UPDATEs, manages a cache so repeated reads of the same row don't re-hit the database, and lets relationships between tables be navigated as object references (order.getCustomer().getName()) instead of manual joins. The trade-off is a learning curve and less direct control over exactly what SQL runs, which is why performance-critical or highly custom queries often still drop down to native SQL or JDBC directly even in an ORM-based codebase; for the bulk of everyday CRUD (Create, Read, Update, Delete) work in a service like order-service, though, the productivity and consistency gains from an ORM outweigh that cost.
What is the difference between JPA, Hibernate, and Spring Data JPA?
JPA (Java Persistence API) is a specification — a set of interfaces and annotations (@Entity, EntityManager, JPQL (Java Persistence Query Language), etc.) that define how Java objects should be mapped to relational tables, without providing any actual implementation. Hibernate is the most widely used implementation of that specification — it is the concrete ORM (Object-Relational Mapping) engine that generates SQL, manages caching, and tracks entity state, and it also ships extra features beyond the JPA spec (like its own criteria API extensions and multi-tenancy support). Spring Data JPA is a further abstraction layer on top of JPA (backed by Hibernate or another provider like EclipseLink) that eliminates boilerplate by letting you declare repository interfaces (extending JpaRepository) and have Spring generate the implementation, including derived queries from method names. In short: JPA is the "what," Hibernate is the "how," and Spring Data JPA is the "don't make me write this by hand" layer on top of both.
What is the EntityManager and what is the persistence context?
The EntityManager is the core JPA API used to perform CRUD (Create, Read, Update, Delete) operations, run queries, and manage entity state; it is the client-facing handle to Hibernate's underlying Session. The persistence context is the first-level cache and unit-of-work that the EntityManager owns — it is a map of entity identity to entity instance for everything that has been loaded or saved during the current session. While an entity is inside the persistence context, Hibernate tracks changes to it automatically, and repeated lookups by the same primary key within that context return the exact same Java object reference (this is called identity map behavior). The persistence context is typically scoped to a single transaction in a Spring-managed application, so it is created and discarded per business operation, for example the lifetime of a single "place order" call in order-service.
What are the entity lifecycle states in JPA?
A JPA entity moves through four states. Transient means the object was just created with new and has no association with the persistence context or the database at all — a plain, unmanaged Java object. Managed (persistent) means the entity is currently tracked by an active persistence context, meaning any field changes will be detected and flushed to the database automatically; an entity becomes managed after calling persist(), or after being loaded via find() or a query. Detached means the entity was managed at some point but the persistence context has since closed (for example, the transaction ended) — the object still has data and an identifier, but changes to it are silently ignored until it is reattached with merge(). Removed means remove() has been called on a managed entity, marking it for deletion when the persistence context next flushes. Confusing detached with managed is a classic bug source: mutating a detached Order object after its transaction ended does nothing until you explicitly merge it back in.
What is dirty checking in Hibernate?
Dirty checking is Hibernate's mechanism for automatically detecting that a managed entity's field values have changed since it was loaded, and issuing the corresponding UPDATE SQL at flush time — without the developer ever calling an explicit "save" or "update" method. Hibernate does this by keeping a snapshot of the entity's original state when it was loaded into the persistence context, and at flush time (end of transaction, or an explicit flush()) it compares the current field values against that snapshot. If a Seller updates a Product's price field on a managed entity inside a @Transactional method, Hibernate will detect that difference and generate an UPDATE products SET price = ? statement with no further code needed. This is convenient but has a cost: for entities with many fields, or bytecode-enhancement-free setups, computing that diff on every flush adds overhead, which is why some teams use immutable/read-only entities or DTOs (Data Transfer Objects) for read-heavy paths to skip dirty checking entirely.
What do @Entity, @Id, and @GeneratedValue do?
@Entity marks a plain Java class as a JPA-managed entity, telling the persistence provider it should be mapped to a database table (by default, a table named after the class, though @Table can override that). @Id designates the field that serves as the entity's primary key, which JPA uses for identity comparisons and as the key in the first-level cache. @GeneratedValue tells the provider that the primary key should be generated automatically rather than assigned by application code, and its strategy attribute (IDENTITY, SEQUENCE, AUTO, or TABLE) controls exactly how. For example, a ShopSphere Order entity would typically declare @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id; so the database allocates a unique order ID on insert.
What are the trade-offs between IDENTITY, SEQUENCE, and UUID primary key strategies at scale?
IDENTITY relies on a database auto-increment column, which is simple but forces Hibernate to execute the INSERT immediately to learn the generated ID, which disables JDBC batch inserts and hurts throughput when writing many rows at once (for example, bulk-inserting OrderItem rows). SEQUENCE uses a database sequence object that Hibernate can pre-fetch in batches (via the allocationSize setting), so it can assign IDs in memory before the insert and still batch statements efficiently — this is generally the preferred strategy on databases that support sequences (PostgreSQL, Oracle) for write-heavy services like order-service. UUID (Universally Unique Identifier) primary keys are generated in application code with no database round-trip and are ideal for distributed systems where IDs must be unique across multiple services or databases without coordination (for example, an event ID that flows through Kafka from order-service to inventory-service), but a random UUID as a clustered/primary index key causes index fragmentation and worse insert locality than a monotonically increasing key, which can hurt write performance on large tables unless a time-sortable variant (like UUIDv7) is used. The practical trade-off is: SEQUENCE for single-database throughput, UUID for distributed uniqueness, with awareness that raw random UUIDs cost you index efficiency at high volume.
What is the difference between persist(), merge(), and save()?
persist() is the standard JPA operation for making a transient (brand-new) entity managed: it schedules an INSERT and, if you are using SEQUENCE or IDENTITY generation, assigns the entity its generated ID as a side effect, but it must only be called on a transient instance — calling it on a detached entity (one with an ID Hibernate doesn't already track in this context) throws an exception. merge() is the JPA operation for reattaching a detached entity: rather than making the object you passed in managed, it copies that object's state onto a managed entity (loading one from the database first if needed) and returns that managed copy, which is why the common bug is calling merge() and continuing to use the original reference instead of the returned one. save() is not part of the JPA spec at all — it is a Hibernate-native Session method (and also the name Spring Data JPA's CrudRepository uses for its own save operation, implemented internally as a persist-or-merge decision based on whether the entity's ID is null) that always returns the generated identifier. In a Spring Data JPA codebase you almost always call repository.save(entity) and let Spring Data decide between insert and update; understanding persist() versus merge() directly matters most once you drop to the raw EntityManager API.
What is the difference between EntityManager.find() and getReference() (or Hibernate's get() vs load())?
find() (Hibernate's older API calls this get()) hits the database immediately (or the first/second-level cache) and returns a fully initialized entity, or null if no row exists with that ID. getReference() (Hibernate's load()) does not query the database at all up front — it returns a lazy proxy that only fires a SELECT the moment one of its real fields is accessed, and if no row actually exists for that ID, you don't find out immediately; instead you get an EntityNotFoundException later, when the proxy is finally initialized. getReference() is useful purely as a performance optimization when you only need the ID to set up an association and never intend to read any other field, for example orderItem.setProduct(entityManager.getReference(Product.class, productId)) avoids a wasted SELECT on Product just to link it to a new OrderItem. The trade-off is safety versus one fewer query: reach for getReference() only when you are confident the row exists and you won't touch its fields, otherwise the deferred exception can surface in a confusing place far from where the bad ID was actually used.
What is the difference between JPQL, native SQL queries, and the Criteria API?
JPQL (Java Persistence Query Language) is an object-oriented query language that looks like SQL (Structured Query Language) but operates on entity names and field names rather than table and column names (SELECT o FROM Order o WHERE o.status = :status), so it stays portable across different databases and lets you navigate entity associations directly in the query. Native queries (@Query(value = "...", nativeQuery = true), or entityManager.createNativeQuery(...)) drop down to raw, database-specific SQL, which is necessary when you need a vendor-specific feature JPQL can't express — window functions, full-text search, database hints, or a heavily optimized query a DBA (Database Administrator) hand-tuned — at the cost of losing portability and, for non-entity result sets, losing automatic object mapping. The Criteria API builds queries programmatically as Java objects (CriteriaBuilder, CriteriaQuery, Root) instead of as query strings, which makes it well suited to queries whose structure depends on runtime conditions, such as a product search endpoint in catalog-service that adds a variable number of WHERE clauses depending on which filters (price range, category, seller) the customer actually applied; the trade-off is that Criteria API code is considerably more verbose and harder to read than the equivalent JPQL string. Most teams default to JPQL or Spring Data derived/@Query methods for anything static, and reach for the Criteria API (or a library like QueryDSL built on top of it) only when query shape is genuinely dynamic.

Fetching & Performance

What is the difference between lazy and eager fetching, and what causes a LazyInitializationException?
Eager fetching (FetchType.EAGER) loads an association immediately, as part of the same query (or an additional immediate query) that loads the owning entity, while lazy fetching (FetchType.LAZY) defers loading the association until it is actually accessed in code, returning a proxy object in the meantime. LazyInitializationException occurs when code tries to access a lazy association (for example, calling order.getOrderItems().size()) after the persistence context that would have fetched it has already closed — the proxy has no active session left to run the query through, so it throws instead of silently returning nothing. This commonly happens when an entity is loaded inside a @Transactional service method, returned to a controller, and then a view or serializer tries to touch a lazy field outside that transaction. Fixes include fetching what you need inside the transaction (via a fetch join or entity graph), restructuring the query to eagerly load only the needed associations, or using DTO projections so the web layer never touches a managed entity at all.
What is the N+1 select problem, and how do fetch joins or entity graphs fix it?
The N+1 select problem happens when you run one query to fetch a list of N parent entities, and then, because an association is lazily fetched, Hibernate triggers one additional query per parent to fetch each one's related collection or reference — resulting in 1 + N total queries instead of one efficient query. For example, fetching 100 Orders and then looping over each to read its Customer triggers 1 query for the orders plus 100 queries for the customers, one per row. A fetch join (JPQL: SELECT o FROM Order o JOIN FETCH o.customer) fixes this by pulling the association into the same SQL query via a SQL JOIN, so it comes back in a single round trip. An entity graph (@EntityGraph, or a dynamically built EntityGraph) achieves the same result declaratively without hand-writing JPQL joins, letting you specify per-query which associations should be eagerly loaded regardless of how the entity itself is mapped. Both approaches trade a wider result set (and potential duplicate rows for collection joins, which usually calls for DISTINCT) for eliminating the round-trip explosion, which is almost always the right trade at any real scale.
What is the difference between the first-level cache and the second-level cache?
The first-level cache is the persistence context itself — it is mandatory, always on, and scoped to a single EntityManager/Hibernate Session (in practice, one transaction), meaning it disappears as soon as that transaction ends and cannot be shared across requests. The second-level cache is optional, must be explicitly configured (via a provider like Ehcache or Infinispan plus @Cacheable/@Cache annotations), and is scoped to the SessionFactory (i.e. the whole application), so entities loaded by one transaction can be served from cache to a completely different transaction later without hitting the database. Second-level caching is a good fit for read-heavy, rarely-changing data, such as a ShopSphere catalog-service caching Product records, but it is risky for frequently updated data like Inventory stock counts, where a stale cached read could let two customers both believe an item is in stock. Because the second-level cache sits outside transaction boundaries, teams must also think carefully about cache invalidation and, in clustered deployments, about keeping the cache consistent across nodes.
How does pagination work in JPA, and where does it hurt performance at high offsets?
JPA pagination is typically done with Query.setFirstResult(offset) and setMaxResults(pageSize), which Hibernate translates into database-specific LIMIT/OFFSET (or ROW_NUMBER() window functions) clauses. The catch is that OFFSET-based pagination is not free: to return, say, rows 100,000–100,020, most databases still have to scan and discard the first 100,000 matching rows before returning the next 20, so query cost grows roughly linearly with the offset even though the page size stays constant. This becomes a real problem browsing deep into a large Order history table in ShopSphere — page 1 is fast, but page 5,000 can be dramatically slower. The standard fix is keyset (or "seek") pagination: instead of skipping N rows, you filter with WHERE id > :lastSeenId ORDER BY id LIMIT :pageSize, which lets the database use an index to jump straight to the next page regardless of how deep you are, at the cost of losing the ability to jump to an arbitrary page number directly.
Besides fetch joins and entity graphs, what other techniques reduce N+1 and over-fetching in practice?
@BatchSize(size = N) (Hibernate-specific, applied on an entity or a collection mapping) doesn't eliminate the extra queries the way a fetch join does, but it batches them: instead of one query per parent for a lazy association, Hibernate rewrites the lookups to fetch up to N parents' associations per query using an IN (...) clause, cutting 100 queries down to something like 10. @Subselect or projection-based DTO (Data Transfer Object) queries sidestep the problem entirely by selecting only the exact columns needed with a JPQL constructor expression (SELECT new com.shopsphere.OrderSummaryDto(o.id, o.status, c.name) FROM Order o JOIN o.customer c), which avoids loading full entity graphs, avoids proxies, and avoids the persistence context altogether for pure read paths. Hibernate also ships a statistics/interceptor mechanism (and tools like the open-source datasource-proxy or p6spy libraries) that logs actual SQL statement counts, which is how N+1 problems are usually caught in the first place — in code review it's invisible, but in a query log a list endpoint firing 200 queries for 20 rows stands out immediately. In production, teams often combine an integration test that asserts a maximum query count for a given endpoint with APM (Application Performance Monitoring) query-count dashboards, because N+1 regressions are easy to reintroduce silently when a new field is added to a serializer.

Relationships & Transactions

How do @OneToMany, @ManyToOne, and @ManyToMany mappings work?
@ManyToOne is the "owning side" mapping used on the entity that holds the foreign key column, for example an Order entity having a @ManyToOne private Customer customer; field backed by a customer_id column — this is almost always the cheapest and most common direction to map because it requires no extra join table. @OneToMany is typically the inverse side of that same relationship, declared on the "one" entity (a Customer having @OneToMany(mappedBy = "customer") List<Order> orders;), and it is usually configured with mappedBy to tell Hibernate not to expect its own foreign key column, since the @ManyToOne side already owns that. @ManyToMany models relationships where both sides can have many of the other, such as Products belonging to many Categories and Categories containing many Products, and Hibernate implements it using a separate join table with two foreign keys; in practice, many teams replace @ManyToMany with two @OneToMany/@ManyToOne relationships against an explicit join entity once that join table needs its own columns, like a quantity on a CartItem linking Cart and Product.
What problems come up with bidirectional relationships, like infinite recursion when serializing to JSON?
When both sides of a relationship reference each other — a Customer holding a List<Order> and each Order holding a Customer back-reference — a naive JSON (JavaScript Object Notation) serializer like Jackson will happily follow customer to orders, then each order back to customer, then back to orders again, recursing until it hits a StackOverflowError. The standard fixes are @JsonManagedReference/@JsonBackReference to break the cycle by only serializing one direction, @JsonIgnore on one side entirely, or — the approach most production codebases settle on — never serializing entities directly at all and instead mapping to dedicated response DTOs (Data Transfer Objects) that only include the fields the API contract actually needs. A second, easy-to-miss bug in bidirectional mappings is forgetting to keep both sides in sync in application code: calling customer.getOrders().add(order) alone does nothing to the database if Order is the owning side, because Hibernate only looks at the owning side's foreign key field when deciding what to persist, so teams typically add a helper method like addOrder(Order o) on Customer that sets both this.orders.add(o) and o.setCustomer(this) together.
What are cascade types and orphanRemoval, and how do they differ?
Cascade types (set via the cascade attribute on a relationship annotation, e.g. CascadeType.PERSIST, MERGE, REMOVE, REFRESH, DETACH, or ALL) control whether an operation performed on a parent entity should automatically propagate to its associated child entities. For example, cascade = CascadeType.PERSIST on Order.orderItems means saving the Order also automatically saves its OrderItem children without a separate explicit save call for each. orphanRemoval = true is a related but distinct setting: it specifically tells Hibernate to delete a child entity when it is removed from the parent's collection (or the parent itself is deleted), even if no cascading remove() was explicitly called — for example, calling order.getOrderItems().remove(item) would actually issue a DELETE for that OrderItem row. The distinction matters: CascadeType.REMOVE only cascades an explicit deletion of the parent, whereas orphanRemoval also catches the more subtle case of a child simply being unlinked from its parent's collection. Both should be used carefully on @ManyToOne/@ManyToMany parent-owned collections, since cascading REMOVE the wrong way can silently delete shared data, like accidentally deleting a Product because it was removed from one Seller's catalog list.
What are the common @Transactional propagation types and isolation levels?
Propagation controls how a transactional method behaves when it is called from inside another transaction. REQUIRED (the default) joins the existing transaction if one is active, or starts a new one if not — this is what you want for most service methods, like a placeOrder method that should be part of whatever transaction called it. REQUIRES_NEW always suspends any existing transaction and starts a fresh, independent one, useful when a sub-operation (like writing an audit log entry) must commit regardless of whether the outer transaction later rolls back. Other propagation types include NESTED (a savepoint within the same physical transaction that can be rolled back independently), SUPPORTS (joins if a transaction exists, otherwise runs non-transactionally), MANDATORY (throws if no transaction exists), and NOT_SUPPORTED/NEVER (explicitly run outside a transaction). Isolation levels control how much one transaction can see of another's uncommitted or concurrently changing data: READ_UNCOMMITTED allows dirty reads, READ_COMMITTED (a common default) prevents dirty reads but still allows non-repeatable reads, REPEATABLE_READ prevents those too but allows phantom rows, and SERIALIZABLE is the strictest, effectively executing transactions as if they ran one at a time at the cost of the most contention. A payment-service processing a Payment would typically want at least READ_COMMITTED, and possibly stronger guarantees around balance checks to avoid double-spending races.
What is the difference between optimistic locking and pessimistic locking?
Optimistic locking assumes conflicts are rare and detects them only at commit time, typically implemented in JPA with a @Version column: every update includes a WHERE version = :originalVersion clause, and if another transaction already updated the row (bumping the version), zero rows match and Hibernate throws an OptimisticLockException for the application to retry or surface as a conflict. Pessimistic locking instead assumes conflicts are likely and prevents them upfront by acquiring an actual database row lock at read time (LockModeType.PESSIMISTIC_READ or PESSIMISTIC_WRITE, translating to SELECT ... FOR SHARE/FOR UPDATE), blocking other transactions from touching that row until the lock is released. Optimistic locking scales better under low contention because it never blocks, making it a good fit for something like a Product edit form where two Sellers rarely edit the same Product simultaneously. Pessimistic locking is safer under high contention on a single hot row, such as decrementing Inventory stock for a flash-sale Product where many concurrent Orders are competing for the same row and you would rather serialize access than have most of them fail and retry.
Why does a @Transactional method calling another method in the same class not get proxied (the self-invocation problem)?
Spring implements @Transactional (and most other declarative annotations like @Cacheable or @Async) using proxies: by default it wraps your bean in either a JDK dynamic proxy (if it implements an interface) or a CGLIB subclass proxy, and the transactional logic runs in that proxy's method interceptor before delegating to your actual method. When code inside the bean calls another method on this directly (self-invocation), that call goes straight to the real object's method, completely bypassing the proxy wrapper — so the interceptor that would have started a new transaction or checked propagation never runs. Concretely, if OrderService.placeOrder() is not itself @Transactional but calls this.chargeAndReserve() which is annotated @Transactional, that inner call will silently execute non-transactionally. The standard fixes are to move the called method into a separate Spring-managed bean and inject that bean instead (so the call goes through the proxy), or to inject a self-reference proxy of the same bean, or in some cases to use AopContext.currentProxy(); the underlying lesson interviewers are checking for is understanding that Spring's declarative annotations are proxy-based AOP (Aspect-Oriented Programming), not bytecode magic that works on every call site.
By default, does @Transactional roll back on every exception?
No — Spring's default rollback rule only rolls back a transaction on unchecked exceptions, meaning RuntimeException (and its subclasses) or Error; a checked exception (any Exception that is not a RuntimeException, declared with throws) is allowed to propagate out of a @Transactional method and the transaction will still be committed. This trips people up constantly: if chargeCard() in payment-service throws a checked PaymentDeclinedException, Spring commits whatever was written so far unless you tell it otherwise. The fix is to explicitly declare @Transactional(rollbackFor = PaymentDeclinedException.class), or design failure paths around unchecked exceptions instead. There is also noRollbackFor for the opposite case — excluding a specific unchecked exception type from triggering a rollback. The underlying reason for the default is historical: it mirrors EJB (Enterprise JavaBeans) container-managed transaction semantics, which treated checked exceptions as expected business outcomes and unchecked exceptions as unexpected failures.
Why is it risky to base equals() and hashCode() on an auto-generated database ID in a JPA entity?
A newly created (transient) entity has a null ID until it is persisted and the database assigns one, so if equals()/hashCode() are based purely on the ID field, every transient instance compares as "equal" to every other transient instance of that type (all have the same null ID), which means a HashSet of unsaved entities silently collapses distinct objects into one, or a Map keyed on them behaves incorrectly, until each one is actually persisted and gets a real, distinct ID. It also breaks the Java contract that an object's hash code should not change over its lifetime: the same object's hash code changes the moment it goes from transient (null ID) to managed (assigned ID), so if you insert it into a HashSet before saving, you may never find it again after the ID is assigned because it now hashes to a different bucket. A safer approach is to base equals()/hashCode() on a stable natural/business key that is known before persistence (for example, a Customer's email address, or a Product's SKU (Stock Keeping Unit)), or, if no such key exists, to use a constant hash code and an identity-based equality check that also accounts for Hibernate proxies (comparing getClass() can fail against a proxy subclass, so instanceof is typically preferred).
