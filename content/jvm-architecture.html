JVM Architecture, Memory Model & Garbage Collection

Why this matters
Everything a Java program does — every object, every thread, every field access — is mediated by the JVM. Understanding its internals turns "my service crashed with an OutOfMemoryError" from a mystery into a diagnosis, and turns "why did this static field print 0 instead of 42" from a surprise into an expected consequence of a well-defined lifecycle. This page builds the complete mental model from the ground up: how a class becomes runnable, where every piece of runtime state physically lives, how bytecode actually executes, and how memory gets reclaimed.

1. The Big Picture: What "JVM" Actually Means

The JVM specification defines three independent-but-connected subsystems. Every other topic on this page is a detail inside one of these three:

  1. Class Loader Subsystem — finds, reads, verifies, and prepares .class bytecode, and turns it into runtime Class objects.
  2. Runtime Data Areas (Memory) — where loaded classes, objects, threads, and execution state actually live: Heap, Stack, Metaspace, PC Registers, Native Method Stacks.
  3. Execution Engine — actually runs the bytecode: the Interpreter, the JIT Compilers (C1/C2), and the Garbage Collector that reclaims memory in the Heap.

2. Class Loading — The Full Lifecycle

A class goes through five distinct phases before you can use it. This ordering is exactly what determines when static fields get their values and when static blocks run.

2.1 Loading

The classloader locates the .class file (from disk, JAR, or network) and reads its binary data into the Method Area, creating an in-memory representation. A java.lang.Class object representing this class is created and placed in the heap (the class's metadata lives in Metaspace, but the Class object itself is a heap object).

2.2 Linking

Linking has three sub-phases, always in this order:

  • Verification — the bytecode verifier checks structural correctness: valid jump targets, correct operand stack types, no illegal type casts, access control rules honored. This is what stops corrupted or hand-crafted invalid bytecode from crashing or exploiting the JVM.
  • Preparation — memory is allocated for static (class) variables and they are set to their default values (0, 0.0, false, null) — not their initializer values yet. A static int count = 42; is 0 at the end of Preparation, not 42. The initializer expression hasn't executed yet — that happens later, in Initialization (§2.3).
  • Resolution — symbolic references in the constant pool (class names, field names, method signatures stored as strings/indices) are resolved to direct references or memory offsets. In modern JVMs this is largely lazy — resolved on first actual use rather than eagerly for every reference. That laziness is why a reference to a missing class can compile fine and even run fine, only failing with NoClassDefFoundError the first time that specific code path actually executes.

2.3 Initialization — where static blocks and static field initializers actually run

This is the phase that governs exactly when a static variable gets its real value and when a static block executes. The JVM specification guarantees:

  • Static variable initializers and static initializer blocks (static { ... }) execute in textual (top-to-bottom) source order, exactly as written, as if the compiler concatenated them into one implicit method called <clinit>.
  • Initialization of the superclass always completes before the subclass's static initializers run. The JVM walks up to Object and initializes top-down (full mechanics and a worked trace in §2.4).
  • A class is initialized lazily, on first active use — not at load time, and not at link time. Active use includes: creating an instance (new), invoking a static method, reading or assigning a static field (except a compile-time constant — see below), or doing any of the above reflectively. Merely referencing another class's static final field does not always count as active use: if that field is a compile-time constant (a primitive or String literal the compiler can fully resolve at compile time), javac inlines the literal value directly into the caller's bytecode. The caller never actually touches the defining class at runtime, so its static block never fires from that access alone.
  • Initialization is thread-safe and happens exactly once per class per classloader, guarded by a lock the JVM manages internally on the class object. This guarantee — "exactly once, and every other thread blocks until it's done" — is the entire basis of the "initialization-on-demand holder" idiom for lazy, thread-safe singletons without explicit synchronization.

2.4 Inheritance Loading & Initialization Order — a generic algorithm for any hierarchy

Rather than memorizing one example, internalize the algorithm. It works for any hierarchy of any depth. Given a chain GrandParent → Parent → Child and a statement new Child(), there are two completely separate passes that never interleave with each other:

The algorithm

PASS 1 — Static initialization (runs at most once per class, ever, per classloader, triggered by the first active use of that class):

  1. Find the topmost not-yet-initialized class in the hierarchy (walk up via extends toward Object).
  2. For each class from top to bottom, if it isn't already initialized: run its static field initializers and static blocks interleaved in textual source order (top-to-bottom exactly as written in that one class's source file).
  3. Interfaces: a superinterface is initialized before the implementing class only if that interface declares at least one default (or static) method — a marker interface holding only constants is not initialized merely because a class implements it, since its constants are inlined at compile time wherever referenced. Interface fields are always implicitly public static final.

PASS 2 — Instance construction (runs every single time, for every new):

  1. Allocate the object on the heap. Every field at every level of the hierarchy is zeroed to its type's default (0 / false / null) — this happens for the entire object before any constructor body runs anywhere.
  2. Enter the Child constructor. The very first thing that happens — whether you wrote it explicitly or the compiler inserted it for you — is a call to super(...). This recurses: Parent's constructor itself first calls its own super, and so on, all the way up to Object.
  3. Now the stack unwinds back down. At each level, immediately after that level's super(...) call returns, but before the rest of that level's constructor body executes, that level's instance field initializers and instance initializer blocks run, in textual source order.
  4. Then the remainder of that level's constructor body executes.
  5. Control returns one level down (e.g. from the finished Parent() body back into Child(), right after its super() line) and steps 3–4 repeat for that level, continuing until Child's own body finishes.

Two consequences fall directly out of this algorithm and resolve almost any ordering question you can construct:

  • All of Pass 1, for every class in the chain, always finishes before Pass 2 even begins — but only for the very first object ever created from that hierarchy. On the second and any later new call, Pass 1 is skipped entirely (every class is already initialized) and only Pass 2 runs.
  • Within Pass 2, the two orders run in opposite directions: the dive (via chained super() calls) goes Child → Parent → GrandParent, but the actual initializer/constructor-body execution, as the stack unwinds, goes GrandParent → Parent → Child.

2.5 A fully worked trace: field hiding, dynamic dispatch, and overriding together

This example deliberately combines several interacting mechanics in one hierarchy so you can see how they compose — and so you can pattern-match any other hierarchy an example throws at you against the same shape.

class GrandParent {
    static int sCounter = log("GP static field", 100);
    static { log("GP static block", null); }

    int id = log("GP instance field", 1);
    { log("GP instance block", null); }

    GrandParent() {
        log("GP constructor start", null);
        describe();              // virtual call on a not-yet-fully-constructed object
        log("GP constructor end", null);
    }

    void describe() { log("GP.describe()", null); }

    static int log(String tag, Integer val) {
        System.out.println(tag + (val != null ? " = " + val : ""));
        return val == null ? 0 : val;
    }
}

class Parent extends GrandParent {
    static { log("Parent static block", null); }

    int id = log("Parent instance field", 2);   // hides GrandParent.id, does NOT override it
    { log("Parent instance block", null); }

    Parent() {
        // implicit super(); inserted here by the compiler
        log("Parent constructor start", null);
        log("Parent constructor end", null);
    }

    @Override
    void describe() { log("Parent.describe(), sees id=" + id, null); }
}

class Child extends Parent {
    static { log("Child static block", null); }

    int id = log("Child instance field", 3);
    { log("Child instance block", null); }

    Child() {
        super();
        log("Child constructor start", null);
        log("Child constructor end", null);
    }

    @Override
    void describe() { log("Child.describe(), sees id=" + id, null); }
}

new Child();

Applying the algorithm step by step, instead of recalling a memorized order:

PASS 1 (static, top -> bottom, once):
  GP static field  = 100
  GP static block
  Parent static block
  Child static block

PASS 2 (instance construction for `new Child()`):
  [heap alloc: GrandParent.id=0, Parent.id=0, Child.id=0 -- all zeroed first]
  Child()  -> calls super() -> Parent() -> calls super() -> GrandParent()
    GrandParent field/block init runs first (top of the dive-unwind):
      GP instance field = 1        (GrandParent.id is now 1)
      GP instance block
    GP constructor start
      describe() is called virtually -> the object's ACTUAL runtime class is
      Child, so Child.describe() executes -- even though Parent and Child
      haven't run THEIR field initializers yet!
      Child.describe() reads Child.id, which is still 0 (not yet initialized)
      => prints: "Child.describe(), sees id=0"
    GP constructor end
  (back in Parent's constructor, now past its super() call)
    Parent instance field = 2      (Parent.id is now 2 -- a SEPARATE slot from GrandParent.id)
    Parent instance block
    Parent constructor start
    Parent constructor end
  (back in Child's constructor, now past its super() call)
    Child instance field = 3       (Child.id is now 3)
    Child instance block
    Child constructor start
    Child constructor end
What this example demonstrates
  • A virtual call made from a constructor dispatches to the most-derived override, even before that subclass has initialized its own fields. GrandParent's constructor calls describe() expecting its own behavior, but Java's method dispatch is always based on the object's actual runtime type — so it runs Child.describe(), operating on a half-built object and reading id=0 instead of the eventual 3. The general rule this teaches: calling an overridable (non-final, non-private, non-static) method from a constructor is dangerous, because the object graph below the currently-executing constructor is not yet built.
  • Field hiding is resolved statically; method overriding is resolved dynamically. Each class in the chain that redeclares int id gets its own, separate memory slot — which slot a field access reads is decided at compile time, based on the declared (static) type of the reference expression, never the runtime type. A method call on the same object, in contrast, always resolves at runtime to the most-derived override via the class's method table (vtable). Concretely: ((GrandParent) childObj).id reads GrandParent's own slot (1), while ((GrandParent) childObj).describe() still runs Child.describe() — same object, two completely different resolution rules.
  • Static initialization (Pass 1) always fully completes, top-to-bottom, exactly once — before any instance construction (Pass 2) work begins, and it is never repeated no matter how many times new Child() is subsequently called.
One more consequence worth internalizing
Instantiate Child a second time and none of the "static" lines print again — that class is already initialized. But the entire Pass 2 trace repeats identically every time, including describe() resolving to Child.describe() with id=0 at that exact point in the dive, since the fields are re-zeroed for the new object and the same dive/unwind order applies again.

2.6 Classloader Delegation Model & Subsystems

The JVM ships with a hierarchy of classloaders, each responsible for a different slice of code, following parent-first delegation by default:

LoaderLoadsNotes
Bootstrap ClassLoaderjava.lang.*, core java.base module classes from the JDK's own runtime librariesImplemented in native code, not a Java object itself — calling getClassLoader() on a core class returns null.
Platform ClassLoader (formerly "Extension" pre-Java 9)JDK platform modules outside java.base (e.g. java.sql, crypto providers)Replaced the old extension classloader once the JDK moved to a module system.
Application/System ClassLoaderThe application classpath: your own JARs and classesWhat ClassLoader.getSystemClassLoader() returns; the parent of any custom loaders an application defines.
Custom ClassLoadersWhatever an application or container definesUsed by application servers and plugin systems to isolate independently-deployed units of code from one another, and by fat-jar launchers to load nested JARs.

The delegation algorithm, run on every loadClass call: a loader first asks its parent to load the requested class; only if the parent fails (throws ClassNotFoundException) does the loader attempt to load it itself. This guarantees core classes like java.lang.String can never be shadowed by application-supplied code with the same name, and it produces the runtime class identity rule: two classes are the "same class" to the JVM only if they share the same fully-qualified name and were loaded by the same classloader instance. This is the root cause of a confusing ClassCastException between two classes with an identical name and identical bytecode — it happens whenever the same class gets loaded twice by two different classloader instances (common in app-server and plugin-isolation environments).

Where delegation is deliberately inverted
JDBC needs the bootstrap-loaded DriverManager to load driver classes that live on the application classpath — code the bootstrap loader can't normally see, since delegation only looks upward toward parents. It solves this with a context classloader: each thread carries a reference to an application-level classloader (Thread.currentThread().getContextClassLoader()), which framework and library code can consult to reach "down" into application code despite running in a more privileged loader. The same mechanism underlies JNDI lookups and executable-jar launchers that need to load nested application JARs.

3.1 Metaspace vs. PermGen — why the change (Java 8)

Before Java 8, class metadata lived in PermGen, a fixed-size region inside the heap's own contiguous address space. Applications that dynamically generated or reloaded many classes at runtime (heavy use of reflection, dynamic proxies, or repeated redeployment inside a long-running process) routinely exhausted this fixed region and hit OutOfMemoryError: PermGen space, forcing awkward manual tuning of a size limit that had no natural relationship to the rest of heap sizing. Java 8 replaced it with Metaspace, allocated out of native (off-heap) memory and, by default, bounded only by total available system memory (a cap can still be set with a sizing flag). This removed most PermGen-related failures, but introduced a different failure mode: because Metaspace draws from the same native memory pool the operating system and other processes share, an unbounded leak there (most commonly a classloader that never becomes garbage because something external still references it, along with every class it loaded) can now destabilize the entire host rather than staying contained inside one process's fixed heap.

3.2 Heap Generational Layout

┌───────────────────────────── HEAP ─────────────────────────────┐
│                     Young Generation                            │
│  ┌───────────┐   ┌──────────┐   ┌──────────┐                    │
│  │   Eden     │   │ Survivor │   │ Survivor │                    │
│  │  (largest) │   │  S0      │   │  S1      │                    │
│  └───────────┘   └──────────┘   └──────────┘                    │
│                                                                   │
│                     Old (Tenured) Generation                     │
│              (long-lived / promoted objects)                     │
└───────────────────────────────────────────────────────────────┘
  (G1/ZGC/Shenandoah use region-based layouts instead — see §5)

This layout exists because of one empirical observation about how real programs allocate memory, known as the generational hypothesis: most objects die young (loop-local variables, intermediate calculation results, short-lived request/response objects), while a small minority live for a very long time (caches, connection pools, singletons). Splitting the heap by expected lifetime lets the collector spend most of its effort scanning a small, cheap region full of likely-garbage, instead of repeatedly re-scanning the entire heap.

  • Eden — where nearly all objects are allocated first. Allocation here is extremely cheap: each thread is handed its own private slice of Eden called a Thread-Local Allocation Buffer (TLAB), inside which allocating an object is just bumping a pointer forward — no locking, no coordination with other threads, in the common case.
  • Survivor spaces (S0/S1) — objects still reachable when Eden fills up are copied here during a Young (Minor) GC. The two survivor spaces alternate roles on every collection: one is always the current destination, the other is always empty going in, which avoids fragmentation entirely for this part of the heap since copying naturally compacts.
  • Tenuring — every time an object survives a collection, an age counter in its object header increments. Once that age crosses a configured threshold (or a survivor space fills up before all ages get there, triggering "dynamic tenuring"), the object is promoted into the Old generation instead of copied to the other survivor space again.
  • Old (Tenured) Generation — holds objects expected to live a long time. It's collected far less frequently, but because it's typically much larger than the young generation, a collection here (a Major or Full GC) takes proportionally much longer.

4. Execution Engine: Interpreter, JIT & Bytecode

The JVM begins by interpreting bytecode directly, instruction by instruction — slow per-instruction, but with zero delay before execution starts. While interpreting, it simultaneously profiles which methods and loops are "hot" (invoked, or iterated, frequently). Once a method crosses an invocation or loop-back-edge count threshold, the JIT compiler compiles that method down to native machine code and swaps it in for the interpreted version — this compile-then-swap delay is exactly what "warm-up time" refers to in JVM performance discussions.

  • C1 (Client compiler) — compiles quickly and applies lighter optimizations, favoring low compilation latency over peak output quality.
  • C2 (Server compiler) — compiles more slowly but applies much more aggressive optimizations: method inlining, loop unrolling, and escape analysis, which can prove an object never "escapes" the method it's created in and eliminate its heap allocation entirely, turning what looks like an object allocation into cheap stack or register values instead. C2 also makes speculative optimizations based on the profiling data gathered so far (for example, assuming a call site only ever sees one concrete implementing type); if a later call breaks that assumption, the JVM deoptimizes — discards the compiled code and falls back to the interpreter for that method until it can safely recompile.
  • Tiered Compilation (the default mode) — a method progresses through several C1 profiling levels before being promoted to full C2 compilation once it's proven hot enough to be worth the heavier optimization cost. This gets the fast startup of C1 and the eventual peak throughput of C2 in the same run.
  • Alternative JIT backends exist (most notably Graal, written in Java itself) that apply more aggressive optimizations than the default C2, and the same technology underlies ahead-of-time native-image compilation that skips the interpret-then-JIT pipeline entirely in exchange for near-instant startup.

5. Garbage Collection — Algorithms Compared

Every modern collector uses the same underlying liveness rule: an object is reachable — and therefore not garbage — if it can be traced from a GC Root (a local variable on any thread's stack, an active static field, or a JNI reference held by native code). Anything not reachable from some GC root is garbage and eligible for reclamation.

5.1 Phases common to most collectors

  1. Mark — traverse the live object graph starting from GC roots, marking every object reached along the way.
  2. Sweep — reclaim the memory occupied by everything left unmarked.
  3. Compact (used by most, but not all, collectors) — slide the surviving objects together to eliminate the gaps left behind, so future allocation can keep using a cheap bump-the-pointer scheme instead of searching a free list for a big-enough hole.

5.2 Collector-by-collector

CollectorAlgorithmBest suited to

Parallel GC (the throughput collector)The same mark-sweep-compact approach as Serial, but performed by multiple threads simultaneously during the stop-the-world pauseWorkloads where total throughput matters far more than the length of any individual pause — batch and offline processing

5.3 G1 in depth

  • The heap is split into many equal-sized regions (sized as a power of two, chosen automatically based on heap size); each region is independently labeled Eden, Survivor, Old, or Humongous — a special label for any object at least half the size of a region, which gets allocated directly into one or more contiguous Old regions rather than going through Eden.
  • Young GC: a stop-the-world pause that evacuates every live object out of the current Eden and Survivor regions into new Survivor or Old regions, using multiple threads in parallel.
  • Concurrent Marking Cycle: runs mostly alongside the running application to identify which Old regions are the most garbage-heavy. It proceeds through an initial mark (piggybacked onto a Young GC pause), a concurrent scan of "root regions," concurrent marking of the rest of the heap, a short stop-the-world remark to finalize results, and a cleanup step.
  • Mixed GC: once marking identifies garbage-dense Old regions, the next few collections handle the current Young regions together with a bounded subset of those Old regions — this is precisely what lets G1 reclaim Old-generation garbage incrementally instead of needing one pause that scans the entire Old generation at once.
  • A Remembered Set (RSet) attached to each region tracks which other regions hold references into it, so collecting one region never requires scanning the whole heap just to find its incoming pointers.

5.4 Weak, Soft, and Phantom references

Beyond ordinary (strong) references, Java exposes finer-grained levels of reachability for building caches and cleanup hooks without fighting the collector: a SoftReference is only cleared when the JVM is genuinely under memory pressure, making it suitable for memory-sensitive caches that should shrink under load rather than cause an OutOfMemoryError; a WeakReference is cleared as soon as no strong references to the object remain, regardless of memory pressure (the basis of structures like a weak-keyed map that shouldn't be the thing keeping its keys alive); and a PhantomReference refers to an object that has already been finalized and is used together with a ReferenceQueue purely to run cleanup logic after an object is confirmed gone — the modern, more predictable replacement for the old finalizer mechanism.

6. JVM Tuning & Profiling

6.1 What the common tuning flags actually control

A few categories cover most day-to-day tuning: setting the heap's minimum and maximum size (often to the same value, so the JVM never pays the cost of growing the heap mid-run), sizing Metaspace explicitly (both an initial size, to avoid early resize pauses, and a cap, so a classloader leak fails loudly with an OutOfMemoryError instead of silently consuming all native memory), choosing a garbage collector explicitly, giving G1 a target maximum pause time (a goal it tries to meet, not a hard guarantee), and enabling automatic heap-dump capture and structured GC logging so a production incident leaves behind the evidence needed to diagnose it after the fact rather than requiring a live reproduction.

6.2 How to diagnose a memory leak

  1. Capture a heap dump automatically at the moment of failure (rather than trying to reproduce the issue under a debugger) so the exact state that caused the failure is preserved.
  2. Load the dump into a heap-analysis tool and look at its dominator tree / leak-suspect report — this surfaces which single object graph is retaining a disproportionate share of memory. Classic culprits: an ever-growing static collection, a cache with no eviction policy, listeners or callbacks that get registered but never unregistered, or a ThreadLocal value that never gets cleared in a thread that gets reused from a pool.
  3. Cross-check against GC logs: a genuine leak shows Old-generation occupancy that keeps climbing after every Full GC — the "floor" after each collection never comes back down. A pure sizing problem looks different: GC runs frequently, but each collection still reclaims a healthy amount of memory, meaning the working set is simply larger than the heap allows, not that something is being retained forever.
  4. For ongoing, low-overhead investigation without needing a full heap dump, sampling profilers can capture CPU or allocation flame graphs directly against a live production process with minimal overhead, since they read stack samples via lightweight OS-level mechanisms rather than instrumenting every method call.
How to choose a collector
Frame the decision around the tradeoff between latency and throughput, combined with heap size: G1 is the safe general-purpose default for most services; ZGC or Shenandoah when there's a hard requirement for very short, consistent pauses on a large heap; Parallel GC when a workload is offline/batch and total throughput matters far more than any individual pause.

Concepts Worth Being Able to Explain From First Principles

Given a static block written above a static variable, and another below it, what does each one see?
Both run in strict textual order as part of the implicit <clinit> method, exactly as the compiler concatenates all static field initializers and static blocks in source order. A static block placed above a given static variable's declaration observes that variable still at its Preparation-phase default (0 / false / null), since its own initializer expression hasn't executed yet. A static block placed below the declaration observes the assigned value.
Why doesn't referencing another class's static final field always trigger that class's static initializer?
If the field is a compile-time constant — a primitive or String literal fully resolvable by the compiler — javac inlines the literal value directly into the referencing class's own bytecode. The referencing class never actually needs to load or resolve the defining class to use that value, so this specific kind of access is explicitly excluded from what the JVM spec calls "active use," and initialization never fires from it alone.
A constructor calls an overridable method that a subclass overrides. What actually executes, and why is this a known hazard?
The subclass's override executes, because instance method dispatch is always based on the object's actual runtime type, never the type of the code currently running. The hazard is that this happens at a point where the subclass's own field initializers haven't run yet — the dive down the constructor chain hasn't unwound that far — so the override ends up reading its own fields at their zeroed defaults instead of their intended values. The general takeaway: avoid calling any non-final, non-private, non-static method from a constructor, since the object below the currently-executing constructor level isn't fully built yet.
Two classes redeclare a field with the same name, and the subclass overrides a method that reads it. Why do the field access and the method call resolve so differently?
Fields are resolved statically: each class in a hierarchy that redeclares a field gets its own independent memory slot, and which slot a given expression reads is decided at compile time based on the declared (static) type of the reference — this is called hiding, and it is not polymorphic. Methods are resolved dynamically through the object's method table based on its actual runtime type — this is overriding, and it is the only one of the two that is polymorphic. As a result, casting a reference to a supertype changes which field slot you read, but never changes which method override actually runs.
Two classes share the exact same fully-qualified name and bytecode, yet a cast between them throws ClassCastException. Why?
The JVM's notion of runtime type identity is the pair (fully-qualified name, defining classloader instance) — not just the name. If the same class gets loaded twice by two different classloader instances (common in application-server or plugin-isolation setups), the JVM treats the two results as entirely unrelated types even though their bytecode is identical, so a cast between an instance of one and a reference typed as the other fails. The fix is ensuring any class that needs to be shared across those boundaries is loaded from a common ancestor classloader instead of being loaded independently by each one.
A G1-managed process occasionally experiences a multi-second stop-the-world pause. What happened, and what would you check?
A G1 Full GC is a fallback path, not part of its normal operation — it means the concurrent/mixed collection cycle couldn't keep up with the rate of new garbage (for example, allocation outpacing concurrent marking, or a Humongous allocation failing to find enough contiguous free regions), so G1 degraded to a single-threaded, full-heap stop-the-world compaction as a last resort. The response is to give the heap more headroom, start concurrent marking earlier (lowering the occupancy threshold that triggers it), reconsider region sizing if Humongous allocations are frequent, and use an allocation profiler to understand what's actually driving the allocation rate.
Beyond one being off-heap, what's the practical consequence of the PermGen-to-Metaspace change?
Because Metaspace draws from native memory shared with the rest of the operating system rather than a fixed region carved out of the heap, an unbounded leak there (most often a classloader that never becomes unreachable, keeping every class it loaded alive too) can now degrade or crash the entire host rather than staying contained as a clean, isolated OutOfMemoryError inside one process's heap. This is why production configurations should always cap Metaspace explicitly rather than relying on its unbounded default.
