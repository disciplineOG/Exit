Real-Time Communication: WebSockets, STOMP & Server-Sent Events

WebSockets STOMP Server-Sent Events Long Polling Real-Time Scaling SockJS
Why this matters

A customer staring at ShopSphere's order-tracking page wants to see "Preparing → Shipped → Out for delivery" update the instant order-service processes each transition, not after they hit refresh. A seller watching their dashboard wants an inventory-count tile to drop in real time the moment a competing order reserves the last unit of a hot SKU. Neither of these is a request the browser can ask for at the right moment, because the browser has no way of knowing when the server has something new to say — this is the fundamental gap this page is about, and it's one every backend engineer eventually has to close with something more than plain REST. The techniques here (long polling, SSE, WebSockets, STOMP, SockJS) aren't interchangeable — each is the right tool for a different shape of problem, and picking the wrong one either wastes server resources or leaves you building infrastructure you didn't need.

1. Why REST Cannot Push, and the Spectrum of Fixes

The HTTP request/response model that ordinary REST APIs are built on has a structural asymmetry baked into it: a client sends a request, and only after that request lands does the server get a chance to say anything back. The server cannot initiate a message. It has no way to reach out to a browser tab and say "the order you're viewing just shipped" unless that browser has, at that very moment, an open request waiting for exactly that answer. This isn't a limitation of any particular framework or library — it's the shape of the protocol itself. A GET request to /api/orders/{id} answers the question "what is the state of this order right now," but it cannot answer a question nobody asked yet, like "let me know the next time this order's state changes."

Three concrete ShopSphere scenarios make the gap tangible. A customer's order-tracking page needs to reflect status transitions (Placed → Paid → Shipped → Delivered) as order-service processes them, without the customer manually refreshing. A seller's inventory dashboard needs a stock-count widget to update the moment inventory-service decrements a SKU's available quantity, so two sellers don't both believe they have units to sell. An admin's operations dashboard needs a live feed of order volume, payment failure rate, and queue depth across the whole platform, updating continuously as events happen. In every case the event that matters — an order transition, an inventory decrement, a Kafka message landing — originates on the server's timeline, not the client's, and standard request/response REST has no channel for the server to speak first.

The techniques covered in this page sit on a spectrum, roughly ordered by how much they bend the request/response model to fake or genuinely achieve server-initiated push: plain polling (the client just asks repeatedly, wasteful but trivial), long polling (a clever variant that holds the request open), Server-Sent Events (a real, standardized one-way push channel), and WebSockets (a real two-way channel). Each step up this ladder buys more capability at the cost of more infrastructure complexity, and picking the least-complex one that actually satisfies the requirement is the recurring theme of this whole page.

2. Long Polling: The Universal Fallback and Its Cost

Long polling was the original workaround, invented before any browser offered a real push primitive, and it remains relevant today as a fallback for clients and network paths (old proxies, restrictive corporate firewalls, ancient browsers) that can't do anything fancier. The idea is simple: the client sends an ordinary HTTP request, but instead of the server answering immediately, the server holds the connection open and does not write a response until it actually has something new to say — or until some timeout (say, 30 seconds) elapses, at which point it responds with "nothing new" and the client immediately opens another request to wait again. From the client's point of view it looks exactly like a normal HTTP call; the trick is entirely in the server's willingness to delay its answer.

Applied to ShopSphere, a customer's order-tracking page could issue GET /api/orders/{id}/status-poll, and order-service would hold that request open, only responding once the order's status actually changes (or the timeout fires with the current, unchanged status). The moment a response arrives, the browser processes it and immediately fires the next poll request, so from the user's perspective updates appear close to instantly, without the wasteful "ask every 2 seconds whether anything changed" pattern of naive short polling.

The cost is real and it's structural, not incidental: every client with an open long-poll request is occupying a server-side connection and, in a classic thread-per-request servlet container like Tomcat running Spring MVC, a whole thread, for as long as it's waiting — which could be tens of seconds. If ShopSphere has 50,000 customers simultaneously watching an order-tracking page, that's potentially 50,000 threads sitting mostly idle, just holding a socket open in case something happens. This is exactly the same shape of resource-exhaustion problem covered in the WebFlux deep dive as the C10K problem: the bottleneck isn't CPU, it's the fact that a traditional server ties up a whole thread (with its megabyte-scale stack) for the entire time a client is merely waiting, not computing. Long polling can be made to scale further with an async servlet model (DeferredResult in Spring MVC decouples the waiting from a dedicated thread), but it's still fundamentally repeated HTTP requests dressed up to feel like a push channel, with all the overhead — TLS handshake avoidance aside, still full HTTP headers on every round trip — that entails.

Why long polling still matters despite better options existing

Long polling isn't obsolete trivia. It's the fallback SockJS reaches for (see section 5) when a client genuinely cannot open a raw WebSocket connection, and it remains a legitimate first choice for lower-volume, infrequent-update scenarios where standing up SSE or WebSocket infrastructure isn't worth the operational overhead. The lesson to take from it isn't "never use this" — it's "understand exactly what it costs," because that same held-open-connection cost reappears, in a different shape, with every technique in this page.

3. Server-Sent Events: One-Way Push Over Plain HTTP

Server-Sent Events (SSE) is a standardized way for a server to push a stream of text events to a browser over a single, long-lived HTTP connection, using nothing more exotic than a response whose Content-Type is text/event-stream and whose body never actually "finishes" — the server keeps writing new event chunks onto the same open response as they become available, and the browser keeps reading them as they arrive. Unlike long polling, there's no repeated request/response cycle: the client opens the connection once, and the server writes to it indefinitely.

On the browser side, the API is deliberately minimal — the EventSource JavaScript object handles the entire protocol, including the reconnect logic, for you:

const source = new EventSource('/api/orders/' + orderId + '/status-stream');

source.onmessage = (event) => {
  const update = JSON.parse(event.data);
  renderOrderStatus(update.status);
};

source.onerror = () => {
  // EventSource automatically retries the connection on its own;
  // this fires when a reconnect attempt is in progress or has failed.
};

On the server side, a Spring MVC controller can return an SseEmitter, which represents that same long-lived, kept-open HTTP response, and the controller pushes named events onto it whenever order-service observes a status change (for example, by consuming an OrderShipped event off Kafka and forwarding it to whichever emitters are currently subscribed for that order):

@GetMapping(path = "/api/orders/{id}/status-stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter streamOrderStatus(@PathVariable String id) {
    SseEmitter emitter = new SseEmitter(0L); // no timeout
    orderStatusEmitterRegistry.register(id, emitter);
    emitter.onCompletion(() -> orderStatusEmitterRegistry.remove(id, emitter));
    emitter.onTimeout(() -> orderStatusEmitterRegistry.remove(id, emitter));
    return emitter;
}

// elsewhere, when order-service processes an OrderShipped Kafka event:
emitter.send(SseEmitter.event()
        .name("status-update")
        .data(new OrderStatusPayload(orderId, "SHIPPED")));

The wire format itself is plain text, which is part of SSE's appeal — no binary framing, no special client library required beyond what every modern browser ships built in, and it's trivially debuggable with a plain HTTP client or even curl:

event: status-update
data: {"orderId":"ORD-4471","status":"SHIPPED"}

The defining trait of SSE, and the reason it belongs in the comparison at all, is that it is strictly one-directional: the server can push events to the browser, but the browser has no matching channel to send data back over that same connection. This sounds like a limitation, but it's frequently exactly the right shape for the problem. The order-tracking page is a textbook fit — the customer's browser never needs to send anything back over the status channel itself; whatever actions the customer takes (cancel the order, contact support) are ordinary, independent REST calls, entirely separate from the read-only stream of status updates flowing the other way. Reaching for a full-duplex WebSocket here would mean standing up more infrastructure (handshake negotiation, a message sub-protocol, bidirectional routing) to solve a problem that was never bidirectional in the first place. SSE also inherits HTTP's ordinary behavior for free — it works through standard HTTP proxies and load balancers without special-casing, and the EventSource client automatically reconnects (with a server-suggested retry delay) if the connection drops, without the application having to hand-roll that logic.

4. Raw WebSockets: A Full-Duplex Channel via HTTP Upgrade

When the browser genuinely needs to send data back over the same live channel the server is pushing on — not just fire independent REST calls on the side — SSE's one-directional model stops being enough, and this is where WebSockets come in. A WebSocket connection starts life as an ordinary HTTP request but carries a special Upgrade: websocket header; if the server agrees, it responds with HTTP status 101 (Switching Protocols), and from that point on the same underlying TCP connection stops speaking HTTP at all and instead carries WebSocket frames — a lightweight, low-overhead binary or text framing format with none of the header bloat that a repeated HTTP request/response cycle would carry. The connection stays open indefinitely, and either side — client or server — can write a frame onto it at any moment, independent of any request having been made. This is what "full-duplex" means here: it isn't request/response at all anymore, it's two parties who can each speak whenever they want, much like a phone call rather than a series of letters.

GET /ws/live-updates HTTP/1.1
Host: shopsphere.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Spring supports raw WebSockets directly through spring-websocket, with a handler model conceptually equivalent to the Jakarta EE @ServerEndpoint annotation style, but expressed as a WebSocketHandler registered against a URL path:

public class SellerDashboardHandler extends TextWebSocketHandler {

    @Override
    public void afterConnectionEstablished(WebSocketSession session) {
        sellerSessionRegistry.register(sellerId(session), session);
    }

    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) {
        // handle a message the browser sent up this same connection,
        // e.g. "subscribe to SKU-1042 stock updates"
    }

    @Override
    public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
        sellerSessionRegistry.remove(sellerId(session), session);
    }
}

@Configuration
@EnableWebSocket
public class WebSocketConfig implements WebSocketConfigurer {
    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(new SellerDashboardHandler(), "/ws/seller-dashboard");
    }
}

This raw handler model is powerful but low-level: you're working directly with byte or text frames, session registries, and your own message format, with none of the higher-level conveniences (structured destinations, subscribe/unsubscribe semantics, automatic routing to the right handler method) that a real messaging system gives you. That's exactly the gap STOMP fills.

5. STOMP Over WebSocket, and SockJS as a Transport Fallback

STOMP: messaging semantics on top of raw frames

STOMP (Simple/Streaming Text Oriented Messaging Protocol) is a small, text-based messaging sub-protocol that Spring layers on top of the raw WebSocket connection described in section 4. Instead of every application inventing its own ad hoc framing for "what kind of message is this and where should it go," STOMP borrows the vocabulary and semantics that anyone who has used a message broker (like the Kafka topics ShopSphere's services already communicate over) will find familiar: clients SUBSCRIBE to a named destination, the server or other clients SEND messages to a destination, and STOMP frames carry that routing information explicitly, so a single physical WebSocket connection can multiplex many logically distinct subscriptions.

Spring's STOMP support (spring-messaging plus @EnableWebSocketMessageBroker) wires this up with an internal message broker that routes by destination prefix, so a seller's browser can subscribe to exactly the inventory topic it cares about:

@Configuration
@EnableWebSocketMessageBroker
public class StompConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws")
                .withSockJS(); // fallback transports, see below
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableSimpleBroker("/topic", "/queue");
        registry.setApplicationDestinationPrefixes("/app");
    }
}

@Controller
public class InventoryUpdateController {
    @MessageMapping("/inventory/watch")     // client sends to /app/inventory/watch
    @SendTo("/topic/inventory/{sku}")       // broadcast to everyone subscribed here
    public InventoryUpdate handleWatch(WatchRequest request) {
        return inventoryService.currentStatus(request.getSku());
    }
}

On the browser side, the seller's dashboard subscribes to /topic/inventory/SKU-1042, and any time inventory-service pushes an update to that destination — say, in response to a Kafka InventoryReserved event it consumed — every subscribed browser receives it over its already-open connection, without needing to know or care how many other sellers are also watching. This destination-based fan-out is precisely the piece raw WebSockets don't give you for free; STOMP is what turns "a socket I can write bytes to" into "a pub/sub messaging surface with a shape any backend engineer already understands from Kafka or RabbitMQ."

SockJS: transport fallback for clients and proxies that can't upgrade

Not every client, and not every network path between the client and the server, actually supports a raw WebSocket upgrade — some corporate proxies strip the Upgrade header, some older browsers never implemented WebSockets at all, and some intermediary infrastructure simply doesn't pass the handshake through cleanly. SockJS is a library (with matching client- and server-side halves) that solves this by trying a real WebSocket connection first and, if that fails for any reason, automatically falling back to a sequence of other transports — including, ultimately, exactly the long-polling technique from section 2 — while presenting the exact same application-level API regardless of which transport ended up being used underneath. Calling .withSockJS() on the STOMP endpoint registration shown above is what enables this: the application code never has to know or branch on which transport a particular client actually ended up using, because SockJS normalizes the difference away beneath the STOMP layer.

SockJS is a fallback ladder, not a WebSocket replacement

It's worth being precise that SockJS doesn't make WebSockets faster or better — every fallback transport it offers below raw WebSocket is strictly worse (more overhead, higher latency, or both), including the long-polling fallback with its held-open-connection cost from section 2. The point of SockJS is compatibility, not performance: it guarantees the feature works everywhere, at the cost of some clients silently getting a degraded transport without any application code changes needed. If you control every client and every network path (a scenario that's genuinely rare for a public-facing e-commerce site with browser clients on arbitrary corporate networks), you can skip SockJS entirely and use raw STOMP over WebSocket.

6. Authenticating the Handshake and Handling Reconnection

A REST API can put a fresh Authorization: Bearer <token> header on every single request, because every single request is a brand-new HTTP exchange. A WebSocket connection breaks that assumption: once the HTTP Upgrade handshake completes, the connection stops being a series of independent HTTP requests and becomes one continuous, long-lived TCP-like stream carrying WebSocket frames — there is no "next request" to attach a fresh header to, because there is no next request. Authentication has to happen once, at the moment of the handshake, and then the server has to remember, for the entire lifetime of that connection, which authenticated user this particular socket belongs to.

The most common approach is to pass the auth token as a query parameter or a STOMP CONNECT frame header on the initial handshake request (since custom headers on the WebSocket handshake itself are awkwardly supported across browsers, many teams put the token in the URL query string instead, accepting that it will show up in server access logs unless those are scrubbed), and validate it in a HandshakeInterceptor before the upgrade to 101 is even allowed to complete:

public class JwtHandshakeInterceptor implements HandshakeInterceptor {
    @Override
    public boolean beforeHandshake(ServerHttpRequest request, ServerHttpResponse response,
                                    WebSocketHandler wsHandler, Map<String, Object> attributes) {
        String token = extractTokenFromQuery(request.getURI());
        Authentication auth = jwtTokenService.validate(token); // throws / returns null if invalid
        if (auth == null) {
            response.setStatusCode(HttpStatus.UNAUTHORIZED);
            return false; // handshake refused, upgrade never happens
        }
        attributes.put("principal", auth); // stashed on the WebSocketSession for the connection's lifetime
        return true;
    }
}

Once validated, that identity is attached to the WebSocketSession (or, for STOMP, the underlying Principal Spring associates with the STOMP session) and reused for every subsequent frame on that connection — there's no re-checking a header on every message, because there is no header on every message. This has a direct consequence: if a customer's JWT expires while their order-tracking WebSocket is still open, the server has no natural moment to notice, short of explicitly checking token expiry against a clock and forcibly closing the connection when it lapses, since no new "request" is ever going to arrive carrying a renewed token for the server to reject.

The second, related concern is what happens when the connection drops — and on a real network, over a real mobile connection, it eventually always does: a customer's phone loses signal, a corporate proxy times out an idle socket, a server instance behind the load balancer gets redeployed. The client is responsible for detecting the drop (a WebSocket onclose event) and reconnecting, which means re-running the entire handshake-and-authentication sequence above from scratch, and then — critically — re-establishing whatever subscriptions it had before (re-subscribing to /topic/orders/{id}, or whatever destinations mattered), since none of that state survives the old connection's death. A well-behaved client implements reconnection with exponential backoff (retry after 1s, then 2s, then 4s, capped at some maximum) rather than hammering the server the instant a connection drops, especially important at ShopSphere's scale, where a brief server-side blip could otherwise cause a stampede of tens of thousands of clients all reconnecting in the same instant.

7. Scaling Stateful Connections Across a Fleet

Every technique in this page after plain short polling shares one structural property that ordinary stateless REST does not: the server holds state — an open connection, and typically an in-memory registry of which user or order that connection belongs to — for as long as the client is connected. A stateless REST call can be served by any instance behind a load balancer, because nothing about handling it depends on which instance happens to pick it up. A WebSocket connection is the opposite: once a customer's browser completes its handshake against, say, order-service instance #3, that specific TCP connection is pinned to that specific instance for its entire lifetime. Instance #3 is the only process in the fleet that can write a frame onto that particular socket, because it's the only process that physically holds the open connection.

This creates a genuinely hard problem the moment ShopSphere runs more than one instance of order-service, which any horizontally-scaled production deployment does. Say a customer's browser is connected to instance #3, watching Order 123. When order-service processes the ShipmentConfirmed event for Order 123, that processing might happen on any instance in the fleet — whichever instance's Kafka consumer happened to be assigned that partition, entirely independent of which instance is holding the customer's actual WebSocket connection. Instance #7 knows Order 123 just shipped; only instance #3 has a live connection to the browser that needs to hear about it. Without some mechanism to bridge that gap, the update simply never reaches the customer, even though the right information exists somewhere in the fleet.

There are two standard ways to solve this, and they trade off against each other directly:

Sticky sessions

The load balancer can be configured to route a given client to the same backend instance for the lifetime of its session (commonly via a cookie or, for WebSockets, simply by the fact that the connection itself, once established, naturally stays on one instance for as long as it's open — sticky sessions mostly matter for the initial handshake and any related HTTP traffic around it). This doesn't solve the instance #3-versus-instance #7 problem above by itself — it only guarantees that a given client always talks to the same instance, it says nothing about how other instances get updates to that instance. Sticky sessions are also an operational constraint on the load balancer's freedom: it can no longer freely spread load exactly evenly, and rebalancing (e.g., during a rolling deployment, when instance #3 needs to be drained and replaced) forcibly disconnects every client pinned to it, all of whom then have to reconnect and get re-pinned somewhere else.

A shared message relay (Redis pub/sub or a STOMP broker relay)

The more general and more commonly used solution is to make the fact that a connection is pinned to one instance a purely local, internal detail, and give every instance a way to publish a message that will reach whichever instance actually holds the relevant connection, regardless of which one that is. Instance #7, having just processed the ShipmentConfirmed event, publishes "Order 123 shipped" to a shared channel — a Redis pub/sub channel, or a real STOMP-capable broker (RabbitMQ or ActiveMQ configured as Spring's STOMP relay) — that every instance in the fleet is subscribed to. Instance #3, subscribed to that same channel, receives the message, recognizes (from its own local session registry) that it is the one holding a live connection interested in Order 123, and writes the update onto that socket. Every other instance receives the same broadcast and does nothing with it, because none of them have a matching local connection.

// Spring's STOMP broker relay config — delegates fan-out to a real external broker
// instead of the in-memory "simple broker" shown earlier, so any instance can
// publish to /topic/orders/123 and the message reaches whichever instance
// actually holds that customer's connection.
@Override
public void configureMessageBroker(MessageBrokerRegistry registry) {
    registry.enableStompBrokerRelay("/topic", "/queue")
            .setRelayHost("rabbitmq.internal")
            .setRelayPort(61613);
    registry.setApplicationDestinationPrefixes("/app");
}

Redis pub/sub is the more common relay choice specifically because most ShopSphere-scale deployments already run Redis as a cache (see the caching deep dive) — reusing it as the fan-out relay for WebSocket/STOMP messages avoids standing up an entirely separate piece of broker infrastructure just for this one purpose, at the cost of Redis pub/sub's own limitations (it's fire-and-forget, with no message persistence or delivery guarantee if a subscriber is briefly disconnected, which is usually an acceptable trade for ephemeral live-update traffic where a missed update will simply be superseded by the next one).

This is the same fan-out shape as event-driven notification delivery

Structurally, "publish once, deliver to whichever instance actually holds the recipient's live connection" is the same problem the notification-service HLD deep dive covers for delivering push notifications to a specific device — the shared relay (Redis pub/sub, a broker) exists precisely to decouple "who produced this event" from "who has the live channel to the specific recipient," and that decoupling is the recurring answer any time a stateful, pinned connection needs to receive something produced somewhere else in the fleet.

8. Backpressure on Slow WebSocket Clients

A WebSocket connection is only as fast as its slowest participant, and unlike a request/response REST call — where a slow client just means a slow individual response, contained to that one exchange — a slow WebSocket client creates an ongoing problem for as long as the connection stays open. If ShopSphere's admin dashboard is pushing a continuous stream of live order-volume and payment-failure-rate updates over a WebSocket, and the admin's browser tab is backgrounded, running on a throttled CPU, or simply on a slow network link, the server keeps producing new updates on its own schedule regardless of whether the client has actually finished consuming — and therefore made room for — the previous ones.

Left unmanaged, this forces a choice the server has to make somewhere, whether or not anyone explicitly designed for it: buffer the unconsumed messages in memory on the server side (a queue that grows without bound if the client never catches up, eventually risking an out-of-memory condition, especially painful when it's not one slow client but thousands of them each holding a growing per-session buffer), or start dropping messages silently (acceptable for some data, like a live order-count tile where only the latest value actually matters, but silently wrong for anything where every message carries meaning that can't be inferred from the next one, like a running total that depends on not missing an increment).

This is precisely symmetrical to the backpressure problem covered in the WebFlux and Reactive Streams deep dive, just appearing on the opposite side of the connection: there, a fast Publisher risks overwhelming a slow Subscriber inside a single service's data pipeline, and Reactive Streams solves it by making the subscriber pull data at the rate it can actually handle. Over a WebSocket, the "publisher" is effectively the server pushing live updates, and the "subscriber" is a browser tab with no equivalent request(n) mechanism built into the raw WebSocket protocol — there's no standard way for a browser to tell the server "I've only processed 3 of the last 10 messages you sent, slow down." Spring's WebSocket support does expose a practical, blunter tool for this: WebSocketSession.setTextMessageSizeLimit/getAsyncRemote()-style backpressure hooks and buffer-size limits that let the server detect when a session's send buffer is filling up and make an explicit policy decision — drop the oldest queued update in favor of the newest one (the right call for a "latest inventory count" style feed, where only the freshest value matters and stale intermediate values are worthless the instant a newer one exists), or close the connection outright as pathologically slow, forcing the client to reconnect and start fresh rather than let one slow consumer accumulate unbounded server-side memory.

A slow consumer's cost is per-connection, not per-message

The easy mistake is to reason about a single slow client in isolation and conclude the risk is small. The real risk is that "slow client" isn't a rare edge case at ShopSphere's scale — some meaningful fraction of tens of thousands of concurrently connected admin/seller/customer sessions will, at any given moment, be on a throttled connection, a backgrounded tab, or a struggling device. Each one independently accumulating an unbounded server-side buffer is exactly the kind of failure mode that looks fine in testing (one client, fast network) and takes down a server under real production traffic (thousands of clients, a realistic spread of network conditions) — which is why an explicit, bounded backpressure policy has to be a deliberate design decision, not something left to whatever the default buffer behavior happens to be.

Concepts Worth Being Able to Explain From First Principles

Why can't a REST API just let the server send a response whenever it wants to?
HTTP request/response is fundamentally a turn-taking protocol: the server only gets to speak in reply to a specific request, and it has no channel to initiate a message when nothing was asked. Even if the server wanted to push "Order 123 shipped" to a customer's browser the instant it happens, there's no open request sitting there waiting to carry that answer unless one was deliberately kept open for that purpose — which is exactly what long polling, SSE, and WebSockets each do in different ways, rather than REST gaining some new capability. The asymmetry is structural to the protocol, not a missing feature that a newer HTTP version fixes.
Why does long polling cost more server resources than the number of messages it delivers would suggest?
The cost of long polling isn't proportional to how many updates get delivered — it's proportional to how many clients are simultaneously waiting, because each waiting client is occupying a held-open connection (and, on a classic thread-per-request server, a whole OS thread with its own stack) for the entire time it's waiting, whether or not anything ever actually happens for that client. Fifty thousand customers watching order-tracking pages costs roughly fifty thousand held connections even on a quiet day with almost no order updates happening, because the resource is consumed by waiting, not by the events themselves.
When is SSE's one-directional limitation actually a non-issue rather than a real constraint?
SSE's one-way nature is a non-issue whenever the browser never needed to talk back over that specific channel in the first place. ShopSphere's order-tracking page is the clean example: the stream exists purely to push status changes to the customer, and anything the customer does in response — cancelling the order, messaging support — is a completely independent REST call that has nothing to do with the status stream's plumbing. The mistake would be assuming you need bidirectional infrastructure just because the overall page has some interactivity somewhere; the question to ask is specifically whether that interactivity needs to travel back over the same live channel the server is pushing on.
What actually happens during a WebSocket's HTTP Upgrade handshake?
The client sends a normal-looking HTTP GET request carrying an Upgrade: websocket header and a Sec-WebSocket-Key. If the server agrees to upgrade, it responds with HTTP status 101 (Switching Protocols) rather than a normal 200, and from that exact moment on, the same underlying TCP connection stops carrying HTTP semantics at all and instead carries WebSocket frames in both directions, indefinitely, until either side closes it. It's genuinely one connection changing what protocol it speaks partway through its life, not two separate connections or a new socket being opened.
What does STOMP add on top of a raw WebSocket connection that you'd otherwise have to build yourself?
A raw WebSocket gives you nothing but a channel to write bytes or text onto — no concept of "this message is meant for this logical topic," no subscribe/unsubscribe semantics, no routing. STOMP adds exactly that layer: named destinations (like /topic/inventory/SKU-1042), SUBSCRIBE/SEND frame types, and a broker (in-memory, or relayed to a real external broker like RabbitMQ) that routes messages to the right subscribers. Without it, every application would have to hand-roll its own equivalent of pub/sub semantics on top of raw frames, which is exactly the kind of already-solved problem STOMP exists to avoid re-solving per project.
Why can't a WebSocket connection just re-validate a Bearer token the way REST does on every call?
A REST call can carry a fresh Authorization header because every REST call is a brand-new, independent HTTP exchange — there's always a "next request" to attach a token to. A WebSocket connection, once the handshake completes, is one continuous stream of frames with no more HTTP requests inside it, so there's no natural place to attach a header on an ongoing basis. Authentication has to happen once, during the handshake, and the resulting identity has to be cached against the session for the connection's whole lifetime — which also means a token that expires mid-connection requires an explicit, deliberate check against the clock, since no future request is ever going to arrive that the server could simply reject.
Why does horizontally scaling order-service actually make WebSocket delivery harder, not easier?
A stateless REST call benefits from horizontal scaling in the obvious way — any instance can serve it. A WebSocket connection is pinned to whichever specific instance completed its handshake, so scaling out to more instances increases the odds that the instance producing an update (say, the one whose Kafka consumer happened to process a ShipmentConfirmed event) is a different instance from the one holding the customer's live connection. More instances means more chances for that mismatch, which is exactly why a shared relay — Redis pub/sub or a STOMP broker relay — becomes necessary specifically because of scaling out, not despite it.
How do sticky sessions and a shared pub/sub relay solve genuinely different problems, even though both come up in the same scaling discussion?
Sticky sessions only guarantee that a given client keeps talking to the same backend instance across its session — they say nothing about how a different instance, which just produced an update relevant to that client, gets that update to the instance actually holding the connection. A shared relay solves exactly that second problem: any instance can publish, and the one instance holding the relevant connection picks it up and delivers it. In practice both often coexist — sticky routing for the connection itself, plus a relay so instances that aren't holding a particular connection can still get relevant updates to whichever instance is.
Why is a slow WebSocket client a backpressure problem, and how is it the same problem WebFlux solves?
A server pushing live updates over a WebSocket has no way to know or control how fast the client on the other end is actually consuming them, and the raw WebSocket protocol has no built-in equivalent of Reactive Streams' request(n) mechanism for the client to signal "slow down." Left alone, the server either buffers unboundedly (risking memory exhaustion across many simultaneously slow clients) or silently drops messages. This is the exact same fast-producer-versus-slow-consumer shape that Reactive Streams backpressure solves inside a single service's data pipeline — just appearing across a network connection instead of between in-process Publisher and Subscriber objects, which is why the fix (an explicit, bounded policy — drop-oldest, drop-newest, or disconnect) has to be designed in deliberately rather than assumed away.
