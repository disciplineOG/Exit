API Design: REST Maturity, OpenAPI, Versioning, Idempotency

Richardson Maturity Model Resource Modeling HTTP Status Codes Idempotency Versioning Pagination OpenAPI
Why this matters

Most of what teams call "REST" is really "HTTP with JSON," and the gap between the two is exactly where production bugs live: a POST endpoint that isn't idempotent will double-charge a customer the moment a load balancer times out and a client retries; a 500 returned for a validation failure will make a retry loop hammer a service that was never going to succeed. Understanding the actual mechanics behind status codes, idempotency, and versioning turns API design from a matter of taste into a set of decisions with predictable, checkable consequences for every client that has to consume the API for years.

1. The Richardson Maturity Model — a vocabulary for "how RESTful"

"Is this API RESTful?" is usually an unanswerable yes/no question because REST (Representational State Transfer) as Roy Fielding defined it is a constraint set, not a checkbox. The Richardson Maturity Model gives you four levels so you can say precisely which constraints an API satisfies, which is far more useful than arguing about the label.

Level 3  HATEOAS               responses carry links describing legal next actions
           |                   (rare in practice - see below)
Level 2  HTTP verbs + status codes used correctly
           |                   nouns as URIs, GET/POST/PUT/DELETE carry meaning,
           |                   status codes communicate outcome  <- most real APIs stop here
Level 1  Resources, one verb
           |                   distinct URIs per resource, but everything is POST
           |                   (/orders/42/cancel as a POST-only "action" URI)
Level 0  POX (Plain Old XML/JSON) - the RPC swamp
                                one endpoint, verb-in-body, HTTP is just a transport tunnel

Each level strictly adds a constraint on top of the one below it — Level 2 doesn't replace Level 1's resource URIs, it adds correct verb/status-code usage on top of them, and Level 3 adds hypermedia on top of that. This is why the model is a ladder you can point at a real API and say "this one satisfies Level 2, and here's specifically the Level 3 constraint it doesn't," rather than a binary RESTful/not-RESTful label.

Level 0 — the swamp of POX (Plain Old XML/JSON)

A single endpoint, usually POST, that acts as an RPC dispatcher. The HTTP verb and URI carry no meaning — everything is decided by an "action" or "method" field in the body.

POST /api
{ "action": "getOrder", "orderId": 8831 }

POST /api
{ "action": "cancelOrder", "orderId": 8831 }

This is HTTP used purely as a transport tunnel, functionally identical to SOAP or a raw RPC framework. HTTP infrastructure — caches, proxies, load balancers, browsers — cannot help you at all because it has no visibility into what the request actually does.

Level 1 — resources, one verb

You introduce distinct URIs per resource, but still funnel everything through one HTTP method (almost always POST):

POST /orders/8831/get
POST /orders/8831/cancel
POST /orders/8831/promoteToPriority

This is progress — at least the URI names a thing — but the verb-in-the-path pattern (/get, /cancel) is a strong signal that the API hasn't adopted HTTP semantics yet; it's still RPC, just with prettier addresses.

Level 2 — HTTP verbs and status codes used correctly

This is where the overwhelming majority of real-world "REST" APIs live, and it's a perfectly legitimate place to stop. Resources are nouns, HTTP methods carry the meaning of the operation, and status codes communicate the outcome:

GET    /api/v1/orders/8831        → 200 OK
POST   /api/v1/orders             → 201 Created
PUT    /api/v1/orders/8831        → 200 OK / 204 No Content
DELETE /api/v1/orders/8831        → 204 No Content
GET    /api/v1/orders/999999      → 404 Not Found

Reverse proxies can now cache GETs, browsers can prefetch safely, monitoring can alert on 5xx rates without parsing bodies, and any HTTP-aware tool (curl, an API gateway, a service mesh) understands the shape of the traffic without custom logic. This is almost always the right target for internal and external APIs — Level 3 buys diminishing returns for the complexity it costs.

Level 3 — HATEOAS (Hypermedia as the Engine of Application State)

The response body includes links describing what the client can legally do next, and the client is expected to navigate by following those links rather than hardcoding URI templates:

{
  "orderId": 8831,
  "status": "PENDING_PAYMENT",
  "_links": {
    "self":   { "href": "/api/v1/orders/8831" },
    "pay":    { "href": "/api/v1/orders/8831/payment", "method": "POST" },
    "cancel": { "href": "/api/v1/orders/8831/cancellation", "method": "POST" }
  }
}

The theoretical payoff is huge: the server can change URI structure, retire an action, or add a new state transition, and a hypermedia-aware client adapts automatically because it never hardcoded a path — it just follows whatever links are present. In practice this level is rare, for concrete reasons:

  • Client code almost always ends up hardcoding which link relations it looks for anyway (_links.pay is still a contract), so much of the promised decoupling doesn't materialize without extremely disciplined client design.
  • There's no dominant, boring media type standard — HAL, JSON:API, and Siren all compete, and mobile/SPA teams increasingly consume typed OpenAPI-generated clients that make link-following feel like extra indirection rather than freedom.
  • The complexity cost (designing link relations, versioning the relations themselves, teaching every client team the navigation model) is paid by every team, while the benefit only shows up during specific server-side refactors.

Level 3 is not "the correct way to do REST that everyone is too lazy to do." It solves a specific problem — decoupling client navigation logic from server URI structure — that most APIs don't actually have, because their URI structure is stable and their clients are versioned and deployed in lockstep with the API anyway. Knowing this lets you evaluate HATEOAS on its actual merits for your system instead of treating it as a purity test.

2. Resource modeling: nouns, nesting, and the query-parameter boundary

Nouns, not verbs

A URI names a resource — a thing that has representation and state — not an operation. The verb belongs to the HTTP method:

Instead ofUse
POST /createOrderPOST /api/v1/orders
POST /orders/42/cancelOrderPOST /api/v1/orders/42/cancellation or PATCH /api/v1/orders/42 {"status":"CANCELLED"}
GET /getCustomerOrders?customerId=42GET /api/v1/customers/42/orders

Some actions genuinely resist noun-ification (login, search, bulk import). Modeling them as a resource — a "session" you create with POST /api/v1/sessions when a Customer logs in, a "search" you create with POST /api/v1/product-searches whose result you then GET — keeps the verb discipline intact even for workflow-shaped operations, though a pragmatic, well-documented action endpoint is a reasonable escape hatch rather than a design failure.

Nesting for ownership

Nest a resource under its parent when the child cannot meaningfully exist, or cannot be addressed uniquely, without the parent: /api/v1/customers/42/orders/17 says order 17 belongs to customer 42. Two rules keep nesting from spiraling out of control:

  • Nest one level deep for the primary relationship, then flatten. /api/v1/orders/17/items/3 is defensible; /api/v1/marketplaces/9/regions/2/customers/42/orders/17/items/3 forces every client to carry the whole ancestry chain just to fetch one order line. Prefer exposing the leaf resource at its own root once it has a globally unique ID: /api/v1/orders/17/items/3, with /api/v1/customers/42/orders reserved for the "list orders belonging to this customer" view.
  • If a resource can have more than one legitimate parent (an OrderItem might logically hang off an Order or off a warehouse shipment record in inventory-service), nesting under just one parent is misleading — model it as a top-level resource referenced by ID from both, not nested under either.

Query parameters vs. path segments

The path identifies which resource; the query string modifies how you want to view or filter a collection. A useful test: if the value is part of what makes the resource unique and addressable, it's a path segment; if it's a lens applied to a collection (filtering, sorting, pagination, field selection), it's a query parameter.

GET /api/v1/orders/17                       — a single, uniquely identified resource → path
GET /api/v1/orders?status=SHIPPED&sort=-createdAt&limit=50   — a filtered, ordered view of a collection → query params
GET /api/v1/orders/17/items                 — a sub-collection identified by its parent → path
GET /api/v1/products?category=electronics&inStock=true       — the catalog, filtered → query params

3. HTTP status codes: precise semantics in the 4xx range

Returning the wrong status code isn't a cosmetic issue — clients (including retry middleware, circuit breakers, and monitoring) branch on the status code, not on the response body's prose. A 500 for a validation error tells a resilience layer "the server is unhealthy, back off and retry"; a 422 for the same error correctly tells it "this specific request is unfixable by retrying, surface it to the user."

The five status-code classes, at a glance

Before the 4xx detail below, it's worth having the whole taxonomy in view — every status code's first digit tells any HTTP-aware intermediary (proxy, gateway, browser, retry middleware) which of five broad categories a response falls into, without it needing to parse a single byte of the body:

1xx  Informational   — request received, protocol-level, processing continues
       100 Continue                client may proceed to send the request body
       101 Switching Protocols     e.g. upgrading an HTTP connection to WebSocket

2xx  Success          — the request was received, understood, and accepted
       200 OK                      generic success, body carries the result
       201 Created                 a new resource now exists (POST /api/v1/orders)
       202 Accepted                accepted for async processing, not yet done
                                    (checkout accepted, inventory reservation in flight)
       204 No Content              success, deliberately no response body
                                    (DELETE /api/v1/carts/8841/items/3)

3xx  Redirection      — the client must take an additional step to complete the request
       301 Moved Permanently       resource now lives at a new URI, update bookmarks
       304 Not Modified            cached representation is still valid (conditional GET)

4xx  Client Error     — the request itself is the problem; retrying unchanged won't help
       400 / 401 / 403 / 404 / 409 / 422  — see the table below

5xx  Server Error     — the server failed to fulfill a valid request; may be transient
       500 Internal Server Error   unhandled exception, generic catch-all
       502 Bad Gateway             upstream service (e.g. payment-service) returned garbage
       503 Service Unavailable     server temporarily can't handle the request (overload,
                                    deploy in progress) — often paired with a Retry-After header
       504 Gateway Timeout         an upstream call (order-service -> inventory-service)
                                    exceeded its deadline

The 4xx/5xx boundary is the single most consequential line in this taxonomy for retry logic (see resilience-fault-tolerance): a 5xx is a signal that the server failed and the same request might succeed later (transient overload, a crashed dependency), so retrying — ideally with backoff — is reasonable. A 4xx is a signal that the request is the problem, and retrying the exact same request will fail identically every time; a well-behaved client should not blindly retry a 4xx (400/404/409/422) the way it would a 503, though a 409 conflict specifically can sometimes be resolved by re-fetching state and retrying with corrected data, which is different from a blind retry of the same bytes.

Precise 4xx semantics

CodeMeaningWhen to use it, precisely
400 Bad RequestMalformed requestThe request itself is syntactically broken — invalid JSON, wrong content-type, a required field of the wrong data type. The server couldn't even parse enough to evaluate business rules.
401 UnauthorizedNot authenticatedThe caller's identity is missing or the credential is invalid/expired. Despite the name, this is about authentication, not authorization — "I don't know who you are." (See spring-security for the full authentication-vs-authorization mechanics.)
403 ForbiddenAuthenticated but not permittedThe server knows exactly who you are and you are not allowed to do this — e.g. a Customer's JWT is valid, but they're trying to POST /api/v1/admin/refunds, which requires ROLE_ADMIN. Never return 403 when you actually mean "you're not logged in" — that's 401.
404 Not FoundResource doesn't exist (or you won't say)Also legitimately used to hide the existence of a resource from unauthorized callers — returning 403 on someone else's private order confirms it exists; 404 reveals nothing.
409 ConflictRequest conflicts with current server stateThe request is well-formed and permitted, but can't be applied right now given the resource's current state — a version mismatch on optimistic locking, a Seller trying to create a Product SKU that already exists in their catalog, a Customer trying to cancel an Order that's already SHIPPED.
422 Unprocessable EntitySemantically invalidSyntactically valid (parses fine, right types) but fails business validation — a Coupon's percentOff over 100, a Review's rating outside 1–5. The distinction from 400 is subtle but matters: 400 means "I couldn't understand this," 422 means "I understood it perfectly and it's still wrong."

A common and costly mistake is collapsing every failure into 400 or, worse, always returning 200 with an "error" field in the body. This defeats every piece of HTTP-aware infrastructure sitting in front of your service — API gateways, client SDKs generated from OpenAPI (see section 7), and retry/circuit-breaker logic (see resilience-fault-tolerance) all key off the status code to decide whether to retry, alert, or fail fast. A 200-wrapped error is invisible to all of them until someone inspects the body.

4. Idempotency: the property that makes retries safe

What idempotent actually means

A request is idempotent if making it once has the same effect on server state as making it many times in a row. This is a statement about the side effect, not about the response body being identical byte-for-byte on every call (a GET after a DELETE will correctly return 404 the second time even though the delete itself was idempotent).

MethodSafe (no side effects)?Idempotent?Why
GETYesYesRead-only by definition; repeating it changes nothing.
PUTNoYesPUT means "make the resource at this URI look exactly like this representation." Sending the same representation five times leaves the resource in the same final state as sending it once.
DELETENoYesAfter the first delete the resource is gone; the second delete finds nothing to delete (typically 404 or a no-op 204). Server state after N deletes equals server state after 1 delete.
POSTNoNoPOST means "create a new subordinate resource" or "execute a non-idempotent action." Two identical POSTs to /api/v1/orders naturally create two orders — that's the whole reason it isn't idempotent by specification.
PATCHNoNot guaranteedDepends entirely on the semantics of the patch. {"status": "SHIPPED"} is idempotent (setting the same value twice is a no-op the second time); {"$inc": {"stockQuantity": -1}} is not (each application changes the result — decrementing inventory twice leaves stock two units lower, not one).

Why this matters for retries

Network failures are ambiguous by nature: if a client sends a request and the connection drops before a response arrives, the client cannot tell whether the server never received the request, received it but crashed before processing, or processed it successfully and the response was lost in transit. The only safe general strategy on a timeout is "retry" — but retrying is only safe without qualification when the method is idempotent. Blindly retrying POST /api/v1/orders on a timeout is how a Customer's checkout ends up placing two Orders, or how a flash-sale spike hammering checkout with client-side retry logic ends up double-charging a Payment for what the Customer believed was one purchase.

The Idempotency-Key pattern

Since POST is inherently non-idempotent by specification but many POST operations (creating a payment, placing an order) desperately need retry-safety in practice, the standard fix is to make idempotency an explicit, application-level contract layered on top of HTTP rather than relying on the method semantics:

  1. The client generates a unique key (typically a UUID) once, at the moment the Customer clicks "Place Order" — not once per HTTP attempt.
  2. The client sends this key on every attempt, usually as a header: Idempotency-Key: 6f1c1a1e-....
  3. The server, before executing the side effect, checks whether it has already seen this key. If not, it executes the operation, stores the key alongside the result (and typically the request payload's hash, to detect misuse), and returns the result.
  4. If the server has seen the key before, it does not re-execute the side effect — it returns the stored result from the first execution, verbatim.
POST /api/v1/orders
Idempotency-Key: 6f1c1a1e-9b2e-4b7a-8e34-9d1a2b3c4d5e
{ "customerId": 8841, "items": [{"productId": "prod-42", "quantity": 2}] }

// Server logic (conceptual, inside order-service)
key = request.header("Idempotency-Key")
existing = idempotencyStore.get(key)
if existing != null:
    return existing.response, existing.statusCode   // no second Order created, no second charge
else:
    order = createOrderAndReserveInventory(request.body)   // executes exactly once
    idempotencyStore.put(key, order, ttl = 24h)
    return order, 201

The store lookup and the side effect must be made atomic — typically via a unique constraint on the idempotency key column in the same transaction that inserts the Order row, or a distributed lock — otherwise two near-simultaneous retries (the client's HTTP library retrying on timeout while the first attempt is still mid-flight) can both pass the "not seen yet" check and both create an Order, which defeats the entire purpose. A TTL (commonly 24 hours) bounds how long the server needs to remember keys; after expiry, reusing an old key is treated as a brand-new operation, which is an acceptable trade-off since legitimate retries happen within seconds to minutes, not days. This exact mechanism is what protects payment-service's Payment.idempotencyKey field from a duplicate card capture on the same order — see payment-systems-idempotency for the full mechanics of applying this pattern specifically to money-moving operations, including how it composes with database-level unique constraints and distributed locks under real concurrent load.

Notice what this pattern actually does architecturally: it converts a non-idempotent HTTP method into an idempotent operation by pushing deduplication into application state, keyed by something the client controls. This is the same underlying idea as deduplication in message-driven systems (microservice-patterns) — "at-least-once delivery plus a dedup key equals effectively-once processing" — just applied at the HTTP layer instead of a message broker. A Kafka consumer processing OrderPlaced or PaymentCaptured events downstream of this same checkout flow needs the identical discipline: at-least-once delivery from the broker plus a dedup key (often the same idempotency key, carried through as an event field) to avoid, say, notification-service sending a Customer two "your order shipped" emails for one OrderShipped event redelivery.

5. API versioning strategies

Versioning exists because backward compatibility is not always achievable — sometimes a resource's shape or a field's meaning has to change in a way that breaks existing clients, and you need a way to serve both the old and new contract simultaneously while clients migrate on their own schedule. ShopSphere's /products catalog API is a good concrete case: a redesign that splits a single flat price field into {basePrice, currency, taxIncluded} to support international Sellers is a breaking shape change for every existing client of the catalog-service that expects a single numeric price.

StrategyExampleStrengthsWeaknesses
URI versioning/api/v1/products, /api/v2/productsExtremely visible and discoverable; trivial to route at a gateway/load-balancer level without inspecting headers; easy to test with a browser or curl.Violates the idea that a URI identifies a resource — /api/v1/products/42 and /api/v2/products/42 are "the same" product at two different addresses, which complicates caching and linking. Encourages whole-API version bumps even when only the catalog resource changed.
Header-basedApi-Version: 2 or a custom headerKeeps the URI stable as the true resource identifier; version is metadata about the request, not the resource's identity.Invisible in logs, browser address bars, and casual curl testing unless you know to look; easy for a client to forget to set it and silently get default (often latest, sometimes oldest) behavior; harder to route at some gateway layers without deeper packet inspection.
Content negotiation (media type)Accept: application/vnd.shopsphere.v2+jsonThe most "correct" from a REST purity standpoint — version is a property of the representation format, negotiated the same way HTTP negotiates JSON vs XML vs HTML.Least ergonomic for API consumers to discover and set correctly; tooling support (Postman collections, quick manual testing) is weaker; still shares the header approach's invisibility problem.

In practice, URI versioning dominates public APIs because its visibility lowers the support burden — a client can see /api/v1/ in a stack trace or a support ticket and immediately know which contract is in play. For ShopSphere's /products catalog specifically, this matters more than for most resources: the catalog API is consumed by external Seller integrations (bulk inventory upload tools, price-sync scripts written by third-party Sellers' own engineering teams) who have no ongoing relationship with ShopSphere's platform team and would never reliably set a custom header correctly — a visible /v1/ vs /v2/ path is the only versioning signal likely to actually reach them. Header and media-type versioning are more common internally, where the team controls both ends and can enforce header discipline through generated clients (see the OpenAPI section below), and where keeping the URI stable matters more because internal tooling often treats the URI as a durable resource identifier.

Whichever strategy you pick, version the smallest thing that actually changed. Bumping ShopSphere's entire API from v1 to v2 because the /products catalog's price shape changed forces every client of every other unaffected endpoint — /orders, /cart, /reviews — to migrate too, or forces the platform team to run two nearly-identical copies of the whole API surface. Versioning just /api/v2/products while leaving /api/v1/orders, /api/v1/cart, etc. untouched, while more bookkeeping (the OpenAPI spec now describes a mixed-version surface), avoids this blast radius problem entirely.

6. Pagination: offset vs. cursor

Offset-based pagination

GET /api/v1/products?category=electronics&offset=200&limit=50

Simple to implement (LIMIT 50 OFFSET 200 in SQL) and lets a client jump directly to "page 5" of the catalog. It has two structural problems that get worse as the dataset grows and changes:

  • Performance degrades with offset size. Most databases implement OFFSET by scanning and discarding the first N rows before returning the next page — OFFSET 1000000 means the database still touches a million rows it throws away. There's no way to seek directly to row 1,000,000 without an index that already orders rows by position, which generally doesn't exist.
  • Consistency breaks under concurrent writes. If a Product is delisted (deleted) from before the current offset while a client is paging through the catalog, every subsequent page shifts by one, causing the client to either see the same product twice or skip a product entirely — silently, with no error to signal it happened.

Cursor-based (keyset) pagination

GET /api/v1/orders?limit=50&after=eyJpZCI6IDIwMH0=   // opaque cursor encoding {"id": 200}

-- underlying query, assuming id is the sort key and indexed
SELECT * FROM orders WHERE id > 200 ORDER BY id ASC LIMIT 50

Instead of "skip N rows," the client sends an opaque cursor that encodes the last item it saw, and the server translates that into a WHERE clause on an indexed sort column. This fixes both offset problems at once: the query is an indexed range scan regardless of how deep into the collection the cursor points (constant-ish cost, not proportional to depth), and inserts or deletes anywhere outside the current page don't shift the client's position, because the cursor is anchored to a specific row's key rather than a numeric position that everything after it is relative to. This is exactly the pagination style you want for a Customer's order history (GET /api/v1/customers/8841/orders) — new Orders are constantly being inserted by other Customers system-wide, but that churn happening elsewhere in the table must never shift which page of this Customer's own order history they're currently looking at.

The trade-off is that you give up random access — a client can't jump straight to "page 40" with a cursor, only "the next page after where I am," which is a fine trade for infinite-scroll catalog browsing and order-history APIs but a real limitation for admin UIs that need a page-number jump control. Cursors should also be treated as opaque tokens (base64-encode and, ideally, sign them) rather than raw values, both to allow the encoding to evolve later and to prevent clients from constructing arbitrary offsets by hand.

The sort key backing a cursor must be unique and stable — sorting purely by created_at when multiple Orders can share the same timestamp (a flash-sale spike placing hundreds of orders within the same second) lets rows silently vanish from or duplicate across pages at the boundary. The standard fix is a composite cursor and sort key, such as (created_at, id), so ties are broken deterministically.

7. OpenAPI as a machine-readable contract

An OpenAPI (formerly Swagger) document describes an API's paths, methods, request/response schemas, status codes, and authentication requirements in a structured YAML or JSON file that both humans and tools can read:

paths:
  /api/v1/orders/{orderId}:
    get:
      summary: Fetch an order by ID
      parameters:
        - name: orderId
          in: path
          required: true
          schema: { type: integer }
      responses:
        '200':
          description: Order found
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '404':
          description: No order with this ID
components:
  schemas:
    Order:
      type: object
      required: [id, customerId, status, totalAmount]
      properties:
        id: { type: integer }
        customerId: { type: integer }
        status: { type: string, enum: [CREATED, PAID, SHIPPED, DELIVERED, CANCELLED] }
        totalAmount: { type: number }

Because this is a formal schema rather than prose documentation, it can drive tooling that prose cannot:

  • Generated client SDKs. Tools like OpenAPI Generator or Swagger Codegen turn the spec directly into typed client classes in Java, TypeScript, Python, etc., so a third-party Seller's integration team gets compile-time checking against ShopSphere's actual catalog/order contract instead of hand-writing HTTP calls against a wiki page that drifts out of date.
  • Generated, always-current documentation. Swagger UI or Redoc render the spec into interactive docs that can never lag behind the code if the spec is generated from annotations in the source (Springdoc/springfox in a Spring Boot service, for instance) rather than maintained by hand in parallel.
  • Contract testing. The spec becomes the executable source of truth that both the provider and consumer test against — order-service can validate that its real responses conform to the schema it publishes, and notification-service (which consumes order data to send shipment emails) can validate its expectations against that same schema, catching drift before a breaking change reaches production rather than after a client crashes on an unexpected field. This is the same discipline discussed in testing-strategies under contract testing, and OpenAPI is what makes that contract concrete and machine-checkable instead of an informal agreement between teams.

8. Designing for backward compatibility

Not every change requires a new version — the distinction between additive and breaking changes determines whether existing clients keep working unmodified or need to migrate.

Safe (additive)Breaking
Adding a new optional field to a responseRemoving or renaming an existing field
Adding a new endpointChanging a field's data type (string to number, singular to array)
Adding a new optional request parameter with a sensible defaultMaking a previously optional request field required
Adding a new value to an open-ended enum, if clients are told to tolerate unknown valuesAdding a new value to an enum a client switches on exhaustively with no default case
Relaxing a validation constraint (widening an accepted range)Tightening a validation constraint (narrowing an accepted range, now rejecting previously valid input)
Adding a new, distinct error code alongside existing onesChanging the status code returned for an existing, documented failure case

The enum case deserves particular attention because it's the most common accidental break: a field documented as an enum feels closed, so client code frequently pattern-matches on it exhaustively (a switch with no default, or a Map lookup that throws on a miss). Adding RETURNED to an Order.status enum that used to be {CREATED, PAID, SHIPPED, DELIVERED, CANCELLED} is "just adding a value" from order-service's perspective but breaks every downstream client — notification-service's status-to-email-template lookup, a Seller's own inventory-sync script parsing webhook payloads — that assumed the set was closed. The fix is contractual, not technical: document enums that may grow as open sets from day one, and require clients to have an explicit fallback branch for unrecognized values.

A useful discipline is to make the additive/breaking distinction part of code review for API changes specifically, backed by the OpenAPI spec: diff the spec between versions and treat any removal, type change, or new required field as requiring a deliberate version bump and a documented migration window, not something that ships silently in a routine deploy.

9. JSON serialization with Jackson: the layer between your objects and the wire

Every one of the request/response bodies discussed so far — the Order resource, the OpenAPI schemas block, the error bodies in the next section — has to actually be converted between a Java object graph and JSON bytes on the wire. In a Spring Boot service that conversion is handled by Jackson, and Spring wires it in automatically: a @RestController method that returns an Order gets it serialized by an ObjectMapper bean without you ever calling it directly. Understanding what that ObjectMapper is doing, and where its defaults are dangerous, matters because serialization bugs are invisible in code review — they only show up as a field silently missing from a response, or a security report six months later.

ObjectMapper basics

The ObjectMapper is Jackson's central class — it's what walks a Java object's fields (or, for deserialization, a JSON tree) and converts between the two representations. Spring Boot auto-configures a shared, thread-safe ObjectMapper bean for you (thread safety matters because it's reused across every request), but the same operations are visible if you use it directly:

ObjectMapper mapper = new ObjectMapper();

// Java object -> JSON string
String json = mapper.writeValueAsString(order);

// JSON string -> Java object
Order order = mapper.readValue(json, Order.class);

// JSON string -> a generic type, e.g. List<Order>
List<Order> orders = mapper.readValue(json, new TypeReference<List<Order>>() {});

By default, Jackson matches JSON field names to Java field names (or, more precisely, to the property implied by a getter/setter pair) using reflection, with no annotations required at all. This "it just works" default is exactly why the annotations below matter — the moment your JSON shape and your Java shape need to diverge even slightly, you need a way to tell Jackson explicitly.

Controlling the mapping: @JsonProperty, @JsonIgnore, @JsonCreator, @JsonInclude

The default name-matching convention breaks down the instant the wire format and the Java model disagree — a common case is an external payment provider's webhook using snake_case while ShopSphere's Payment class uses Java's camelCase convention. @JsonProperty gives you an explicit, per-field mapping instead of relying on the convention matching by accident:

public class Payment {
    @JsonProperty("payment_id")
    private String paymentId;

    @JsonProperty("card_last_four")
    private String cardLastFour;
}

@JsonIgnore excludes a field from serialization (and, by default, deserialization too) entirely — the field exists on the Java object but never appears on the wire in either direction. This is the mechanism that keeps a Customer entity's passwordHash field from ever leaking into an API response just because it happens to sit on the same JPA entity that gets returned from a controller:

public class Customer {
    private Long id;
    private String email;

    @JsonIgnore
    private String passwordHash;   // never serialized, regardless of caller
}

@JsonCreator, usually paired with @JsonProperty on constructor parameters, tells Jackson which constructor to use when deserializing — essential once a class has no no-arg constructor, is immutable, or has multiple constructors and Jackson's default "guess the right one" heuristic can't be trusted:

public class Money {
    private final BigDecimal amount;
    private final String currency;

    @JsonCreator
    public Money(@JsonProperty("amount") BigDecimal amount,
                 @JsonProperty("currency") String currency) {
        this.amount = amount;
        this.currency = currency;
    }
}

@JsonInclude controls whether a field is written out at all based on its value — the most common use is @JsonInclude(JsonInclude.Include.NON_NULL), which omits a field from the JSON entirely rather than emitting "discountCode": null. This matters for API consumers that use "is this key present" as a signal distinct from "is this key present with a null value" (a common convention in PATCH semantics — see the error-contract section below for how validation failures are shaped), and it keeps response payloads smaller when a resource has many optional fields that are usually absent, such as an Order's optional giftMessage or couponCode.

Polymorphic deserialization: @JsonTypeInfo and @JsonSubTypes

Deserialization gets genuinely harder when a JSON payload needs to become one of several possible Java subtypes, and the correct subtype isn't knowable from the target field's declared type alone. ShopSphere's payment domain is a natural example: a PaymentMethod field on a checkout request might need to become a CreditCardPayment, a WalletPayment, or a BankTransferPayment depending on what the client sent, and Jackson has no way to know which one to instantiate just by looking at the abstract PaymentMethod type. @JsonTypeInfo and @JsonSubTypes solve this by embedding a discriminator field in the JSON that tells Jackson which concrete class to pick:

@JsonTypeInfo(
    use = JsonTypeInfo.Id.NAME,
    include = JsonTypeInfo.As.PROPERTY,
    property = "type")
@JsonSubTypes({
    @JsonSubTypes.Type(value = CreditCardPayment.class, name = "CREDIT_CARD"),
    @JsonSubTypes.Type(value = WalletPayment.class, name = "WALLET"),
    @JsonSubTypes.Type(value = BankTransferPayment.class, name = "BANK_TRANSFER")
})
public abstract class PaymentMethod {
    // common fields, e.g. amount
}

public class CreditCardPayment extends PaymentMethod {
    private String cardNumberLastFour;
    private String expiryDate;
}
{
  "type": "CREDIT_CARD",
  "amount": 49.99,
  "cardNumberLastFour": "4242",
  "expiryDate": "09/27"
}

On deserialization, Jackson reads the type property first, looks it up in the @JsonSubTypes table, and instantiates CreditCardPayment instead of trying (and failing) to instantiate the abstract PaymentMethod directly. This is the same underlying problem as an OrderEvent hierarchy on a Kafka topic (OrderPlaced, OrderCancelled, OrderShipped all deserialized off one topic based on an event-type discriminator) — polymorphic deserialization by discriminator field is a recurring pattern anywhere one wire format needs to become one of several possible types.

The security risk: deserializing untrusted input into overly permissive types

Polymorphic deserialization is also one of the most well-documented sources of remote code execution vulnerabilities in the Java ecosystem, and it's worth understanding precisely why. The danger appears when Jackson is configured to determine the target class from a type name embedded in the JSON itself — most dangerously via a global setting like ObjectMapper.enableDefaultTyping() (deprecated precisely because of this issue) or by deserializing directly into a maximally generic type such as Object or a loosely-bounded interface, combined with polymorphic type handling turned on. An attacker who controls the JSON payload can then specify an arbitrary class name as the discriminator — including classes never intended to be deserialization targets at all, such as classes from logging frameworks or connection pools whose constructors or setters have observable side effects (opening a JNDI lookup, reading a file, executing a process) purely as a consequence of being instantiated and populated. Chaining such "gadget classes" together is the basis of well-known Jackson deserialization CVEs.

The defense is architectural, not a single flag: never enable global default typing; scope any @JsonTypeInfo polymorphism to a specific, closed, explicitly-enumerated set of subtypes via @JsonSubTypes exactly as shown above, rather than an open type hierarchy; and never deserialize a request body directly into Object, Map<String,Object> passed on to further polymorphic processing, or any other type whose universe of possible concrete classes isn't fully controlled by your own codebase. This is the JSON-specific instance of a general rule covered in security-hardening-owasp: never let untrusted input control which code runs, and a type discriminator that selects a Java class to instantiate is exactly that kind of control if the set of selectable classes isn't tightly closed.

A concrete rule of thumb for ShopSphere services: any controller endpoint accepting a payload with an open-ended @JsonTypeInfo hierarchy (like the checkout endpoint accepting different PaymentMethod subtypes above) must keep @JsonSubTypes as an explicit, reviewed allowlist. Adding a new payment method type should require a code change and review, never a value the client is free to invent, because the instant the discriminator can select a class no one on the team chose, deserialization stops being a data-mapping concern and becomes a code-execution attack surface.

10. A consistent, centralized error-response contract

Section 3 established precise semantics for which status code a given failure should return. That solves half the problem — the other half is what the body of an error response looks like, and without a deliberate answer, every controller in a codebase tends to invent its own shape: one throws a raw exception message straight into the body, another wraps it in {"error": "..."}, a third returns a bare string. A client integrating against ShopSphere's API then has to write a different error-parsing branch per endpoint, which is exactly the kind of inconsistency an API contract is supposed to prevent.

Mapping an exception hierarchy to status codes with @ControllerAdvice

Spring MVC's @ControllerAdvice (combined with @ExceptionHandler) lets you centralize this decision in one place instead of scattering try/catch blocks across every controller method. A @ControllerAdvice-annotated class is applied globally, across every @RestController in the application, and each @ExceptionHandler method declares which exception type it handles:

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(ErrorResponse.of("RESOURCE_NOT_FOUND", ex.getMessage()));
    }

    @ExceptionHandler(OrderConflictException.class)
    public ResponseEntity<ErrorResponse> handleConflict(OrderConflictException ex) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(ErrorResponse.of("ORDER_CONFLICT", ex.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception ex) {
        // last resort: never leak stack traces or internal messages to the client
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(ErrorResponse.of("INTERNAL_ERROR", "An unexpected error occurred"));
    }
}

The design work here is really in the exception hierarchy this class is mapping, not in the Spring plumbing itself: a well-designed domain defines specific exceptions (ResourceNotFoundException, OrderConflictException, InsufficientInventoryException) that carry enough semantic meaning to determine a status code unambiguously, rather than throwing generic RuntimeExceptions everywhere and forcing the @ControllerAdvice to guess. Spring dispatches to the most specific matching @ExceptionHandler for the thrown exception's actual type, falling back to a broader handler (like the catch-all Exception.class above) only when nothing more specific matches — which is precisely why that catch-all must never leak a raw exception message or stack trace into the response body: it's the backstop for the failure modes you didn't anticipate, and those are exactly the ones most likely to contain something you don't want a client to see (a SQL fragment, an internal class name, a file path).

A consistent error-body shape

Whatever the status code, the body should follow one predictable shape across the entire API, so client-side error handling can be written once instead of per-endpoint. A typical shape carries a stable machine-readable error code, a human-readable message, and — for validation failures specifically — a list of field-level problems:

public class ErrorResponse {
    private String errorCode;         // stable, machine-readable: "VALIDATION_FAILED", "ORDER_CONFLICT"
    private String message;           // human-readable summary, safe to display or log
    private List<FieldError> fieldErrors;   // populated only for validation failures; else empty/omitted
    private Instant timestamp;

    public static class FieldError {
        private String field;         // e.g. "email", "items[0].quantity"
        private String message;       // e.g. "must not be blank", "must be greater than 0"
    }
}
{
  "errorCode": "VALIDATION_FAILED",
  "message": "Request validation failed",
  "fieldErrors": [
    { "field": "email", "message": "must be a well-formed email address" },
    { "field": "items[0].quantity", "message": "must be greater than 0" }
  ],
  "timestamp": "2026-08-26T14:03:11Z"
}

The errorCode is what client code should actually branch on — it's stable across releases and doesn't change if a translator later rewrites the human-readable message for clarity or localization. Relying on parsing the message string in client code is a classic hidden coupling: a well-intentioned copy edit to the error text ("Order not found" → "No order found with that ID") silently breaks any client that was string-matching on the old wording, whereas a stable errorCode like RESOURCE_NOT_FOUND gives them something safe to depend on.

Bean Validation failures map into the same contract

Bean Validation annotations (@NotNull, @Email, @Min, @Size, and the rest of the jakarta.validation.constraints package) on a @RequestBody-annotated DTO, triggered by @Valid on the controller parameter, are what produce the field-level errors above — but by default, Spring throws MethodArgumentNotValidException when validation fails, and left unhandled that exception serializes into Spring's own default error shape, not your custom ErrorResponse. The fix is to catch it in the same @ControllerAdvice and translate it into your contract:

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
    List<ErrorResponse.FieldError> fieldErrors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .map(fe -> new ErrorResponse.FieldError(fe.getField(), fe.getDefaultMessage()))
            .toList();

    ErrorResponse body = ErrorResponse.of("VALIDATION_FAILED", "Request validation failed");
    body.setFieldErrors(fieldErrors);
    return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(body);
    // Note: some teams map this to 422 instead of 400 - see the 400-vs-422 distinction in section 3
}

ex.getBindingResult() is where Spring accumulates every individual constraint violation across the whole request body — every @NotBlank, @Min, and @Pattern failure on the DTO, not just the first one encountered — which is exactly what lets the handler above produce the full list of fieldErrors in one response instead of forcing the client through a frustrating fix-one-error-resubmit-see-the-next-one cycle. Handling this one exception type in the shared @ControllerAdvice, right alongside the domain exceptions from the previous subsection, is what makes "malformed checkout payload" and "order already shipped" show up to a client as the same predictable ErrorResponse shape rather than two unrelated formats — one accident of Bean Validation's default behavior, and one hand-rolled by whoever wrote that particular controller.

11. API documentation and developer experience

Section 7 covered OpenAPI as a machine-readable contract in the abstract; in a real Spring Boot service, that spec is almost never written by hand — it's generated from the controllers, DTOs, and validation annotations that already exist in the code, using springdoc-openapi (the actively maintained successor to the older springfox/Swagger 2 libraries).

springdoc-openapi and Swagger UI

Adding the springdoc-openapi-starter-webmvc-ui dependency to a Spring Boot application is enough, with zero configuration, to get a working OpenAPI spec at /v3/api-docs and an interactive Swagger UI at /swagger-ui.html — springdoc inspects the application's @RestController classes, their @RequestMapping/@GetMapping/@PostMapping methods, the DTOs used as @RequestBody and return types, and the Bean Validation annotations on those DTOs, and derives the spec's paths and schemas directly from them. Annotations refine what's auto-derived when the code alone is ambiguous or under-documented:

@RestController
@RequestMapping("/api/v1/orders")
@Tag(name = "Orders", description = "Order lifecycle operations")
public class OrderController {

    @Operation(summary = "Fetch an order by ID")
    @ApiResponses({
        @ApiResponse(responseCode = "200", description = "Order found"),
        @ApiResponse(responseCode = "404", description = "No order with this ID")
    })
    @GetMapping("/{orderId}")
    public OrderDto getOrder(@PathVariable Long orderId) {
        // ...
    }
}

The practical payoff mirrors section 7's point about generated documentation: because the spec is derived from the same source code that actually executes, it cannot silently drift out of date the way a hand-maintained wiki page or Postman collection does — if a field is removed from the DTO, it disappears from the generated spec and the Swagger UI in the very same deploy, with no separate documentation-update step to forget.

Code-first vs. contract-first

What springdoc does is the "code-first" approach — the code is the source of truth, and the OpenAPI spec is a derived artifact generated after the fact. The alternative, "contract-first" (or "design-first"), reverses the order: the team hand-writes the OpenAPI YAML first, as an explicit design and negotiation step, and then generates server-side interface stubs (and client SDKs) from that spec before implementation begins.

Code-first (springdoc)Contract-first (hand-written spec)
Source of truthThe Java codeThe YAML/JSON spec file
Speed for a small teamFast — no separate design artifact to maintainSlower up front — the spec is a deliverable before any code exists
Cross-team / external API designWeaker — the shape emerges from implementation details, and other teams can't review it until code existsStronger — consumers (mobile team, third-party Sellers) can review and agree on the contract before a single controller is written
Risk of driftLow — spec is regenerated from code every build, can't lag behind itHigher — nothing forces the implementation to actually match the hand-written spec unless contract tests enforce it
Good fit forInternal services with one team owning both API and implementationPublic/partner-facing APIs (like ShopSphere's Seller integration APIs) where the contract needs sign-off from multiple independent teams before implementation

Neither approach is universally correct — the trade-off is essentially "optimize for implementation speed and freshness" versus "optimize for up-front cross-team agreement," and it's reasonable for a platform team to use code-first internally for services only they consume, while using contract-first for the small set of APIs that external Sellers or partner teams build against, where an API's shape changing out from under a partner mid-integration is a far more expensive mistake than the extra up-front design time.

Generating client SDKs from the spec

Whichever approach produces the spec, the same OpenAPI document — whether generated by springdoc or hand-written contract-first — is what tools like OpenAPI Generator consume to produce typed client libraries, exactly as introduced in section 7. This closes the loop between documentation and actual developer experience: a third-party Seller's engineering team, or ShopSphere's own mobile team, doesn't need to hand-write HTTP calls and hope they match the Swagger UI's description — they run a code-generation step against the published spec and get a typed OrdersApi client class whose method signatures are checked by their own compiler, so a breaking change to the spec (a field removed, a type changed) shows up as their build failing immediately, rather than as a runtime error discovered by a confused end user weeks later.

Concepts Worth Being Able to Explain From First Principles

Why is Level 2 of the Richardson Maturity Model treated as "good enough" rather than a compromise?
Level 2 already gives you the property that matters most in practice: HTTP-aware infrastructure (caches, gateways, browsers, monitoring, retry logic) can understand your traffic without any custom logic, purely by looking at the method and status code. Level 3's hypermedia links add a further decoupling — clients don't hardcode URI structure, they follow links — but that decoupling only pays off when the server's URI structure changes often and independently of client deployments, which is uncommon in most systems where the client and server evolve together and are typically versioned in lockstep. The added complexity of designing, documenting, and versioning link relations is a cost paid unconditionally, while the benefit is conditional, which is why most production APIs rationally stop at Level 2.
Why does POST retry on a network timeout carry real risk, while GET retry does not?
A timeout is ambiguous — the client cannot distinguish "the server never got the request," "the server got it but crashed mid-processing," and "the server finished successfully but the response was lost." For GET, none of these ambiguity branches matter because GET has no side effect: retrying just re-reads state, so the outcome is identical no matter which branch actually happened. For POST, the branches matter enormously: if the server actually did finish processing (say, charging a card) and only the response was lost, a naive retry executes the charge a second time. The fix is not to avoid retrying POST — retries are still necessary for resilience — but to make the specific POST operation idempotent at the application level, typically via an idempotency key, so that whichever branch occurred, the retry converges to the same single side effect.
What is the difference between "idempotent" and "safe" in HTTP method semantics, and why does PUT count as one but not the other?
Safe means the method has no side effects at all — it only reads state (GET, HEAD). Idempotent means repeating the request N times produces the same server state as doing it once, but it may still have a side effect on the first call. PUT is not safe — it can create or overwrite a resource, which is very much a side effect — but it is idempotent, because sending the exact same representation five times in a row leaves the resource in exactly the state described by that representation, identical to sending it once. The two properties are independent: all safe methods are idempotent, but not all idempotent methods are safe.
Why must the idempotency-key check and the side-effect execution be atomic, and what goes wrong if they aren't?
If the server checks "have I seen this key?" as a separate step from "execute the payment and store the key," two retries arriving close together can both read "not seen yet" before either has written its result, because the check-then-act sequence isn't protected from interleaving. Both requests then proceed to charge the card, and only afterward does one of the writes to the idempotency store win — defeating the entire purpose of the pattern. The standard fix is to make the key's uniqueness enforced by the same transaction that performs the side effect, for example a unique constraint on the idempotency-key column in the same database transaction that inserts the payment row, so the second concurrent attempt fails the insert and is forced to read back the first attempt's result instead of executing its own charge.
Why does offset-based pagination silently skip or duplicate rows under concurrent writes, and how does keyset pagination avoid it?
Offset pagination defines a page purely by numeric position in a result set — "give me rows 200 through 250." That position is relative to everything before it, so if a row is deleted from among the first 200 while a client is midway through paging, everything shifts left by one: what used to be row 250 is now row 249, causing the client's next request for "starting at 250" to skip what was originally row 251. Insertions cause the mirror problem, duplicating a row across two pages. Keyset pagination instead anchors each page to the actual identity of the last row seen — "give me rows where id > 200" — so the page boundary moves with the data rather than being a fixed numeric offset; a deletion elsewhere in the table doesn't change what "greater than the last id I saw" means, so no row is skipped or repeated.
Why is adding a value to an enum considered a breaking change even though nothing existing was removed or renamed?
The server-side view of a schema is additive-friendly by nature — adding a case to an enum's declared set doesn't remove any existing capability. But client code frequently treats a documented enum as a closed, exhaustive set: a switch statement with no default branch, or a lookup table that throws on a miss, both implicitly assume no new values will ever appear. When the server starts returning a new value, that client code doesn't get a compatible response, it gets a runtime exception or an unhandled branch — a real break, even though the API's contract was only extended, not altered. This is why enums intended to grow need to be documented as open sets up front, with clients required to implement a default/fallback case, shifting the compatibility burden to where it can actually be handled safely.
Why does URI versioning dominate public APIs even though it's arguably less "correct" from a strict REST standpoint?
Strictly, a URI is supposed to identify a resource, and /v1/orders/17 and /v2/orders/17 encoding "the same order" at two different addresses muddies that identity — header or media-type versioning keeps the URI stable and treats the version as metadata about the representation instead. But URI versioning wins in practice because it is maximally visible: it shows up in browser address bars, curl commands, stack traces, and support tickets without anyone needing to know to inspect a header. That visibility lowers the operational and support cost of running multiple versions simultaneously, which matters more for most organizations than the purity of resource identity — especially for public-facing APIs consumed by many independent teams (like ShopSphere's third-party Seller integrations) who won't reliably set a custom header correctly.
Why does the 4xx/5xx boundary matter more for retry logic than the specific status code within each class?
The first digit of a status code is a deliberate, coarse signal about where the failure originates: 4xx says the problem is in the request itself (a Customer's malformed checkout payload, a Coupon code that doesn't exist), and 5xx says the problem is on the server's side (order-service crashed, payment-service timed out calling its own database). This distinction is exactly what a resilience layer (circuit breaker, retry-with-backoff middleware) needs to make a retry decision without understanding any application-specific semantics: retrying the identical bytes of a 4xx request will fail identically every time, because nothing about the server's state changed and the request was the defect — retrying just wastes a round trip and adds load for no benefit. A 5xx, by contrast, often reflects a transient condition (a momentary overload, a dependency blip) that may have cleared by the time a retry arrives, so backing off and retrying is a reasonable default. This is precisely why generic HTTP infrastructure — API gateways, load balancers, client SDK retry policies — can implement a single, universal rule ("retry 5xx with backoff, don't retry 4xx") without knowing anything about orders, payments, or ShopSphere's domain at all; the status-code class alone carries enough information to make the decision correctly.
Why is unrestricted polymorphic JSON deserialization a security risk, not just a data-mapping inconvenience?
When Jackson resolves a concrete class to instantiate from a type name embedded in the JSON itself, and that resolution isn't scoped to a small, explicit, developer-controlled set of classes, an attacker who controls the request body effectively gets to choose which Java class gets instantiated and populated on your server. If that universe of selectable classes is unbounded (as it is with global default typing enabled, or deserialization into a bare Object/loosely-typed Map), the attacker can pick classes never intended as deserialization targets — ones whose constructors or setters have side effects purely from being invoked, such as opening a network connection or invoking a lookup. Chaining such classes together is the basis of real, well-documented remote code execution vulnerabilities. The fix is to always scope polymorphism to an explicit, closed @JsonSubTypes allowlist and never enable global default typing, so the set of classes a JSON payload can cause to be instantiated is exactly the set your own code chose, not the set an attacker can name.
Why should client error-handling code branch on an errorCode field rather than the message string in an error response?
The message field exists to be read by a human — it's expected to change over time as copy gets clarified, localized, or made more specific, and none of those changes are meant to be breaking. If client code parses or string-matches against message, a purely cosmetic wording change on the server becomes a silent breaking change for every client that depended on the old phrasing. A stable, machine-readable errorCode (like RESOURCE_NOT_FOUND or ORDER_CONFLICT) is explicitly designed not to change across such edits, giving clients something safe and durable to branch their logic on, while the message remains free to evolve for readability without needing a version bump or a migration notice.
Why does centralizing exception-to-status-code mapping in one @ControllerAdvice matter more than just getting each individual status code right?
Getting a single endpoint's status code right is necessary but not sufficient — if every controller in a codebase independently decides how to catch and translate its own exceptions, the resulting error bodies inevitably drift into inconsistent shapes: one controller returns a bare string, another wraps a message in a differently-named field, a third leaks a raw stack trace by accident. A single, centralized @ControllerAdvice makes the mapping from exception type to status code and body shape a one-time architectural decision applied uniformly across the entire API, including a catch-all handler for exceptions no one anticipated. That uniformity is what actually lets a client write one error-parsing code path for the whole API instead of one per endpoint, and it's also what guarantees the catch-all backstop for unexpected exceptions never accidentally leaks internal details, since that logic lives in exactly one place instead of being re-implemented, and potentially forgotten, per controller.
Why would a team choose contract-first API design over code-first even though it's slower up front?
Code-first (generating the OpenAPI spec from annotated controllers, as springdoc does) optimizes for a single team moving fast and never having the spec drift from the implementation, since the spec is regenerated from the code on every build. But it means the API's actual shape only becomes visible to other teams once the code exists, which is a problem when the consumers of that API — a mobile team, or especially independent third-party partners like ShopSphere's Sellers — need to review, negotiate, and even start building their own integration before the server-side implementation is finished. Contract-first flips the order: the spec is hand-written and agreed upon first, as an explicit design artifact multiple teams can review and sign off on, and both server stubs and client SDKs are generated from that agreed contract afterward. The up-front cost is slower initial delivery and the need for contract tests to keep the implementation honest against the spec, but that cost buys cross-team agreement before anyone has written code that's expensive to change — worth it precisely for the APIs where a mid-integration breaking change would be costly for a partner who doesn't share your deploy pipeline.
