LLD #1: Parking Lot System

Requirements Modeling SOLID in Practice Strategy Pattern Factory Pattern Concurrency & Races State Management Extensibility
Why this matters

A parking lot looks trivial until two cars arrive at the two remaining compact spots at the same instant through two different gates, or until the business asks you to add electric-vehicle spots with a new pricing model six months after launch. The value of designing this system carefully isn't the parking lot itself — it's that the same three failure modes (a naive read-then-write race on shared state, a design that requires editing five classes to add one new type, and business rules hardcoded where they can't be swapped) show up in booking systems, elevator controllers, and inventory reservation systems everywhere. Working through parking lot design from first principles is really a rehearsal for the entity-modeling and concurrency-safety instincts you need in almost every stateful backend system.

1. Gathering and Stating Requirements Explicitly

The single biggest failure mode in low-level design exercises is jumping straight to classes before the requirements are pinned down. Every ambiguity you leave implicit becomes a design decision you make by accident, usually the wrong one. For a parking lot, the requirements worth stating out loud before writing anything are:

  • Structure: the lot has multiple floors; each floor has a fixed number of spots of different types.
  • Spot types: at minimum MOTORCYCLE, COMPACT, LARGE, and HANDICAPPED, each with different physical dimensions and different eligibility rules (a motorcycle can park in a large spot but not vice versa; a handicapped spot requires a permit check).
  • Vehicle types: MOTORCYCLE, CAR, BUS/TRUCK — each vehicle type maps to a set of spot types it's allowed to occupy, not a 1:1 mapping.
  • Gates: multiple physical entry gates and multiple exit gates operate concurrently and independently; each entry gate can issue a ticket, each exit gate can process payment and close a ticket.
  • Ticketing: entering issues a ticket bound to a vehicle, an assigned spot, and an entry timestamp; the ticket is the sole proof of parking and the sole input to the exit flow.
  • Pricing and payment: cost is a function of duration and spot type (or vehicle type), computed at exit, and paid through a pluggable payment mechanism (cash, card, wallet).
  • Availability tracking: the system must answer "is there a free spot of type X" in something close to O(1), not by scanning every spot on every floor on every query — this becomes a real cost at scale with many floors and frequent entry attempts.
Requirements shape the class boundaries, not the other way around

Notice that "multiple gates operate concurrently" is a requirement, not an implementation detail you notice later. If you don't write it down up front, it's very easy to design ParkingLot.parkVehicle() as a simple sequential method, get it "working" against a single-threaded test, and only discover the race condition when someone explicitly asks about concurrent entry. Stating concurrency as a first-class requirement up front is what makes you design the spot-allocation path to be atomic from the start rather than retrofitting a lock onto a broken design later.

2. Core Entities and Their Responsibilities

The right entity boundary follows the Single Responsibility Principle: each class should have exactly one reason to change. Working backward from the requirements above:

Notice the pattern: every class that could plausibly change for a business reason (allocation policy, pricing policy, payment channel) has been pulled out of ParkingLot into its own interface. That separation is not incidental — it's the direct consequence of applying SRP and is what makes the next section's SOLID discussion concrete rather than abstract.

3. Applying SOLID to the Design

Single Responsibility — why ParkingLot doesn't compute fares

If ParkingLot both tracked spots and computed pricing, a change to the pricing model (say, switching from flat-per-hour to a tiered rate) would require editing and re-testing the same class responsible for spot bookkeeping — two unrelated concerns coupled by accident. Splitting pricing into PricingStrategy means a pricing change touches exactly one class, and that class has no idea how spots are laid out.

Open/Closed — why allocation and pricing are Strategy objects

The requirement "the business may want to change how spots are assigned" (nearest-to-entrance first, largest-fit first, load-balanced across floors) is exactly the situation the Strategy pattern exists for. Define:

interface SpotAllocationStrategy {
    Optional<ParkingSpot> findSpot(VehicleType type, List<Floor> floors);
}

class NearestFirstStrategy implements SpotAllocationStrategy { ... }
class LargestFitStrategy implements SpotAllocationStrategy { ... }

ParkingLot holds a reference to a SpotAllocationStrategy (injected at construction, or swappable at runtime) and simply calls strategy.findSpot(...). Adding "prefer floors closest to the elevator" as a new policy means writing one new class and wiring it in — ParkingLot's source is never touched. That is precisely what Open/Closed means in practice: open for extension (new strategy classes), closed for modification (the class that uses the strategy doesn't change). The same reasoning applies to PricingStrategy — a "first hour free" promotion is a new class, not an if branch inserted into existing fare logic.

Liskov Substitution — why SpotType eligibility must be modeled as data, not type-checking code

A tempting but wrong design is to give Vehicle subclasses (Car, Motorcycle, Bus) an overridden method like canParkIn(ParkingSpot spot) with type-specific logic duplicated in each subclass. This risks Liskov violations the moment a new spot type is added, because every vehicle subclass now needs a matching branch, and it's easy for one subclass to enforce a stricter or laxer rule than its siblings in a way that breaks substitutability (code that works correctly for a generic Vehicle should keep working when handed any concrete vehicle). The more robust model is a single compatibility table — a Map<VehicleType, Set<SpotType>> — consulted uniformly regardless of concrete vehicle class, so behavior is data-driven and every vehicle type is checked through the same code path.

Interface Segregation — why EntryGate and ExitGate are separate types

A single fat Gate interface with both issueTicket() and processPayment() would force every gate implementation to depend on methods it may never use — a purely entry-only turnstile has no business implementing payment logic. Splitting into EntryGate and ExitGate means each concrete gate depends only on the operations it actually performs.

Dependency Inversion — why ParkingLot depends on interfaces, not concrete classes

ParkingLot should hold references typed as SpotAllocationStrategy, PricingStrategy, and (indirectly, through ExitGate) PaymentProcessor — never as concrete classes like NearestFirstStrategy. This is what actually enables Open/Closed to hold in practice: if ParkingLot held a concrete NearestFirstStrategy field, swapping strategies would still require editing ParkingLot's source. Dependency Inversion is the mechanism; Open/Closed is the payoff. This mirrors the same interface-first thinking covered in SOLID & design patterns generally — the parking lot is simply a concrete vehicle for applying it.

Factory — why ParkingSpot construction is centralized

Constructing the right concrete spot behavior (a handicapped spot needs a permit check baked into its acceptance logic; a large spot needs to know it can also host motorcycles) is exactly what a Factory exists to encapsulate:

class ParkingSpotFactory {
    static ParkingSpot create(SpotType type, String spotId, int floorNumber) {
        switch (type) {
            case MOTORCYCLE:   return new ParkingSpot(spotId, floorNumber, SpotType.MOTORCYCLE);
            case COMPACT:      return new ParkingSpot(spotId, floorNumber, SpotType.COMPACT);
            case LARGE:        return new ParkingSpot(spotId, floorNumber, SpotType.LARGE);
            case HANDICAPPED:  return new HandicappedSpot(spotId, floorNumber);
            default: throw new IllegalArgumentException("Unknown spot type: " + type);
        }
    }
}

The benefit is not just "less repeated construction code" — it's that Floor's constructor and anything else building out the lot's layout never needs to know about the existence of HandicappedSpot as a distinct class; it only asks the factory for a SpotType.HANDICAPPED and gets back something that satisfies the ParkingSpot contract.

4. Concurrency: The Real Problem This Design Must Solve

Where the race condition actually lives

Assume the lot has exactly one free COMPACT spot left. Two cars arrive at two different entry gates within milliseconds of each other. Both entry threads execute logic that looks, at first glance, completely reasonable:

// BROKEN — check-then-act is not atomic
ParkingSpot spot = findFirstAvailable(SpotType.COMPACT);  // both threads read the SAME free spot
if (spot != null) {
    spot.setOccupied(true);      // both threads write true — no conflict detected here!
    spot.setVehicle(vehicle);    // second write silently overwrites the first
    issueTicket(vehicle, spot);  // BOTH gates issue a ticket for the SAME physical spot
}

This is the canonical check-then-act race: "check availability" and "act on it" are two separate operations with a window between them, and nothing prevents a second thread from performing its own check before the first thread's act has taken effect. The visible symptom in production would be two vehicles physically directed to the same spot, or — just as bad — a spot that gets marked occupied by thread B's write clobbering thread A's ticket reference, leaving one ticket pointing at a spot with no reliable owner. This is exactly the same shape of bug covered generally in multithreading & concurrency: visibility and atomicity are two separate guarantees, and neither a plain boolean field nor even a `volatile` one gives you atomicity for a read-modify-write sequence.

Why "make the field volatile" does not fix this

volatile only guarantees that a write becomes visible to subsequent reads — it says nothing about two threads performing a read-check-write sequence without interleaving. Both gate threads can each observe occupied == false (a perfectly valid, up-to-date read) before either has written true. The fix has to make the entire "check and claim" sequence a single indivisible operation.

Fix 1 — a lock per spot

class ParkingSpot {
    private final ReentrantLock lock = new ReentrantLock();
    private volatile boolean occupied = false;
    private Vehicle vehicle;

    boolean tryOccupy(Vehicle v) {
        lock.lock();
        try {
            if (occupied) return false;
            occupied = true;
            vehicle = v;
            return true;
        } finally {
            lock.unlock();
        }
    }
}

Now the allocation strategy must call tryOccupy() — not just check a getter — and treat a false return as "this spot was taken between when I found it and when I tried to claim it; look for the next candidate." This turns allocation into a retry loop rather than a single check-then-assign step, but it makes each individual claim atomic. A lock per spot (rather than one lock guarding the entire floor or lot) is the right granularity because it lets two unrelated spots be claimed concurrently with zero contention between them — coarse-grained locking (a single lock around the whole ParkingLot) would work correctly too, but would serialize every entry attempt across the entire building even when they're targeting spots on different floors, which becomes a real throughput bottleneck as gate count grows.

Fix 2 — atomic compare-and-swap on spot state

An alternative that avoids blocking entirely: model spot state as an AtomicReference<SpotState> (or an AtomicBoolean for occupied/free) and claim a spot with compareAndSet(FREE, OCCUPIED). If the CAS fails, another thread won the race for that exact spot, and the caller moves on to the next candidate spot without ever blocking on a lock. This is preferable under high contention because failed CAS attempts are cheap (no OS-level thread suspension), whereas a contended ReentrantLock can eventually escalate to actual thread parking. For a resource with many interchangeable candidates (many compact spots, not one bottleneck resource), CAS-with-retry across candidates tends to scale better than locking, because contention is naturally spread across many independent atomic references rather than funneled through one shared lock.

Locking order still matters even with per-spot locks

Per-spot locks solve the race on a single spot, but if any code path ever needs to hold locks on two spots at once (for example, a "swap this vehicle to a better spot" feature), acquiring them in inconsistent order across threads reintroduces deadlock risk — thread A locks spot 12 then wants spot 47, while thread B locks spot 47 then wants spot 12. The general fix, as elsewhere, is to always acquire multiple locks in a single global order (e.g., by spot ID) regardless of which spot a given operation "starts" from.

Availability counters need the same discipline

Requirement 1 asked for near-O(1) availability queries, which implies maintaining a running count per spot type (e.g., Map<SpotType, AtomicInteger> on each Floor) rather than scanning all spots. That counter must be decremented as part of the same atomic claim, not as a separate subsequent step — otherwise you reintroduce a race between "spot marked occupied" and "counter updated," which would let the availability query return a stale nonzero count for a type that is actually full, sending a gate down a dead-end search.

5. Extensibility: Adding Without Modifying

Adding a new vehicle type

Because vehicle-to-spot eligibility is data (a compatibility map) rather than per-subclass logic, adding VehicleType.EV_CAR means: add the enum constant, add its row to the compatibility map, and optionally add a new spot type (SpotType.EV_CHARGING) via the existing factory. No existing SpotAllocationStrategy implementation, no existing ParkingSpot subclass, and no existing gate class needs to change. If eligibility had instead been encoded as a chain of instanceof checks scattered through the allocation code, this same change would require hunting down and editing every such check.

Adding a new pricing model

A promotional "first 30 minutes free, then hourly" scheme is a new class implementing PricingStrategy, wired into ExitGate (or into ParkingLot, whichever owns the reference) via configuration or dependency injection. Because ExitGate depends on the PricingStrategy interface, not a concrete class, this is a pure addition — a textbook demonstration of Open/Closed paying off at the point where a real business request ("run a launch promotion next month") arrives.

Adding a new gate type or payment channel

A UPI or wallet-based PaymentProcessor implementation, or an automated ANPR-camera-based EntryGate implementation, plugs in the same way: implement the interface, wire it in, existing code untouched. The pattern repeating across every extension point is deliberate — it's what "designed for change" concretely looks like, as opposed to a design that merely happens to work for the requirements known at the time it was written.

  + charge(BigDecimal amount, PaymentMethod method): PaymentResult

Flow: a vehicle enters and receives a ticket

  1. Driver approaches an EntryGate; the gate calls lot.parkVehicle(vehicle, this).
  2. ParkingLot delegates to allocationStrategy.findSpot(vehicle.getType(), floors), which consults the vehicle-to-spot compatibility rules and the per-floor freeCountByType to shortlist candidate floors/spots without scanning everything.
  3. For the first candidate spot returned, the lot calls spot.tryOccupy(vehicle). If it returns false (another gate won the race), the lot asks the strategy for the next candidate and retries — this retry loop is what makes the overall allocation correct under concurrent entry, not just the atomicity of a single tryOccupy call.
  4. Once a claim succeeds, the lot decrements that spot type's counter atomically as part of the same critical section, constructs a Ticket with entry timestamp and gate ID, stores it in activeTickets, and returns it to the gate, which hands it to the driver (printed, or as a mobile pass).

Flow: a vehicle exits and pays

  1. Driver presents the ticket at an ExitGate; the gate calls lot.unparkVehicle(ticketId, this).
  2. The lot looks up the Ticket by ID from activeTickets (a missing or already-closed ticket is rejected here — this is also where a lost-ticket policy, typically a flat maximum-stay charge, is applied).
  3. The lot stamps exitTime and calls pricingStrategy.calculateFare(ticket), which computes duration from entryTime to exitTime and applies whatever rate rules that strategy encodes for the ticket's spot type.
  4. ExitGate calls paymentProcessor.charge(fare, method); only on a successful result does the flow proceed to release the spot — this ordering matters, because releasing the spot before payment succeeds would let a car leave (or a new car be assigned that spot) before the transaction is confirmed.
  5. On successful payment, the lot calls spot.release() (atomically clearing occupancy and incrementing the free-count for that type), removes the ticket from activeTickets, and returns a Receipt to the gate.

7. State Management: Who Is Allowed to Mutate a Spot

A ParkingSpot's occupancy has exactly two legal transitions: FREE → OCCUPIED via a successful tryOccupy(vehicle), and OCCUPIED → FREE via release(). The design decision worth being deliberate about is that no other class ever sets these fields directly — not ParkingLot, not Floor, not the gates. Both mutating methods live on ParkingSpot itself and are the only entry points, which means the atomicity guarantee (the lock or CAS discussed in Section 4) is enforced in exactly one place and cannot be bypassed by a caller that forgets to synchronize. This is encapsulation doing real work, not just hiding fields for style: if occupied had a public setter, any future caller — including one written by someone unfamiliar with the concurrency requirement — could perform an unsynchronized read-modify-write and silently reintroduce the exact race Section 4 fixed.

Model spot state as an enum, not a boolean, once real systems get involved

A plain boolean quickly becomes insufficient once you add reservations (a spot held for a pre-booked vehicle, not yet occupied), maintenance holds (a spot taken out of service), and out-of-order arrivals. A SpotState enum — FREE, RESERVED, OCCUPIED, OUT_OF_SERVICE — with an explicit transition table makes illegal transitions (e.g., releasing a spot that was never occupied, or occupying one that's under maintenance) detectable in one place instead of scattered boolean-logic bugs. This same "state as an explicit enum with a transition table" habit is worth carrying into designs like elevator and seat-booking systems, where the number of legal states is larger and the cost of an illegal transition (double-booking a seat) is just as real.

Concepts Worth Being Able to Explain From First Principles

Why does making ParkingLot depend on a SpotAllocationStrategy interface (instead of a concrete NearestFirstStrategy) actually change what "adding a new allocation policy" costs?
If ParkingLot held a field typed as the concrete class NearestFirstStrategy, then introducing a second policy would require either adding a conditional inside ParkingLot to pick between concrete classes, or replacing the field's type — either way, ParkingLot's source has to change and be re-tested. By typing the field as the SpotAllocationStrategy interface and injecting a concrete implementation from outside (constructor injection, a configuration bean, or a factory), ParkingLot's code path is fixed once and for all: it calls strategy.findSpot(...) and never needs to know which concrete strategy that is. New policies are then purely additive — new classes that implement the existing interface — which is what "closed for modification, open for extension" means operationally rather than as a slogan.
Walk through exactly why "check if a spot is free, then assign it" is broken even if the occupied field is volatile.
Volatile guarantees that once a value is written, subsequent reads observe it (and don't see a stale cached copy) — that's a visibility guarantee. It says nothing about the composite operation of reading a value and then, based on that read, performing a write, because two threads can both perform their read before either performs their write. Concretely: thread A reads occupied == false. Before A gets to write occupied = true, thread B also reads occupied == false (a completely valid, non-stale read, since A hasn't written anything yet). Both threads now believe they've found a free spot and both proceed to assign it. The bug is not about visibility of writes — it's that "read" and "write" need to happen as one indivisible unit (a lock, or a CAS operation) so that once one thread's write has happened, the other thread's read is forced to see the new value before it decides anything.
Why is a lock per ParkingSpot preferable to a single lock guarding the entire ParkingLot?
Correctness-wise, both approaches prevent the double-assignment race — a single global lock trivially serializes all mutation, so no two threads can ever race on the same spot. The difference is throughput: a single lot-wide lock means only one entry attempt across the entire building can proceed at a time, even when two cars are headed to spots on completely unrelated floors that share no state. Per-spot locks let unrelated claims proceed fully in parallel and only force threads to actually contend when they are genuinely racing for the same physical spot, which is the only situation where serialization is actually necessary. The general principle is to size the lock to the actual unit of contention — locking more than that unit serializes work that didn't need to be serialized.
Why does releasing a spot only after payment succeeds (not before) matter operationally?
If the spot were released as soon as the exit process began — before payment was confirmed — two problems open up. First, another entry gate could immediately assign that "free" spot to a new vehicle while the original vehicle is still physically parked in it, because the system's model of reality has diverged from physical reality. Second, if the payment step then fails or times out, there is no clean way to reconcile a ticket that has been closed and a spot that has been reassigned but is still physically occupied. Ordering the release strictly after a successful payment result keeps the system's state consistent with the physical world at every intermediate step, and makes failure handling straightforward: a failed payment simply means the ticket stays open and the spot stays occupied, exactly matching reality.
Why should spot occupancy be modeled as an enum with an explicit transition table instead of a boolean, once reservations or maintenance holds exist?
A boolean can only represent two states, but a real system needs to distinguish "free and assignable," "reserved for a specific upcoming vehicle but not yet occupied," "physically occupied," and "deliberately taken out of service," and each of these has different legal next-states (a reserved spot shouldn't be claimed by a different vehicle's tryOccupy; an out-of-service spot shouldn't be assignable at all even though it's technically "free"). Cramming this into a boolean forces the extra states to live as separate flags or as implicit conventions in calling code, which is exactly how illegal-state bugs slip in — nothing stops a caller from calling release() on a spot that was never occupied to begin with. An enum with an explicit, enforced transition table makes every legal transition visible in one place and every illegal one a rejected call rather than silently-corrupted state.
How does a Factory for ParkingSpot construction relate to the Open/Closed principle applied elsewhere in this design?
The Factory pattern and the Strategy pattern are solving the same underlying problem from two different angles: both let calling code depend on an abstraction (a ParkingSpot reference, a SpotAllocationStrategy reference) while the decision of exactly which concrete implementation to use is made in one centralized place. For the factory, that decision point is "given a SpotType, which concrete subclass do I instantiate" — centralizing it means that adding HandicappedSpot or a future EvChargingSpot only requires touching the factory's switch/mapping, not every place in the codebase that currently constructs spots. It's the construction-time analog of what Strategy does for behavior-time decisions.
Why does the vehicle-to-spot compatibility rule belong in a data structure (a map) rather than as logic on Vehicle subclasses?
If each Vehicle subclass implements its own canParkIn(spot) method, then every time a new spot type is introduced, every existing vehicle subclass's method needs to be revisited to decide whether it should now return true for that type — an addition to one axis (spot types) forces edits across an unrelated axis (every vehicle class). Representing compatibility as a single Map<VehicleType, Set<SpotType>> consulted through one shared code path means adding a new spot type or vehicle type is a data change (add a row, or add entries to existing rows), not a code change scattered across N classes, and it also removes any risk of one subclass's method silently diverging from the intended eligibility rule.
