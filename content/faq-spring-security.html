Most Asked Interview Questions: Spring Security, Auth & JWT

AuthN vs AuthZ Filter Chain JWT OAuth2 CORS vs CSRF RBAC
Why this matters

Almost every backend Java interview has at least one round that probes whether you can secure an API, not just build one — because a service that leaks another user's order history or lets any authenticated user hit an admin endpoint is a shipped vulnerability, not a hypothetical. Interviewers use Spring Security and JWT (JSON Web Token) questions as a fast way to check whether you actually understand authentication, authorization, and token handling, or whether you just copy-pasted a security config that happens to work. This page is the answer key for that round: crisp, standalone answers you can say out loud in under a minute each.

Authentication & Authorization

What is the difference between authentication and authorization?
Authentication (AuthN) answers "who are you?" — it's the process of verifying an identity, typically by checking a username/password pair, a valid token, or a certificate. Authorization (AuthZ) answers "what are you allowed to do?" — it's the process of deciding, once identity is known, whether that identity has permission to perform a specific action or access a specific resource. In Spring Security these are deliberately separate stages: an AuthenticationManager establishes who the caller is and populates a SecurityContext with an Authentication object, and then separate authorization checks (URL-based rules or method-level annotations) decide if that authenticated principal can proceed. In ShopSphere terms, logging in as a Seller proves you are that seller (AuthN); being blocked from viewing another seller's payout report is authorization (AuthZ) — you can be authenticated and still be unauthorized.
What is the Spring Security filter chain, at a high level?
Spring Security is implemented as a chain of Filter objects (a FilterChainProxy registered as a single servlet filter) that every HTTP request passes through before it reaches your controller. Each filter in the chain has one job — for example UsernamePasswordAuthenticationFilter handles form-login credential extraction, BasicAuthenticationFilter handles HTTP Basic headers, a custom JWT filter validates bearer tokens, ExceptionTranslationFilter converts security exceptions into 401/403 responses, and FilterSecurityInterceptor (or AuthorizationFilter in newer versions) makes the final allow/deny decision based on configured access rules. Filters run in a fixed, well-defined order, and each one can either pass the request along, short-circuit it with a response (e.g. redirect to login, or a 401), or enrich the request context (e.g. by populating the SecurityContext). Because it's just a chain, you can insert your own filter at a specific position — this is exactly how a custom JWT-validation filter gets added, typically placed before UsernamePasswordAuthenticationFilter.
How does a login request actually flow through Spring Security?
For a classic username/password login: the request hits UsernamePasswordAuthenticationFilter, which extracts the credentials and wraps them in an unauthenticated UsernamePasswordAuthenticationToken. That token is handed to the AuthenticationManager, which delegates to one or more AuthenticationProvider implementations (commonly DaoAuthenticationProvider). The provider loads the user via a UserDetailsService (typically backed by a database lookup), then uses a PasswordEncoder to compare the submitted password against the stored hash. If it matches, a fully-authenticated Authentication object (now carrying granted authorities/roles) is returned and stored in the SecurityContext for the duration of the request (or the session, in session-based setups). If it fails, an AuthenticationException propagates up and ExceptionTranslationFilter converts it into a 401 Unauthorized response. For a JWT-based API this flow is similar but compressed: a custom filter validates the token's signature and expiry directly and populates the SecurityContext from claims in the token, with no database round trip needed on every request.
Why do we hash passwords with BCrypt instead of storing them in plaintext or reversibly encrypting them?
Plaintext storage means a single database breach exposes every user's real password immediately, and because people reuse passwords across sites, that breach cascades to their email, banking, and other accounts. Reversible encryption is only marginally better — if an attacker also compromises the encryption key (often stored in the same application's config), they can decrypt every password back to plaintext just as easily. Hashing is one-way by design: BCrypt (a password-hashing function, not a general encryption cipher) takes the password and produces a fixed-length hash that cannot practically be reversed, so even a full database dump only gives an attacker hashes, not passwords. BCrypt specifically is deliberately slow and includes a per-password random salt baked into its output, which defeats both rainbow-table attacks (precomputed hash lookups) and brute-force attacks that rely on hashing being cheap; it also has a configurable "work factor" so it can be made slower over time as hardware gets faster. On login, Spring Security never decrypts anything — PasswordEncoder.matches(rawPassword, storedHash) re-hashes the submitted password with the same salt and compares the two hashes.
What is role-based access control (RBAC) and how does it differ from attribute-based access control (ABAC)?
RBAC (Role-Based Access Control) grants permissions based on a role assigned to the user — a user is a Customer, Seller, or Admin, and each role has a fixed set of permissions baked into the security configuration (e.g. only ADMIN can hit DELETE /products/{id}). It's simple to reason about and easy to audit, but it's coarse: if you need "a Seller can edit their own products but not another seller's," a role alone can't express that. ABAC (Attribute-Based Access Control) makes decisions using arbitrary attributes of the user, the resource, and the context — for example, "allow update if request.user.id == product.sellerId" or "allow refunds only if order.status == 'DELIVERED' and requester is the order's owner." ABAC is strictly more expressive and handles ownership/contextual rules that RBAC cannot, at the cost of being harder to audit and reason about because the rules are scattered logic rather than a static role table. In practice, most real systems (ShopSphere included) use RBAC for the coarse gate — is this caller even allowed to call this endpoint at all — and layer ABAC-style checks (via @PreAuthorize SpEL expressions or explicit code) on top for ownership and business-state rules.
How does method-level security with @PreAuthorize work?
@PreAuthorize is a Spring Security annotation that evaluates a SpEL (Spring Expression Language) expression before a method is allowed to execute, throwing an AccessDeniedException (translated to a 403 Forbidden) if the expression evaluates to false. It requires method security to be enabled (@EnableMethodSecurity in current Spring Security versions) and is implemented under the hood with an AOP (Aspect-Oriented Programming) proxy that wraps the bean and intercepts the call before it reaches the real method body. Its power over pure URL-based rules is that the expression has access to the method's actual arguments and to the current Authentication/principal, so you can write ownership checks like @PreAuthorize("hasRole('ADMIN') or #sellerId == authentication.principal.id") on an updateProduct(Long sellerId, ...) method. This is the natural place to enforce the ABAC-style, per-resource rules that a blanket URL rule can't express — for example ensuring a Seller in ShopSphere can only cancel their own listings, not a competitor's. There's also @PostAuthorize (checks after the method runs, useful when the decision depends on the return value) and @PreFilter/@PostFilter for filtering collections, but @PreAuthorize is by far the most commonly used in interviews and in practice.
How do you actually configure Spring Security in code for a stateless JWT API?
In current Spring Boot (2.7+/3.x), you expose a SecurityFilterChain bean instead of extending WebSecurityConfigurerAdapter (which is deprecated/removed). A typical stateless config disables CSRF, tells Spring Security not to create or use an HttpSession at all via .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)), declares which endpoints are public versus protected via .authorizeHttpRequests(auth -> auth.requestMatchers("/api/auth/**").permitAll().anyRequest().authenticated()), and registers your custom JWT filter with .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class). The STATELESS policy is the key line for a JWT setup — it tells Spring Security to never read from or write to HttpSession, which forces every request to be authenticated fresh from the token rather than relying on a server-side session. This is the piece of code an interviewer is really checking for when they ask "how would you wire up JWT auth in Spring Security" — knowing the annotation names is less important than knowing these three decisions (no CSRF, no session, custom filter before the standard one).
What does a custom UserDetailsService actually need to implement?
UserDetailsService is a single-method functional interface: loadUserByUsername(String username), which must return a UserDetails object or throw UsernameNotFoundException if no such user exists. UserDetails itself is a contract, not a class you're handed — you implement it (or wrap your JPA User entity in an adapter) to expose the username, the already-hashed password, a collection of GrantedAuthority objects (the roles/permissions like ROLE_ADMIN or ROLE_SELLER), and account-state flags such as isAccountNonExpired(), isAccountNonLocked(), isCredentialsNonExpired(), and isEnabled(). Spring Security calls loadUserByUsername during authentication (via DaoAuthenticationProvider), then uses the returned password hash to compare against the submitted credentials and uses the granted authorities to populate the Authentication object for later authorization checks. In ShopSphere this is typically a thin adapter class that loads a Customer, Seller, or Admin row from the database and maps its role column to a SimpleGrantedAuthority.
What is the difference between a 401 Unauthorized and a 403 Forbidden response?
A 401 Unauthorized means the request has no valid identity attached at all — authentication failed or was never attempted, so the server doesn't know who is calling (a missing, expired, or malformed JWT, or a bad username/password). A 403 Forbidden means the opposite: the server knows exactly who you are (authentication succeeded), but that identity is not allowed to perform the requested action or access the requested resource (a Customer authenticated correctly but tried to hit an ADMIN-only endpoint). In Spring Security this maps directly onto the two-stage model: an AuthenticationException (e.g. bad credentials, invalid token) results in a 401, while an AccessDeniedException thrown by an authorization check (a URL rule, @PreAuthorize, or an ACL) results in a 403, and ExceptionTranslationFilter is the component that catches both exception types and converts them into the correct HTTP status. Getting this distinction right matters in interviews because candidates often say "403" for a plain missing-token case when it should be 401 — the mnemonic is 401 = "I don't know you," 403 = "I know you, and no."
How does SecurityContext propagation break across threads, and how do you fix it for async code?
By default, Spring Security stores the current request's Authentication in a SecurityContextHolder backed by a ThreadLocal, meaning the security context only exists on the thread that's actively handling the HTTP request. The moment you hand work off to another thread — a @Async method, a manually submitted ExecutorService task, or a reactive/parallel stream — that new thread has an empty ThreadLocal and SecurityContextHolder.getContext().getAuthentication() returns null, which is a very common production bug: code that calls @PreAuthorize-protected methods or reads the current user from async workers silently fails or throws unexpected AccessDeniedExceptions. The fix is to explicitly propagate the context: wrap the Runnable/Callable with DelegatingSecurityContextRunnable/DelegatingSecurityContextCallable (or decorate the executor itself with DelegatingSecurityContextExecutorService), or switch the holder's strategy to MODE_INHERITABLETHREADLOCAL so child threads inherit the parent's context automatically. In a ShopSphere order-service handler that kicks off an async task to publish an OrderPlaced event and also needs to check the caller's role inside that task, this propagation gap is exactly the kind of bug that only shows up under load once work actually starts running on a separate thread pool thread.

Tokens & Federated Auth

What is the structure of a JWT, and why is it called "stateless"?
A JWT (JSON Web Token) is a compact, URL-safe string made of three Base64Url-encoded parts separated by dots: header.payload.signature. The header specifies the token type and the signing algorithm (e.g. HS256 or RS256); the payload contains "claims" — key/value data like the subject (user id), roles, issued-at time, and expiry; the signature is computed over the header and payload using a secret (HMAC) or a private key (RSA/EC), and is what lets a server verify the token hasn't been tampered with. It's called stateless because the server doesn't need to keep any session record to validate it — everything needed to authenticate and authorize the request (identity, roles, expiry) travels inside the token itself, so any server instance that has the verification key can validate it independently, with no shared session store and no database lookup on every request. The trade-off is that because the payload is only Base64-encoded, not encrypted, it is fully readable by anyone who intercepts the token — sensitive data should never go in a plain JWT payload — and because there's no server-side session, revoking a single token before it expires isn't naturally supported.
What are the trade-offs between session-based and token-based authentication?
Session-based auth issues an opaque session ID (usually in a cookie) that maps to server-side state — the server stores who the user is, and every request just looks up that ID. Its strengths are instant revocation (delete the session server-side and the user is immediately logged out) and a very simple client (the browser just sends the cookie). Its weakness is that it doesn't scale horizontally without extra work: every server instance needs access to the same session store (a shared database or a cache like Redis), or you need sticky sessions pinning a client to one instance. Token-based auth (typically JWT) puts the state in the token itself, so any stateless server can validate a request independently with no shared session store — this fits microservice architectures like ShopSphere's order-service/inventory-service/payment-service well, since each service can validate a token locally without calling back to an auth service. The trade-off flips: you lose instant revocation (a stolen token is valid until it expires, unless you build a denylist, which reintroduces state), and tokens are commonly used from non-browser clients (mobile apps, other services) where cookies are less natural.
What are the four core roles in OAuth2?
OAuth2 defines four roles in its delegated-authorization model. The resource owner is the end user who owns the data (a ShopSphere Customer). The client is the application requesting access on the user's behalf (e.g. a third-party budgeting app that wants read access to the customer's order history). The authorization server is the system that authenticates the resource owner and issues access tokens after the user consents (e.g. Keycloak, Okta, or Spring Authorization Server). The resource server is the API that actually holds the protected data and accepts the access token to authorize requests (e.g. ShopSphere's order-service). The whole point of OAuth2 is that the client never sees the resource owner's password — it only ever receives a scoped, time-limited access token from the authorization server, which it then presents to the resource server.
What is OIDC and how is it different from plain OAuth2?
OIDC (OpenID Connect) is an identity layer built on top of OAuth2. OAuth2 by itself is an authorization protocol — it's about granting a client scoped access to a resource, and technically says nothing about who the user is beyond an opaque token. OIDC adds a standardized way to answer "who logged in?" by introducing the ID token, a JWT containing verified identity claims (subject id, email, name) that the client can decode to know exactly who authenticated, plus a standard /userinfo endpoint for fetching more profile data. In short: OAuth2 answers "can this client access this resource," OIDC answers "who is this user," and in practice most "Login with Google/GitHub" flows are OIDC (they authenticate the user and hand back an ID token), while an access token used to call a downstream API is the OAuth2 part of the same flow.
What is the difference between a refresh token and an access token?
An access token is what the client sends with every API request to prove it's authorized — it's typically short-lived (minutes to an hour) specifically so that if it leaks, the exposure window is small. A refresh token is longer-lived and is used only to obtain a new access token from the authorization server once the current one expires, without forcing the user to log in again. Refresh tokens are more sensitive (a leaked refresh token can be used to mint new access tokens indefinitely until it's revoked or expires), so they're stored more carefully — often as an httpOnly cookie or in secure server-side storage — and are typically revocable server-side, unlike a plain stateless access token. This split lets you keep access tokens short-lived for security without forcing constant re-authentication, since the refresh token silently handles renewal in the background.
Where should a JWT be stored on the client, and why does it matter?
The two common options are browser storage (localStorage/sessionStorage) and an httpOnly cookie, and they have opposite risk profiles. Storing a JWT in localStorage is convenient (JavaScript can read it and attach it as an Authorization: Bearer header) but it's fully readable by any JavaScript running on the page, which means an XSS (Cross-Site Scripting) vulnerability anywhere on the site can exfiltrate every logged-in user's token. Storing it in an httpOnly cookie means client-side JavaScript can never read the cookie's value, which neutralizes token theft via XSS — but cookies are automatically attached to every request to that domain by the browser, which reopens the door to CSRF (Cross-Site Request Forgery) unless mitigated with the cookie's SameSite attribute and/or a CSRF token. The generally recommended pattern is an httpOnly, Secure, SameSite=Strict (or Lax) cookie for the token, combined with short access-token lifetimes and a separate refresh flow, rather than trusting client-side JavaScript storage at all.
How does a server actually validate a JWT, and what is the "alg: none" attack?
Validating a JWT means checking three things, all handled by a library such as JJWT or Nimbus JOSE + JWT rather than hand-rolled parsing: the signature is recomputed from the header and payload using the server's known key and compared against the token's signature; the exp (expiry) claim is checked against the current time; and any other required claims (issuer, audience) match what's expected. For an HS256-signed token, "the server's known key" is a single shared secret used for both signing and verifying; for RS256, the authorization server signs with a private key and any resource server can verify with the corresponding public key, without ever holding the ability to forge new tokens. The classic "alg: none" attack targets naive implementations: because the algorithm is itself declared inside the token's header, an attacker can rewrite the header to say "alg": "none", strip the signature, and some poorly-configured or older JWT libraries would accept it as validly "unsigned." The fix — built into modern libraries and Spring Security's JWT support by default — is to never trust the algorithm from the token itself; the server must be configured to expect one specific algorithm and reject anything else outright, regardless of what the token's header claims.
What are the main OAuth2 grant types, and when do you use each?
The authorization code grant is the standard flow for user-facing apps with a backend: the client redirects the user to the authorization server, the user logs in and consents, and the server redirects back with a short-lived one-time code that the client's backend exchanges (server-to-server, with a client secret) for an access token — the token itself never touches the browser's URL bar or history. PKCE (Proof Key for Code Exchange) is a mandatory extension of the authorization code grant for clients that can't safely hold a secret — mobile apps and single-page apps — where the client generates a random verifier/challenge pair so that even if the authorization code is intercepted, an attacker can't redeem it without the original verifier. The client credentials grant is for machine-to-machine calls with no end user at all — one ShopSphere microservice (e.g. inventory-service) authenticating directly to another using its own client id/secret to get a token that represents the service itself. The legacy resource owner password credentials grant, where the client collects the user's raw username/password and exchanges them directly for a token, is now considered insecure and deprecated in the OAuth2 spec because it requires the client to handle raw credentials — it defeats the entire point of OAuth2's "the client never sees the password" model, so modern guidance is to avoid it entirely in favor of authorization code + PKCE.
At scale, how do multiple microservices validate JWTs without hammering the authorization server?
A naive design has every resource server call the authorization server on every request to check whether a token is valid — this defeats the entire point of a stateless token and turns the auth server into a single point of failure and a bottleneck under load. The standard production pattern instead uses asymmetric signing (RS256/ES256): the authorization server signs tokens with a private key it never shares, and publishes the corresponding public key(s) at a well-known JWKS (JSON Web Key Set) endpoint. Each resource server — order-service, inventory-service, payment-service, and so on in ShopSphere's architecture — fetches and locally caches that public key (Spring Security's JwtDecoder does this automatically, refreshing on a schedule and on key-id cache misses) and verifies every token's signature entirely in-process, with zero network call to the auth server on the hot request path. This scales horizontally with no shared state and no additional latency per request; the only operational wrinkle is key rotation, which is why JWKS responses include a key id (kid) in the token header so multiple valid keys can be in flight during a rotation window without breaking already-issued tokens.
If JWTs are stateless, how do you actually log a user out or revoke a compromised token?
This is the classic gotcha follow-up to "JWTs are stateless": pure statelessness and instant revocation are fundamentally in tension, because the whole point of a stateless token is that the server doesn't check anything beyond the signature and expiry. The simplest mitigation is to keep access tokens very short-lived (minutes), so a compromised token or a "logged out" session naturally becomes useless soon regardless of server action — the client just deletes its copy and stops sending it, and lets the refresh token (which is revocable server-side) not get renewed. For cases that need immediate, hard revocation — a compromised account, an admin forcibly logging someone out — the standard fix is a denylist: a fast, shared store (typically Redis) holding either specific revoked token ids (using the JWT's jti claim) or a "tokens issued before timestamp X for this user are invalid" marker, which the validating filter checks on every request. This reintroduces a small piece of shared state and a lookup per request, which is a deliberate trade-off against pure statelessness — it's why interviewers ask this question, to see if a candidate understands that "stateless" is a spectrum choice, not an absolute, and that ShopSphere would only pay this cost for tokens that truly need instant kill-switch capability (e.g. payment-service credentials) rather than every session.

Web Security Basics

What is the difference between CORS and CSRF, and what does each protect against?
CORS (Cross-Origin Resource Sharing) and CSRF (Cross-Site Request Forgery) sound similar but solve opposite problems. CORS is a browser-enforced relaxation mechanism: by default browsers block a page on shopsphere.com from reading responses from a different origin like api.shopsphere.com (the Same-Origin Policy), and CORS is the set of response headers (Access-Control-Allow-Origin, etc.) a server uses to explicitly allow specific origins to read its responses via JavaScript. It's about which sites are allowed to consume your API's responses. CSRF is an attack, not a protection mechanism by itself: it exploits the fact that browsers automatically attach cookies (like a session cookie) to any request to a domain, even one triggered by a malicious third-party page — so a hidden form or auto-submitting request on evil.com can make the victim's browser send a legitimate, cookie-authenticated request to shopsphere.com to, say, change their shipping address, without the user's knowledge. CSRF protection (typically a per-session anti-CSRF token that must be included in state-changing requests and that an attacker's page can't know) defends against that by requiring proof the request was intentionally initiated from your own site, not just that a valid cookie was attached.
What is a CORS preflight request, and when does the browser send one?
A preflight is an automatic OPTIONS HTTP request the browser sends before the "real" request, asking the server for permission — it happens for any cross-origin request that isn't a plain, simple GET/POST with basic headers, which in practice means almost every real API call: a JSON POST/PUT/DELETE with a Content-Type: application/json body, or any request carrying a custom header like Authorization: Bearer <token>, triggers one. The browser sends the OPTIONS request with Access-Control-Request-Method and Access-Control-Request-Headers describing what the real request intends to do, and the server must respond with matching Access-Control-Allow-Origin, Access-Control-Allow-Methods, and Access-Control-Allow-Headers values before the browser will actually send the real request at all. This is entirely a browser-side safety check — the request never even leaves for the actual endpoint if the preflight response doesn't explicitly allow it — and it's why a Spring Boot API that returns correct data via curl or Postman can still fail from a browser frontend with a "blocked by CORS policy" console error: the OPTIONS preflight itself needs a permissive, explicit CORS configuration (a CorsConfigurationSource bean in Spring Security), separate from and in addition to the actual endpoint's logic.
Why is CSRF protection typically disabled for stateless JWT APIs?
CSRF attacks work specifically because browsers automatically attach cookies to cross-site requests without the attacker needing to know the cookie's value — the victim's browser does the work for them. A stateless JWT API that expects the token in an Authorization: Bearer <token> header rather than a cookie isn't vulnerable to this in the same way: a malicious page on another origin cannot make the victim's browser automatically attach an arbitrary header, and it has no way to read the token to add the header itself (assuming the token isn't sitting in localStorage where XSS could grab it, and assuming CORS is configured correctly so the attacker's origin can't even complete the request). Because there's no implicit credential attachment happening, the CSRF token mechanism — which exists purely to prove intent on top of automatically-sent cookies — has nothing to defend against, so it's standard practice to disable Spring Security's built-in CSRF protection (.csrf(csrf -> csrf.disable())) for pure token-based APIs. The important caveat: if you ever store the JWT in a cookie instead of sending it as a header, you've reintroduced automatic attachment and CSRF protection needs to come back.
What is XSS and how does output encoding prevent it?
XSS (Cross-Site Scripting) is an attack where an attacker gets malicious JavaScript to execute in another user's browser in the context of a trusted site — typically by injecting a <script> tag or event handler into content that the application later renders as HTML without sanitizing it. A classic example is a product review field: if a Customer submits a review containing a script tag and the frontend renders it directly into the DOM as raw HTML, that script now runs in every other visitor's browser session, with access to their cookies, local storage, and ability to make requests as them. Output encoding is the primary defense: instead of inserting user-supplied data into HTML as-is, you encode special characters (<, >, &, quotes) into their HTML-entity equivalents so the browser renders them as literal text rather than interpreting them as markup — most modern frontend frameworks (React, Angular, Thymeleaf) do this automatically for anything rendered through their standard templating/binding, which is why manually injecting raw HTML (e.g. dangerouslySetInnerHTML or an unescaped th:utext) is the dangerous exception you have to justify. On the server side, input validation and a strict Content-Security-Policy header add defense-in-depth on top of output encoding, but encoding at the point of output is the layer that actually stops the injected script from executing.
What is SQL injection, and how does Spring Data/JPA protect against it?
SQL injection happens when untrusted user input is concatenated directly into a SQL query string, letting an attacker inject their own SQL logic — the textbook example is a login query built as "SELECT * FROM users WHERE username = '" + input + "'", where an attacker submitting ' OR '1'='1 as the username turns the query into one that matches every row, bypassing authentication entirely. More destructive variants can chain a ; DROP TABLE or exfiltrate data with a UNION SELECT. The fix is parameterized queries: a PreparedStatement (or, in Spring, a @Query with named/positional parameters, or a Spring Data JPA derived query method like findByUsername(String username)) sends the SQL structure and the user-supplied values to the database separately, so the database driver treats the input strictly as data and never as executable SQL syntax, no matter what characters it contains. Spring Data JPA and Hibernate use parameterized queries by default for every generated and @Query-annotated method, which is why SQL injection in a typical Spring Data repository requires a developer to actively opt out of safety — usually by building a native query with raw string concatenation instead of using :paramName bindings, which is exactly the pattern to flag in a code review on a ShopSphere search-by-seller-name endpoint or similar free-text filter.
Beyond CORS/CSRF/XSS, what production hardening do you add against brute-force login attempts and common HTTP-level attacks?
A login endpoint with no rate limiting is an open invitation to credential-stuffing and brute-force attacks — an attacker can script thousands of password guesses per minute against /api/auth/login unless something throttles them. Production systems typically add rate limiting per IP and/or per account (via an API gateway, a library like Bucket4j, or infrastructure like a WAF/reverse proxy), account lockout or exponential backoff after repeated failures, and CAPTCHA challenges once a threshold is crossed. Alongside that, a set of security response headers closes off other common attack classes: Strict-Transport-Security (HSTS) forces the browser to only ever use HTTPS for the domain going forward, preventing protocol-downgrade attacks; Content-Security-Policy (CSP) restricts which sources scripts/styles/frames can be loaded from, which meaningfully limits the blast radius of an XSS bug even if one slips through output encoding; X-Content-Type-Options: nosniff stops the browser from guessing a different MIME type than the server declared; and X-Frame-Options/frame-ancestors prevents clickjacking by blocking the page from being embedded in a hidden iframe on an attacker's site. Spring Security enables several of these headers by default and exposes a headers() DSL to customize them, but rate limiting on the login path specifically is something you have to add yourself — it's a very common "what would you add before this ships" follow-up after the CORS/CSRF/XSS basics in a senior-level interview.
