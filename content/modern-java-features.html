Modern Java: Records, Sealed Classes, Pattern Matching

Records Compact Constructors Sealed Types Exhaustiveness instanceof Patterns Switch Patterns Optional Design
Why this matters

These three features are not syntactic sugar bolted onto Java for convenience — they close a real gap between Java's type system and the algebraic data types that languages like Kotlin, Scala, and Rust have had for years. Once you understand why a record forces immutability at the language level, why a sealed hierarchy lets the compiler prove a switch is exhaustive, and why pattern matching exists to eliminate a specific class of null-check and cast bugs, you start designing domain models that make illegal states unrepresentable instead of merely discouraged. That shift — from "the type system allows this but you shouldn't do it" to "the type system will not compile this" — is the difference between bugs you catch at review time and bugs the compiler catches for you.

1. Records: what the compiler actually generates

A record declaration like record Point(int x, int y) {} is a compressed way of writing a final class with a very specific, mechanically-generated shape. Understanding exactly what the compiler emits — not an approximation of it — is what lets you predict how a record behaves in serialization, equality checks, and reflection. The same mechanics apply to a domain-shaped record like record OrderItem(String productId, int quantity, BigDecimal unitPriceAtPurchase) {}, which is how ShopSphere models one line of an Order.

For record Point(int x, int y) {}, javac generates:

  • A private final field for each component: private final int x; and private final int y;.
  • A canonical constructor whose parameter list matches the component list exactly, in order: Point(int x, int y). It assigns each parameter to its corresponding field.
  • Accessor methods named after the components, not JavaBean-style getters: x() and y(), not getX() and getY(). This is deliberate — records are not beans, and the naming signals "this is a plain accessor over an immutable value," not "this may trigger side effects or lazy computation" the way a getter conventionally might. For OrderItem above, that means quantity() and unitPriceAtPurchase(), not getQuantity().
  • equals(Object) and hashCode() that consider all components, generated to be consistent with each other (two records with equal components have equal hash codes).
  • toString() that prints the record name and all components, e.g. Point[x=3, y=4] (or OrderItem[productId=prod-8841, quantity=2, unitPriceAtPurchase=19.99]).
  • The class itself is implicitly final and implicitly extends java.lang.Record (an abstract class), which means a record can never be extended and can never extend another class — it can only implement interfaces.
Why records exist instead of just "a class with less boilerplate"

The point of a record is not to save keystrokes on getters and constructors. It's to make a declaration like record Money(BigDecimal amount, Currency currency) — or, in ShopSphere terms, record OrderItem(String productId, int quantity, BigDecimal unitPriceAtPurchase) — mean something specific and load-bearing: this type's entire identity is its components, it is immutable, and it carries no hidden state. That guarantee is what the JVM, IDEs, and libraries like Jackson can rely on. A hand-written class with the same fields and methods only has that guarantee by convention — nothing stops someone from later adding a mutable cache field or overriding equals to ignore a component. A record's transparency is enforced by the language: you cannot add instance fields beyond the components, and you cannot override the field-based semantics without deliberately overriding the generated method. This matters concretely for OrderItem: once an order is PAID, its line items should never silently drift — unitPriceAtPurchase must stay frozen at what the customer was actually charged even if the Product's current price changes later, and an immutable record makes that a structural guarantee rather than a "please don't mutate this" comment.

1.1 Why records are for transparent carriers, not general-purpose classes

"Transparent" here means the public API and the internal state are the same thing — there is no encapsulation gap between what the record exposes and what it stores. This is exactly backwards from the encapsulation principle you'd apply to a normal domain class (hide fields, expose behavior), and that's intentional: records are for the specific case where the value is the data, like a coordinate, a money amount, a database row projection, a ShopSphere Product catalog snapshot, or a network message payload (a Kafka OrderPlaced event body, say). If you find yourself wanting private helper fields, mutable state, or an inheritance hierarchy, that's a signal the type is not a value carrier and should be a regular class instead — a Seller entity with mutable inventory-management behavior belongs in a regular class, while the immutable Product row it manages is a natural record.

1.2 Compact canonical constructors

Writing a full canonical constructor to add validation means repeating the entire parameter list and every assignment, which is exactly the kind of boilerplate records are trying to eliminate. The compact constructor syntax solves this: you write validation/normalization logic without restating the parameter list or the field assignments — the compiler inserts the assignments automatically after your compact constructor body runs.

public record Product(String id, String sellerId, String name,
                       BigDecimal price, String category, int stockQuantity) {

    // Compact canonical constructor — no parameter list, no explicit assignments.
    public Product {
        if (price.signum() < 0) {
            throw new IllegalArgumentException("price cannot be negative: " + price);
        }
        if (stockQuantity < 0) {
            throw new IllegalArgumentException("stockQuantity cannot be negative: " + stockQuantity);
        }
        // You can reassign parameters here to normalize before the implicit
        // field assignment happens. Below, price is rounded to cents before storage.
        price = price.setScale(2, RoundingMode.HALF_UP);
    }
}

(price.setScale(2, RoundingMode.HALF_UP) is BigDecimal's way of rounding to exactly 2 decimal places — i.e. whole cents — rounding a trailing 5 up rather than using banker's rounding, which is the conventional rule for currency amounts.) Note the mechanics precisely: inside a compact constructor you can reassign the constructor's parameters (here, price is still a local parameter variable at this point), but you cannot assign directly to this.price — the compiler forbids explicit field assignment in a compact constructor and inserts the field assignments itself, using whatever the parameters hold at the end of your block. This is what makes compact constructors safe for validation and normalization without letting you accidentally skip initializing a component — no seller can construct a Product with a negative price or negative stock, because the exception fires before any field is ever set.

A record can still have a non-canonical constructor

You can overload additional constructors, but every non-canonical constructor must delegate to the canonical constructor (directly or transitively via another constructor) as its first statement — the same rule that applies to this(...) chaining in ordinary classes. This preserves the guarantee that all validation logic in the canonical/compact constructor always runs, no matter which constructor a caller used — a convenience overload like Product(String id, String sellerId, String name, BigDecimal price, String category) that defaults stockQuantity to 0 still can't bypass the price/stock validation above.

1.3 Records and the class initialization lifecycle

A record compiles to an ordinary final class file at the bytecode level, so it goes through exactly the same static and instance initialization sequence covered on the JVM internals page: static initializers and static field initializers run once, in textual order, the first time the class is actively used, guarded by the classloader's per-class initialization lock; then, for each instance, instance initializer blocks and instance field initializers run in textual order immediately before the constructor body, every time a canonical (or delegating) constructor is invoked. Nothing about the record shorthand changes that model — a compact constructor body is simply spliced in as the first part of the "constructor body" step, and the implicit field assignments happen after it, then any explicit trailing statements you wrote after the compact block's validation. If a record implements an interface with a static method, or has its own static fields (records can declare static fields and static methods — the restriction is only on instance fields beyond the components), classloading proceeds identically to any other class.

2. Sealed Classes and Interfaces

Before sealed types, Java's inheritance model was open by default: any class in the classpath could extend any non-final public class or implement any public interface. That openness is usually good for extensibility, but it's actively harmful when you're trying to model a closed set of variants — a type that represents "exactly these possibilities and no others." ShopSphere's own domain is full of exactly this shape: an Order is always in exactly one of a small, fixed set of lifecycle states — CREATED, PAID, SHIPPED, DELIVERED, or CANCELLED — and it is never in some sixth state nobody anticipated, because the business process itself doesn't allow one.

A sealed class or interface declares, via a permits clause, the exhaustive list of classes allowed to directly extend or implement it. Modeled as a sealed hierarchy instead of a plain enum so that each state can carry the data that's only meaningful in that state (a CANCELLED order has a reason; a SHIPPED order has a carrier and tracking number; a plain enum constant cannot carry per-instance fields like this):

public sealed interface OrderStatus
        permits Created, Paid, Shipped, Delivered, Cancelled {}

public record Created(Instant at) implements OrderStatus {}
public record Paid(Instant at, String paymentId) implements OrderStatus {}
public record Shipped(Instant at, String carrier, String trackingNumber) implements OrderStatus {}
public record Delivered(Instant at) implements OrderStatus {}
public record Cancelled(Instant at, String reason) implements OrderStatus {}

Each permitted type here is a record, which is itself implicitly final (section 1) — that's what satisfies the sealing rule below without needing to write final explicitly. The hierarchy, as a tree, looks like this:

sealed interface OrderStatus  (permits: exactly these 5, nothing else)
  ├── record Created(Instant at)
  ├── record Paid(Instant at, String paymentId)
  ├── record Shipped(Instant at, String carrier, String trackingNumber)
  ├── record Delivered(Instant at)
  └── record Cancelled(Instant at, String reason)

Every class named in permits must itself declare how it participates in the sealing: it must be final (no further extension), sealed (it defines its own restricted set of subclasses), or non-sealed (it deliberately reopens extension to arbitrary subclasses from that point down). This is not optional boilerplate — the compiler rejects a permitted subclass that doesn't declare one of these three modifiers, because otherwise the "closed set" guarantee at the OrderStatus level would be silently undermined by an unrestricted subclass three levels down.

Why this needs compiler enforcement, not just discipline

You could always simulate a closed hierarchy by convention — package-private constructors, documentation comments saying "do not extend this." But none of that is checked. Before sealed types, ShopSphere's OrderStatus would likely have been an ordinary open interface, and nothing would have stopped a careless PR from adding a sixth implementation (say, a PartiallyShipped record for split fulfillment) without anyone updating every switch that pattern-matches over order status elsewhere in order-service. A sealed hierarchy is checked at compile time and recorded in the class file (via a PermittedSubclasses attribute), which means tooling and the compiler itself can reason about completeness. That's the entire point: it turns "we intend this to be a closed set" into "the compiler can prove this is a closed set," which is the property that unlocks exhaustive switches in the next section.

2.1 permits and same-module / same-package constraints

Permitted subclasses must be knowable at compile time, so they're constrained to be co-located with the sealed type: either in the same module (for modular code) or, for classpath-based code, the same package. If all permitted subclasses are declared in the same source file or as nested classes of the sealed type, the permits clause can even be omitted — the compiler infers it from what it sees in that compilation unit. In practice, order-service would keep OrderStatus and its five permitted records together in one order.status package (or one file), which is also exactly what makes it safe to omit an explicit permits clause on OrderStatus if you prefer — the compiler already sees every implementor in that same compilation unit.

3. Pattern Matching: instanceof, switch, and deconstruction

3.1 instanceof pattern matching

Before pattern matching, the idiomatic instanceof check required a redundant explicit cast immediately afterward, because the compiler didn't retain any relationship between the check and the subsequent use:

// Old style — the cast repeats information the instanceof check already proved.
// obj here is some Object pulled off a Kafka OrderPlaced-style event payload.
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.length());
}

Pattern matching for instanceof lets you bind a variable directly in the condition, and the compiler makes that variable available — correctly typed, with no cast — in any branch where flow analysis can prove the check succeeded:

if (obj instanceof String s) {
    System.out.println(s.length()); // s is a String here, no cast
}

// Flow-sensitive negation also works: the compiler tracks that if this
// condition is true, obj was NOT a Cancelled, so returning/throwing means
// cancelled is definitely a Cancelled after this point too.
if (!(obj instanceof Cancelled cancelled)) {
    return;
}
System.out.println("cancelled because: " + cancelled.reason()); // in scope, typed Cancelled here

This eliminates an entire category of bugs where the cast type silently drifts from the instanceof type during a refactor (someone changes the check but forgets to update the cast, producing a ClassCastException at runtime instead of a compile error).

3.2 Switch pattern matching over types

Traditional switch only worked on a fixed set of types (primitives, strings, enums) and matched by exact value equality. Pattern matching for switch generalizes this to match by type, with optional deconstruction, directly in the case label:

static String describe(Object obj) {
    return switch (obj) {
        case Integer i -> "int " + i;
        case String s  -> "string of length " + s.length();
        case null      -> "it's null";
        default        -> "something else";
    };
}

Note that case null is legal directly in a pattern-matching switch — something that was illegal for traditional switches, which threw NullPointerException on a null selector. This matters because it removes the need for a separate null check before the switch, folding null-handling into the same exhaustiveness-checked construct. Concretely, this matters for ShopSphere's OrderItem.unitPriceAtPurchase lookups, where a missing price should mean "not yet priced," not a crash:

static String priceLabel(BigDecimal unitPriceAtPurchase) {
    return switch (unitPriceAtPurchase) {
        case null                          -> "not yet priced";
        case BigDecimal p when p.signum() == 0 -> "free";
        case BigDecimal p                  -> "$" + p;
    };
}

3.3 Record deconstruction patterns

Because a record's canonical form is fully known (its components, in order, with fixed types), a case label can destructure a record's components directly, binding each one to a new variable without calling any accessor manually. Here, deconstructing ShopSphere's sealed OrderStatus hierarchy from section 2 to build a one-line summary for an order-history page:

static String summarize(OrderStatus status) {
    return switch (status) {
        case Created(var at)                         -> "placed at " + at;
        case Paid(var at, var paymentId)              -> "paid (payment " + paymentId + ") at " + at;
        case Shipped(var at, var carrier, var track)  -> "shipped via " + carrier + ", tracking " + track;
        case Delivered(var at)                        -> "delivered at " + at;
        case Cancelled(var at, var reason) when reason.isBlank() -> "cancelled at " + at + " (no reason given)";
        case Cancelled(var at, var reason)            -> "cancelled at " + at + ": " + reason;
    };
}

Deconstruction patterns nest arbitrarily — a record whose component is itself another record can be destructured in one pattern, e.g. destructuring a record OrderItem(Product product, int quantity) as case OrderItem(Product(var id, var name, var price, var category, var stock), var qty), which recursively unpacks the nested Product's fields and the item's quantity in a single case label.

3.4 Guarded patterns (when clauses)

A type pattern alone can only discriminate on type, but you frequently need to refine further — "it's a Cancelled order, but specifically one with no reason recorded." The when clause adds an arbitrary boolean guard evaluated only after the type/deconstruction pattern has already matched, as shown in the summarize example above. This is what lets pattern-matching switches subsume a chain of if (x instanceof T t && t.someCondition()) checks into one readable, exhaustively-checked construct.

Pattern order matters, just like exception catch clauses

Case labels are evaluated top to bottom, and the first match wins. A guarded pattern case Cancelled(var at, var reason) when reason.isBlank() placed before an unguarded case Cancelled(var at, var reason) is fine, but if you reverse the order, the unguarded case shadows the guarded one and the compiler will flag it as unreachable — the same "more specific must come first" discipline you already apply when ordering catch blocks from subclass to superclass.

4. Sealed types + pattern matching: compiler-enforced exhaustiveness

This is where the three features compose into something genuinely new for Java. When the selector of a switch expression has a sealed type, the compiler knows the complete set of permitted subtypes from the permits clause. If every permitted subtype has a corresponding case, the switch is provably exhaustive, and no default branch is required — in fact, for a switch expression (one that must produce a value), omitting a case for a permitted subtype without a default is a compile error, not a runtime gap.

Consider modeling the result of calling out to payment-service to capture a payment for a ShopSphere Order — a closed set of outcomes, deliberately built to exercise generics, nested records, and multi-level sealing at once:

public sealed interface PaymentResult permits PaymentAccepted, PaymentRejected {}

public record PaymentAccepted(String paymentId, BigDecimal amountCharged) implements PaymentResult {}

public sealed interface PaymentRejected extends PaymentResult
        permits InsufficientFunds, GatewayTimeout {}

public record InsufficientFunds(String cardLast4) implements PaymentRejected {}
public record GatewayTimeout(long elapsedMillis) implements PaymentRejected {}

static String render(PaymentResult result) {
    return switch (result) {
        case PaymentAccepted(var paymentId, var amount) ->
            "charged $" + amount + " (payment " + paymentId + ")";
        case InsufficientFunds(var last4) when last4.isBlank() ->
            "declined: insufficient funds (card unknown)";
        case InsufficientFunds(var last4) ->
            "declined: insufficient funds on card ending " + last4;
        case GatewayTimeout(var ms) when ms > 30_000 ->
            "payment gateway timed out badly after " + ms + "ms — do not retry automatically";
        case GatewayTimeout(var ms) ->
            "payment gateway timed out after " + ms + "ms — safe to retry with the same idempotencyKey";
    };
}

This is a two-level sealed hierarchy — a sealed interface (PaymentRejected) that is itself one of the permitted branches of an outer sealed interface (PaymentResult), rather than a flat list of leaves. As a tree:

sealed interface PaymentResult  (permits: exactly these 2, nothing else)
  ├── record PaymentAccepted(String paymentId, BigDecimal amountCharged)
  └── sealed interface PaymentRejected  (permits: exactly these 2, nothing else)
        ├── record InsufficientFunds(String cardLast4)
        └── record GatewayTimeout(long elapsedMillis)

Walk through why this compiles with no default: PaymentResult permits exactly PaymentAccepted and PaymentRejected; PaymentRejected itself is sealed and permits exactly InsufficientFunds and GatewayTimeout. The compiler flattens this two-level sealed hierarchy and confirms that PaymentAccepted, InsufficientFunds, and GatewayTimeout — the only three concrete leaves — each have at least one unconditional (guard-free) case covering them. The guarded cases (when last4.isBlank(), when ms > 30_000) don't count toward exhaustiveness on their own, precisely because a guard can be false — which is why each guarded case here is paired with a fallback unguarded case for the same pattern.

Now suppose someone extends the hierarchy: payment-service starts distinguishing fraud holds from ordinary declines, so they add permits InsufficientFunds, GatewayTimeout, FraudHold to PaymentRejected, and a new record FraudHold(String reviewCaseId) implements PaymentRejected {}, but never revisit render. Because render's switch is exhaustive over a sealed type with no default, the compiler immediately reports an error at the switch — something like the switch expression does not cover all possible input values — pointing at the exact call site that needs updating, rather than letting the new variant silently fall through to a wrong branch or an IllegalStateException discovered later in production, e.g. checkout code that treats every rejection identically and tells a customer "insufficient funds" when their payment was actually flagged for a fraud review. This is the concrete payoff: adding a variant to a closed hierarchy turns every place that pattern-matches over it into a to-do list the compiler generates for you.

This guarantee disappears the moment you add a catch-all

If render had a trailing default -> "payment declined", adding FraudHold would compile cleanly and silently route through default — exactly the bug sealed exhaustiveness exists to prevent. Add a default to a sealed-type switch only when you deliberately want new variants to degrade gracefully rather than force an update; otherwise, leaving it off is the feature, not an oversight.

MechanismWhat it restrictsCompiler guarantee unlocked

The idempotencyKey referenced in the GatewayTimeout branch isn't incidental

Notice that the guarded GatewayTimeout branch above explicitly calls out "safe to retry with the same idempotencyKey." Modeling PaymentResult as a sealed type is what makes that distinction expressible and enforceable in the first place: a caller pattern-matching over PaymentResult can tell a genuine gateway timeout (safe to retry, because payment-service's own idempotency key deduplicates the retried attempt so the customer is never double-charged) apart from an insufficient-funds decline (never safe to blindly retry — the customer needs to act). Collapsing every failure into a single PaymentException or a boolean success flag would destroy exactly the information a correct retry policy needs. See the payment systems page for how idempotency keys make retries safe at the payment-provider level.

5. Optional revisited: anti-patterns and the functional style it was designed for

Optional<T> was added specifically to give method return types an explicit, type-checked way to say "this might not have a value," replacing the ambiguous convention of returning null and hoping every caller remembers to check. But Optional is frequently used in ways its designers explicitly warned against, because it superficially looks like "a nicer null" rather than what it actually is: a container meant to be composed functionally, similar in spirit to the Stream pipelines covered on the streams and functional programming page.

5.1 Optional as a field

Optional does not implement Serializable. A field of type Optional<String> on a class that gets serialized (via Java serialization, or even naively via some reflection-based frameworks) either fails outright or requires special-case handling that defeats the purpose of using Optional for clarity. Beyond serialization, an Optional field also doubles the ways "no value" can be represented: the field reference itself can be null (nobody stops you from writing this.appliedCoupon = null; instead of Optional.empty()), so you've added a wrapper without actually eliminating the null case you were trying to avoid.

Idiomatic replacement: use a plain, possibly-null field (with @Nullable annotations or clear documentation), and only wrap it in Optional at the accessor boundary if you want callers to be forced to handle absence — here, a ShopSphere Order that may or may not have had a Coupon applied at checkout:

public class Order {
    private final Coupon appliedCoupon; // may be null internally — most orders have none

    public Optional<Coupon> appliedCoupon() {
        return Optional.ofNullable(appliedCoupon);
    }
}

5.2 Optional as a method parameter

Making a parameter Optional<T> pushes the wrapping cost onto every caller, including callers who have a perfectly ordinary, always-present value — they now have to write Optional.of(value) just to call your method. It also allows a second, unwanted way to express "no argument": passing null itself instead of Optional.empty(), which Optional-typed parameters do nothing to prevent.

Idiomatic replacement: use method overloading for the "this argument may be omitted" case — here, catalog-search-service's search endpoint, where a category filter is optional but a query string is always required:

// Instead of: void search(String query, Optional<String> category)
void search(String query) {
    search(query, null);
}

void search(String query, String category) {
    String effectiveCategory = (category != null) ? category : "ALL";
    // ...
}

5.3 isPresent()/get() instead of the functional style

Writing if (opt.isPresent()) { return opt.get().percentOff(); } else { return 0; } reproduces exactly the imperative null-check structure Optional was meant to replace — it's a null check with extra ceremony. Optional's actual API is a small set of combinators designed to be chained. All four rows below use Optional<Coupon> from the Order.appliedCoupon() accessor in section 5.1:

if (opt.isPresent()) return opt.get().percentOff(); else return 0;opt.map(Coupon::percentOff).orElse(0)One expression; no branch to accidentally get wrong; reads as a pipeline

The unifying idea is the same discipline that makes Stream pipelines composable: treat Optional as a zero-or-one-element container you transform with map/filter/flatMap and only terminate with orElse/orElseGet/orElseThrow, never by manually branching on presence and reaching in with get().

Optional and sealed Result types solve overlapping but distinct problems

Optional<T> only tells you value-or-nothing; it carries no information about why there's nothing. The sealed PaymentResult pattern from section 4 is what you reach for when the failure case itself carries structured data (which card, which timeout, which fraud case) that callers need to branch on. Don't force a rich failure into Optional.empty() and lose that information — an Optional<PaymentResult> that's empty on both "the gateway rejected the charge" and "the gateway timed out" throws away exactly the distinction a retry policy needs; model it as a sealed type and pattern-match instead.

Concepts Worth Being Able to Explain From First Principles

Why can't you add an extra instance field to a record beyond its declared components?
Because the entire value proposition of a record is transparency: its public state (accessors) and its actual state (fields) are guaranteed identical, which is what allows the compiler to safely auto-generate equals, hashCode, and toString purely from the component list. If arbitrary extra instance fields were allowed, those generated methods would need to either silently ignore the extra field (breaking the equals/hashCode contract's usual expectation that "equal objects" means "equal in all state you'd reasonably compare") or the compiler would need to guess whether to include it — there's no principled default. Restricting records to exactly their components removes that ambiguity entirely: everything about a record's identity is visible in its header.
What actually happens in a compact canonical constructor if you never reassign a parameter?
The compiler still performs the implicit field assignment using whatever value the parameter holds at the end of the compact constructor's body — which, if you never touched it, is just the value the caller passed in. The compact syntax doesn't remove the assignments; it just lets the compiler write them for you after your validation/normalization code runs, using the current (possibly reassigned) parameter values as the source. This is why you can throw partway through the compact constructor to reject bad input before any field is ever set, since the implicit assignments only happen after your block completes normally.
Why does sealing need a permits clause instead of just marking the interface "sealed" and letting the compiler scan the classpath?
Java classes are typically compiled and loaded incrementally, and the classpath at compile time for one module isn't guaranteed to contain every class that will exist at runtime (separately compiled JARs can be added later). If sealing worked by scanning "whatever happens to exist," the set of permitted subtypes could differ between compilation and runtime, and exhaustiveness checks would be unsound — the compiler could prove a switch exhaustive against one set of subtypes while a different set exists when the code actually runs. Requiring an explicit, compile-time-checked permits list (co-located in the same module or package) pins the set of subtypes to something the compiler can verify is closed and complete at the moment it type-checks your switch.
Why doesn't a guarded pattern (a case with a when clause) count toward exhaustiveness on its own?
A when clause is an arbitrary boolean expression evaluated at runtime — the compiler has no way to statically prove that expression is true for every value of that type, or that some other case doesn't need to catch the values where the guard is false. If the compiler treated a single guarded case as "covering" a type, a switch could compile cleanly and then, at runtime, hit a value that matches the type pattern but fails the guard, with no remaining case to handle it — exactly the kind of silent gap sealed exhaustiveness is designed to prevent. That's why the pattern in section 4 always pairs a guarded case with a subsequent unguarded case for the same shape: the unguarded case is what actually satisfies exhaustiveness, and the guarded case in front of it just intercepts a refined subset first.
What's the practical difference between Optional.ofNullable(x).orElse(y) and simply writing x != null ? x : y?
For that single line in isolation, they're equivalent, and the ternary is arguably clearer and cheaper (no wrapper object allocation). Optional earns its keep when you're chaining multiple steps that can each fail to produce a value — map, filter, flatMap — because it lets you express a pipeline without nesting conditionals or repeating null checks at every step. Reaching for Optional for a single not-null-or-default check is itself a mild anti-pattern: it adds an allocation and an API surface for no compositional benefit over the ternary.
If a sealed interface's permitted subtype is itself sealed, how does the compiler check exhaustiveness through both levels?
The compiler recursively expands the hierarchy: for a switch over the top-level sealed type, it walks each permitted subtype, and if that subtype is itself sealed (non-final), it recurses into its own permits list instead of treating it as a single leaf, continuing until it reaches only final classes, records, or non-sealed types (which it cannot fully enumerate, since non-sealed reopens extension). The switch is exhaustive only if every reachable final/record leaf across that whole recursive expansion has a matching case, as demonstrated in the PaymentResult/PaymentRejected example, where the compiler flattens PaymentResult's two permitted branches down through PaymentRejected's own two permitted branches to arrive at three total leaves.
Why does record deconstruction in a switch pattern require knowing the record's canonical component order, and what happens if you get it wrong?
A deconstruction pattern like case Shipped(var at, var carrier, var trackingNumber) matches positionally against the canonical constructor's parameter order, not by name lookup against accessor methods. If you write case Shipped(var trackingNumber, var carrier, var at) intending to relabel things, the compiler doesn't reorder anything based on your chosen names — it still binds the first pattern variable to the first canonical component (which is actually the Instant at), the second to the second (carrier), and so on; only the local variable names you chose are different, which can silently produce logically inverted code that still compiles, since the variable names are just labels you pick and the compiler only checks that each bound variable's declared type is compatible with the corresponding component's actual type (a String-typed pattern variable bound against the Instant component would be a compile error, catching some but not all misordering). There is no protection against a human choosing confusing names for the position — only against binding a variable of the wrong type to a position.
