Modern Java: Records, Sealed Classes, Pattern Matching

Records Compact Constructors Sealed Types Exhaustiveness instanceof Patterns Switch Patterns Optional Design
Why this matters

These three features are not syntactic sugar bolted onto Java for convenience — they close a real gap between Java's type system and the algebraic data types that languages like Kotlin, Scala, and Rust have had for years. Once you understand why a record forces immutability at the language level, why a sealed hierarchy lets the compiler prove a switch is exhaustive, and why pattern matching exists to eliminate a specific class of null-check and cast bugs, you start designing domain models that make illegal states unrepresentable instead of merely discouraged. That shift — from "the type system allows this but you shouldn't do it" to "the type system will not compile this" — is the difference between bugs you catch at review time and bugs the compiler catches for you.

1. Records: what the compiler actually generates

A record declaration like record Point(int x, int y) {} is a compressed way of writing a final class with a very specific, mechanically-generated shape. Understanding exactly what the compiler emits — not an approximation of it — is what lets you predict how a record behaves in serialization, equality checks, and reflection.

For record Point(int x, int y) {}, javac generates:

  • A private final field for each component: private final int x; and private final int y;.
  • A canonical constructor whose parameter list matches the component list exactly, in order: Point(int x, int y). It assigns each parameter to its corresponding field.
  • Accessor methods named after the components, not JavaBean-style getters: x() and y(), not getX() and getY(). This is deliberate — records are not beans, and the naming signals "this is a plain accessor over an immutable value," not "this may trigger side effects or lazy computation" the way a getter conventionally might.
  • equals(Object) and hashCode() that consider all components, generated to be consistent with each other (two records with equal components have equal hash codes).
  • toString() that prints the record name and all components, e.g. Point[x=3, y=4].
  • The class itself is implicitly final and implicitly extends java.lang.Record (an abstract class), which means a record can never be extended and can never extend another class — it can only implement interfaces.
Why records exist instead of just "a class with less boilerplate"

The point of a record is not to save keystrokes on getters and constructors. It's to make a declaration like record Money(BigDecimal amount, Currency currency) mean something specific and load-bearing: this type's entire identity is its components, it is immutable, and it carries no hidden state. That guarantee is what the JVM, IDEs, and libraries like Jackson can rely on. A hand-written class with the same fields and methods only has that guarantee by convention — nothing stops someone from later adding a mutable cache field or overriding equals to ignore a component. A record's transparency is enforced by the language: you cannot add instance fields beyond the components, and you cannot override the field-based semantics without deliberately overriding the generated method.

1.1 Why records are for transparent carriers, not general-purpose classes

"Transparent" here means the public API and the internal state are the same thing — there is no encapsulation gap between what the record exposes and what it stores. This is exactly backwards from the encapsulation principle you'd apply to a normal domain class (hide fields, expose behavior), and that's intentional: records are for the specific case where the value is the data, like a coordinate, a money amount, a database row projection, or a network message payload. If you find yourself wanting private helper fields, mutable state, or an inheritance hierarchy, that's a signal the type is not a value carrier and should be a regular class instead.

1.2 Compact canonical constructors

Writing a full canonical constructor to add validation means repeating the entire parameter list and every assignment, which is exactly the kind of boilerplate records are trying to eliminate. The compact constructor syntax solves this: you write validation/normalization logic without restating the parameter list or the field assignments — the compiler inserts the assignments automatically after your compact constructor body runs.

public record Range(int low, int high) {

    // Compact canonical constructor — no parameter list, no explicit assignments.
    public Range {
        if (low > high) {
            throw new IllegalArgumentException("low (" + low + ") must be <= high (" + high + ")");
        }
        // You can reassign parameters here to normalize before the implicit
        // field assignment happens. Below, "high" is clamped before storage.
        high = Math.min(high, 1_000_000);
    }
}

Note the mechanics precisely: inside a compact constructor you can reassign the constructor's parameters (here, low and high are still local parameter variables at this point), but you cannot assign directly to this.low or this.high — the compiler forbids explicit field assignment in a compact constructor and inserts the field assignments itself, using whatever the parameters hold at the end of your block. This is what makes compact constructors safe for validation and normalization without letting you accidentally skip initializing a component.

A record can still have a non-canonical constructor

You can overload additional constructors, but every non-canonical constructor must delegate to the canonical constructor (directly or transitively via another constructor) as its first statement — the same rule that applies to this(...) chaining in ordinary classes. This preserves the guarantee that all validation logic in the canonical/compact constructor always runs, no matter which constructor a caller used.

1.3 Records and the class initialization lifecycle

A record compiles to an ordinary final class file at the bytecode level, so it goes through exactly the same static and instance initialization sequence covered on the JVM internals page: static initializers and static field initializers run once, in textual order, the first time the class is actively used, guarded by the classloader's per-class initialization lock; then, for each instance, instance initializer blocks and instance field initializers run in textual order immediately before the constructor body, every time a canonical (or delegating) constructor is invoked. Nothing about the record shorthand changes that model — a compact constructor body is simply spliced in as the first part of the "constructor body" step, and the implicit field assignments happen after it, then any explicit trailing statements you wrote after the compact block's validation. If a record implements an interface with a static method, or has its own static fields (records can declare static fields and static methods — the restriction is only on instance fields beyond the components), classloading proceeds identically to any other class.

2. Sealed Classes and Interfaces

Before sealed types, Java's inheritance model was open by default: any class in the classpath could extend any non-final public class or implement any public interface. That openness is usually good for extensibility, but it's actively harmful when you're trying to model a closed set of variants — a type that represents "exactly these possibilities and no others," like a JSON value that's either a string, a number, a boolean, an array, or an object, and nothing else.

A sealed class or interface declares, via a permits clause, the exhaustive list of classes allowed to directly extend or implement it:

public sealed interface Shape permits Circle, Rectangle, Triangle {}

public final class Circle implements Shape {
    public final double radius;
    public Circle(double radius) { this.radius = radius; }
}

public final class Rectangle implements Shape {
    public final double width, height;
    public Rectangle(double width, double height) {
        this.width = width; this.height = height;
    }
}

public final class Triangle implements Shape {
    public final double base, height;
    public Triangle(double base, double height) {
        this.base = base; this.height = height;
    }
}

Every class named in permits must itself declare how it participates in the sealing: it must be final (no further extension), sealed (it defines its own restricted set of subclasses), or non-sealed (it deliberately reopens extension to arbitrary subclasses from that point down). This is not optional boilerplate — the compiler rejects a permitted subclass that doesn't declare one of these three modifiers, because otherwise the "closed set" guarantee at the Shape level would be silently undermined by an unrestricted subclass three levels down.

Why this needs compiler enforcement, not just discipline

You could always simulate a closed hierarchy by convention — package-private constructors, documentation comments saying "do not extend this." But none of that is checked. A sealed hierarchy is checked at compile time and recorded in the class file (via a PermittedSubclasses attribute), which means tooling and the compiler itself can reason about completeness. That's the entire point: it turns "we intend this to be a closed set" into "the compiler can prove this is a closed set," which is the property that unlocks exhaustive switches in the next section.

2.1 permits and same-module / same-package constraints

Permitted subclasses must be knowable at compile time, so they're constrained to be co-located with the sealed type: either in the same module (for modular code) or, for classpath-based code, the same package. If all permitted subclasses are declared in the same source file or as nested classes of the sealed type, the permits clause can even be omitted — the compiler infers it from what it sees in that compilation unit.

3. Pattern Matching: instanceof, switch, and deconstruction

3.1 instanceof pattern matching

Before pattern matching, the idiomatic instanceof check required a redundant explicit cast immediately afterward, because the compiler didn't retain any relationship between the check and the subsequent use:

// Old style — the cast repeats information the instanceof check already proved.
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.length());
}

Pattern matching for instanceof lets you bind a variable directly in the condition, and the compiler makes that variable available — correctly typed, with no cast — in any branch where flow analysis can prove the check succeeded:

if (obj instanceof String s) {
    System.out.println(s.length()); // s is a String here, no cast
}

// Flow-sensitive negation also works: the compiler tracks that if this
// condition is true, obj was NOT a String, so returning/throwing means
// s is definitely a String after this point too.
if (!(obj instanceof String s)) {
    return;
}
System.out.println(s.length()); // s is in scope and typed String here

This eliminates an entire category of bugs where the cast type silently drifts from the instanceof type during a refactor (someone changes the check but forgets to update the cast, producing a ClassCastException at runtime instead of a compile error).

3.2 Switch pattern matching over types

Traditional switch only worked on a fixed set of types (primitives, strings, enums) and matched by exact value equality. Pattern matching for switch generalizes this to match by type, with optional deconstruction, directly in the case label:

static String describe(Object obj) {
    return switch (obj) {
        case Integer i -> "int " + i;
        case String s  -> "string of length " + s.length();
        case null      -> "it's null";
        default        -> "something else";
    };
}

Note that case null is legal directly in a pattern-matching switch — something that was illegal for traditional switches, which threw NullPointerException on a null selector. This matters because it removes the need for a separate null check before the switch, folding null-handling into the same exhaustiveness-checked construct.

3.3 Record deconstruction patterns

Because a record's canonical form is fully known (its components, in order, with fixed types), a case label can destructure a record's components directly, binding each one to a new variable without calling any accessor manually:

record Point(int x, int y) {}

static String classify(Object obj) {
    return switch (obj) {
        case Point(int x, int y) when x == 0 && y == 0 -> "origin";
        case Point(int x, int y) when x == y            -> "on the diagonal";
        case Point(int x, int y)                        -> "point at " + x + "," + y;
        default                                          -> "not a point";
    };
}

Deconstruction patterns nest arbitrarily — a record whose component is itself another record can be destructured in one pattern, e.g. case Line(Point(int x1, int y1), Point(int x2, int y2)), which recursively unpacks both endpoints in a single case label.

3.4 Guarded patterns (when clauses)

A type pattern alone can only discriminate on type, but you frequently need to refine further — "it's a Point, but specifically one at the origin." The when clause adds an arbitrary boolean guard evaluated only after the type/deconstruction pattern has already matched, as shown in the classify example above. This is what lets pattern-matching switches subsume a chain of if (x instanceof T t && t.someCondition()) checks into one readable, exhaustively-checked construct.

Pattern order matters, just like exception catch clauses

Case labels are evaluated top to bottom, and the first match wins. A guarded pattern case Point(int x, int y) when x == y placed before an unguarded case Point(int x, int y) is fine, but if you reverse the order, the unguarded case shadows the guarded one and the compiler will flag it as unreachable — the same "more specific must come first" discipline you already apply when ordering catch blocks from subclass to superclass.

4. Sealed types + pattern matching: compiler-enforced exhaustiveness

This is where the three features compose into something genuinely new for Java. When the selector of a switch expression has a sealed type, the compiler knows the complete set of permitted subtypes from the permits clause. If every permitted subtype has a corresponding case, the switch is provably exhaustive, and no default branch is required — in fact, for a switch expression (one that must produce a value), omitting a case for a permitted subtype without a default is a compile error, not a runtime gap.

Consider modeling a computation result as a closed set of two outcomes, deliberately built to exercise generics, nested records, and multi-level sealing at once:

public sealed interface Result<T> permits Success, Failure {}

public record Success<T>(T value) implements Result<T> {}

public sealed interface Failure extends Result<Object>
        permits ValidationFailure, TimeoutFailure {}

public record ValidationFailure(String field, String reason) implements Failure {}
public record TimeoutFailure(long elapsedMillis) implements Failure {}

static <T> String render(Result<T> result) {
    return switch (result) {
        case Success<T>(var value) ->
            "ok: " + value;
        case ValidationFailure(var field, var reason) when reason.isBlank() ->
            "validation failed on " + field + " (no reason given)";
        case ValidationFailure(var field, var reason) ->
            "validation failed on " + field + ": " + reason;
        case TimeoutFailure(var ms) when ms > 30_000 ->
            "timed out badly after " + ms + "ms";
        case TimeoutFailure(var ms) ->
            "timed out after " + ms + "ms";
    };
}

Walk through why this compiles with no default: Result<T> permits exactly Success and Failure; Failure itself is sealed and permits exactly ValidationFailure and TimeoutFailure. The compiler flattens this two-level sealed hierarchy and confirms that Success, ValidationFailure, and TimeoutFailure — the only three concrete leaves — each have at least one unconditional (guard-free) case covering them. The guarded cases (when reason.isBlank(), when ms > 30_000) don't count toward exhaustiveness on their own, precisely because a guard can be false — which is why each guarded case here is paired with a fallback unguarded case for the same pattern.

Now suppose someone extends the hierarchy: they add permits ValidationFailure, TimeoutFailure, RateLimitedFailure to Failure, and a new record RateLimitedFailure(int retryAfterSeconds) implements Failure {}, but never revisit render. Because render's switch is exhaustive over a sealed type with no default, the compiler immediately reports an error at the switch — something like the switch expression does not cover all possible input values — pointing at the exact call site that needs updating, rather than letting the new variant silently fall through to a wrong branch or an IllegalStateException discovered later in production. This is the concrete payoff: adding a variant to a closed hierarchy turns every place that pattern-matches over it into a to-do list the compiler generates for you.

This guarantee disappears the moment you add a catch-all

If render had a trailing default -> "unknown failure", adding RateLimitedFailure would compile cleanly and silently route through default — exactly the bug sealed exhaustiveness exists to prevent. Add a default to a sealed-type switch only when you deliberately want new variants to degrade gracefully rather than force an update; otherwise, leaving it off is the feature, not an oversight.

5. Optional revisited: anti-patterns and the functional style it was designed for

Optional<T> was added specifically to give method return types an explicit, type-checked way to say "this might not have a value," replacing the ambiguous convention of returning null and hoping every caller remembers to check. But Optional is frequently used in ways its designers explicitly warned against, because it superficially looks like "a nicer null" rather than what it actually is: a container meant to be composed functionally, similar in spirit to the Stream pipelines covered on the streams and functional programming page.

5.1 Optional as a field

Optional does not implement Serializable. A field of type Optional<String> on a class that gets serialized (via Java serialization, or even naively via some reflection-based frameworks) either fails outright or requires special-case handling that defeats the purpose of using Optional for clarity. Beyond serialization, an Optional field also doubles the ways "no value" can be represented: the field reference itself can be null (nobody stops you from writing this.middleName = null; instead of Optional.empty()), so you've added a wrapper without actually eliminating the null case you were trying to avoid.

Idiomatic replacement: use a plain, possibly-null field (with @Nullable annotations or clear documentation), and only wrap it in Optional at the accessor boundary if you want callers to be forced to handle absence:

public class Person {
    private final String middleName; // may be null internally

    public Optional<String> middleName() {
        return Optional.ofNullable(middleName);
    }
}

5.2 Optional as a method parameter

Making a parameter Optional<T> pushes the wrapping cost onto every caller, including callers who have a perfectly ordinary, always-present value — they now have to write Optional.of(value) just to call your method. It also allows a second, unwanted way to express "no argument": passing null itself instead of Optional.empty(), which Optional-typed parameters do nothing to prevent.

Idiomatic replacement: use method overloading for the "this argument may be omitted" case:

// Instead of: void search(String query, Optional<String> region)
void search(String query) {
    search(query, null);
}

void search(String query, String region) {
    String effectiveRegion = (region != null) ? region : "GLOBAL";
    // ...
}

5.3 isPresent()/get() instead of the functional style

Writing if (opt.isPresent()) { return opt.get().toUpperCase(); } else { return "DEFAULT"; } reproduces exactly the imperative null-check structure Optional was meant to replace — it's a null check with extra ceremony. Optional's actual API is a small set of combinators designed to be chained:

Anti-patternIdiomatic replacementWhy it's better
if (opt.isPresent()) return opt.get().toUpperCase(); else return "DEFAULT";opt.map(String::toUpperCase).orElse("DEFAULT")One expression; no branch to accidentally get wrong; reads as a pipeline
if (opt.isPresent()) { doSomething(opt.get()); }opt.ifPresent(this::doSomething)No manual unwrap; the lambda only runs when a value exists
if (!opt.isPresent()) throw new IllegalStateException(); return opt.get();opt.orElseThrow(() -> new IllegalStateException()) (or no-arg orElseThrow() for NoSuchElementException)Expresses "required value or a specific failure" as one call

The unifying idea is the same discipline that makes Stream pipelines composable: treat Optional as a zero-or-one-element container you transform with map/filter/flatMap and only terminate with orElse/orElseGet/orElseThrow, never by manually branching on presence and reaching in with get().

Optional and sealed Result types solve overlapping but distinct problems

Optional<T> only tells you value-or-nothing; it carries no information about why there's nothing. The sealed Result<T> pattern from section 4 is what you reach for when the failure case itself carries structured data (a validation reason, a timeout duration) that callers need to branch on. Don't force a rich failure into Optional.empty() and lose that information — model it as a sealed type and pattern-match instead.

Concepts Worth Being Able to Explain From First Principles

Why can't you add an extra instance field to a record beyond its declared components?
Because the entire value proposition of a record is transparency: its public state (accessors) and its actual state (fields) are guaranteed identical, which is what allows the compiler to safely auto-generate equals, hashCode, and toString purely from the component list. If arbitrary extra instance fields were allowed, those generated methods would need to either silently ignore the extra field (breaking the equals/hashCode contract's usual expectation that "equal objects" means "equal in all state you'd reasonably compare") or the compiler would need to guess whether to include it — there's no principled default. Restricting records to exactly their components removes that ambiguity entirely: everything about a record's identity is visible in its header.
What actually happens in a compact canonical constructor if you never reassign a parameter?
The compiler still performs the implicit field assignment using whatever value the parameter holds at the end of the compact constructor's body — which, if you never touched it, is just the value the caller passed in. The compact syntax doesn't remove the assignments; it just lets the compiler write them for you after your validation/normalization code runs, using the current (possibly reassigned) parameter values as the source. This is why you can throw partway through the compact constructor to reject bad input before any field is ever set, since the implicit assignments only happen after your block completes normally.
Why does sealing need a permits clause instead of just marking the interface "sealed" and letting the compiler scan the classpath?
Java classes are typically compiled and loaded incrementally, and the classpath at compile time for one module isn't guaranteed to contain every class that will exist at runtime (separately compiled JARs can be added later). If sealing worked by scanning "whatever happens to exist," the set of permitted subtypes could differ between compilation and runtime, and exhaustiveness checks would be unsound — the compiler could prove a switch exhaustive against one set of subtypes while a different set exists when the code actually runs. Requiring an explicit, compile-time-checked permits list (co-located in the same module or package) pins the set of subtypes to something the compiler can verify is closed and complete at the moment it type-checks your switch.
Why doesn't a guarded pattern (a case with a when clause) count toward exhaustiveness on its own?
A when clause is an arbitrary boolean expression evaluated at runtime — the compiler has no way to statically prove that expression is true for every value of that type, or that some other case doesn't need to catch the values where the guard is false. If the compiler treated a single guarded case as "covering" a type, a switch could compile cleanly and then, at runtime, hit a value that matches the type pattern but fails the guard, with no remaining case to handle it — exactly the kind of silent gap sealed exhaustiveness is designed to prevent. That's why the pattern in section 4 always pairs a guarded case with a subsequent unguarded case for the same shape: the unguarded case is what actually satisfies exhaustiveness, and the guarded case in front of it just intercepts a refined subset first.
What's the practical difference between Optional.ofNullable(x).orElse(y) and simply writing x != null ? x : y?
For that single line in isolation, they're equivalent, and the ternary is arguably clearer and cheaper (no wrapper object allocation). Optional earns its keep when you're chaining multiple steps that can each fail to produce a value — map, filter, flatMap — because it lets you express a pipeline without nesting conditionals or repeating null checks at every step. Reaching for Optional for a single not-null-or-default check is itself a mild anti-pattern: it adds an allocation and an API surface for no compositional benefit over the ternary.
If a sealed interface's permitted subtype is itself sealed, how does the compiler check exhaustiveness through both levels?
The compiler recursively expands the hierarchy: for a switch over the top-level sealed type, it walks each permitted subtype, and if that subtype is itself sealed (non-final), it recurses into its own permits list instead of treating it as a single leaf, continuing until it reaches only final classes, records, or non-sealed types (which it cannot fully enumerate, since non-sealed reopens extension). The switch is exhaustive only if every reachable final/record leaf across that whole recursive expansion has a matching case, as demonstrated in the Result/Failure example.
Why does record deconstruction in a switch pattern require knowing the record's canonical component order, and what happens if you get it wrong?
A deconstruction pattern like case Point(int x, int y) matches positionally against the canonical constructor's parameter order, not by name lookup against accessor methods. If you write case Point(int y, int x) intending to swap semantics, the compiler doesn't reorder anything — it still binds the first pattern variable to the first canonical component and the second to the second; only the local variable names you chose are swapped, which can silently produce logically inverted code that still compiles, since the variable names are just labels you pick. This is why the type of each bound variable must be compile-time compatible with the corresponding component's declared type — that's the check the compiler performs — but there is no protection against a human choosing confusing names for the position.
