Most Asked Interview Questions: Spring Framework & Spring Boot

IoC & DI Bean Lifecycle Auto-Configuration REST Controllers AOP Profiles
Why this matters

Spring and Spring Boot questions show up in almost every backend Java interview because the framework is where object-oriented theory (dependency injection, proxies, lifecycle hooks) meets the practical job of shipping a REST service. Interviewers use these questions to check two things at once: do you understand what the framework is doing for you under the hood, and can you actually wire together a working, well-behaved API. This page collects the questions that come up over and over — from "what is dependency injection" to "how do you return the right HTTP status code" — so you can rehearse tight, concrete answers instead of vague ones.

Core Spring: IoC, DI & AOP

What is the IoC (Inversion of Control) container, and how does Dependency Injection relate to it?
Inversion of Control is the general principle of handing control over object creation and wiring to a framework instead of writing that logic yourself with new. Spring's IoC container (the ApplicationContext) is the concrete implementation of that principle: it reads configuration (annotations, XML, or Java config classes), instantiates the objects it discovers, and manages their entire lifecycle. Dependency Injection (DI) is the specific technique the container uses to achieve IoC — instead of a class looking up or constructing its own collaborators, the container "injects" those collaborators into it, typically through the constructor. For example, an OrderService in ShopSphere doesn't do new PaymentClient() itself; it declares that it needs a PaymentClient, and the container supplies one. This decoupling is what makes classes easy to unit test in isolation and easy to swap implementations without touching consumer code.
What are the stages of the Spring bean lifecycle?
A managed bean goes through a well-defined sequence: (1) Instantiation — the container calls the constructor to create the raw object; (2) Populate properties — dependencies are injected, either via the constructor or via setters/field injection; (3) Aware interfaces — if the bean implements interfaces like BeanNameAware or ApplicationContextAware, Spring calls the corresponding setter methods so the bean can access its own name or the context; (4) BeanPostProcessor pre-initialization hooks run; (5) Initialization — any method annotated @PostConstruct, or an InitializingBean.afterPropertiesSet(), or a custom init-method is invoked, in that order of precedence; (6) BeanPostProcessor post-initialization hooks run, which is also where proxies (for AOP, transactions, etc.) get wrapped around the bean; (7) the bean sits ready for use; (8) on container shutdown, Destruction callbacks run — @PreDestroy, DisposableBean.destroy(), or a custom destroy-method. Knowing this order matters in practice: if you need a bean's dependencies fully injected before doing setup work, that's exactly what @PostConstruct is for.
What are the main Spring bean scopes, and when would you use each?
Singleton (the default) means the container creates exactly one instance per Spring container and returns that same instance for every injection point — appropriate for stateless services like a ProductService or a repository. Prototype creates a brand-new instance every time the bean is requested from the container, which suits objects that hold mutable, request-specific state that must not be shared, like a stateful builder. Request scope creates one instance per HTTP request and is only meaningful in a web application context — useful for something like a per-request audit context object that accumulates data as a request flows through layers. Session scope creates one instance per HTTP session, useful for things like a shopping cart object tied to a logged-in Customer's session in ShopSphere. The critical gotcha interviewers probe for: injecting a narrower-scoped bean (request/session) into a wider-scoped singleton requires a scoped proxy (proxyMode = ScopedProxyMode.TARGET_CLASS), otherwise the singleton would capture a stale reference from whichever request happened to create it first.
What's the difference between @Component, @Service, @Repository, and @Controller?
All four are specializations of the same meta-annotation, @Component, and functionally they all register a class as a Spring-managed bean discovered via component scanning — so at the container level they behave identically. The distinction is about semantic intent and, for two of them, extra behavior. @Component is the generic, no-special-meaning form used for utility or infrastructure classes. @Service marks a class as holding business logic (e.g. OrderService, InventoryService) and exists mainly for readability and future-proofing. @Repository marks data-access classes and additionally enables Spring's persistence exception translation, converting database-specific exceptions (like a JDBC SQLException) into Spring's unchecked DataAccessException hierarchy so calling code doesn't need to depend on a specific database driver's exception types. @Controller marks a class as a Spring MVC web controller whose methods, by default, return view names to be resolved by a view resolver — it's the annotation you'd combine with @ResponseBody if you wanted JSON output instead (which is exactly what @RestController does for you automatically).
Constructor injection vs field injection — what's the difference, and why is constructor injection preferred?
Field injection uses @Autowired directly on a class field and relies on reflection to set the value after the object is constructed; constructor injection declares dependencies as constructor parameters, and Spring supplies them when it builds the object (as of recent Spring versions, @Autowired on the constructor is even optional if there's only one constructor). Constructor injection is preferred for several concrete reasons: it lets you declare fields as final, guaranteeing immutability and that the object is never in a partially-constructed, dependency-missing state; it makes circular dependencies fail fast at startup with a clear error instead of Spring silently trying to work around them; it makes unit testing trivial because you can construct the object directly with mocks, with no need for a Spring context or reflection-based test utilities; and it makes a class's dependencies explicit and visible in one place (the constructor signature) rather than scattered across annotated fields. Field injection is more concise to write but hides the true size of a class's dependency list, which is often itself a signal that the class is doing too much.
How do you resolve a circular dependency error in Spring?
A circular dependency happens when, for example, OrderService needs PaymentService injected and PaymentService needs OrderService injected — neither can be fully constructed before the other. With constructor injection this fails immediately at startup with a BeanCurrentlyInCreationException, because the container cannot resolve the chicken-and-egg problem of a fully-built constructor argument. The right fix is almost always to break the cycle through better design: extract the shared behavior both classes need into a third class that both depend on, or invert one of the dependencies so only one class holds a reference to the other. If you truly need to unblock it without redesigning immediately, workarounds include switching one side to field/setter injection (which lets Spring create the raw beans first and wire the property afterward) or wrapping one dependency in @Lazy, which injects a proxy that only resolves the real bean on first use. These workarounds should be treated as a temporary patch, though — a circular dependency is usually a symptom of two components that are too tightly coupled and shouldn't be, in the same way a circular import is a code smell in Core Java.
What's the difference between @Qualifier and @Primary when multiple beans of the same type exist?
Both solve the ambiguity that arises when the container finds more than one bean matching a required type and can't pick automatically. @Primary is declared on one of the candidate bean definitions to mark it as the default choice whenever autowiring by type is ambiguous — it's a "use this one unless told otherwise" rule set at the bean's definition site. @Qualifier("beanName") is declared at the injection point (the constructor parameter or field) and explicitly names which specific bean should be wired there, overriding whatever the default would be. A practical example: if ShopSphere has two implementations of a NotificationSender interface — EmailNotificationSender and SmsNotificationSender — you might mark EmailNotificationSender as @Primary since most services just want email, but use @Qualifier("smsNotificationSender") in the one place (like order-service's urgent delivery alerts) that specifically needs SMS. If both a qualifier and a primary bean are present, the qualifier at the injection point wins because it's more specific.
What is AOP (Aspect-Oriented Programming), and where does Spring use it internally?
AOP (Aspect-Oriented Programming) is a paradigm for separating cross-cutting concerns — logic that would otherwise be duplicated across many unrelated classes, like logging, security checks, or transaction management — into standalone modules called "aspects," which are then woven into the target code at specific join points without the target code needing to know about them. Spring implements AOP primarily through dynamic proxies: at startup, for any bean that matches an aspect's pointcut (the rule describing which methods to intercept), Spring wraps that bean in a proxy (a JDK dynamic proxy if the bean implements an interface, or a CGLIB subclass proxy otherwise) that runs the aspect's advice (before/after/around logic) around the real method call. The most common example every Spring developer touches is @Transactional: the annotation itself does nothing by itself, it's the AOP proxy wrapped around the bean that opens a database transaction before the method runs and commits or rolls it back after, based on whether an exception was thrown. Spring also uses this same mechanism for @Async, @Cacheable, and method-level security checks like @PreAuthorize, and developers commonly write their own aspects for cross-cutting logging or auditing, such as logging every call into ShopSphere's payment-service with its arguments and execution time.
Why doesn't @Transactional work when a method calls another @Transactional method on the same class?
This is the classic AOP proxy "self-invocation" pitfall: Spring's transaction support works by wrapping the bean in a proxy, but that proxy only intercepts calls that come in from outside the bean, through the proxy itself. When a method inside OrderService calls another @Transactional method on this directly — this.updateInventory(...) — that call is a plain Java method invocation on the raw target object, bypassing the proxy entirely, so no transaction is started or joined even though the annotation is present. The usual fixes are to move the called method into a separate bean and inject that bean (so the call goes back through its proxy), or to inject the current bean's own proxy (for example via ApplicationContext.getBean(...) or AopContext.currentProxy()) and call through that instead. This same self-invocation limitation applies to every Spring feature built on proxy-based AOP, not just @Transactional — including @Async, @Cacheable, and @Retryable, so it's worth recognizing as a general rule rather than a one-off gotcha.
What's the difference between BeanFactory and ApplicationContext?
BeanFactory is the root interface for Spring's IoC (Inversion of Control) container and provides the most basic functionality: it can create and wire beans, but it does so lazily — a bean isn't instantiated until something actually asks for it. ApplicationContext is a sub-interface that builds on BeanFactory and adds the features almost every real application needs: eager instantiation of singleton beans at startup (so configuration errors surface immediately instead of at some arbitrary later request), built-in support for internationalization, the ability to publish and listen for application events, integration with AOP (Aspect-Oriented Programming) proxying, and automatic registration of BeanPostProcessor/BeanFactoryPostProcessor beans. In practice, ApplicationContext (via concrete implementations like AnnotationConfigApplicationContext or, in Spring Boot, the auto-configured context Boot builds for you) is what every real application uses; BeanFactory is mostly of historical and academic interest today, and the distinction mainly comes up as a "do you understand what's underneath Boot" interview check rather than something you'd choose between day to day.

Spring Boot Essentials

What is the actual difference between Spring and Spring Boot?
Spring (the Spring Framework) is the underlying framework that provides the IoC (Inversion of Control) container, Dependency Injection, Spring MVC, AOP (Aspect-Oriented Programming), and transaction management — but using it directly means you write your own configuration classes or XML to wire beans, manually manage a servlet container, and hand-pick compatible versions of every dependency yourself. Spring Boot is built on top of the Spring Framework, not a replacement for it; it adds auto-configuration, starter dependencies with centrally managed versions, an embedded server, and sensible production-ready defaults so you can get a working application running with almost no boilerplate configuration. Concretely: every @Service, @Autowired, and @Transactional you write in a Spring Boot app is still plain Spring — Boot hasn't changed how DI or AOP work, it has just automated the setup work around them. The way to frame this in an interview: Spring gives you the tools, Spring Boot gives you an opinionated, pre-wired starting point so you spend your time on business logic like ShopSphere's order and payment flows instead of on infrastructure plumbing.
What does Spring Boot's auto-configuration actually do, and how is @SpringBootApplication composed?
Auto-configuration is Spring Boot's mechanism for automatically registering beans it infers you'll need, based purely on what's present on the classpath and what beans you've already defined yourself. Concretely, Boot ships a large set of @Configuration classes, each guarded by conditional annotations like @ConditionalOnClass (only apply if a given class is on the classpath) or @ConditionalOnMissingBean (only apply if you haven't already defined your own bean of that type) — so if you add the spring-boot-starter-data-jpa dependency, Boot detects Hibernate and a DataSource class on the classpath and auto-configures an EntityManagerFactory and transaction manager for you, but backs off entirely if you've configured your own. @SpringBootApplication is a convenience meta-annotation bundling three separate things: @Configuration (marks the class itself as a source of bean definitions), @EnableAutoConfiguration (turns on the conditional auto-configuration mechanism just described), and @ComponentScan (tells Spring to scan the current package and sub-packages for @Component-annotated classes). Understanding this composition is what lets you explain, for instance, why moving your main class to a different package can silently break component scanning for classes outside its subtree.
What are Spring Boot "starters," and why do they matter?
A starter is a curated dependency descriptor — just a Maven/Gradle artifact with no code of its own — that pulls in a coherent, version-compatible set of libraries for a particular purpose, so you don't have to hand-pick and version-match a dozen individual dependencies. For example, spring-boot-starter-web pulls in Spring MVC, an embedded Tomcat server, and Jackson for JSON serialization in one go, and spring-boot-starter-data-jpa pulls in Hibernate, Spring Data JPA, and the JDBC layer. The versions of every transitive dependency are managed centrally by the Spring Boot "parent" BOM (Bill of Materials), which is precisely what prevents the classic problem of two libraries pulling in incompatible versions of the same transitive dependency. In practice, when you add a starter to a new microservice like ShopSphere's notification-service, you're not just adding a library — you're also opting into whatever auto-configuration classes are conditionally triggered by that library's presence on the classpath.
How do application.properties/application.yml and Spring profiles work together?
application.properties (or the equivalent application.yml, which is just a more structured, hierarchical syntax for the same key-value data) is Spring Boot's default externalized configuration file, loaded automatically at startup to configure things like server port, datasource URLs, and logging levels without touching code. Profiles let you maintain environment-specific overrides on top of that baseline: a file named application-dev.yml or application-prod.yml only gets loaded when that profile is active (set via the spring.profiles.active property, an environment variable, or a JVM flag), and any properties it defines override the base file's values for that environment. This is how ShopSphere's order-service can point at a local Postgres instance and log at DEBUG level when the dev profile is active, but point at a production connection pool and log at WARN when prod is active, using the exact same compiled JAR. Classes can also be conditionally registered per profile with @Profile("dev"), which is useful for swapping in a fake payment gateway stub during local development.
What's the difference between Spring Boot's embedded server model and traditional WAR deployment?
In the traditional model, you package your application as a WAR (Web Application Archive) and deploy it into a separately installed and managed servlet container (Tomcat, JBoss, WebSphere) that already exists on the target machine — the server's lifecycle is independent of your application's. Spring Boot flips this by embedding the servlet container (Tomcat by default, though Jetty or Undertow can be swapped in) directly inside the application's executable JAR; running java -jar app.jar starts both the JVM and an in-process HTTP server together, and the two share a single lifecycle. This is what makes Spring Boot such a natural fit for microservices and containers: each of ShopSphere's services (order-service, inventory-service, payment-service, etc.) can be built as one self-contained, independently deployable JAR with everything it needs baked in, dropped straight into a Docker image, with no separate application-server installation or configuration step on the host. Boot still supports building a deployable WAR for legacy environments that require it, but the embedded-JAR model is the default and by far the more common choice today.
What is Spring Boot Actuator, and how do health checks work?
Actuator is a Spring Boot module that exposes a set of production-ready HTTP endpoints for monitoring and managing a running application without you having to build that tooling yourself — things like /actuator/health, /actuator/metrics, /actuator/info, and /actuator/env. The health endpoint aggregates status from individual "health indicators," each of which checks one dependency the application relies on — a database connection pool, a Kafka broker connection, disk space — and rolls them up into a single overall status (UP, DOWN, or OUT_OF_SERVICE). This is exactly what a Kubernetes liveness or readiness probe hits: if ShopSphere's payment-service loses its database connection, its health indicator flips to DOWN, the aggregated /actuator/health response reflects that, and Kubernetes can automatically stop routing traffic to that pod or restart it. You can also write custom HealthIndicator beans to check application-specific conditions, and most of Actuator's endpoints are disabled or restricted by default in production and need explicit exposure configuration, since some of them (like /actuator/env) can leak sensitive configuration if left open.
What is externalized configuration, and how does @ConfigurationProperties work?
Externalized configuration is the practice of keeping environment-specific or tunable values (URLs, timeouts, feature flags, credentials) outside compiled code, in property files, environment variables, or command-line arguments, so the same build artifact can run correctly in different environments. Spring Boot supports injecting single values directly with @Value("${some.property}"), but for a related group of settings, @ConfigurationProperties is the cleaner, type-safe alternative: you define a plain class with fields matching a property prefix, annotate it with @ConfigurationProperties(prefix = "shopsphere.payment"), and Spring Boot binds every matching property (like shopsphere.payment.retry-count and shopsphere.payment.timeout-ms) onto that object's fields automatically, including nested objects and lists. This is preferable to scattering many individual @Value annotations because it gives you IDE auto-completion, validation support via @Validated, and a single class you can inject wherever the whole configuration group is needed, rather than re-declaring the same property key as a string in multiple places.
How do you write tests for a Spring Boot application — what's the difference between @SpringBootTest and slice tests like @WebMvcTest?
@SpringBootTest boots the entire application context — every bean, every auto-configuration, optionally a real embedded server — which gives you the most realistic test but is the slowest, so it's typically reserved for a handful of true end-to-end integration tests, such as verifying that ShopSphere's order-service actually persists an order and publishes an OrderPlaced event when hit through its real HTTP endpoint. "Slice" test annotations load only the beans relevant to one architectural layer, which makes tests much faster and more focused: @WebMvcTest(OrderController.class) loads just the web layer (controllers, filters, @ControllerAdvice) and lets you use MockMvc to fire simulated HTTP requests while mocking out the service layer with @MockBean; @DataJpaTest loads just the JPA (Java Persistence API) layer with an in-memory database to test repository queries in isolation. The interview-relevant judgment call is choosing the narrowest slice that still gives you confidence — over-relying on full @SpringBootTest integration tests for logic that a plain unit test (no Spring context at all, just constructing the class with mocked dependencies) could cover just as well is a common reason test suites in real Spring Boot codebases become slow.
How would you troubleshoot a bean that Spring Boot's auto-configuration isn't creating the way you expect?
This is a debugging skill senior engineers are expected to have because auto-configuration failures are otherwise a black box. The first tool is running the application with the --debug flag (or setting debug=true in configuration), which prints an auto-configuration report at startup listing every conditional configuration class Spring Boot considered, split into "positive matches" (applied) and "negative matches" (skipped, with the exact condition that failed — e.g. "did not match because required class DataSource was not on the classpath"). The second is understanding that auto-configuration always defers to explicit user configuration: if you've defined your own bean of a given type, any auto-configuration guarded by @ConditionalOnMissingBean for that type silently backs off, which is a common source of "why isn't my custom bean being used" confusion when someone doesn't realize their own @Bean method is actually winning. You can also explicitly exclude a specific auto-configuration class via @SpringBootApplication(exclude = DataSourceAutoConfiguration.class) when you need to rule one out entirely, such as a service that talks only to Kafka and deliberately has no database. Being able to reason through this chain — classpath presence, conditional annotations, explicit bean overrides, the debug report — is what separates "Spring Boot just works by magic" from actually understanding the mechanism well enough to fix it when it doesn't.

Building REST APIs with Spring

What is the DispatcherServlet, and how does a request flow through Spring MVC?
The DispatcherServlet is the single front-controller servlet that sits in front of every Spring MVC application and coordinates the entire request-handling pipeline — Spring Boot registers and configures it for you automatically when spring-boot-starter-web is on the classpath, so you rarely touch it directly, but understanding what it does is how you reason about anything going wrong before your controller code runs. A request flow looks like: (1) the embedded servlet container (Tomcat by default) hands an incoming HTTP request to the DispatcherServlet; (2) it consults a HandlerMapping to figure out which controller method matches the request's URL and HTTP verb; (3) any registered HandlerInterceptors or servlet Filters run pre-processing logic, such as authentication checks; (4) the matched controller method executes, with Spring resolving its parameters (@RequestBody, @PathVariable, and so on) and validating them if @Valid is present; (5) the return value is handed to an HttpMessageConverter (for a @RestController) to be serialized into the response body, or to a ViewResolver (for a plain @Controller) to render a view; (6) interceptors run their post-processing, and the response is sent back. Knowing this pipeline is what lets you correctly place cross-cutting logic — for example, deciding that a request-ID-stamping concern for ShopSphere's order-service belongs in a Filter or interceptor rather than duplicated inside every controller method.
What's the difference between @RestController and @Controller?
@Controller is the base Spring MVC annotation for a web controller, and by default its methods are expected to return a view name (a JSP or template name) that gets resolved and rendered as HTML. @RestController is a convenience meta-annotation equal to @Controller combined with @ResponseBody on every method, which tells Spring to take a method's return value and serialize it directly into the HTTP response body (typically as JSON via Jackson) instead of treating it as a view name to resolve. For a REST API like ShopSphere's catalog-service returning product data, you almost always want @RestController; you'd only reach for plain @Controller with individual @ResponseBody annotations if a controller mixed server-rendered pages with a handful of JSON endpoints.
What do @GetMapping, @PostMapping, and @RequestMapping actually do?
@RequestMapping is the original, general-purpose Spring MVC annotation for mapping an HTTP request to a handler method or class, and it needs an explicit method attribute to restrict which HTTP verb it matches — for example @RequestMapping(value = "/products", method = RequestMethod.GET). @GetMapping, @PostMapping, @PutMapping, @PatchMapping, and @DeleteMapping are shorthand meta-annotations built on top of @RequestMapping that hard-code the HTTP verb into the annotation name itself, so @GetMapping("/products") is exactly equivalent to the more verbose form above but reads more clearly and is what real-world Spring codebases use almost universally today. @RequestMapping is still commonly applied at the class level to declare a shared base path — for instance @RequestMapping("/api/orders") on OrderController, with each handler method inside using @GetMapping("/{orderId}") or @PostMapping for the specific sub-path and verb. Getting the HTTP verb right matters beyond style: it's what makes an endpoint properly RESTful (GET for safe, cacheable reads with no side effects; POST for creating a resource; PUT/PATCH for updates; DELETE for removal), which browsers, proxies, and API gateways all rely on for correct caching and retry behavior.
What's the difference between @RequestBody, @PathVariable, and @RequestParam?
These three annotations tell Spring where in the incoming HTTP request to pull a method parameter's value from. @RequestBody deserializes the entire HTTP request body (typically JSON) into a Java object — used for POST/PUT endpoints like creating an order, where the client sends a full OrderRequest payload. @PathVariable extracts a value embedded directly in the URL path, matching a placeholder in the route mapping — for example @GetMapping("/orders/{orderId}") with @PathVariable String orderId pulls the ID out of a URL like /orders/A123. @RequestParam extracts a value from the URL's query string (or form data), such as @RequestParam(defaultValue = "10") int pageSize handling a request to /products?pageSize=20. The distinguishing factor to lead with in an interview: path variables identify a specific resource, query params filter or modify a request against that resource (or a collection), and the request body carries the actual payload data for writes.
How do you validate incoming request data with @Valid, and what happens when validation fails?
You annotate the fields of your request DTO (Data Transfer Object) with Bean Validation constraint annotations — @NotNull, @NotBlank, @Size(min=1, max=100), @Email, @Positive, and so on — and then add @Valid in front of the @RequestBody parameter in your controller method signature, for example validating that a ShopSphere CreateOrderRequest has a non-null customer ID and at least one line item. Spring intercepts the request before it reaches your method body, runs the validation framework (Hibernate Validator, the standard implementation of the Bean Validation spec) against the deserialized object, and if any constraint fails, throws a MethodArgumentNotValidException before your controller code ever executes — meaning invalid data never reaches your business logic. Left unhandled, that exception results in a generic 400 Bad Request; in practice, you pair @Valid with a centralized @ExceptionHandler (see below) to turn it into a clean, structured error response listing exactly which fields failed and why.
How do you implement centralized exception handling with @ControllerAdvice and @ExceptionHandler?
@ExceptionHandler marks a method as the handler for a specific exception type thrown anywhere in a request's processing — if placed inside a single controller, it only catches exceptions from that controller. @ControllerAdvice (or its REST-specific variant, @RestControllerAdvice) turns that into a global, cross-cutting concern by applying to every controller in the application, so you write your error-handling logic exactly once instead of duplicating try/catch blocks in every endpoint. A typical setup for ShopSphere would have one class annotated @RestControllerAdvice with separate @ExceptionHandler methods for MethodArgumentNotValidException (mapping to 400 with field-level error details), a custom ProductNotFoundException (mapping to 404), a custom InsufficientInventoryException (mapping to 409 Conflict), and a catch-all Exception handler (mapping to 500 with a generic message that doesn't leak internals). This pattern keeps controllers focused purely on the happy path, gives you one place to enforce a consistent error response shape across the whole API, and avoids the common code smell of repeating the same try/catch scaffolding in every handler method.
How do you return the correct HTTP status codes using ResponseEntity?
If a controller method just returns a plain object, Spring defaults to a 200 OK response for any successful, non-null return — which is often not the status code you actually want. ResponseEntity<T> wraps your response body together with an explicit status code (and optionally custom headers), giving you full control: ResponseEntity.ok(product) for 200, ResponseEntity.status(HttpStatus.CREATED).body(newOrder) for 201 after creating a resource, ResponseEntity.noContent().build() for 204 after a successful delete with no body to return, or ResponseEntity.status(HttpStatus.CONFLICT).body(errorDetails) for 409 when, say, ShopSphere's inventory-service rejects an order because stock ran out. Using the correct status code isn't just cosmetic — API clients and tools (retry logic, monitoring dashboards, other services in the call chain) branch their behavior based on the status code class (2xx success, 4xx client error, 5xx server error), so returning 200 for everything, including failures, breaks that contract and forces callers to parse the body just to know if something went wrong.
What is content negotiation, and how does Spring handle it?
Content negotiation is the process by which a client and server agree on the representation format (JSON, XML, etc.) for a resource, typically driven by the client's Accept HTTP header stating what formats it can understand, and the request's Content-Type header stating what format the request body is actually in. Spring MVC handles this automatically through its HttpMessageConverter mechanism: when a @RestController method returns an object, Spring looks at the request's Accept header and picks a registered converter that can produce that format — by default, Jackson's converter handles application/json, which is why a Spring Boot REST API returns JSON out of the box without any extra configuration. The same mechanism works in reverse for incoming @RequestBody data, using the Content-Type header to pick the right converter to deserialize the payload. In most real-world APIs, including everything in ShopSphere, JSON is the only format ever configured, so content negotiation is invisible day-to-day — but it becomes relevant the moment an API needs to also support XML clients or versioned response formats via custom media types.
How would you version a Spring REST API, and what are the trade-offs between the common approaches?
The four common strategies each have real trade-offs, and a senior candidate should be able to argue for one rather than just naming them. URI versioning (/api/v1/orders, /api/v2/orders) is the most visible and cache-friendly, since the version is part of the resource identity, but it clutters the URL space and technically means /v1/orders/123 and /v2/orders/123 are different resources for the same underlying entity. Header versioning (a custom header like X-API-Version: 2) keeps URLs clean and resource identity stable, but is less discoverable and harder to test by just pasting a URL into a browser. Content negotiation via the Accept header (Accept: application/vnd.shopsphere.order.v2+json) is the most "correct" REST style since it treats versions as different representations of the same resource, but it's the least intuitive for API consumers and the hardest to explore manually. In practice, most production APIs — including how you'd evolve ShopSphere's order-service API without breaking existing mobile clients — favor URI versioning for its simplicity and operational visibility (it's trivial to route, log, and monitor by path), reserving header/content-negotiation approaches for organizations with mature API governance. The deeper judgment call interviewers are probing for is recognizing that versioning is fundamentally a backward-compatibility problem: additive, non-breaking changes (new optional fields) shouldn't need a new version at all, and only genuinely breaking changes (removing/renaming a field, changing a type) justify the operational cost of running two versions in parallel.
