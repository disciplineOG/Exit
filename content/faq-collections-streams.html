Most Asked Interview Questions: Collections & Streams API

ArrayList vs LinkedList HashMap Internals ConcurrentHashMap Comparator Streams Collectors
Why this matters

Collections and Streams questions show up in nearly every backend Java interview because they double as a proxy for how well you understand data structures and functional-style code under the hood, not just API surface. Interviewers use them to see whether you can reason about time complexity, thread safety, and memory behavior rather than just recite method names. This page collects the exact questions that come up again and again — pick ArrayList vs LinkedList, explain a HashMap resize, or fix a broken Collectors.toMap() call — with answers written to be interview-ready on their own.

Lists, Sets & Maps

What's the difference between List, Set, and Map, and how do you choose between them?

These are the three core shapes in the Java Collections Framework, and the choice comes down to what you need to guarantee about your data. List (implementations like ArrayList, LinkedList) is an ordered, index-accessible sequence that allows duplicates — use it whenever position and repetition both matter, like the ordered list of OrderItem objects on an Order. Set (implementations like HashSet, LinkedHashSet, TreeSet) guarantees no duplicate elements (as defined by equals()/hashCode()) and generally doesn't support index access — use it when the question you're answering is "have I seen this before," like a set of productIds already added to a Cart. Map (implementations like HashMap, TreeMap, LinkedHashMap) stores key-value pairs with unique keys — use it whenever you need to look something up by an identifier, like resolving a customerId to a Customer object in O(1) instead of scanning a list. A common beginner mistake is defaulting to List for everything and then writing a linear contains() scan where a Set or Map would have given O(1) lookups instead of O(n).

ArrayList vs LinkedList — what's the internal structure and when does that matter?

ArrayList is backed by a single resizable array of object references, so it gives O(1) amortized indexed access via get(i) because it's just array-offset arithmetic. LinkedList is a doubly-linked list of node objects, so get(i) is O(n) because it has to walk the chain from whichever end is closer. Where they invert is insertion/removal: adding or removing at the head or in the middle of an ArrayList is O(n) because every subsequent element has to shift; a LinkedList can do that in O(1) once you already hold a reference to the node (e.g. via an iterator), since it's just re-pointing a couple of links. In practice ArrayList wins for almost all ShopSphere workloads — iterating Order.items, building a List<Product> from a query result — because sequential access and cache locality (array elements sit contiguously in memory) dominate real-world performance; LinkedList is rarely the right default and is mostly useful when you specifically need a Deque with cheap head/tail operations.

How does a HashMap actually work internally — buckets, hashing, and treeification?

A HashMap stores entries in an internal array of "buckets." When you call put(key, value), the map computes key.hashCode(), runs it through an internal spreading function (XORing the hash with its own upper bits to reduce collisions from poor hash implementations), and uses hash & (capacity - 1) to pick a bucket index. If that bucket is empty, the entry is stored directly; if another entry already hashes to the same bucket (a collision), entries are chained together and compared with equals() to find or insert the right one. Historically each bucket was a linked list of entries, giving O(n) worst-case lookup if many keys collide; since Java 8, if a single bucket's chain grows to 8 or more entries (and the table has at least 64 buckets), that bucket is "treeified" into a red-black tree, dropping worst-case lookup in that bucket from O(n) to O(log n). This treeification is purely a defense against pathological hash collisions (accidental or adversarial) — a well-distributed hashCode() almost never triggers it, and buckets shrink back to a linked list if they drop below 6 entries.

HashMap vs Hashtable vs ConcurrentHashMap — what actually differs?

HashMap is unsynchronized and allows one null key and multiple null values — it's the default choice for single-threaded or externally-synchronized use, such as building a local Map<String, Product> cache inside a single request. Hashtable is a legacy class (predates the Collections Framework) that synchronizes every method with a single lock on the whole table, making it thread-safe but effectively single-threaded under contention, and it disallows null keys/values entirely — it should be treated as deprecated in new code. ConcurrentHashMap is the modern thread-safe answer: instead of one lock for the whole map, it uses fine-grained synchronization (bucket-level locking with CAS — Compare-And-Swap — operations for many updates) so multiple threads can read and write different buckets concurrently without blocking each other, and reads are largely lock-free. For something like a shared per-productId reserved-inventory counter map read and written by many threads in inventory-service, ConcurrentHashMap is the correct choice; plain HashMap under concurrent mutation can corrupt its internal structure (historically even causing infinite loops during resize) and Hashtable would serialize all access unnecessarily.

What ordering guarantees do TreeMap and TreeSet give you?

TreeMap and TreeSet are backed by a red-black tree (a self-balancing binary search tree) and always keep their elements/keys in sorted order — either the natural ordering defined by Comparable, or a custom Comparator supplied at construction time. This gives O(log n) for put/get/contains/remove, slightly worse than a hash-based map's average O(1), but in exchange you get sorted iteration for free plus navigation methods like firstKey(), lastKey(), floorKey(), ceilingKey(), and subMap()/headMap()/tailMap() range views. A good ShopSphere use case is a TreeMap<Instant, OrderEvent> for events belonging to a single order — you get chronological iteration automatically and can cheaply ask "give me all events after this timestamp" without sorting anything yourself. The trade-off is that every key must be mutually comparable (either implementing Comparable or covered by the supplied Comparator), or you'll get a ClassCastException at insertion time.

What does LinkedHashMap add over HashMap, and what is access-order mode?

LinkedHashMap extends HashMap but additionally threads a doubly-linked list through all the entries, so iteration order is predictable — by default that order is insertion order, unlike plain HashMap where iteration order depends on bucket layout and can even change after a resize. If you construct it with the three-argument constructor passing accessOrder = true, the linked list is instead reordered on every get()/put() so the most recently accessed entry moves to the end — this is the standard building block for an LRU (Least Recently Used) cache. Combined with overriding removeEldestEntry() to return true once the map exceeds a size threshold, a LinkedHashMap in access-order mode becomes a complete bounded LRU cache in a few lines, which is exactly how you'd implement a small in-memory price cache in catalog-service without pulling in an external caching library.

How does HashSet detect duplicates if it's backed by a HashMap?

HashSet is literally implemented as a thin wrapper around a HashMap internally — every element you add becomes a key in that backing map, with all values pointing to a single shared dummy constant object. Duplicate detection therefore uses the exact same mechanism as map key lookup: the element's hashCode() determines its bucket, and if another element already occupies that bucket, equals() is called to check whether they're actually the same logical value. This is precisely why overriding equals() without also overriding hashCode() breaks a HashSet — two objects that are "equal" by your equals() could still land in different buckets and both get inserted, silently violating the no-duplicates contract. For example, a HashSet<String> tracking productIds already added to a Customer's Cart only works correctly because String has a well-defined equals()/hashCode() pair based on character content.

What's the difference between fail-fast and fail-safe iterators, and what triggers ConcurrentModificationException?

Fail-fast iterators — used by ArrayList, HashMap, HashSet, and most core collections — keep an internal modCount (modification count) that's checked on every call to next(); if the collection was structurally modified (add/remove, not just a value update) by anything other than the iterator's own remove() method since the iterator was created, it throws ConcurrentModificationException immediately rather than risk returning inconsistent results. This commonly bites people who try to remove elements from a List<OrderItem> with a for-each loop instead of an explicit Iterator — the fix is to use iterator.remove() or a removeIf() call instead. Fail-safe iterators, by contrast, operate on a snapshot or a separately synchronized structure rather than the live collection — CopyOnWriteArrayList iterates over an immutable snapshot array taken at iterator-creation time, and ConcurrentHashMap's iterators are weakly consistent, meaning they tolerate concurrent modification without throwing but may or may not reflect updates made after iteration started. The trade-off is memory and staleness: fail-safe iteration avoids the exception but can give you a slightly outdated view of the data.

What are load factor and resizing in HashMap, and why do they matter for performance?

A HashMap's load factor (default 0.75) is the threshold ratio of entries to bucket-array capacity at which the map decides it's getting too crowded and triggers a resize — so with the default 16-bucket initial capacity, the map resizes once it holds more than 12 entries. Resizing doubles the bucket array's capacity and then rehashes every existing entry into its new bucket position (because the bucket index formula depends on capacity), which is an O(n) operation that temporarily doubles memory usage and pauses further inserts. A lower load factor means more wasted space but fewer collisions and faster lookups; a higher load factor packs entries tighter at the cost of longer collision chains. The practical interview-relevant takeaway is: if you know roughly how many entries a map will hold upfront — say, loading a fixed catalog of a few thousand Products into a Map<String, Product> at startup — you should size the initial capacity accordingly (new HashMap<>(expectedSize / 0.75f)-ish) to avoid paying for repeated resizes during a hot startup path.

Why should you never use a mutable object as a HashMap key without care?

A HashMap decides which bucket a key lives in at insertion time, based on that key's hashCode() at that moment. If you later mutate the key object in a way that changes its hashCode() or its equals() outcome, the entry is now effectively lost — a subsequent get() with an object that's logically equal will compute a different bucket index than where the entry was actually stored, so the lookup silently fails, and the entry becomes unreachable "garbage" sitting inside the map. For example, using a mutable OrderItem object as a map key and then changing its quantity field (if that field participates in equals()/hashCode()) after insertion would corrupt the map from the caller's perspective, even though nothing throws an exception. The safe pattern is to use immutable keys — String, boxed primitives, records, or a custom immutable value object whose fields never change after construction — or to guarantee by convention that a key's hash-relevant state is never mutated while it's in use as a map key.

How do you make a List or Map thread-safe without reaching for ConcurrentHashMap or CopyOnWriteArrayList?

Collections.synchronizedList(list) and Collections.synchronizedMap(map) wrap an existing collection so every method call is guarded by a single intrinsic lock on the wrapper — this is the older, coarse-grained approach that predates ConcurrentHashMap and effectively serializes all access, similar to Hashtable. It's still occasionally useful for simple cases with low contention, but it has a sharp edge: iteration is not automatically thread-safe even though individual method calls are, so you must manually wrap any iteration in a synchronized(list) block on the same lock object, or you risk a ConcurrentModificationException from a concurrent writer. In production backend code — say, a shared list of recently-processed Kafka event IDs in notification-service accessed by multiple consumer threads — the modern default is to reach for a purpose-built concurrent collection (ConcurrentHashMap, CopyOnWriteArrayList, ConcurrentLinkedQueue) instead, since they offer better throughput under contention and don't have the same iteration gotcha. Collections.synchronizedXxx() is mostly worth knowing as the "how would you retrofit thread-safety onto a plain collection" answer, not as a first choice for new code.

How do you decide between HashMap, TreeMap, and LinkedHashMap in a real system, and why is HashMap's capacity always a power of two?

Default to HashMap unless you have a specific reason not to — it gives the best average-case O(1) performance for arbitrary key lookups and is the right choice for something like a Map<String, Product> cache. Reach for TreeMap only when you need sorted iteration or range queries (like "all Orders placed before a given timestamp") and can accept O(log n) instead of O(1). Reach for LinkedHashMap when you need predictable insertion-order iteration for reproducibility or logging purposes, or access-order mode for an LRU cache, while still wanting near-HashMap performance. On the power-of-two question: HashMap always sizes its internal bucket array to a power of two (16, 32, 64, ...) because that lets it replace the relatively expensive modulo operation (hash % capacity) with a much cheaper bitwise AND (hash & (capacity - 1)) to compute a bucket index — this only produces a correct, evenly-distributed result when capacity is a power of two, which is also why HashMap silently rounds any capacity you pass to its constructor up to the next power of two.

How do you safely remove elements from a collection while iterating over it?

Calling list.remove() directly inside a for-each loop throws ConcurrentModificationException because the for-each loop is sugar over an Iterator that doesn't know about modifications made outside itself. The correct fix is to get the Iterator explicitly and call its own iterator.remove() method, which updates the iterator's internal bookkeeping (the modCount check) as part of the removal so no exception is thrown. In modern code the simpler answer is collection.removeIf(predicate) — for example, orderItems.removeIf(item -> item.getQuantity() == 0) — which handles the iterate-and-remove pattern safely and concisely in one call without you managing an Iterator by hand at all. A related trap: building a brand-new filtered list (via a stream and collect()) instead of mutating in place is often clearer and avoids the whole class of iterator bugs, at the cost of allocating a new collection.

Ordering & Comparison

Comparable vs Comparator — what's the difference and when do you use each?

Comparable<T> is implemented by the class itself and defines a single "natural ordering" via compareTo(T other) — for example, Product might implement Comparable<Product> to sort by productId by default. Comparator<T> is a separate strategy object with a compare(T a, T b) method that you define externally and pass to a sort call, so you can define as many different orderings as you need without touching the class itself — sort Order objects by total price in one place and by creation timestamp in another, without Order having any opinion on which is "natural." The rule of thumb: implement Comparable when there's one obviously correct default ordering for a type, and use Comparator instances (often built with the fluent Comparator.comparing() factory methods) for every other ordering, including ad hoc ones needed only at a single call site.

What does "natural ordering" mean and how do collections rely on it?

Natural ordering is whatever ordering a class defines for itself by implementing Comparable — it's called "natural" because it's the default a consumer gets if they don't supply an explicit Comparator. Sorted structures like TreeSet, TreeMap, and calls like Collections.sort(list) (the no-argument overload) or Collections.max(list) fall back to natural ordering automatically, calling each element's compareTo() method. This is why String sorts lexicographically by default (its compareTo() compares character by character) and why Integer sorts numerically — both implement Comparable with a sensible built-in ordering. If a class doesn't implement Comparable and you try to put it in a TreeSet or call the no-arg sort() without a Comparator, you get a ClassCastException at runtime because there's no ordering to fall back on.

Why must compareTo() be consistent with equals(), and what breaks in a TreeSet if it isn't?

TreeSet and TreeMap never call equals() to decide whether two elements are "the same" — they use compareTo() (or the supplied Comparator) exclusively, treating any two elements that compare as 0 as duplicates, even if equals() would say they're different objects. So if a class's compareTo() is not "consistent with equals" — meaning x.compareTo(y) == 0 doesn't imply x.equals(y) == true — a TreeSet can silently drop elements that a HashSet would have happily kept as distinct entries. A classic failure case: a Product class whose compareTo() only compares price but whose equals() compares productId — adding two different products that happen to cost the same price to a TreeSet<Product> results in only the first one being kept, because the second one's compareTo() returns 0 against the first and the set treats that as "already present." The fix is either to make compareTo() fully consistent with equals() (comparing the same identifying fields, with a tiebreaker on a truly unique field like productId if the primary sort key isn't unique), or to be aware that this trade-off exists and choose LinkedHashSet (which uses equals()/hashCode() like a regular HashSet but preserves insertion order) if you need uniqueness by equals() and still want stable iteration order.

How do you chain multiple comparators, e.g. with thenComparing?

Comparator has default methods designed specifically for chaining: Comparator.comparing(keyExtractor) builds an initial comparator from a field accessor, and .thenComparing(anotherKeyExtractor) appends a tiebreaker that only gets consulted when the primary comparison returns 0 (equal). This reads naturally for multi-field sorts — for example, sorting a List<Order> primarily by status and, within the same status, by placement timestamp: orders.sort(Comparator.comparing(Order::getStatus).thenComparing(Order::getPlacedAt)). You can chain as many thenComparing() calls as needed, and there's also .reversed() to flip direction and Comparator.comparing(keyExtractor, Comparator.nullsFirst(...)) style helpers for null-safe field comparisons. This composability is why modern code almost always builds comparators this way instead of hand-writing a multi-branch compare() method.

How would you sort a list of custom objects by multiple criteria?

The idiomatic approach is list.sort(comparator) or Collections.sort(list, comparator), building the comparator with the Comparator.comparing()/thenComparing() chain rather than implementing a standalone Comparator class or overriding equals()-adjacent logic. For example, sorting List<Product> by category ascending and then by price descending within each category would be products.sort(Comparator.comparing(Product::getCategory).thenComparing(Product::getPrice, Comparator.reverseOrder())). This is stable — Java's sort algorithms (Timsort for objects) preserve the relative order of elements that compare as equal, which matters when you're layering multiple sort criteria and want earlier tiebreakers to still hold for elements the later criteria can't distinguish. It's also strongly preferred over manually implementing compareTo() logic with nested if/else branches, which is both harder to read and easier to get wrong (e.g. inconsistent with equals()).

What is a PriorityQueue and how does it decide ordering?

PriorityQueue is a queue backed by a binary heap (stored internally as an array) that always returns the smallest element first according to natural ordering or a supplied Comparator — not FIFO (first-in, first-out) order like a regular queue. Insertion (offer()) and removal of the head (poll()) are both O(log n) because the heap only needs to maintain a partial order (each parent node is smaller than its children), not a fully sorted structure, while peeking at the head via peek() is O(1). A natural ShopSphere use is ranking pending Orders by SLA (Service Level Agreement) deadline — new PriorityQueue<>(Comparator.comparing(Order::getSlaDeadline)) — so that whichever worker pulls the next order always gets the most urgent one, without needing to sort the entire pending list on every pull. It's worth noting PriorityQueue is not thread-safe (use PriorityBlockingQueue for concurrent producers/consumers) and iterating it directly does not yield elements in priority order — only repeated poll() calls do.

Streams API

What is the Streams API, and how is a Stream different from a Collection?

The Streams API (introduced in Java 8) lets you express bulk operations over a sequence of elements — filtering, transforming, aggregating — as a declarative pipeline instead of a hand-written loop, and it's built to support both sequential and parallel execution with the same code. A Collection (like List or Set) is a data structure that actually stores elements in memory and can be iterated multiple times; a Stream is not a data structure at all — it's a one-time, on-demand computation pipeline over a source (often a collection, but also an array, a file, or an infinite generator) that produces elements on the fly as they're consumed. Because of that, a stream can only be traversed once: calling a terminal operation like collect() or forEach() a second time on the same stream throws IllegalStateException, whereas you can iterate the same List as many times as you like. For a beginner-friendly mental model: you get a stream from a collection (list.stream()), chain transformations, and end with a terminal operation that either produces a result or a side effect — the original collection is never modified by any of it unless you explicitly write back to it.

What's the difference between map and flatMap?

map() transforms each element of a stream into exactly one other element, producing a stream of the same size — for example, Stream<Order>.map(Order::getTotalPrice) turns a stream of Orders into a stream of prices, one per order. flatMap() is for when each element maps to zero, one, or many elements that you want flattened into a single stream, rather than a stream-of-streams — for example, given a Stream<Order> where each Order has a List<OrderItem>, orders.stream().flatMap(order -> order.getItems().stream()) gives you a single flat Stream<OrderItem> across all orders, instead of a Stream<Stream<OrderItem>> or Stream<List<OrderItem>> that map() would have produced. The rule of thumb: reach for flatMap() whenever your mapping function itself returns a collection or a stream and you want to work with the flattened element type afterward.

What's the difference between intermediate and terminal operations, and why does laziness matter?

Intermediate operations — filter(), map(), sorted(), distinct(), flatMap() — return a new stream and are lazy, meaning they don't actually execute any work when called; they just build up a pipeline description. Terminal operations — collect(), forEach(), reduce(), count(), anyMatch() — trigger the pipeline to actually run, pulling elements through all the intermediate steps element-by-element in a single pass, and once a terminal operation runs, the stream is consumed and can't be reused. Laziness matters because it enables short-circuiting: a chain like products.stream().filter(p -> p.getCategory().equals("Electronics")).findFirst() can stop as soon as one match is found instead of filtering the entire list first and then looking for the first result, which is a meaningfully different (and often better) execution shape than the equivalent imperative loop would suggest. It also means that if you build a stream pipeline but never call a terminal operation on it, none of the intermediate lambdas ever actually execute — a common source of "why didn't my filter run" confusion for people new to streams.

What are the most commonly used Collectors, and how do you use each one?

Collectors.toList() (or the newer Stream.toList()) collects elements into a List. Collectors.groupingBy(classifierFn) buckets elements into a Map<K, List<T>> keyed by whatever the classifier function returns — for example, grouping a List<Order> by Order::getStatus gives you all orders per status in one pass, and it can be combined with a downstream collector (like Collectors.counting()) to get counts per group instead of full lists. Collectors.partitioningBy(predicate) is a specialized two-bucket version of grouping that always produces exactly a Map<Boolean, List<T>>, splitting elements into "matches the predicate" and "doesn't" — useful for splitting Orders into paid vs. unpaid in one call. Collectors.joining(delimiter) concatenates a stream of Strings with an optional delimiter/prefix/suffix, handy for building a comma-separated list of productIds for a log line. Collectors.toMap(keyFn, valueFn) builds a Map<K, V> from stream elements, but throws IllegalStateException if two elements produce the same key — you fix that by supplying a third argument, a merge function like (existing, incoming) -> incoming, that tells the collector how to resolve key collisions instead of failing.

What does reduce() do, and when would you use it over a Collector?

reduce() combines all elements of a stream into a single result by repeatedly applying a binary combining function — for example, orders.stream().map(Order::getTotalPrice).reduce(BigDecimal.ZERO, BigDecimal::add) sums every order's total starting from an identity value of zero. The two-argument form takes an identity (the starting value and the result if the stream is empty) and a combiner; a three-argument overload adds a combiner function for use in parallel streams, where partial results computed by different threads need to be merged back together. In practice, prefer the purpose-built Collectors (like Collectors.summingInt()/summingDouble(), or Collectors.counting()) or the primitive stream methods (IntStream.sum(), DoubleStream.average()) whenever they cover your case, since they're clearer and often more efficient — reach for raw reduce() when you need a genuinely custom accumulation that doesn't map to an existing collector, like combining objects with custom merge logic that isn't a simple sum or list.

What are short-circuiting stream operations, and how do anyMatch/allMatch/noneMatch/limit differ?

Short-circuiting operations can produce a result without processing every element in the stream, which matters for both correctness (they work on infinite streams) and performance (they can stop early on huge finite ones). anyMatch(predicate) returns true and stops as soon as one element matches; allMatch(predicate) returns false and stops as soon as one element fails to match; noneMatch(predicate) returns false and stops as soon as one element matches. findFirst()/findAny() stop at the first (or any, in parallel) element found. limit(n) is a short-circuiting intermediate operation that only lets the first n elements flow through the rest of the pipeline. A concrete case: checking whether any Order in a huge batch has a payment failure — orders.stream().anyMatch(o -> o.getPaymentStatus() == PaymentStatus.FAILED) — stops the moment it finds one, instead of the O(n) worst case (and no early exit at all) you'd get from first collecting a filtered list and then checking if it's non-empty.

Why can a stream only be consumed once, and what's the risk of using stateful lambdas inside a stream pipeline?

A Stream models a single pass of computation over a source, not a reusable data structure — once a terminal operation runs, the stream is marked consumed internally, and any further operation on the same stream reference throws IllegalStateException: stream has already been operated upon or closed. If you need to run the same pipeline twice, you must build a fresh stream from the source collection each time (list.stream() again), not cache and reuse a Stream object. A separate, subtler senior-level trap is using a stateful lambda — one that reads or writes to shared mutable state outside the lambda, like incrementing an external counter or appending to a non-thread-safe List inside forEach() — because the Streams API doesn't guarantee an element-by-element execution order or thread confinement, especially once .parallel() is involved; that pattern can silently produce wrong counts, lost updates, or ArrayIndexOutOfBoundsException-style corruption depending on timing. The fix is to keep stream lambdas pure (no side effects on shared state) and use the appropriate terminal operation or collector — count() instead of a manual counter, collect(Collectors.toList()) instead of manually populating an external list — to get the result the API is designed to produce safely.

When do parallel streams help, and when do they hurt?

Calling .parallel() (or parallelStream()) splits the stream's work across multiple threads from the common ForkJoinPool and combines the results, which can help when you have a large amount of data, CPU-bound per-element work, and a data source that splits cheaply and evenly (like an ArrayList or an array) — for example, running an expensive fraud-scoring calculation across tens of thousands of Orders. It tends to hurt, or simply provide no benefit, for small collections (the overhead of splitting, thread coordination, and merging outweighs the work itself), for I/O-bound operations like calling payment-service over the network per element (parallel streams don't manage blocking I/O well and can starve the shared thread pool other parts of the application depend on), or for data sources like LinkedList that don't split efficiently. It also introduces subtle bugs if the stream's operations aren't stateless and side-effect-free — mutating a shared, non-thread-safe collection inside a parallel stream's forEach() is a classic race condition. As a default: measure before reaching for .parallel(), and prefer it only for large, CPU-heavy, easily-splittable, side-effect-free workloads.

What are Optional best practices, and what are the common anti-patterns?

Optional<T> is a container that may or may not hold a value, meant primarily as a return type to signal "this method might not have a result" more explicitly than returning null — for example, Optional<Customer> findByEmail(String email) makes the caller confront the missing-value case at compile time rather than risking a NullPointerException later. Good usage means chaining it functionally: customerRepository.findByEmail(email).map(Customer::getLoyaltyTier).orElse("STANDARD") reads cleanly and never unwraps early. The most common anti-pattern is calling .get() without checking .isPresent() first, which just relocates the null-pointer-style crash into an Optional wrapper and defeats the entire point — prefer .orElse(), .orElseGet() (lazy, for expensive defaults), or .orElseThrow() with a specific exception. Other anti-patterns: using Optional as a field type in an entity or as a method parameter type (it was designed as a return type, not for general-purpose use, and it isn't even Serializable), and wrapping a collection in Optional — an empty List already communicates "nothing found" without needing an extra wrapper.

Method references vs lambdas — when should you use each?

A method reference (ClassName::methodName or instance::methodName) is shorthand for a lambda that does nothing but call an existing method, and the compiler infers the functional interface shape from context — orders.stream().map(Order::getTotalPrice) is exactly equivalent to orders.stream().map(order -> order.getTotalPrice()) but shorter and arguably clearer about intent, since it's visibly just "call this method." Lambdas remain necessary whenever the logic is more than a single direct method call — combining multiple calls, using a constant, applying conditional logic, or referencing an outer local variable, e.g. products.stream().filter(p -> p.getPrice().compareTo(threshold) > 0) can't be expressed as a plain method reference because of the comparison logic. The four method reference forms worth recognizing are: static (Math::max), instance-on-particular-object (customer::getEmail), instance-on-arbitrary-object-of-a-type (String::toUpperCase, where the first stream element becomes the receiver), and constructor references (ArrayList::new). Prefer method references when they exist and read cleanly; fall back to lambdas the moment the body needs more than one expression's worth of logic.
