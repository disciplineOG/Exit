HLD #2: E-Commerce / Flash Sale System

Inventory Locking Optimistic vs Pessimistic Concurrency Redis Atomic Counters Async Order Queueing Backpressure Taxonomy Cache Pre-Warming Saga Pattern Rate Limiting & Bot Mitigation
Why this matters

A flash sale is the one scenario in ordinary e-commerce where "eventually consistent, mostly available" stops being an acceptable default, because the thing being protected — a fixed count of physical or limited inventory — has a correctness property (never sell more than exists) that no amount of horizontal scaling can relax away. Understanding this system deeply means understanding exactly where a distributed system is forced to trade throughput for a hard invariant, and where it can cheat that trade-off by moving work off the critical path instead. Get this wrong and you get the two failure modes that make headlines: oversold inventory that has to be apologetically refunded, or a storefront that falls over the instant the sale opens because every request tried to do a synchronous, lock-contending write at the same moment.

1. Why a Flash Sale Is a Different Design Problem

Steady-state e-commerce traffic is comparatively gentle: requests arrive smoothly, diurnal patterns are predictable, and autoscaling groups have minutes to react to load trends. A flash sale inverts every one of these assumptions. Traffic that was near-zero a second before the sale opens can jump 100-1000x baseline within the same second, because the demand isn't organically arriving — it's a crowd that has been refreshing a page or holding a countdown timer, all converging on the same endpoint at the same instant. This is a thundering-herd problem by design, not by accident.

Two properties compound to make this hard, and it's worth separating them clearly because they pull in opposite directions:

  • A hard consistency requirement: inventory is finite and specific. If 500 units of a product exist, exactly 500 (or fewer, never more) can be sold. This is not a case where showing a slightly stale follower-count or like-count is harmless — overselling means real orders that cannot be fulfilled, refunds, and reputational cost that is disproportionate to the technical shortcut that caused it.
  • An extreme availability/throughput requirement: the system must absorb a spike orders of magnitude larger than normal without falling over, and it must do so within a window that might be minutes, because the whole point of a flash sale is scarcity-driven urgency.

The tension is direct: the straightforward way to guarantee "never oversell" is to serialize access to the inventory count (one write at a time, strictly ordered), but serialization is exactly what caps throughput under extreme concurrency. Every technique in this design is, in one way or another, a way to preserve the correctness guarantee while pushing the serialization point somewhere narrower, faster, and further from the part of the system taking the brunt of the traffic.

This is a scaled-up version of a familiar problem

The inventory-decrement race is the same class of problem covered in distributed-systems-core under concurrent state mutation — but a flash sale is the extreme case where the naive fix (a database lock) is guaranteed to become the bottleneck, because concurrency isn't occasional, it's the entire premise of the event.

2. The Inventory-Locking Problem

The race condition in the naive approach

The obviously-wrong-but-instructive implementation is "check, then act" against the Inventory table (productId, warehouseId, availableQty, reservedQty):

// NOT safe under concurrency
SELECT available_qty FROM inventory WHERE product_id = 'prod-42';
// application code checks: available_qty > 0 ?
UPDATE inventory SET available_qty = available_qty - 1 WHERE product_id = 'prod-42';

This looks correct read top-to-bottom in isolation, but correctness under concurrency is not a property of one thread's code path — it's a property of every possible interleaving of many threads' code paths. With 10,000 concurrent Customers hitting checkout for a Product with 1 unit left, all 10,000 can execute the SELECT at nearly the same moment, all read available_qty = 1, all conclude "available," and all proceed to decrement. The database will happily execute 10,000 UPDATE statements (possibly driving the count negative, or requiring an application-side floor check that still doesn't prevent multiple successful "purchases" being recorded before anyone notices the count is wrong). The bug isn't in either statement individually — it's in the gap between them, during which the "check" result goes stale for every concurrent reader.

This is exactly the classic lost-update anomaly, and it's why "it worked in my local test with one browser tab" is meaningless evidence for this code path — the failure only appears under genuine concurrent access, which is precisely what a flash sale guarantees.

Solution A: Pessimistic row-level locking

The direct fix is to make the check-then-act sequence atomic by acquiring an exclusive lock on the row before reading it, so no other transaction can read-and-race until the first transaction commits or rolls back:

BEGIN;
SELECT available_qty FROM inventory WHERE product_id = 'prod-42' FOR UPDATE;
-- row is now locked; every other transaction requesting
-- FOR UPDATE on this row blocks here until we commit/rollback
UPDATE inventory SET available_qty = available_qty - 1 WHERE product_id = 'prod-42';
COMMIT;

SELECT ... FOR UPDATE tells the database to take a row-level exclusive lock as part of the read, not just the write, closing the gap where a stale read could be acted on. This is genuinely correct — no amount of concurrency can cause an overshoot, because the database itself is now the serialization point.

The problem is throughput. Every concurrent request for the same product now queues behind a single row lock, turning what should be a highly parallel workload into an effectively single-threaded one for that row. If each locked transaction (lock acquisition, decrement, commit, lock release) takes even a few milliseconds, the theoretical ceiling for one hot row is in the low thousands of operations per second — nowhere near what a 1000x traffic spike on a single popular SKU demands. Worse, waiting transactions hold connections open, which can exhaust the database's connection pool and start blocking unrelated queries against the same pool, turning one hot product into an outage for the whole storefront.

Solution B: Optimistic locking with a version column

Optimistic locking assumes contention is the exception rather than the rule and only pays a penalty when a conflict actually happens, rather than serializing every access up front:

SELECT available_qty, version FROM inventory WHERE product_id = 'prod-42';
-- application checks available_qty > 0

UPDATE inventory
SET available_qty = available_qty - 1, version = version + 1
WHERE product_id = 'prod-42' AND version = :versionReadEarlier;
-- if 0 rows affected, someone else updated first: retry from the SELECT

No lock is held between the read and the write. Instead, the WHERE version = :versionReadEarlier clause makes the update conditional on nothing else having changed the row in between. If another transaction won the race and updated the row first, the version no longer matches, zero rows are affected, and the application detects this and retries the whole read-modify-write cycle.

Under moderate contention this is a clear win — most requests succeed on the first try with no blocking at all, so throughput is much closer to the database's raw update capacity than the pessimistic approach. But it degrades badly under extreme contention, which is exactly the flash-sale regime: if 10,000 requests are racing for the last few units, the vast majority will fail their version check and retry, and those retries re-contend with the next wave of retries, producing a retry storm — a self-inflicted amplification of load where the system spends most of its capacity re-attempting work that will mostly fail again, rather than making forward progress. Optimistic locking assumes conflicts are rare; a flash sale on a scarce item is a scenario engineered to make conflicts the common case.

Solution C: Move the hot counter into Redis

The insight that actually resolves the tension is that the database doesn't need to be the arbiter of the hot counter at all. Redis is single-threaded for command execution, which means a single DECR is inherently atomic with no locking overhead — there's no interleaving to race against because commands execute one at a time, in order, by construction:

DECR inventory:available:prod-42
-- returns the new value atomically; if it goes below 0,
-- that request "lost" and should not proceed to checkout

This alone handles the decrement atomically, but a plain DECR can't express "decrement only if the result would stay non-negative" as a single operation — you'd be back to check-then-act if you read the value first. The fix is a Lua script, which Redis executes atomically as a single unit (no other command can run in the middle of it):

-- KEYS[1] = inventory:available:prod-42
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock and stock > 0 then
    redis.call('DECR', KEYS[1])
    return stock - 1
else
    return -1  -- sold out; caller must not proceed
end

Because the entire check-and-decrement happens inside one atomic Lua execution on a single-threaded server, this reproduces exactly the correctness guarantee of SELECT ... FOR UPDATE — no two callers can both see "stock available" and both succeed when only one unit remains — but at in-memory speed with no lock queue, no connection pool contention, and no disk I/O on the hot path. Redis can sustain tens to hundreds of thousands of such operations per second on modest hardware, which is the throughput regime a flash sale actually needs.

The trade-off is that Redis now holds a piece of state that must eventually be reconciled with the database of record. The typical pattern is: Redis is the fast, authoritative gate for "is there stock left, and did this request reserve a unit," while the database is updated asynchronously (often via the queue described in Section 3) to persist the final, durable record. This introduces a brief window where Redis and the database can disagree, which is acceptable as long as Redis is treated as the single source of truth for the decrement decision during the sale window, and the database write is guaranteed to eventually happen (not "may happen").

It's a common misreading to treat optimistic locking as strictly "better" than pessimistic locking because it doesn't block. It doesn't block, but under enough contention the aggregate work done by all the failed-and-retried attempts can exceed what a queue of waiting pessimistic locks would have cost, because every failed attempt already paid for a full read round-trip before discovering it lost. The right lens is: pessimistic locking pays cost up front in waiting, optimistic locking pays cost after the fact in wasted retries, and at flash-sale-level contention neither is as cheap as removing the database from the hot path entirely.

3. Queueing Instead of Processing Synchronously

Even with an atomic Redis decrement, synchronously handling every incoming "buy" request end-to-end — validate, reserve inventory, charge payment, create the Order, confirm — means every one of the 100-1000x spike of requests is doing real, non-trivial work on the request thread, including a call to an external Payment provider that the system does not control the latency of. The pattern that actually survives the spike is to shrink the synchronous critical path down to the bare minimum needed to make a correctness decision, and defer everything else.

Concretely: the checkout endpoint in order-service does only the atomic inventory check-and-reserve (the Lua script in Section 2), and if a unit was successfully reserved, it publishes an OrderPlaced event to a queue and immediately returns an acknowledgment to the Customer — something like "we've received your request, you'll be notified" — rather than a final "your order is confirmed" response. A pool of consumer workers in payment-service and inventory-service, sized to what the payment provider and the Order/Inventory tables can sustainably handle (not sized to match the spike), drains the queue at a controlled rate and performs the slower steps: Payment capture, order persistence, shipping kickoff.

This is a direct application of load leveling: the queue acts as a buffer that absorbs the burst and lets consumers process at a smooth, sustainable rate instead of being forced to scale instantaneously to match an instantaneous spike. It connects directly to the mechanics in async-messaging — the queue needs at-least-once delivery (a message is guaranteed to be delivered, but a crash or network blip between "processed" and "acknowledged" can cause the same message to be redelivered and processed twice) with idempotent consumers (each consumer must produce the same end result whether it processes a given message once or several times — typically enforced with the Payment.idempotencyKey, so a redelivered "charge this order" message doesn't double-charge the Customer or double-reserve the same unit). It also needs a dead-letter path: a separate queue that a message is automatically routed to after it has failed processing some configured number of times (a declined card, a payment provider timeout that never resolves), so a handful of permanently-failing orders don't sit at the head of the queue being retried forever and blocking every healthy order queued behind them.

The user experience genuinely changes, and that's the point

This is a real product trade-off, not just an implementation detail: the user no longer gets an instant "confirmed" response, they get an instant "accepted" response followed by an asynchronous confirmation (push notification, email, or a status they can poll). This is the correct trade during a spike because a synchronous confirmation for every request would require synchronous capacity for every request, which is precisely what the system cannot provide at 100-1000x baseline. Communicating this honestly in the UI (a countdown, a queue position, or just "processing your order") is what makes the asynchronous model feel intentional rather than broken.

3.1 The queueing/backpressure taxonomy

"Put it on a queue" is really a choice among several distinct strategies for what to do when arrival rate exceeds processing rate, and they trade off differently between latency, memory, and correctness. It's worth seeing them as one taxonomy rather than as unrelated tricks, because a flash sale typically uses more than one layer of it at once:

Backpressure / overload-handling strategies
  |
  ├── Do nothing (let the queue grow unbounded)
  |     -> smooths bursts perfectly, but memory grows without limit and
  |        latency for the last-in message grows without limit too --
  |        never acceptable on a checkout path with real users waiting
  |
  ├── Bounded queue + block the producer
  |     -> caller (the checkout request) blocks until there's room;
  |        this just moves the pile-up from the queue to blocked
  |        request threads/connections -- same problem, different location
  |
  ├── Bounded queue + reject/shed load (this design's checkout endpoint)
  |     -> once the queue (or the Redis reservation gate) is full/exhausted,
  |        new requests fail fast with a clear "sold out" / "try again"
  |        response instead of waiting -- correctness-preserving, and the
  |        fast Redis DECR check in Section 2 IS this: a full rejection
  |        the instant stock hits zero, no request left dangling
  |
  ├── Rate limiting the producer (Section 7)
  |     -> cap how fast requests are even allowed to attempt to enqueue,
  |        independent of queue depth -- protects against a burst arriving
  |        faster than the admission check itself can run
  |
  ├── Load leveling via async queue (this section)
  |     -> decouple arrival rate from processing rate entirely; a bounded
  |        number of consumers drain at a sustainable, constant rate while
  |        the queue absorbs the difference for a bounded time window
  |
  └── Priority/SLA-aware draining
        -> not all queued orders are equal (e.g. a VIP customer's order,
           or one closest to a promised delivery cutoff); drain in
           priority order instead of strict FIFO, the same PriorityQueue
           idea covered on the collections-internals page, applied to a
           durable message queue instead of an in-memory heap

The flash-sale design in this page actually layers three of these: the Redis gate in Section 2 sheds load the instant stock is exhausted (reject, not queue), the checkout-to-fulfillment hop in this section uses load leveling (queue, don't reject, because a reserved unit deserves to be fulfilled), and Section 7 adds rate limiting in front of both so the admission check itself is never overwhelmed.

4. Pre-Warming Caches Before the Sale Starts

A cache that is cold — empty, or evicted due to inactivity — is invisible during normal traffic because the first request that misses simply pays a one-time penalty populating it, and subsequent requests are fast. During a flash sale this dynamic is catastrophic instead of mild: the sale start time is a known, scheduled instant at which the entire spike arrives simultaneously, so if the cache is cold at that exact moment, the full 100-1000x request volume all misses at once and falls through to the origin (database, product service) simultaneously — which is worse than having no cache at all, because now every one of those requests also pays the overhead of a failed cache lookup on top of the origin hit, and the origin receives a thundering herd it was never sized for.

The fix is deliberate and simple: since the sale start time is known in advance, run a warming job minutes before the sale opens that proactively reads the hot keys — product detail pages, images metadata, the initial inventory count — into the cache, so that the very first wave of real traffic is already served from a warm cache. This is fundamentally different from organic cache warming (letting real traffic populate it) because organic warming assumes a ramp-up period during which occasional misses are tolerable; a flash sale has no ramp-up, it has a step function.

Pre-warming interacts with TTLs and eviction policy

Warming the cache five minutes early is wasted effort if the entries are configured with a two-minute time-to-live and expire before the sale actually opens, or if an LRU eviction policy under unrelated background traffic evicts the just-warmed keys before they're used. Pre-warming needs a TTL set to comfortably outlast the gap between the warming job and the sale start (or no expiry at all until the sale concludes), and ideally a separate cache instance or reserved capacity for sale-critical keys so they aren't competing for eviction priority with unrelated traffic. See caching-strategies for the general mechanics of TTL and eviction that this builds on.

5. Separating the Read Path from the Write Path

Not all traffic during a flash sale is a purchase attempt — the large majority is browsing: loading the product page, checking the countdown timer, refreshing to see if the sale has started, viewing images and descriptions. This read traffic is enormous in volume but has no correctness constraint remotely as strict as inventory — serving a product description that's a few seconds stale is harmless, unlike serving a stale inventory count that leads to overselling. The design implication is to physically and architecturally separate these two paths so they don't compete for the same resources:

  • Static assets and product pages behind a CDN: images, CSS/JS bundles, and largely-static product page HTML/JSON should be served from edge caches geographically close to users, so this volume never even reaches the origin infrastructure. This is the single highest-leverage thing to get right, because it removes the largest fraction of total request volume from the systems that actually need to be protected.
  • Product detail caching separate from the inventory counter: a product's title, description, images, and price change rarely and can be cached aggressively (minutes to hours) in a general-purpose cache layer or even the CDN. The inventory count changes on every successful purchase and must live in its own fast, atomically-updatable store (the Redis counter from Section 2). Conflating these — for example, caching the whole product object including its quantity field with one TTL — either makes the count stale (risking oversell if served too loosely) or forces frequent invalidation of the entire product object just because the count changed (defeating the purpose of caching the stable fields at all).

The net effect is that the purchase path — the part of the system doing hot, contended, correctness-critical writes — only ever sees traffic from users who have actually decided to buy, not the much larger population still browsing or refreshing. Without this separation, read traffic alone could saturate the same database connections and application servers the purchase path depends on, causing the write path to degrade even though none of that read traffic was itself trying to buy anything.

6. The Saga Pattern for Order Fulfillment

Once an Order moves past the initial inventory reservation, it typically spans multiple services or resources that cannot be updated in a single local database transaction: payment-service (talking to an external Payment provider), inventory-service (a decrement that should become durable, not just reserved in Redis), the Order record itself, and shipping/fulfillment kickoff. Distributed transactions across these boundaries (two-phase commit) don't scale well and don't fit well with an external payment provider that has no notion of participating in your internal transaction protocol. The Saga pattern solves this by breaking the overall operation into a sequence of local transactions, each with a corresponding compensating action that undoes its effect if a later step in the sequence fails:

Step 1: Reserve inventory (Redis DECR against Inventory.reservedQty,
         or a "reserved" status row)
Step 2: Create Order record (status = CREATED, then PENDING_PAYMENT)
Step 3: Charge Payment via provider (Payment.status: PENDING -> CAPTURED/FAILED)
Step 4: Confirm inventory decrement as final/durable (Inventory.availableQty--)
Step 5: Kick off shipping/fulfillment (Order.status -> SHIPPED)

If Step 3 (payment) fails (Payment.status = FAILED):
  -> Compensate Step 2: mark Order CANCELLED
  -> Compensate Step 1: release the reserved unit back to Inventory.availableQty

If Step 5 (shipping kickoff) fails after payment succeeded:
  -> Retry shipping kickoff (idempotent), do NOT unwind payment —
     compensate forward, not backward, once money has moved

The critical design decision in a saga is choosing, for each step, whether a failure should be handled by compensating backward (undoing prior steps) or retrying forward (because undoing would itself be more disruptive or impossible — refunding a Payment that already succeeded, for instance, is a much heavier operation than retrying a shipping API call). This is why the ordering in the pipeline above matters: inventory reservation happens before payment specifically so that a failed payment can cheaply release inventory that was only ever "reserved," not yet durably committed, whereas nothing after a successful payment should trigger an inventory-release compensation, because that would mean taking a Customer's money for an item no longer being reserved for them.

This composes directly with the queueing model from Section 3: each saga step is naturally implemented as a queue consumer that, on success, publishes the next step's event (InventoryReserved, PaymentCaptured, OrderShipped), and on failure, publishes a compensation message rather than throwing an exception that's invisible to the rest of the pipeline. The full mechanics of choreographed versus orchestrated sagas, and how compensating actions are tracked and replayed reliably, are covered in distributed-systems-core; the mechanics of making the Payment charge itself safe to retry without double-charging are covered in payment-systems-idempotency — the flash sale is simply the domain where the consequence of getting either wrong (a charged Customer with no reserved inventory, or reserved inventory nobody paid for) is maximally visible.

Reservation is a distinct state from a final decrement

It's worth keeping "reserved" (Inventory.reservedQty) and "sold" (a decremented Inventory.availableQty) as explicitly different states rather than collapsing them into one decrement. A reservation (the Redis DECR at request time) says "don't let anyone else take this unit while we find out if this Order will actually complete." Only after payment succeeds does that reservation become a final, durable sale. If payment fails and the two states were never distinguished, releasing the unit back to available stock requires re-incrementing a counter that other concurrent operations are also mutating — reintroducing exactly the kind of race this design was built to avoid. A short-lived reservation with an expiry (release automatically if payment doesn't complete within, say, 5-10 minutes) also protects against a Customer that reserves a unit and simply abandons the checkout flow.

7. Rate Limiting and Bot Mitigation on the Purchase Endpoint

A flash sale creates a strong, direct financial incentive for automated buying — scripts that hit the purchase endpoint far faster and more reliably than a human clicking a button, often to acquire scarce inventory for resale. This isn't an edge case to shrug off; unmitigated, bots can claim a disproportionate share of limited stock within the first fraction of a second, before most legitimate Customers have even finished loading the page. Protecting against this requires layering several distinct mechanisms, because no single one is sufficient on its own:

  • Per-customer/per-IP rate limiting on the purchase endpoint — commonly implemented as a token bucket: each account/IP has a bucket that holds a fixed maximum number of tokens, refilled at a steady rate (e.g. one token every few seconds), and each purchase attempt consumes one token; once the bucket is empty, further attempts are rejected until it refills. This bounds a single account/IP's burst rate without needing to track a sliding time window, blunts the simplest scripted attacks, and is easily defeated by an attacker with many accounts or many IPs.
  • A queueing/virtual-waiting-room step before checkout — admitting Customers into the purchase flow at a controlled rate (matching what the backend can sustain) rather than letting the entire spike hit the purchase endpoint simultaneously — protects the backend regardless of whether the incoming load is legitimate or automated, and has the side benefit of making the experience fairer and more predictable for real users.
  • CAPTCHA or proof-of-work challenges at the point of adding to cart or checking out add friction that is cheap for a human doing it once but expensive for a script trying to do it thousands of times per second, though they add real friction for legitimate users too and are an arms race against increasingly sophisticated bypass tooling.
  • Behavioral and device signals (request timing patterns too regular to be human, missing browser fingerprint signals, known data-center IP ranges rather than residential ones) can be scored to flag likely automation without necessarily blocking outright, feeding into a soft throttle rather than a hard reject that risks false-positiving real customers.

None of these are perfect in isolation, which is why production systems layer them: rate limiting handles the crude case cheaply, a waiting-room step caps absolute throughput to what the backend can handle regardless of traffic legitimacy, and challenge/behavioral signals raise the cost of automation without fully relying on any single signal being unbeatable. The rate limiter here shares the same first-principles grounding as the general resilience patterns in resilience-fault-tolerance — including circuit breaking, which stops calling a downstream dependency (like the payment provider) entirely once it's failing past a threshold, rather than continuing to send it doomed requests — a flash sale is simply the scenario where the "what if load exceeds capacity by orders of magnitude" question stops being hypothetical. Input validation and secrets handling for the purchase endpoint and payment credentials specifically are covered in security-hardening-owasp.

Concepts Worth Being Able to Explain From First Principles

Why does "check quantity, then decrement" fail even if each individual SQL statement is correct?
Correctness under concurrency isn't a property of a single thread's sequence of statements — it's a property of every possible interleaving across all concurrently executing threads. The SELECT and the UPDATE are each individually valid SQL, but nothing prevents another transaction's SELECT from executing in the gap between this transaction's SELECT and its UPDATE. If ten requests all read "quantity = 1" before any of them commits a decrement, all ten will independently conclude the item is available and proceed, because each one's decision was based on a read that became stale the instant a concurrent transaction also read it. The fix always involves closing that gap — either by locking the row so no other reader can even take a stale read (pessimistic), by making the write conditionally fail if anything changed since the read (optimistic), or by making the read-and-decrement a single atomic operation (Redis DECR/Lua) so there's no gap to race into in the first place.
Why does optimistic locking perform worse than expected under extreme contention, given that it avoids blocking?
Optimistic locking is designed around the assumption that most attempts will succeed on the first try and conflicts are the exception — it trades the cost of blocking for the cost of occasionally redoing work. Under moderate contention this assumption holds and it outperforms pessimistic locking. But when thousands of requests are racing for the last few units of an item, the assumption inverts: most attempts will fail their version check, because by definition only as many can succeed as there are units left. Every failed attempt still paid for a full read round-trip and a failed write attempt before discovering it lost, and then it retries, competing with the next wave of already-failing retries. The aggregate work done across all the doomed attempts can exceed what a bounded queue of waiting pessimistic locks would have cost, because pessimistic locking never does wasted work — it just waits.
Why is a single Redis DECR not enough to safely handle inventory, and what does the Lua script add?
A plain DECR is atomic in the sense that Redis will never lose or misapply a decrement under concurrent callers — but atomicity of the decrement alone doesn't express the business rule "only decrement if the result stays non-negative." If the application reads the current value first, checks it's positive, and then issues DECR as a separate step, that reintroduces exactly the check-then-act gap that caused the original race, just relocated to Redis instead of the database. A Lua script solves this because Redis executes the entire script as one atomic unit — no other client's command can execute in the middle of it — so the read-check-decrement sequence becomes indivisible, reproducing the guarantee of SELECT FOR UPDATE without needing a lock, because there's genuinely nothing else running concurrently with it on Redis's single command-execution thread.
Why does moving the counter to Redis create a new problem of its own, and how is it managed?
Redis becomes a second source of state for inventory that must eventually agree with the database of record, and there's a window during which they can disagree — for example, if the process that's supposed to asynchronously persist a Redis decrement to the database crashes before doing so. This is managed by treating Redis as authoritative for the fast admission decision (did this request get to reserve a unit, yes or no) during the sale window, while guaranteeing the database write happens eventually via a durable queue with retries, rather than a fire-and-forget call. The consumer that performs this persistence must also be idempotent, since at-least-once delivery means the same "persist this decrement" message might be processed more than once, and a non-idempotent handler would double-count the decrement in the database even though Redis only decremented once.
Why does accepting the purchase request into a queue and returning an immediate acknowledgment actually help, rather than just delaying the same amount of total work?
It doesn't reduce the total amount of work the system eventually has to do, but it decouples the rate at which work arrives from the rate at which it's processed. Without a queue, every one of the spike's requests must be fully handled — including a call to an external payment provider — on a request thread at the moment it arrives, which means the system's peak capacity requirement is dictated by the spike itself. With a queue, the synchronous path only does the minimal, fast, atomic inventory check, and a fixed-size pool of consumers drains the queue at a rate matched to what downstream systems (payment provider, order database) can sustainably handle. The queue's depth absorbs the difference between arrival rate and processing rate, so the system needs to be provisioned for sustainable throughput, not peak instantaneous throughput — at the cost of the user getting an "accepted" response before a "confirmed" one.
Why must a Saga's compensating actions be direction-aware — why not just always roll everything back on any failure?
Not all steps are equally reversible, and treating them as if they were leads to worse outcomes than the failure itself. Releasing a reservation that hasn't been paid for is cheap and safe — nobody has been charged, so undoing it has no external side effect beyond making the unit available again. But unwinding a step after a payment has already succeeded means issuing a refund, which is a heavier, sometimes delayed, and user-visible operation, and doing it reflexively for a downstream failure that has nothing to do with the payment (a shipping API hiccup, for instance) creates unnecessary refund-and-recharge churn for the customer. The general rule is to compensate backward only for steps that are cheap and safe to undo and haven't yet had irreversible external effects, and to retry forward (with idempotent retries) once a step's effects are no longer cheaply reversible.
Why is layering rate limiting, a waiting room, and challenge mechanisms necessary instead of picking the single best one?
Each mechanism defends against a different shape of abuse and has a different failure mode when used alone. Rate limiting per account or IP is cheap but trivially defeated by an attacker with many accounts or many IP addresses. A waiting-room admission step caps the absolute rate at which requests reach the purchase endpoint regardless of whether the traffic is legitimate or automated, which protects backend capacity unconditionally, but doesn't by itself stop bots from occupying a disproportionate share of the admitted slots. Challenge mechanisms raise the cost of automating a single attempt but add friction for real users and are subject to an ongoing arms race with bypass techniques. None of them close every gap alone; together, they raise the total cost and reduce the total throughput available to automated actors while keeping the experience workable for people, which is the realistic goal — the aim is to make abuse expensive and rare, not to make it mathematically impossible.
